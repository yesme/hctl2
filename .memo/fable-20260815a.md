## 阻断级问题（high）

### H1 无 Run 轻量路径要求的「评审 Receipt」没有任何合法写入者

- File: task.md:63、task.md:51、connections.md:93 ↔ run.md:30、docs/design/README.md:12
- 无 Run 路径把「精确 ReviewSubjectRef 的评审 Receipt」列为 CompleteTaskIntent 的必需输入；但 Verdict/Receipt 的所有权与写入合同全部在 Run 模块（「只有 Run reducer 与 control/core 校验事务可写」），其产生流程（Gate/Seat/计票/quorum）全部以 Run 存在为前提。project.md:103 封死 Room 签发，harness.md:29 封死 Proposal 升格。于是无 Run 时：评审由谁发起、用什么类型化命令提交结论、reviewer/作者分离是否适用、control/core 以何种事务写出这份 Receipt，均无定义。delivery.md 纵向切片 A（B2 首次自举入口）第 4-5 步直接依赖这条未定义路径，契约测试矩阵也没有覆盖它的任何用例。
- Suggestion: 三选一并全链同步：(a) 在 Receipt 的 owner 侧显式定义无 Run 评审的类型化命令（如 SubmitReviewVerdictIntent）及其 actor/权限/事务；(b) 把无 Run 路径的「评审 Receipt」改为不含 Receipt 的证据形态，由 CompleteTaskIntent/TaskCompletionReceipt 一次收口；(c) 规定无 Run 评审必须经最小 Run 承载。并为该路径补至少一个契约测试失败用例。

### H2 Attempt 状态机禁止 Pending→Lost，与连接恢复合同直接矛盾

- File: run.md:61 ↔ connections.md:130
- connections.md 失败恢复表无条件规定「执行身份、lease 或 generation 无法证明 → Attempt 进入 Lost」；但 run.md 的合法边只允许 `Pending → Running/Failed/Cancelled`，Lost 仅能从 Running/WaitingForInput 进入。真实场景：dispatch outbox 已提交、agentd 预留/激活 ACK 丢失、control 崩溃恢复——Attempt 仍在 Pending 而执行可能已启动且身份不可证明，两份规范给出互斥指令。对照 RoomInvocation 显式允许 `Pending → Interrupted`（project.md:65），应属 run.md 遗漏。
- Suggestion: 为 Attempt 增加 `Pending → Lost` 合法边；或把 connections.md:130 限定为已确认激活的执行，并为「Pending 且结果未知」单独指定收口终态。

## 需要收口的问题（medium，24 条）

### A. 合同矛盾与措辞冲突

1. **system.md:82「adapter……写成功 Receipt」违反单写者合同**——Receipt 只能由 control/core 校验事务写入，adapter 只投递/回读（run.md:30、project.md:29）；应改为「adapter 回读确认后，control/core 才能写成功 Receipt」。
2. **AdoptTaskRevisionIntent 前置只写了外部来源场景**（task.md:29 无条件要求 Snapshot/BindingRevision）——connections.md:48 把同一命令用于 Room 提案采纳，纯本地 Task 无法满足该前置；应限定适用条件或拆成两条命令。
3. **跨模块 Request 字段词汇两套并存**（connections.md:99 的 `dedupe root / affected_revision_ref / blocked_scope` vs project.md:71 的「根因 / blocking ref/version」）——去重与 Supersede 判定无法机械映射，应统一为一处定义、他处引用。
4. **合并/交付到目标分支没有显式 owner 和命令**（delivery.md:61、harness.md:51、system.md:80）——切片 B 第 7 步与 core 校验都预设发生了合并，但四模块无 merge/push 命令，ExternalEffectIntent 又只覆盖「Git/SCM 以外」。harness.md:51 的回读校验为「HCTL 外完成 + core 校验」留了可实现路径，但 owner、授权与 Git 副作用的 outbox 纪律归属需要显式写出。

### B. 一等对象缺定义 / 缺写入合同

5. **TerminalGateway 与 attach provider 无 owner**（system.md:12,29 使用，harness.md 从未定义）；system.md 端口叫「Harness」、harness.md 叫「HarnessAdapter」，命名也不一致。
6. **Skill 无任何模块定义**——却被 Gate 计票要求校验「required Skill refs+digests」（run.md:69）、进入 Context 组装序（project.md:55）和存储拓扑（system.md:99-100）；其身份、Revision、digest 口径、写入者全部缺失。
7. **Gate 不在 run.md 对象表**；Gate/review 策略存放在 WorkflowRevision、Run Manifest 还是独立 policy 对象无定论；quorum-unreachable 之后 Obligation/Seat/Run 如何推进没有下文（run.md:69）。
8. **project.md 对象表约半数没有写入合同**——Participant/ProjectRoleBinding、ContextManifest/ContextBundle、Repo/RepoInstance 的创建/冻结命令缺失，而 Gate 硬性依赖「彼此独立的逻辑 Participant」。
9. **AttachDescriptor 无签发命令**（harness.md:83 定义了字段但无人签发），CLI 却要求「必须指向精确 descriptor」（delivery.md:28）；TerminalBundle 创建规则同缺。HarnessDefinition/Installation 可由 system.md:35 的 discovery/install 机制覆盖，属可接受的共享机制引用。
10. **「本地 TaskSource」在 task.md 中不存在**（delivery.md:12 承诺交付）——task.md 把 TaskSource 定义为外部连接，`local` 只是字段权威模式；指纯本地 Task 还是本地 provider 适配器，两种对象模型完全不同。
11. **ArtifactRevision 作为评审 subject 的摘要字段集未定义**（grok Issue 1 残留半边）——project.md:59 只说「至少固定」六项；ChangeSetRevision 的 `revision_digest` 与 5 字段评审 subject 摘要是否同值也未写明（harness.md:47-49）。

### C. 状态机与恢复路径缺口

12. **Attempt `ResultProposed` 没有任何出边、终态集合未列举**（run.md:61）——准入拒绝无 → Failed 边，准入成功无终态，「修正提交新 Proposal」（harness.md:29）回到哪个状态未定义；按现文实现每个成功 Attempt 永久停在 ResultProposed。
13. **Run 状态机缺边**（run.md:32）——Cancelling 唯一出边是 Cancelled（引擎失联即永久卡死）；Paused 无 → Failed；Starting/Pausing/Cancelling 均无法进入 Superseded。叠加 task.md:51「非终态 Run 存在时 Complete/Cancel 一律拒绝」，卡死的 Run 会永久阻塞 Task 终态。
14. **Request 的 deadline/default policy 无定义，Expired 后无收口路径**（connections.md:99、project.md:30）——Request 到期时被阻塞的 Seat/Attempt/Invocation 收到什么信号、如何收口，全文没有交代。
15. **Lost 旧 writer 与 worktree 复用规则缺失**（harness.md:35、connections.md:130）——静默不可证明时，未禁止在同一 worktree 上授予新写租约；僵尸进程的写入会混进新租约下封存的 ChangeSetRevision，破坏证据归属。

### D. 机制可实现性

16. **`control_writer_generation` 的持久位置未定义**（system.md:109,119）——恢复顺序「先推进 generation、后打开 SQLite」在 generation 存于 SQLite 的常规实现下不可按写执行；7 步恢复序列也未区分 control 与 agentd 两个进程的执行主体。
17. **agentd 单 owner 租约无互斥机制**（system.md:111）——「RuntimeBackend ownership scope」粒度未定义；租约由 control 记账则旧 agentd 不知自己失权，tmux/Zellij socket 对同用户进程开放，物理上无人拦截旧 agentd 的输入/停止；缺少与 control.lock 对等的资源侧排他原语。
18. **Project 聚合的权威存储在 SQLite 与 Git 之间不明**（project.md:27 写入者只有 control；system.md:91 把共享 Project 配置判给 Git+core）——多 clone 各自的 control writer 并发修改 Git-tracked `projects/` 时的冲突与收敛没有任何合同，未决清单也没有列。
19. **Gate 评审分离所需的身份链不完整**——ChangeSetRevision 无作者/producer 字段，producer 经 ResultProposal owner 可回溯，但到逻辑 Participant 的映射（AttemptSpec 冻结字段不含 Participant）与「彼此独立」的判定标准（run.md:69）缺失；单用户第一阶段「三选二」的三个独立 reviewer 从何构成无法实现。
20. **`~/.hctl2/` 用户级可变存储被多 RepoInstance 共享而无锁、无版本合同**（system.md:99）——WorkerProfile 的 immutable revision 持久在哪一侧、跨实例引用是否同一身份，没有答案。
21. **外部排序写回强制要求 provider remote token**（task.md:82）——Linear/GitHub 的排序 API 普遍不提供乐观并发令牌；该原语是否存在未列入 Spike 验证项，也没有无令牌时的降级合同。

### E. 交付与验证面

22. **Harness 适配器没有「至少一个通过完整契约测试」的出门条件**（delivery.md:14 只要求能力探测，而两条切片都依赖可执行的 HarnessAdapter）；「OpenCode 是第一阶段目标」这一范围决定只写在非规范 evidence（implementation-evidence.md:443），违反「范围统一记录在交付文档」。
23. **契约测试矩阵未覆盖共同规则第 4 条的大部分非完成信号**——「Run 终态 / Git commit / CI 绿色 / 进程退出不完成 Task」均无失败用例；「同一 Task 最多一个活动 Run」「Memo 只由用户发布」「Artifact current pointer 只由 Publish 推进」「digest JCS 规范化」也没有验证手段，与 delivery.md:102 的自我要求不符。
24. **implementation-evidence 的「HCTL 的取舍」小节以规范口吻新增产品规则**（implementation-evidence.md:413-424）——其中「响应式依赖只用于准入前发现」「disposer 只能撤销注册」「第一阶段只允许第一方或经审计的进程内扩展」等约束只存在于该非规范文档，违反「evidence 只记录来源 / 不得反向定义产品」；应把净新增规则移入 system.md/delivery.md。
