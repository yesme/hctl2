# 构建确定性与 Buck2（打包与工具链讨论）

> 日期：2026-08-27<br>
> 对象：`src/` Cargo workspace 与 `src/packaging/dependencies` 的现行打包；草案约 v0.13.1 及其后的运行包/源码包拆分<br>
> 状态：Informative · 讨论备忘，不改规范。实现若采纳，另走转向并钉 Buck2 commit。<br>
> 来源：构建平台调研、Tuwunel Darwin 工具链问答、所有者对「确定性不够」的判断。文中「所有者」是立场压缩；其余为工作笔记。

## 怎么来的

通读设计并更新仓库之后，所有者要求调研 Bazel 一类构建平台。讨论从「Tuwunel 在 Mac 上为什么用 rustc 1.95」落到「Linux / Darwin 是否必须同一把编译器」，再落到真正的选择理由：不是为了编聊天服务器，而是现有打包**确定性不够，违反工程实践**。所有者明确要上 **Buck2**。

## 所有者的判断

1. **Linux 和 Darwin 是不同的构建。** 两边的 toolchain 版本不必一致。Darwin 上 Tuwunel 可以用 1.98，只要编译通过、该平台测试通过。钉死版本，不要漂成 `stable`。
2. **选 Buck2 不是因为 Tuwunel。** 是在整段打包/工具链过程里看见输入没进产物身份、宿主机工具链靠 PATH 和事后 tsv 记账——确定性是纪律不是机制。Buck2 要兑现的是「构建是函数」这条实践。
3. **调研范围是整个产品构建**（跨平台、toolchain、多语言），不是某一个上游包。

## 现行构建实际在做什么

三件活已经分开，没有总图：

| 活 | 现在 |
| --- | --- |
| 第一方代码 | `src/` Cargo workspace（`agentd` / `tool` / `web-server` / `protocol`），`rust-toolchain.toml` = **1.98.0** |
| 上游运行时 | `packaging/dependencies`：按 target 钉 URL/SHA，打原生离线包 |
| 开发机工具 | rustup、Xcode/`xcrun`、Homebrew bison/pkgconf、apt；脚本约定，不是图里的目标 |

三个发布 target：`linux-x86_64`、`macos-aarch64`、`macos-x86_64`。官方有包的用官方包（Linux 上的 Tuwunel、各平台 Vikunja/Dagu/Element Web）；没有官方 Darwin 包的 Tuwunel、以及 tmux，从锁定源码编。

## Tuwunel 与两套 rustc（事实，不是选型理由）

锁定源码 [`v1.9.0 / 5b366914`](https://github.com/matrix-construct/tuwunel/tree/5b3669144219d5d4c0774743c84191b476f1b54f) 的 `rust-toolchain.toml` 写着 `channel = "1.95.0"`，并注明这是该项目的权威工具链。Darwin 两个 target 在文件里是注释，只表示 rustup **不会自动下载** `*-apple-darwin` 标准库，不是源码不能编 Mac。

因此：

- Linux：拿官方 deb，不现场编，碰不到 rustc。
- Darwin：解开同一份源码 tar，**不改上游 src**。`prepare_source_tree` 只有校验哈希和解压。改的是我们的 cargo 调用：`rustup target add` 补上 Darwin std；`--no-default-features` 后自选 feature（关掉 `io_uring` / `systemd` / `jemalloc`，另开 `direct_tls`）；`LIBCLANG_PATH` 指向 Xcode；编完改 Mach-O `@loader_path`、ad-hoc 签名、核对 minos。feature 写入 `tuwunel-features.txt`。

**1.95 对齐的是上游那份 toolchain 文件**，不是「Linux 官方包是 1.95 所以 Mac 必须 1.95」。Linux 包碰巧也是那份文件编的。两套 rustc 只出现在 **Mac 打包机**上：1.95 编 Tuwunel，1.98 编 HCTL2（含随包 `hctl2-web-server`）。日常在 `src/` 开发只要 1.98。用户装好的离线包不需要 rustc。

1.95（2026-04-16）到 1.98（2026-08-20）隔三个稳定版。对打包有意义的主要是 1.97 默认 v0 符号修饰、Cargo 警告配置，以及用新 rustc 编旧 lockfile 一般能过、但不保证和上游 CI 字节同构。所有者已判定：不要求跨平台同构。

## 确定性缺口（选 Buck2 要对上的那件事）

已经有的是**事后记账**：下载 SHA、`MANIFEST.sha256` / `PAYLOAD.sha256`、Mac 的 `macos-build-environment.tsv`（事后抄 rustc/clang/make/macOS 版本）。缺的是**事前约束**：没声明的不准参加构建；参加了的必须进入产物身份。

Darwin 上 `TUWUNEL_BUILD_INPUT_SHA256` 等于源码 tar 的哈希，**不含 rustc / clang / SDK**。换 Xcode、换 PATH 上的 rustc，源码哈希仍对得上。官方 zip/deb 钉哈希的那一段是确定的；一进入自己编（Tuwunel、tmux、`hctl2-web-server`），确定性就变成纪律。

宿主机漏进动作的东西包括：`xcrun` 的 clang 与 libclang、`require_command clang`、Homebrew bison/pkgconf（只核 formula 版本字符串）、Linux 上「支持范围内最旧 glibc」的文字约定、两套 rustc 和 Darwin feature 写在 shell 变量里——没有「编译器变了旧产物必须作废」的机械关系。

多 harness 自举时，这种漂移会看起来像代码 bug。这和产品自己反对的失败同类。

## 构建平台对照（压缩）

封闭图（Bazel / Buck2 / Pants）：构建当纯函数；工具链也是输入；适合多语言、按平台分叉。Bazel 9 + `rules_rust` 生态最大，公开口径偏大团队。Pants 偏 Python。Buck2 核心 Rust、规则全在 Starlark、入门即 `rust_binary`、Apache-2.0/MIT、Reindeer 把 Cargo 依赖生成 `BUCK`；**没有稳定 tag**，内部跟 HEAD，开源用 `latest` 预编译或 DotSlash 钉进仓库；**本机步骤默认不沙箱**，封闭性要接 Remote Execution 才硬；prelude 与内部同一份，工具链未开源。

任务编排（Nx / moon / just）：不管 `rustc` 的每一个 crate。Nix 钉机器上有什么，可给 Buck 喂 toolchain，不是 Cargo 的替代。Earthly 是容器步骤，和「桌面发行不进 Docker」不是一条路。第一方代码继续用 Cargo 当语言构建器仍然成立；Buck2 要取代的是「没有总图、输入靠 PATH」。

## 若上 Buck2：要兑现什么

选择理由是工程实践，兑现形态应是：

- Buck2 自身用 DotSlash / 审过的 commit 钉死，和 Tuwunel 同一纪律。
- `Cargo.toml` / `Cargo.lock` 仍是 crate 依赖的事实源；`BUCK` 由 Reindeer（或同类）生成，不两份手写图。
- **每个发布 target 是 configuration**：toolchain、feature、链接基线按平台分叉，不建成「全世界同一把 rustc 的一个 Tuwunel 目标」。
- rustc / clang / SDK 做成声明的 toolchain 目标（钉哈希下载，或 Nix 提供再喂给 Buck）。没有远程执行时，不能假装 `buck2 build` 会挡住没声明的 `xcrun` clang。
- 第一方 crate、自己编的 Tuwunel / tmux / web-server 进图；官方包继续 `http_archive` + SHA。
- 清单从「编完抄环境」改成动作 digest 的投影。Mach-O `@loader_path`、签名、minos、Intel 必须在 Intel 上编，仍是我们的规则，prelude 不会自带。
- Workbench / Electron 等壳定了再决定是否进图。

成功标准：`buck2 build //apps/hctl2-agentd:hctl2-agentd` 与 `buck2 build //packaging:<target>`；改 Darwin 的 rustc 会使该平台产物 digest 失效；开发者能问图而不是读 tsv。切默认之前，Cargo + 现有打包脚本仍是能打出发行物的路。

## 与先前相关判断的关系

Darwin Tuwunel 改钉 1.98 **不依赖**先有 Buck2，可以仍是 `targets/macos-*.sh` 里的配方变更。Buck2 要收的是「输入进身份」整条实践；Tuwunel 只是最先掀开缝的那一处。

OS 沙箱（执行面、Harness 入场券）是另一件事，见 [grok-20260824a](./grok-20260824a.md)。本文的确定性是**构建面**：编产品和编上游依赖时，宿主机漏进动作的工具链。不要把两套沙箱写进同一个门票。

## 尚未落地（实现，不是再争论要不要 Buck2）

1. 仓库钉 Buck2 + prelude commit / DotSlash。
2. 第一方 Rust 进图，Reindeer 生成 third-party；保留 `cargo test --locked` 作对照直到对得上。
3. 按 platform configuration 收 Tuwunel / tmux / web-server；官方包保持哈希。
4. Darwin Tuwunel 是否改为 1.98.0：所有者原则已定（过编译和该平台测试即可），改配方时把 rustc 写入该 target 的构建输入。
5. 无远程执行时，toolchain 目标如何强制（钉死的 rustup 发行物 vs Nix）。不上执行集群就把封闭性写在「钉死的 toolchain」，不要写在「Buck2 会替你沙箱」。
