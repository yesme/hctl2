## 仓库是什么

这不是代码仓库，是一份已经写到可执行合同精度的设计基线。权威版本是草案 v0.10.2；根 README 也写明了：没有可安装应用、CLI、构建或测试。约 3800 行 Markdown（设计正文 + 合同层 + 证据 + memo）。v0.7 以来大约三十次提交，语义变更单独成 commit 并标 `(semantic change)`。

下面评的是这份规范本身，不是还不存在的实现。

## 0.7 以来在修什么

主线不是功能加码，是两次摆动后的收口：先删过猛，再分层；然后把存储和部署从「clone 里的本地 IDE」改成「用户级控制面」。

| 版本 | 做了什么 |
| --- | --- |
| **v0.7–0.8** | 收敛成四模块。0.8 为了去平行权威，把愿景层一起删了，文档变成纯合同。三轮评审（kimi / grok / fable，合计 2 阻断 / 24 中 / 47 低）把补丁链问题摊开。 |
| **v0.9.0** | 把愿景加回来。原则写得很清楚：**权威去重只针对合同，不针对解释。** 四阶段链「意图 → 承诺 → 治理 → 运行」作为心智模型恢复，并加一句消解误读：一件事不必走完四个阶段。 |
| **v0.9.1** | 设计层 / 合同层分家；75+ 散概念按六族收到 28 个复合名；立命名门槛。这是文档方法论成型点。 |
| **v0.10.0–0.10.2** | 真正的架构转向：4 场景 × 3 类数据立法；三面架构；第四模块从 Harness 正名为 Agent；控制面升到用户级；chat server 拥有消息 content；Board 上移 Repo 级；砍掉 per-clone 物理账本，变成「一本账 + Git」。 |

0.7 的 kimi/grok 清单里那些真 bug——`ChangeSetRevision` / `Artifact` 未定义、`HUMAN` 任务留下第二条完成路径、lifecycle 政策逃生口、Phase 1 验收面打架——现在都已经在合同里合上了。fable 的 2 个阻断、24 条 medium 也基本核销（见 [fable-followup-20260819](./fable-followup-20260819.md)）。剩下的不是「对象没定义」，而是交付体量和未验证依赖。

## 这套设计真正强的地方

核心洞察就一句：**七件事实不许互相冒充**——Harness 跑完、进程退出、代码提交、评审通过、CI 绿、外部 Issue 关闭、Task 验收。整份文档是在把这条边界做成机械可校验的事实链，而不是靠 prompt 和界面习惯。

三刀切分是正交的，而且现在真的写进了不同文件、由不同层拥有：

1. **语义分责（四模块）**：Project / Task / Run / Agent。短路是显式设计（无 Run 的 RoomInvocation、无 Task 的 Run），不是流水线例外。
2. **部署分面（三面）**：展示面只投影；控制面拥有治理；执行面拥有 content。client-server 是架构，local-first 只是默认部署。
3. **数据分类（三类）**：metadata / content / artifact，配三条法——能承载 ≠ 能裁决；冻结摘要是防火墙；命令走 HCTL、记录落平台。

v0.10 把第三条推广到 Chat 和 Kanban，是整段演进里最值钱的一步。此前 Workflow 和 Terminal 已经是「引擎/harness 拥有记忆、HCTL 只留绑定」；Chat 和看板却把记忆锁在 clone 的 SQLite 里——同一个人两台机器各 clone 一份，协作历史跟着某一个 clone 走。这是灵魂存肉体。三分法之后：平台可以拥有记忆，不能拥有裁决；协作随用户走，clone 只是物理现场。

机械纪律也配得上这个洞察：

- 正式变化 = 类型化命令（actor + expected version + 幂等键 + digest）；外部事件只能先当 Snapshot / ResultProposal。
- actor provenance 不能自报。模型在执行环境里调 `hctl2 task complete` 也会因 execution provenance 被拒，不靠 prompt 自律。
- Task 完成只有两条路：有权人从看板提交，或 task-bound Run 正常完成后 reducer 提交**同一个** `CompleteTaskIntent`，Task 再独立重验。失败类 Run 不终结 Task。
- 「重试」拆成五条身份不同的路径（传输重投 / 候选切换 / Engine retry / 语义返工 / 替代执行）。混用就会复制票数或复活旧执行。
- 权限只能逐级缩小。三个单写者全部锁 + generation，旧代次一律失权。

文档工程本身也很少见：分层写作被执行而不是宣称；连接和共享机制只在一个权威位置定义；语义变更单独提交并清扫受影响文件；`.memo/` 里的讨论、否决、核销都入库。`implementation-evidence.md` 对参考实现固定 commit、许可证和「采用 / 不采用」边界，不是竞品名录。

写作原则上，v0.9 那一轮比 v0.10 的架构转向更值得当样本：**不是每个 CamelCase 都该成为类**；场景概念对齐 Matrix / Linear / Conductor / PTY，自造词只留差异化语义（Obligation、Verdict/Receipt、WriteLease）。设计正文大体说人话，合同词沉在 `spec/`。

## 作为仓库，现在的问题不在正确性，在可开工性

合同已经写到接近可执行规范，但仓库里还是零代码。这个落差本身就是主要风险。下列各项与 kimi-20260821a 的五条风险部分重合，此处按独立判断展开，不重复机械校验结论。

**第一阶段进程拓扑和 local-first 体验是拧着的。** 出门条件是：Electron Workbench + `control`/`core`/`agentd` + Conductor（持久化要 Redis/Postgres，没有 SQLite）+ Matrix homeserver + 本地任务服务器 + 至少一个完整双向远端适配器。架构上「轻 ≠ 嵌入式」说得通，但用户打开一个 repo、十秒内回答六个问题，先要拉起这一串。纵向切片 A（无 Run 自举）才是真 MVP；切片 A 到 B5 之间的项现在没有「可独立砍掉」的标记。

**合同押在还没跑过的依赖上。** 治理引用假定 Matrix 事务 ID 幂等和单 homeserver 线性顺序；看板排序假定后端有可条件写入的并发令牌（Vikunja 是否具备未证实）；Conductor 的单机最小持久化组合也没验证。五项限时验证写在 `delivery.md` 里，失败则重开 ADR、不自研第二套——规则对，但它们是事实上的 phase 0，应该先于 B0。否则合同层会返工。

**两块用户天天碰到的东西还在 memo 里。** `ContextManifest` / `ContextBundle` 在合同里是票据，组装顺序只有一行；真正的新鲜度、覆盖、预算、索引规则在 [context-design-20260819](./context-design-20260819.md)（337 行讨论稿）。Participant 的七层拆分（身份 / 角色 / persona / 模型制品 / Skill / WorkerProfile / 端口）同样在 [participant-design-20260819](./participant-design-20260819.md)，规范明文「进入规范前不得成为第二套权限」。B2 是「从 Project Room 在隔离 worktree 做一次真实改动」——没有可执行的 Context 组装合同，第一次自举会在这里分叉。

**单用户自举和三选二 Gate 还没对上。** 合同写：被评对象的作者不得占必需 reviewer Seat；必需 Seat 绑定彼此独立的逻辑 Participant。B4/B5 又要求在 HCTL2 自己的真实变更上走完三选二。一个人开发自己的仓库时，要么三个 Participant 绑同一个人（独立性作废），要么用模型 Participant 当评审（作者/评审分离沿 `producer_ref` 解析，这条路合同允许但没写成第一阶段构成规则）。fable 的 M19 把这个问题交给了 Participant memo，现在还挂着。

**「一本账」跨机器仍是方向，不是机制。** `~/.hctl2/control.lock` 是本机 OS 锁；账本路径也是本机 `~/.hctl2/control.sqlite`。架构已经把「打开远端 repo、一人两机」写成产品体验，但远程认证/传输在未决清单里，第一阶段只交本机连接。更硬的是：用户级 metadata 账本被声明为**唯一不可再生的权威、必须备份**，备份和搬迁合同还不存在。对单用户产品，这是最大单点。

**一处具体的合同残留。** `docs/design/spec/connections.md` 连接模型第 3 条仍写「同一 **RepoInstance** 内的目标状态……由 control 在一个事务中提交」。v0.10.2 之后事务边界是用户级账本，RepoInstance 只是注册在账本里的物理现场。实现者若按字面把 SQLite 事务又做成 per-clone，会把 v0.10.2 的转向做回去。

## 总评

作为设计阶段的仓库，纪律性和概念收敛都在高位。0.7 以来每次转向都在做同一件事：把「靠 prompt 和界面维持的正确性」换成「靠身份、版本、证据机械维持的正确性」。四模块分责、三类数据、三条法、两种完成路径、五种重试——这些硬边界现在是自洽的。

它还不是一个可以 clone 下来跑的项目。下一件该做的不是再写一轮 0.11，而是：

1. 把五项限时验证当 phase 0 跑掉（Matrix / Vikunja / Conductor 本地分发尤其是）；
2. 把 Context 组装和单用户 Gate 构成从 memo 收进合同，否则 B2/B4 会各写各的；
3. 把切片 A 标成可独立交付的最小闭环，Conductor 和远端双向适配器放到它后面；
4. 契约测试矩阵带上稳定编号，和 B0 的命令信封一起落地——状态机现在是散文加表格，矛盾会在第一份实现里而不是下一轮评审里出现。

仓库对自己的状态是诚实的。风险不在设计有没有逻辑洞，而在规格已经比实现跑得远了一截：每周继续长文档、B0 不开工，第一份代码碰到的就会是「状态机组合不起来」，而不是「模块分不清」。
