## 一、先确定依据，再给结论

这是架构与用户路径的问题，不是替换几个英文单词的问题。我的判断是：**以〈control, repo〉为工作边界、首次进入 Repo Room、其后按话题开房间，这个模型成立；Rooms、Tasks、Runs 可以并列，但“没有强制的父子关系”不能扩大成“所有关联都没有约束”。**

所有者 2026-09-18 明确了三份第一手依据，本文按它们判断需求：

1. [原始用例](../notes/HCTL_case_study.md)：多控制面、多 Agency、多前端如何共同使用仓库。里面的 Project 用词有混用，不能拿这个词本身证明存在一个独立的业务容器。
2. 所有者 2026-09-17/18 的用户流程：「新建项目」「产生 topic」「观测 Run」。它说明人实际做什么、想看到什么；本文第五节逐步核对。
3. 所有者 2026-09-18 的澄清：首个无主题房间是 Repo Room；Project 曾混指 Repo 或 Topic；边界是〈control, repo〉；三种视图间的关系交本次验证。后续消息再次确认这三项是第一手资料。

现行设计只用于找受影响的位置，不反过来当作否定用例的尺子。我[昨天的备忘](./user-journey-alignment-20260917.md)只用于核对和撤回自己的旧建议，不是需求证据。本次不做跨家汇总，不以其他家的评价为依据。

以下把所有者明确的意思与我的推论分开。特别是“取消强制 Project 容器”“一个看板可接多个来源”，都是我的建议，不能因写入本文就算所有者已经选定。

## 二、最小用户模型

边界里有三种并列入口；房间内部的消息、Run 内部的步骤则仍有明确归属。以下是导航示意，不是部署图：

```text
某个控制面里的某个仓库〈control, repo〉
├─ Rooms
│  ├─ Repo Room：不预设主题的默认聊天室
│  ├─ Topic Room A：围绕话题 A 的聊天室
│  └─ Topic Room B：围绕话题 B 的聊天室
├─ Tasks / Kanban：任务及其看板视图
└─ Runs：各次执行的任务书、拓扑与进展
```

这里的 Repo 是人选定、由该控制面登记的逻辑仓库，不是某台机器上的目录。〈mac_ctl, gh-jssdk〉和〈cloud_ctl, gh-jssdk〉是两份工作范围；〈mac_ctl, gh-jssdk〉和〈mac_ctl, gl-jstui〉也分别组织工作。共同读到一个平台上的提交，不会让两边的授权或任务完成状态自动相同。

“闭包”在这里宜解释为**工作身份、授权和判定的范围**，而不是所有相关东西都变成私有部署。Agency 的工种、内容服务、模板与 Git 副本仍可复用；在某个范围里选人、发出的派工及接纳的结果各有归属。把另一边的成果作为材料引用，与共用另一边正在生效的授权，是两件事。这也不要求每个 Repo 新建一个 Agency 租户或一套控制面。

Repo Room 与 Topic Room 的差别是讨论用途，不是权限高低。我建议 Topic 暂只表示 Room 的主题，不再增加一个 Topic 对象及其唯一 Room：本轮路径没有要求话题独立于房间被授权、执行或验收。话题可以长期讨论，也可以没有 Task；“话题”不天然等于临时答疑、一次任务或一个 Run。

三个入口也不是全部领域职责。Repo 的代码、评审与集成，Agency 的选人、派工与观察仍然存在；它们不必各占一个左栏入口。三种视图不能据此推导成只剩三个模块。

## 三、三者并列成立，关联的含义要区分

我支持去掉 `Room → Task → Run` 这条强制创建链，但不建议把所有关系统一写成一个没有含义的“可关联”。

| 关系 | 本轮可成立的关系 | 为什么不等于父子容器 |
| --- | --- | --- |
| Room 与 Task | 一个 Room 可讨论零到多个 Task；同一 Task 可在多个 Room 讨论 | Task 可以从看板创建；后来换房间讨论，不该变成新任务，也不该改验收目标。任务有聊天出处时，保留出处不等于永远属于那个房间 |
| Room 与 Run | 一个 Room 可提出、查看多个 Run；同一 Run 的结果可被多个 Room 引用 | Run 可以从任务或 Run 列表启动；另一个房间分享它，不该复制执行。来源消息和本次实际采用的材料仍要能说清 |
| Task 与 Run | 一个 Task 可以经历零到多次 Run；Run 也可以不承担某个 Task 的完整交付 | 人或外部平台可以完成工作后提交验收证据，不必补造 Run；研究、咨询也不必先立完整交付任务。Run 之间的目的与授权各自明确 |

**这里有一个真正不能省的区别：关联任务，和承担完成这个任务的责任，不是同一件事。** 一个研究 Run 可以给三个 Task 提供材料，却不因此有权把三个 Task 一起标完成。一个施工 Run 也不会因为被分享到另一个 Room，就换了所依据的任务书。

现文允许 Run 不绑定 Task；绑定时至多绑定一个 Task 契约，并承担它的完整交付；同一 Task 同时只有一个活动的完整施工 Run，见 [Run 约束 §Workflow 与 Run 授权](../../docs/design/spec/run.md#workflow-与-run-授权)及 [Task 约束 §写入约束](../../docs/design/spec/task.md#写入约束)。这不是“视图并列”的逻辑后果，而是现有行为选择。**本条用户路径不要求撤掉它们，我建议暂时保留，不把普通讨论、材料引用也算成这种绑定。** 多次历史 Run 与多个同时活动的 Run 也不是一回事。

用例外：若以后明确要一个 Run 同时承担多个 Task 的完整验收，就另核每个 Task 如何分别完成、部分失败怎样处理。来源是对当前零或一个完整契约限制的反向检查，不是本轮已经出现的需求；不为这种可能性先造多任务执行机制。

“三者没有必然从属”也不取消各自内部的归属：消息归某个 Room；某次 Run 的工序、评审位置和尝试归该 Run；选进房间讨论的人与为执行选的人可以采用同一工种，但一次输入究竟送给谁仍要明确。自由关联不要求会话、上下文或授权自动共享。

## 四、Project 不宜再作为必经的中间容器

我的推荐是：**这条用户主路径不再强制建立独立的 Project 对象，也不把 Project 整体改名为 Topic。** 选择代码仓库就是进入 Repo；展开一个讨论主题就是开 Topic Room；作出可验收承诺是 Task；授权的一次自动施工是 Run。用户已经能表达当前路径，没有再经过一个中间容器的理由。

保留 Project 作为额外目标容器并非永远错误：如果人明确要跨多个房间维护一个独立目标、预算或结案状态，它可能有自己的用途。但这三份原始材料目前没有把这个需求与 Repo、话题、Task 区分出来。现在硬留，只是为旧模型找理由；把它改名 Topic，则会把原来的强制归属一并带回来。

这不意味着删掉原 Project 模块保存的长期事实。建议按事实本身处理，而不是按旧名字搬家：

| 原 Project 承担的事情 | 我的建议归向与理由 |
| --- | --- |
| 关联仓库、提供总体导航 | 〈control, repo〉；人开工时已经选定，不再问一个含义不明的 Project |
| 讨论目标、论证、来源、Room 名册 | 相应 Room；主题与长期讨论仍然保留，不强迫它先成为 Task |
| 明确要交付什么、怎样验收 | Task 契约；一次谈话或房间改名不改变已采纳承诺 |
| 本次做什么、谁执行、可以做多大、花多少 | 本次 Run 或房间调用的授权；原 Project 的通用选人和预算设置可作为仓库范围的缺省，实际采用什么仍随本次授权明确 |
| Memo、材料与待答问题 | 保留现有对象及精确来源、作用范围；房间归档不等于承诺已取消、请求已解决或材料失效 |

上表是架构建议，不是字段迁移方案。收益是减少强制容器与重复归属；代价是现文挂在 Project 上的启动条件、默认策略和归档效果要逐条重新安放。不能只删 `project_id`，留下这些规则悬空。模块叫什么、文件是否改名，由后续正式改写统一处理，本稿不另造模块。

## 五、沿用户流程验证

这张表核的是建议模型能否解释原路径，不是声称产品已经实现。

| 原始步骤 | 此刻究竟要决定什么 | 人已声明还是系统推断；我的判断 |
| --- | --- | --- |
| 选择 SCM 地址 | 在哪个控制面，针对哪个仓库工作 | 人选定；不因本地副本或相同提交替人猜出另一个工作范围。远端接入与本地另起两条路径都保留，本次不改变它们的产品含义 |
| 绑定 Kanban | 从哪里读任务、新建卡写到哪里 | 由人选；推荐源只是预填。读回已有卡与采纳其验收承诺分开，源中的卡不必因此全部变成 HCTL 已承诺的工作 |
| 首次选人聊天 | 为这个仓库的无主题讨论选哪些参与者 | 仓库与名单均已由人给出，得到 Repo Room；没有另外需要系统猜测的 Project 目标 |
| 聊天建议新话题，用户选 Yes | 是否开新 Room、主题是什么、带哪些出处与人 | 系统推断候选话题，人确认创建。话题 Room 可以无任务；父房间名单可预填，选入与实际带走的材料仍明确。No 不创建 |
| 在任意房间建立、修改或删除 Task | 对哪张任务卡、哪项承诺作哪种动作 | 房间提供入口与来源，人确认目标；无需先给 Task 找一个唯一所属 Room。删除源卡、取消 HCTL 承诺与停止活动 Run 的效果要说清，不靠“删除”一个词代替 |
| 用模板表单生成施工图并开工 | 对哪个目标，采用什么图、材料与授权 | 模板帮助填写，人确认具体执行；生成图不等于已经启动。由哪个房间提出只是出处，不决定整个 Run 的权限 |
| 从 Run 列表切任务书或 DAG | 展示同一次执行的哪一面 | 纯粹切视图；任务书与图都指向同一 Run，平行步骤各显其状态，切页不改变执行 |
| 点某个施工者观察或输入 | 要看、要输入的是哪次派工 | 经 Agency 提供约定的观察能力；虚拟机画面、TUI 或无交互界面都可以。无界面不等于没有状态、结果或证据；也不把同名参与者的另一场执行当作当前执行 |

我不把“选源 → 选人 → 开房间”的向导顺序解释成运行依赖：它可以是推荐首用流程，但选源失败不应让已经可用的聊天和独立研究变成不可用。现行 [Task 约束 §契约与来源](../../docs/design/spec/task.md#契约与来源)本来允许没有任务源时其他模块照常。这是我的建议，不是替用户取消看板步骤。

用同一仓库里的两个话题走一遍：在 Repo Room 提出“改善测试”，开话题 Room A，建立 Task T；在 Room B 讨论“升级依赖”时发现也涉及 T，直接引用 T，不新建任务。为 T 启动 Run R，R 的进展可在两个房间被分享。归档 A 后，T 与 R 仍在 Tasks、Runs 中；R 完成后按 T 的验收规则判 T，不看哪个房间还活跃。这里放开的都是讨论与展示关系，没有让一次任务凭两个房间多出两份授权。

这个例子也给出三条可检查的反例：在 B 引用 T 却创建了第二个 T；归档 A 导致 R 被取消；把 R 分享给另一个话题就改了 R 的任务书。任一出现，都说明实现仍把房间当成了任务或执行的父容器。它们是纸面验收建议，本轮没有运行产品测试。

## 六、旧用例不能逐字替换

[原始用例 §实践方案 - mac](../notes/HCTL_case_study.md#实践方案---mac)明确说 `mac_ctl` 基于 `gh-jssdk` 开了 `mac_jssdk_01`、`mac_jssdk_02` 两个“projects”，并分别选人。**它证明用户希望针对同一仓库开展两组工作，不证明两组工作一定各有一个独立的 Project 治理容器。**

按这次澄清，把这两组工作解释为〈mac_ctl, gh-jssdk〉里的不同话题协作，是自然的候选解释。但原用例没有说每组恒等于一个话题或一个房间，我不把它直接写成已定的一一映射。同样，云端对两个仓库分别开展工作，首先对应两个〈control, repo〉范围，而不是两个 Topic。

不含糊的部分则照留：同一个控制面可以被多个前端访问，一个前端也可以连接多个控制面；一份仓库可以在多个控制面分别工作；远程 Agency 供人、工作副本在哪与前端在哪并不一致。Repo Room 与 Topic Room 的改口没有理由推翻这些用例事实。

因此正式修用例时，应逐处回答旧 Project 指的是“哪份仓库工作”“哪段主题讨论”，还是确实另有独立目标。判不出的注明待确认，不通过批量换词制造一个原文没有声明过的关系。

## 七、现文哪些地方真受影响；我撤回什么

当前架构并非全错：[系统边界 §固定内核与受控端口](../../docs/design/spec/system.md#固定内核与受控端口)已经以控制面中的每个 Repo 保持独立语义范围；[Project 正文 §Room 类型](../../docs/design/project.md#room-类型)也已经把 Repo Room 定为无固定主题的入口。应保留这部分，再处理仍然强绑 Project 的地方。

| 现行位置 | 已有事实或冲突 | 后续正式改写要核的方向 |
| --- | --- | --- |
| [architecture §5×3 归属矩阵](../../docs/design/architecture.md#53-归属矩阵) | Room 元数据写“归属 Project”，末段另列 Repo Room；聊天两级与 Project 分组仍是固定模型 | 用〈control, repo〉及两种房间用途解释导航与归属；三种视图不改变三面分责 |
| [spec/project §Repo 注册与 Project 归档](../../docs/design/spec/project.md#repo-注册与-project-归档) | 创建 Project 连带唯一 Project Room；Project 归档会限制 Task、Run、Request 等动作 | 去掉把话题房间当作共同生命周期父对象的效果；长期事实按第四节分别安放 |
| [spec/task §对象、契约与来源](../../docs/design/spec/task.md#对象) | Task 的 Project 是不可变身份，创建、源选择和认领依赖它 | 任务归仓库范围，房间关联不是身份或验收契约。默认建卡源与讨论分组分开，不为换讨论地点取消旧任务 |
| [spec/run §Workflow 与 Run 授权、启动与 Manifest](../../docs/design/spec/run.md#workflow-与-run-授权) | 即使不绑定 Task，Run 也冻结 Project；启动要求 Project 活跃、匹配 | 若采用本文建议，启动依据改为仓库范围和本次具体授权，而不是先建 Project。已授权的图与任务契约仍保持精确 |
| [spec/project §Room 与消息](../../docs/design/spec/project.md#room-与消息) | Scoped Room 强制完成条件与回填动作 | 普通 Topic Room 不因“从讨论中开出来”就承担结案或回填义务；真的承接请求时，再沿该请求的规则处理 |
| [spec/project §Room Invocation](../../docs/design/spec/project.md#room-invocation) | 无 Project 的仓库范围调用只读，写入另要求 Project | 此处的“只读”限制参与者调用，不是禁止人在 Repo Room 点任务命令。对象调整时专门核写入授权依据；不把“换个房间名称”当成扩权，也不借此擅自扩大本轮代码写入需求 |
| [participant §Agency 与执行体](../../docs/design/participant.md#agency-与执行体)、[spec/connections §Project / Run → Participant](../../docs/design/spec/connections.md#project--run--participant从授权到派工) | Room 与 Run 各自选人，调用冻结实际范围、材料和权限；通路归 Agency | 保留执行与选人的分责，替换对 Project 默认策略的依赖，不新建仓库级成员总表或复活现场对象 |

实体键、跨仓认领等更细的限制，也要在正式改写时按实际受影响句子核对。本轮没有给出“同一卡片在同一控制面的两个仓库分别承诺”的路径，不能据“闭包”二字就宣布已有去重规则必须改成某组新字段。

对[昨天自己的备忘](./user-journey-alignment-20260917.md)，我明确撤回三项建议：

- §三把〈control, Project〉当作工作边界，并建议取消 Repo Room、研究也先建 Project。
- §四把“以 Project 为入口”继续推导成仓库合并板退到背后，并建议另一 Project 已认领的卡不能作为本 Project 的同一 Task 使用。若原文的两个 Project 其实是同仓库的两个话题，这个边界就设错了。
- §五把新 topic 房间固定成“某个 Project 里的 Scoped Room”。普通话题不强制回填的理由仍成立，但不再用那个 Project 父容器解释它。

前稿分别保留卡片来源、冻结执行授权、依 Agency 能力观察等判断，不因这次术语澄清一起作废。它们的理由不是 Project 必须存在。

这里我也有责任：原始流程只要求人选 SCM，却突然说“建立 Project”，这时我应先问这个 Project 与 Repo 的差别，而不是把混用的词固化成边界，再据此提议删除原本合适的 Repo Room。以后遇到同一名字同时承担仓库、话题和承诺三种角色，应先指出它们，不顺着词面扩写规则。

## 八、还需明确的取舍

本次已经澄清的 Repo Room、〈control, repo〉边界不再重复提问。我的推荐与尚不能从原文确定的部分只有以下两项：

1. **Project 是否退出强制对象模型。** 我推荐退出本条主路径，不改名为 Topic 继续保留；长期目标与讨论不删，按第四节分责。若仍希望保留独立 Project，应先给一个 Repo、Room、Task、Run 的组合确实表达不了的具体使用步骤。这是模型取舍，不能当作普通术语替换直接施工。
2. **“有且只有一个 Kanban”是一个视图，还是只许一个任务源。** 我推荐一个仓库范围一个看板入口，首用显式选一个默认建卡源；已有卡仍认各自来源。单视图不妨碍多个来源，现文已有这条路径。若用户要的是只能接一个源，也可以选择，但会收窄现有多源能力：代价是同一仓库不能在这个看板同时看 SCM issues 与外部任务系统。原流程列出三种供给选择，还不足以证明要删除后续多源能力，我不替所有者做这个决定。

这份备忘只提供独立判断。下一步宜先确认上述模型含义，再让主笔按受影响职责统一改写；不继续围绕旧 Project 的某个字段加补丁，也不把本文当作已经获准修改正式设计的命令。
