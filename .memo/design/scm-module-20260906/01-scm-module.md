## 一、要决定什么，以及我的判断

起因是一个观察：我们开发 HCTL2 自己的时候，走的一直是「开 PR、几位审阅者在评论里给意见、作者改、再审、合入」这条路。这条路把协作放在了 GitHub 上，而设计文档没有明说这个依赖。所有者问：要不要显式地放进设计？如果放，是不是恰好就是第五个模块？

先说事实。约束层没有把 GitHub 定为必需：它只在 Task 模块里作为任务后端的例子之一出现，与 Linear 并列。远端代码托管一侧，文档一律写「远端 SCM」这个通用词，GitHub、GitLab、Gitea 都算；把改动推到远端、开 PR、合并 PR 由适配器做，适配器就是把我们的命令翻译给某个外部系统的那层代码。远端副作用本身已有完整规则：`spec/system.md` §外部权威副作用 规定意图先持久化、记录绑定与冲突范围、结果未知怎么处理；`spec/participant.md` §ChangeSet 与 Git 事实 规定集成命令要固定哪些字段。**缺的不是规则，是三样东西**：这些对象与规则的领域归属（今天散在 Participant、Project 和系统层）；平台上的内容（PR 线程、评审状态、检查结果）在事实权威地图里没有位置；以及两条产品路径（经平台合入、纯本地合入）各自怎么走、怎么降级。`spec/system.md` §场景端口 的表只有四行、没有代码托管这一行，是这个缺口的表面症状。实现层今天确实用了 GitHub：工具箱的 `wait` 命令读 CI 状态、PR 是否合并、分支是否推进，用的是随包带的 gh。

再说判断。**成立：代码变更与集成应立为第五个模块，理由是它拥有一组有独立生命周期、恢复边界和权限边界的治理事实，不是因为它有一个平台客户端。** 它有两条正式的集成路径，经平台和纯本地，按每次集成的目标选，不是全局开关。它要从三个地方把已有对象搬进来（变更集与集成从 Participant，Repo 注册从 Project，Repo Instance 从系统层），并给工具箱一个正式的家。它有自己的场景。下面分节展开。

## 二、为什么是模块：按治理责任，不按客户端

`docs/design/spec/README.md` §词汇分类法 给「独立对象」的判据是：有独立的生命周期、恢复边界或权限边界。模块是拥有一组这样的对象并为它们定写入者与不变量的归属者。用这个判据看代码变更与集成：

- **Repo（逻辑仓库）** 有自己的稳定身份和注册命令，先于任何 Project 存在，一个 Repo 承载多个 Project；它的恢复边界是「Git 中的身份与账本中的身份互证」，与 Project 的目标、范围无关。
- **Repo Instance（一台机器上的物理现场）** 有自己的挂接、移除、现场锁与代次栅栏；它的恢复是「从账本、Git 与运行时观测对账重建」，与任何执行实例无关。
- **ChangeSet 与 ChangeSet Revision（获准的写入边界及其不可变版本）** 有自己的只追加版本序列和写权；写入者换人、接管、取消都是它这一侧的失权动作；恢复边界是「证明不了旧写入者失权就隔离现场」。
- **集成意图与 Integration Receipt（把精确版本合入目标的持久授权与回读证明）** 有自己的状态（待启动、结果未知、成功、失败）、幂等键和冲突范围；权限边界是「合入钥匙不进工具，只有持有当前代次栅栏的工具箱或适配器代用」。

这四组东西今天分属三个归属者，而它们之间的不变量（版本必须在有效写权下封存、集成必须固定版本与预期头、Receipt 只在回读后签发）是同一条链上的。把链的各环放进一个模块，写入者与恢复规则才能在一处判定。这是立模块的理由。

v1 用的理由是「一个自带原生客户端的外部系统就是一个新场景，一个场景绑一个模块」。Codex 指出这条推导不成立，我接受：Vikunja、Linear、GitHub 都有原生客户端，却是同一个 Kanban 场景的候选；同一个 GitHub 可以同时承载任务卡和代码评审；`spec/system.md` §组件 明说第三方平台可以同时提供场景客户端和受控端口、两种接入分别绑定。产品、客户端、场景、模块之间没有逐个对应的关系。更要紧的反证是：纯本地仓库没有任何平台内容系统，这个模块照样要存在，所以模块的存在不能挂在 GitHub 的界面上。

平台内容在哪里落脚，是立了模块之后的第二个问题，不是立模块的理由。答案是：PR 线程、平台评审状态、检查结果、合并状态是这个模块的场景内容，事实源在平台，控制面只保存映射、引用与冻结摘要；纯本地仓库没有这类内容，场景显示本地事实，讨论回到聊天室。这一层在第三节和第五节。

这个模块**不是**什么：不是第四个「面」，三面架构不变；不是通吃各模块的垫片，`docs/design/architecture.md` §避免供应商锁定 的禁令继续有效；不把控制面变成内容仓库，控制面照旧只存身份、准入、摘要、映射和凭证；也不新造一个通用的外部副作用系统，那一层留在系统层。

## 三、工具箱总在，平台按仓库绑定：两条集成路径与冻结的契约

所有者要求纯本地集成有正式方案，类比 Participant 模块的 Agency：本地参考实现随包发布、总是可用，远端供应端可以外接。这个模块的样子是：

**GitHub 是缺省的平台实现，不是唯一实现，也不点名谁是第二个。** 代码协作平台是一个端口，接在上面的供应端可以是托管服务（GitHub、GitLab.com），也可以是自建服务器（GitLab 自建版、Gitea、Forgejo、Gerrit）；对我们它们是同一种东西，差别用绑定上的能力声明表达。本批只实现 GitHub 的适配器，因为我们自己的仓库在上面；未来支持哪些后端、先后如何，看研究层的市场调研（第十二节），不在这里下结论。集成目标因此分三类：某个 Repo Instance 上的本地 ref、自建平台上的远端 ref、托管平台上的远端 ref；后两类走同一个端口。

**工具箱是每个仓库都有的本地执行者，不是「本地供应端」与「平台供应端」二选一。** 无论仓库有没有平台，物化工作树、封存版本、读取 Git 事实、本地现场锁都由 `hctl2-tool` 做；平台仓库照样要它。平台适配器只管平台上才有的事：推送分支、开或更新 PR、读检查与评审状态、请求合并。两者是分工，不是互斥。

**平台按仓库绑定；集成路径按目标选。** 一个 Repo 的绑定记录（`spec/system.md` §固定内核与受控端口 的 Port–Provider Binding，固定供应端、配置、凭据引用、实测能力和降级策略）写明这个仓库有没有平台、哪个平台、平台上的仓库身份、目标分支的保护条件。每一次集成意图必须固定自己的目标：是某个 Repo Instance 上的本地 ref，还是平台上的远端 ref；固定目标 ref 名、预期目标头、所用绑定的版本。本地目标走工具箱的比较并交换，远端目标走适配器。同名的本地分支和远端分支是两个目标，对本地 `main` 做的集成不能算作远端 `main` 已合入。依据是同节的「同一端口种类和作用域在一次准入中只能解析出一个绑定版本」「已有执行继续使用原绑定」。

**能力声明决定契约能不能被满足，不能替人改契约。** 绑定要声明平台有没有评审线程、有没有正式评审状态、有没有检查、能不能远端合入、有没有身份映射、能不能保证预期目标头（第六节）。这些声明在两个时刻起作用：采纳契约、预览集成时，控制面据此判断契约里的验收项能不能由这个仓库的供应端满足；执行时，缺了声明过的能力，命令等待、拒绝或标为需要关注。v1 写过「没有检查就让机械验收项只认本地事实、没有远端合入就走本地比较并交换」，这是错的，与 `spec/system.md` §命令与跨服务正确性 的「组件不可用不会改变命令前置条件」冲突：契约要求 GitHub 的三个检查通过，平台失联时本地测试退出码为零不能顶替；契约要求合入远端 `main`，本机 `main` 前移不能顶替。改契约只能由有权的人显式做。

**纯本地仓库是完整的正常路径，不是降级。** 一个从头到尾没有平台的仓库，契约在采纳时就只会要求本地能给的证据：工具箱回读的测试退出码与输出、本地目标头；讨论在 Project 模块的 Scoped Room，也就是为某个变更开的专题聊天室；集成走 `hctl2-tool integrate`；凭证照常写。将来给它绑上平台，是加一份绑定、多一类目标和能力；Repo 身份、既有版本与凭证不变，进行中的意图沿用原绑定版本。

本地路径今天有一个**交付缺项**，写在这里不藏：P1 丙的 `integrate` 在目标分支正被某个工作树检出时默认拒绝（人的主工作树通常停在 `main`，改动在另一个工作树，集成回 `main` 就是这个情形）；显式放行时只推进 ref，不更新那个工作树的文件与索引，人接着一次普通提交就会把集成撤销。产品层的处理有两种，P2 要选一种：由人先把目标工作树切离目标分支再重试，工具箱给出精确的工作树路径与恢复动作；或者提供一种只在目标工作树干净时才顺带更新它的安全动作，形态类似 git 自己的 `receive.updateInstead`。前者已经能用，后者要另做。不能写成「装了工具箱本地路径就完整」。

「现在在哪」以 v0.16.5 为准。这张表是 v0.17.0 改文档的清单之一。

| 对象 | 现在在哪 | 挪到第五模块后 | 说明 |
| --- | --- | --- | --- |
| Repo（逻辑仓库的稳定身份与注册） | Project 模块，`spec/project.md` §Repo 注册与 Project 归档 | 第五模块拥有身份、注册命令、Git 中稳定身份的写入与回读 | Project 保留「一个 Repo 一个 Repo Room」与 Project 归属于 Repo 的关系；注册确认与建 Repo Room 仍在同一账本事务里，见第八节 |
| Repo Instance（物理执行现场） | 系统层，`spec/system.md` §Repo 与执行现场 | 第五模块拥有挂接、移除、现场记账 | `site_generation` 继续列在系统层的代次家族表，指向本模块；工具箱无副作用读身份这一步不变 |
| ChangeSet 与 ChangeSet Revision | Participant 模块，`spec/participant.md` §对象、§ChangeSet 与 Git 事实 | 第五模块拥有；封存、保全、拆除这些工具箱动作随之归本模块 | Participant 的三条底线里「隔离工作树」继续引用本模块的 ChangeSet |
| Write Lease（对一个 ChangeSet 的独占写权） | Participant 模块，与 ChangeSet 同一行 | **方案甲（我与 Codex 都选它；所有者倾向甲，但未拍板，交各家审后再定）：随 ChangeSet 进第五模块。** 唯一写权和封存前置放在同一归属者，避免两处各自判定可写 | 失权是两个模块各做自己的动作：第五模块记撤权、不重授；Participant 停止或隔离旧执行并提供证据（`spec/connections.md` §失败与恢复 要求同一事务撤销租约并提交停止、隔离记录）。两边不各建一份写租约 |
| 集成意图与 Integration Receipt | Participant 模块，写作「外部副作用命令（executor = tool）/ Integration Receipt」 | 第五模块拥有**属于代码集成的**那些命令：本地集成、远端推送与 PR、远端合入，及其凭证 | 通用的外部副作用命令族（建任务卡、聊天写回等）、命令信封、outbox 与 inbox（待投递与已接收记录）、恢复算法留在系统层，`spec/system.md` §固定内核与受控端口 明写它们是共享机制；Task 有自己的后端 outbox。工具箱替各模块写 Git 正文，不转移那些正文的准入权 |
| 变更与平台的映射 | 没有 | 新增绑定，双端命名，例如 ChangeSet–Platform Binding | 更新规则见下 |
| 平台账号与人的映射 | 没有（可参照 Room 的聊天账号身份映射） | 新增，放在平台绑定里 | 只有映射到有权用户本人的平台动作才可能成为命令请求；接受哪些动作、映射到哪个命令，第十节 |
| 外部机械事实（CI 状态、PR 是否合并、引用推进、路径与摘要） | 工具箱 `wait` | 归本模块的读侧 | 语义不变；Run 的节点前置继续只认工具箱回读 |
| Git 的双重角色（不可变正文与判决结晶副本） | 系统层，`spec/system.md` §Git 的双重角色 | 规则留在系统层，因为 Task Revision、Workflow Revision、Memo 的正文写入是跨模块的 | 只补一句「执行者是本模块的工具箱」 |

**变更与平台的映射怎么更新。** 评审身份是 ChangeSet Revision 的摘要（基于结果树），不是 PR 号，也不是提交 SHA；`spec/participant.md` §ChangeSet 与 Git 事实 已写明 `result_commit_sha` 不属于 Revision，同一版本换提交包装不改变评审身份。映射记两类东西：PR 的当前状态（当前头、检查、线程）是回读事实，随时变；「某个冻结版本对应当时平台上的哪个提交」是证据，冻结后不变。PR 的头变了，工具箱重算结果树：树变了就是新版本，旧裁决按 Run 的返工规则失效；树没变只是换了包装，版本不变。一个 ChangeSet 对应几个 PR、一个 PR 能不能换 ChangeSet，交付文档仍列为未决，本备忘不在绑定名字下默认一对一。

**不搬的东西。** Gate、Seat、Verdict 留在 Run；评审对象引用（ReviewSubjectRef）继续是「对 ChangeSet Revision **或 Artifact Revision** 的精确引用」，`spec/run.md` §对象 原文如此，纯文档工件的评审不能被搬没。Task Revision 与完成凭证留在 Task。Execution Spec 里「可选 ChangeSet / Write Lease 规则」留在连接约束，它是派工时冻结的。

## 五、场景：代码评审，以及评论怎样回到作者手里

这个场景回答：这一次变更改了什么、谁怎么看它、检查过了没有、它进目标了没有、怎么让它进去。

- 看：某个版本的精确 diff（今天写在 Project 场景和 Participant 那一行，要挪来）、评审讨论（平台上的 PR 线程，或本地仓库的 Scoped Room）、检查结果、集成状态与凭证。
- 做：发布评审（推分支、开或更新 PR）、发起集成（预览、提交）、把 Gate 的结论写回平台。写回是记录，走已有的副作用命令，不绕过授权；写回产生的平台事件不再触发一次人的请求，这是 `spec/README.md` §三类数据 的第三条法。
- 原生客户端：GitHub 的 PR 页面和 gh；其他平台各有对应的页面与命令行工具，例如 GitLab 的 MR 页面和 glab。Workbench 到 P3 才做投影；P2 用命令行。
- 命令行：`repo register|list|show`、`repo instance attach|list|show|detach` 从「Repo / Project」组挪来；`changeset show|diff`、`integration preview|submit|show` 从「Participant / Integration / Terminal」组挪来；新增发布评审的命令。命令名不改。

评审这个词在 Run 模块已经用在 Gate 上，要划清：Gate 是 Run 模块的判定，`spec/run.md` §Request、重试与 Gate 说它是 Run 内冻结的治理节点和规则；代码评审场景是内容与状态的呈现处，Gate 的裁决在这里只是投影，就像 Task 的状态出现在看板上一样。

**评论怎样回到作者手里，是这次需求的本体，v1 漏了。** 我们自己的流程之所以能转，是因为作者读得到评审意见。在产品里，作者是下一次调用的执行体，它拿不到平台评论：`docs/design/context.md` §投喂三档 规定指针只能指向执行体自己能打开的 Git 对象和工作树路径，平台评论不是；所以评论走「代取」，由控制面的组装器取回、冻结来源与摘要、放进开工包。今天代取来源只列了聊天史、任务后端评论线和账本里的裁决与凭证，要加一项：**平台评审评论线**，普通评论与正式评审都算，按精确的版本与评论标识冻结。本地仓库没有这一项，讨论本来就在聊天室里，走既有路径。

## 六、端口：操作面、目标保护、两个「头」

端口只放我们实际会调用的操作，按自举等级逐步长出来，不预先设计通用对象模型。多平台工具的共同做法是窄接口、第一个平台先做、第二个平台进来时修正接口，并且保留假的或本地的驱动给测试用（go-scm 有 fake 驱动，Renovate 有 local 平台，Zuul 有纯 git 驱动）。v1 说「我们的本地工具箱就是那个本地驱动」，Codex 指出这个等同不成立：Renovate 的 local 是试跑用、不建分支，Zuul 的 git 驱动只读仓库和触发；它们能支持「按能力拆接口」这一点，不能为我们的正式本地集成背书。本地路径按自己的真实功能验收。

B2 的「无 Run 切片」第一次消费这个端口，需要的操作：

| 方向 | 操作 | 平台（GitHub） | 本地 |
| --- | --- | --- | --- |
| 读 | 仓库身份、目标 ref 当前头 | gh 加本地 git | 本地 git |
| 读 | PR 当前头、必需检查逐项状态与时效、评审线程是否解决、正式评审状态、合并资格 | gh；今天的 `wait` 只有三类事实，不含评审线程与正式评审，要补 | 无平台事实；契约只能要求本地证据 |
| 读 | 评审评论正文（供代取） | gh | 无 |
| 写 | 推送变更集分支、开或更新 PR（含三节描述） | 适配器经 gh | 无 |
| 写 | 把 Gate 结论或集成结果写回 PR | 适配器经 gh，用控制面自己的平台身份 | 无 |
| 写 | 合入目标 | 适配器请求平台合并，回读合并提交与目标头 | `hctl2-tool integrate` |
| 映射 | 平台账号到人 | 绑定里配置 | 不需要 |

**目标保护不止「是否必须 PR」。** 绑定要能回读目标分支的保护条件：必须经 PR 与否、必需检查的清单、是否要求分支与目标同步、是否要求评审线程解决、要求的正式批准数。几个检查为绿不等于平台允许合入。我们自己的 `main` 今天是：必须经 PR，必需检查 `CI gate`、`Release gate`、`PR contract`，要求与目标同步，要求线程解决，管理员也受约束，要求的正式批准数为零。

**两个「头」要分清。** 源分支头是待合入的提交；目标分支头是预览时主干所在的提交。约束要求集成命令固定「预期目标头」。实现层脚注：gh 的 `pr merge --match-head-commit` 和 GitHub 合并接口的 `sha` 参数校验的都是**源头**，平台没有「预期目标头不符就拒绝」的比较并交换。目标头的保证要靠平台的另一条规则：分支保护开了「要求分支与目标同步」时，目标一旦前移，PR 就变成过期、合并被挡，等于替我们做了预期头检查；再加上源头匹配，合并结果的父提交就是可预期的。没有开这条规则的目标，适配器就要在绑定里声明「不能保证预期目标头」，集成意图的策略据此决定：拒绝，或者由人显式接受「目标可能前移、以回读为准」。这一条要在 B2 前用真实仓库验过；如果要放宽授权语义，交所有者裁决，不由适配器悄悄放宽。合入后的回读不能撤销已经发生的、超出授权的远端写入。

**已开启自动合并、已排队，都只是请求被接受，不是已合入。** 凭证只在回读到合并提交与目标头之后签。

## 七、B2 在受保护的 main 上走一遍：从封存到凭证

B2 是「无 Run」的第一次真正自举：不用 Run 这个受治理的自动施工，从聊天室发起一次真实代码改动并合入。v1 只写了后半程，Codex 指出前半程缺。完整走法如下，每一步标出归属和它依据的既有规则；带「拍板」的是新的取舍。

1. **发起。** 有权的人从 Project Room 发起写入型 Room Invocation（聊天室中的一次有边界调用），Trigger Preview 展示执行者、上下文、权限、预算。Execution Spec 冻结 ChangeSet 规则，**并冻结「评审发布策略」：封存后是否自动推分支并开或更新 PR，PR 描述从哪来**。所有者倾向这样做并加一个可选开关，未拍板，交各家审；理由见第 5 步。
2. **施工。** 工具箱物化独立工作树，执行体在有效写租约下改代码、在自己的分支上提交。执行体不持有平台凭据，不能自己推远端（第十节）。
3. **提案与封存。** 执行体提交 Result Proposal（执行结果提案）；归属模块 Project 按 `spec/connections.md` §Participant → Project / Run：结果准入 核对租约、代次、输出范围，然后经第五模块的「封存」命令取得 ChangeSet Revision 的精确引用，再准入提案。封存由工具箱执行；封存本身不是准入，平台上出现提交也不是准入。
4. **发布评审。** 按第 1 步冻结的策略，第五模块执行副作用命令：适配器推送变更集分支、创建或更新 PR，PR 描述来自提案里的文本产出（对我们自己的仓库就是三节描述）。这一步产生 ChangeSet–Platform 映射的第一条证据：该版本对应平台上的哪个提交。
5. **人的预览次数。** `contract-tests.md` 的 CT-PRODUCT 要求无 Run 路径从封存到完成凭证人只预览两次（合入、完成）。如果发布评审再要一次预览，就是三次。我的建议：发布评审的授权放在第 1 步的 Trigger Preview 里冻结，它发生在封存之前，不计入这两次；封存后不再单独预览发布。**所有者倾向采用这条并给仓库或项目一个可选的策略开关「发布评审须人显式确认」，未拍板，交各家审。** 开了开关的仓库自愿多一次预览，那是它自己的选择，产品的默认路径仍是两次。不能靠执行体自己推分支绕过。
6. **检查与评论。** 平台跑检查，评审者在 PR 上留评论。控制面回读检查与线程状态；评论正文按第五节走代取。
7. **返工。** 无 Run 路径没有自动返工。有权的人发起**新的** Room Invocation，`spec/project.md` §Room Invocation 规定重试创建新调用、不能复活旧调用；新调用的开工包里带上选中的评论；执行体在同一 ChangeSet 上产出新版本，封存为新 Revision；按策略更新 PR。目标主干在此期间前移的，新版本要以新的基线封存（执行体在自己的工作树里合并或变基目标，这是它的正常 git 操作），谁触发、按什么策略，P2 定。
8. **合入前的准入。** 有权的人预览「合入」：控制面读平台当前状态：必需检查是否齐全且对应的是当前候选版本的提交、线程是否解决、正式评审是否满足这份 Task 契约的要求、目标头是否仍是预期头。这不是 HCTL 的 Gate：`spec/connections.md` §Human Kanban / Run reducer → Task → Project 写明无 Run 路径不生成 Gate Receipt，`docs/design/task.md` §无 Run 的轻量路径 允许契约接受可回读的外部评审证据。只有契约要求内部独立评审时才先授权 Run。三个 `wait` 事实代替不了这一步的判断，一次 `PR contract` 成功也冒充不了全部验收。
9. **合入与凭证。** 人提交集成意图；控制面持久化意图与 outbox；适配器请求平台合并（源头匹配、目标保护由平台执行）；回读合并提交、目标头、PR 状态；确认后写 Integration Receipt。结果未知按第九节。
10. **完成。** 人在 Kanban 预览并提交「完成 Task」，Task 校验精确凭证与其余验收项，写完成凭证。这是第二次预览。

纯本地仓库的同一条链：第 4 步没有，第 6 步的检查是本地测试事实，第 7 步的评论来自 Scoped Room，第 8 步读的是本地目标头，第 9 步走 `hctl2-tool integrate`。两条链都要进 CT-PRODUCT。

## 八、与其他四个模块的连接

按 `spec/connections.md` §连接模型 的写法：每条连接交付一个冻结的、带摘要的不可变对象；来源模块不直接写目标模块。

- Project 到第五模块：注册 Repo 时第五模块激活身份，Project 在同一账本事务里建 Repo Room；Project 引用 Repo。
- Project / Run 到第五模块：获准的 Result Proposal 经第五模块的封存命令取得版本引用（第七节第 3 步）；Project 与 Run 保留各自的结果准入，第五模块不接收提案。
- 第五模块到 Participant：派工时 Execution Spec 冻结 ChangeSet 与 Write Lease 规则，工具箱按它物化独立工作树；失权时两个模块各做自己的动作（第四节）。
- 第五模块到 Run：评审对象引用指向本模块的 ChangeSet Revision 或 Project 的 Artifact Revision；Gate 的证据可以引用平台检查与评审状态，证据通道等级仍按「工具箱回读高于适配器结构化上报高于模型转述」记。
- 人、Run reducer 到第五模块：无 Run 时有权的人预览后直接提交集成意图；有 Run 时 Gate 通过后由有权的人或冻结的 reducer 提交。本模块准入、持久化、执行、回读、写凭证。
- 第五模块到 Task：Integration Receipt 作为 `mechanical` 验收项的证据；Task 的完成命令校验精确凭证。
- 平台事件到第五模块：映射到有权用户本人的平台动作在满足操作者、目标、版本、幂等依据齐全时可成为命令请求，其余只作快照或分歧；控制面自己写回产生的事件排除在外。接受哪些动作，第十节。

## 九、事实权威、失败与恢复

`spec/system.md` §全系统事实权威地图 加一行：

| 事实 | 权威来源 | 不可用时怎么降级 | 永久丢失时怎么重建 |
| --- | --- | --- | --- |
| PR 线程、平台评审状态、检查结果、合并状态（content） | 所选代码协作平台；控制面只保存变更集与 PR 的映射、事件引用与冻结摘要 | 依赖平台当前回读的命令安全拒绝：远端合入、读 PR 状态、发布评审；不依赖它的新操作继续：本地物化、封存、面向本地目标的集成。已提交的远端意图保持结果未知，不改道 | PR 讨论与平台评审状态丢失；Git 历史、变更集快照、账本里的凭证与裁决存活。可替换的接口不等于可迁移的历史，普通 clone 不带 PR 线程 |

恢复按**目标**分：

- 面向本地目标的意图，确认丢失时只回读它的本地目标与同一意图的 Git 证据，不等待任何 PR；这是 P1 丙已实现的行为。
- 面向远端目标的意图，合并请求超时或回执丢失时保持结果未知，继续占用冲突范围，即使本地已有同一结果树也不解锁；这是 `spec/system.md` §外部权威副作用 的原话「结果保持未知，并继续占用冲突范围以阻止重叠写」。PR 合并的恢复是 P2 要做的，P1 没有。
- 凭证的权威在账本，`spec/system.md` §Git 的双重角色 说 Git 里只有审计影子；平台丢失后不能凭 Git 提交重建凭证。

## 十、身份与安全：三条底线在这个模块的样子

- **合入钥匙不进工具。** 平台的写凭据只在控制面的适配器手里。执行体在自己的工作树里可以正常用 git 提交、看日志、和目标比对，但**不推远端**：远端推送、PR、合并全部走适配器命令，这是 `spec/participant.md` §不可关闭的三条底线 与 §ChangeSet 与 Git 事实 的原话。v1 写「也可以推自己的变更集分支到平台」是错的，删去。
- **工具箱的只读回读用 gh 复用用户登录，那仍是在用凭据。** 可信工具箱的只读回读，与执行体能自行调用持有写权限的 gh，是两回事；不能说工具箱「不碰平台授权」。也不夸大隔离：`spec/system.md` §安全边界 明说未启用加固时执行体与同一 OS 用户的其他进程在同一信任域。要说清的是 HCTL 不交付什么凭据、谁代用什么，不新增未实现的物理隔离承诺。
- **平台动作到命令的映射要逐项写。** 账号映射只证明来源，不证明「在 PR 上批准」等于「授权合入」。约束批里要列：接受哪些平台动作（批准、请求修改、评论、合并按钮）、各映射到什么（Gate 的一票、无 Run 路径的评审证据、只作快照）、是否要先预览、是否允许自动提交；控制面自己写回的事件排除。依据 `spec/system.md` §客户端动作与 provider 事件。
- **席位身份是 Participant，不是平台账号。** 今天四家 harness 的评论都经同一个 GitHub 账号发出（GPT 备忘回读 #176 证实），映射不出席位；共享账号不产生多张独立票。正式 Gate 在交付文档里是 **B4** 引入，不是 v1 写的 B3。到那时席位经 HCTL 命令投票，控制面把结论写回 PR；是否给参与者各自的平台身份，P2 定。

## 十一、命名：候选与理由，交各家挑

所有者 2026-09-06 的裁定：把候选和理由写清楚，让各家审阅者来挑；模块与场景不要同名，Change / Change 这种组合太一致，排除。下面先列要守的规矩，再列候选。

**命名要守的三条。** 第一，模块按它拥有的根对象或它治理的事命名，前例是第四模块从 Agent 改名 Participant，决策史 §34 的原话是「第四个模块从一开始就是干活的那一方，只是名字取错了」。第二，场景按人在那里做的事命名，四个老场景是聊天室、看板、施工图、终端。第三，核心产品词是英文单词加中文对照，不用缩写。

**模块名候选。**

| 候选 | 好处 | 代价 |
| --- | --- | --- |
| Change（变更） | 说的正是模块治理的事：一次变更从产生、封存、评审到进入目标的全过程；Gerrit 把待评审的变更就叫 Change；Codex 主审选它 | 与 ChangeSet（变更集）、ChangeSet Revision（变更集版本）三个词叠在一起，「Change 模块」可能被误读成「一个变更集」；中文「变更」与「变更集」倒是分得开 |
| Repo（仓库） | 最符合「模块按根对象命名」：Repo 是根，下面挂现场、变更集、集成；中文对照现成 | Repo 已经是横跨各模块的限定词：Repo Room 归 Project，Repo Board 归 Task，Repo policy 归系统层，「一个 Repo 一个 Board」到处都是。叫「Repo 模块」之后，读者见到「Repo 某某」要多分辨一层：这是 Repo 模块的对象，还是别的模块里按仓库划定的东西。所有者问它会不会和 Project 撞车：不直接撞 Project 这个模块，撞的是这个限定词用法 |
| SCM | 与所有者口头说法一致；「源码管理」确实涵盖本地 git 与平台 | 缩写，没有自然的中文对照；是外部系统的类别名；已经用作适配器名 SCM provider，模块再用会混 |

**场景名候选。**

| 候选 | 好处 | 代价 |
| --- | --- | --- |
| Change（变更） | 人在这里看的就是一次变更：diff、讨论、检查、集成状态；GitHub 的 PR 页面、GitLab 的 MR 页面、Gerrit 的 change 页面的公共称呼 | 与模块名 Change 同名的组合已被排除；作为场景名时，它与变更集对象的关系要在词表里说一句 |
| Review（评审） | 直观，PR 页面的日常叫法 | 「评审」在 Run 模块的约束里已经是 Gate 的词汇：评审席位、评审对象引用、评审策略、增量评审，`spec/run.md` 出现九处。场景也叫评审，文档里要一直靠「Gate 评审」「评审场景」消歧 |

**可选的组合。** Change / Review（Codex 之选，代价是评审撞词）；Repo / Change（我在与所有者讨论时的倾向，代价是 Repo 限定词的歧义）；Repo / Review（两种代价都有）；SCM / Change、SCM / Review（缩写，且与适配器同名）。审阅者请挑一个组合并给一句理由；所有者最后定。

不论选哪个：「SCM provider」留作平台适配器的称呼；新增的只是模块名与场景名，不新增一个同名的持久对象，对象仍是 Repo、Repo Instance、ChangeSet、ChangeSet Revision、Write Lease、集成意图与 Integration Receipt；两个名字都是用户可见词，首现带中文对照。本文其余各节用「第五模块」「第五场景」占位。

## 十三、契约测试补核

CT 是契约测试的族名，测可观察的成功与拒绝行为。除新增 CT-<模块名> 外，至少改这些：

- CT-PROJECT：「首次注册生成稳定 Repo 身份、同一 Repo 的新 clone 只新增 Repo Instance、fork 或身份碰撞拒绝」这一条的责任迁到 CT-<模块名>，但 Repo Room 的唯一性与同事务连接仍在 CT-PROJECT 测。
- CT-CONNECTION 与 CT-<模块名>：新旧写租约的交接（第五模块撤权、Participant 隔离、确认前不重授）；Project 归档时仍能看见迁走的活动租约与未决集成；未经 Project 或 Run 准入的提案不能产生获准版本；平台批准、控制面自己写回的批准、重复事件、无法映射的动作各走正确的来源规则；执行体拿不到远端写凭据。
- CT-RUN：Artifact Revision 的评审仍成立；同一 PR 换结果树，旧票不能用于新版本；同一版本换提交包装不改变评审身份。
- CT-<模块名> 与 CT-TASK：契约冻结要求远端检查时，本地成功不能顶替；远端合并回执丢失、目标竞争、换绑都不能写错凭证；同一意图重试只得同一结果；「已开启自动合并」不算已合入。
- CT-PRODUCT：无平台的普通仓库与受保护的 `main` 两条 B2 成功路径，都不能借 Gate、特例权限或第三次强制预览过关；纯本地用例覆盖目标正被检出与确认丢失后的恢复。
- CT-WORKBENCH-IA：没有 Workbench 时第五场景对应的命令仍可达；改「Overview 不是第五场景」的字样时保住「Overview 只是投影」的原义。
- CT-SYSTEM：现有「executor 越界拒绝」一条改指新模块的工具箱与适配器。

## 附录一：操作模块后端的四级顺序（所有者 2026-09-06）

顺序：第一，随包发布的官方命令行工具，以工具调用的方式使用；第二，官方 SDK；第三，读接口描述自动生成客户端；第四，完全手写。这是在研究层现有三级顺序（官方 SDK、生成、手写）顶上加一层，方向与交付文档「跨平台二进制优先于 SDK」的借用偏好一致。落点：`delivery.md` §选型判据 与 §技术基线、`docs/research/sdk/README.md`。

Codex 的提醒要写进去：**有官方命令行，不等于我们需要的调用面已经满足**。要逐个操作核对它能不能给结构化结果、能不能带身份、能不能做条件写入。第六节的源头与目标头就是反例：换成 gh 不会自动得到约束要求的预期目标头保证。逐家看：GitHub 有 gh，已随包，控制面一侧原定的 octocrab 退为第二选择，gh 的短处（每次调用起进程、不能接收 webhook、App 身份只能拿预先换好的安装令牌）留到 B2 权衡；GitLab 有官方 glab；Dagu 的二进制自带命令行；Herdr 有命令行，打包冒烟测试已在用；这四家先按第一级核对调用面，核对不过再降级。Matrix 没有官方命令行，第二级，ruma；Vikunja 与 Linear 没有官方命令行也没有官方 Rust SDK，第三级，从接口描述生成。已有研究文件的结论有变的，逐份追加复核记录，不只改目录总表。
