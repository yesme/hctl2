## 一、要决定什么，以及我的判断

起因是一个观察：我们开发 HCTL2 自己的时候，走的一直是「开 PR、几位审阅者在评论里给意见、作者改、再审、合入」这条路。这条路把协作放在了 GitHub 上，而设计文档没有明说这个依赖。所有者问：要不要显式地放进设计？如果放，是不是恰好就是第五个模块？

先说事实。约束层没有把 GitHub 定为必需：它只在 Task 模块里作为任务后端的例子之一出现，与 Linear 并列。远端代码托管一侧，文档一律写「远端 SCM」这个通用词，GitHub、GitLab、Gitea 都算；把改动推到远端、开 PR、合并 PR 由适配器做，适配器就是把我们的命令翻译给某个外部系统的那层代码。远端副作用本身已有完整规则：`spec/system.md` §外部权威副作用 规定意图先持久化、记录绑定与冲突范围、结果未知怎么处理；`spec/participant.md` §ChangeSet 与 Git 事实 规定集成命令要固定哪些字段。**缺的不是规则，是三样东西**：这些对象与规则的领域归属（今天散在 Participant、Project 和系统层）；平台上的内容（PR 线程、评审状态、检查结果）在事实权威地图里没有位置；以及两条产品路径（经平台合入、纯本地合入）各自怎么走、怎么降级。`spec/system.md` §固定内核与受控端口 里「可以替换的端口」那张表只有四行、没有代码托管这一行，是这个缺口的表面症状（同文件 §场景端口 说的是查询、预览、提交、订阅四类公共操作，新模块不增加第五类操作）。实现层今天确实用了 GitHub：工具箱的 `wait` 命令读 CI 状态、PR 是否合并、分支是否推进，用的是随包带的 gh。

再说判断。**成立：代码变更与集成应立为第五个模块，理由是它拥有一组有独立生命周期、恢复边界和权限边界的治理事实，不是因为它有一个平台客户端。** 它有两条正式的集成路径，经平台和纯本地，按每次集成的目标选，不是全局开关。它要从三个地方把已有对象搬进来（变更集与集成从 Participant，Repo 注册从 Project，Repo Instance 从系统层），并给工具箱一个正式的家。它有自己的场景。下面分节展开。

## 二、为什么是模块：按治理责任，不按客户端

`docs/design/spec/README.md` §词汇分类法 给「独立对象」的判据是：有独立的生命周期、恢复边界或权限边界。模块是拥有一组这样的对象并为它们定写入者与不变量的归属者。用这个判据看代码变更与集成：

- **Repo（逻辑仓库）** 有自己的稳定身份和注册命令，先于任何 Project 存在，一个 Repo 承载多个 Project；它的恢复边界是「Git 中的身份与账本中的身份互证」，与 Project 的目标、范围无关。
- **Repo Instance（一台机器上的物理现场）** 有自己的挂接、移除、现场锁与代次栅栏；它的身份不附属于任何一次执行，恢复时按 `spec/system.md` §控制面自己的存储 的规则，从账本、Git 与运行时观测三方对账重建，其中包括核对现场上仍在跑的执行。
- **ChangeSet 与 ChangeSet Revision（获准的写入边界及其不可变版本）** 有自己的只追加版本序列和写权；写入者换人、接管、取消都是它这一侧的失权动作；恢复边界是「证明不了旧写入者失权就隔离现场」。
- **集成意图与 Integration Receipt（把精确版本合入目标的持久授权与回读证明）** 有自己的状态（待启动、结果未知、成功、失败）、幂等键和冲突范围；权限边界是「合入钥匙不进工具，只有持有当前代次栅栏的工具箱或适配器代用」。

这四组东西今天分属三个归属者，而它们之间的不变量（版本必须在有效写权下封存、集成必须固定版本与预期头、Receipt 只在回读后签发）是同一条链上的。把链的各环放进一个模块，写入者与恢复规则才能在一处判定。这是立模块的理由。四家评审对这一节都维持。

v1 用的理由是「一个自带原生客户端的外部系统就是一个新场景，一个场景绑一个模块」。Codex 指出这条推导不成立，我接受：Vikunja、Linear、GitHub 都有原生客户端，却是同一个 Kanban 场景的候选；同一个 GitHub 可以同时承载任务卡和代码评审；`spec/system.md` §组件 明说第三方平台可以同时提供场景客户端和受控端口、两种接入分别绑定。更要紧的反证是：纯本地仓库没有任何平台内容系统，这个模块照样要存在，所以模块的存在不能挂在 GitHub 的界面上。

平台内容在哪里落脚，是立了模块之后的第二个问题，不是立模块的理由。答案是：PR 线程、平台评审状态、检查结果、合并状态是这个模块的场景内容，事实源在平台，控制面只保存映射、引用与冻结摘要；纯本地仓库没有这类内容，场景显示本地事实，讨论回到聊天室。

这个模块**不是**什么：不是第四个「面」，三面架构不变；不是通吃各模块的垫片，`docs/design/architecture.md` §避免供应商锁定 的禁令继续有效；不把控制面变成内容仓库，控制面照旧只存身份、准入、摘要、映射和凭证；也不新造一个通用的外部副作用系统，那一层留在系统层。

## 三、工具箱总在，平台按仓库绑定：两条集成路径与冻结的契约

所有者要求纯本地集成有正式方案，类比 Participant 模块的 Agency：本地参考实现随包发布、总是可用，远端供应端可以外接。这个模块的样子是：

**GitHub 是缺省的平台实现，不是唯一实现，也不点名谁是第二个。** 代码协作平台是一个端口，接在上面的供应端可以是托管服务（GitHub、GitLab.com），也可以是自建服务器（GitLab 自建版、Gitea、Forgejo、Gerrit）；对我们它们是同一种东西，差别用绑定上的能力声明表达。本批只实现 GitHub 的适配器，因为我们自己的仓库在上面（所有者已拍板）；未来支持哪些后端、先后如何，看研究层的市场调研（第十二节），不在这里下结论。集成目标因此分三类：某个 Repo Instance 上的本地 ref、自建平台上的远端 ref、托管平台上的远端 ref；后两类走同一个端口。

**工具箱是每个仓库都有的本地执行者，不是「本地供应端」与「平台供应端」二选一。** 无论仓库有没有平台，物化工作树、封存版本、读取 Git 事实、本地现场锁都由 `hctl2-tool` 做；平台仓库照样要它。平台适配器只管平台上才有的事：推送分支、开或更新 PR、读检查与评审状态、请求合并。两者是分工，不是互斥。

**两层绑定，别混成一个名字。** 仓库一级是 Port–Provider Binding（`spec/system.md` §固定内核与受控端口：固定供应端、配置、凭据引用、实测能力和降级策略），写明这个仓库有没有平台、哪个平台、平台上的仓库身份、目标分支的保护条件、能不能保证预期目标头。版本一级是第四节的变更与平台映射，记「这个冻结版本当时对应平台上哪个提交、哪条 PR」。`spec/README.md` 的 Binding 族规则是「一条绑定钉一对外物」，这两层各钉各的。Grok 指出 v4 把两层混叫，这里分开。

**集成路径按目标选。** 每一次集成意图必须固定自己的目标：是某个 Repo Instance 上的本地 ref，还是平台上的远端 ref；固定目标 ref 名、预期目标头（或第六节说的另一种授权形态）、所用绑定的版本。本地目标走工具箱的比较并交换，远端目标走适配器。同名的本地分支和远端分支是两个目标，对本地 `main` 做的集成不能算作远端 `main` 已合入。依据是「同一端口种类和作用域在一次准入中只能解析出一个绑定版本」「已有执行继续使用原绑定」。

**能力声明决定契约能不能被满足，不能替人改契约。** 绑定要声明平台有没有评审线程、有没有正式评审状态、有没有检查、能不能远端合入、有没有身份映射、能不能保证预期目标头（第六节）。这些声明在两个时刻起作用：采纳契约、预览集成时，控制面据此判断契约里的验收项能不能由这个仓库的供应端满足；执行时，缺了声明过的能力，命令等待、拒绝或标为需要关注。v1 写过「没有检查就让机械验收项只认本地事实、没有远端合入就走本地比较并交换」，这是错的，与 `spec/system.md` §命令与跨服务正确性 的「组件不可用不会改变命令前置条件」冲突：契约要求 GitHub 的三个检查通过，平台失联时本地测试退出码为零不能顶替；契约要求合入远端 `main`，本机 `main` 前移不能顶替。改契约只能由有权的人显式做。

**纯本地仓库是完整的正常路径，不是降级。** 一个从头到尾没有平台的仓库，契约在采纳时不会要求平台上才有的机械证据，但 `spec/task.md` §契约与来源 的三种校验等级它都可以有：机械项的证据是工具箱回读的本地事实，例如测试的退出码与输出、本地目标头；要人判的项由人判；要内部评审的项先授权 Run。本地事实是例子，不是一份完整的证据白名单。讨论在 Project 模块的 Scoped Room，也就是为某个变更开的专题聊天室；集成走 `hctl2-tool integrate`；凭证照常写。将来给它绑上平台，是加一份绑定、多一类目标和能力；Repo 身份、既有版本与凭证不变，进行中的意图沿用原绑定版本。

**本地目标被工作树检出时的正常入口。** P1 丙的 `integrate` 在目标分支正被某个工作树检出时默认拒绝（人的主工作树通常停在 `main`，改动在另一个工作树，集成回 `main` 就是这个情形）；显式放行时只推进 ref，不更新那个工作树的文件与索引，人接着一次普通提交就会把集成撤销。**本地路径的正式走法定为：人先把目标工作树切离目标分支（切到别的分支或 detach），再重试同一意图；工具箱在拒绝时给出精确的工作树路径与这个恢复动作。** Grok 与 GPT 都指出这不能留成「P2 再选」，因为第七节的 B2 走法与第十三节的契约测试都要覆盖它。另一种处理，只在目标工作树干净时顺带更新它（形态类似 git 的 `receive.updateInstead`），可以以后再做，不是本地路径的前置。

## 四、模块拥有什么：对象迁移表

「现在在哪」以 v0.16.5 为准。这张表是 v0.17.0 改文档的清单之一。

| 对象 | 现在在哪 | 挪到第五模块后 | 说明 |
| --- | --- | --- | --- |
| Repo（逻辑仓库的稳定身份与注册） | Project 模块，`spec/project.md` §Repo 注册与 Project 归档 | 第五模块拥有身份、注册命令、Git 中稳定身份的写入与回读 | Project 保留「一个 Repo 一个 Repo Room」与 Project 归属于 Repo 的关系；注册确认与建 Repo Room 仍在同一账本事务里，见第八节 |
| Repo Instance（物理执行现场） | 系统层，`spec/system.md` §Repo 与执行现场；`spec/participant.md` 文件头也写着「Repo Instance 仍归系统层」 | 第五模块拥有挂接、移除、现场记账 | `site_generation` 继续列在系统层的代次家族表，指向本模块；工具箱无副作用读身份这一步不变；participant 文件头那句同批改 |
| ChangeSet 与 ChangeSet Revision | Participant 模块，`spec/participant.md` §对象、§ChangeSet 与 Git 事实 | 第五模块拥有；封存、保全、拆除这些工具箱动作随之归本模块 | Participant 的三条底线里「隔离工作树」继续引用本模块的 ChangeSet。迁模块不等于升可见性：ChangeSet 在 `spec/README.md` §核心产品词 仍是治理内部，场景给人看的是 diff 的投影，词表要写清（Grok） |
| Write Lease（对一个 ChangeSet 的独占写权） | Participant 模块，与 ChangeSet 同一行 | **方案甲：随 ChangeSet 进第五模块。** 我与 Codex 首审选它，四家评审一致支持，所有者倾向甲、待拍板 | 唯一写权和「封存前置是有效租约」是同一条判定链，放在同一归属者。失权是两个模块各做自己的动作：第五模块记撤权、不重授；Participant 停止或隔离旧执行并提供证据，证明不了就不重授（`spec/connections.md` §失败与恢复 要求同一事务撤销租约并提交停止、隔离记录）。两边不各建一份写租约 |

| 变更与平台的映射 | 没有 | 新增，双端命名，例如 ChangeSet–Platform Binding | 更新规则见下 |
| 平台账号与人的映射 | 没有（可参照 Room 的聊天账号身份映射） | 新增，放在平台绑定里 | 只有映射到有权用户本人的平台动作才可能成为命令请求；接受哪些动作、映射到哪个命令，第十节 |
| 外部机械事实（CI 状态、PR 是否合并、引用推进、路径与摘要） | 工具箱 `wait` | 归本模块的读侧 | 语义不变；Run 的节点前置继续只认工具箱回读 |
| Git 的双重角色（不可变正文与判决结晶副本） | 系统层，`spec/system.md` §Git 的双重角色 | 规则留在系统层，因为 Task Revision、Workflow Revision、Memo 的正文写入是跨模块的 | 只补一句「执行者是本模块的工具箱」 |

**评审身份与变更与平台的映射怎么更新。** 评审身份是评审对象摘要，`spec/participant.md` §ChangeSet 与 Git 事实 规定它由 `{change_set_revision_id, change_set_id, parent_revision_id?, base_commit_sha, result_tree_sha}` 生成，提交 SHA（`result_commit_sha`）不在其中。所以：同一个获准版本只是换了提交包装（比如重新生成了一个内容相同、基线相同的提交），身份不变；基线变了、或结果树变了，就是新版本，旧裁决按 Run 的返工规则失效。v4 写过「树没变就版本不变」，GPT 指出这是把树相同当成了充分条件，错在漏了基线，这里改正，也和第七节第 7 步「换基线就封新版本」对上了。映射记两类东西：PR 的当前状态（当前头、检查、线程）是回读事实，随时变；「某个冻结版本对应当时平台上的哪个提交」是证据，冻结后不变。PR 的头变了，工具箱重算基线与结果树，按上面的规则判是不是新版本。一个 ChangeSet 对应几个 PR、一个 PR 能不能换 ChangeSet，交付文档仍列为未决，本备忘不在绑定名字下默认一对一。

**不搬的东西。** Gate、Seat、Verdict 留在 Run；评审对象引用（ReviewSubjectRef）继续是「对 ChangeSet Revision **或 Artifact Revision** 的精确引用」，`spec/run.md` §对象 原文如此，纯文档工件的评审不能被搬没；Artifact Revision 是 Project 登记的工件版本，它到 Run 的引用是既有连接，不经第五模块转交（GPT）。Task Revision 与完成凭证留在 Task。Execution Spec 里「可选 ChangeSet / Write Lease 规则」留在连接约束，它是派工时冻结的。

## 五、场景：代码评审，以及评论怎样回到作者手里

这个场景回答：这一次变更改了什么、谁怎么看它、检查过了没有、它进目标了没有、怎么让它进去。

- 看：某个版本的精确 diff（今天写在 Project 场景和 Participant 那一行，要挪来）、评审讨论（平台上的 PR 线程，或本地仓库的 Scoped Room）、检查结果、集成状态与凭证。
- 做：发布评审（推分支、开或更新 PR）、发起集成（预览、提交）、把 Gate 的结论写回平台。写回是记录，走已有的副作用命令，不绕过授权；写回产生的平台事件不再触发一次人的请求，这是 `spec/README.md` §三类数据 的第三条法。
- 原生客户端：GitHub 的 PR 页面和 gh；其他平台各有对应的页面与命令行工具，例如 GitLab 的 MR 页面和 glab。Workbench 到 P3 才做投影；P2 用命令行。
- 命令行：`repo register|list|show`、`repo instance attach|list|show|detach` 从「Repo / Project」组挪来；`changeset show|diff`、`integration preview|submit|show` 从今天叫「Participant / Integration / Terminal」的那一组挪来（以约束批落地时交付文档的现文组名为准，GLM）；新增发布评审的命令。命令名不改。

评审这个词在 Run 模块已经用在 Gate 上，要划清：Gate 是 Run 模块的判定，`spec/run.md` §Request、重试与 Gate 说它是 Run 内冻结的治理节点和规则；代码评审场景是内容与状态的呈现处，Gate 的裁决在这里只是投影，就像 Task 的状态出现在看板上一样。

**评论怎样回到作者手里，是这次需求的本体，v1 漏了。** 我们自己的流程之所以能转，是因为作者读得到评审意见。在产品里，作者是下一次调用的执行体，它拿不到平台评论：`docs/design/context.md` §投喂三档 规定指针只能指向执行体自己能打开的 Git 对象和工作树路径，平台评论不是；所以评论走「代取」，由控制面的组装器取回、冻结来源与摘要、放进开工包。今天代取来源只列了聊天史、任务后端评论线和账本里的裁决与凭证，要加一项：**平台评审评论线**，普通评论与正式评审都算，按精确的版本与评论标识冻结。评论进入上下文只是给作者看，它本身不变成授权、契约或裁决；能证明什么，看验收契约（GPT）。本地仓库没有这一项，讨论本来就在聊天室里，走既有路径。

## 六、端口：操作面、目标保护、两个「头」

端口只放我们实际会调用的操作，按自举等级逐步长出来，不预先设计通用对象模型。多平台工具的共同做法是窄接口、第一个平台先做、第二个平台进来时修正接口，并且保留假的或本地的驱动给测试用（go-scm 有 fake 驱动，Renovate 有 local 平台，Zuul 有纯 git 驱动）。这些先例说明「按能力拆接口」可行；它们不能为我们的正式本地集成背书，本地路径按自己的真实功能验收。

B2 的「无 Run 切片」第一次消费这个端口，需要的操作：

| 方向 | 操作 | 平台（GitHub） | 本地 |
| --- | --- | --- | --- |
| 读 | 仓库身份、目标 ref 当前头 | gh 加本地 git | 本地 git |
| 读 | PR 当前头、必需检查逐项状态与时效、评审线程是否解决、正式评审状态、合并资格、目标保护条件 | gh；今天的 `wait` 有五类事实，其中三类是 GitHub 事实（提交的检查、PR 是否合并、引用是否推进），不含评审线程、正式评审与保护条件，要补 | 无平台事实；契约只能要求本地证据 |
| 读 | 评审评论正文（供代取） | gh | 无 |
| 写 | 推送变更集分支、开或更新 PR（含三节描述） | 适配器经 gh | 无 |
| 写 | 把 Gate 结论或集成结果写回 PR | 适配器经 gh，用控制面自己的平台身份 | 无 |
| 写 | 合入目标 | 适配器请求平台合并，回读合并提交与目标头 | `hctl2-tool integrate` |
| 映射 | 平台账号到人 | 绑定里配置 | 不需要 |

**目标保护不止「是否必须 PR」。** 绑定要能回读目标分支的保护条件：必须经 PR 与否、必需检查的清单、是否要求分支与目标同步、是否要求评审线程解决、要求的正式批准数。几个检查为绿不等于平台允许合入。预览时读到的保护条件要作为快照冻结进集成意图，执行与回读时对照，上游悄悄改了规则不能让账本失序（Antigravity）。我们自己的 `main` 今天是：必须经 PR，必需检查 `CI gate`、`Release gate`、`PR contract`，要求与目标同步，要求线程解决，管理员也受约束，要求的正式批准数为零。

**两个「头」要分清，而且平台给不了目标头的比较并交换。** 源分支头是待合入的提交；目标分支头是预览时主干所在的提交。约束要求集成命令固定「预期目标头」，本地路径用 `update-ref` 的旧值比较做到了。实现层脚注：gh 的 `pr merge --match-head-commit` 和 GitHub 合并接口的 `sha` 参数校验的都是**源头**；GitHub 没有「预期目标头不符就拒绝」的参数。v4 曾写「分支保护开了『要求与目标同步』就等于替我们做了预期头检查」，GPT 推翻了这条推论，我接受：同步要求只保证合并时候选分支包含当前主干，不保证主干还停在预览时的位置。规则层的反例：主干 A，预览时目标是 A；之后主干前移到 B，候选分支也更新到包含 B 的 H；同步要求满足、源头匹配，平台照常合并，可是预期的 A 早已不是当前头。合并队列也一样，它在最新主干上重新验证候选，语义是「接受目标前移、重新验证」，不是「目标没动才合」。所以 GitHub 的绑定必须声明「不能保证预期目标头」；据我所知没有哪家平台能保证。那怎么办，是第十五节第 5 项：两种授权形态，人事前选，不是执行时降级。

**已开启自动合并、已排队，都只是请求被接受，不是已合入。** 凭证只在回读到合并提交与目标头之后签。合并后的回读不能撤销已经发生的、超出授权的远端写入。

## 七、B2 在受保护的 main 上走一遍：从封存到凭证

B2 是「无 Run」的第一次真正自举：不用 Run 这个受治理的自动施工，从聊天室发起一次真实代码改动并合入。**前置**（GPT）：已有一个活跃的 Project，以及一个开放的、已采纳验收契约的 Task；没有契约的卡不进这条链，「两次预览」的产品约束也只对有契约的 Task 计数。每一步标出归属和它依据的既有规则。

1. **发起。** 有权的人从 Project Room 发起写入型 Room Invocation（聊天室中的一次有边界调用），Trigger Preview 展示执行者、上下文、权限、预算。Execution Spec 冻结 ChangeSet 规则，**并冻结「评审发布策略」**。发布策略要有范围，不是一句「允许发布」（GPT）：固定仓库、平台绑定版本、发布到哪个分支或 PR 的规则、允许创建还是也允许更新、PR 描述从哪来（执行体提案里的文本产出）；真正发布时再固定精确版本与文本摘要；提案只能提供被允许的内容，不能换发布地点、不能扩大权限，这是 `spec/connections.md` §版本、权限与替代 「权限只能逐级缩小」的应用。仓库或项目可以设可选开关「发布评审须人显式确认」，开关的值随本次授权冻结，以后改默认值不影响已接受的调用。Trigger Preview 要写明：这里授权的是发布去评审，不是合入（Grok）。所有者倾向这个做法，四家一致支持，待拍板。
2. **施工。** 工具箱物化独立工作树，执行体在有效写租约下改代码、在自己的分支上提交。执行体不持有平台凭据，不能自己推远端（第十节）。
3. **提案、封存、准入。** 执行体提交 Result Proposal（执行结果提案）。要分开两件事（GPT）：工具箱把工作树内容封存成 Git 字节并回读，这是保存；账本接受这次结果和这个版本，这是准入。顺序是：工具箱按有效租约封存并回读；控制面复核调用状态、代次、租约仍然有效；然后 Project 准入提案、第五模块准入版本，两者连同来源关联、必要的发布记录在同一账本事务里提交。封存期间被取消的调用，不能因为 Git 对象已经存在而继续走到发布；平台上出现一个提交也不是准入。
4. **发布评审。** 按第 1 步冻结的策略，第五模块执行副作用命令：适配器推送变更集分支、创建或更新 PR，PR 描述来自提案里的文本产出（对我们自己的仓库就是三节描述）。这一步产生变更与平台映射的第一条证据：该版本对应平台上的哪个提交。
5. **人的预览次数。** `contract-tests.md` 的 CT-PRODUCT 要求无 Run 路径从封存到完成凭证人只预览两次（合入、完成）。发布评审的授权在第 1 步，发生在封存之前，不计入这两次；它合法的原因是第 1 步把授权范围写清了，不只是「在计数窗口之外」（GPT）。开了「须人显式确认」开关的仓库自愿多一次预览，那是它自己的选择，产品的默认路径仍是两次，契约测试要把这两条路分开写（第十三节）。
6. **检查与评论。** 平台跑检查，评审者在 PR 上留评论。控制面回读检查与线程状态；评论正文按第五节走代取。
7. **返工，以及主干前移。** 无 Run 路径没有自动返工。有权的人发起**新的** Room Invocation，`spec/project.md` §Room Invocation 规定重试创建新调用、不能复活旧调用；新调用的开工包里带上选中的评论。新调用在同一个 ChangeSet 上产出新版本的前提是旧写入者已经失权；证明不了就按第三节隔离现场、由人选择接管、采用或丢弃，不能把每次返工都强行套成原现场接管（GPT）。评审期间主干前移是常态（Grok）：第 8 步一发现预期头漂移，本意图拒绝；人开新调用，执行体在自己的工作树里把新主干合并进来或变基上去（这是它的正常 git 操作），封存为新版本——基线变了，按第四节它就是新版本，旧评审失效；然后按策略更新 PR、重跑检查。这是默认走法，不留「P2 定」。
8. **合入前的准入。** 有权的人预览「合入」：控制面读平台当前状态：必需检查是否齐全且对应的是当前候选版本的提交、线程是否解决、正式评审是否满足这份 Task 契约的要求、目标头是否仍是预期头（或按第六节选定的另一种授权形态核对保护条件）。这不是 HCTL 的 Gate：`spec/connections.md` §Human Kanban / Run reducer → Task → Project 写明无 Run 路径不生成 Gate Receipt，`docs/design/task.md` §无 Run 的轻量路径 允许契约接受可回读的外部评审证据。只有契约要求内部独立评审时才先授权 Run。三个 `wait` 事实代替不了这一步的判断，一次 `PR contract` 成功也冒充不了全部验收。
9. **合入与凭证。** 人提交集成意图，意图里写明选的是哪种授权形态（第十五节第 5 项）；控制面持久化意图与 outbox；适配器请求平台合并（源头匹配；目标保护由平台执行）；回读合并提交、目标头、PR 状态，对照冻结的保护快照与所选形态；确认后写 Integration Receipt，凭证记实际的目标头。结果未知按第九节。
10. **完成。** 人在 Kanban 预览并提交「完成 Task」，Task 校验精确凭证与其余验收项，写完成凭证。这是第二次预览。

纯本地仓库的同一条链：第 4 步没有，第 6 步的检查是本地测试事实，第 7 步的评论来自 Scoped Room，第 8 步读的是本地目标头并要求目标工作树已切离，第 9 步走 `hctl2-tool integrate`。两条链都要进 CT-PRODUCT。

## 八、与其他四个模块的连接

按 `spec/connections.md` §连接模型 的写法：每条连接交付一个冻结的、带摘要的不可变对象；来源模块不直接写目标模块。

- Project 到第五模块：注册 Repo 时第五模块激活身份，Project 在同一账本事务里建 Repo Room；Project 引用 Repo。
- Project / Run 到第五模块：按第七节第 3 步的顺序，工具箱封存并回读之后，Project 或 Run 准入提案、第五模块准入版本，同一事务；提案的接收者仍是 Project 或 Run，第五模块不接收提案。
- 第五模块到 Participant：派工时 Execution Spec 冻结 ChangeSet 与 Write Lease 规则，工具箱按它物化独立工作树；失权时两个模块各做自己的动作（第四节）。
- 第五模块到 Run：评审对象引用指向本模块的 ChangeSet Revision；Artifact Revision 的引用是 Project 到 Run 的既有连接，不经这里。Gate 的证据可以引用平台检查与评审状态，证据通道等级仍按「工具箱回读高于适配器结构化上报高于模型转述」记。
- 人、Run reducer 到第五模块：无 Run 时有权的人预览后直接提交集成意图；有 Run 时 Gate 通过后由有权的人或冻结的 reducer 提交。本模块准入、持久化、执行、回读、写凭证。
- 第五模块到 Task：Integration Receipt 作为 `mechanical` 验收项的证据；Task 的完成命令校验精确凭证。
- 平台事件到第五模块，按 `spec/system.md` §客户端动作与 provider 事件 分四类（GPT）：普通评论只进上下文；批准与请求修改是外部评审证据，能证明什么由契约定，账号映射只证明来源，不把它变成 Gate 的一票；HCTL 席位的投票走第十节的提案路径；平台上「已经合并了」的通知不是事前授权，有匹配的持久集成意图时供回读，没有时只作外部事实和对账，不能倒补「先意图、后副作用」。控制面自己写回产生的事件排除在外。

## 九、事实权威、失败与恢复

`spec/system.md` §全系统事实权威地图 加一行：

| 事实 | 权威来源 | 不可用时怎么降级 | 永久丢失时怎么重建 |
| --- | --- | --- | --- |
| PR 线程、平台评审状态、检查结果、合并状态（content） | 所选代码协作平台；控制面只保存变更集与 PR 的映射、事件引用与冻结摘要 | 依赖平台当前回读的命令安全拒绝：远端合入、读 PR 状态、发布评审；不依赖它的新操作继续：本地物化、封存、面向本地目标的集成。已投递或可能已投递的远端意图保持结果未知，不改道 | PR 讨论与平台评审状态丢失；Git 历史、变更集快照、账本里的凭证与裁决存活。可替换的接口不等于可迁移的历史，普通 clone 不带 PR 线程 |

恢复按**目标**分，状态按**是否可能已写**分（GPT）：

- 面向本地目标的意图，确认丢失时只回读它的本地目标与同一意图的 Git 证据，不等待任何 PR；这是 P1 丙已实现的行为。
- 面向远端目标的意图：确定尚未投递的仍是待启动，可以照原意图重投；已经可能产生远端写入而无法确认的才是结果未知，保持未知、继续占用冲突范围，即使本地已有同一结果树也不解锁，这是 `spec/system.md` §外部权威副作用 的原话「结果保持未知，并继续占用冲突范围以阻止重叠写」。两种状态都不能改道、不能签成功凭证。PR 合并的恢复是 P2 要做的，P1 没有。
- 凭证的权威在账本，`spec/system.md` §Git 的双重角色 说 Git 里只有审计影子；平台丢失后不能凭 Git 提交重建凭证。

## 十、身份与安全：三条底线在这个模块的样子

- **合入钥匙不进工具。** 平台的写凭据只在控制面的适配器手里。执行体在自己的工作树里可以正常用 git 提交、看日志、和目标比对，但**不推远端**：远端推送、PR、合并全部走适配器命令，这是 `spec/participant.md` §不可关闭的三条底线 与 §ChangeSet 与 Git 事实 的原话。
- **工具箱的只读回读用 gh 复用用户登录，那仍是在用凭据。** 可信工具箱的只读回读，与执行体能自行调用持有写权限的 gh，是两回事；不能说工具箱「不碰平台授权」。也不夸大隔离：`spec/system.md` §安全边界 明说未启用加固时执行体与同一 OS 用户的其他进程在同一信任域。要说清的是 HCTL 不交付什么凭据、谁代用什么，不新增未实现的物理隔离承诺。
- **席位怎么投票。** Gate 的席位是 Run 里的逻辑席位，坐席位的是参与者的一次执行；三条底线说执行体「只能提交 Result Proposal，不能提交治理命令」。所以席位的一票是那次执行提交的提案，由 Run 校验生产者、评审版本、角色和权限后计票（`spec/run.md` §从节点到结果、§Request、重试与 Gate）；v4 写「席位经 HCTL 命令投票」是错的，GPT 指出并改正。控制面把 Gate 的结论写回 PR，那是记录。
- **平台动作到命令的映射要逐项写。** 账号映射只证明来源，不证明「在 PR 上批准」等于「授权合入」，也不等于 Gate 的一票。约束批里要列：接受哪些平台动作（批准、请求修改、评论、合并按钮）、各映射到什么（外部评审证据、只作快照、或映射到有权用户本人时的命令请求）、是否要先预览、是否允许自动提交；控制面自己写回的事件排除。依据 `spec/system.md` §客户端动作与 provider 事件。
- **共享账号不产生多张独立票。** 今天四家 harness 的评论都经同一个 GitHub 账号发出（GPT 备忘回读 #176 证实），映射不出席位。正式 Gate 在交付文档里是 **B4** 引入。是否给参与者各自的平台身份，P2 定，不为此新建账号系统。

## 十一、命名：候选与理由，四家一致挑了 Repo / Change

所有者 2026-09-06 的裁定：把候选和理由写清楚，让各家审阅者来挑；模块与场景不要同名。四家评审都挑了 **Repo（仓库）/ Change（变更）**，Codex 从上一轮的 Change / Review 改选过来。候选、理由与组合表保留如下，供所有者拍板。

**命名要守的三条。** 第一，模块按它拥有的根对象或它治理的事命名，前例是第四模块从 Agent 改名 Participant，决策史 §34 的原话是「第四个模块从一开始就是干活的那一方，只是名字取错了」。第二，场景按人在那里做的事命名，四个老场景是聊天室、看板、施工图、终端。第三，核心产品词是英文单词加中文对照，不用缩写；产品专名（GitHub、Vikunja、Herdr）不进设计层，业界成词（Git、ChangeSet）按专有名词保留英文（GLM 指出 v4 把 Git 也列成禁词，改正）。

**业界怎么叫这一块。** GitHub 叫 Pull requests，GitLab 叫 Merge requests，Bitbucket 也叫 Pull requests；Gerrit 的单位叫 Change；Phabricator 叫 Differential，单位是 Diff 与 Revision；Meta 内部沿用 Diff；Jujutsu 的单位也叫 change，带稳定的 change ID；Azure DevOps 把这一块作为产品分区命名为 Repos，与 Boards、Pipelines 并列，后两者对应我们的 Kanban 与 Workflow。

**模块名候选。**

| 候选 | 好处 | 代价 |
| --- | --- | --- |
| Repo（仓库） | 最符合「模块按根对象命名」：Repo 是根，下面挂现场、变更集、集成；中文对照现成；Azure DevOps 用 Repos 命名同一分区。四家一致选它 | Repo 已是横跨各模块的限定词：Repo Room 归 Project，Repo Board 归 Task，Repo policy 归系统层。叫「Repo 模块」之后，读者见到「Repo 某某」要多分辨一层。所有者问它会不会和 Project 撞车：不直接撞 Project 这个模块，撞的是这个限定词用法；四家的看法是「Repo 是共享作用域」这一点今天读者已经在处理（Project Room 也不归 Project 以外的模块），词表加一条消歧足够 |
| Change（变更） | 说的正是模块治理的事：一次变更从产生、封存、评审到进入目标的全过程；Gerrit、Jujutsu 都把这个单位叫 Change | 与 ChangeSet（变更集）、ChangeSet Revision（变更集版本）三个词叠在一起，「Change 模块」可能被误读成「一个变更集」 |
| Integration（集成） | 点出模块最要紧的输出 | 只说了末端，模块还拥有仓库身份、现场、变更集与写权 |
| Source（源码） | 涵盖仓库、变更、集成 | 英文 Source 与设计里到处用的「来源」撞词 |
| Code（代码） | 最直白 | 太宽；与文档纪律里的「代码体」用法撞 |
| Codebase（代码库） | 与 Repo 同义又避开「Repo 某某」的歧义 | 与根对象 Repo 不同词，多一个近义词要在词表里解释；规矩一允许按「治理的事」命名，所以这是解释成本，不是违规（GPT） |
| SCM | 与所有者口头说法一致 | 缩写，没有自然的中文对照；是外部系统的类别名 |

排除掉的：Merge、Commit、Submission 只说一步且与命令名或 git 词撞；Delivery 与交付文档撞；Land、Landing 与我们「已落地」的状态词撞；Workspace 是愿景 §3 明确放弃的直觉；Version 与到处的 revision、version 字段撞；GitHub 之类产品专名不能进设计层。

**场景名候选。**

| 候选 | 好处 | 代价 |
| --- | --- | --- |
| Change（变更） | 人在这里看的就是一次变更：diff、讨论、检查、集成状态；GitHub 的 PR 页面、GitLab 的 MR 页面、Gerrit 的 change 页面的公共称呼。四家一致选它 | 与变更集对象的关系要在词表里说一句 |
| Review（评审） | 直观 | 「评审」在 Run 模块的约束里已是 Gate 的词汇，`spec/run.md` 出现九处，文档里要一直消歧 |
| Diff（差异） | 具体、短，与现有词不撞 | 比场景窄；中文对照当场景名别扭 |
| Integration（集成） | 点出决定性动作 | 比场景窄 |
| Code（代码） | GitHub 的「Code」页签 | 太宽 |

**组合表**（各家都选第一行）：Repo / Change；Change / Review；Change / Diff；Change / Integration；Repo / Review；Repo / Diff；Integration / Change；Source / Change；SCM / Change。

**内容系统与适配器的叫法。** 内容系统沿用 GPT 的「代码协作平台」，它比「代码托管平台」多出评审协作这一层意思；英文圈的通称 forge 没有像样的中文对照，只在研究文件里作对照词。适配器在设计层叫「平台适配器」（Grok 建议不用 SCM provider，免得和 SCM 这个词搅在一起）；研究与实现层沿用 SCM provider 无妨。

不论选哪个：新增的只是模块名与场景名，不新增一个同名的持久对象，对象仍是 Repo、Repo Instance、ChangeSet、ChangeSet Revision、Write Lease、集成意图与 Integration Receipt；两个名字都是用户可见词，首现带中文对照。本文其余各节用「第五模块」「第五场景」占位，命名拍板后替换。

## 十三、契约测试补核

CT 是契约测试的族名，测可观察的成功与拒绝行为。除新增 CT-<模块名> 外，至少改这些（Codex 首审、Grok、GPT 的补项已并入）：

- CT-PROJECT：「首次注册生成稳定 Repo 身份、同一 Repo 的新 clone 只新增 Repo Instance、fork 或身份碰撞拒绝」这一条的责任迁到 CT-<模块名>，但 Repo Room 的唯一性与同事务连接仍在 CT-PROJECT 测。
- CT-CONNECTION 与 CT-<模块名>：新旧写租约的交接（第五模块撤权、Participant 隔离、确认前不重授）；Project 归档时仍能看见迁走的活动租约与未决集成；未经 Project 或 Run 准入的提案不能产生获准版本；Git 封存完成、结果准入前取消调用，不产生可供下游消费的获准版本或发布动作；平台批准、控制面自己写回的批准、重复事件、无法映射的动作各走正确的来源规则；执行体拿不到远端写凭据。
- CT-RUN：Artifact Revision 的评审仍成立；同一结果树、不同基线或版本身份，不能复用旧票；同一获准版本仅换提交包装，可以保持身份；同一账号的多个平台批准不增加内部席位票数；有效的席位结果提案仍可计票；接受外部评审的无 Run 契约不被强行送去 Gate。
- CT-<模块名> 与 CT-TASK：契约冻结要求远端检查时，本地成功不能顶替；远端合并回执丢失、目标竞争、换绑都不能写错凭证；同一意图重试只得同一结果；「已开启自动合并」不算已合入；绑定声明不能保证预期目标头、人又没有显式选择另一种授权形态时，集成意图拒绝；开了「要求与目标同步」的目标在预览与执行之间变化时，仍按冻结的目标策略接受或拒绝，不能凭「同步开关为真」通过；PR 被改投另一目标分支时不对错误目标写凭证；推送成功但建 PR 的确认丢失、更新 PR 后确认丢失，按原意图回读、不重复建 PR；旧版本的迟到重试不能覆盖新版本的分支或映射；提前授权只发布本次已获准产出，换仓库、换绑定或扩大发布范围须重新授权。

## 十四、与 P2 的顺序
