## 一、要决定什么，以及我的判断

起因是一个观察：我们开发 HCTL2 自己的时候，走的一直是「开 PR、几位审阅者在评论里给意见、作者改、再审、合入」这条路。这条路把协作放在了 GitHub 上，而设计文档没有明说这个依赖。所有者问：要不要显式地把它放进设计？如果放，是不是恰好就是第五个模块？

先说事实。设计的约束层（`docs/design/spec/` 目录）没有把 GitHub 定为必需：GitHub 只在 Task 模块里作为「任务后端」的一个例子出现，和 Linear 并列。代码集成那一侧，文档一律写「远端 SCM」这个通用词，意思是远端的代码托管服务，GitHub、GitLab、Gitea 都算；把改动推到远端、开 PR、合并 PR 这些动作，文档说由「适配器」做，适配器就是把我们的命令翻译给某个外部系统的那层代码。缺的一块是：设计有一张「场景端口」表，列出每类外部系统从哪个口子接进来，表里只有四行，没有代码托管这一行。远端 SCM 的适配器该挂在哪、守什么规则，只在别处顺带提了一句。实现层今天确实用了 GitHub：工具箱的 `wait` 命令读 CI 状态、PR 是否合并、分支是否推进，用的是随包带的 gh。

再说判断。**成立：代码变更与集成符合我们对「模块」的定义，应当立为第五个模块；把它只当一个端口是塞不进现有四个模块的。** 理由在第二节。它有两种供应端：代码协作平台（GitHub 是第一个）和本地工具箱，两者都是正式的、可绑定的供应端，绑定按仓库选；这是第三节。它要从三个地方把已有对象搬进来（ChangeSet 与集成从 Participant，Repo 注册从 Project，Repo Instance 从系统层），并给工具箱一个正式的家；这是第四节。它有自己的场景，代码评审；这是第五节。

## 二、为什么是模块，不是端口

我们在 `docs/design/architecture.md` §三个面 里对模块的定义是一句话：四个领域模块是语义分责；每个模块的治理元数据在控制面，场景内容在执行面的对应系统，场景由展示面呈现。展开说，一个模块要同时有三样东西：

1. 它拥有一类长期的治理事实，记在控制面的账本里。
2. 它有一个外部系统承载场景内容，那个系统是这类内容的事实源，用户可以用那个系统自己的客户端直接操作。
3. 它有一个场景，也就是用户在 Workbench 或命令行里看到并操作的那一面。

所有者给的三条判据，有自己的存储、有第三方操作界面、模块内的存储是事实源且可被控制面消费，和上面三条是同一个意思。拿代码变更与集成去对：

- 治理事实：仓库的身份与注册、仓库在某台机器上的物理现场、变更集及其不可变版本、集成意图与集成凭证、变更与平台上 PR 的映射、平台账号与人的映射。这些今天分散在三个地方，第四节列表。
- 内容系统：代码协作平台。PR 线程、行内讨论、平台上的评审状态、检查结果、合并状态，事实源都在平台上；原生客户端是 GitHub 网页和 gh。
- 场景：代码评审。看一次变更的 diff、讨论、检查和集成状态，并从这里发起集成。

决定性的理由在第二条。一个自带原生客户端的外部系统，在我们的设计里就意味着一个新场景，而设计把一个场景绑在一个模块上（`architecture.md` §场景与系统：四个场景的外部系统各有一个实现）。如果代码协作平台只当端口、不当模块，那 PR 线程这类内容就得挂到某个已有模块下面。挂到 Participant 不合身：它的内容系统是执行体的会话转录和终端字节流，PR 线程不是那种东西。挂到 Project 也不合身：它的内容系统是 Matrix 聊天服务器，设计明确说非 Matrix 的聊天平台经 Matrix 桥接接入、不另设端口，PR 线程不是聊天平台，也桥接不了。所以「只加端口」在端口这一层说得通，在场景这一层站不住。GPT 备忘里「不意味着第五个模块」这一句，就是只看了端口这一层。

还有一个反向的检验。决策史 §33 给工具箱定的五项职责，物化与隔离工作树、执行已持久化的意图并回读、现场锁与栅栏、封存保全、判决结晶副本写入，全部是 Git 的事；今天它在组件表里是一个没有模块归属的「现场执行者」。立了这个模块，工具箱就是它的本地执行者，远端适配器就是它的端口，两边都有了家。

顺带说明这个模块**不是**什么：它不是第四个「面」，三面架构不变；它不是通吃各模块的垫片，那条禁令（`architecture.md` §避免供应商锁定）继续有效；它也不把控制面变成内容仓库，控制面在这个模块里照旧只存身份、准入、摘要、映射和凭证，评审讨论的字节留在平台上。

## 三、两种供应端：代码协作平台与本地工具箱

所有者要求纯本地集成也有正式的解决方案，类比 Participant 模块的 Agency：本地参考实现随包发布、总是可用，远端供应端可以外接。这个模块正好是镜像：平台大概率是常用的那个，本地也必须成立。设计里更近的前例其实是 Task 模块：任务内容的家按仓库选，本地任务服务器或者 GitHub、Linear 这类远端平台，选定之后经同一套命令准入。这个模块照此办理，**供应端按仓库绑定，两种供应端都是正式的**：

| 供应端 | 是什么 | 什么时候用 |
| --- | --- | --- |
| 代码协作平台 | GitHub 是第一个实现，GitLab 是第二个。适配器在控制面里，按仓库的 Port–Provider Binding（端口与供应端的绑定记录）接入。操作平台优先用它随包发布的官方命令行工具，GitHub 是 gh，GitLab 是 glab；细节见附录一的顺序 | 仓库托管在平台上；或者目标分支受平台的分支保护，必须经 PR 才能合入。我们自己的 `main` 就是这种 |
| 本地工具箱 | `hctl2-tool`，随产品发布，总是在。集成用它的 `integrate` 子命令，就是 P1 做完的那条：校验树、基线、预期头，然后比较并交换地推进目标 ref，再回读 | 仓库没有远端平台；或者目标 ref 在本地、不受平台保护。也是平台不可用时唯一还能走的路 |

「默认」这个词要拆开说。总是可用的基线是本地工具箱，就像 Agency 的本地参考实现：装了产品就有。日常最常用的大概率是平台，因为大多数仓库在平台上。绑定是每个仓库一份，不是全局开关。

两种供应端的能力不一样，差在四处：

| 能力 | 代码协作平台（GitHub） | 本地工具箱 |
| --- | --- | --- |
| 评审讨论的载体 | PR 线程，平台是事实源 | 没有。讨论回到 Project 模块的 Scoped Room，也就是为某个变更开的专题聊天室 |
| 检查结果 | 平台上的 CI 检查，工具箱经 gh 回读 | 本地测试的退出码与输出，工具箱直接回读；没有远端 CI |
| 合入到目标 | 平台合并 PR，适配器投递并回读合并后的提交与目标头 | `hctl2-tool integrate` 的本地比较并交换 |
| 身份 | 平台账号要映射到我们账本里的人，才能让「在 PR 上批准」算作一次输入 | 不需要，一切经 HCTL 命令 |

这些差异写成**绑定上的能力声明**，和 Participant 模块处理 Agency 差异的做法一样：Agency 的绑定要声明能不能回显代次栅栏、有没有事件游标，控制面按声明降级。这里绑定声明有没有评审线程、有没有平台评审状态、有没有检查、能不能远端合入、有没有身份映射；准入规则按声明走：没有评审线程就让讨论去 Scoped Room，没有检查就让 `mechanical` 验收项只认工具箱的本地事实，没有远端合入就走本地比较并交换。没有声明的能力不得被记为已生效，这一句和 Participant 那边一字不差。

降级模式要单独写一段，因为它是所有者点名的：一个仓库从头到尾没有平台，这个模块的场景照样有内容。diff 来自工具箱对变更集版本的读取，讨论在 Scoped Room，检查是本地测试的事实，集成走本地路径，凭证照常写。将来给这个仓库绑上平台，只是加一份绑定，仓库身份、既有的变更集与凭证都不变；和 Room 换聊天服务器绑定不改 Room 身份是同一条规则。

平台不可用时的规则沿用连接约束的写法：依赖平台当前回读的命令一律安全拒绝，比如「合入 PR」和「读 PR 是否已合并」；不依赖它的命令继续，比如本地物化、封存、本地集成；不得把本地事实当成远端已完成。

## 四、模块拥有什么：对象迁移表

下面这张表是这次分责调整的核心，也是 v0.17.0 改文档时的清单。「现在在哪」以 v0.16.5 为准。

| 对象 | 现在在哪 | 挪到第五模块后 | 说明 |
| --- | --- | --- | --- |
| Repo（逻辑仓库的稳定身份与注册） | Project 模块（`spec/project.md` §Repo 注册与 Project 归档） | 第五模块拥有 Repo 的身份、注册命令、Git 中的稳定身份写入与回读 | Project 模块保留「一个 Repo 一个 Repo Room」：Room 是聊天内容，仍归 Project；Project 归属于某个 Repo 这条关系不变 |
| Repo Instance（一台机器上的物理执行现场） | 系统层（`spec/system.md` §Repo 与执行现场） | 第五模块拥有；挂接命令由本模块准入，工具箱无副作用读身份这一步不变 | 系统层的代次家族表继续列 `site_generation`，指向本模块 |
| ChangeSet 与 ChangeSet Revision（获准的写入边界及其不可变 Git 快照） | Participant 模块（`spec/participant.md` §对象、§ChangeSet 与 Git 事实） | 第五模块拥有 | 封存、保全、拆除这些工具箱动作随之归本模块；Participant 的三条底线里「隔离工作树」那条继续引用本模块的 ChangeSet |
| Write Lease（对一个 ChangeSet 的独占写权） | Participant 模块，与 ChangeSet 同一行 | **待拍板**。方案甲：随 ChangeSet 进第五模块，作为变更集的写权；方案乙：留在 Participant，作为执行体对变更集的租约 | 我倾向甲。租约锁的是变更集，失权也是变更集这一侧的动作；Participant 保留 Terminal Input Lease，两种租约各归各 |
| 外部副作用命令（executor = tool 或 adapter）与 Integration Receipt | Participant 模块 | 第五模块拥有：本地集成意图由工具箱执行，远端集成意图由平台适配器执行，两者都回读后才写凭证 | Task 模块继续把 Integration Receipt 当验收证据引用；Run 模块的 Gate 通过后由有权 human actor 或冻结的 reducer 提交集成意图，这条不变 |
| 变更与平台的映射（哪个 ChangeSet Revision 对应哪个 PR、哪个提交） | 没有 | 新增，绑定族命名照「双端命名」惯例，例如 ChangeSet–Platform Binding | 只记引用与冻结摘要，不复制 PR 内容 |
| 平台账号与人的映射 | 没有（Room 模块有聊天账号的身份映射可参照） | 新增，放在平台绑定里 | 只有映射到有权用户本人的平台动作才可能成为命令请求，这是系统约束里已有的规则 |
| 外部机械事实（CI 状态、PR 是否合并、引用推进、路径与摘要） | 工具箱 `wait`，组件表里挂在 hctl2-tool 下 | 归本模块的读侧；Run 模块的节点前置继续只认工具箱回读 | 不改语义，只改归属 |
| Git 的双重角色（不可变正文与判决结晶副本） | 系统层（`spec/system.md` §Git 的双重角色） | 规则留在系统层，因为 Task Revision、Workflow Revision、Memo 的正文写入是跨模块的；执行者写明是本模块的工具箱 | 不搬规则，只补一句归属 |

不搬的东西也要说清楚：Gate、Seat、Verdict 留在 Run 模块，评审对象引用改为指向本模块的 ChangeSet Revision；Task Revision 与完成凭证留在 Task；Execution Spec 里「可选 ChangeSet / Write Lease 规则」这一项留在连接约束里，因为它是派工时冻结的。

## 五、场景：代码评审

这个场景回答的问题是：这一次变更改了什么、谁怎么看它、检查过了没有、它进主干了没有、怎么让它进主干。

- 看：变更集某个版本的精确 diff（今天写在 Project 场景和 Participant 那一行里，要挪过来）、评审讨论（平台上的 PR 线程，或者本地模式下的 Scoped Room）、检查结果、集成状态与凭证。
- 做：发起集成（预览、提交）、把评审结论写回平台（记录，不是命令）。
- 原生客户端：GitHub 的 PR 页面和 gh；GitLab 的 MR 页面和 glab。Workbench 到 P3 才做这个场景的投影；P2 用命令行。
- 命令行：交付文档里今天分在两组的命令要合到这个模块下面。`repo register|list|show` 与 `repo instance attach|list|show|detach` 从「Repo / Project」组挪来；`changeset show|diff` 与 `integration preview|submit|show` 从「Participant / Integration / Terminal」组挪来。命令名不改。

评审这个词在 Run 模块已经用在 Gate 上，要划清：Gate 是 Run 模块的**判定**，几个席位投裁决、够票数才出凭证；代码评审场景是**内容与状态的呈现处**，Gate 的裁决出现在这个场景里只是投影，就像 Task 的状态出现在看板上一样。谁拥有什么，一句话：讨论内容归平台或聊天室，裁决归 Run 的账本，集成事实归本模块。

## 六、端口：操作面与能力声明

端口只放我们实际会调用的操作，按自举等级逐步长出来，不预先设计通用对象模型。这是业界所有多平台工具的做法：go-scm、Renovate 的 platform 模块、Zuul 的驱动，接口都是各自产品用到的那几个操作，GitHub 先做，第二个平台进来时修正接口，并且都保留一个假的或本地的驱动给测试用。我们的本地工具箱正好就是那个本地驱动。

B2 的「无 Run 切片」第一次消费这个端口，那时需要的操作大致是：

| 方向 | 操作 | 平台供应端（GitHub） | 本地供应端 |
| --- | --- | --- | --- |
| 读 | 仓库身份、目标 ref 当前头 | gh 与本地 git | 本地 git |
| 读 | PR 状态、平台评审状态、检查结果 | gh，`wait` 已有三类 | 无；检查用本地测试事实替代 |
| 写 | 推送变更集分支、开或更新 PR | 适配器经 gh | 无 |
| 写 | 把 Gate 结论写回 PR（评论或正式评审） | 适配器经 gh，用控制面自己的平台身份 | 无 |
| 写 | 合入目标 | 适配器请求平台合并，带预期头，回读合并提交与目标头 | `hctl2-tool integrate` |
| 映射 | 平台账号到人 | 绑定里配置 | 不需要 |

绑定要声明的能力在第三节列过；这里补一条：**目标保护**。仓库要声明目标分支是否受平台保护、必须经 PR 合入。受保护的目标不允许走本地集成，因为推不上去；这条让「平台路径还是本地路径」成为绑定上的事实，而不是调用方临场的选择。

## 七、与其他四个模块的连接

按连接约束的写法，每条连接交付一个冻结的、带摘要的不可变对象：

- Project 到第五模块：Repo 注册时，本模块激活 Repo 身份，Project 模块在同一事务里建 Repo Room。Repo 归属关系是 Project 引用本模块的 Repo。
- 第五模块到 Participant：派工时 Execution Spec 冻结「可选 ChangeSet / Write Lease 规则」；工具箱按它物化独立工作树。三条底线里的「隔离工作树」由本模块的对象兑现。
- 第五模块到 Run：评审对象引用指向本模块的 ChangeSet Revision；Gate 的证据可以引用平台检查与评审状态，证据通道等级仍按「工具箱回读高于适配器结构化上报高于模型转述」记。
- Run 与 human 到第五模块：Gate 通过后，有权 human actor 或冻结的 reducer 提交集成意图；本模块准入、持久化、执行、回读、写凭证。
- 第五模块到 Task：Integration Receipt 作为 `mechanical` 验收项的证据；Task 的完成命令校验精确凭证，这条不变。
- 平台事件到第五模块：映射到有权用户本人的平台动作（比如在 PR 上批准）可以成为命令请求，条件是操作者、目标、版本、幂等依据齐全；其余平台动作只作快照或分歧。这是系统约束里既有规则在本模块的实例。

## 八、事实权威、失败与恢复

`spec/system.md` §全系统事实权威地图 要加一行：

| 事实 | 权威来源 | 不可用时怎么降级 | 永久丢失时怎么重建 |
| --- | --- | --- | --- |
| PR 线程、平台评审状态、检查结果、合并状态（content） | 所选代码协作平台；控制面只保存变更集与 PR 的映射、事件引用与冻结摘要 | 依赖平台当前回读的命令安全拒绝（远端合入、读 PR 状态）；本地物化、封存、本地集成继续；场景显示待同步 | PR 讨论与平台评审状态丢失；Git 历史、变更集快照、集成凭证与裁决在 Git 和账本里存活。GPT 备忘说得对：可替换的接口不等于可迁移的历史，普通 clone 不带 PR 线程 |

失败与恢复复用连接约束的表，不另写算法。本模块特有的两点：集成结果未知时，工具箱或适配器先回读目标头与 PR 状态，收敛前不签成功凭证、不清理现场，这是 P1 丙已经实现的行为；平台合并被中断，按结果未知处理并返回类型化恢复动作。

## 九、身份与安全：三条底线在这个模块的样子

- 合入钥匙不进工具。平台令牌只在控制面的适配器手里，Harness 拿不到；工具箱本身也不持有平台令牌，它只用宿主 git 和随包的 gh，而 gh 读事实复用的是用户自己的登录。
- 席位的身份是 Participant，不是平台账号。今天我们四家 harness 的评论都经同一个 GitHub 账号发出，GPT 备忘回读 #176 证实了这一点。这意味着平台上的「谁批准了」映射不出席位。自举到 B3 以后，席位投票走 HCTL 命令，由控制面把 Gate 结论写回 PR；是否给每个参与者一个平台身份，是 P2 里的一题，本备忘不定。
- Harness 在自己的工作树里可以正常用 git，也可以推自己的变更集分支到平台，但改写目标引用不产生凭证，下一次预览只会显示预期头不匹配。这条原话保留，只是挪到本模块。

## 十、命名候选

所有者说的 SCM 我当作工作名。有一个前例要提醒：第四模块最初叫 Agent，后来改成 Participant，决策史 §34 的原话是「第四个模块从一开始就是干活的那一方，只是名字取错了」。模块应按它拥有的事实命名，而 SCM 这个词平时指的正是外部系统。三个候选：

| 方案 | 模块名 | 场景名 | 内容系统 | 适配器 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 甲（我推荐） | Change（变更） | Review（评审） | 代码协作平台 | SCM provider（沿用 GPT 的叫法） | 按拥有的事实命名；Change 与 ChangeSet 的关系如 Task 模块与 Task 对象。Gerrit 把一次待评审的变更就叫 Change |
| 乙 | SCM | Review | 代码协作平台 | SCM provider | 与所有者的口头说法一致；缺点是拿外部系统类别当模块名 |
| 丙 | Repo（仓库） | Review | 代码协作平台 | SCM provider | 强调仓库身份是根；缺点是 Repo 已是核心产品词里的对象名，模块与对象同名会和「Room 也是场景名」那类双重身份叠在一起 |

中文对照按核心产品词表的规则给：模块名与场景名都是用户可见词，首现要带对照。

## 附录一：操作模块后端的四级顺序（所有者 2026-09-06）

所有者给的顺序：第一，随包发布的官方命令行工具，以工具调用的方式使用；第二，官方 SDK；第三，读接口描述自动生成客户端；第四，完全手写。这是在研究层现有的三级顺序（官方 SDK、生成、手写）顶上加了一层，方向与交付文档「跨平台二进制优先于 SDK」的借用偏好一致。落点是 `delivery.md` §选型判据 与 `docs/research/sdk/README.md`。
