## 一、结论与先审题

**这条用户路径与多单元架构兼容，不需要重做控制面、Agency 或部署模型；但与现文的部分产品边界、入口和强制步骤有冲突，不能只换一套界面就算完成。**

问题在产品与架构层：用户以一个项目组织工作，现文还有以仓库组织聊天、看板和无项目调用的规则。它们会让“新建项目”的用户先处理额外容器，或者让项目之外仍有参与者和执行。另一些缺口是产品能力尚未写全：话题建议、轻量话题房间、模板表单、图形观察面。它们不要求增加第六个领域模块。

受影响的是日常建项目、展开讨论和观察施工的人。不修正，产品会出现“界面说项目封闭，底层允许项目外调用”“按钮提供本地另起，后台却拒绝”“开个话题先填结案手续”等不一致。反过来，若把闭包当作部署隔离，就会误造每项目一套控制面、Agency 和服务器。

| 判断 | 结论 |
| --- | --- |
| 保留 | 四类单元及仓库底座；五模块分工；一个控制面管理多个项目；一家 Agency 服务多个控制面；共享 Git 对象库；Workbench/CLI 共用命令能力 |
| 真正要改 | 项目外的协作对象；“有外部来源就禁止本地另起”；仓库优先的看板入口与可无看板的成品项目；话题房间强制结案设计 |
| 要补齐 | 自动建议的授权与成本边界；聊天操作任务的删除语义；模板到任务书的产品路径；图形/TUI/headless 观察能力及验收 |
| 不必改核心 | 同一 Run 的任务书/拓扑两视图；并行施工者侧栏；房间与任务、Run 的多重关联；选人时复用 Agency 名册 |

业界已有两类可借的组织方式：GitHub Projects、Linear 用已有工作项形成不同视图；Grok Bot 从会话进入执行观察面。我们借视图和入口，不照搬它们的对象归属或治理规则。具体一手依据在第八节。

本轮不写代码、不改规范版本、不增加依赖，也不把本文合并当成所有建议已获裁决。审查采用仓库设计评审技能的“方案批”规则：逐项指出原句、用例、备选、代价和落点，不扩成全库四轴重审。

## 二、当前有效要求与参考路径

### 用户已经明确的方向

来源为所有者 2026-09-17 本轮“我们再一起对齐一下用户路径”消息；以下是需求记录，不是假称已经落入规范的历史裁决。

| 步骤 | 用户动作与期望 |
| --- | --- |
| P1 | Workbench 主界面新建 Project，选 SCM 地址。远端地址直接走接入；本地 Git 先找远端，有远端推荐接它，也能断开原远端、另建 Gitea；纯本地直接走 Gitea |
| P1-边界 | 控制面 + Project 是闭包，Task、Run、Participant 等不越界；里面的关系允许直接相连、一对多，不强压成单链 |
| P2 | 每个 Project 有且只有一个 task-kanban。任务源优先用 SCM 原生 issues，其次已有外部系统（如 Linear），也可本地；读回并可视化 |
| P3 | 从 Agency 选参与者，建立含这些参与者的 Project 聊天室 |
| T1 | 聊天中持续归纳、建议值得做的 topic；人选择 Yes 后，为该话题新开聊天室，并按相同方式选人；No 不创建 |
| T2 | Project/话题聊天室都能通过聊天操作任务，包括建立、删除；可选快捷模板、填交互表单，给任务生成 Run 的 DAG 施工图 |
| R1 | 每个 Project 左栏有 Kanban、Room 列表、Run 列表 |
| R2 | 每个 Run 有“内容介绍”和“DAG 拓扑图”；前者显示任务书，后者显示实际执行位置（可并行）；两者右侧都显示施工者及当前步骤 |
| R3 | 选择施工者，按 Agency 选人时约定的能力，看到图形计算机、Herdr 式 TUI，或 headless 无交互输出 |

### 累积约束，不借这次需求重开

- 最新[约束集](../../CONSTRAINTS.md)：先查现成方案；安全集中为可配置策略，不在每条用户路径附加安全机制；约束变化须有版本与失败用例。给人看的文档用中文。
- 多单元用例 [S1 §一至三](../../docs/design/scenarios/S1-multi-unit.md)：控制面、Agency、前端可以分机；同一个仓库可以被多个控制面及多个 Project 使用。闭包不撤掉这种复用。
- [决策史 §22](../../docs/design/references/decision-history.md#22-信任模型收窄三条底线不可关外层笼子可选cli-即人v0130)：Workbench/CLI 的用户入口足够，不重建“人在场证明”；worktree 共享 common-dir 和 refs 没问题。
- [安全策略面](../../docs/design/spec/system.md#安全策略面)与 [PR #244](https://github.com/yesme/hctl2/pull/244)：沿用集中策略；HCTL Room 非 E2EE 不变。
- [PR #243](https://github.com/yesme/hctl2/pull/243)及其[裁决底稿](./case-study-20260907/14-delivery-open-questions.md)：Task 与 Run 可以一对多；任务依赖归源，HCTL 展示而不另造依赖系统。现文另限“一 Task 同时至多一个活动 Run”，本轮没有明确要求推翻这一并发限制。
- [已定模板方向](../notes/grokbot-compare/claude-disposition-20260917.md#一所有者的裁决)：跟进到可交付用缺省施工图，不新造授权类型；[当前交付安排](../../docs/design/delivery.md#实现阶段)仍是 P0–P3，产品使用顺序不等于代码施工顺序。

下文“建议”“推论”均是本次研究的判断，不与以上用户要求或已有裁决混写。

## 三、闭包怎么落在现有架构里

### 1. 是工作归属边界，不是安装边界

建议把边界说成一句话：**每份 HCTL 项目工作都属于某个控制面里的某个 Project；项目内可自由建立有意义的关联，不能把另一个项目的活动身份、授权和执行当作自己的。**

```text
同一 Workbench（只是组合入口）
├─ 控制面甲
│  ├─ Project A：一个看板、主聊天室与话题房间、任务、Run、参与者选入记录
│  └─ Project B：自己的上述对象
└─ 控制面乙
   └─ Project C：自己的上述对象

以上项目可以各自连接同一家 Agency、同一代码仓库、同一内容服务器。
共享的是供给或外部事实，不是一份跨项目生效的 Task、Run 或参与者身份。
```

Repo 登记、供应端连接、Agency 工种目录、模板和 Skill 定义可复用；它们是供给与配置，不是项目里正在工作的实例。项目内产生的调用、变更、请求、成果与判定则要能明确回到一个 Project。共享同一 SCM 时，A 合入的代码会成为 B 看到的外部事实；闭包不承诺外部世界互不影响，也不取消同一目标的既有写入协调。

**不要由此增加**每 Project 数据库、进程、Agency 租户、Git 对象库或网络隔离。Agency 仍按控制面配对；项目归属是现有命令和对象的范围检查。跨项目读取代码也不等于跨项目共享执行身份。

### 2. 哪些是已有关系，哪些不应趁机放大

| 关系 | 对这条路径的解释 |
| --- | --- |
| Project → Repo | 保留当前每 Project 引用一个 Repo；同一 Repo 可被多个 Project 用。本轮没有提出多仓库 Project |
| Project → Room | 一个长期 Project Room，加零到多个话题房间；每个都属于本 Project |
| Room ↔ Task / Run | 讨论和来源引用，不是独占所有权。一个房间可讨论多项任务、多次 Run；同一任务/Run 可在本项目不同房间被引用 |
| Task → Run | 历史上可有多次 Run；现文每次 Run 绑定零或一个任务契约版本、同 Task 至多一个活动 Run。若要多个同时施工，属于额外需求，不从“一对多”擅自推导 |
| Room / Run → Participant | 复用同一工种选择界面，不活体共享选入身份。Room 选规划者、Run 席位选施工者；现有两次选人规则与 P3/T1 不冲突 |
| Run → 施工者 → 执行 | Run 可有多个并行席位；右栏展示这些施工者当前的具体执行，不把显示名或工具名当执行身份 |
| 项目之间 | 不互相调用对方的 Room/Run/参与者，不活体继承对方授权。显式引用外部代码、导出的文本可作为新项目自己的来源，不共享原判定 |

“关系直接”不等于各模块直接写对方状态；已有的同控制面命令与引用足够，不需要中间再造一个协调模块。

表中的“选入身份不共享”来自基线的 Room 名册/Run 席位定义，不是从闭包推导出的额外限制。同一工种、执行配置和显示风格可以在本项目多个房间与 Run 中反复选用；各处记录的是这一次承担的职责和授权。用户若希望在这些记录之上另有项目级连续参与者身份，需要单独比较产品价值，不能暗中以当前选入规则否定项目内部可直接关联的要求。

### 3. 闭包确实碰到的旧规则

现文[Project §Room 类型](../../docs/design/project.md#room-类型)有 Repo Room；[Project 约束 §Room Invocation](../../docs/design/spec/project.md#room-invocation)明确允许“没有 Project 的只读研究”；Artifact 也允许在 Project/Repo 两种范围登记。它们会在闭包之外产生 Room、参与者、调用或治理成果，不能靠隐藏侧栏消除冲突。

**建议：不再为新工作建立 Repo Room 或无 Project 调用。** 研究也先建普通 Project，再在它的 Room 里做；Repo 只管仓库登记与代码协作事实。项目产生的 Memo、Artifact、Request、调用及变更的来源都归入项目，不删除 Repo 模块，也不把共享的代码仓库复制进每个闭包。

这是有含义的修改，不是纯导航改版。已有历史如确实存在，应保留为只读旧记录，不偷偷挪归属；迁移只在有真实数据需要时设计，不为文档假造一套迁移引擎。

## 四、新建 Project：哪些步骤要改

### P1：接 SCM；本地另起不是偷偷镜像外部仓库

进入向导时确定目标控制面；只连一个时无需多问。选远端地址后，登记/引用所选 SCM 仓库，继续 P2。远端暂时不可访问、适配器未支持或权限不足时如实显示缺项，不把“填了 URL”显示成“已可施工”。

选本地路径时，系统查出可用远端并预填；多个候选（例如 origin 是 fork、upstream 是原仓库）列出来让人选，不能拿固定名字当判据。“没找到可用远端”“有远端但暂时连不上”“Git 中没有配置远端”也不能混作一回事。无 remote 是本次进入本地路径的依据，不证明这段代码历史上从未来自外部。

- **接原远端，推荐：** 后续评审、issues 和合入走所选平台；本地工作副本不是 Project 的权威，不自动上传本地未提交修改。
- **本地另起：** 明确建立一个独立的 Gitea 仓库和新的 Repo 登记，使用用户选定的初始代码；后续不自动同步回原平台，原平台的 issues、PR 和评审史也不因代码被复制而自动迁来。
- **纯本地：** 同样建立 Gitea 仓库；不是第三套执行逻辑。

现行[Repo 约束 §Repo 注册](../../docs/design/spec/repo.md#repo-注册)直接写了“外部平台仓库绑定或换绑到本地平台时拒绝”。P1 的第二选项因此走不通。建议把旧禁令收窄为：**不自动把原仓库换绑成本地平台，也不自动建立同步镜像；人显式选择的本地独立副本允许建立，并保留来源说明。** 这样保持旧 Project 原地不动，又满足“另搞一套”。

**detach 的建议解释与取舍：** 推荐在独立工作副本中切断原远端作为后续目标、接上新 Gitea，原输入目录不变。它满足“独立开展后续工作”，但不等于把用户原目录里的 remote 配置删掉。若用户要求原目录也 detach，界面应明确列出将修改的配置及受影响的工作树，再执行用户选定动作；不静默扩大到共享该配置的其他工作树。是否必须改原目录，是本文第十节保留的产品选择，不冒称用户已选推荐项。

本地路径在哪台机器就在哪台读取：Mac Workbench 连云端控制面时，Mac 的路径不能被当作云端路径。持有本地材料的一方经已有 Git 交付方式提供初始代码；尚未实现跨机路径时明确不支持，不转而注册云端同名目录。这不要求把所有参与者的目录登记到控制面。

“暂不支持”只是分期状态，不是最终取消这条路径。第二期跨机验收应包含“Workbench 的本地目录 → 选定的远端控制面 → 该控制面所用的 SCM”；成功以选定代码实际送达并回读为准。

**实现层脚注：** 用 Git 自己识别仓库、gitfile、worktree 及其有效配置，不能手工假定 `.git` 一定是目录。Git 文档提供 `rev-parse` 和 `remote get-url`；worktree 默认共享仓库配置，因此直接移除 remote 可能影响其他工作树。Gitea 已有建仓、迁入和镜像能力；本路径选择建独立仓库，不开周期镜像。不侵入上游、不写一套 Git 元数据解析器。依据见第八节。

### P2：一个项目一张板，先不要把“板”和“源”混起来

这里其实已有一半：现行[Task 约束 §契约与来源](../../docs/design/spec/task.md#契约与来源)规定，**启用看板的 Project 恰有一个源引用**；新建任务落到这个源。优先建议 SCM issues、其次外部系统、再本地，完全可以沿用。

要改的是：现文默认“一个 Repo 一张合并板，Project 是分组”，还允许只开聊天室、不选源的 Project。按这次路径，完成向导的 Project 应有且仅有一个 Kanban 入口及已选任务源；向导中途退出可保留已完成配置并提示继续，不新增一套“创建项目工作流”领域对象。

本地 SCM 是 Gitea 时，其 issues 也属于第一推荐项；“本地方案”不必强制再起另一台任务服务器。外部系统则要选择具体范围，如 Linear 的工作区/项目，而不只是填一个品牌名。

默认板只展示本 Project 的任务；导入时可预览所选源范围内的候选卡，尚未归入项目的卡与本项目任务分开。读回来不等于全部认领，更不等于全部采纳为可施工的契约。重新打开时读回当前内容，不把上次缓存冒充最新。

**一个板不必意味着底层只许一个连接。** 现有控制面可登记多个任务源、也有显式认领其他源卡片的能力；它们不是 P2 首用步骤的必需内容。建议保留后端能力，首用只选一个源、一个范围，不让用户管理仓库级合并板。是否公开高级跨源入口可后续决定，不用为这一条用户路径删掉已定能力或另造同步系统。

现文还有“同一外部卡在同一控制面只映射一个 Task，Task 的 Project 不变”。本轮未要求同一张卡在两个项目分别履约，建议保留：已被另一个项目认领的卡显示归属，不伪装成本项目 Task；真有重复履约需求时另建卡。本轮不因闭包二字自动把全局去重改成项目内去重。

### P3：选完人，打开主聊天室

沿用 Agency 工种名册与 Room 选人。所选名单归主聊天室，不再复制一份 Project 成员表；Project 可以显示本项目各房间和 Run 的参与者汇总，但它是视图。选人不会自动开始派工，也不要求这些人预先分配 VM 或终端。

现文“创建 Project 时同时创建唯一 Project Room”可保留为内部动作：用户在第三步完成名单、看到可用聊天室即可，不必为向导展示顺序拆控制面事务。供应端房间尚未创建成功时显示准备中/可重试，不能假装可以发言。

同一页面安排“聊天归纳”配置，展示已有可选模型及费用范围；用户确认后，后面的持续建议路径即可使用，不要求到隐藏设置里再找入口。若没有可用归纳模型或用户选择关闭，明确显示该能力未启用；这是降级使用，不作为 T1 持续建议已验收的证据。

## 五、聊天产生 topic、任务和施工图

### T1：轻量话题房间，而不是先办一套结案手续

建议卡显示“话题是什么、为什么值得展开、来自哪段讨论”，人可接受、忽略或改标题。接受后用同一选人界面，父房间阵容可以预填但可增删；确认后创建**本 Project 的一个新 Room**，有自己的消息与名单，带精确来源回链。它不是另一个 Project，也不是整个父会话的活体副本。

建议复用 Scoped Room 的身份与机制，界面称“话题聊天室”；不再增加独立 Topic 对象及另一套成员、状态和权限。当前 Scoped Room 已能服务“复杂 Request 或决定”，问题不在名字，而在[Room 与消息](../../docs/design/spec/project.md#room-与消息)强制创建时冻结完成条件、回填动作，且归档必须回填成功或带理由结案。

建议改成：**普通话题只需讨论主题和来源；绑定某个 Request/决定并承诺回填时，才要求相应完成与回填规则。** 普通话题由人归档，不必为“不聊了”编一个失败理由；已有需要回填的讨论不能靠普通归档伪装成已解决。闲置汇总提示可保留，不自动归档。一个话题可产生多项任务，任务也能由主房间直接产生。

**持续建议是新增的产品行为，不能假装现文已经全部支持。** 现有滚动纪要只有配置 small-brain 后才生成；而 Room 里的参与者不能自行唤醒下一位。建议扩展既有 Room 归纳能力，用户一次启用并明确模型/费用范围，系统按新增讨论更新建议，合并重复、接受后不重复建议、No 后不连续打扰。它只产出建议，不创建 Room、Task 或 Run，不变成常驻“总指挥”。具体频率、模型、提示词留给实现与实测，不写成架构常数。

未配置归纳能力时，应说明尚未启用，仍可手动开话题/建任务；不能显示“没有值得讨论的点”来掩盖未分析。生成建议失败也不阻塞聊天。若实现选择通过参与者调用来生成建议，需把预授权的只读调用范围写清，不能把模型调用伪装成“控制面纯计算”绕过现有规则。

### T2：聊天是入口，不是另一个任务系统

两类房间提供相同操作：把讨论提炼成新任务，更新已有任务，取消任务，按源能力删除卡片，或为任务生成施工图。目标任务在本 Project 中选择，不靠标题猜身份。系统生成可编辑草稿，展示动作和后果；用户直接命令或确认卡片进入现有公共命令入口，不让模型的一句“已删除”改变事实。

表单本身可承载预览；用户点一次确认就提交该次已展示的选择，不再串接“确认建议 → 确认同一表单 → 再确认有人在”。涉及不同事实的动作可以在同一界面讲清并编排，但不能谎称外部建卡与控制面写入是一个原子操作。

**“删除”还需要一个产品裁决。** 现文 Task 有取消，没有删除治理历史；源平台删除只形成 tombstone。建议区分三种实际后果，而不是把按钮都叫删除：

| 用户真正要做的事 | 建议呈现与结果 |
| --- | --- |
| 丢掉尚未提交的任务草稿 | 删除草稿；未建外部卡、未形成承诺 |
| 已登记的任务不做了 | 取消任务并从活跃视图移开，保留执行和完成历史；有活动 Run 时先显式结束它并满足既有失权/隔离前置，再取消 Task。预览可组合呈现“停止施工并取消任务”，不能在停止待确认时报告整个动作已成功 |
| 确实删源平台卡片 | 明示“删除源卡片”，按源能力和权限执行；源卡删除不等于取消 HCTL Task，Task 仍在本项目视图中可见并标源已删除，Run 不被隐式停止，依赖源回读的后续动作按既有规则处理。若不支持，则如实提供取消或跳到原生界面，不把替代操作报成删除成功 |

取消 Task 已有命令；从聊天删除源卡片则须补能力声明与准入/回读路径。本文不建议新建垃圾箱服务或万能删除状态机。若用户所说删除要求物理抹掉所有治理历史，那与现文直接冲突，不能在本 memo 中擅自批准。

### T2 的模板路径：先得到计划，不是填完表自动开工

用户选一个任务和快捷模板，表单预填目标、交付物、验收、步骤依赖、所需工种、预算；后台生成同一份施工图版本。任务书和 DAG 都由它展示，**不是分别编辑并维护两份计划**。

模板已有缺省方向，不需要通用拖拽编程器；表单也不是 Dagu YAML 编辑器。推荐先完整做“施工—检查—必要返工—评审—合入”这条已有缺省模板，再按真实用例补模板。

用户可只保存计划；要开工时才选施工者、确认资源与副作用。当前施工图批准与 Run 启动已有区分，也允许一次预览提交，沿用即可。任务尚无契约时，表单明确补齐并采纳验收标准；模板不能暗中替用户决定承诺。

**有一处容易被界面掩盖的成本：** 当前[Workflow 与 Run 授权](../../docs/design/spec/run.md#workflow-与-run-授权)默认需要独立读回、三张清单等材料；用户填表并不自动满足这些前置。表单可以生成这些材料并展示读回进度，使用现有机制完成；现文也允许图版本声明跳过读回。建议首批模板按当前缺省自动安排读回，在同一预览展示，不能让用户再去另开房间、手抄三张表。是否对成熟固定模板默认省掉读回，是额外取舍，不能从“快捷”两字推成已批准放宽。

Room 只是来源和讨论处，不独占生成的 Run。计划或 Run 在本项目其他房间被引用，不需要复制它；运行中改计划则按现有新版本/替代路径，不让一次填表悄悄改掉正在执行的任务书。

## 六、观测 Run：同一份工作，两个视图和一个侧栏

```text
左栏                         中栏                         右栏（同一 Run）
Project A                    任务书 / DAG                 施工者与当前步骤
├─ Kanban                    切换展示，不切换执行         ├─ 作者甲：步骤 2 运行中
├─ Rooms                                                 ├─ 评审乙：尚未开始
│  ├─ Project Room                                       └─ 作者丙：步骤 3 等待输入
│  └─ 话题房间
└─ Runs
   └─ Run 17
      ├─ 内容介绍
      └─ DAG 拓扑图
```

R1/R2 主要是 Workbench 的信息组织，不改变五模块权威。Run 列表是 Project 下的独立入口，不硬塞到 Room 子树中，也不要求“一个 Run 一个聊天室”。任务书描述获准的目标、步骤和验收；拓扑图叠加本次实际进度。图可以同时高亮多个进行中的节点，不能只有一个“当前步骤”指针。

右栏无论当前查看任务书还是图，都来自同一 Run 的席位与执行记录。节点被选中可以筛选/强调相关施工者，不能因此漏掉其他并行节点。等待输入、待检查、失败、联系不上、已完成、尚未开始应有清楚区分。引擎报步骤结束、施工者交回结果、HCTL 验收通过也不是同一个绿灯。

选择施工者时定位到当前或用户指定的那次执行；未开始时显示选人信息和等待原因，已结束时显示结果/历史，重试后旧执行保留历史标识，不按显示名误连旧会话。关窗口、切页或断开观察不取消 Run。这些可沿用[Participant §Terminal 场景](../../docs/design/participant.md#terminal-场景)和[连接约束 §场景与第三方适配器](../../docs/design/spec/connections.md#场景与第三方适配器)。

### R3：图形、TUI、headless 是供给能力，不是三种 Participant

| 观察方式 | 产品承诺 | 不承诺什么 |
| --- | --- | --- |
| 图形计算机 | Agency 提供时，可观察该次执行的桌面/浏览器，并按约定接管、交还 | 不默认一人一 VM；不要求控制面管理 VM 或复制远程桌面服务 |
| TUI / 终端 | 经 Agency 观察、按能力输入；可复用 Herdr 等原生界面与现成终端组件 | 不让前端绕过 Agency 直接寻址它内部的运行时 |
| headless | 不提供交互屏幕/终端；任务书、状态、结果、用量与需要人处理的请求仍可查看 | 不是不回报状态、没有结果，更不是终端没输出就判完成 |

选人时显示支持的方式、是否能输入及实际降级；同一供给可支持多种方式，不应设计为互斥的三选一工种。Run 确实要求图形交互而候选不支持时，应在选人/开工前说明，不能到点开窗口才发现只能 headless。

现文主要覆盖结构化事件与 PTY；图形观察是已有[候选池第 3 项](../notes/grokbot-compare/claude-disposition-20260917.md#三候选池登记不实施)，尚非交付完成。建议把 Agency 的观察能力补全到能表达图形工作面，仍绑定精确派工；观察与输入是能力，不新增图形参与者对象。**这次需求提出了产品目标，但尚未选定一个可交付的 VM/桌面供应端。** 后续先对实际接口做验证，再决定接现成组件；本轮不把 Grok Bot 的界面当成可公开嵌入的 SDK。

本次查阅日期 2026-09-17；下列是官方文档核对及仓库已有证据，不是本机接入测试，也不据此升级任何锁定版本。

| Herdr | 仓库已有[运行时调研](../../docs/research/runtime/herdr.md)与[接口调研](../../docs/research/sdk/herdr.md)，现文选定其 TUI/运行时为本地参考实现的基础 | 复用现成终端能力；不因这次要三种显示方式就重建 PTY 持有、恢复或观察转发 |

研究结论是对已有组件的使用方式作取舍，未引入新组件，因此本次不新增一组重复的调研对象文件。将来选图形供应端或新增客户端组件时，仍先在 `docs/research/` 为该对象立证据，再写代码。

### 主线必需的失败与恢复

| 触发 | 人看到什么、下一步是什么 | 验收失败的反例 |
| --- | --- | --- |
| 多 remote、不可达 remote、平台不能识别 | 候选与原因；选择目标、修复访问或主动选本地另起 | 静默挑 upstream、因断网改走 Gitea |
| Gitea 已建仓但初始代码交付失败 | 注册仍待确认，重试继续同一动作；不要求抛掉已配内容重来 | 再建一份仓库，或自动把原 remote 删除 |
| 选的是共享 worktree | 识别公共配置；独立副本路径不改原组；原地操作先呈现影响 | “只改这个项目”实际改掉其他工作树 remote |
| 看板读回失败/只有部分页 | 显示待同步或覆盖不全；修复后继续读取 | 空列表显示为“没有任务”，缓存当最新 |
| 卡已被本控制面另一 Project 认领 | 显示原归属，可另建任务，不把它放进新闭包 | 自动改旧 Task 的 Project，或两项目共用活动 Task |
| 主房间/话题房间创建结果未知，用户重复点击 | 显示创建待确认，按已有命令关联恢复；确认是否存在后继续 | 无条件重建多间房，或没有供应端房间却报告聊天可用 |
| 聊天建任务时源卡已创建、控制面未收到确认 | 保留待同步，按原关联回读并接回同一张卡；无法确认就保持未知 | 用户再点一次生成第二张卡，或凭超时报“没创建” |
| 删除源卡请求超时 | 保留待确认并回读源事实；确实删除后再标源已删除，HCTL 历史与 Run 入口仍在 | 超时就报告删除成功，或把未知结果变成第二次任务取消 |
| 归纳模型未配置、失败或建议被否决 | 普通聊天不受影响；可手动建话题；不自动建任务、不反复刷同一建议 | 失败导致聊天不能用，或 No 后仍开房派工 |
| 模板输入不足/读回未完成/Agency 能力不符 | 在同一预览列出待补内容，保留草稿；不开工 | 表单点击即绕过契约/读回，或静默换施工者 |
| 活动 Run 对应任务被请求删除 | “停止并取消”须先结束 Run 再取消 Task；“只删源卡”则保留可见的 HCTL Task 与 Run，标源缺失、不隐式停止，后续按原契约判 | 源卡消失就自动签任务取消或完成，或 Run 还在却把 HCTL 入口隐藏 |
| 切视图、关闭 Workbench、Agency 断线 | Run 继续按既定授权；显示最后观察时间与联系不上，重连原归属 | 关页面就取消；无输出算成功；仅失联就称丢失 |
| 图形/TUI 不可用 | 如实显示无该能力/断开；仍保留 headless 的任务状态与结果 | 把另一个 worker 的桌面当作当前执行，或伪称已接管 |
| S2.1 契约改了、S2.2 评审后代码改了 | 两视图都显示所依据版本与分歧，旧结果/旧票不冒充新版本完成 | 两个页面出现不同的权威版本或一个全绿一个未验收 |
| S2.3 旧执行失联后回来 | 侧栏明确旧/新执行；能否继续以原授权与失权事实判 | 点同名 worker 接到已替代执行并给它新输入权 |
| S2.4 合入超时但平台可能已成功 | 显示结果未知，按原意图回读，不再发一遍合入 | Run 图因超时回到未开始、按钮生成重复意图 |

**用例外，明确不借本轮扩大：** 多仓库 Project、同 Task 多个同时活动 Run、同一外部卡在同一控制面多个项目分别履约、跨项目任务搬家、跨源双向同步、历史 PR/issues 无损迁移、通用 DAG 编辑器、虚拟机调度平台、任意操作自动补偿。它们不是正常多单元路径的必然后果。

## 十、施工边界、成本与待裁项

建议按依赖分三块，不改 P0–P3 的总施工顺序，也不按 UI 的点击顺序排后端代码：

1. **先定项目边界与首用语义：** A/B/C/D/F。它们会决定控制面的对象归属和命令含义，应在相应模块代码定型前落规范与失败用例。A 是跨模块修改最大的一块；B 有真实代码交付副作用；C 主要是组织方式；D/F 主要是少数生命周期与动作含义。
2. **用 control + CLI 跑通动作：** 不新增与 Workbench 平行的命令。检验远端/本地独立路径、任务源绑定、选人建房、模板计划与现有启动流程。外部任务系统是本轮已要求的目标；以 Linear 提供该选项时，完整任务操作必须补出当前只有身份/快照的交付缺口，不能拿“读到了”当作“全功能支持”，也不能以降级标签代替交付。跨机本地导入在现有第二期范围单列验收。
3. **Workbench 装上路径和观察：** E/G/H 及首用向导、项目导航。建议归纳的实际模型成本要量；图形接入以一家真实 Agency 的能力验证为入口；终端/headless 与图形分别验收，不互相冒充已完成。

成本粗估用改动面而非天数：**一块跨模块边界调整，几块产品交互补齐，一项图形供应端接入待验证。** 不需要新控制面、通用协调服务、任务同步器、消息服务或虚拟机管理器。已有命令、房间、任务源、模板、观察流可继续使用。主要收益是减少用户需先理解的容器和手续；主要代价是文档/契约的项目归属要全链路对齐，以及持续建议和图形接入增加真实运行成本。

留给所有者的选择应只问方向和取舍，不问字段或接口实现：

| 待裁项 | 推荐 | 与用户已定方向的区别 |
| --- | --- | --- |
| 项目闭包下是否取消 Repo Room / 无 Project 调用 | 取消新建路径，研究也进普通 Project，保留既有历史 | 闭包已定；这是清理旧对象边界的具体改法，不另造隐形 Project |
| “本地 detach”是否必须改输入的原目录 | 默认独立副本接 Gitea、原目录不动；需要时明选原地切换并说明范围 | 用户已要求本地独立选项；物理影响哪份工作副本尚未明确 |
| 话题房间是否免填完成条件与回填动作 | 普通话题免填，真正承接 Request/决定时再配置 | 新 topic 聊天室已定；这是撤掉旧强制步骤的取舍 |
| “删除 task”的正式含义 | 草稿可删、已登记任务默认取消并保留历史；源卡可显式另删 | 聊天操作任务已定；不能把取消伪装为所有种类的删除 |

持续建议的触发频率、表单组件、侧栏布局细节和各接口字段由实施者设计，不再拆成一串拍板题。单项目一张板、以 Project 为导航中心、Run 两视图、按 Agency 能力观察这几条也不重复请用户确认。

本文入主线只表示**路径、冲突与改法已记录可审阅**。上述选择和其他建议获逐条确认后，才改规范、推进版本并补 CT；本轮没有声称产品已实现或运行验证已通过。

## 十一、与主线新增同题 memo 的对照

本稿完成后再次同步，主线新增 [Grok 的同题 memo](./grok-user-journey-20260917.md)（[PR #247](https://github.com/yesme/hctl2/pull/247)）；提交前又同步并读了 [GLM 的同题 memo](./user-journey-review-20260917.md)（[PR #249](https://github.com/yesme/hctl2/pull/249)），两次都未改设计正文。以下针对 Grok 稿比较：共同判断是多单元架构不需推翻、Repo 不应删除、观察能力由 Agency 提供。本稿保留以下不同建议，交所有者比较，不改对方记录，也不把新增 memo 当作已生效的规范：

- **本地另起已经是明确需求。** 不建议再问“要不要提供”，更不推荐拿掉选项；要定的是独立副本与原目录 detach 的具体后果。
- **新话题房间不等于第二个主房间。** 不必先把问题改写成“长期房间还是临时房间”；复用 Room，按是否真的有回填义务决定是否填完成条件，就能覆盖当前需求。
- **单板不是板级权威，单源引用也不等于产品路径全齐。** 默认组织可改为 Project 视图而不复制任务；同时应承认现文无看板 Project、Linear 仅身份/快照与本轮完整路径之间的缺口。
- **图形观察与持续建议是明确的产品目标，尚未实现。** 不因已有端口可扩展就标为功能已支持，也不擅自决定第一期取消；排期需要与真实可用能力对齐。
- **新建项目内部是否先登记 Repo 属于实现编排，不是要人批准的架构选择。** 没有必要把它与“一仓多 Project 要不要保留”捆成一道题；后者在本轮不重开。

按 `hctl2-design-review` 的方案读回规则，另起独立上下文，只给本方案和原始用户路径，不给讨论史或其他 harness 的意见。读回不投票，不代所有者裁决。首轮处置如下：

| 读回发现 | 作者处置 |
| --- | --- |
