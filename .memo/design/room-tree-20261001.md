## 一、起点

所有者读 Pi 的设计时注意到它的会话是一棵树，提出 Room 也可以组织成树：Room 是🎄，Task 是🏊‍♀️泳道，Workflow 是🗺️地图，Change 是🎄（Git 历史其实是分了要合的 DAG）。这样 Rooms 就不再是列表，可以在一个项目的 ideas 上导航。

核实结果：Pi 的会话文件确实是树（每条记录带 `id`/`parentId`），`/tree` 在同一文件里跳到任意节点接着聊，离开的分支可写一段摘要带过去。但它是「一个人 + 一个 agent」的树，模型每次只看到叶到根的一条路径；树导航不还原工作区文件。详细事实见 [`harness-access.md` 复核记录](../../docs/research/harness-access.md#复核记录)。

## 二、所有者定的四条

1. **Room 与 Room 之间可以组成树；房间之间的关系归 Matrix 原生存储。** 正如 Kanban 里卡与卡的关系归任务源（`spec/task.md:89`）。控制面不另存一份树，只读出来投影；改挂走 Matrix 写入，以回读为准。
2. **分支只能 fork 主观，不能 fork 客观。** 回退做不到彻底，因为不是所有副作用都在纳管之内，所以不假装没有副作用。想换方向就 fork 出一个新房间继续讨论，带前情提要。
3. **同一个房间里只有讨论串（thread），没有可以随时切方向的分支树。** 核心论点是多观察者：多人协同时，所有人眼里只有一份对客观世界的观测。
4. **两个视角：平铺与原生。** 左侧导航栏是平铺列表（roomA、roomB、roomC）；选中某一类对象时，在右侧打开它的原生结构视图（Room 看树，Run 看 DAG）。怎么做先留 TODO：这是经典的信息可视化问题，先调研业界和 UX 研究，不自己发明。

### 怎么得出的（讨论过程摘要）

- **三类产品的规律。** 存储几乎都是父指针树，区别在「当前路径」这个指针归谁、旁边有没有退不回去的第二方。单人聊天（ChatGPT、Claude.ai）和 Pi 原地分叉；协作平台（Slack、Discord、Zulip、Matrix）从不原地分叉，分歧一律变成所有人可见的新容器、链回出处，并且只许一层；编码 harness 有工作区这个第二方，于是收敛到线性记录、不完整的文件检查点和复制式 fork，并行时连工作区一起复制（worktree）。worktree 就是编码 harness 版本的「另开一个讨论串」。反向验证：Hermes Agent 的 `/branch` 在桌面是父会话下的分叉，到 Discord、Slack、Matrix 上改为另开同级讨论串；Claude Tag 的 `!fork` 是开新讨论串并双向链接。
- **rewind 彻不彻底。** 没有一家做到：所有工具都让用户在「都回 / 只回对话 / 只回文件」里选，没有一家能撤销 shell 和外部副作用；而且两个方向都出过事（回退丢了手工修改，或根本没回退）。Codex 删掉了实验性 `/undo`，Amp 不再回滚文件；Pi 核心只回对话，三四十个社区扩展补文件快照。结论是「彻底」只对被纳管的状态成立。所有者提到的 rcopy 一类 CoW 克隆（XFS/btrfs reflink、APFS clonefile，再往外是 VM 快照）能让 fork 纳管的那部分世界变得便宜，但边界仍在：推出去的 git、发出去的消息、远端数据库回不去。
- **主笔的一次更正。** 主笔曾建议「父节点以控制面存储为准，Matrix 只负责展示」。所有者指出模块内对象之间的关系应归模块原生系统，控制面只记跨模块映射；仓库里 Kanban 早已如此，主笔的建议与先例不一致，已撤回。
- **Matrix 怎么表达层级。** 只有 Space（创建时声明 `type: m.space` 的房间）能有子节点，而 Space 不是聊天室；父子关系由 `m.space.child`（在父 Space 里）和 `m.space.parent`（在子房间里，可标 `canonical`）各写一条；一个房间可挂多个 Space，环被禁止但协议不拦；权限不沿树继承，受限加入只在进门时查一次；thread 只有一层。原生画法是「子 Space + 一个排第一的主房间」，mautrix-discord 就这样映射频道分类。

## 三、主笔建议（所有者 2026-10-01 确认）

**1. 「模块内关系归原生系统」补一条例外。** 规则写成：模块内对象关系归该模块的原生系统；进控制面的只有两类，跨模块映射，以及本身就是治理事实的关系（契约、授权、修订谱系）。没有这条例外，Workflow 套不进去：DAG 的边在控制面保存的 Workflow Revision 里（`spec/run.md:68`），引擎只拿编译副本，因为这些边本身就是「什么可以自动推进」的契约。按这条规则对一遍各模块：

| 模块 | 对象间关系 | 归属 |
| --- | --- | --- |
| Room | 房间父子（挂在谁下面） | Matrix 原生（`m.space.*`） |
| Room | 出处（从哪条消息或 Request 开出来） | 控制面，前情提要的冻结来源 |
| Kanban | 父子卡、阻塞 | 任务源原生（已定，`spec/task.md:89`） |
| Workflow | 图内的边 | 控制面，是契约；引擎只拿编译副本 |
| Workflow | 图与图之间 | 没有关系：编译器拒绝子 DAG（`spec/run.md:102`） |
| Change | 堆叠 PR 的 base、`#123` 互引 | 平台原生，只读投影 |
| Change | ChangeSet 修订谱系（`parent_revision_id`） | 控制面，治理事实 |

**2. 出处与挂靠分开。** Topic Room 身上有两种关系，只是出生时重合：出处属于治理事实，在控制面，永不改；挂在谁下面属于协作组织，在 Matrix，可以改挂。Kanban 里有同样的二分：Task–Backend Binding 的家指针不改写，卡在源里的父卡可以挪。这也回答了改挂是否违反「内容归属固定」（`04-project-navigation.md:7`）：不违反，消息仍留在原房间，变的只是房间的挂靠。

## 四、主笔默认（接口细节，可直接推翻）

- **深度不设硬上限。** 界面默认展开两到三层，更深的「以此为根」打开并带面包屑。实现层脚注：Tuwunel 的 `/hierarchy` 默认深度 3、最多 10。
- **关闭父节点不级联。** 每间 Topic Room 仍由人各自关闭；父节点关闭后子节点照常挂在原处。Project 归档时整棵树随之只读，规则不变。
- **关闭时的结题卡不做。** 第一轮提过「关闭 Topic Room 时可选回贴一张结题卡到父 Room」，所有者没有接；v0.18.7 已去掉普通话题的强制回填，放进停车位，不进本包。
- **与 v0.18.7 扁平化不冲突。** 那次撤掉的是跨层级的包含（Repo Room → Project → Scoped Room）；这次的树只在同一 Project 的 Rooms 内部。契约测试「Rooms/Kanbans/Runs 被排成必须逐层进入的包含链时失败」（`contract-tests.md:269`）也不受影响。
