## 1 · ChangeSet / PR 的默认基数，与多 Task Run 的集成策略

- **背景**：现行约束里一个 Run 绑至多一个 Task Revision；Execution Spec 冻结「可选 ChangeSet / Write Lease 规则」；发布评审是一条意图对应一条评审请求，新 Revision 更新同一请求。没写的是：一次调用或一个 Run 缺省开几个 ChangeSet、开几条评审请求；一个 Task 要几个 Run 合力时怎么集成。
- **问题**：缺省基数是几；多 Task Run 的集成策略要不要在当前范围定。
- **影响面**：`spec/repo.md` §发布评审、`spec/run.md` Manifest 字段、P2.4 丑与 P2.5。
- **阻塞级别**：不阻塞 P2.1–P2.3；P2.4 丑 开工前要定缺省基数；多 Task 策略在 P2.5 前。
- **选法**：甲，缺省「一次调用或一个 Run 一个 ChangeSet，一个 ChangeSet 一条评审请求，新 Revision 更新同一请求」，多 ChangeSet 须在 Execution Spec 显式声明；多 Task Run 与跨 Run 合并成一条 PR 的策略当前范围不做，每个 Run 只绑 0..1 Task 照旧；乙，允许一个 Run 缺省多 ChangeSet（按节点切）——多条评审请求、多条集成意图，返工与去重都要按 ChangeSet 分开算。
- **利弊**：甲最简单、与「一票也行」的轻量路径同向，代价是大改动要人显式拆 Task；乙灵活，代价是 Run 内多条评审线程与集成意图的对账规则要新写。
- **推荐**：甲；多 Task 策略明确推迟，触发条件「P2.5 开工前，或自举 A2 出现第一个要两个 Run 合力的 Task」。
- **用例例子**：S1 里 mac_ctl 与 cloud_ctl 各自对 gh-jssdk 开 PR，各一条；没有两个 Run 合一条 PR 的情形。

## 2 · Repo Room 的隐私与保留期限

- **背景**：HCTL 房间对 control 明文可读，不开端到端加密；所以隐私只能靠 homeserver 侧的访问控制、传输与存储加密、保留策略。当前范围只交付本机连接，homeserver 随包、缺省回环。
- **问题**：房间谁能进、消息留多久、远程接入时怎么保护传输。
- **影响面**：`spec/project.md` §Room 与消息、`docs/research/matrix-homeserver.md`、delivery 第二期。
- **阻塞级别**：不阻塞第一期；第二期共享 homeserver 前要定。
- **选法**：甲，第一期：房间一律邀请制（invite-only）、homeserver 只接受认证访问、消息不设保留期限（治理引用要能一直解析到事件 ID）、磁盘级加密交给宿主；第二期再定传输加密与共享 homeserver 的访问控制，先在 `matrix-homeserver.md` 追加 Tuwunel 的保留策略与访问控制能力复核；乙，现在就定保留期限（例如 N 天后清理消息正文，只留治理引用）——治理引用会指向已删事件，读回与审计要另存正文副本。
- **利弊**：甲不新增机制、不破坏引用链，代价是 Room 只增不减；乙省存储，代价是「治理引用与冻结 digest 仍可校验」这条现行规则要改成「可校验但正文可能已删」。
- **推荐**：甲；触发条件「第二期共享 homeserver 方案，或任一 Repo Room 存储超过所有者定的上限」。

## 3 · Project 拆分 / 合并与 Task 依赖的产品表达

- **背景**：现行有：Project 归档与恢复、跨 Project 换 Task 用「取消或保留旧 Task、在目标 Project 新建、来源引用连历史」、Task 依赖没有治理对象。任务源原生有依赖（GitHub sub-issues 与 blocked_by、Gitea 的依赖、Linear 的关系）；Gitea 的 `…/issues/{index}/dependencies` 增删查 2026-09-17 已在本机跑通（#240 复核记录）。
- **问题**：要不要给 Project 拆合、Task 依赖各造一个 HCTL 命令或对象。
- **影响面**：`spec/project.md`、`spec/task.md`、看板投影。
- **阻塞级别**：不阻塞任何阶段。
- **选法**：甲，不造：Project 拆合就是归档旧的、新建新的、来源引用连历史（现行规则够用）；Task 依赖是任务源的 content，按各源原生能力承载并投影到合并板，不进治理、不阻塞 Run（要阻塞用 Request 或施工图的边）；乙，加「拆分 Project」「Task 依赖」两个治理对象——多两个族外对象，看板要维护跨源依赖的一致性。
- **利弊**：甲不加对象，代价是依赖只是显示、不强制；乙强制，代价是每个任务源都要映射一套依赖语义，与「一张卡一个家」相抵。
- **推荐**：甲；触发条件「自举 A2 之后，出现人要求依赖阻塞派工的真实需求」。

## 4 · Scoped Room 自动归档策略

- **背景**：现行归档只有两条路径：回填动作成功，或有权的人显式以 abandoned / no-decision / superseded 结案并记理由；未回填且无结案的 Scoped Room 阻止 Project 归档。
- **问题**：长期没动静的 Scoped Room 要不要自动归档。
- **影响面**：`spec/project.md` §Scoped Room；Workbench「需要关注」投影。
- **阻塞级别**：不阻塞。
- **选法**：甲，不自动归档；加一条投影规则：Scoped Room 超过缺省 N 天没有新消息也没有回填，进「需要关注」清单，人一键选结案理由；N 放 delivery §运行默认值（建议 14 天）；乙，超时自动以 no-decision 结案——系统替人写理由，与「归档只允许两条路径」相抵。
- **利弊**：甲守住「人结案」，代价是人要点一下；乙省点，代价是理由是假的。
- **推荐**：甲；N 为运行默认值，改缺省只改那一节。

## 5 · 首批原生会话导入的范围与长期维护预算

- **背景**：原生会话导入是可选能力，已写明「不是当前范围的交付前提」；由 Agency 接受用户指定的导入来源并保留外部会话 ID，控制面只收获准的摘要或内容引用；解析器用固定版本的样本测试。harness 各家会话文件格式无承诺（`docs/research/harness-adapters.md`）。
- **问题**：首批做哪几家、做到什么程度、格式变了谁买单。
- **影响面**：`participant.md` §原生会话导入、Agency 参考实现、研究层。
- **阻塞级别**：不阻塞；不在当前范围。
- **选法**：甲，当前范围不交付；首批范围事先定死为「摘要加外部会话 ID 引用」两样，不导入逐条历史；解析器只做样本测试过的格式版本，格式变了标 unknown、不猜；触发条件「自举 A1 之后，所有者点名要导入哪家」；乙，现在就交付 Claude Code 与 Codex 两家的会话导入——多两个解析器要维护，格式无承诺。
- **利弊**：甲零维护，代价是暂时没有；乙有功能，代价是每次上游改格式都是一次返工。
- **推荐**：甲。

## 6 · 多主机与远程的实施：远程连接的认证与传输、多主机执行现场的编排、Windows 与多用户权限

- **背景**：架构方向已定（前端连本机或远程控制面；Agency 唯一通路、非本地必须认证、每个配对控制面一个租户）；B 批把 Agency 一侧的配对认证写进约束，怎么认证、什么传输留实现；前端到控制面的远程连接是第二期。Windows 与多用户明确不在当前范围。
- **问题**：第二期开工前要定什么。
- **影响面**：delivery 第二期、`spec/system.md` §端点与输入的信任边界、研究层。
- **阻塞级别**：不阻塞第一期；阻塞第二期开工。
- **选法**：甲，现在只定「先研究后定」：第二期开工前落一份研究对象文件 `docs/research/remote-transport.md`（候选：mTLS 加本地 CA、SSH 隧道复用宿主 ssh、按令牌的 TLS；两条连接——前端到控制面、控制面到 Agency——分别评），多主机执行现场的编排按 B 批的租户模型不另造对象，Windows 与多用户仍不做；乙，现在拍一种传输——没有研究就拍，违反纪律三。
- **利弊**：甲不占现在的时间；乙快但没依据。
- **推荐**：甲；触发条件「第一期 B2 走通后开第二期方案」。

## 7 · 成本 / 预算硬上限及运行中耗尽的交互

- **背景**：现行：Run Manifest 冻结预算；候选切换与再开尝试都以「候选、预算与剩余截止允许」为条件；Trigger Preview 展示 token 估算；Gate Receipt 逐票记用量；Agency 报派工的用量，报不全标未知。没写的是：预算耗尽时正在跑的派工怎么办、人怎么追加。
- **问题**：预算是硬上限还是软提醒；耗尽时的交互。
- **影响面**：`spec/run.md` Manifest 与候选切换、`spec/project.md` Trigger Preview、Agency 用量报告、delivery 运行默认值。
- **阻塞级别**：不阻塞 P2.1–P2.2；P2.3 Trigger Preview 实现前要定缺省。
- **选法**：甲，预算是控制面授权的一部分，硬在「不再开新的派工或尝试」：耗尽后不再派、正在跑的派工按冻结策略处理，缺省「让它跑完当前派工，结果照常准入」，施工图或调用可声明「超限即取消」；追加预算走 Request 找人，追加后才能再派；用量以 Agency 上报为准，报不全标未知、按估算计；乙，硬在「超限即强杀正在跑的派工」——半成品作废、代价白付，且 Agency 门后的用量本来就有延迟。
- **利弊**：甲少浪费、边界清楚，代价是实际花费可能略超预算（一个派工的量）；乙严格，代价是浪费与误杀。
- **推荐**：甲；缺省进 delivery §运行默认值：「预算耗尽：跑完当前派工，不再派；超限即取消须显式声明」。

## 复盘

- **第 1 条怎么来的。** 2026-08-14 四层重组稿（`729238e`）的「未闭合问题」第 1 条是英文的「Task/ChangeSet/PR 默认基数与 multi-Task Run integration branch policy」，那时 Run 可绑 0..N 个 TaskRevision，问题成立。次日 v0.7/v0.8 评审备忘（`eb7c63c`）指出 0..N 没有分支政策，建议冻结成每个 Run 至多一个；同日的简化稿（`ff73679`）采纳了「0..1」，同一提交却把这条未决只翻译成中文留下来。前提没了，问题没删，挂了一个月。教训：改前提的批要顺手扫未决问题清单，每条问「前提还在吗」。
- **第 5 条怎么来的。** 「原生会话导入」最早出现在 08-14 四层重组稿，是写稿的 harness 从同赛道产品的观察清单（MindFS「外部会话导入与同步」、Happy「端到端加密会话同步」）里带进来的可选能力，同一稿把它列为未闭合问题第 6 条；所有者没有提过这个需求。设计正文 `participant.md` §原生会话导入 一节与 delivery 这条未决是它仅有的落点，约束层没有。建议整节删除、未决条目删除。
- **第 3 条我犯的错。** 「两卡不同源的依赖」不在参考用例里，是我沿着「一张卡一个家」推出来的用例外情形，违反了用例优先。裁决后的形状：依赖是任务源内部的语义，HCTL 认得它（从源读、在卡上投影、派工时用）但不持有、不写；派工启动预览时该 Task 的卡被阻塞要人确认；跨源依赖不设计。四家事实核对：GitHub 子 issue 与 blocked_by / blocking（沙箱 REST 跑通）、Gitea dependencies（本机跑通）、Linear blocks / duplicate / related / similar 加父子（schema）、Vikunja subtask / parenttask / blocked / blocking / precedes / follows 等十二种（源码）。
