## 〇、这一批解决什么

#216 审计留下三处"规则写了一半"的地方，都在 Run 模块的约束层，都不是回退，是 #211 新规则与旧规则并存后没人把接缝写清：

- **F1**：两个席位配置相同、材料相同只算一票（重复组），组内裁决不一致按最不利——但"达到法定票数就撤销剩余尝试"这条旧规则没说重复组什么时候算数，同一张施工图两种到达顺序能得出两种结果；否决席没投票时能不能被当成"剩余"撤掉，候选切换后两席变成重复组怎么算，"去重后票少于法定票数"是立刻失败还是等一等，都没写。
- **R1**：读回记录要引用"三张清单快照的版本与摘要"，可谁把清单物化成快照、从哪个来源冻结、CT 里的"版本过旧"和什么比，现文没有定义。
- **R3**："读回须由与本版本产出调用不同的 Worker Profile 做"——施工图是多轮塑形的产物，或者人直接写的，"本版本产出调用"未必唯一存在。

三处的共同做法：只补结算、来源、求值三条规则，不新建对象、代次或超时；等待的上界钉在既有的 Attempt 终态与 Obligation 截止上。

## 二、每处有哪几种改法，各自的好处坏处

### F1 · 重复组何时算一票，与提前结束怎么衔接

先说清现文已定、不重开的骨架：一个席位一票；两席配置相同、交付内容相同只算一票（09-11 设计句，决策史 v0.17.3 行）；席位间不设商量回合（09-09 补充裁决）；否决权只有策略声明才有（M-35 降为写法后保留的口径）；返工轮数有上限（M-38/M-43）。要定的只是：**重复组在什么时候形成它那一票，以及"达到法定票数"看哪些票。**

| 改法 | 规则 | 好处 | 坏处与代价 |
| --- | --- | --- | --- |
| 甲 · 等本组稳定（推荐） | 重复组的一票在组内每个成员都"交回裁决或到终态"之后才形成；组的裁决取组内已交回裁决里最不利的一个，否决优先；法定票数只按已形成的票算；独立席位或已形成的组够数时照常提前结束，撤销剩余尝试——包括还没交回的重复成员，它们的组就此不形成 | 结果不依赖到达顺序；最不利规则真的有机会生效；控制面睡着醒来后按关联键收取的一堆结果无论什么顺序处理都是同一结果（S1.I11）；不新建对象 | 一个重复组里只要还有成员在跑，这一票就要等，等的上界是该成员的 Obligation 截止或终态；这是等待的代价，由发起 Run 的人在预览警告"两席配置相同"时就知道 |
| 乙 · 关闸时比较 | 法定票数按关闸前已准入且未撤销的票算，重复组只在这些票里比最不利；达到法定票数即撤销剩余尝试，被撤销的重复成员不参加比较 | 最快；与独立席位"先到先关"同一套 | 同一组两种到达顺序结果不同（先到通过就关闸，先到要求修改就按最不利），最不利规则形同虚设一半；控制面睡着后的处理顺序变成结果的一部分，违反 S1.I11 的精神；否决席的处理要另写 |
| 丙 · 派发时定组、不派重复 | 交付内容摘要派发后即可预判，两席重复就只派一个 | 根本不产生重复票 | 候选切换后仍可能中途成组（K3），所以"不派重复"防不住；且"两票都留在裁决与审计记录里"的既有规则要撤——多样性策略未声明时，重复席位本来就是允许的配置 |

甲的三条附则，都是既有机制的引用，不造新东西：

1. **组籍在投票时定**（F1-f）：按投票时实际使用的 Worker Profile 摘要与交付内容摘要分组；派发时的预判只用于预览警告与"确定不可达"的提前判定。候选切换让两席中途成组，照算，不拒绝——拒绝只在切换违反已声明的多样性时（现文已有）。
2. **否决席不是"剩余"**（F1-e）：策略声明了否决权的席位，其裁决未交回时不得签通过凭证，也不得被当作剩余尝试撤销；它到终态而未交回时，走候选切换；候选耗尽按现文「候选耗尽且必须取得额外输入或授权时创建 Request；否则把 Seat/Obligation 标为类型化技术失败」，不伪装成通过或驳回。
3. **两种"不够"分开写**（F1-b、F1-d、F1-g）：**确定不可达**——已形成的票加上仍可能形成的票也少于法定票数，或返工轮数已到上限，立刻返回 `quorum-unreachable`，派发后按预判即可判；**暂未收齐**——已形成的票少于法定票数但仍可能够，继续等，等待的上界是各成员的 Obligation 截止与终态。"不得靠补席位、改门槛或换人补足"照旧。

"组"不是对象：它是计票时按两个已记录摘要算出来的划分，没有标识、没有状态、没有代次；"形成"是对已记录裁决与 Attempt 状态的一个谓词。修 PR 若写出「重复组」的表或状态机，就是走样（GLM 在 #216 的提醒）。

### R1 · 三张清单快照从哪来

| 改法 | 规则 | 好处 | 坏处与代价 |
| --- | --- | --- | --- |
| 甲 · 随施工图登记（推荐） | 「登记 Workflow」命令携带三张清单的最终版：人指定来源（塑形 Skill 最后一次贴出清单的 Room 消息事件 ID，或直接给文本），control 把三张清单按固定结构物化成快照，作为 Workflow Revision 的附属正文由 `hctl2-tool` 写入 Git 并回读，快照摘要记进该 Revision 的登记记录，来源事件 ID 与内容摘要也记在登记记录里（来源链）；读回调用的 Bundle 条目引用这份快照，它是 Git 正文条目，不是 Room 消息条目 | 复用既有的"登记/编译/批准"命令与 Git 正文机制；来源链可审；快照只含三张清单，讨论全文不会借条目换标签混进读回；"版本过旧"有了固定比较对象 | 人多做一步：登记时指定清单来源；施工图与清单绑成一体，改清单就是新 Revision——这正是设计说的「图改一个字就要重做」 |
| 乙 · 清单快照作独立对象 | 新对象「清单快照 Revision」，施工图与读回记录各引用它 | 清单可独立于图演化 | 多一个对象、一套 current 指针与准入；清单离开图没有单独的用途 |
| 丙 · 直接引用 Room 消息 | 快照 = 冻结事件 ID 与内容摘要的那条消息 | 不用物化 | 与 R1-b 准入条件正面冲突：读回 Bundle 不得含来源 Room 消息条目；且那条消息的内容不受结构约束，讨论文字可能夹带 |

甲之下，R1-c 的「版本过旧」改成一句可判的话：读回记录所引的快照摘要必须等于本次批准的 Workflow Revision 所附快照的摘要；快照在 Revision 正文里，所以改快照就是新 Revision，现有的「读回所引 Workflow Revision 摘要与本次批准相同」已经把它盖住，CT 里那个独立的"版本过旧"情形改为"快照摘要不符"即可。清单相对讨论是不是最新，机器判不了，那是登记的人的事，读回抓的是图与清单对不上。

### R3 · 「本版本产出调用」指谁

| 改法 | 规则 | 好处 | 坏处与代价 |
| --- | --- | --- | --- |
| 甲 · 登记时记来源调用集合（推荐） | Workflow Revision 的登记记录含「产出来源」：零个或多个 Room Invocation 引用（塑形过程中写图的调用，人登记时指定），加上登记的人；回避声明的求值：读回调用实际使用的 Worker Profile 摘要与来源集合里任一调用的实际 Worker Profile 摘要都不同；来源集合为空（人直接写图）时该声明视为已满足，读回记录标「无产出调用」 | 多轮塑形有唯一可比集合；人直接写图不被无意义地拒绝；不伪造作者调用 | 人登记时多指定一项；来源集合由人指定，指少了机器查不出——但漏指只会让回避变宽松，不会误拒 |
| 乙 · 来源为空即声明不满足 | 无产出调用时拒绝批准 | 最严 | 人直接写的图只能删掉回避声明才能批，声明失去意义（Codex #216 修订：只作候选，不当已定规则） |
| 丙 · 取最近一次调用 | 用批准前最近一次涉及该 Room 的调用 | 不用记来源 | 多轮塑形里"最近一次"与"写图的那次"常不是一回事，且不可审（Codex #216 修订明确反对） |

甲之下 R3-b 的缺省值改写为「读回默认由与产出来源集合里任一调用都不同的执行配置做；无产出调用时缺省自动满足」。

## 三、代价谁在什么时候付

- **F1 甲**：等待由发起 Run 的人付，付在预览时——预览已经警告"两席配置相同"，选择保留重复席位就是选择等；控制面的实现付一个谓词（组是否形成），不付新状态。
- **R1 甲**：登记施工图的人付一步"指定清单来源"；`hctl2-tool` 多写一份附属正文。
- **R3 甲**：登记的人付一步"指定来源调用"；控制面在批准时多一次摘要比较。

三处都不增加 Agency、执行体或读回者的负担。

## 四、作者推荐哪种，为什么

F1 甲、R1 甲、R3 甲。共同理由：都只补"什么时候算、从哪来、和谁比"三句，复用既有的 Attempt 终态、Obligation 截止、Git 正文、登记命令，不添对象；三处都让结果与到达顺序、处理顺序无关，这是 S1.I10/I11 要求的"期限按已接受的规则判、醒来幂等收取"在计票上的自然延伸。F1 乙更快，但快在牺牲最不利规则和顺序无关性上，而重复席位本来是可以在预览时避免的配置，不值得为它把结算规则写成依赖时序。

## 七、拿 S1 走一遍

S1 的主流程没有 Gate 计票的步骤，必然情形里只有第 7 条（跨机返工：旧版本评审失效要让远端参与者看得到）沾边——返工产生新 Revision 后旧票失效、重新过 Gate，本批不改。真正被本批影响的是五条失败路径：

- **(a)(b) 失联**：重复组里一个成员失联，按 S1.I10 它不因失联撤权，到截止或被判丢失才进终态；甲之下这一票要等到那时才形成，等待有上界；乙之下先到的一票已经关闸，失联的那个成员的裁决永远不进比较——结果取决于谁先失联。甲走得通，乙走得通但结果依赖时序。
- **(c) 控制面睡着**：参与者在已接受范围内干到封存，控制面醒来按关联键幂等收取（S1.I11）。甲之下收取顺序不影响任何组的形成与法定票数判定；乙之下醒来后先处理哪个结果就先关闸，同一批结果两种处理顺序两种结论。这是推荐甲最硬的一条理由。
- **(d)(e)** 与本批无关（平台仲裁、同一张卡）。
