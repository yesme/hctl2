## 〇、这一批解决什么

#216 审计留下三处"规则写了一半"的地方，都在 Run 模块的约束层，都不是回退，是 #211 新规则与旧规则并存后没人把接缝写清：

- **F1**：两个席位配置相同、材料相同只算一票（重复组），组内裁决不一致按最不利——但"达到法定票数就撤销剩余尝试"这条旧规则没说重复组什么时候算数；否决席没投票时能不能被当成"剩余"撤掉，候选切换后两席变成重复组怎么算，"去重后票少于法定票数"是立刻失败还是等一等，都没写。
- **R1**：读回记录要引用"三张清单快照的版本与摘要"，可这三张清单从哪个获确认来源冻结、CT 里的"版本过旧"和什么比，现文没有定义（控制面物化 Bundle 是既有职责，`spec/project.md` §写入约束、§根 Context Manifest 已写；缺的是来源与比较对象）。
- **R3**："读回须由与本版本产出调用不同的 Worker Profile 做"——施工图是多轮塑形的产物，或者人直接写的，"本版本产出调用"未必唯一存在。

三处的共同做法：只补结算、来源、求值三条规则，不新建对象、代次或超时；等待的上界钉在既有的准入、候选范围、截止与撤权规则上。三处都是本批的行为取舍，不是从参考用例已能推出的唯一答案。

## 二、每处有哪几种改法，各自的好处坏处

### F1 · 重复组何时算一票，与提前结束怎么衔接

先说清现文已定、不重开的骨架：一个席位一票；两席配置相同、交付内容相同只算一票（09-11 设计句，决策史 v0.17.3 行）；席位间不设商量回合（09-09 补充裁决）；否决权只有策略声明才有（现文既有，v0.9.1 起；M-35 只确立法定票数由施工图声明、没有缺省三选二）；返工轮数有上限（M-38/M-43）；候选切换只在冻结策略列明的类型化技术故障下、受候选、预算与剩余截止约束（现文）。要定的只是：**重复组在什么时候形成它那一票，以及"达到法定票数"看哪些票。**

先定四个都能从冻结数据与已记录事实算出来的词，三种改法都用：

- **有效裁决**：席位的 Result Proposal 已经过结果准入的裁决。提案已冻结但准入未完成的，既不算票，也不当作没有。
- **席位仍可产出**（仍可能产出有效裁决）：义务仍有效、未到截止，并且满足其一——有已冻结、尚未准入的提案；有尝试在跑；或按冻结策略发生获准的技术故障后，候选、预算与剩余截止仍允许再开尝试。反过来，席位**已结束**：有了有效裁决；或到截止、候选耗尽、被取消、被替代。已结束由既有的准入与撤权规则判，不由 Attempt 终态单独决定——「已交提案」是 Attempt 终态，但席位不算结束。
- **席位仍可能加入某组**：它仍可产出，并且它可能产出的有效裁决的键能与该组相同。键的两半分别看：Worker Profile 摘要按选入记录的获准候选范围看能不能落到该组；交付内容摘要在 Bundle 已交付时用实际交付摘要，尚未交付时按已冻结的引用（ReviewSubjectRef、席位必需 Skill 的引用摘要、根 Manifest）判"能不能证明不同"——证明不了不同，就算可能相同。已结束的席位不再可能加入任何组。
- **组已定**：组内至少有一张有效裁决，且没有席位仍可能加入它。组的裁决取组内有效裁决里最不利的一个，否决优先。组内没有任何有效裁决的组不形成票。

| 改法 | 规则 | 好处 | 坏处与代价 |
| --- | --- | --- | --- |
| 甲 · 等本组稳定（推荐） | 每有新事实就按五步重算，只用已记录事实：① 按现文校验并准入席位结果；② 按有效裁决的键分组，对每组算仍可能加入的席位；③ 先按冻结规则处理否决、技术失败与非通过裁决——策略声明的否决票按现文触发返工路径，`rejected` / `changes_requested` 进归约器、契约内分歧标需要关注，技术故障按现文候选切换或类型化失败与 Request；④ 已定的通过组够法定票数、没有仍可产出而无有效裁决的否决席、且剩余席位按冻结规则不能否定通过时，签汇总凭证并撤销剩余尝试——被撤销席位的组就此不形成，它们之后交回的提案只留历史；⑤ 否则算上界：以当前全部有效裁决（含未定组里的）为固定输入，对仍可产出的席位考虑冻结策略允许的后续结果，两部分合在一起按实际键去重、按冻结规则归约，得到最多可能取得的通过票数；上界仍少于法定票数就返回法定票数不可达，否则等待 | 同一重复组里成员的到达顺序不影响该组那一票，最不利规则有机会生效；不新建对象；等待有界——每个席位到"已结束"有界（截止、候选耗尽、取消、替代），所以每个组到"已定或不形成"有界 | 等待：只要还有席位可能加入某个组，那个组就不能定——不只是预览时两席配置相同才等，**候选范围重叠、或交付内容尚未能证明不同**也会等，这笔代价由启动 Run 的人付，预览要把"候选范围重叠"也警告出来；独立席位够数仍提前关闸、未形成的组就此不形成，这一条与现文同构，仍是顺序相关 |
| 乙 · 关闸时比较 | 法定票数按关闸前已准入且未撤销的有效裁决算，重复组只在这些票里比最不利；够数即撤销剩余尝试，被撤销的重复成员不参加比较；否决席同样不得被撤 | 最快；与独立席位"先到先关"同一套；不用算"仍可能加入" | 同一组两种到达顺序结果不同（先到通过就关闸，先到要求修改就按最不利），最不利规则只在两票都赶在关闸前时生效；这是合法候选，不是违反已有不变量 |
| 丙 · 派发时定组、不派重复 | 交付内容摘要派发后即可预判，两席重复就只派一个 | 根本不产生重复票 | 候选切换后仍可能中途成组（K3）也可能中途拆组（Codex），"不派重复"防不住；且"两票都留在裁决与审计记录里"的既有规则要撤——多样性策略未声明时，重复席位本来就是允许的配置 |

甲的附则，都是既有机制的引用，不造新东西：

1. **组籍在有效裁决产生时定**（F1-f）：按投票时实际使用的 Worker Profile 摘要与交付内容摘要分组；候选切换让两席中途成组或中途拆组，都照键算，不拒绝——拒绝只在切换违反已声明的多样性时（现文已有）。派发时的预判只用于预览警告和第 3 条的启动拒绝。
2. **否决席不是"剩余"**（F1-e）：策略声明了否决权的席位，没有有效裁决而仍可产出时，不得签通过凭证，也不得为了签通过凭证把它当作剩余撤销；这两件事与它是不是某个重复组的成员无关，不得借"组未形成、别处已够数"把它撤掉。它的尝试失败时，仅在义务仍有效、发生获准的技术故障且候选、预算、截止允许时切换；已交提案不是这类故障，已取消、被替代不重启，提案待准入不切换。否决席最终没有取得有效裁决时，沿现文「候选耗尽且必须取得额外输入或授权时创建 Request；否则把 Seat/Obligation 标为类型化技术失败」处理，不签通过凭证，不伪装成通过或驳回。否决席挡住的是"能不能签通过"这道门，不把法定票数加一。
3. **两种"不够"分开写**（F1-b、F1-d、F1-g）：**确定不可达**——第⑤步的上界少于法定票数。已有的有效裁决是固定输入，不能把已投票的席位当成还能按候选重选配置的人；也不能把已定的负面裁决当通过票。当前重复的预判本身不是证明：两席现在都用 X、材料相同，只要有一席的获准候选里有 Y，上界就仍是两票。**启动拒绝**（待裁）：启动前已有的事实——选入记录的候选范围、席位要求、能证明相同的冻结引用——已足以证明上界少于法定票数时，启动拒绝，与"声明了多样性而选定记录不满足"同一道门，人此时还能改图或改候选范围；交付内容尚不能确定时不把未知当相同，只作预览警告，运行时再判。**暂未收齐**——已定的组少于法定票数但上界还够，继续等，不得提前失败。"不得靠补席位、改门槛或换人补足"照旧。
4. **返工上限不进"不可达"的定义**（Codex）：汇总要求继续返工、但再开一轮将超过已声明上限时，沿既有失败边或按策略创建 Request；本轮已取得的合格结果不因轮数恰好用满而失败。形成一份组裁决也不等于取得通过票：`rejected` / `changes_requested` 仍交冻结归约规则处理，契约内分歧仍标需要关注，不被统一改写成票数不可达。
5. **形成是对当前 ReviewSubjectRef 的谓词**（Grok）：返工产生新 Revision 后旧票失效（现文），新一轮从零等组。
6. **等组期间的提案不是迟到**（Grok）：席位在其组形成之前不是被取消的归属者，它的提案走正常结果准入；只有第④步撤销之后交回的才按 `spec/connections.md` 的"迟到结果只留历史"处理，不得再把组"补形成"，也不得改已签的汇总。
7. **恢复后不等"收齐"**（Codex）：控制面睡着或失联恢复后，沿既有准入、去重、截止与撤权规则收取结果，据当前已记录事实重算五步；不要求先证明全部供应端的已封存结果已经收齐——没有这种全局信号。一个远端仍失联时，它仍可产出、仍可能加入它能落到的组，那些组就等它到截止或被判丢失；与它无关的组照常定、照常结束。

"组"不是对象：它是求值时按两个已记录摘要算出来的划分，没有标识、没有状态、没有代次；"已定""仍可产出""仍可能加入"都是对已记录裁决、提案与尝试状态、选入记录候选范围、冻结引用与实际交付摘要的谓词。修 PR 若写出「重复组」的表或状态机，就是走样（GLM 在 #216 的提醒）。

| 甲 · 随施工图登记（推荐） | 「登记 Workflow」命令携带三张清单的最终版：来源要么是塑形 Skill 最后一次贴出清单的 Room 消息事件 ID，要么显式标「直接文本、无消息来源」并记提交者与提交内容摘要；control 把三张清单按固定结构物化成快照，作为 Workflow Revision 的附属正文由 `hctl2-tool` 写入 Git 并回读，快照摘要与来源链记进该 Revision 的登记记录；读回调用的 Bundle 条目引用这份快照，它是 Git 正文条目，不是 Room 消息条目。Workflow Revision 声明关闭读回时，登记不强制快照与来源链 | 复用既有的"登记/编译/批准"命令与 Git 正文机制；来源链可审；快照只含三张清单的结构；"版本过旧"有了固定比较对象 | 人多做一步：登记时指定清单来源；施工图与清单绑成一体，改清单就是新 Revision——这正是设计说的「图改一个字就要重做」 |

| 丙 · 直接引用 Room 消息 | 快照 = 冻结事件 ID 与内容摘要的那条消息 | 不用物化 | 与 R1-b 准入条件正面冲突：读回 Bundle 不得含来源 Room 消息条目；且那条消息的内容不受结构约束，讨论文字可能夹带 |

甲之下的两条校验（Codex）：

- **核实际交付，不只核自报**：批准时三处逐项一致——登记记录里的图与快照摘要、读回记录里抄的摘要、该读回调用的 Execution Spec 所冻结且实际交付的 Bundle 里的图与快照摘要（`spec/project.md` §根 Context Manifest：control 在派工交付前核对实际交付摘要）。读回记录填了新快照、包里装的是旧快照，必须拒绝。读回调用是无 Run 的 Room Invocation，它的产物按 `spec/connections.md` §结果准入 由 Project 记录；三处一致是「批准 Workflow」对登记记录、读回记录与实际 Bundle 的核，不是读回准入的第五条。
- **机器只核结构**：快照有三张清单以外的字段、条目种类不合法、缺项或摘要不符时拒绝；文本装在三个合法字段里有没有夹带讨论，机器证明不了，那是读回本身要发现的事。

R1-c 的「版本过旧」退出 CT，留下「读回记录所引快照摘要 ≠ 本次批准 Revision 所附快照摘要」作字段级核对；快照在 Revision 正文里，改快照就是新 Revision，现有「读回所引 Workflow Revision 摘要与本次批准相同」已经盖住内容变化，这一条不写成互不相干的第二次失败。清单相对讨论是不是最新，机器判不了，那是登记的人的事，读回抓的是图与清单对不上。

| 甲 · 登记时记来源调用集合（推荐） | Workflow Revision 的登记记录含「产出来源」，三种取值：非空的 Room Invocation 引用集合（塑形过程中写图的调用，人登记时指定）；人的显式声明「本图无模型产出调用」；缺失。只在启用读回且声明了配置回避时求值：读回调用实际使用的 Worker Profile 摘要与来源集合里每个调用的实际 Worker Profile 摘要都不同；显式声明无产出调用时回避记为无需比较；**来源缺失、引用无法解析、或未知**时不自动判满足——人补齐来源，或显式放开回避声明后才能批准，读回本身照做。关闭读回时不强制产出来源，与 R1 对齐 | 多轮塑形有唯一可比集合；人直接写图不被无意义地拒绝，但要说一句；不伪造作者调用；不把"没登记"当成"没有" | 人登记时多指定一项；集合由人指定，机器只能核每个引用能解析到真实存在、属于来源 Room 的调用，核不了"写过图的都在集合里"，漏指会让回避变宽松——这是这条策略本来的代价，写明 |

甲之下 R3-b 的缺省值改写为「启用读回时，读回默认由与产出来源集合里每个调用都不同的执行配置做；登记显式声明无模型产出调用时缺省自动满足；来源缺失时不能批准，直到补齐来源或显式放开回避」。

## 三、代价谁在什么时候付

- **F1 甲**：等待由启动 Run 的人付，付在预览时——预览警告"两席配置相同"和"候选范围重叠"，保留这样的席位就是选择等；控制面的实现付三个谓词（席位仍可产出、席位仍可能加入、组已定）和一个上界计算，不付新状态。
- **R1 甲**：登记施工图的人付一步"指定清单来源"；`hctl2-tool` 多写一份附属正文；control 在批准时多一次三处摘要比对。
- **R3 甲**：登记的人付一步"指定来源调用或声明没有"；控制面在批准时多一次摘要比较。

三处都不增加 Agency、执行体或读回者的负担。

## 四、作者推荐哪种，为什么

F1 甲、R1 甲、R3 甲。共同理由：都只补"什么时候算、从哪来、和谁比"，复用既有的结果准入、候选范围、截止、撤权、Git 正文、登记命令，不添对象。F1 甲的价值是让最不利规则真的生效、让同一组内的到达顺序不影响那一票；它的代价是等，等的范围在预览时可见，上界由既有截止保证。F1 乙更快，代价是最不利规则只在两票都赶在关闸前时才有意义，结果随到达顺序走——这是合法的取舍，不是违约，由所有者选。

## 七、拿 S1 走一遍

S1 的主流程没有 Gate 计票的步骤，必然情形里只有第 7 条（跨机返工：旧版本评审失效要让远端参与者看得到）沾边——返工产生新 Revision 后旧票失效、重新过 Gate，本批不改。失败路径里与本批相关的是三条：

- **(a)(b) 失联**：重复组里一个成员失联，按 S1.I10 它不因失联撤权，到截止或被判丢失才算已结束；甲之下它能落到的组要等到那时才能定，与它无关的组照常定、照常结束，等待有上界。乙之下先到的一票已经关闸，失联成员的裁决不进比较。两种都走得通，区别是甲等、乙不等。
- **(c) 控制面睡着**：参与者在已接受范围内干到封存，控制面醒来按关联键幂等收取（S1.I11）。甲之下醒来后按既有准入与去重规则收取结果、据已记录事实重算五步，不要求先证明"都收齐了"——I11 说的是同一条结果重投仍是那一条，没有全局收齐的信号；组的形成只看已记录事实与各席位是否仍可产出，所以收取顺序不改变已定的组，只改变"什么时候定"。乙之下醒来后先处理哪个结果就先关闸，那是乙的代价，不是违约。
- **(d)(e)** 与本批无关（平台仲裁、同一张卡）。

读回两处（R1、R3）在 S1 里没有对应步骤。08 施工图的 N0 只能用来演练"图与清单快照一起交付"的意图：08 由 Fable 整理写成、按读回意见修订，没有正式的 Room Invocation 记录，按 R3 甲属于"来源未登记"——登记时要么补齐来源，要么由人显式放开配置回避；已知有模型参与的图不能靠声明"无模型产出调用"抹掉来源。它不是"人直接写图、空来源自动通过"的正例，那个正例要另构造：一份人直接撰写、登记时显式声明无模型产出调用的图。
