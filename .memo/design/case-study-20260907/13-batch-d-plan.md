## 二、改法与推荐

### K1 任务源零到多个；缺省源由人显式选定，继承只在选择时解析

**已定边界**：所有者原话（§一 K1 行）；C 批已落「注册由人登记仓库与声明平台绑定」（#227）；09-11/09-12 不重做的部分与本项无关。

**拟改义：** 仓库到任务源的绑定零到多个，仍是 Port–Provider Binding（`port_kind = task_source`），每个 `provider + account_stable_id + scope_stable_id` 至多一个活跃绑定不变；一个仓库可以一个都不绑，只开聊天室的 Project 不因此被要求选源。注册仓库或首次启用看板时，人从候选列表显式选定仓库级**缺省建议**：候选列出仓库所绑平台自带的 issues（GitHub Issues、本地平台的 issues）、本地任务服务器、Linear 这类远端平台，其中缺省建议项是平台自带的 issues，显式不挂平台的仓库缺省建议项是本地任务服务器；能作缺省源的只有能力声明含建卡与字段写回的绑定，只过了身份与快照的绑定在列表里标「不能作缺省源、可认领」。只开聊天室的 Project 没有源引用；仓库一个源都没绑时不能给 Project 启用看板，先绑源再启用。启用看板的 Project 恰有一个源引用：Project 启用看板时显式确认所选源——「继承」的意思是在这次选择里采用仓库的缺省建议并保存自己的源引用；之后仓库缺省建议变化不改既有 Project 与 Task 的来源，也不搬卡与分组锚点。没有显式同意，系统不绑源、不建卡、不启用看板；从 HCTL 新建的 Task 落到 Project 的源引用。注册与建 Project 的两层选择可以在同一个预览里确认，不必是两次交互。

几种改法：甲，零到多个绑定加 Project 源引用（推荐）；乙，仍然一个仓库一个源，别的源只读引用、不认领——所有者的原话是「一边用 GitHub 一边用 Linear 管看板」，只读引用做不到在两个源里各管各的卡；丙，不设缺省、每张 Task 建卡时临场选源——与「缺省给平台自带 issues」拧着。推荐甲。代价：多一层显式选择，用户付；适配器按源各接一套（E1）。词汇：「任务源」是任务后端作为看板来源时的产品叫法，与既有「task backend（任务后端）」是同一样东西，绑定层叫 task_source 端口；「Task–Backend Binding」是 Task 与一张卡的绑定，「家指针」是它所含实体键的叫法；「Task Backend Snapshot」不变——这四个近名的映射进词汇表。

### K2 一张卡一个家；认领分两路，落定不搬家

**已定边界**：现行唯一键与「停用或重新绑定端口不释放映射」；01 §五 的收敛。

**拟改义：** 卡的身份仍是现行实体键 `(provider, account_stable_id, external_entity_kind, immutable_external_entity_id)`，不含绑定版本、范围或放置位置；唯一范围是本控制面。**家指针**就是这把键：它已经说明卡在哪个源（provider 加账号），不另加绑定版本字段；创建或认领时落定，此后不改写——现行「不改写规范实体身份」照旧。键做身份、绑定做寻址：实体键识别卡片，读写这张卡经选定且有权访问该实体的端口绑定；同 provider 同账号不同 scope 可以各有活跃绑定，不写成「该实体的活跃绑定」跨 scope 唯一，也不为此新增解析机制或选绑政策。同一实体键就是同一张卡、同一个家，不论经哪条 scope 的绑定读到；不同 scope 的绑定只是寻址路径，不产生第二张卡。认领分两路：源内稳定归属到恰好一个已准入 Project 分组的规范卡片，可由对账自动认领（现行 content-first 路径，只作自动认领的前置）；其他情形——仓库已绑的非缺省源里的卡、源内未分组或多分组的卡、源里没有 Project 分组锚点的卡——只能由有权的人经「认领卡片」命令显式认领进指定 Project，按实体身份、权限与所选 Project 核验，不要求外源替它建分组，适配器不自选 Project、不先建 Task。认领不搬家：卡留在它所在的源，HCTL 只记键；一个事实源不等于只有一个写入客户端，用户用合适的客户端编辑那张卡照样可以，写发往卡实际所在的源，HCTL 不自动跨源同步。认领后，卡在外源的分组与它在 HCTL 的 Project 归属脱钩（见 K3）。

迁往另一实体（换卡）不做——所有者 2026-09-15 拍板原话：「一个卡一个家，卡不搬家——如果卡后端挂了，那就是 control/workbench 的后端挂了，那还搬啥搬？ground-truth 都在那里。」不加命令，不给 Task 加状态；Kimi 的候选不再保留。

### K3 两套分组；脱钩要把三句旧限制一起换掉

**已定边界**：01 §五（GLM 提出，五家无异议；GLM 第二轮的脱钩声明）；现行分组锚点规则。

**拟改义：** 源内分组是源原生的 milestone、Linear project、标签，只在该 Project 的源引用所指的源里建，锚点仍存在该绑定的元数据里（现行字段不变）；「一个活跃 Project 在一个绑定中恰有一个获准锚点」改为「在其源引用所指的绑定中恰有一个」，其他源不建 Project 分组锚点。跨源归组靠控制面投影：Task 到 Project 记录。稳定唯一的原生分组只作为自动认领的前置；认领后原生分组变化只更新内容与位置的观测，不改 Task 的 Project，也不再以「偏离旧分组」本身冻结治理动作；后端不支持的分组或移动操作按能力拒绝。因此三句旧限制一起换：「适配器做不到按锚点稳定回读归属时，该后端只能显示过滤视图，不能声称支持 Task 身份导入或跨组移动」改为「做不到时没有自动认领，只有人的显式认领与过滤视图」；「外部卡随后移到另一 Project 分组……在恢复原位置或建立新 Task 前，系统必须阻止采纳、启动、完成和后端操作字段写入」改为「只追加 Snapshot，不改 Task 的 Project，不冻结治理动作」；「“移动 Task”只能在原 Project 锚点内改变阶段和排序；跨 Project 分组的预览必须拒绝」改为「“移动 Task”只改阶段与排序，不改 Project；跨源相对移动拒绝」。这不取消实体校验、来源新鲜度或字段写权限，只取消已被显式选择替代的分组推断。替换后仍然冻结的只有两类，一个没卸：需要当前回读的动作——采纳、移动、完成的比较并交换与当前回读前置，现行不变；来源停用（K6）与卡被删除（tombstone，现行不变）各按各的规则。「偏离旧分组本身」不再是冻结理由。CT-TASK 对应的旧行同批替换（§六）。只有一种写法。

### K4 合并板是投影，不是新的权威表

**已定边界**：01 §五（Codex）；A 批的联合视图规则；v0.10.1「Board 从 Project 级上移为 Repo 级」只改投影的口径，不改归属。

**拟改义：** 「一个 Repo 一个 Board」改为「一个仓库一张合并板，它是本控制面所知各源的派生视图」：行是本控制面该仓库的全部 Task（各取实体键所指的卡）加各绑定源里尚未认领的卡；泳道、健康状态按现行投影规则算；每个源绑定各有自己的 `board_scope_stable_id`（现行字段），合并板不另存。一个前端连着两个控制面时，本控制面的 Task、未认领的卡、另一控制面的 Task 三者分开展示，同一张外部卡可以合并显示但治理状态不合并，沿现有实体键去重，不设板级权威、板级命令或跨控制面锁。合并板不是对象，不进写入约束表，`spec/task.md` §对象 不加 Board 对象。只有一种写法。

### K5 跨控制面绑同一张卡：多写通则在任务后端上的实例

**已定边界**：D16（所有者「2 认」）；现行 `spec/task.md` 的供应端 Done 信封、服务账号写回只追加 Snapshot、排序归后端与「以回读为准」；`spec/run.md` §Run → Task 不动。

**拟改义：** `spec/task.md` 加一段引用[多写通则](../../../docs/design/spec/system.md#命令与跨服务正确性)：另一控制面把它的 Task 绑到同一张卡，它的评论、写回与 Done 对本控制面是事实，不是命令，也不是违规；本控制面的 Task 不因此完成或取消，本控制面的 Run 也不因此完成；人经原生客户端做的 Done 仍可分别成为两个控制面各自的完成请求、各自独立验收，不等于两边都完成；本控制面的自动写回不能冒充人的新动作，写回评论必须带控制面与 Task 标识；卡内容的并发写按任务源自己的能力处理，有条件写入的用，没有的以回读为准——未确认时不报成功，能确认的结果照常收口，不是这种后端永远只能未知，也不靠 HCTL 虚构并发保证；两个控制面各有一份绑定不产生第二张卡。`spec/system.md` 多写通则段加「任务后端实例见 Task 约束」半句；Run → Task 的交接照旧，「另一控制面的 Done 不触发本控制面的 Run 完成」「本 Run 正常完成但本 Task 当前版本已前移则 Task 拒绝、Run 不回滚」沿 CT-TASK 既有行核。只有一种写法。

### K6 源停用后：保留 Task，重新接通同一实体即恢复

**已定边界**：现行「停用或重新绑定端口不释放或重定向映射」；Task 生命周期只有开放、完成、已取消；01 §五 的悬空句。

**拟改义：** 现行「停用或重新绑定端口不释放或重定向映射」不改，本项补的是停用之后 Task 怎么显示、怎么恢复。固定的是规范外部实体身份，不是接通它的某次绑定版本。家所在的源被停用后，保留 Task、历史与实体认领，标需要关注；人经现有「接通/换绑」命令恢复对同一实体的访问，Task 不换、不新建；确需当前来源回读的动作（采纳、移动、完成的当前回读前置，按现行 `spec/task.md` §启动 Run 的前置与排序令牌）在恢复前按既有规则拒绝，其余按已冻结契约与现行准入判；系统不猜新家，也不静默。迁往另一实体不做（K2，所有者拍板）。

### L1 施工图 lint 的票数检查：拒能证明的，提示重复风险，不造第二套上界

**已定边界**：D17（所有者原话）；R 批 v0.17.7 的去重键（投票时实际 Worker Profile 摘要且交付内容摘要相同只计一票）、上界算法（最多可能通过票数）与启动拒绝（[spec/run.md §计票与结束](../../../docs/design/spec/run.md#计票与结束)）；B 批 v0.18.2 的多样性只留「Worker Profile 互异」「回避作者」。

**v1 的错处与撤回：** v1 让 lint 把「声明相同且未声明互异」的两席算作一票并拒绝。这算的是最坏值，不是上界：两个要求与材料相同、未声明互异的席位，启动时合法选中两个不同的 Worker Profile、交付相同内容，R 批计两票；v1 会在尚未选人时拒掉这张合法的施工图。「未声明必须不同」不等于「确定只能相同」。撤回。

**拟改义：** lint（「登记 Workflow」的编译前检查）只用当时已有的声明，按 R 批的同一条去重键做两件事；先后固定：先算能证明的拒绝，拒了就不再出提示，没拒的图再出重复风险提示，两者都在同一次登记结果里。一是**能证明的拒绝**：只有已能证明所有合法取值都凑不足法定票数时才拒绝——现行规则下能证明的只有「法定票数大于必需评审席位数」：重复引用同一个 Seat 身份不增加票位；同一席位模板展开成多个 Seat 不能仅凭模板相同证明同键，不作拒绝依据，也不为此补新字段或新许可。二是**重复风险提示**：声明的席位要求（工种、必需 Skill、证据等级）与材料来源（ReviewSubjectRef 的来源节点、席位必需 Skill 引用）相同、Gate 又未对它们声明「Worker Profile 互异」的席位，lint 在登记结果里机械地列出「这几席可能按去重合成一票」、缺哪项信息、三种可选的处理（声明互异、改席位要求或必需 Skill、降法定票数）——这些是供人选择的建议，不是必须制造材料差异或降票数；这是机械检出，但不把未知合成确定的一票。配置与交付内容确定之后的判定仍分别由既有的启动检查（实际候选、实际交付摘要）与运行中计票完成；三处同一条键，lint 只是在没有候选时只取声明层。不提前要求登记时已有启动才冻结的根 Manifest，不把工种或证据等级添成第二把键，不要求作者制造材料差异。

几种改法：甲，重复风险提示阻塞登记，作者须声明互异或降票数才能登记——比任何现有裁决都严，会要求合法的施工图多写一条声明；乙，只作机械提示，登记通过，能证明的情形拒绝，启动拒绝兜底。**所有者 2026-09-15 拍板：乙。** 例子（作者在聊天里说错过一次，这里写对）：两票 Gate，两席都要「mac_tpl_sdet 工种加评审 Skill」、未声明互异——登记通过并附提示；启动预览时若两席都从 mac_tpl_sdet 选人且实际执行配置相同（同 harness、同模型、同模式、同权限），最多可能通过票数为一，启动拒绝；mac_gemini 是 harness 不是工种，席位选的是工种的实例。`delivery.md` §运行默认值「席位多样性策略默认不声明」不改。

### X1 跨机返工：派给持有封存版本的那家 Agency；Run 内沿候选切换，换 Agency 要人

**已定边界**：S1 必然情形 7（所有者补写）；R 批的语义返工路径与返工席位必用 Verdict 正文；B 批的派工、Agency 唯一通路、门后换主机对控制面无感、无法履约 / 联系不上三分；C 批的封存、保全、旧写者隔离与「已封存并获准交付的精确副本可经获准路径送达，不要求共享对象库或公共平台」；`spec/run.md` 的候选切换只在选入记录的获准候选范围内换 Worker Profile、换 Agency 须替代 Run；无 Run 调用没有候选自动切换。

**拟改义：** 通用规则一句话：返工派给谁只看授权——Run 沿冻结的选入记录，无 Run 由人选；字节从哪取只看获准副本——已封存并获准交付的版本，谁持有都行。返工是新的 Attempt（Run 内）或新的 Room Invocation（无 Run 路径），因此是新的派工。两件事分开：谁持有封存版本回答字节从哪取得，谁获准返工由本次授权回答。S1 的这次返工按用例声明在 cloud 环境落实，作为用例安排照写，不升成通用规则。通用规则：Run 返工按冻结的选入记录与施工图派工——选入记录已含 Agency，同一 Seat 的新 Attempt 自然回到同一家 Agency 的本控制面租户；候选切换只换获准候选范围内的 Worker Profile，不换选入记录、工种或 Agency，更换它们须走既有的替代 Run；技术故障切换的条件按 `spec/run.md` 原句：冻结策略列明的类型化技术故障（含 Agency 报无法履约），且义务仍有效、候选、预算及剩余截止允许时才切换，已到义务截止按原截止规则处理，不是切换条件；无 Run 路径由人发起新的 Room Invocation 并明确选人，可以选另一家获准 Agency 的参与者，原 Agency 在线与否不构成限制；持有封存版本的那家 Agency 下线时：Run 内是技术故障，冻结策略允许且义务有效时在同一选入记录（同一 Agency）的候选范围内另开尝试，候选耗尽按类型化技术失败或 Request，换 Agency 由人替代；字节从其他获准副本取得——已交付到平台源分支或已送达的精确副本；没有任何获准副本时只能等它回来或由人显式恢复，不搬未封存字节；原树续做还是从封存版本重建、用哪台主机与进程，归 Agency 门后，控制面不重建。

开工包按既有规则交付，不为凑齐包伪造对象：Run 返工交付精确的被驳回评审对象（ChangeSet Revision 或 Artifact Revision）与必用的 Verdict 正文，材料按现行 inline / pointer 规则交付，必需的是精确内容可读、摘要正确；无 Run 调用交付人选中的精确版本与评论（可能没有 HCTL Verdict）。返工开始时引用被驳回的旧版本，新版本产出并准入后，后续评审才绑定新的 ReviewSubjectRef。需要重建代码时使用可核验、已封存并已获准交付的版本，从获准来源取得并确认送达——同一版本可以有多个获准副本，不据此唯一选出一家「持有版本的 Agency」；未封存的字节不搬去别的机器，旧工作树里未封存的修改按 C 批规则保全并隔离；不要求公共平台或共享对象库。旧版本评审失效对远端参与者的可见性靠既有路径检验，不新增通知对象：旧版本的提案不能计入新版本的 Gate；远端后续派工实际收到新版本引用；查询与投影能辨认旧评审已失效。

几种改法：甲，如上（推荐）；乙，把「持有封存版本的 Agency」写成派工条件——会误拒人授权的新调用，且多副本时选不出唯一一家；丙，一律从平台源分支物化——要求返工前已推送，显式不挂平台的仓库走不通。推荐甲；只引用既有对象，不新增返工对象、位置字段或通知对象。

## 三、代价与批次切法

一个 D 动手 PR，v0.18.3，落点表逐行对照（同 B 批做法）。改动面比 B 小：约束层动 `spec/task.md`（多处）、`spec/run.md`、`spec/repo.md`、`spec/project.md`、`spec/system.md` 各一两处；新文件一个；研究层两份追加复核记录。

## 四、借用现成机制与分层
