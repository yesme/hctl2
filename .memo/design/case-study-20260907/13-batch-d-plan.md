## 二、改法与推荐

### K1 任务源零到多个；缺省源由人显式选定

**已定边界**：所有者原话（§一 K1 行）；09-11/09-12 不重做的部分与本项无关；C 批已落「注册由人登记仓库与声明平台绑定」（#227）。

**拟改义：** 仓库到任务源的绑定零到多个，仍是 Port–Provider Binding（`port_kind = task_source`），每个 `provider + account_stable_id + scope_stable_id` 至多一个活跃绑定不变；一个仓库可以一个都不绑，只开聊天室的 Project 不因此被排除。仓库级**缺省任务源**在注册仓库或首次启用看板时由人从候选列表里显式选定：候选列表列出仓库所绑平台自带的 issues（GitHub Issues、本地平台的 issues）、本地任务服务器、Linear 这类远端平台；缺省建议项是平台自带的 issues，显式不挂平台的仓库缺省建议项是本地任务服务器；没有显式同意，系统不绑源、不建卡、不启用看板。启用看板的 Project 恰有一个缺省源引用，缺省继承仓库级缺省源，创建 Project 时可以显式换成仓库已绑的另一个源；从 HCTL 新建的 Task 落到 Project 缺省源。

几种改法：甲，零到多个绑定加 Project 缺省源（推荐）；乙，仍然一个仓库一个源，别的源只读引用，不认领——省事，但所有者的原话是「一边用 GitHub 一边用 Linear 管看板」，只读引用做不到在两个源里各管各的卡；丙，不设缺省源、每张 Task 建卡时临场选源——每次建卡多一次选择，Trigger Preview 与 CLI 都要多一个必填项，且「缺省给平台自带 issues」本身就要求有缺省。推荐甲。代价：注册与建 Project 各多一次显式选择，用户付；适配器按源各接一套（E1）。

### K2 一张卡一个家；认领跨源由人选，落定不搬家

**已定边界**：现行唯一键与 content-first 认领规则（`spec/task.md`）；01 §五 的收敛（Codex 纠正 GLM：键不含绑定，唯一范围是控制面内；GLM 的脱钩声明）。

**拟改义：** 卡的身份仍是现行实体键 `(provider, account_stable_id, external_entity_kind, immutable_external_entity_id)`，不含绑定、范围或放置位置；唯一范围是本控制面。Task 到「卡在哪个源」的引用零或一——**家指针**，即任务源绑定加外部实体——在创建或认领时落定，此后不迁移。认领分两路：缺省源里稳定归属到恰好一个已准入 Project 分组的规范卡片，可由对账自动认领（现行 content-first 路径）；仓库已绑的其他源里的卡，或缺省源里未分组、多分组的卡，只能由有权的人经「认领卡片」命令显式认领进指定 Project，适配器不自选 Project、不先建 Task。认领不搬家：卡留在它所在的源，HCTL 只记指针；认领后，卡在外源的分组与它在 HCTL 的 Project 归属正式脱钩，合并板上的跨源归组只认控制面自己的 Task 到 Project 记录，不去外源补建分组来「修复」归组。一个事实源不等于只有一个写入客户端：用户用合适的客户端编辑那张卡照样可以，写发往卡实际所在的源，HCTL 不自动跨源同步。

不做迁移：换家等于新建 Task 认领另一张卡并显式把旧 Task 标为被替代（Kimi 的候选，记在这里，本批不加命令）。只有一种写法。

### K3 两套分组并存

**已定边界**：01 §五（GLM 提出，五家无异议）；现行分组锚点规则。

**拟改义：** 源内分组是源原生的 milestone、Linear project、标签，只在该 Project 的缺省源里建，锚点仍存在缺省源绑定的元数据里（现行字段不变）；现行「一个活跃 Project 在一个绑定中恰有一个获准锚点」改为「在其缺省源绑定中恰有一个」，其他源不建 Project 分组锚点。跨源归组靠控制面投影：Task 到 Project 记录。适配器做不到按锚点稳定回读归属时，该源只能显示过滤视图（现行规则不变）。只有一种写法。

### K4 合并板是投影，不是新的权威表

**已定边界**：S1.I3；01 §五（Codex）；v0.10.1「Board 从 Project 级上移为 Repo 级」只改投影的口径，不改归属。

**拟改义：** 「一个 Repo 一个 Board」改为「一个仓库一张合并板，它是本控制面所知各源的派生视图」：行是本控制面该仓库的全部 Task（各取家指针的卡）加各绑定源里尚未认领的卡；泳道、健康状态按现行投影规则算；每个源绑定各有自己的 `board_scope_stable_id`（现行字段），合并板不另存。同一张外部卡在一个前端连着两个控制面时可以合并显示，但两份 Task、各自的验收状态与控制面来源分别展示（A 批的联合视图规则）。合并板不是对象，不进写入约束表；`spec/task.md` §对象 只加家指针字段组，不加「Board」对象。只有一种写法。

### K5 跨控制面绑同一张卡：多写通则在任务后端上的实例

**已定边界**：D16（所有者「2 认」）；现行 `spec/task.md` 的供应端 Done 信封、HCTL 服务账号写回只追加 Snapshot、排序归后端与「以回读为准」。

**拟改义：** `spec/task.md` 加一段引用[多写通则](../../../docs/design/spec/system.md#命令与跨服务正确性)：另一控制面把它的 Task 绑到同一张卡，它的评论、写回与 Done 对本控制面是事实，不是命令，也不是违规；本控制面的 Task 不因此完成或取消；人经原生客户端做的 Done 仍可按本控制面自己的绑定成为一次完成请求、由本控制面独立验收；本控制面的自动写回不能冒充人的新动作，写回评论必须带控制面与 Task 标识；卡内容的并发写按任务源自己的能力处理，有条件写入的用，没有的以回读为准并保留结果未知，不承诺所有任务源都能拒绝竞争写入；两个控制面各有一份绑定不产生第二张卡。`spec/system.md` 多写通则段加「任务后端实例见 Task 约束」半句。只有一种写法。

### K6 源解绑后悬空；本批不做迁移

**拟改义：** 家指针所指的绑定被停用或替换时，Task 悬空：标需要关注，采纳、启动、完成与后端字段写入拒绝，直到人显式认领到别处（新建 Task 并替代旧 Task）或取消；系统不静默，也不猜新家。只有一种写法。

### L1 施工图 lint 去重检查：静态上界

**已定边界**：D17（所有者原话）；R 批 v0.17.7 的去重键（投票时实际 Worker Profile 摘要且交付内容摘要相同只计一票）、上界算法与启动拒绝（[spec/run.md §计票与结束](../../../docs/design/spec/run.md#计票与结束)）；B 批 v0.18.2 的多样性只留「Worker Profile 互异」「回避作者」。不造第二套上界；算不出的仍由启动拒绝兜底。

**拟改义：** lint（「登记 Workflow」的编译前检查）对每个 Gate 节点算一个**静态上界**：只用施工图声明，不用候选。规则是同一条去重键在声明层的最坏值——两个必需评审席位的声明材料相同（同一 ReviewSubjectRef 来源节点、同一组席位必需 Skill 引用、同一根 Manifest 引用；席位要求的工种、证据等级也相同），而 Gate 未对它们声明「Worker Profile 互异」时，启动前无法证明它们会成为两票，静态上界把它们算作一票；声明了互异的席位各算一票；声明材料或要求不同的席位各算一票。静态上界少于 Gate 法定票数，登记拒绝，拒绝信息列出会合成一票的席位与三种修法：声明互异、改席位要求或必需 Skill、降法定票数；法定票数大于必需评审席位数是它的平凡情形。静态上界够时，启动预览仍按 R 批用实际候选算，运行中仍按计票与结束重算——三处用同一条键，lint 只是把「实际 Worker Profile 摘要」在没有候选时按「未声明互异则可能相同」取最坏值，不是第二套上界。

几种改法：甲，静态上界不足即登记拒绝（推荐）；乙，只警告，留给启动拒绝——所有者的原话是「mechanical 地检验出来」，警告是 R 批启动预览已有的行为，不算新检出；丙，把「法定票数大于一」隐含为要求互异——隐含规则读不出来，评审时会当成漏写。推荐甲。代价：多票 Gate 的施工图作者必须写明席位怎样互异，否则登记不过；`delivery.md` §运行默认值「席位多样性策略默认不声明」改为只对单票 Gate 成立。

### X1 跨机返工：派工回到封存它的参与者，未封存字节不搬机

**已定边界**：S1 必然情形 7（所有者补写）；R 批的语义返工路径与返工席位必用 Verdict 正文；B 批的派工、Agency 唯一通路与 Agency 报无法履约 / 联系不上三分；C 批的封存、保全与旧写者隔离。

**拟改义：** 返工是新的 Attempt（Run 内）或新的 Room Invocation（无 Run 路径），因此是新的派工；派工优先发给封存被驳回版本的那位参与者——同一选入记录、同一 Agency——开工包带 Verdict 正文（必用）与旧 ChangeSet Revision 的 pointer。那位参与者用原工作树还是从封存版本重新物化，是 Agency 门后的事；控制面只要求：重新物化的来源只能是封存的 ChangeSet Revision（对象库里的提交，或已由持凭据单元交付到平台源分支的版本），未封存的字节不搬去别的机器。原参与者不可用（Agency 报无法履约，或联系不上且到了冻结的截止）时按候选范围另派，另派的参与者只能从封存版本物化，旧工作树里未封存的修改按 C 批规则保全并隔离，不混进新产出。旧版本评审失效对远端参与者的可见性就是三样：开工包里的 Verdict 正文、新的 ReviewSubjectRef、Change 场景的投影；不另发通知对象。

几种改法：甲，优先原参与者、不可用时另派（推荐）；乙，强制原参与者，不可用就等——把返工绑死在一台机器上，与 B 批「Agency 挂了由人换」相悖；丙，任何参与者都从平台源分支物化——要求返工前必须已推送，显式不挂平台的仓库走不通。推荐甲；返工席位的 Bundle 规则、封存与保全规则都引用既有条款，不新增对象。

失败路径按本批只核四类：任务源不可用（依赖当前回读的采纳、移动、完成拒绝，现行不变；合并板对该源标待同步）；家指针所指绑定被停用（悬空，需要关注，不静默）；静态上界不足（登记拒绝，给修法）；返工的原参与者不可用（按候选另派，只从封存版本物化）。
