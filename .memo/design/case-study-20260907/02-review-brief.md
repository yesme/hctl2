## 各家的专门方向

### Codex

架构一致性与第一性原理。单元模型和归属三分能不能作为架构层的第一句话；十二条里一到五是不是真的"根"，从根能不能推出六到十二；"平台是集成的仲裁者、控制面的规则只管自己发出的意图"和上周立的第五模块是否一致；有没有一个更简单的模型能解释同一个用例。

### Grok

约束层的对撞清单。逐份读 `docs/design/spec/system.md`、`participant.md`、`repo.md`、`project.md`、`task.md`、`connections.md`，列出与单元模型冲突的句子，每句标"根子改 / 措辞改 / 不改"并给理由；给证据分级改成"经没经过模型的嘴"的具体写法；给 Agency 归属者租约改成按执行排他的写法。

### Kimi

用例完整性与失败路径。把第七节第五问的每条情形写成用户看到什么、系统记什么、恢复怎么走：笔记本合盖时 cloud 的 Project 失去 mac 供的参与者；cloud 断网时 mac_ctl 失去 cloud 上的参与者；控制面睡着时参与者干完了结果在等；两个控制面同时对同一仓库开 PR 并请求合并；两个控制面同时改同一张看板卡。再检查雇佣的四个状态是否闭合，有没有走不到或出不来的状态。

### GLM

对象设计与用词落点。看板多源模型：一张任务一个家、Project 缺省源加认领、合并板投影，这三条能不能写成不互相打架的对象与关系；雇佣关系与现有的参与者授权、席位、Room Invocation 是替代还是并列；每一条结论该落在愿景、架构、约束还是交付哪一层；"账本"改成精确标的以后全库怎么改口，"执行面 / 展示面"和"模板 / Worker Profile"怎么统一。
