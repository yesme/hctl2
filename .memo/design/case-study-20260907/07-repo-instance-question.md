# Repo Instance 的去留：与 Codex 对齐后的立场（v3）

> 状态：已对齐 · v3 按 Codex 与所有者讨论后的收窄意见改：Repo Instance 不作为 HCTL 的必备架构抽象，也不改名成"精确现场引用"后靠分散字段继续维护同一个对象；请 Codex 确认<br>
> 基线：main @ `96f5cf3`（草案 v0.17.1）<br>
> 去向：C 批 Repo 与治理正文的方案；`spec/repo.md` §对象、§Repo 注册与 Repo Instance 挂接、§写入约束、§集成、§恢复；`spec/system.md` §Repo 与执行现场、§单写者、§启动与恢复

## 一、所有者定下的分责原则

> 参与者负责自己的工作环境与工作副本；控制面负责它发出的任务与授权、接受的代码版本，以及获准的目标更新。参与者只需交付履行这些约定所必需的信息，不必公开内部工作区布局。

"参与者一侧"包括它的运行环境：目录由 harness 自己选还是 Agency 替它安排，是这一侧内部的分工。控制面要验证约定被履行了，不因此去管理参与者的生产工具。

## 二、结论

**Repo Instance 不作为 HCTL 的必备架构抽象。** 不保留控制面拥有的这个对象、它的活跃与移除生命周期、必经的挂接命令；也不把它改名成"精确现场引用"，再靠派工、封存、变更集记录里的分散字段维护同一个对象（v2 就是这样写的，Codex 指出后撤回）。要删掉的是"控制面必须管理每份物理仓库副本"这个假设。

替代不是一个新东西，而是按操作各留必要的引用：

- **派工**："基于这个版本完成修改，把精确成果和证据交给我。"固定的是任务、基线版本、权限与预算。参与者用哪份克隆、哪个目录、哪条临时分支，是它内部的事；换了工作目录不自动要求重新授权。
- **封存与交付**：固定的是精确成果（提交或树的摘要）、它的来源（哪次执行、哪个基线）与证据。控制面认的是版本、来源和执行，不是目录。
- **更新目标**："把已批准的成果合入指定的目标分支。"平台目标用平台绑定与 ref；本地目标用供应端提供的目标引用加 ref，意图冻结它，执行时供应端按它解析，解析不到或不是同一个目标就拒绝。这一步必须认准目标：Codex 的 A、B 两份克隆的反例只证明"授权更新 A 时不能更新成 B"，证明不了"参与者用 A 还是 B 生产成果控制面都得知道"。目标不能被偷换，不等于承载目标的物理存放永远不能迁移；连续性按授权所指的目标判，供应端能证明是同一个目标就可以，不要求某个目录或克隆永远不变。

只有约定本身明确涉及具体物理资源时，才识别那个资源。

## 三、三层各留什么

- **架构层**：参与者管理工作环境，控制面负责授权与验收，供应端负责它承载的资源与事实。顶层保留 Repo 模块与逻辑仓库，不引入管理每份物理副本的对象。
- **约束层**：只写操作与交付的条件，不推出统一的现场标识、现场代次或挂接生命周期。条件是：交付的版本与证据可核验；获准的更新不能写错目标；未确认的动作可以恢复核对；成果在接收方确认保全之前不得丢失；共享同一份资源的多个写入者，它们的写入要互斥、旧写者要能失权、引用不能撞名。互斥、失权、恢复"必须达到什么"写在约定里，怎么达到留给实现。
- **实现层**：克隆与工作树的组织、内部句柄、锁与代次由具体供应端选择。某个实现可以有一个叫 RepoInstance 的内部结构，也可以没有；不预先设计一套所有供应端都得采用的同类对象，也不要求它们把 `site_generation` 或统一的物理现场身份暴露给控制面。

内部信息不等于免除履约责任：拒收旧执行的结果证明不了旧进程已失去文件写权，需要隔离的写入由资源管理方落实；控制面仍按约定核验结果与权限条件；但这些不意味着控制面要维护供应端内部资源的完整状态。

## 四、三处核的结果（v3）

1. **没有平台的受限路径：维持。** 目标写成"供应端提供的目标引用加 ref"，意图冻结它；执行时供应端按引用解析，不是同一个目标就拒绝。两条原边界不动：不挂平台才有本地目标；平台不可用不改道为本地目标。本地分支前移不证明平台分支已合入。
2. **恢复：控制面恢复自己的，供应端恢复自己的。** 控制面恢复自己发出的执行、待交的结果、未确认的动作与意图，按原授权核验完成报告与目标；不重建供应端的目录状态，不抢占供应端全部克隆的排他权，只让自己的过期动作失权。供应端恢复自己的工作区，并对"旧写者已失权、资源仍是原目标"给出可核的答复；答不了的，控制面保持未确认状态与恢复动作，不假定已完成，也不把同一可写资源交给新写者。Codex 第一轮的五种情形（控制面重启而供应端正常；供应端重启或不可达；执行已结束、结果待交、控制面由旧备份恢复；集成已写入但响应丢失或人的显式封存未准入；供应端换机器或同路径重建克隆）作为 C 批写恢复条件的核对表，每种情形写"控制面核什么、供应端答什么"，不写供应端内部怎么实现。
3. **所有者自己的本机克隆：维持直接编辑加显式采用。** 人直接改代码；要 HCTL 接受时，由工具回读、用户预览并提交封存或采用命令，控制面按原规则准入，不要求先走挂接向导，也不要求先雇一个参与者。

## 五、落到 C 批方案的写法（v3）

- `spec/repo.md` §对象：删 Repo Instance 行，不加"现场引用"对象；派工固定任务、版本、权限；封存与交付固定精确成果及其来源；面向本地目标的集成意图多一个"供应端提供的目标引用"字段，只在这类操作里出现。§Repo 注册与 Repo Instance 挂接 改为"Repo 注册"，挂接命令删除。
- `spec/system.md` §Repo 与执行现场 改写为第一节的分责原则加第三节约束层的条件；`site_generation` 与现场 OS 锁从系统层的代次家族里退出，改成对供应端的条件"共享资源上的写入互斥与旧写者失权由资源管理方保证，并能对控制面作答"；§单写者 只管控制面存储的写者；§启动与恢复 按第四节第 2 点重写。
- 引用命名空间不相交（单元稿第 14 条）写成条件，不写格式。
- Repo 模块仍负责本控制面的代码变更授权、版本准入、集成意图与凭证，不退化为平台配置，也不兼任远程工作区管理器。

## 六、v2 到 v3 撤回的话

"保留精确现场引用作为取消对象后的通用替代要求"撤回；"现场引用一律列为派工、封存、变更集记录的必备字段"撤回；"要求供应端暴露 site_generation 或统一的物理现场身份"撤回；"每条授权或每份结果都必须回答针对哪一份实际 Git 资源"撤回，改为对成果认版本、来源与执行，对目标更新认获准改变的目标。
