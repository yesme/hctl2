# Repo Instance 的去留：与 Codex 对齐的题目

> 状态：讨论中 · 所有者 2026-09-07 把这个问题交给 Fable 与 Codex 对齐后定；本文是 Fable 的立场与要核的三处，Codex 在 PR 评论里答<br>
> 基线：main @ `1d6ca5c`（草案 v0.17.1）<br>
> 去向：C 批 Repo 与治理正文的方案；`spec/repo.md` §Repo 注册与 Repo Instance 挂接、§写入约束；`spec/system.md` §Repo 与执行现场、§单写者、§启动与恢复

## 一、所有者的问题

原话："我就没理解为啥 Repo Instance 这个会存在——这个是 participant 自己的 implementation details？处理同一台机器上的同一个 repo 的 harness 们，完全可以事实上被不同的 control 雇佣，因此根本就很难建立起 control-repo 这种映射关系。我们都改成单元化了，还有 repo instance 存在的必要么？"

## 二、它今天在干什么

Repo Instance 是控制面拥有的对象，指某台机器上一份 Git 克隆连同它的工作树，有稳定编号、主机与站点身份、现场代次，工具箱替它持有操作系统级的锁。它承担三件事：认现场，控制面派工前知道代码在哪台机器哪个目录，靠"挂接"命令把克隆登记成自己的现场；防旧写者，控制面重启或换机器后用现场代次把上一任写者挡在外面；恢复对账，控制面重启时以现场为单位对控制面存储、Git、运行时三方。

## 三、Fable 的立场

三件事都以"控制面是那份克隆的主人"为前提，单元模型拿掉了这个前提：用例里 cloud 上那份 gh-jssdk 的克隆同时被 mac_ctl 与 cloud_ctl 的参与者用，主人只能是 cloud 的 Agency。于是：认现场归 Agency，控制面雇人时说"我要在仓库 gh-jssdk 上干活"，Agency 负责有一份克隆，没有就用自己的凭据克隆（单元稿第 15 条）；防旧写者，锁与代次留在机器上由 Agency 管，控制面靠每次执行一张令牌防旧执行冒充（单元稿第 4 条）；恢复对账的单位改成执行与变更集，控制面重启后问各 Agency"哪些执行还活着、哪些结果等我收"（单元稿第 16 条）。

所以立场是：控制面拥有的 Repo Instance 对象与"挂接"命令一起取消；控制面存储里只剩引用，例如变更集记录里写"这次执行在哪个 Agency 的哪个现场、哪个工作树"，现场编号由 Agency 报上来；现场作为概念只留在 Agency 一侧，是它的实现细节；仓库在控制面这边只剩平台绑定与各 Project 的归属。

## 四、要核的三处

1. **没有平台的受限路径。** 那条路的集成目标今天是"某个 Repo Instance 上的本地分支"，现场归 Agency 之后目标要写成"某个 Agency 的某个现场上的分支"，集成由那台机器上的工具以比较并交换推进。这条路还成不成立，值不值得留，还是随 Repo Instance 一起收窄。
2. **恢复。** 现有约束"恢复第一步经工具箱取得适用现场的 OS 排他权"要改成"向各 Agency 要活着的执行清单并按令牌对账"。有没有漏掉的对账场景，例如 Agency 也重启了、或 Agency 换了机器。
3. **所有者自己的机器。** 所有者在本机编辑的那份克隆，按单元模型本机也跑着随包的 Agency，那份克隆是它的现场，控制面同样只引用。这样会不会把日常操作绕远，例如人在自己的工作树上直接改代码、想让控制面认这次改动的时候。

## 五、请 Codex 回答的

对第三节的立场给维持、修正、推翻；对第四节三处各给一个答案与理由；如果认为 Repo Instance 应保留，说清它保留下来回答的是哪个别的对象回答不了的问题。
