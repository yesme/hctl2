## 一、用例说了什么

三台机器。cloud 常开，装了三个 harness 和一个 Agency，Agency 上定义了四个参与者模板；mac 装了两个 harness 和一个 Agency，两个模板；ubuntu 装了两个 harness 和一个 Agency，两个模板。两个仓库，gh-jssdk 在 GitHub，gl-jstui 在 GitLab。

mac 上跑一个控制面 mac_ctl，对 gh-jssdk 开两个 Project，参与者一部分从本机 Agency 拿，检出在 mac，几个参与者共用一个对象库、各有检出；另一部分从 cloud 和 ubuntu 的 Agency 拿，检出在那两台机器上。cloud 上跑一个控制面 cloud_ctl，对 gl-jstui 和 gh-jssdk 各开一个 Project，参与者从本机、mac、ubuntu 三个 Agency 拿。cloud 建完 Project 之后没有常驻的本机前端，之后的人机交互经远程前端进来。ubuntu 不跑控制面，只跑 Agency 和一个 bench，bench 同时连着两个控制面上的三个 Project。mac 上 CLI 和 bench 都连着 mac_ctl。

所有者的世界观变化：以前从 harness 会话看问题，希望 ubuntu 上的 harness 能接管 mac 上做到一半的任务；现在不这么想了。机器之间不接管会话，传的是结晶和契约。

五家对"用例对不对"的结论一致：对，这是 HCTL2 该有的用法，内部没有自相矛盾。用例文本要对齐的细节见第八节。

## 二、用例的实质：单元模型（v3）

架构层的首句与第二句（Codex 起草，Kimi 要求第二句一起进，否则仓库从第一句里消失）：

> HCTL2 让多个独立的控制面复用 Agency 与各类内容服务开展协作；每个控制面负责自己的授权和判定，供应端负责它承载的资源与事实，前端组合这些视图和入口。仓库是共同工作的对象：代码版本由 Git 识别，平台拥有它所承载目标的更新与评审记录。

所有者对这个方向的原话是"按模块解耦"。"单元"作为下文的词汇，不进首句（GLM：首句先说权威归属，再展开谁能独立装）。

**四类单元和一个底座。** 判据只留两条：能独立安装、启动、停止，与别的单元只靠连接来往；生命周期不随别的单元起落。Kimi 第一轮的"持有自己的凭据、有自己的持久状态"不作判据（GLM、Codex 反驳成立：前端没有持久状态照样是单元；凭据放哪定不了信任边界），改成两条义务：持有事实的单元必须有持久状态；需要凭据的动作在持有凭据的单元上做。工具箱不是单元，它是参与者所在机器上的一组工具，见第四节第 3 条。

- **Agency**：一台机器上装了哪些 harness、能派出什么模板，由这台机器的主人决定；生命周期与任何控制面无关；一台只跑 Agency 的服务器是正常形态；同时给多个控制面供人；模型凭据是模板打包的一部分；持有还没被控制面收走的结果与证据，所以必须有持久存储。
- **控制面**：只拥有治理记录，即 Project、Task、Run、参与者身份、授权、意图、凭证，在自己的存储里；向任何 Agency 要人，向任何平台绑仓库；一个仓库同时被多个控制面开 Project 是常态。
- **前端**：CLI 和 bench，不拥有事实，可以连一个或多个控制面，本机或远程；不越过控制面去碰参与者。联合视图里每项事实和动作保留它来自哪个控制面；前端的投影不构成新的权威（Codex）。
- **内容系统**：聊天服务器、任务源、代码协作平台、工作流引擎。各自独立，多个控制面可以绑同一个。随包只是缺省安装位置，不是信任范围，也不是只能由本机控制面拉起；这句要进架构正文，因为"只绑回环"那条约束就是从"随包等于本地"长出来的（GLM、Grok）。
- **仓库不是单元，是底座**：Git 与平台。显式不挂平台的受限路径下，底座只有 Git（Kimi）。

**部署对等不是权威对等**（Grok）：控制面独占治理命令、意图与凭证；Agency 永远不含治理权威。机器是几种单元的宿主，不是单元；一个 Agency 不必永远只占一台机器；Project 的聊天室归控制面，不等于聊天服务器必须部署在那台机器上（Codex）。

**三种关系，不再合写成"归属三分"。**

- **放置**：会话、检出、对象库、还没推出去的提交，都在参与者所在的机器上。平台不因此拥有全部代码字节。
- **权威**：每个控制面对自己的授权与判定负责；平台拥有它承载的目标的更新与评审记录；聊天、卡、评审线程各归自己的内容系统。一个控制面的批准不是另一个控制面的批准；一个平台上的合并结果谁都能读。另一个控制面能读到一份正文，不等于它采纳了那份契约、批准或 current 指针；字节可见不转移治理权威（Codex，用于第 13 条）。
- **交付**：结果与证据要有一条可达的路径到验收方。共同平台是一种路径，持凭据单元的中转是另一种。#191 反馈文件里"跨机集成必须依赖公共 Remote"这句由此推翻，Antigravity 作为作者已认可："没有共同平台"和"没有任何数据通路"不是一回事。

**单元之间的总规则**（Kimi 提出，Codex 改写，Grok 补"没有跨单元事务指没有跨单元的原子提交"）：

> 各类事实按职责确定权威；跨单元的操作不依赖一次原子提交，靠请求、确认与恢复对账衔接。

平台仲裁合入、联系不上与丢失分开、结果在 Agency 等控制面来收、任务源按自己的能力处理并发写，都是它的特例。

## 三、所有者对追问的回答（2026-09-07）

1. **聊天室归 Project。** Project 是协作的起点，聊天室与它绑定，跟着 Project 所在的控制面走。看板另论，见第五节。
2. **会话。** "mac_tpl_sdet 基于 mac_gemini"只是说物理上有一个 gemini 会话在跑。由此引出待命原则，见第六节。
3. **推送由参与者做。** 控制面告诉参与者要推，推的动作来自参与者自己。
4. **分层各有闭包。** bench 不越过控制面去抓参与者。控制面睡着时，参与者照常干到封存，结果在 Agency 那边等，控制面醒来再收；产品要显示"这个结果在等哪个控制面"。
5. **凭据。** 模型凭据在 Agency 这边，本来就是参与者 offering 的一部分。git 凭据与 gh 登录怎么传，实现时具体看，最坏情况让持有凭据的单元中转。

## 四、从用例反推的设计问题（v3：五组十七条）

分组按 Codex 第一轮的推导表，第二轮五家都接受。Codex 第二轮补的性质标注写在各条开头：第 6 条是所有者已定的取舍加它的权限条件；第 13 条是存放选择；第 16 条是离线交付推出的保管责任；第 17 条是各种期限的含义与裁决范围；第 10、11 条是所有者明确要求的能力，不是从部署推出的。第 9 条留在乙组（Grok 反驳 Kimi 的降格成立：独立部署推得出会连不上，推不出丢失的定义）。

### 甲、部署前提

1. **没有单元模型。** 三面架构讲职责分层，没讲什么可以独立装、独立活、互相怎么连。要改的是把生命周期与连接范围写成控制面附属的那些句子，即"一人多机只连同一控制面""随控制面一键启停""只绑回环"，不是笼统说现文把一切嵌在控制面旁边（Codex 收窄，Grok 接受）。落点：`architecture.md`、`vision.md`、`spec/system.md` §组件与 §信任边界。

### 乙、独立原则

6. **凭据在哪，动作在哪。**（所有者已定的取舍，加它的权限条件。）推送在持 git 凭据的单元上做，缺省是参与者所在的机器；开评审请求、请求合并、写回结论缺省在控制面，但这也是同一条原则的例子，不是定律（Grok）。授权、防止越权、证明结果是三件事（Codex）：推送权限与更新集成目标的权限分别限定，落到有权执行的单元与平台能力上；报告的认证只解决证据来源，不代替权限限制；令牌不交给模型，没有令牌的工具输出按转述处理（Grok）；原来靠"机器上没有凭据"保证的部分，做不到的要明确列出，不能写成"分支保护加带令牌报告"就等价承接（Codex、Kimi）。落点：`spec/repo.md` §发布评审、`spec/participant.md` §三条底线。
7. **仓库身份的范围。** 多控制面之后，"注册确认激活唯一 Repo 身份"只在一个控制面之内成立；往仓库里写身份文件作废（Antigravity 作为原提议者已认可）。平台上的仓库身份、各控制面自己的本地引用、实际的克隆是三样东西，分开写；显式不挂平台的受限路径没有平台身份，只剩 Git 根提交这个更弱的旁证，要写明；仓库从一个平台迁到另一个平台时怎么认，也要写。这三个子问题写进清单不等于已解决（Codex）。落点：`spec/repo.md` §Repo 注册。
8. **跨控制面的效力。** "同一目标同时至多一个待决集成意图"是一个控制面内的规则；跨控制面靠平台的分支保护和合并串行化，平台是集成的仲裁者。别的控制面的合法合入是外部事实，不是"不支持的供应端修改"；控制面不能只订阅自己发出的事件，要观察共同事实并据此重核自己的后续动作；平台上的结果不自动成为自己的 Task 完成凭证，另一个控制面怎么把已合入的代码用于自己的验收是未回答的问题（Codex）。独立写入者的分支必须事前不相交，但不固定唯一的命名格式，共享工作树的写入互斥也不靠分支名（Codex 收窄 Kimi、GLM 的写法）。落点：`spec/repo.md` §集成、§平台动作与命令；`spec/system.md` §客户端动作与 provider 事件；`spec/task.md` §写入约束。
9. **联系不上、截止已过、身份不可证是三件事。**（v2 把前两件混了，Codex 第二轮纠正，Kimi 撤回"两个状态"的写法。）联系不上是观测，叠在雇佣状态上，不是新状态（Grok）；失联本身不证明执行已丢失，也不延长它的授权：执行是否仍获准继续，按事先接受的范围、截止与取消条件判断，控制面睡着不给 Agency 过夜的许可，除非事先约定只算活跃时间（Codex）；恢复后核对身份与结果，身份可证则原执行继续，不可证才按丢失处理；Agency 重连后的回答是核对的输入，不是唯一判据，坏掉的 Agency 不必无限等（Codex 收窄 Kimi）。"完结待交"是用户要看得见的一种情形：参与者封存完毕、结果在 Agency 等某个控制面收（GLM）。落点：`spec/participant.md` §运行时与观测、`spec/connections.md` §失败与恢复。
13. **治理正文的存放。**（存放选择，GLM 立根，Grok、Codex 同。）`spec/system.md` 规定 `<repo>/.hctl2/` 下的 repo.toml、projects、memos、policies 是 Git 跟踪文件。给别人的仓库贡献时写不进去；同一仓库上的两个控制面互相覆盖，也未必愿意把材料公开给对方。取消身份文件没有回答这个问题。真正的问题是写入权限、公开范围和取回路径，不是字节被看见就转移了权威（Codex）。五家收敛后的形状与待选见第九节第 7 点。落点：`spec/system.md` §Git 的双重角色、§控制面自己的存储。
16. **单元各有持久状态与交付责任。**（离线交付推出的保管责任；Grok、Kimi、Codex。）控制面睡着时，结果、证据、对应代码可能只有 Agency 一侧持有；它们没有治理权威，但不是可以随意删的缓存。Agency 要有自己的持久存储，保留到接收方确认具体交付项已保全，只记下摘要或指针不算保全（Codex）；重连后双方按关联键幂等对账，重复收取返回同一结果。落点：`spec/system.md` §启动与恢复、`spec/participant.md`。
17. **期限各有各的钟。**（Kimi 提出"时钟归属"，Codex 收窄。）多单元之后没有全局的"同时"。各单元的时间戳是证据，控制面的判定是权威；Agency 的闲置条件、控制面的执行截止、平台自己的有效期是三只不同的钟，各按各的规则算；睡眠不改变已冻结的截止，"只算活跃时间"要事先约定，不能在恢复时替用户延长。落点：与恢复规则一起写。

### 丙、分责选择（各自要说理由）

2. **执行现场的归属。** 检出在参与者所在的机器上，那台机器可能没有控制面，或同时服务几个控制面。物化、对象库管理、现场锁与代次栅栏搬到机器一侧；挂接记录、代次的引用、对这个现场的写入授权留在控制面（Kimi）；Repo 模块仍然拥有本控制面对现场的登记与授权（Codex）。同机共用对象库是允许的布局，不是必须的布局（Codex）。落点：`spec/repo.md` §Repo 注册与 Repo Instance 挂接、§写入约束。
3. **工具箱的形态与证据分级。** 所有者定：工具箱是一组工具，在参与者内部被当作工具调用。五家第二轮一致：语义上它仍是 Repo 模块的现场执行者，"属于哪个模块"与"谁起这个进程、进程在哪"是两条轴（Grok 撤回根子改）。要拆掉的是现文暗绑在这句上的三件附属物（Grok）：它是控制面旁边的进程；证据最高是因为它是控制面的进程；推送默认从控制面旁边发出。改成：工具不以与控制面同机、由控制面直接起进程为前提（Codex 纠正 v2 的"控制面没有现场进程"，控制面本机也可以运行工具，那时它就是持有凭据的单元之一，例如派工前查 CI、人显式封存）；由参与者当作工具调用时，报告走模型写不进去的通道。GLM 建议把"现场执行者"这个固定短语拆成"执行 Repo 模块的命令"与"部署在参与者一侧"两句，归第二个问题时的文风处理，不作为保留语义的条件（Codex）。

   证据分级采纳 Grok 的三档，中文名用 GLM 的：直报（unmediated，字节没进过模型的嘴）、旁路（adapter_event，适配器旁路观察到的结构化事件）、转述（narrated，出现在模型输出里的声称）；未标注按转述，转述不能升级。Codex 第二轮的两处收窄采纳：直报的来源不止一种，控制面自己的适配器读平台、控制面本机运行的工具、参与者内部带执行凭据的工具都可以是直报，不能把派工前查 CI、无 Run 的人工封存这些路径硬套成"必须先有 Agency 执行令牌"；未经模型只是条件之一，控制面还要核报告的来源、它证明的是哪次执行、哪个目标与版本。Kimi 的搭配条件一并写：保留"现场执行者"成立的前提是三档分级、直报通道和 `spec/repo.md`、`spec/participant.md`、`spec/task.md`、`spec/run.md` 里所有以工具箱回读为最高级的句子同步改；Task 的机械项现文允许工具箱回读或适配器结构化事件，Run 的节点前置才限定工具箱回读，改写时不要顺手把 Task 收紧（Codex 核出处，Kimi 核实）。落点：`spec/participant.md` §证据通道、`spec/system.md` §组件、`spec/repo.md` §对象。
5. **模板的归属。** 用例里模板是 Agency 定义的。分清供给与需求：Agency 发布供给条件，即模板、安装与凭据；控制面记录自己的选择、权限上限和实际生效的配置；模板之后的变化不能悄悄改掉控制面已接受的条件（Codex）。Worker Profile 怎么拆、要不要改名，不由"模板归供给方"直接推出，归第二个问题时定（Codex 第二轮），GLM 的"模板升核心产品词、Worker Profile 降为模板内字段组"记为候选。落点：`spec/participant.md` §对象、`participant.md`。

### 丁、推论

4. **Agency 端点排他改为按执行排他。**（第 1 条的推论。）配对不排他，同一 Agency 同时服务多个控制面；对具体执行的输入、停止与结果准入有范围，一个执行同一时间只听一个控制面。机制留给约束批，但要满足 Codex 第二轮的三个条件：同一进程续做下一次调用不续用上次的权限；进程已结束、结果尚待交付时，已完成的报告仍能核验；一个控制面重启、换绑或从旧备份恢复时，只隔离自己过期的动作权限，保留未确认的意图与结果，恢复后核对原授权再处理，不使别人在同一 Agency 上的执行失效。Grok 第一轮的执行令牌方案是候选，签发与撤销的责任要厘清；删掉"Agency binding owner generation"这个代次家族要先证明替代办法仍能隔离旧动作（Codex）。落点：`spec/system.md` §单写者、§代次家族、§启动与恢复；`spec/connections.md`。
10. **随包内容系统的访问范围。**（所有者要求的能力。）缺省回环、非本地必须认证，不是默认对外裸绑（Grok）。落点：`spec/system.md` §信任边界。
11. **一个前端连多个控制面。**（所有者要求的能力。）联合视图是投影层的合并，不转移权威，每项事实与动作保留控制面来源。落点：`architecture.md` §三个面。
14. **共享对象库上的 ref 命名空间。**（GLM、Kimi 补。）同一台机器的对象库被两个控制面共用时，refs/hctl2 与变更集分支会撞名；要求是独立写入者的引用事前不相交，格式不在本轮定（Codex）。落点：`spec/repo.md` §ChangeSet 与 Git 事实。
15. **参与者机器的引导。**（GLM、Codex 补。）ubuntu 第一次给 mac_ctl 供人时，得先有 gh-jssdk 的克隆：谁下第一笔 clone、用谁的凭据、克隆归谁管。写法按 Codex 对齐第三节第 5 问：首次取得材料与交付结果都要有获准且可达的路径，有凭据直接做，没有按既定中转安排，不悄悄加"每台机器都必须登录平台"的前置。落点：交付层。

## 五、看板：多源（v3）

所有者：一边用 GitHub 一边用 Linear 管看板并不罕见；缺省任务源要把选项列出来让用户选，缺省给平台自带的 issues，但必须显式同意。

- **卡的内容有一个事实源，源可以有很多种。** 标题、描述、讨论、板上位置住在某一个任务源里；一个仓库可以同时绑多个任务源，也可以一个都不绑；Project 只在启用了看板时才要有缺省源，只开聊天室的 Project 不被这张表默默排除（Codex）。
- **一张任务只有一个事实源，不做源与源之间的双向同步。** Linear 里的一条和 GitHub 里的一条对 HCTL 是两张卡；别的源里的相关卡只是引用。一个事实源不等于只有一个写入客户端（Codex 收窄 GLM 的"单写者"）：用户用合适的客户端编辑那张 Linear 卡照样可以，写发往卡实际所在的源，HCTL 不自动跨源同步。卡的身份是现行的实体键，即供应端、账号、实体种类与不可变外部 ID，不含绑定；换绑或两个控制面各有一份绑定都不产生第二张卡；多源之后要核的是控制面内的唯一范围，不是往键里加绑定（Codex 纠正 GLM）。
- **Project 绑一个缺省源，认领可以跨源。** 从 HCTL 新建的任务落到缺省源；仓库绑定的其他源里已有的卡，Project 可以认领，认领不搬家，认领进哪个 Project 由人显式选，不沿用"外部卡必须恰在一个分组里才可认领"的旧前置。认领之后，卡在外源的分组与它在 HCTL 的 Project 归属正式脱钩，合并板上的跨源归组只认控制面自己的 Task 到 Project 记录，不去外源补建分组来"修复"归组（GLM 的脱钩声明）。
- **两套分组并存**（GLM）：源内分组是源原生的 milestone、Linear project、标签，只在缺省源里建；跨源归组靠控制面投影。
- **合并板是投影，不是新的权威表**（Codex）：合并的是当前控制面或前端所知的各源；同一张外部卡可以合并显示，但关联的两份 Task、各自的验收状态与控制面来源分别展示；还没被认领的卡也要出现在板上。
- **对象与基数**（GLM 提出，Codex 收窄）：仓库到任务源绑定 0..N；启用看板的 Project 到缺省源引用恰一个；Task 到"卡在哪个源"的引用 0..1。本轮只做引用不做迁移；迁移要不要新建 Task、要不要显式命令，是另一项取舍（Codex）；Kimi 的建议记为候选：不留迁移命令，迁移等于新建 Task 认领另一张卡并把旧 Task 显式标为被替代。
- **跨控制面绑同一张卡的边界**（Grok、Kimi、Codex）：一方完成自己的 Task 不自动完成另一方；控制面的自动完成写回不能冒充人的新命令；人用原生客户端做的 Done，仍可按另一方自己的绑定成为一次请求，由它独立验收（Codex 纠正 Grok 的"只是 Snapshot"全称）；写回评论必须带控制面与 Task 标识。卡内容的并发写按任务源自己的能力处理，有条件写入的用条件写入，没有的以回读为准并保留结果未知，不承诺所有任务源都能拒绝竞争写入（Codex 纠正 Kimi）。
- **认领的卡所在的源后来被解绑**（Kimi）：Task 悬空，标为需要关注，不静默。
- **缺省源须显式同意。**

## 六、雇佣与待命（v3）

所有者的原则：谁"占有、雇佣、使用"了某个参与者，只要它的生命周期没有完结，参与者就一直待命，既不新起会话，也不关闭进程后再恢复；只有闲置超时能让进程退出、会话冬眠。

- **雇佣是正式关系，与授权、席位、Room Invocation 并列，不是替代**（五家一致；GLM 的定义：雇佣是会话的持有关系，回答"下次找它时它是醒着、睡着还是在磁盘上"）。授权回答准许做什么；Room Invocation 回答这次做什么；席位是 Run 里的位置；雇佣可以跨越多次调用，但不代替它们，也不自动赋予新的席位或票权。
- **雇佣怎么建立、怎么结束**（Codex 第二轮要求写明，v2 的"调用创建雇佣"不够）：雇佣由一项持续的安排建立，Project 一级是为这个 Project 常驻的参与者安排，Run 一级是席位的安排；调用和尝试使用这项安排，不是每次调用各建一份。结束要指明结束的是哪项雇佣、哪次执行、还是以后的派工资格：Project 结束或撤销该参与者在这个 Project 的授权，结束这项雇佣与它的会话，不牵连这个参与者在别处的雇佣，也不追溯已完成的交付（Kimi、Codex）。
- **复用会话不复用授权**（Codex 的两个反例）：Project 的聊天参与者还雇着，上一轮写任务已取消，会话可以待命，旧写权限必须结束；"雇着"不自动成为新一轮施工授权，也不延长旧的写租约。
- **三样东西分开。** 参与者身份在控制面存储里，永久；harness 会话是 Agency 那台机器磁盘上的对话状态，有会话号；执行进程用完就没。所有者的"内存与磁盘对偶"是帮助理解的类比：进程、会话记录、未封存修改的寿命各不相同，只有已保全的字节才谈得上重建（Codex、Antigravity 认可）。
- **会话状态与执行身份是两回事**（Codex 第二轮纠正 Kimi 的"会话文件也丢了才丢失"）。会话可恢复，不证明被打断的写入有没有发生，也不证明旧执行身份仍成立。进程意外死亡时，被打断的那次执行按既有规则记为失败、丢失或待核对；雇佣可以用恢复的会话开始下一次执行，但那是新执行，不是旧执行继续。
- **四个状态与转换**（Kimi 的表，按上一条修正）。活跃：进程在，会话在内存，正在干活。待命：进程在，闲着。冬眠：进程不在，会话在磁盘，不问是主动冬眠还是被杀后靠会话文件恢复。结束：雇佣完结，会话归档，是终态；重聘算新雇佣，可以从归档会话分叉，审计要求与从冬眠会话分叉同一档（GLM）。转换：活跃到待命，调用交付即回待命；待命到活跃，有新任务；待命到冬眠，闲置超时；冬眠到活跃，唤醒即新起进程并按会话号恢复，唤醒失败不能伪装成活跃（Codex）；待命与冬眠可以直接结束，Project 结束时不强制唤醒归档（GLM、Kimi）；活跃到结束，先等交付或按撤权终止再结束。
- **两个叠加态，不是新状态**：联系不上是观测，叠在活跃或待命上，合盖时进程可能只是被操作系统冻结，那是联系不上的活跃，不是冬眠（Grok）；完结待交是参与者封存完毕、结果在 Agency 等某个控制面收，用户要看得见（GLM）。
- **分叉。** 席位雇的那个可以从聊天室的会话分叉，起点带着 Project 的上下文。分叉的来源可以为空：直接进 Run 的席位、替补参与者、没有 Project 的只读研究都要能从零新起（Kimi、Codex）。来源在冬眠时先唤醒，或允许从磁盘会话分叉并记审计（Grok）。
- **分叉要可审计，只记会话号和位置不够**（Codex，Grok 第二轮撤回"摘要够用"）：要能核对"获准继承的具体会话状态加本次增量"，继承的内容要可取回、要过范围检查，才知道模型实际收到了什么；核对不了的部分可以保留续用能力，但要记缺口，不能宣称输入已完整冻结。评审独立性不是一刀切的禁令（Codex 第二轮纠正 v2 的归因与写法，本轮的交叉审阅本身就要求读作者说明）：生产者与评审者的身份分离、本次允许的输入范围，分别核对；只有契约或 Gate 策略要求盲审、要求隔离作者讨论时，评审席位才不得继承作者一侧的会话。
- **两个参数在模板里，机器的主人定**：闲置多久冬眠；会话长到什么程度主动整理一次。控制面记录它接受的版本与实际生效值。
- **会话不跨机器。** 冬眠的会话是文件，理论上能搬，但记着工作树路径、工具状态和那台机器的凭据；换机器只能新起，带上结晶与契约。这是本批恢复范围的选择，不论证成所有实现都做不到迁移（Codex）；Antigravity 从实践确认活跃进程跨异构机器迁移从未稳定过。

实现层脚注：每个回合 harness 都要把整段对话重新送给模型，进程活着省的是启动时间和提示缓存的热度，不省这部分 token；真正省 token 的是续用而不是新起。Claude Code 与 Codex 都有按会话号恢复的原生入口（`docs/research/harness-adapters.md`）。Antigravity 从实践补一句：每次封存后拆工作树、返工再物化，磁盘 I/O 与本地依赖缓存的代价不小，雇佣期间保留工作树是对的。

## 七、失败路径（Kimi 为主，Codex、Grok 修正）

总模式见第二节的总规则。五个情形：

| 情形 | 用户看到什么 | 各方保留什么、怎么继续 |
| --- | --- | --- |
| mac 合盖，cloud_ctl 用的参与者在 mac | 该参与者标"联系不上"，最后观测时间明确；不是丢失；进行中的调用显示等待恢复；其他机器的工作照常 | 控制面记断开的事实与时间；已接受的范围、截止与取消条件不变，失联不延长授权也不撤权；mac 一侧什么都不记，进程被 OS 挂起。开盖重连后核对：执行身份可证则原调用继续，零重建；不可证则按丢失处理，走既有失权与恢复；截止已过的按截止处理。Agency 的回答是核对的输入，不是唯一判据 |
| cloud 断网，mac_ctl 用的参与者在 cloud | mac 的前端里 cloud 来的参与者标联系不上，本地一切正常；不能声称知道远端是在跑、待命还是已结束 | cloud 上的参与者在已接受的范围与截止内照常干活、照常封存，结果交不了；Agency 把待交付结果存在自己的持久存储里；重连后双向按关联键补同步，重复收取返回同一结果；已撤权或被替代的结果另作处理 |
| 控制面睡着，参与者干完了 | 事后从任一前端看到"某参与者在某时刻完成了某调用，结果待某控制面收取"，不显示已验收；Agency 本机没前端也能从别处看到 | 封存不依赖控制面，准入才需要；Agency 保留结果与证据，直到接收方确认具体交付项已保全；控制面醒来先与各 Agency 对账"我睡着期间你有什么等我的"，按原授权核验，不因普通断线重连就丢弃结果；睡眠不改变已冻结的截止，只算活跃时间要事先约定 |
| 两个控制面同时对同一仓库开 PR 并请求合并 | 平台上两条评审请求，分支可辨来自哪个控制面的哪个 ChangeSet；先合入的正常进，后合入的按平台保护规则被拦、要求重新确认，或事前选了接受目标前移时带目标前移合入；各自的 Change 场景如实显示自己那条 | 各记各的意图与凭证，跨控制面没有互斥；另一控制面的合法合入是外部事实，不算违规，也不自动成为自己的完成凭证；预期目标头形态的旧前提失效要重新确认。事前要求：独立写入者的分支不相交 |
| 两个控制面同时改同一张看板卡 | 合并板上同一张卡出现在两个 Project 的投影里；卡内容以任务源为准；治理状态各自独立，同一张卡在 mac_ctl 是"进行中"、在 cloud_ctl 是"待办"不矛盾 | 各控制面记自己的绑定与版本；卡内容的并发写按任务源的能力处理，有条件写入的用，没有的以回读为准；写回评论带控制面与 Task 标识；自动写回互不触发完成，人的原生 Done 按各自绑定处理 |

## 八、用例文本要对齐的地方（所有者 2026-09-07 同意，已按下列写法改入用例与反馈文件）

1. 场景环境写 ubuntu"创建了 3 个 participant templates"，下面只列了两个（Grok、Codex）。
2. cloud"之后就没有前端了"改成"没有常驻的本机前端"，并写明合入预览、完成 Task 这些治理动作经 ubuntu_bench 进来；无前端不等于无须人决策（Kimi、Grok、Codex）。
3. 跨 Project 共用对象库"可商榷"：两种布局在单元模型下都合法；形成具体验收用例时写清测哪种即可，本轮不必定死一条（Codex 收窄 Grok 的"不能留分叉"）。
