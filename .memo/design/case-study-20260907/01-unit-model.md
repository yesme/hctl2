v2 改了什么：单元从"五种"改为四类加一个底座，补单元的判据和"部署对等不是权威对等"；"归属三分"拆成放置、权威、交付三种关系，并加一条单元之间的总规则；十二条改成前提、原则、分责选择、推论、交付五组，补五条漏项成十七条；看板补对象表与跨控制面写回的边界；雇佣补状态转换、两个叠加态、分叉的来源与审计要求；新增失败路径一节和用例文本要对齐的清单。每处改动在括号里标来源，四家意见互相矛盾处写明取舍。

## 一、用例说了什么

三台机器。cloud 常开，装了三个 harness 和一个 Agency，Agency 上定义了四个参与者模板；mac 装了两个 harness 和一个 Agency，两个模板；ubuntu 装了两个 harness 和一个 Agency，两个模板。两个仓库，gh-jssdk 在 GitHub，gl-jstui 在 GitLab。

mac 上跑一个控制面 mac_ctl，对 gh-jssdk 开两个 Project，参与者一部分从本机 Agency 拿，检出在 mac，几个参与者共用一个对象库、各有检出；另一部分从 cloud 和 ubuntu 的 Agency 拿，检出在那两台机器上。cloud 上跑一个控制面 cloud_ctl，对 gl-jstui 和 gh-jssdk 各开一个 Project，参与者从本机、mac、ubuntu 三个 Agency 拿。cloud 建完 Project 之后没有常驻的本机前端，之后的人机交互经远程前端进来。ubuntu 不跑控制面，只跑 Agency 和一个 bench，bench 同时连着两个控制面上的三个 Project。mac 上 CLI 和 bench 都连着 mac_ctl。

所有者的世界观变化：以前从 harness 会话看问题，希望 ubuntu 上的 harness 能接管 mac 上做到一半的任务；现在不这么想了。机器之间不接管会话，传的是结晶和契约。

四家对"用例对不对"的结论一致：对，这是 HCTL2 该有的用法，内部没有自相矛盾。用例文本要对齐的细节见第八节。

## 二、用例的实质：单元模型（v2）

架构层首句的候选（Codex 起草，我认为比"几种单元"更准，因为它先说了权威在哪）：

> HCTL2 让多个独立的控制面复用 Agency 与各类内容服务开展协作；每个控制面负责自己的授权和判定，供应端负责它承载的资源与事实，前端组合这些视图和入口。

所有者对这个方向的原话是"按模块解耦"。下面是它展开后的样子。

**四类单元和一个底座。** 判据（Kimi）：一个单元有独立的生命周期，有独立的信任域即持有自己的凭据，有独立的可用性域即能独立活、独立死，并且有自己的持久状态。按这个判据，工具箱不是单元，它是参与者所在机器上的一组工具，见第四节第 3 条（Kimi、Grok、GLM 一致）。

- **Agency**：一台机器上装了哪些 harness、能派出什么模板，由这台机器的主人决定；生命周期与任何控制面无关；一台只跑 Agency 的服务器是正常形态；同时给多个控制面供人；模型凭据是模板打包的一部分；有自己的持久存储，保管还没被控制面收走的结果与证据。
- **控制面**：只拥有治理记录，即 Project、Task、Run、参与者身份、授权、意图、凭证，在自己的存储里；向任何 Agency 要人，向任何平台绑仓库；一个仓库同时被多个控制面开 Project 是常态。
- **前端**：CLI 和 bench，不拥有事实，可以连一个或多个控制面，本机或远程；不越过控制面去碰参与者。联合视图里每项事实和动作保留它来自哪个控制面（Codex）。
- **内容系统**：聊天服务器、任务源、代码协作平台、工作流引擎（Codex 补上引擎）。各自独立，多个控制面可以绑同一个。随包只是缺省安装位置，不是信任范围，也不是只能由本机控制面拉起（GLM、Grok）；这句要进架构正文，因为"只绑回环"那条约束就是从"随包等于本地"这个隐含假设长出来的。
- **仓库不是单元，是底座**：Git 与平台。显式不挂平台的受限路径下，底座只有 Git（Kimi）。

**部署对等不是权威对等**（Grok）：控制面独占治理命令、意图与凭证；Agency 永远不含治理权威。机器是几种单元的宿主，不是单元；一个 Agency 不必永远只占一台机器；Project 的聊天室归控制面，不等于聊天服务器必须部署在那台机器上（Codex）。

**三种关系，不再合写成"归属三分"。** 四家都指出原来那三句"归"混了不同的关系（Codex 说得最准：放置、权威、存储与目标各是一回事）；GLM 补对象库，Grok 补内容，Kimi 指出"代码归平台"在受限路径下没有着落。改成：

- **放置**：会话、检出、对象库、还没推出去的提交，都在参与者所在的机器上。平台不因此拥有全部代码字节。
- **权威**：每个控制面对自己的授权与判定负责；平台拥有它承载的目标的更新与评审记录；聊天、卡、评审线程各归自己的内容系统。一个控制面的批准不是另一个控制面的批准；一个平台上的合并结果谁都能读。
- **交付**：结果与证据要有一条可达的路径到验收方。共同平台是一种路径，持凭据单元的中转是另一种。#191 反馈文件里"跨机集成必须依赖公共 Remote"这句由此推翻（Codex）："没有共同平台"和"没有任何数据通路"不是一回事。

**单元之间的总规则**（Kimi）：每个单元是自己事实的权威；单元之间只有"联系不上、拒绝、事后对账"三种关系，没有跨单元事务。平台仲裁合入、联系不上与丢失分开、结果在 Agency 等控制面来收、任务源的条件写入，都是它的特例。

## 三、所有者对追问的回答（2026-09-07）

1. **聊天室归 Project。** Project 是协作的起点，聊天室与它绑定，跟着 Project 所在的控制面走。看板另论，见第五节。
2. **会话。** "mac_tpl_sdet 基于 mac_gemini"只是说物理上有一个 gemini 会话在跑。由此引出待命原则，见第六节。
3. **推送由参与者做。** 控制面告诉参与者要推，推的动作来自参与者自己。
4. **分层各有闭包。** bench 不越过控制面去抓参与者。控制面睡着时，参与者照常干到封存，结果在 Agency 那边等，控制面醒来再收；产品要显示"这个结果在等哪个控制面"。
5. **凭据。** 模型凭据在 Agency 这边，本来就是参与者 offering 的一部分。git 凭据与 gh 登录怎么传，实现时具体看，最坏情况让持有凭据的单元中转。

## 四、从用例反推的设计问题（v2：五组十七条）

第一版把一到五叫根、六到十二叫推论。四家都认为这个划分要调：GLM 把 4 降为推论；Grok 说 6、7 的身份、9 都含独立原则；Kimi 说 6 来自所有者的独立拍板；Codex 给了一张推导表，把它们分成部署前提、独立原则、需要各自说理由的分责选择、推论和交付安排。v2 采用 Codex 的五组，编号沿用第一版，新增 13 到 17。

### 甲、部署前提

1. **没有单元模型。** 三面架构讲职责分层，没讲什么可以独立装、独立活、互相怎么连。Codex 的修正采纳：架构正文已经说执行系统是独立进程或服务器，真正要改的是把生命周期与连接范围写成控制面附属的那些句子，即"一人多机只连同一控制面""随控制面一键启停""只绑回环"，而不是笼统说现文把一切都嵌在控制面旁边。落点：`architecture.md`、`vision.md`、`spec/system.md` §组件与 §信任边界。

### 乙、独立原则

6. **凭据在哪，动作在哪。**（Grok 补为根；Kimi：它来自所有者的独立拍板，从一到五推不出来。）推送在持 git 凭据的单元上做，缺省是参与者所在的机器；开评审请求、请求合并、写回结论缺省在控制面，但这也是"凭据在哪动作在哪"的一个例子，不是定律（Grok）。Codex 补的一条要写进约束：授权、防止越权、证明结果是三件事。令牌只证明报告来自哪次执行，不证明内容对本次候选成立，也不替代合入权限；允许推哪些源分支、谁能更新集成目标，分别落到有权执行的单元和平台的能力上。"合入的钥匙不进工具"的保证从"机器上没有凭据"改为"平台分支保护加控制面只认带令牌的报告"，这是安全模型的真实变化，不是等价替换，要作为约束新写并配失败用例（Kimi、GLM）。落点：`spec/repo.md` §发布评审、`spec/participant.md` §三条底线。
7. **仓库身份的范围。** 多控制面之后，"注册确认激活唯一 Repo 身份"只在一个控制面之内成立；往仓库里写身份文件这条路作废。Grok 与 Codex 的修正采纳：平台上的仓库身份、各控制面自己的本地引用、实际的克隆是三样东西，要分开写；显式不挂平台的受限路径没有平台身份，只剩 Git 根提交这个更弱的旁证，要写明；仓库从一个平台迁到另一个平台时怎么认，也要写。落点：`spec/repo.md` §Repo 注册。
8. **跨控制面的效力。** "同一目标同时至多一个待决集成意图"是一个控制面内的规则；跨控制面靠平台的分支保护和合并串行化，平台是集成的仲裁者。Codex 的修正采纳：别的控制面的合法合入是外部事实，不是"不支持的供应端修改"；控制面不能只订阅自己发出的事件，要观察共同事实并据此重核自己的后续动作（预期目标头形态的旧前提失效要重新确认，接受目标前移形态按冻结条件继续）；平台上的结果不自动成为自己的 Task 完成凭证，另一个控制面怎么把已合入的代码用于自己的验收是未回答的问题。Kimi 补：分支名字空间必须事前不相交，分支名嵌控制面身份与 ChangeSet 稳定 ID。落点：`spec/repo.md` §集成、§平台动作与命令；`spec/system.md` §客户端动作与 provider 事件；`spec/task.md` §写入约束。
9. **联系不上与丢失。** 远程 Agency 断连一分钟、执行体还在跑，不是丢失。三家的修正一起采纳：连接健康是观测，叠在雇佣状态上，不是第五个状态（Grok）；丢失仍然只指执行身份不可证（Codex）；从联系不上转到丢失的判据是重连后 Agency 的回答，不是固定时长，笔记本过夜八小时不该被判成丢失（Kimi）；"完结待交"是用户要看得见的一种状态：参与者封存完毕、结果在 Agency 等某个控制面收（GLM）。两个方向都会发生：mac 合盖时 cloud 的 Project 失去 mac 供的参与者，cloud 断网时 mac_ctl 失去 cloud 上的参与者。落点：`spec/participant.md` §运行时与观测、`spec/connections.md` §失败与恢复。
13. **治理正文的存放。**（GLM 补为根；Grok、Codex 同。）`spec/system.md` 规定 `<repo>/.hctl2/` 下的 repo.toml、projects、memos、policies 是 Git 跟踪文件。给别人的仓库贡献时写不进去；同一仓库上的两个控制面互相覆盖，也未必愿意把各自的治理材料发布给对方。取消身份文件没有回答这个问题。要单独讨论：既不能默认沿用旧拓扑，也不能顺手推成"全部正文搬进控制面存储"。落点：`spec/system.md` §Git 的双重角色、§控制面自己的存储。
16. **单元各有持久状态与交付责任。**（Grok 补为根；Kimi 的失败路径与 Codex 的第二处一起。）控制面睡着时，结果、证据、对应代码可能只有 Agency 一侧持有；它们没有治理权威，但不是可以随意删的缓存。Agency 要有自己的持久存储，保留到收到控制面的持久确认；重连后双方按关联键幂等对账，重复收取返回同一结果。落点：`spec/system.md` §启动与恢复、`spec/participant.md`。
17. **时钟归属。**（Kimi 补。）多单元之后没有全局的"同时"。各单元的时间戳是证据，控制面的判定是权威；睡着期间的超时不以墙钟沉睡时长判定，以醒来后对账时的证据判定。落点：与恢复规则一起写。

### 丙、分责选择（各自要说理由）

2. **执行现场的归属。** 检出在参与者所在的机器上，那台机器可能没有控制面，或同时服务几个控制面。Kimi 要求写清搬什么、留什么：物化、对象库管理、现场锁与代次栅栏搬到机器一侧；挂接记录、代次的引用、对这个现场的写入授权留在控制面。Codex 补：Repo 模块仍然拥有本控制面对现场的登记与授权；同机共用对象库是允许的布局，不是必须的布局，用例自己保留了"单独 clone"的选择。落点：`spec/repo.md` §Repo 注册与 Repo Instance 挂接、§写入约束。
3. **工具箱的形态与证据分级。** 所有者定：工具箱是一组工具，在参与者内部被当作工具调用。Codex 与 Grok 在这里有分歧，我取 Codex：语义上它仍是 Repo 模块的现场执行者，这句不必推翻，改的是部署位置、派发方式、授权和证据关系，"控制面没有现场进程"才是变化。证据分级采纳 Grok 的三档：unmediated（工具持本次执行令牌，经模型写不进去的通道报到控制面，或经 Agency 原样转交）、adapter_event（适配器旁路观察到的结构化事件）、narrated（出现在模型输出里的声称）；未标注按 narrated，转述不能升级，机械事实前置与凭证回读只认 unmediated。Codex 的补充一起写：未经模型只是条件之一，控制面还要核报告的来源、本次执行、目标与版本。落点：`spec/participant.md` §证据通道、`spec/system.md` §组件、`spec/repo.md` §对象。
5. **模板的归属。** 用例里模板是 Agency 定义的。Codex 的修正采纳：分清供给与需求，Agency 拥有模板、安装与凭据条件，控制面拥有需求、选择和权限上限，不能把混了两边的 Worker Profile 原样搬家就算分完。GLM 的写法采纳：参与者模板升为核心产品词、归 Agency；Worker Profile 降为模板内部的字段组，仍冻结进 Execution Spec；模板之后的变化不能悄悄改掉控制面已接受的条件（Codex）。落点：`spec/participant.md` §对象、`participant.md`。

### 丁、推论

4. **Agency 端点排他改为按执行排他。**（第 1 条的推论，四家一致。）Grok 的改写采纳：配对不排他，同一 Agency 同时服务多个控制面；要人成功后 Agency 为该次执行签发执行令牌，与 runtime_generation 同生同灭，只有持令牌的控制面能对这次执行发输入、停止和结果准入；删掉"Agency binding owner generation"这个代次；一个控制面恢复时只作废自己签发的票据、令牌和自己存储里的 outbox，不得推进整个 Agency 端点的归属代次。落点：`spec/system.md` §单写者、§代次家族、§启动与恢复；`spec/connections.md`。
10. **随包内容系统的访问范围。** 所有者已说放开。Grok 的措辞采纳：缺省回环、非本地必须认证，不是默认对外裸绑。落点：`spec/system.md` §信任边界。
11. **一个前端连多个控制面。** 要进架构；联合视图是投影层的合并，不转移权威，每项事实与动作保留控制面来源。落点：`architecture.md` §三个面。
14. **共享对象库上的 ref 命名空间。**（GLM、Kimi 补。）同一台机器的对象库被两个控制面共用时，refs/hctl2 与变更集分支会撞名；按控制面身份加 ChangeSet 稳定 ID 隔离，事前避免。落点：`spec/repo.md` §ChangeSet 与 Git 事实。
15. **参与者机器的引导。**（GLM、Codex 补。）ubuntu 第一次给 mac_ctl 供人时，得先有 gh-jssdk 的克隆：谁下第一笔 clone、用谁的凭据、克隆归谁管；上游贡献时每台供人的机器都要能推 fork。落点：交付层。

### 戊、交付安排

12. **当前范围改分期。** "单用户、单机、单 Repo Instance"改成先单机装齐所有单元、再交付跨机连接，设计从第一天按多单元写。Codex 提醒：这是交付次序，不是从部署模型逻辑推出的唯一排期。落点：`delivery.md` §当前范围。

另有用词问题，所有者明确提出："账本"太模糊，要用精确的标的物指代。GLM 给了改法：全库规范文本一律写"控制面存储"，更细时用"治理记录"或"一致性快照"；决策史与备忘是历史记录不改；把"账本"加进 CONSTRAINTS 禁用词并给决策史、`.memo` 白名单。Kimi 补：词汇表留一行旧称对照，否则既有备忘都成了没人敢引的死文。归第二个问题处理。

## 五、看板：多源（v2）

所有者：一边用 GitHub 一边用 Linear 管看板并不罕见；缺省任务源要把选项列出来让用户选，缺省给平台自带的 issues，但必须显式同意。

- **卡的内容有一个家，家可以有很多种。** 标题、描述、讨论、板上位置住在某一个任务源里；一个仓库可以同时绑多个任务源。
- **一张任务只有一个家。** Linear 里的一条和 GitHub 里的一条对 HCTL 是两张卡；HCTL 不做源与源之间的双向同步；别的源里的相关卡只是引用。卡的身份不因为换了绑定、或两个控制面各有一份绑定就变成两张（Codex）。
- **Project 绑一个缺省源，认领可以跨源。** 从 HCTL 新建的任务落到缺省源；仓库绑定的其他源里已有的卡，Project 可以认领，认领不搬家。一个 Project 的任务分布在两个源里是认领的结果，不是 Project 绑了两个源。认领进哪个 Project 由人显式选，不沿用"外部卡必须恰在一个分组里才可认领"的旧前置（Codex）。
- **两套分组并存**（GLM）：源内分组是源原生的 milestone、Linear project、标签，只在缺省源里建；跨源归组靠控制面自己记的 Task 到 Project 关系投影，不在外源再建分组。
- **合并板是投影，不是新的权威表**（Codex）：它合并的是当前控制面或前端所知的各源，同一张外部卡可以合并显示，但关联的两份 Task、各自的验收状态与控制面来源分别展示；还没被认领的卡也要出现在板上，不能消失。
- **对象与键**（GLM）：仓库到任务源绑定 0..N，每个绑定有自己的锚点、字段权威与能力；Project 到缺省源引用恰一个；Task 到"卡的家"指针 0..1，创建时落缺省源、认领时落卡所在的源，落定后不可迁移。卡内容的单写者是它的家，HCTL 永不跨源写卡内容。`spec/task.md` 里"同一规范实体不得产生第二个 Task"的唯一键要加上源这一维。
- **跨控制面绑同一张卡的边界**（Grok、Kimi、Codex 一致）：一方完成自己的 Task 不自动完成另一方；源上的 Done 对另一方只是 Snapshot；A 的完成写回不能被 B 当成人又下了一次完成命令，B 也不能为了自己的开放状态把卡改回去；写回评论必须带控制面与 Task 标识。卡内容的并发写由任务源的条件写入仲裁，失败的一方重读后重试或报分歧。
- **认领的卡所在的源后来被解绑**（Kimi）：Task 悬空，标为需要关注，不静默。
- **缺省源须显式同意。**

## 六、雇佣与待命（v2）

所有者的原则：谁"占有、雇佣、使用"了某个参与者，只要它的生命周期没有完结，参与者就一直待命，既不新起会话，也不关闭进程后再恢复；只有闲置超时能让进程退出、会话冬眠。

- **雇佣是正式关系，与授权、席位、Room Invocation 并列，不是替代**（四家一致；GLM 的定义最清楚：雇佣是会话的持有关系，回答"下次找它时它是醒着、睡着还是在磁盘上"）。授权回答准许做什么；Room Invocation 回答这次做什么；席位是 Run 里的位置；雇佣可以跨越多次调用，但不代替它们，也不自动赋予新的席位或票权。Invocation 与席位创建雇佣，雇佣延续会话。
- **复用会话不复用授权**（Codex 的两个反例）：Project 的聊天参与者还雇着，上一轮写任务已取消，会话可以待命，旧写权限必须结束；"雇着"不自动成为新一轮施工授权，也不延长旧的写租约。参与者授权被撤销时，雇佣必须结束（Kimi）。
- **三样东西分开。** 参与者身份在控制面存储里，永久；harness 会话是 Agency 那台机器磁盘上的对话状态，有会话号；执行进程用完就没。所有者的"内存与磁盘对偶"是帮助理解的类比，不是字面规则（Codex）：进程活着、会话记录、未封存修改的寿命各不相同，只有已保全的字节才谈得上重建。
- **四个状态与转换**（Kimi 的表）。活跃：进程在，会话在内存，正在干活。待命：进程在，闲着。冬眠：进程不在，会话在磁盘，不问是主动冬眠还是被杀后靠会话文件恢复（Kimi：笔记本没电、OOM 是高频事件，必须有落点）；会话文件也丢了才按丢失处理。结束：雇佣完结，会话归档，是终态；重聘算新雇佣，可以从归档会话分叉。转换：活跃到待命，调用交付即回待命；待命到活跃，有新任务；待命到冬眠，闲置超时；冬眠到活跃，唤醒即新起进程并按会话号恢复；待命与冬眠可以直接结束，Project 结束时不强制唤醒归档（GLM、Kimi）；活跃到结束，先等交付或按撤权终止再结束；唤醒失败不能伪装成活跃（Codex）。
- **两个叠加态，不是新状态**：联系不上是观测，叠在活跃或待命上，合盖时进程可能只是被操作系统冻结，那是联系不上的活跃，不是冬眠（Grok）；完结待交是参与者封存完毕、结果在 Agency 等某个控制面收，用户要看得见（GLM）。
- **分叉。** 席位雇的那个从聊天室的会话分叉，起点带着 Project 的上下文。分叉的来源可以为空：直接进 Run 的席位、替补参与者、没有 Project 的只读研究都要能从零新起（Kimi、Codex）。来源在冬眠时先唤醒，或允许从磁盘会话分叉并记审计（Grok）。
- **分叉要可审计，只记会话号和位置不够**（Codex）：要能核对"获准继承的具体会话状态加本次增量"，继承的内容要可取回、要过范围检查，才知道模型实际收到了什么；核对不了的部分可以保留续用能力，但要记缺口，不能宣称输入已完整冻结。一个必须写死的反例：评审席位如果从已经读过作者讨论的会话分叉，转录摘要再准确也证明不了输入符合本次评审允许的范围；契约要求评审独立时，评审席位不得从作者一侧的会话分叉。
- **两个参数在模板里，机器的主人定**：闲置多久冬眠；会话长到什么程度主动整理一次。控制面记录它接受的版本与实际生效值。
- **会话不跨机器。** 冬眠的会话是文件，理论上能搬，但记着工作树路径、工具状态和那台机器的凭据；换机器只能新起，带上结晶与契约。Codex 提醒这是恢复范围的选择，不必论证成所有实现都做不到迁移。

实现层脚注：每个回合 harness 都要把整段对话重新送给模型，进程活着省的是启动时间和提示缓存的热度，不省这部分 token；真正省 token 的是续用而不是新起。Claude Code 与 Codex 都有按会话号恢复的原生入口（`docs/research/harness-adapters.md`）。

## 七、失败路径（Kimi 为主，Codex、Grok 补）

总模式见第二节的总规则。五个情形：

| 情形 | 用户看到什么 | 各方保留什么、怎么继续 |
| --- | --- | --- |
| mac 合盖，cloud_ctl 用的参与者在 mac | 该参与者标"联系不上"，最后观测时间明确；不是丢失；进行中的调用显示等待恢复；其他机器的工作照常 | 控制面记断开的事实与时间，不撤权、不终止调用；mac 一侧什么都不记，进程被 OS 挂起。开盖重连后由 Agency 回答：活着则原调用继续，零重建；死了才转丢失，走既有失权与恢复；答不知道且持续，由人裁决。判据是 Agency 的回答，不是时长 |
| cloud 断网，mac_ctl 用的参与者在 cloud | mac 的前端里 cloud 来的参与者标联系不上，本地一切正常；不能声称知道远端是在跑、待命还是已结束 | cloud 上的参与者照常干活、照常封存，结果交不了；Agency 把待交付结果存在自己的持久存储里；重连后双向按关联键补同步，重复收取返回同一结果 |
| 控制面睡着，参与者干完了 | 事后从任一前端看到"某参与者在某时刻完成了某调用，结果待某控制面收取"，不显示已验收；Agency 本机没前端也能从别处看到 | 封存不依赖控制面，准入才需要；Agency 保留结果与证据到收到控制面的持久确认；控制面醒来先与各 Agency 对账"我睡着期间你有什么等我的"；睡着期间的超时以对账证据判定，不以墙钟 |
| 两个控制面同时对同一仓库开 PR 并请求合并 | 平台上两条评审请求，分支名可辨来自哪个控制面的哪个 ChangeSet；先合入的正常进，后合入的按平台保护规则被拦或带目标前移合入；各自的 Change 场景如实显示自己那条 | 各记各的意图与凭证，跨控制面没有互斥；后合入那条按接受目标前移处理或要求重新确认；另一控制面的合法合入是外部事实，不算违规，也不自动成为自己的完成凭证。事前要求：分支名字空间不相交 |
| 两个控制面同时改同一张看板卡 | 合并板上同一张卡出现在两个 Project 的投影里；卡内容以任务源为准；治理状态各自独立，同一张卡在 mac_ctl 是"进行中"、在 cloud_ctl 是"待办"不矛盾 | 各控制面记自己的绑定与版本；卡内容的并发写由任务源仲裁，失败方重读后重试或报分歧；写回评论带控制面与 Task 标识；互不触发完成 |
