# 用例反推：单元模型与设计文档的问题

> 状态：讨论中 · Fable 与所有者三轮讨论的底稿，所有者已确认"单元模型"这个判断与十二条"基本没问题"；看板与雇佣两节按所有者 2026-09-07 的裁定写<br>
> 基线：main @ `9bbab56`（草案 v0.17.1）<br>
> 去向：见状态板；本文只反推问题，不给约束层改法

## 一、用例说了什么

三台机器。cloud 常开，装了三个 harness 和一个 Agency，Agency 上定义了四个参与者模板；mac 装了两个 harness 和一个 Agency，两个模板；ubuntu 装了两个 harness 和一个 Agency，两个模板。两个仓库，gh-jssdk 在 GitHub，gl-jstui 在 GitLab。

mac 上跑一个控制面 mac_ctl，对 gh-jssdk 开两个 Project，参与者一部分从本机 Agency 拿，检出在 mac，几个参与者共用一个对象库、各有检出；另一部分从 cloud 和 ubuntu 的 Agency 拿，检出在那两台机器上。cloud 上跑一个控制面 cloud_ctl，对 gl-jstui 和 gh-jssdk 各开一个 Project，参与者从本机、mac、ubuntu 三个 Agency 拿。cloud 建完 Project 之后没有前端。ubuntu 不跑控制面，只跑 Agency 和一个 bench，bench 同时连着两个控制面上的三个 Project。mac 上 CLI 和 bench 都连着 mac_ctl。

所有者的世界观变化：以前从 harness 会话看问题，希望 ubuntu 上的 harness 能接管 mac 上做到一半的任务；现在不这么想了。机器之间不接管会话，传的是结晶和契约。

## 二、用例的实质：单元模型

用例的实质不是"多机"，而是：HCTL2 是几种可以各自独立部署、互相多对多连接的单元，仓库是它们共同的底座。所有者对这个判断的回复是"很赞同，这就是按模块解耦"。

五种单元：

- **Agency**：一台机器上装了哪些 harness、能派出什么模板，由这台机器决定；生命周期与任何控制面无关；一台只跑 Agency 的服务器是正常形态；可以同时给多个控制面供人；模型凭据是模板打包的一部分，在 Agency 这边。
- **控制面**：只拥有治理记录，即 Project、Task、Run、参与者身份、授权、意图、凭证，存在自己的存储里；向任何 Agency 要人，向任何平台绑仓库；一个仓库同时被多个控制面开 Project 是常态。
- **前端**：CLI 和 bench 不拥有事实，可以连一个或多个控制面，本机或远程；不越过控制面去碰参与者。
- **内容系统**：聊天服务器、任务源、代码协作平台，各自独立，多个控制面可以绑同一个。随包只是缺省安装位置，不是访问范围。
- **仓库不是单元，是底座**：代码的真相在 Git 与平台上；每个参与者在它所在的机器上拿一个检出。

归属三分：会话与检出归机器，治理记录归控制面，代码归平台。一台机器可以同时是几种单元。

用例里所有安排都是这个模型的推论：Project 的参与者可以来自任何 Agency；同机参与者共用对象库；控制面没有前端照跑；瘦客户端只有 Agency 和前端；两个控制面在 GitHub 上以 PR 汇合。

## 三、所有者对追问的回答（2026-09-07）

1. **聊天室归 Project。** Project 是协作的起点，聊天室与它绑定，跟着 Project 所在的控制面走。看板另论，见第五节。
2. **会话。** "mac_tpl_sdet 基于 mac_gemini"只是说物理上有一个 gemini 会话在跑。由此引出待命原则，见第六节。
3. **推送由参与者做。** 控制面告诉参与者要推，推的动作来自参与者自己。
4. **分层各有闭包。** bench 不越过控制面去抓参与者。控制面睡着时，参与者照常干到封存，结果在 Agency 那边等，控制面醒来再收；产品要显示"这个结果在等哪个控制面"。
5. **凭据。** 模型凭据在 Agency 这边，本来就是参与者 offering 的一部分。git 凭据与 gh 登录怎么传，实现时具体看，最坏情况让持有凭据的单元中转。设计层只写：需要凭据的动作在持有凭据的单元上执行，缺省是参与者所在的机器，没有的就中转，控制面记下是哪个单元做的。

## 四、从用例反推的十二条设计问题

现有文档里一批假设写在"单用户、单机、一切都在一个进程边上"的前提下。前提拿掉之后它们要从根上重写，不是修补。按深浅排，一到五是根，六到十二是推论。所有者的回复是"基本没问题"。

1. **没有单元模型。** 三面架构讲职责分层，没讲什么可以独立装、独立活、互相怎么连。Agency、工具箱、聊天服务器、看板都写成控制面拉起、托管、随控制面一键启停的附属物。要改成对等单元，加单元之间的配对与信任。落点：`architecture.md`、`vision.md`、`spec/system.md` §组件与信任边界。
2. **执行现场的归属写反了。** Repo Instance 现在是"本系统拥有的物理执行现场"，归控制面的 Repo 模块。按用例，检出在参与者所在的机器上，那台机器可能没有控制面，或同时服务几个控制面。现场应归 Agency 所在的机器：它维护这个仓库的对象库，给任何控制面的参与者发工作树；控制面只引用它。两个控制面在同一台机器管同一个仓库，共用那台机器的对象库。落点：`spec/repo.md` §Repo 注册与 Repo Instance 挂接、`repo.md`。
3. **工具箱的形态写错了。** 文档把它写成控制面这边的现场执行者，证据等级最高的理由是"它是控制面的进程，不经过模型"。所有者定：它是一组工具，在参与者内部被当作工具调用。要保住那个理由，工具的结果必须走一条模型改不了的路回到控制面，例如工具拿着这次执行的令牌直接报给控制面，或经 Agency 转交。证据分级的标准要改成"经没经过模型的嘴"，而不是"哪个二进制读的"。落点：`spec/system.md` §组件、`spec/participant.md` §证据通道、`spec/repo.md` §对象。
4. **Agency 的归属者租约是错的。** "一个 Agency 端点同时只有一个控制面"是为了防两个控制面对同一个运行时乱发停止和输入。按用例，排他性落在每一次执行上：一个执行体同一时间只听一个控制面，Agency 本身对所有控制面开放。落点：`spec/system.md` §单写者。
5. **参与者模板的归属写在了错的一边。** Worker Profile 现在是控制面这边的可复用配置。用例里模板是 Agency 定义的，机器的主人最清楚装了什么、凭据在哪。控制面留参与者身份、Project 授权和要人时的条件。落点：`spec/participant.md` §对象、`participant.md`。
6. **发布评审假设对象在控制面手边。** 推送分支、开 PR 都由控制面的适配器做。对象在别的机器上时，推送在持有凭据的单元上发生，缺省是参与者所在的机器；开 PR、请求合并、写回结论仍归控制面的适配器。"合入的钥匙不进工具"不能再靠"机器上没有凭据"保证，只能靠平台的分支保护加控制面只认带令牌的工具报告。落点：`spec/repo.md` §发布评审、`participant.md` §关键规则。
7. **仓库身份和内容容器都假设一个控制面。** "注册确认激活唯一 Repo 身份""一个 Repo 一个 Repo Room、一个 Board"都是一个控制面之内的唯一性。多控制面之后，同一仓库的识别靠平台上的仓库身份，加 Git 根提交作旁证；往仓库里写身份文件这条路作废。Repo Room 按控制面各一个（它的定义本来就是"身份在用户级控制面"）；Board 见第五节。落点：`spec/repo.md`、`spec/project.md`、`spec/task.md`。
8. **同一仓库上多个控制面的并发没有仲裁者。** "同一目标同时至多一个待决集成意图"是一个控制面内的规则。跨控制面靠平台的分支保护和合并串行化。文档要明说平台是集成的仲裁者，控制面的规则只管自己发出的意图。落点：`spec/repo.md` §集成、`spec/system.md` §外部权威副作用。
9. **"丢失"的定义是单机的。** 远程 Agency 断连一分钟，执行体还在跑，这不是丢失，是暂时联系不上。两个方向都会发生：mac 合盖时 cloud 的 Project 失去 mac 供的参与者；cloud 断网时 mac_ctl 失去 cloud 上的参与者。要"联系不上"和"丢失"两个状态，恢复规则分开写。落点：`spec/participant.md` §运行时与观测、`spec/connections.md` §失败与恢复。
10. **随包内容系统只绑回环。** 所有者已说放开。随包的聊天服务器、任务源、平台都要能被别的机器上的控制面认证后绑定。落点：`spec/system.md` §信任边界。
11. **前端只写了"连本机或远程控制面"。** 用例要的是一个 bench 同时连多个控制面、Project 并排看。这个概念要进设计。落点：`architecture.md` §三个面、`spec/system.md`。
12. **当前范围那句话。** "单用户、单机、单 Repo Instance 下的多个 Project"要改成单元模型下的分期：先单机装齐所有单元，再跨机连接，设计从第一天按多单元写。落点：`delivery.md` §当前范围。

另有一条用词问题，所有者明确提出：文档里"账本"一词太模糊，什么是账、控制面是账还是 Git 是账说不清；要用精确的标的物指代，控制面的存储就叫控制面的存储，Git 就叫 Git，平台就叫平台。这条影响全库，归第二个问题时处理。

## 五、看板：多源

所有者：一边用 GitHub 一边用 Linear 管看板并不罕见。由此定：

- **卡的内容有一个家，家可以有很多种。** 标题、描述、讨论、板上位置住在某一个任务源里：GitHub issues、Linear、随包平台的 issues、本地任务服务器。一个仓库可以同时绑多个任务源。
- **一张任务只有一个家。** Linear 里的一条和 GitHub 里的一条对 HCTL 是两张卡；连不连是任务源之间的事，HCTL 不做两个源之间的双向同步。HCTL 的 Task 记住自己的卡在哪个源、哪个编号，别的源里的相关卡只是引用。
- **控制面留治理，不留内容。** 任务身份、验收契约、完成凭证在创建这个 Project 的控制面存储里；卡在任务源里。两个控制面各自的 Task 可以绑到同一张卡。
- **Project 绑一个缺省源，认领可以跨源。** Project 从 HCTL 里新建的任务落到它的缺省源；仓库绑定的其他源里已有的卡，Project 可以认领，认领不搬家，卡还在原处，Task 记住它在哪。所以一个 Project 的任务可能分布在两个源里，这是认领的结果，不是 Project 绑了两个源。分组实体（milestone、Linear project、标签）只在缺省源里建；来自其他源的卡在合并板上归到这个 Project，靠控制面自己知道的 Task→Project 关系投影，不在那个源里再建分组。
- **看板是投影出来的合并视图。** "一个 Repo 一个 Board"改成：一个仓库一张合并板，卡来自这个仓库绑定的各个任务源。
- **缺省源。** 所有者定：注册仓库时把选项列出来让用户选，缺省给平台自带的 issues，但用户必须显式同意，不静默生效。

## 六、雇佣与待命

所有者的原则：谁"占有、雇佣、使用"了某个参与者，只要它的生命周期没有完结，参与者就一直待命，既不新起会话（浪费 token 重读仓库），也不关闭进程后再恢复（浪费时间）；只有闲置超时能让进程退出、会话冬眠，像操作系统的冬眠，内存进硬盘，下次再装回来。会话与进程是一组对偶（内存、磁盘）。

由此要进设计的东西：

- **雇佣是正式关系。** 现在文档只有 Project 对参与者的授权和 Run 的席位，没有"雇着"这个持续状态。雇佣有两种来源：Project 的聊天室雇一个参与者，直到 Project 结束；Run 的席位雇一个，直到席位交付。席位雇的那个从聊天室那份会话分叉出来，起点带着 Project 的上下文，之后各走各的。
- **四个状态。** 活跃：进程在，会话在内存。待命：进程在，闲着。冬眠：进程退出，会话在磁盘。结束：雇佣关系完结，会话归档。闲置超时只从待命走到冬眠；下次使用唤醒。
- **两个参数在模板里，机器的主人定。** 闲置多久冬眠；会话长到什么程度主动整理一次。
- **会话不跨机器。** 冬眠的会话是文件，理论上能搬，但里面记着工作树路径、工具状态和那台机器的凭据，搬过去多半是坏的；换机器只能新起，带上结晶与契约。与世界观一致，不留后门。
- **分叉要可审计。** 冻结的输入多一项：从哪条会话、在哪个位置分出来的，位置用转录摘要钉住；开工包变成增量材料。
- **三样东西分开。** 参与者身份在控制面存储里，永久；harness 会话是 Agency 那台机器磁盘上的对话状态，有会话号；执行进程用完就没。常驻的是会话，不是进程。

实现层脚注：每个回合 harness 都要把整段对话重新送给模型，进程活着省的是启动时间和提示缓存的热度，不省这部分 token；真正省 token 的是续用而不是新起。会话越用越长，每回合开销随之涨，harness 会压缩上下文。Claude Code 与 Codex 都有按会话号恢复的原生入口（`docs/research/harness-adapters.md`）。

## 七、待四家审的问题

1. 单元模型：五种单元够不够、有没有多余；内容系统算不算单元；归属三分有没有反例。
2. 十二条里根与推论的划分对不对；有没有漏掉的根问题。
3. 看板多源模型：一张任务一个家、Project 缺省源加认领、合并板投影、缺省须显式同意。
4. 雇佣关系与现有授权、席位、Room Invocation 的关系；四个状态是否闭合；分叉的审计要求够不够。
5. 失败路径：笔记本合盖、Agency 断连、控制面睡着、两个控制面同时对同一仓库开 PR、多源看板并发写，每条用户看到什么、系统记什么。
6. 用词：账本改精确标的；执行面与展示面；模板与 Worker Profile。
