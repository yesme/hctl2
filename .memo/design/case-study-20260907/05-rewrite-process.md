## 一、要做的事和节奏

从用例裁定出发，把设计文档按单元模型改写，基线升到 v0.18.0。所有者的话是：设计阶段"有节奏地做正确的事"远好于"大干快上反复改"；设计没有单元测试过不过，只有考虑是否周全、是否过于繁琐、有没有重复造轮子、层数是否太多，尤其是每个设计都有利弊、怎么权衡；权衡要讨论和探索。所以：

- 一次只走一批，批内不并行，批间不并行。上一批合入之前，下一批只能做讨论。
- 每批两步：先讨论，后动手。讨论阶段的产物是方案，写候选与权衡；所有者逐条拍板之后才改文档。
- 只追正确，不追速度。

## 四、方案的形状

讨论阶段的方案写六样东西，少一样退回来补：

1. 这一批要改哪些句子，各来自哪条不变量或哪条用例事实。
2. 每处有哪几种改法。
3. 各自的好处坏处，代价谁在什么时候付。
4. 作者推荐哪种，为什么。
5. 哪些是已经拍过板、本批不重开的，列出来，免得评审重开——每条引用裁决记录的条目（`21-r2-rulings.md` 的某节、本文 §二 的某行、或所有者的拍板评论）；作者自己推出来的结论单独标「推论」，不与裁决混写（参与者对照表那一行被两份报告当成裁决引用的教训）。
6. 落点：改到哪份文件哪一节。

周全的尺子是参考用例：每批方案要拿用例 S1 走一遍，这一批改完之后，用例的每一步和五条失败路径还成不成立。

## 五、七问：评审的方法

一条设计文本值不值得进正文，问七件事。每一问对应这几周真踩过的一个坑，所以是七个而不是别的数：

| 问 | 问法 | 不过的样子 | 踩过的坑 |
| --- | --- | --- | --- |
| 对 | 它满足参考用例的不变量吗 | 用例的某一步在这条文本下走不通 | 用例的必然情形要补写七条 |
| 全 | 正常路径之外，失败、恢复、生命周期的开头和结尾都写了吗 | 只写了顺路，失联、睡着、返工没着落 | "失联时本地目标集成继续"漏了五处 |
| 分 | 每个概念是不是恰好有一个能对它负责的主人 | 塞：两个主人的东西合成一个概念。冗：同一件事两个概念，或数进不该数的东西 | Worker Profile 把机器装了什么和雇主允许什么塞在一起；Repo Instance 同时指控制面的记录和机器上的现场；把仓库数成第五种单元 |
| 借 | 业界和仓库里已有的机制先用了吗 | 自造一个别人已经解决的东西 | Gogs 与 Gitea、UPX、Git 有没有比较并交换 |
| 衡 | 别的做法列了吗，各自代价谁付、什么时候付 | 只有一个方案，或代价写成"顺带有了" | 旁路 ref 还是独立材料仓库；"备份顺带有了" |
| 层 | 这句话是在愿景、架构、约束、交付还是实现哪一层说的，实现细节有没有漏进架构 | 架构层出现绝对的部署句；约束层出现"为什么更好" | "控制面没有现场进程"写成了绝对句 |
| 验 | 每条约束能不能被观察和测试 | 写成对模型的叮嘱，配不出失败用例 | 契约测试逐条配失败用例这条纪律本身 |

"分"是所有者纠正过的一问：Worker Profile 的毛病不是不够简，是太想简，把不该合的合了。所以不问"简不简"，问"分得对不对"，判据是责任；层数太多归它，多一层间接就多一个没有主人的中间物。

评审的产出形状固定：每家先按七问对整批表态，再逐条给维持、修正、推翻，撤回自己上一轮说错的要写明。

## 六、审在哪一阶段

重的审放在讨论阶段：七问由主审、副审、陪审在方案上答，权衡在这里做完。文档 PR 的审只查三样：改出来的文字是否忠于拍板的方案；每句话的层对不对；约束改了配没配契约测试用例。所以方案阶段可以走独立加交叉两轮，文档 PR 一轮就够。

方案拍板前加一步**读回**（照 `run.md` §施工图怎么凝结 的做法自食其力）：一个不在本批席位上的 harness 只拿方案文件与参考用例 S1，不给评审评论与讨论原文，从零把每处改法复述成人话、走一遍 S1 的每一步与失败路径、单列自己不确定和猜的地方；它不投票不裁决，人看了觉得走样就退回作者。退回后只改措辞、不改任何改法或落点的，不再读回；改了改法、落点或待裁项的，由同一读回席位再读一次；最多两次，第二次仍走样的列为待裁项交所有者。

施工图与任务书里每个席位的提示词要写成成品——按批、节点、席位填好，PR 用分支名定位，不留字段让所有者填：所有者以引擎身份推进时只贴不填（所有者 2026-09-12）。

合入阶段两条纪律（#216 F2 的教训：四处叠词在 #211 评审时已被抓全，坏在合并时的机械换词与作者失实的处置说明）：

- 分支早于某个全库换词批的，并入时冲突处置按该批的判别顺序逐句重判，不按替换处理；PR 描述里的"已修回"先用 `git log -S` 核过再写。
- 每批动手 PR 合入后，由一个非作者做一次合并后核对：只用四种情况的清单（已经改对后来又改坏 / 新规则与保留的旧规则不一致 / 已排后续批次尚未实施 / 所有者有意改变），对着本批改动的文件和本文 §二 的表核；轻量，一家一轮，不是再来一次六家复核。

## 七、拍板与分歧

所有者裁的是方案里的每一处改法，不是整份方案一个"同意"。裁决以所有者在对应 PR 上贴的、标题以「裁决 ·」开头的评论为准，这是推进引擎的信号；写进裁决记录的也要在 PR 上贴一条这样的评论指向它。评审之间的分歧由作者按论证质量先合，写成作者说明；合不拢的列成待裁项给所有者。已经拍过板的不重开，重开要说清新证据。
