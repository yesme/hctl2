## 二、逐处改法与推荐

### C1 仓库身份：本控制面登记，不向代码树写身份

**已定边界**见 §五 D2、D3。以下是「仓库稳定身份：本控制面内怎么认」的**待裁推论**，不是删身份文件自动推出的答案。旧长聊已回答什么、还没回答什么见 §五对照表；本稿不把未决部分自行解冻。

- **甲：本控制面内按平台稳定仓库身份匹配。** 平台身份包含平台服务实例及其稳定仓库标识，不拿 URL、remote 名、凭据身份、绑定修订号或根提交充当仓库身份；无平台时由人的显式登记/选定维持本地 Repo 引用，Git 根提交只作提示。好处是 gh-jssdk 可以在两个控制面分别登记，而同一控制面不会仅因 URL 改名重复建 Repo；代价是无平台、空仓库与身份迁移不能全自动判断，人在登记时付确认成本。
- **乙：全部靠人把每个入口映射到已有 Repo，平台身份只作旁证。** 不需要推断，但同一平台仓库重复登记更容易，日常使用一直付人工成本。

**推荐甲，P.7 须单列裁定其范围与规则，未裁定不实施匹配规则。甲若获准：** Repo 的稳定身份只在所属控制面内唯一；平台仓库用绑定范围内的平台稳定身份匹配，克隆不是 Repo 身份。没有平台身份时，登记记录人的选择及可取得的 Git 根提交旁证；共享根提交不证明是同一仓库，空仓库无根提交不妨碍显式登记。证据不足时预览列出候选或新建选择，不自动并身份。新增或替换平台绑定沿既有显式预览、版本与活动意图冻结规则；平台迁移后的跨身份认同仍留冻结讨论，不在本批自动处理。

现有「先建待注册记录—外部步骤—确认激活 Repo 与 Repo Room」的恢复边界保留；删除写 `repo.toml` 身份与挂接前置。只在本地的仓库仍缺省建本地平台仓库，但初始 Git 交付按 C5 由持凭据单元执行；给检出配置 remote 是参与者一侧的便利操作，不是登记生效条件。

注册时的推送范围与残留清理边界保留：空仓库只建仓，默认源分支及其他 ref 的显式选择不变，不强制覆盖平台已有分支，放弃注册不自动删已建平台仓库。旧句对 `refs/hctl2` 的排除按「私有保管引用」的用途表达，不把格式定死；未准入的变更分支与未经显式发布的治理材料不随初次建仓推送。

### C2 工作副本：不换名重建 Repo Instance

**已定边界**见 D3。两个合法落法是：

- **甲：共享分责条件在 system 写一次，Repo 只定义 ChangeSet 写权与交付要求，派工与恢复引用。** 好处是供应端可选共享对象库或独立 clone；坏处是读者须区分对资源的保证与供应端采用的机制。文档作者付交叉引用成本，供应端在执行前付隔离与冲突检测成本。
- **乙：把工作副本分责全部放 Repo，system 只留链接。** 模块文档更自足，但系统里的启动与单写者容易只剩一次跳转，跨模块读者需要往返。

**推荐甲。拟改义：** 参与者负责工作环境与工作副本；控制面只记录任务、授权、接受的版本与获准目标更新。删除 Repo Instance 对象、生命周期、挂接命令和通用现场字段，不用另一组全局必填引用代替。

ChangeSet 与 Write Lease 保留：需要独占或相互冲突的写入须互斥；旧写者停止，或被限制在旧工作树与旧 ChangeSet 内，才按原规则授予相应新写权。拒收旧结果不证明旧进程已经失去文件写权，资源管理方须落实隔离。共用对象库的独立工作树不整体串行。

独立写入者维护的引用在写入前保证不相交；本地引用和发布到共同平台的源分支都在此列。由管理这些引用的一方分配、核验冲突，不规定 `refs/hctl2/...` 等唯一格式，也不要求控制面保存所有临时分支。共同更新 main 不是独立引用撞名，按 C3、C4 的目标并发条件处理。

### C3 必要引用与恢复：成果认版本，目标更新认目标

**已定边界**见 D3。落法可选甲「按操作列条件表」，或乙「在所有信封列一组全字段，逐字段写适用条件」。乙方便生成类型，但容易把生产目录重新变成全部执行的必填项，由每家供应端为无用字段付适配成本。**推荐甲**，类型布局留实现。

| 操作 | 拟保留的信息与条件 |
| --- | --- |
| 派工 | 任务、基线、权限、预算与既有执行归属；工作副本由参与者安排，搬生产目录不自动改授权。执行体身份和运行时代次仍保留，不把删现场对象解释成删精确执行身份 |
| 封存与交付 | 精确成果、基线、生产者来源、租约（适用时）和可核验证据；来源可为执行或人的显式命令。现场工具可以接收本地路径，但跨单元契约不要求公开生产目录 |
| 更新平台目标 | 冻结平台绑定及目标 ref，沿用两种集成授权形态、源头核对与目标保护快照 |
| 更新无平台本地目标 | 冻结供应端提供的目标引用与 ref；这只属于本次目标更新，不产生通用现场对象。供应端须能解析到获准目标并验证连续性，不能以同名分支或同一路径冒充 |
| 恢复待决更新 | 尚未写且解析不到或目标不匹配，拒绝本次写入；可能已写而确认不足，保留原意图、原目标与冲突范围，记结果未知，回读后才作终局判定 |

本地目标仍只对显式不挂平台的 Repo 开放；平台离线不改道。供应端能证明目标连续时允许迁移其存放位置，反之同路径新 clone 也不是原目标。原本地集成的快进/合并提交、比较并交换、当前检出目标拒绝、幂等和结果未知规则不变。

从激活元组、结果信封、终端动作、Run 替代限制与代次家族中去掉通用 site generation。只删除这一依赖，不删控制面写者、执行归属者、运行时或引擎代次；Agency 端点代次的撤销归 B。Run 替代仍不得伤及其他获准执行，但不再用一个已删除的共享现场代次来表述。

**恢复对照**沿 07 §四，不新造恢复对象：

| 情形 | 控制面核什么 | 供应端答什么 |
| --- | --- | --- |
| 控制面重启、供应端正常 | 原授权、执行与待决动作；只使自己的过期动作失权 | 对应执行、结果和动作的观测；不要求停掉另一控制面的执行 |
| 供应端重启或不可达 | 原身份能否核实、原授权是否仍有效；不能凭失联断言丢失 | 可核实的身份与结果；工作区由自己恢复，网络失败不触发控制面重建目录 |
| 执行结束、结果待交，控制面恢复旧备份 | 原授权与既有处理结果是否有依据；缺依据走显式恢复 | 交精确结果和证据；原进程和临时工作树不必仍存在 |
| 集成可能已写但响应丢失；人的封存尚未准入 | 前者核原意图、原目标；后者核人的原命令与候选 | 分别交更新证据或封存字节，不凭 Git 存在补出授权 |
| 换机器或同路径重建 clone | 普通生产位置变化与待决目标连续性分别判 | 对涉及的目标证明连续性；不是上报全套目录状态 |

### C4 平台共同事实与本控制面验收

**已定部分**见 D2、D4，分两条落：

1. 待决集成互斥限定在本控制面与同一目标；跨控制面由平台按原生保护与并发规则仲裁。目标范围包含平台/供应端目标与 ref，不拿单独的 `main` 字符串当全局互斥键。
2. 各控制面观察共同目标、检查与评审事实，重核自己的待决意图及后续动作；别人的合法合并不是不支持的修改。只有它使本控制面某条冻结前置不成立时，才拒绝或停止依赖那条前置的动作。

两种授权形态不改：预期目标头形态遇头变动按原条件拒绝；接受目标前移形态仍按源版本、合并方式和冻结保护判定，不能见头动了就一律判分歧。没有自己匹配的意图，不伪造自己的 Integration Receipt。

**未决部分，推论：另一控制面的合并怎样用于本 Task 的机械验收？** 这会改 `spec/task.md` §写入约束的证据来源，不只是 Repo 内部选择；与前两条已定条件分开裁。

- **甲：仍只接受本控制面的 Integration Receipt。** 最窄，现有验收入口几乎不动；但已被别人合入的成果可能要求人改契约或再走一次自身集成授权，人在共享平台场景付重复治理成本。
- **乙：验收项可事先明确接受「指定平台目标已合入精确代码版本」的外部事实。** 本控制面的 Repo 模块核回 Repo、目标、版本对应关系与平台结果，按现有 Evidence 交 Task；Task 仍核当前契约、证据等级和其余验收项，并经原完成命令签自己的完成凭证。省掉重复合入，但适配器须能证明平台记录与所需版本的关系，Task 的验收文字也要写清是哪种要求。
- **丙：接纳另一个控制面的 Integration Receipt 当自己的。** 省核对，但读到他人的批准不等于本控制面作过授权，与 A 的权威关系冲突，不推荐且不作为已决方向的重开。

**推荐乙，待所有者拍板。** 只有获准后才增加第三条：契约事先明确接受平台精确合入事实时，由本控制面的 Repo 回读并提供 Evidence，Task 不直接读平台；仍须本控制面的完成命令与其余验收条件。契约明确要求「本控制面授权集成/集成凭证」时仍只能用自己的凭证；不得把新允许的证据偷换进既有契约。只有合并标签、提交自述，或无法对应精确版本的记录不够；squash/rebase 也不能仅靠原提交是否为目标祖先判断。别人合并不自动完成自己的 Task，不改变 Gate/human 判定等级，也不改变 D 要讨论的共享任务卡写入权。

### C5 发布评审：一个授权过程，两段外部动作

**已定方向**见 D4、D5。执行者随凭据位置变，命令提交者不变：人的预先授权由控制面按准入结果发出发布命令，Result Proposal 仍只是内容提案。

- **甲：保留一条发布意图，记录 Git 交付、创建/更新评审请求各自的执行与回读结果。** 不增加用户操作；既有命令、幂等、outbox 可承接。代价在实现者：不能把第一段成功误报成整个发布成功。
- **乙：拆成两条独立的用户命令，各自预览提交。** 故障归属直观，但人每次多确认，且还需关联版本与两条命令；旧「发布评审」体验会改变。

**推荐甲（具体分段为推论）。** 发布策略继续冻结 Repo、平台绑定版本、源分支/评审请求范围、创建或更新权限、描述来源及显式确认开关，并带 C6 的审计公开范围。版本准入之后，持久意图先要求持 Git 凭据的单元交付该精确版本，再要求持平台权限的单元创建或更新请求，最后回读对应关系。缺省前者在参与者一侧、后者在控制面；控制面有 Git 凭据也可推送，其他获准中转同样成立。没有可用路径时不假报已发布。

各段使用原意图关联与稳定幂等依据。推送成功而建请求失败，只重试未确认段；请求可能已创建但响应丢失，先按原版本、源和目标核回，不另建请求。旧版本迟到不得覆盖新版本映射；可能已写而无法核实保持结果未知，不换分支或换平台重试。

推送权限只覆盖获准发布源，不因此拥有更新集成目标的权限；模型不接收通用 human/control 凭据。HCTL 持凭据工具在参与者机器执行动作，与模型持有秘密是两件事。C 只改掉「远端推送一律由控制面平台适配器做」「执行侧绝不推送」的绝对句；B 再统一权限分层与报告通道，报告认证本身不证明写权受限。

### C6 审计关联：发布可见的关联，不分发整份私有治理

**已定方向**见 D6；下列最小发布内容和失败处理为**推论**。

- **甲：在原发布/写回策略里冻结最小关联；需全文或离线审计时再显式发布。** 默认不泄露私有材料；外部读者能认出是哪次决定。代价是没有权限或控制面离线时只能看到关联和允许公开的结论，不一定取得全文。
- **乙：每次发布都附一份完整、去敏的离线审计包。** 审阅者不依赖控制面在线；代价由人和控制面在每次发布付去敏、复制与长期分发成本，某些私有任务不能采用。

**推荐甲。拟改义：** 平台记录按冻结公开范围带产生决定的控制面来源、精确被评版本、裁决/凭证引用与摘要、允许公开的结论及可用的取回位置；位置不承诺公开可读，读不到如实标明。字段沿现有引用与策略承载，不造审计服务。

合入前发布的是「允许合入」的裁决关联；回读确认后才可补「已经合入」的 Integration Receipt 关联，两者不混用。写回失败用既有 outbox 保留并重试，不撤销已确认的集成；是否阻塞 Task 完成取决于它是否为冻结的必需交付项，不能临时加门。更新同一评审请求时保留旧版关联的版本归属，不把它显示成新版批准。

显式不挂平台时没有评审请求，控制面与材料库保留对应记录；仅拿代码 clone 的人不保证能发现私有裁决，若有离线审计需求由人显式发布索引或正文。被治理仓库是私有的也不等于所有控制面的私有材料可以互相公开。

### C7 控制面存储：记录与正文两半

**已定方向**见 D6、D7。落法甲是在 `spec/system.md` §控制面自己的存储定义两半，再在 §Git 的双重角色区分代码 Git 与材料 Git；乙是在各模块逐一规定存放并由 system 汇总。乙模块内易读，但搬家需反复修改多份定义、承担漂移成本。**推荐甲**，模块只写自己的版本、摘要与准入条件。

**拟改义：** 每个控制面保管自己的治理记录与不可变治理正文，同一逻辑写者协调两者。治理记录保有身份、授权、准入、当前指向、版本关系、命令幂等结果与待投递动作；正文承载契约、施工图、Memo、策略与 schema 的不可变字节。材料存储是控制面存储的一部分，不是另一个 Repo、Project、Room 或内容服务。

代码对象与 ChangeSet Revision 的 Git 快照仍在被治理仓库；Task/Workflow/Memo 等 HCTL 治理正文缺省在材料仓库。**Artifact 的落法是推论：** 精确正文来源按实际登记区分材料与代码文件，不强迫全部搬家；理由是 03 §二要求按用途分，而 §九未逐项指定 Artifact 去向，不把这个补充冒充原裁决。Verdict/Receipt 的裁决权仍在治理记录，材料库可保存其审计副本。Git 里的候选、派生索引或 current 副本不决定准入或当前有效版本。

取消系统缺省写入的 Git 跟踪目录 `<repo>/.hctl2/`。人显式发布的项目文档、AGENTS、工具配置照旧，不以「取消默认」为由删已有产品文件；私有治理材料未经显式发布不推到共享代码分支或 ref。实现自己的工作缓存由它管理，但未交付的孤本不是可随意删除的缓存。

**已选实现的落点是 delivery，不是架构定律：** 现有结构化存储保管记录；一个控制面一份私有本地裸 Git 材料库，随包本地平台在时缺省镜像，可选其他镜像或不镜像；平台不是本地保存与已承诺交付的运行前置。旁路 ref 只为读者范围和写入权限都适合的仓库显式开启，ref 名称不提供读隔离。本批不做第二个存储后端。

### C8 存取和定位：保留四个动作，不另加版本系统

**已定方向**见 D7。甲是系统约束用动作结果定义存入/取回/列版本/交付，领域版本关系仍在各模块；乙是把方法签名和 Git 布局一并钉死。乙实现初期少一次设计，但后端迁址会变成契约变更，由适配器和使用者长期付代价。**推荐甲**。

- **存入**：确认的是字节及可恢复定位已持久保管，不是批准业务版本；相同字节可去重。
- **取回**：取指定字节并校验；缺失、不可达、无权限、摘要不符分别返回。
- **列版本**：由治理记录回答已准入版本、次序与当前版本；正文后端不拿 Git log 代替领域顺序，候选不冒充已准入。
- **交付**：按已获准材料集合、接收者与用途取回、发送、接收核验；本地读取成功不等于远端收到。

定位信息仍由现有引用与 Manifest 承载：稳定控制面/材料范围及不可变内容标识；所承诺字节的内容摘要；所属对象、精确 Revision 与版本关系。范围可由已有连接隐含，摘要不自带地址或读权限。原文字节摘要、规范化 Revision 摘要、评审对象摘要继续分开，后端地址变化不改变冻结引用；相同字节不合并领域身份。

不新增公开的回收 API，不在约束里规定引用格式、文件目录或摘要寻址布局。共享摘要算法沿现有约束；本批不另钉密码算法或存储库版本。

### C9 保存到准入：复用命令事务与 outbox

**已定顺序**见 D7，不重新选择「Git 记录权威」或跨库事务。两个落法：甲在 system 定义材料的保存—准入—后续投递，再由 Task/Run/Project 引用；乙复用 Repo 的代码封存命令承载全部正文。乙能少一个内部调用边界，却让每份 Memo、契约都依赖被治理仓库与代码写租约，违背材料库不是 Repo 的分责；**推荐甲**。

**拟改义：**

1. 在适用写权下保存精确字节与可恢复定位；保存到准入判定完成之间受保护，不因还没有已准入记录就被回收。
2. 领域准入事务重新核权限、预期版本与适用代次，一起提交准入、定位与摘要、领域版本、当前指向（适用时）、幂等结果和必要 outbox。只保存过字节不能跳过这一步。
3. 交付、镜像按持久投递记录重试、回读。镜像待同步不阻止本地保存与准入，不能把「写穿」解释成远端成功才返回。

同一命令重投返回同一领域结果；内容去重不代替命令去重。Git 的引用事务不是记录库与 Git 的共同事务。代码 ChangeSet 的封存、Repo 版本准入仍按原模块交接走，不让材料后端去集成代码。

Task 创建携初始契约时保留后端 outbox、关联键与恢复条件，只把原「Git 正文 outbox 经 Repo 工具」改为控制面内部材料保存与 Task 准入；卡片创建不因此与正文假装原子完成。Workflow 与三张清单附属正文同样改保存方，不改变 R 批的来源、登记、读回、批准与摘要一致性条件。

R 的三处核对仍逐项比较原规则的 Workflow Revision 摘要与清单快照摘要，不改成材料 locator、后端地址或 Git 对象编号，也不一概改名为原文字节的「内容摘要」。完整 Bundle 摘要与计票用交付内容摘要继续各管各的；C8 的存取校验不替换任何一项。

### C10 保留、回收与备份：按承诺，不能只看当前版

**已定边界**见 D3、D7。C 在 system 定控制面材料的保留、回收与一致备份；输入副本沿现有 Bundle 窗口，不缩短、不重写。成果留到接收方确认保全是 07 §三、§四已经交给 C 的交付条件，不是输入 Bundle 的期限；Agency 内部怎样持久保存、失联后怎样核回执行身份由 B 落，不在 C 设计其存储机制。

备份落法可选甲「已有备份集扩到同一记录快照所需正文与定位」，或乙「记录和材料各自备份，恢复时尝试凑齐」。乙日常负担较小，但只能在恢复时发现缺件，不能声称一致备份；用户在事故时付不可预测成本。**推荐甲**，备份操作自己付完成前核齐的时间与空间成本。

| 窗口 | 拟定可观察结果 |
| --- | --- |
| 字节已保存、准入尚未提交时崩溃 | 保留候选；恢复原命令并重核前置，不凭 Git 存在补出批准 |
| 准入已提交、响应或镜像确认丢失 | 命令重试返回原结果；不造新 Revision，不重复推进 current |
| 记录在，字节或定位关系丢了 | 只从精确副本恢复并核摘要；不能改指最新版。缺项明示，依赖操作阻塞，原决定不抹掉 |
| 保存与准入之间发生回收 | 候选仍受保护；保管范围还包括待交付、备份正在读、承诺保留的历史，不只当前版 |

写者搬迁/失权同时覆盖记录库和材料库；只有一个逻辑写者不要求 Git 子进程与控制面同一个进程。备份验证同一记录快照、仍承诺保留的精确正文、定位关系和所需定义；材料可以多出候选，不能缺被承诺的内容。镜像中的候选仍受公开范围约束；本地平台的数据亦进备份安排，不只复制 Git 而遗漏平台自己的事实。

Git 分布式副本能恢复字节，不能恢复从未备份的授权与准入；审计副本只能进入显式恢复。源正文按已接受的保留策略结束保管后可按记录丢弃；执行侧 Bundle 沿 `spec/project.md` §根 Context Manifest，至少保留到归属者终态且 Result Proposal 准入窗口关闭，之后保留原规则的引用、摘要、来源、策略与丢弃事实，不声称还能重放。成果按 07 的交付条件留到接收方确认具体交付项已保全，只收摘要不算；删除临时工作树不妨碍交付仍保管着的精确成果。§六把恢复旧句逐句分开，§八明确 C/B 各自的验收责任。

### C11 Context：有可读副本才算指针交付

**已定方向**见 D6、D7、D8。甲是在三种交付方式里区分「治理记录库」与「已交付的正文副本」；乙仍禁所有控制面存储指针、把副本要求散写到每个调用入口。乙字面整齐却把材料库也误禁，各入口需反复解释例外；**推荐甲**，统一交付规则，消费者只引用。

**拟改义：** pointer 只能指向执行体在获准范围内能自行打开且核验为精确内容的 Git 对象、工作副本或已交付的只读材料路径。执行体不直接读治理记录库；在线向控制面解析的定位符本身不算离线可重读副本。控制面材料库里的来源定位、执行侧读副本的位置是两种关系，二者保留可核验关联，不混写。

必用材料与承诺离线查阅的材料在执行前实际送达并核验，可在执行环境反复读取；开工时塞进 prompt 但压缩后无处重读，不满足后一承诺。Bundle 带精确来源与摘要，实际交付摘要经核对后才派工。派工只交获准副本，不因一次交付自动开放整库读权（按 03 §十 3 限定用途的**推论**）；参与者不持材料库凭据是 03 §二已定的主路径，不重列为新取舍。源正文与执行侧副本分别按 C10 保管。

必用且放得下仍内联，超预算仍用精确指针加分片建议；其余未承诺离线的补充材料可按既有 recall 策略代取。控制面离线时已交付副本可读，新的代取不可达如实报缺口。聊天、任务评论、平台评审评论仍走原内联/代取规则，不因增加只读材料路径就获得直读后端的权限。

返工裁决原文必用；按治理记录取其精确正文，获准副本用于交付，公开审计只剩摘要时不能拿摘要顶替。每个消费者冻结自己的完整 Bundle；共享 Task/Workflow 版本与条目摘要不等于各席完整包摘要相同。R 批的「交付内容摘要」排除字段与计票算法不动，备用 Attempt 同包规则不动。

### C12 F4 与投影：按实际位置说，不另订三类数据

**已定范围**见 D8、D9。甲是把存储与交付条件收在 system/project，其他文件改成产品语言与链接；乙在每份正文重写一段两半存储。乙单页更自足但多份重复权威，后续每次修改都由作者与评审重复付成本；**推荐甲**。

同批改齐：架构矩阵 Change metadata 去现场记录；审计副本不是默认随代码 clone 分发；任务契约与完成凭证分别说明正文来源和裁决权；Workflow 登记、凭证副本及返工交付引用新来源；Context 的 Memo/Artifact 指针与返工条改为已交付的精确副本，保留内联超预算例外。三类数据与结晶按产出场景归属的规则不变，Artifact 与数据类别 artifact 不混叫。

`architecture.md` §数据丢了怎么办里「每个 clone 与 remote 都是备份」也按所持精确对象与材料仓库区分，代码 clone 不宣称自带治理正文。§模块交接中「Git 保存」细化为代码封存与材料保存各有主体；若 C4 乙获准，Repo → Task 的产品描述同步涵盖契约明确允许的平台事实证据。

## 三、代价与批次切法

仍推荐一个 C 动手 PR（**推论，待裁**），不在本方案 PR 预先改版本表。既要比较中间版本是否自洽，也要计入评审负担：

| 切法 | 好处 | 代价由谁承担 |
| --- | --- | --- |
| 甲，一个 W 子图，v0.18.1 | Repo 身份、代码交付、材料存储、Context 与镜像句一起自洽；轻审可沿同一个 S1 追到底 | 作者和评审一次读完整跨模块变动；漏改风险由整个基线承担，§六、§八的追踪不能代替通读 |
| 乙，先材料存储、后 Repo 集成，各一个 W 子图 | 每次讨论焦点较窄，可先交 P2.1 的部分存储输入 | system/connections/Task 连续改两次；第一批不能宣称 F4 和交付链全部完成，引用与进度需要再次核对；B/D 版本顺延，所有者与两轮轻审付维护成本 |

采纳 Fable 对甲的漏改风险判断，但不采用「C7–C12 在前、C1–C6 在后」的原样切法：C7 取消默认跟踪目录涉及 C1 的注册身份文件；C12 的 Change 现场记录要靠 C2/C3 退出，审计分发要靠 C6 的发布条件。这不是只将一张表分半。乙仍可选，但须把这些连带句移入第一份或逐句保留尚未迁移的条件，重新确定两份各自能验收的范围；不能宣称前半已完成全部 F4。相较这样的重复迁移，当前仍推荐甲；这个取舍不以 Grok/K3 支持甲的人数作依据。

若所有者选乙，按 08 §四 的拆分规则在 P.7 明确两份落点、版本与依赖后再动手，不由作者临场拆，也不让 P2.1 因材料一半合入就自动开工。

用户的持续成本不是零：控制面多保管一份材料库和一致备份；执行侧在确认保全之前占用磁盘；默认审计关联不承诺所有人离线读全文；无平台身份认同仍需人确认。换来的是不要求上游收 HCTL 内部文件、不要求远端暴露目录，也不靠复制控制面治理权威实现协作。

## 四、借用现成机制与分层

本批不选新依赖。沿 [Gitea 调研](../../../docs/research/gitea.md)分三处引用：§运行形态支撑当前随包平台进程由 control 托管、适配器持平台令牌的部署选择；§不采用与边界支撑不为外部代码仓库建镜像；§调用面核对与§决定建议支撑 tea/API 能力。前一项不是单元必须同机或 Git 推送只能在控制面的架构限制，「HTTP 推送」也只说协议。材料镜像的选择来自 03 §八，研究只供既有平台能力依据。Git 沿 [Git 客户端研究](../../../docs/research/sdk/git.md)；旧责任分配不覆盖 C5 的持凭据交付原则。

**实现层脚注：** 可复用宿主 Git 的对象、引用条件更新、fetch/push 与可达性保护；既有结构化存储事务、outbox、幂等与备份入口继续用。Git 引用事务不是 Git 与记录库的事务，Git 回收也不会自行读取记录库的引用；保护性引用和刷盘配置由后续实现验证，不自建版本库、分布式事务或对象回收器。材料库的目录/摘要寻址布局、方法签名和内部锁不在本批逐项钉死。

架构正文只投影「工作副本由参与者管，治理正文由控制面管，按权限实际交付」。system 定存储与共享条件，Repo 定代码与平台命令，Project 定 Context，Task/Run 保有各自版本与准入；delivery 才写当前 Git/SQLite、本地裸库、可选平台镜像和运维依赖。只跑控制面、没有本机 Agency 或 `hctl2-tool` 的机器也需要正文后端所用的 Git，这项交付前置随 C 登记，不能说原工具依赖会自动带到那台机器。

| CT-TASK：两处「要求集成时只认 Repo 凭证」 | C4 乙获准才改两处：契约要求本控制面授权的仍只认其凭证；预先允许的平台精确事实经本控制面 Repo 出证据；观察到 merged 本身仍不完成 Task |
| CT-REPO / CT-CONNECTION / CT-SYSTEM：注册推送和远端副作用只由平台适配器执行，席位不能推送 | 发布源由持凭据单元在原意图授权范围内交付，不能凭此更新集成目标；注册空仓、初次推送范围、结果未知与残留处理保留；人命令来源与内容准入仍按旧边界 |
| CT-SYSTEM：多个现场登记后按现场代次隔离；clone 运行目录全可删而不丢事实 | 改测操作所需的失权/隔离证明；不要求统一现场对象，未确认保全的唯一成果不当可丢缓存；控制面 writer 排他与代次仍测，Agency 端点规则留 B |
| CT-SYSTEM：控制面一致备份与 restore、writer 重置及 content 回读 | 按 C10 扩正文与定位的核齐反例；留控制面写者、精确定义与各 content 服务恢复，删除 site 前置，不提前改 Agency binding owner 的语义 |

**恢复表到验收的对应**（K3 第 13 项）。07 要求 C 核对五种情形，不等于 C 提前完成 B 的端点与失联规则：

| C3 恢复情形 | C 本次的检查 | 留给 B 的检查 |
| --- | --- | --- |
| 控制面重启、供应端正常 | CT-SYSTEM / CT-CONNECTION：删通用现场排他前置，但仍核本控制面的原授权与待决动作 | Agency 端点改成可共享后，重启一个控制面不使另一控制面的执行失权 |
| 供应端重启或不可达 | CT-CONNECTION / CT-PARTICIPANT：联系不上不触发控制面重建目录；仍按既有精确执行身份与授权核对 | 联系不上、截止已过、身份不可证的完整分支，以及端点重连的准入条件 |
| 执行结束待交、控制面恢复旧备份 | CT-CONNECTION / CT-PARTICIPANT、C9/C10 的 CT-SYSTEM：原授权与结果核对；工作树已删仍可收保管完好的成果，缺依据显式恢复 | Agency 内部持久存储与失联后报告流程 |
| 集成响应丢失；人的封存未准入 | C3 的 CT-REPO 保持原目标与未知；C9/C10 的 CT-SYSTEM 按原命令恢复候选、不补批准 | 无新增 B 条件 |
| 换机器或同路径重建 clone | C3 的 CT-REPO、CT-CONNECTION / CT-PARTICIPANT：生产位置可变，待决目标不能偷换 | 无新增 B 条件 |

上述 CT 名称指现有族，正式行为测试何时实现仍按交付安排；方案的纸面失败路径与本次文档检查都不冒充已运行的多机测试。

机械验收沿既有 `cd src && ./buck2 test root//build/docs/...`、版本戳/锚点/退休词表/生成词汇表检查与 `git diff --check`；不新增脚本或短语禁令。实施时搜索 Repo Instance、repo_instance_id、site_generation、默认跟踪目录和旧 Git 家的全部现行命中，逐处归 C/B/D 或历史，不靠全局替词宣称完成。机械检查不核自然语言正确性；S1、故障反例、层级与裁决保真由既定评审、读回、合并后核对完成。
