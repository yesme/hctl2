> 状态：讨论中 · v2 按 Codex 首轮意见修正（PR #198）：断言补限定条件、脚本真正触发被测情形、一级不做整句短语关卡、不新增 CT 族、复用与排期收窄；所有者授权修完自合<br>
> 基线：main @ `1d6ca5c`（草案 v0.17.1）<br>
> 去向：`docs/design/scenarios/` 参考用例的正式落点；`docs/research/` 场景测试方法的对象文件；P2 计划各工作包的验收；本 PR 只提案

v2 改了什么：第三节十六条不变量补上各自的前提与限定，五条按 Codex 修正；材料存储的四条测试单列，不塞进 S1 主流程；第四节一级检查改成"文档关联与已裁定词汇"，不做整句短语的必须与禁止关卡；第二节不再新增 CT-SCENARIO 族，用例引用既有 CT 用例与将来的测试目标；第五节补"让错误实现真的会失败"的要求：保留调用与副作用历史、区分"永不越权"与"恢复后能完成"、反向用例、假供应端不得超出真供应端的能力、同机隔离；第七节脚本改正两处没有触发被测情形的步骤；第六、八节按能力排期，不把"脚本是数据"和"同机加可注入时钟等于确定性模拟"当硬前提。

## 一、能不能：能，但要分三级，一级一个"神谕"

所有者的问题是：`.memo/notes/HCTL_case_study.md` 这份用例，能不能变成机械化验证器，让用户体验以后不漂。答案是能，前提是承认它验的东西在三个不同的地方，每个地方需要不同的执行方式和不同的判对判错依据：

1. **设计文档里的关联与词汇**：现在就能机械查，查的是引用链是否完整、编号与映射是否对得上、版本是否正确、已退役的词有没有回来。它不查文字的语义，语义由审阅承担。
2. **在一台机器上模拟的多单元行为**：P2 有了对应能力就能做。把用例的拓扑和步骤写成脚本，在一台机器上拉起多个控制面实例、假的 Agency、假的或随包的平台，按步骤跑，按不变量断言，并注入故障。它验的是行为，判对判错的依据是不变量加执行历史。
3. **真机**：A1 影子及之后。同一份不变量换成真 Agency、真平台、真的三台机器验，合盖这类故障由人做、断言由命令行读。

用例文本本身是第零级：**参考用例**。它要有稳定的编号、正式的落点、逐条编号的不变量，三级验证器都引用它，不各自再写一份。

## 二、参考用例的落点与形状

- **落点**：`docs/design/scenarios/S1-multi-unit.md`，状态"验证文档"，与 `contract-tests.md` 同一档。用例原文进去时改成三段：拓扑、步骤、不变量；所有者的世界观那一段留作引言。
- **权威不来回指**（Codex）：行为的含义由相应的 spec 定义；已拍板但还没落到 spec 的方向明确标为待落地；参考用例记录拓扑、步骤和预期结果，并引用权威条款；契约测试是验证清单，不是另一份约束正文。
- **编号**：场景 `S1`，步骤 `S1.步骤号`，不变量 `S1.I编号`。每条不变量写：它来自用例的哪一步；它的前提与限定；它钉住设计文本的哪一句；它引用哪些既有的契约测试用例或将来的测试目标；它在哪几级被检查。
- **不新增 CT 族**（Codex）：v1 提议加一族 CT-SCENARIO 作索引，撤回。既有的契约测试表已经能表达用例与用例的关系，再加一族只是转接索引，多一处要维护。用例引用契约测试用例时引用它的描述文本或将来的稳定标识，不引用会随插入变化的序号。
- **变体要写成变体**：用例里"共用同一个对象库或单独 clone"两种都成立，就写成 `S1.V1a`、`S1.V1b` 两个变体，二级验证器两种都跑。参考用例不留没有神谕的分叉。

## 四、第一级：文档关联与已裁定词汇的检查

v1 提议按文件列"必须出现的短语"和"不许出现的短语"当关卡，Codex 反对成立，撤回：这种关卡会拦正确的修改，比如"不再要求只能绑定本机回环地址"会命中禁止短语却表达了正确方向；也会放过错误的修改，比如保留"多个独立的控制面"一句、却在别处要求 Agency 只能归一个控制面。语义等价的改写也会因为少了指定句子而变红。自然语言有没有改变意思，由审阅承担。

一级保留为两件已经有工具的事：文档关联，参考用例到设计条款、到契约测试用例的引用链完整，编号与映射对得上，版本正确，沿用现有的链接与版本戳检查；已裁定的词汇，确实退役的名字不回来，沿用现有的退休词表与它的例外范围。仓库里没有通用的"按文件要求或禁止短语"解释器，要加就是新工具，按 PR 契约说明复用与自建，本文不预定。

## 五、第二级：一台机器上的多单元行为测试

这是把用例变成可执行测试的主体。形状（v2 按 Codex 收窄）：

- **多单元同机**：一台机器上拉起多个控制面实例（真的控制面代码，各用自己的数据目录与回环端口），Agency 用进程内的假实现（能按模板交付假执行体、能持久保管结果、能被切断连接），平台与任务源用随包的本地平台或假实现。不同机器角色的目录与可达路径要隔离，不能偷用共享内存或任意本地路径递交本应跨机交付的正文与结果。
- **假供应端只替代供应端，不替控制面作决定**，也不能比真供应端多出能力：假 GitHub 不得"保证预期目标头"，现文 `spec/repo.md` §平台绑定与能力声明 明确本批没有已核验的平台能声明它；若为抽象端口加这种能力变体，它的通过不算 GitHub 适配器已通过。白盒测试可以查假 Agency 的内部存储，但二级与三级共用的判据不能依赖某家 Agency 的私有数据库结构；真供应端缺某个可观察点时记录验证缺口，不给产品增设专用接口。
- **判对判错只认不变量，但只查最终状态不够**：同时有效的两个写入权可能在检查前又被收回，重复的平台写入也可能留下看似正常的最终状态。测试期间要保留调用、响应与实际副作用的历史，按具体断言检查历史，这不是解析人类日志。
- **"永不越权"与"恢复后能完成"是两种判据**：后者要写恢复了哪些前置、等待什么结果、等待边界是多少；不能把永远不推进的实现判为合格，也不能在异步操作尚未完成时立即判失败。每个断言写适用前置、触发动作、可观察结果。
- **反向用例**：故意给检查器一份违反该条的结果或执行历史，确认它真的会红。
- **故障注入是脚本的一部分**：控制面停、Agency 断连、执行体被杀、时间推进。可注入的时间值得采用，是快速、可重复地测期限的办法，但"不注入就验不了"太强，真机可以用实际经过的时间验；同机加可注入时钟也不等于确定性模拟，可重放还取决于随机输入、消息次序、调度和外部 I/O。首批做可控故障的集成测试即可，不为模拟数据库集群那样完整而重写运行环境。
- **脚本是数据，不当硬前提**：列出动作之后仍要实现动作、等待、并发、故障、断言和失败处理。先研究现有的 Rust 测试入口、现成的场景框架和已有的端口替身能覆盖多少，再决定要不要新的动作语言。
- **业界复用先研究再决定**（实现层脚注）：FoundationDB 的模拟与它的执行环境紧密结合、会模拟网络和磁盘，TigerBeetle 的 VOPR 跑真实数据库代码并注入网络、存储、进程故障，可以借鉴可重现故障与断言的办法，不能从"一台机器能起多个服务"推得同等保证；Jepsen 记录操作的开始、结束与故障历史再用检查器判历史是否成立，这支持上面"检查历史"的要求；Gherkin 的可读步骤仍对应代码里的步骤实现。落代码前要在 `docs/research/scenario-testing.md` 逐一核对现成代码、框架与方法的适用性，再决定采用范围。

## 六、第三级：真机

同一份不变量换真单元：mac、cloud、ubuntu 三台，真 Agency、真平台。步骤由驱动器经命令行下发，断言经命令行与 bench 读；合盖、断网这类故障由人按脚本做，脚本记录预期与实际。时机是 A1 影子：在试验仓库上跑。整机合盖会影响同机其他任务，要另排测试窗口，不能只凭"用了试验仓库"就认定不影响 HCTL2 自己的开发。A1 从真实 CLI 与无 Run 切片开始，不等于包含真实 bench、GitLab 与完整 Run 的整份 S1 已能跑：Workbench 在 P3，GitLab 的完整走通要等第二个外部平台适配器。三级共用场景意图、断言编号与结果格式，不强求虚拟推进时钟、真实合盖、供应端能力不同时仍执行完全相同的每条命令；不适用、未实现与通过分开记录。

## 七、结构化脚本的草稿（v2，只表达形状）

字段名与格式等研究文件与 P2.1 的协议定稿后再定。v1 有两处步骤没有真正触发被测情形，Codex 指出后改正：I6 要让两方真的共用一个对象库，改用 mac 本机的参与者与 cloud_ctl 雇的 mac 参与者；I11 要在这次工作封存或首次交付之前让控制面不可达，并覆盖接收方已保存但确认丢失的重投。`both` 落实时要产生真正交错的请求，不只是顺序执行两个命令；共享目标前移后各方只能按冻结形态继续或拒绝，驱动器不得替它换授权。

  gl-jstui: { platform: gitlab }
machines:

  mac:   { agency: mac_agency,   templates: [mac_tpl_sdet, mac_tpl_ops] }
  ubuntu:{ agency: ubuntu_agency, templates: [ubuntu_tpl_sde, ubuntu_tpl_pm] }
controls:
  mac_ctl:   { machine: mac,   projects: { mac_jssdk_01: gh-jssdk, mac_jssdk_02: gh-jssdk } }
  cloud_ctl: { machine: cloud, projects: { cloud_jstui_01: gl-jstui, cloud_jssdk_01: gh-jssdk } }
hires:
  - { control: mac_ctl,   project: mac_jssdk_01,   agency: mac_agency,   template: mac_tpl_sdet, as: mac_ptcp_jssdk_01_01 }
  - { control: mac_ctl,   project: mac_jssdk_01,   agency: cloud_agency, template: cloud_tpl_sde, as: mac_ptcp_jssdk_01_04 }
  - { control: cloud_ctl, project: cloud_jssdk_01, agency: mac_agency,   template: mac_tpl_ops,  as: cloud_ptcp_jssdk_01_02 }
frontends:
  ubuntu_bench: { machine: ubuntu, connects: [mac_ctl/mac_jssdk_02, cloud_ctl/cloud_jstui_01, cloud_ctl/cloud_jssdk_01] }

  V1: { a: shared_object_db_per_machine, b: clone_per_project }
steps:
  # I6：两方真的共用 mac 上的对象库（V1a）
  - { do: dispatch, control: mac_ctl,   project: mac_jssdk_01,   participant: mac_ptcp_jssdk_01_01,   task: T1 }
  - { do: dispatch, control: cloud_ctl, project: cloud_jssdk_01, participant: cloud_ptcp_jssdk_01_02, task: T2 }
  - { assert: [S1.I6], with: { object_db: mac/gh-jssdk, both_writing: true } }
  # I5：交错的合入请求，各按冻结形态处理

  - { assert: [S1.I5], with: { history: merge_requests, frozen_forms: true } }
  # I11：控制面在封存与首次交付之前不可达；接收方已保存但确认丢失的重投

  - { fault: control_unreachable, control: mac_ctl }

## 八、代价、排期与边界

- 一级便宜但只查关联与词汇；语义靠审阅，行为靠二、三级。
- 二级要先有假单元，假单元自己也要受约束，不得超出真供应端的能力；执行历史要留；反向用例要有。
- 排期按能力列，不写"能验一半"（Codex）：P2.1 可先验命令、存储、进程间通信与多实例隔离；P2 计划 §十 把 Repo 与 Project 放 P2.2，Participant、调用与 Context 放 P2.3，封存与集成放 P2.4，Run 与 Gate 放 P2.5；假 Agency 不能补出被测控制面尚未实现的领域行为。每条不变量按它依赖的能力标在对应里程碑。
- 三级不能全自动，人的操作要按脚本记录；进程与连接故障先限定到测试实例。
- 用例进 `docs/design/scenarios/` 之后就是验证文档，改它要走 PR、更新引用；这是它当"神谕"的代价。
- 本文只提案，不加脚本、不加研究文件；落地顺序是研究文件、参考用例正式落点、一级的关联检查随设计改法批、二级先接现有 Buck 测试入口做少量真能抓住故障的行为用例，再决定是否值得抽公共驱动器。
