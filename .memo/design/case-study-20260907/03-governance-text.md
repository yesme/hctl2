# 第 13 条：治理正文放哪，以及它怎么到参与者手里

> 状态：讨论中 · Fable 的裁决建议，所有者要求写进 PR 再请 Codex 看一轮有没有更好的办法<br>
> 基线：main @ `09e277c`（草案 v0.17.1）<br>

## 一、问题

现行约束（`spec/system.md` §控制面自己的存储）规定每个被管仓库里有一个 Git 跟踪目录 `<repo>/.hctl2/`：projects/ 放 Project 配置与 Task 契约的各版本正文，workflows/ 放施工图正文，memos/ 放发布过的备忘，policies/ 与 schemas/ 放仓库共享的策略与 schema 版本；同节把这些叫"不可变正文"，另有 Verdict 与 Receipt 在 Git 里的"审计影子"。这两类合称治理正文。

用例把它的毛病摆出来了。mac_ctl 在 mac_jssdk_01 采纳一张契约，按现文要写成 `gh-jssdk/.hctl2/projects/mac_jssdk_01/tasks/…/revision-2.md` 进默认分支。gh-jssdk 是别人的仓库时推不进去；cloud_ctl 的 cloud_jssdk_01 也要往同一棵树写，两个控制面的材料交织、互见、可能互相覆盖；"治理记录归控制面"是本轮定的权威关系，正文却住在共享仓库里。取消身份文件没有回答这个问题（Codex、GLM、Grok 第一轮一致）。

## 二、参与者怎么拿到治理正文：靠开工包，不靠工作树

所有者问："这个治理正文貌似是大家执行的时候要能看见的东西，它怎么在参与者之间传播？"答案在现有设计里，只是存放约束让人误以为参与者从仓库树里读。

派工时控制面组装 Context Manifest 与 Context Bundle（`spec/project.md` §Context 的来源顺序：用户显式引用、当前讨论窗口、Repo/Project/Task/Run/Request 的引用、Git 中的结晶副本、必需 Skill、相关 Memo）：把这张 Task 的契约版本、这次 Run 的施工图、相关备忘、适用的策略版本连同摘要装进包，随执行规格交给 Agency，Agency 把包放到执行体面前。投喂分三档（`context.md` §投喂三档）。内联：每次必用、放得下的，契约与范围、裁决正文直接写进 prompt。指针：精确地址加一句说明，但指针只能指向执行体在自己的检出里用 git 能打开的位置，即 Git 对象与工作树路径，现文把代码、变更集提交、Memo、Skill、登记在 Git 里的 Artifact 都放在这一档。代取：执行体够不着的，聊天史、评论线、控制面存储里的裁决与凭证，开工时由组装器萃取后内联，运行中要补就走受限召回，由 HCTL 自己的检索器取回塞进会话，不经 git。

所以：cloud 上为 mac_ctl 干活的参与者，契约来自 mac_ctl 装的包，它的检出里有没有 `.hctl2/` 无关紧要；cloud_ctl 的参与者只看到 cloud_ctl 装的包，mac 那边的内部备忘不会自动漏过去，共享只能是人显式发布。参与者的可见性与正文存放在哪里无关；变的只是它落在哪一档。契约本来就在内联档，不受影响。Memo、施工图、登记在 Git 里的 Artifact 现在是指针档，前提是它们的对象在参与者那台机器的对象库里：正文若搬进控制面存储或另一个仓库，它们就从指针档掉到内联或代取档，多一轮往返；正文若放在被治理仓库的旁路 ref 里，参与者的 Repo Instance 取一次 `refs/hctl2/<控制面>/*` 就能让指针继续解开。这是存放选择真正影响参与者的地方。

一类东西例外，必须在仓库树里：仓库自己的规约文件，AGENTS.md、CLAUDE.md、CONSTRAINTS.md、lint 配置、PR 模板。harness 按约定在工作树里自己读它们，它们是代码的一部分，随 clone 走，经正常 PR 合入。本仓库就是这么用的，用得对，因为仓库是我们自己的；给别人的仓库贡献时，这类文件是对方的，不是我们的。

## 三、五家的候选与收敛的形状

第一轮与第二轮五家各给了候选（见 PR #193 评论）：GLM 按用途分流（治理正文进控制面存储、审计分发走旁路 ref、有意公开的走正常仓库文件）；Grok 分未发布工作副本、发布后的结晶、给上游看的子集三档；Kimi 选正文归控制面存储、Git 只放结晶副本与摘要、上游不写；Antigravity 分公共规约进主分支、私有治理状态进控制面存储、变更集伴生证据进专用 ref；Codex 首选独立的治理材料仓库，其次控制面存储，显式发布到目标仓库作为选择，并指出"字节被看见不等于治理互认""结晶与正文不互斥"。

收敛的形状：

1. 权威在控制面存储；起草中的契约、未发布的备忘只在控制面存储。
2. 被治理仓库的默认分支不是缺省的家；写进去只能是人的显式发布，像本仓库的 decision-history。
3. 需要版本、分发、跨机取回的材料放 Git 侧存储，普通 clone 默认看不见，要声明怎么取。
4. 给上游贡献时默认什么都不写；要带什么，只附在评审请求的描述或对方允许的位置。
5. 参与者的可见性由开工包保证，与存放无关（第二节）。

留下一处待选：第 3 点的 Git 侧存储，是被治理仓库里按控制面隔离的旁路 ref（GLM、Grok、Kimi、Antigravity），还是一个独立的治理材料仓库（Codex）。

## 四、Fable 的裁决建议

两者都留、按仓库配置，缺省旁路 ref。

- **缺省旁路 ref** 的理由：它和第 14 条要求的 ref 命名空间隔离是同一套设计，一次做两件事；Memo、施工图、Artifact 留在指针档，参与者取一次旁路 ref 就够（第二节）；审计影子能随仓库带走；不多一个仓库要管。代价：普通 clone 默认看不见，要显式取；仓库不是自己的时候一样写不进去。
- **独立治理材料仓库** 用于给上游贡献、或不想往对方仓库写任何东西的情形：不要求上游接受任何 HCTL 文件；可以显式共享而不合并各控制面的批准。代价：代码仓库与材料仓库要明确关联，交付与备份要覆盖实际引用的版本。

一笔明确的代价：现文权威地图把"Git 分布式冗余可恢复正文"记为一项好处；正文的权威进控制面存储之后，这项恢复责任落到控制面的备份集上，与它已经要备的 Profile、Skill 定义字节同类。

## 五、请 Codex 看的问题

1. 第二节"可见性靠开工包、与存放无关，变的只是落在哪一档"这个判断成立吗？有没有参与者必须从仓库树读治理正文的情形；把 Memo、施工图从指针档挤到内联或代取档的代价，够不够成为旁路 ref 优先于独立仓库的理由。
2. 第三节的五点形状有没有漏；有没有比"旁路 ref 缺省、独立仓库备选、按仓库配置"更简单或更稳的办法。
3. 权威进控制面存储后，恢复与备份的责任转移写在哪一层；"Git 分布式冗余"这条好处是不是真的丢了。
4. 审计影子（Verdict、Receipt 的副本）要不要随仓库分发；不分发的话，别的控制面或人在仓库里看到一个合入的 PR 时，怎么知道它经过了哪次裁决。
