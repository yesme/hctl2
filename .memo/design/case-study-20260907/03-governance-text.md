## 一、问题

现行约束（`spec/system.md` §控制面自己的存储）规定每个被管仓库里有一个 Git 跟踪目录 `<repo>/.hctl2/`：projects/ 放 Project 配置与 Task 契约的各版本正文，workflows/ 放施工图正文，memos/ 放发布过的备忘，policies/ 与 schemas/ 放仓库共享的策略与 schema 版本；同节把这些叫"不可变正文"，另有 Verdict 与 Receipt 在 Git 里的"审计影子"。这两类合称治理正文。

用例把它的毛病摆出来了。mac_ctl 在 mac_jssdk_01 采纳一张契约，按现文要写成 `gh-jssdk/.hctl2/projects/mac_jssdk_01/tasks/…/revision-2.md` 进默认分支。gh-jssdk 是别人的仓库时推不进去；cloud_ctl 的 cloud_jssdk_01 也要往同一棵树写，两个控制面的材料交织、互见、可能互相覆盖；"治理记录归控制面"是本轮定的权威关系，正文却住在共享仓库里。取消身份文件没有回答这个问题。

## 二、参与者怎么拿到任务书：冻结输入、实际交付、保留与可再取

所有者的问题：Run 里各家参与者常常要读任务书，参与者不在一台机器上、没有共享的工作树，任务书不在 git 里被显式看到，怎么处理。

答案的骨架在现有设计里：派工时控制面为每个消费者组装 Context Manifest 与它自己的 Context Bundle（`spec/project.md` §根 Context Manifest：每个消费者物化独立的 Bundle，记录消费归属者、权限、预算、条目与自身摘要），随执行规格交给参与者所在机器的 Agency，Agency 起执行体时把它放到执行体面前。任务书不靠共享工作树，也不靠仓库树。

Codex 把这个保证写得比 v1 准，采纳：

> 开工包固定本次输入的来源、版本和交付方式；材料的长期存放位置可以不同。执行前要把必用材料，以及承诺可离线查询的材料，交付为执行者可读取的精确版本；尚未交付的材料是否可取，仍取决于来源、权限与连接状况。

由此三件事分开写：冻结输入是选材，实际交付是把字节送到执行现场，保留与可再取是执行中途、上下文被整理后、控制面暂时离线时还能重新读到。摘要能校验取回的字节，不能代替送达，也不证明模型读过。**现文对第二和第三件写得不全：要求了物化、交付核验与保留，没有写明每个 Agency 都提供可反复读取的本地副本。这要作为交付要求写进约束，不能说现有条文已经保证**（Codex 更正 v1 对话里的说法）。

对话里另外三句要更正：

- "任务书永远内联"不准确。`spec/project.md` 的三种交付方式写明必用内容超预算要降为指针并附分片建议；"任务书"也不能把 Task 契约、施工图全文、该席位的操作说明混成一类，Run 冻结施工图版本不等于每个席位都收到全文。
- "三个席位三份包摘要相同"应为：共同契约条目的精确版本与摘要相同，三个完整 Bundle 各不相同。
- "返工重新装包、摘要一致"不能泛化：同一投递重试不换材料，技术备用沿用原评审依据，语义返工会有新的被评版本或裁决输入（`spec/run.md` §Request、重试与 Gate）。

**哪些东西必须在仓库树里，按用途分，不按名字分**（Codex）：仓库自己的规约、原生工具按路径读取的配置、以及这次工作本来要修改或校验的文档，必须在相应版本的预期路径上，一个文件可以同时是规约和交付物，不因为被叫作治理正文就搬走；只为这次执行提供范围、验收与背景的材料不必进源码树，在获准的只读材料检出或本次交付副本里能反复读即可。harness 会自动读哪些文件是各工具的能力，不当共同保证。

**v1 的主论证撤回。** v1 说正文离开被治理仓库的对象库，Memo、施工图就从指针档掉到内联或代取档，所以旁路 ref 优先。Codex 指出这个比较漏了一种正常交付：指针的条件是"执行体在获准范围内用自身工具能打开的 Git 对象或工作树路径"，没有要求正文长期存放在代码仓库的同一个远端。独立的材料仓库同样可以在派工前取得获准版本、准备只读材料检出，继续给 Git 对象或文件路径的指针；控制面私有正文也可以提前物化本次副本。两条路都能预取、缓存、按需本地读，参与者不需要每读一次就代取。真正要比较的是权限、初次准备、更新、保留与运维，不是假定独立仓库每次多一轮模型往返。我接受这个反驳。

**派工的主路径是控制面把字节送到 Agency，不是让参与者去取材料库**（Grok）。ubuntu 上的参与者没有义务能连上 mac_ctl 的材料库；控制面睡着时已交付的现场副本仍要可读。控制面或它委托的组装器在派工前把获准字节取出来，随执行规格交给 Agency，Agency 落成执行现场里可反复读的只读副本，按提交摘要钉死；参与者不持材料库的凭据。大文件"按获准地址由 Agency 取回"是以后的优化，是可达路径的一种，不是语义缺省。Kimi 补了一条约束层的硬事实：现文指针不得指向控制面存储（`spec/project.md` §三种交付方式），正文若放进控制面存储就永远进不了指针档，材料仓库的正文天然是 Git 对象，一字约束不用改。

## 三、收敛的形状（v2）

1. **治理的准入、当前版本指向、授权与裁决归控制面**；这不自动决定全部正文字节只能放在控制面存储，草稿默认私有与它的存储格式也是两个决定（Codex 收窄 v1 第 1 点）。
2. **被治理仓库的默认分支不是缺省的家**；写进去是人的显式发布，不把贡献上游的能力绑在上游接受 HCTL 文件上。
3. **需要版本、分发、跨机取回的材料放 Git 侧存储**，并写明谁保管哪个版本、读者能取得哪些材料、引用移动或服务不可用后怎么办。"普通 clone 看不见"只指克隆代码仓库；材料仓库自己的克隆不在此列。
4. **给上游贡献时默认不写内部治理材料**；获准的代码、文档变更与评审发布照常；审计关联可发布到允许的评审记录里，见第五节。
5. **参与者的可见性靠"冻结输入、实际交付、保留与可再取"三件事**，不是靠选材清单代替可用性保证（改写 v1 第 5 点）。

还要写清三项条件（Codex）：材料给谁看；谁保留已被引用的版本；控制面不可达时哪些资料已在执行现场。这是现有权限、冻结与交付责任在这里的落点，不新增业务对象。

三句要写死的话（GLM，Grok 同）：

6. **规范字节在材料仓库，控制面存储记准入、当前版本指向与摘要。** "Git 里出现一份正文不等于已被准入"这条不改，只换家；材料仓库里的字节是候选原文，准入仍在控制面。未发布草稿的权威与指向在控制面存储，字节可以作为未准入对象住在材料仓库里（Grok 收窄自己第一轮的甲）。
7. **材料仓库是控制面的持久资产，不是被治理的仓库。** 它不进 Repo 模块的仓库清单，不做平台身份、集成意图、Repo Room 这些事，不注册、不开 Project；在事实权威地图上与控制面存储同一档；写者是控制面，与控制面存储同一写者纪律；参与者与 Agency 只有只读副本。一个控制面一份，按已有 Repo 与 Project 的引用分目录或分 ref，不每个 Project、每次执行新建。
8. **`<repo>/.hctl2/` 作为系统默认写入的跟踪目录取消**（Kimi）。被治理仓库里只剩人显式发布的文件：仓库自己的规约、有意公开的决策记录。这是第一节那两个病的对应治法。

## 四、Fable 的裁决建议（v2，改口）

**缺省：一个控制面管理一份可私有的治理材料仓库，按既有 Repo 与 Project 的引用组织材料；派工时统一准备获准版本的副本。** 旁路 ref 退为显式选项。理由：

- **一种流程覆盖自有仓库和贡献上游。** 旁路 ref 在别人的仓库里一样写不进去，上游场景还得走第二套；材料仓库对两种情形是同一条路。
- **读者范围与代码仓库分开。** ref 命名前缀不是读取权限的边界（Codex 脚注引 Git 的命名空间安全说明）：放在共享代码仓库里的旁路 ref，能读仓库的人都能取到，"内部备忘不会漏给另一个控制面"在旁路 ref 下不成立，它只是 v1 对开工包选材的陈述，不是存储隔离的保证。材料仓库可私有、可显式共享，共享材料也不合并各控制面的批准。
- **指针照旧。** 派工前把获准版本取到参与者机器、准备只读材料检出，Memo、施工图仍然是指针档，不多一轮往返（第二节）。
- **不新增服务，不新增模块。** 材料仓库缺省就是控制面数据目录里的一份裸仓库，派工从它读；它不是新的被治理目标。

**平台托管：本地裸库必有，平台是写穿的镜像与分发通道。** 四家对"要不要缺省托管在随包本地平台"分成两派，Antigravity 强烈支持，Grok 反对写成缺省，GLM 与 Kimi 支持但各附两个条件；条件写进去以后两派其实是一个意思，我按条件写：

- 控制面本地始终保有材料仓库的可服务副本，派工准备只读本地；平台不可达时本地派工照常，跨机的包外补取降级为经控制面中转或稍后同步。随包平台"随包不等于总在"，不能让派工的可用性绑在它身上（Grok、GLM、Kimi）。
- 托管是镜像：本地裸库写穿到平台，随包本地平台在时缺省开启，也可以镜像到外部平台或不镜像；显式不挂平台的 Repo 照样有材料仓库和既定的可达路径（Kimi）。
- 平台给的真收益有三条（GLM 把 Antigravity 的四条收准）：跨机的包外补取有标准协议与令牌，不用自建中转协议；人在 bench 之外白得一个翻阅治理正文的 Web 界面；备份有了落点与复制通道。备份不是"顺带有了"：平台自身的存储与仓库目录仍要进备份集（Kimi 纠正 v2）。
- 两种形态的差别只在两处：没有平台端点时，包外补取经控制面中转、控制面醒着才可补；有平台端点时可直连取回、人可 Web 翻阅。其余等价（GLM）。

代价照 Codex 的列法写明：多管理一个存放位置；材料与代码的精确关联、备份、首次取得权限都要处理；一个控制面一份，不要每个 Project 或每次执行新建。

**旁路 ref 保留为显式选项**：同一读者范围、已有写权限、愿意共用存储时可选，例如某个控制面独用的私有仓库。v1 说它"与第 14 条是同一套设计"不再作理由（GLM、Grok 同撤）：第 14 条解决独立写入不撞名，第 13 条解决存放、读者范围与交付，可以复用命名规则，解决撞名不等于解决访问与保管。Kimi 复核了 Git 命名空间安全说明的原文："私有数据最好放进另一个仓库"，托管平台也没有按读者隐藏 ref 的机制。GLM 另称 GitHub 这类托管只接受 refs/heads 与 refs/tags 的推送、旁路 ref 在最大一类平台上写不进去，这条我标待核：git-bug 把自己的 refs/bugs 推到 GitHub 远端是公开的做法（`docs/research/task-backends.md`），与这个说法相悖；适用面写成"以平台实测能力为准"，不写死。

**显式发布到代码仓库**：仓库自己的规约、有意公开的决策记录，人经正常 PR 合入，像本仓库的 AGENTS.md 与 decision-history。

## 五、审计影子：发布审计关联，完整副本按公开范围分发

别的控制面或人看到 PR 已合入，要问的是"谁针对哪个版本、依据什么规则作了什么裁决"，单看合入事实答不了（Codex）。做法：在获准的发布策略下，向平台上的评审请求发布一份简明的审计关联，含归属控制面、被评的精确版本、裁决或凭证的引用与摘要、可访问的结果说明与取回位置；合入后再关联 Integration Receipt，不把"允许合入的裁决"和"已经集成的证明"写成一件事。这是现有平台写回职责的使用，不另造审计服务。

- 人沿 PR 上的关联读到允许公开的结论；另一控制面可取回作为外部证据，按自己的规则采纳，不继承原控制面的批准。
- 要求离线审计、长期存档、或不依赖原控制面在线时，要分发足够的审计正文与依据，只给一个指向私有或已停机控制面的地址不够。
- 用户选择不公开或读者没有权限时，明确"相关裁决不可访问"，不能声称看到合入就知道它过了哪次评审。
- 要求只靠普通代码克隆就能发现裁决的，必须显式把索引或副本发布进克隆会带走的内容；不分发却要求离线读者自动知道，是无法满足的组合。
- 显式不挂平台的受限路径没有评审请求可写：关联留在材料仓库与控制面存储里，只看到合入提交的人不知道哪次评审。这是诚实的缺口，不用"影子一定随代码走"去填（Grok）。

关联的字段候选（Antigravity）：归属控制面、Task 与 ChangeSet 的稳定标识、被评的精确提交、Verdict 或 Receipt 的引用与摘要、取回位置。落点：`spec/system.md` §Git 的双重角色 写审计副本的效力与公开范围，现文"审计影子由工具箱写入 Git，用于审计与随仓库同步""私有仓库默认全文"两句与本节冲突，要改成"随材料仓库保存，按公开范围发布到评审记录"（Kimi）；`spec/repo.md` §发布评审、§变更与平台的映射、§集成 写写回授权与精确版本关联。

## 六、备份与恢复：谁批准、原文在哪、从哪恢复分开答

v1 说"权威进控制面存储，Git 分布式冗余这项好处就丢了"，推导不成立（Codex）。三种情形：控制面记录在、某份正文丢了，Git 副本里有精确字节，按引用与摘要恢复正文，不重新授予任何批准；控制面的授权、准入或裁决记录丢了、只剩正文，不能据此推测批准过什么，审计影子可辅助显式恢复，不能补造决定；正文只剩摘要、既无备份也无完整副本，才真正不可恢复。不再能依赖的只是"克隆代码仓库就顺便得到这些正文"的便利，而旁路 ref 本来也要显式获取。

落点：架构层说明每类资料由谁保管、丢了能恢复什么；`spec/system.md` §控制面自己的存储、§Git 的双重角色、§全系统事实权威地图、§备份与恢复 规定一致备份覆盖的记录、被引用的正文字节、保留范围与缺项处理。材料仓库是规范字节所在，必须被一致性备份覆盖，单独备还是并入备份集只是形式（GLM 收紧 v2 的"都可以"）；恢复时必须能核齐引用；`spec/project.md` §根 Context Manifest 与连接、Participant 的交付规则负责执行侧副本的保留与断线时的可用性；交付层给备份与恢复入口，沿用 CT-SYSTEM、CT-CONNECTION 验证"记录在而正文缺失""从精确 Git 副本恢复正文""只有审计副本不重造裁决""已交付材料在控制面离线时仍可重读"。

## 七、第三种办法与为什么不选它

Codex 第一轮的候选 B：私有正文由控制面保管在现有持久存储或正文目录，执行者拿冻结材料的副本，Git 只用于显式发布与审计导出。放置在控制面，权威在控制面，交付是必用小段内联、其余派工前物化为精确副本并给路径。好处是不用再管一份 Git 材料仓库；代价是控制面要完整承担正文历史、版本比较、导出、备份与异机交付，非 Git 的交付目录怎么作指针也要写进约束。为省一份仓库而补出另一套正文版本管理，未必更省，所以不作首选，记为候选。

## 八、拍板结果（所有者 2026-09-07 授权 Fable 按五家意见收口自合）

1. **缺省取独立的治理材料仓库**：一个控制面一份、可私有；规范字节在材料仓库，准入与指向在控制面存储；派工前由控制面准备副本送到 Agency；旁路 ref 退为显式选项；显式发布到代码仓库照旧；`<repo>/.hctl2/` 系统默认写入的跟踪目录取消。五家一致。

3. **审计关联发布到评审请求上**，作为发布评审策略的一部分；字段候选见第五节；受限路径的缺口如实写。

## 十、控制面存储的两半与 Git 后端（v5，按 Codex 评审修正）

所有者点出一层关系：第八节把治理正文留在了控制面的存储里，而控制面的存储可以是另一个 Git 仓库，两者不矛盾；访问这份持久存储就是访问一份带版本的内容，定位与引用是控制面的抽象接口，后端是 Git 时，接口的实现就是对 Git 上带版本文件的读写。这个逻辑成立。Codex 审了 v4 的写法，指出一处事实错误、两处归属不清、一段顺序不够，本节按它改。本节不全是实现层脚注：权威、写者、引用稳定性、持久保证是约束，只有布局、命令、参数是实现。

### 1. 两半，一个控制面负责

控制面存储分两类数据。治理记录：身份、准入决定、当前版本指向、授权、代次、意图与凭证，以及命令的幂等结果和待投递动作。治理正文：契约、施工图、备忘、策略、schema 的不可变字节。两类同属一个控制面、同一个逻辑写者。"两半"是职责分开，不要求两个服务；"同一写者"是同一个逻辑 control writer 授权和协调，不要求所有磁盘写入都在同一个进程里，受委托的 Git 子进程和镜像程序不因此取得准入权。写者搬迁与旧写者失权要同时覆盖记录库和材料库，不能只保护记录库（Codex）。材料仓库不是控制面之外的第三个地方，它就是控制面存储放不可变字节的那一半，也不是新的被治理目标。

### 2. 记录留在结构化存储里，理由是事务，不是 Git 的能力缺陷

v4 写"Git 没有事务和条件更新"，这句不成立，撤回：Git 的 update-ref 就是旧值匹配才更新，`--stdin` 支持引用事务，本仓库 `docs/research/sdk/git.md` 实测过这个比较并交换。正确的理由是（Codex 的写法）：

> 准入、当前版本推进、相关领域记录、命令幂等结果及必要的待投递动作一起提交；材料库的引用只能表示字节保存或派生索引，不能独立决定哪个版本已经获准、当前生效。

这是 `spec/system.md` §命令与跨服务正确性 与 §单写者 已有的要求。边界是"Git ref 不作为治理 current 的另一份权威"，不是"Git 里不能出现 current 的副本"：把指向导出成非权威的快照或索引，供人和 fetch 用，不产生第二个权威；让记录库与 Git 各自作准、能分别决定 current，才会。本批继续用既有的结构化存储放记录，不另开 Git 记录后端。

### 3. 接口的四个动作，各自的边界

其余模块看到的最小接口仍是四个动作，但不能说四个都由 Git 后端独自回答（Codex）：

| 动作 | 边界 |
| --- | --- |
| 存入 | 存的是不可变内容，不是批准某个业务版本；成功要含可重新定位、可校验、已保管的保证，不只是一次 Git 命令返回。相同字节可复用，不等于两个不同的契约版本自动成为同一个版本 |
| 取回 | 按精确内容取回并核验；缺失、不可达、无权限、摘要不符是四种不同结果，不能一律冒充"没找到" |
| 列版本 | 归属改到记录那一半：对象有哪些已准入版本、先后关系、哪一版是当前，由记录回答，正文后端只按所得定位符读内容。Git 提交次序不能代替领域版本次序；候选原文与已准入版本不混列 |
| 交付 | 组装与传输动作，可复用取回，但还要带获准的材料集合、接收者、本次用途和接收端核验；本地读成功不等于 Agency 已收到且能反复读。整库镜像与按执行范围交付可共用底层传输，不共用"整库可见"的权限 |

保管、保留期与回收由既有的生命周期与保留策略驱动，是这四个动作成立的条件，不另造公开的回收接口。

### 4. 定位符要说清三种信息

不把 Git 对象编号当 HCTL 的内容身份，维持；但"带 HCTL 规范摘要"一句交代不了定位符，要分三种信息，不必塞进同一个字段组（Codex）：

- **到哪里解析**：所属控制面或材料库的稳定范围，加该范围内不可变内容的标识；范围可由既有连接隐含，不另造全局身份。摘要能验内容，不能独自告诉另一台机器去哪取，也不授予读取权限；后端地址与 Git 对象映射可换，已冻结的逻辑引用不跟着变。
- **验的是什么**：原文字节的内容摘要与完整 Revision 的规范摘要不是一个含义（`spec/project.md` 已分列 content_digest、revision_digest、review_subject_digest）。正文若先规范化再存，就承诺取回规范化后的字节；承诺保留原文，就核原文字节。规范对象等价不等于两份原文字节相同。
- **属于哪个版本**：对象的稳定引用、精确 Revision 与版本线关系由相应模块的记录或 Manifest 携带；按内容摘要去重时内容标识与内容摘要可以合一，不能因此省掉领域版本身份；冻结的摘要不依赖以后会变的磁盘路径或后端地址。

由此第九节那行"指针不得指向控制面存储、不改"要收窄，已在第九节改。

### 5. 写入顺序与两半的一致性

"封存在事务外、准入在事务内"这个次序维持，但同一写者不会把 Git 与结构化存储变成一次原子提交，一致性要另行定义（Codex）：任何已确认、仍负有保管责任的准入记录，都能解析到校验一致的正文；多出的候选允许存在。内容摘要用于字节去重，既有的命令标识与幂等键用于命令去重，前者防不了同一命令重试生成两个领域版本。最小顺序三步：

1. 在适用的写权下把精确字节与可恢复的定位关系持久保存，并保证从保存到准入判定完成之间不会被回收；"保存成功"含对象与引用落盘，不是一次 Git 命令返回。
2. 准入事务重新检查命令的权限、预期版本与适用代次，一起记录准入、定位符与摘要、领域版本与当前指向、幂等结果和必要的待投递动作。封存期间发生取消、换代或版本前移，不能按封存前的检查批准。
3. 后续的交付与镜像按持久的投递记录重试、回读。平台不可达时本地保存与准入照常完成，镜像显示待同步；"写穿"不等于等远端成功才返回，否则与第八节"平台不是派工的运行时依赖"冲突。

崩溃与回收至少要答这四种情形：

| 发生位置 | 应有结果 |
| --- | --- |
| 字节已保存、准入事务未提交时崩溃 | 保留未准入候选；恢复后按原命令与适用前置继续或拒绝，不因为 Git 里已有正文就补出批准 |
| 准入已提交、响应或镜像确认丢失 | 重试回到原命令的结果，不再生成一版、不重复推进当前指向；镜像滞后不撤销已成立的本地准入 |
| 记录在、对应字节或定位映射丢了 | 从精确副本恢复并核摘要，不改指"最近的一版"；恢复不了就明确缺项、阻止依赖这些字节的操作，不抹掉已有决定 |
| 回收在"保存完成、准入提交之前"运行 | 该候选仍受保护；只看数据库里已提交的引用会在这个窗口误删将被准入的正文 |

回收的规则不止"不碰被记录引用的对象"：未完成的写入与准入、待交付的、备份正在读的版本、需要回读的历史版本都要保住，不只保当前版本，由同一写者协调。实现可以借 Git 原生的引用可达性来保管对象，不必自建对象回收器，但 Git 不会自己去读结构化存储发现引用，保护性引用要由控制面维护。

### 6. 保留与备份

源正文与执行侧副本的保留分开：`spec/project.md` §根 Context Manifest 已要求 Bundle 至少保留到归属者终态且结果准入窗口关闭，之后可丢明文、留引用与摘要和丢弃事实。第九节"Agency 保留到执行结束"不得缩短这个窗口，也不把每条残留摘要解释成副本要永久保存；保留范围按对象与已接受的策略定。一致备份要覆盖同一记录快照所需的精确正文与定位关系，材料副本可以多出候选，不能缺快照仍承诺保留的内容。"没有准入的对象无害"只指它不产生领域效果，不等于可以无条件公开或立即删除；同库镜像仍要满足选定的公开范围。

### 8. 实现层脚注

- Git 的 `update-ref <ref> <new> <old>` 是旧值匹配才更新，`--stdin` 支持引用事务；引用事务不等于 Git 与 SQLite 共用事务，也不保证并发读者看到多 ref 的一致快照。
- Git 的回收按自身引用可达性保留对象，官方文档明确提示可能删掉并发写入、尚未挂引用的对象；对象与引用的落盘另有配置，进程返回成功不等于异常关机后一定存在。
- "Git 已是工具箱依赖"不等于只跑控制面的机器装了 Git：采用这个后端后，控制面自身多了这个运行前置，交付检查要覆盖"只有控制面、没有本机 Agency 与工具箱"的部署。不多一种二进制，依赖的位置确实扩大了。
- 布局两种都在接口后面：按 Repo、Project、对象种类、版本分目录，或按摘要寻址加一份小索引。本地裸库到随包平台的写穿镜像，是"交付到另一个单元"的一种实现，完成条件见第 5 点第 3 步。选 Git 不自造版本存储是纪律三：按摘要寻址、不可变、去重与增量传输、fetch 与 push 的复制、任何 Git 工具与平台界面都能直接看，都是现成的。
