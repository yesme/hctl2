## 背景

所有者与 Codex 的对照讨论全文在 `.memo/notes/hctl2_grokbot_compare.md`（1053 行，基线 v0.18.2）；讨论后半所有者提炼的三条观点——数字伙伴 vs 项目与承诺、agent 互聊不增值（价值来自多样性与机械制度）、用扩展 TAMP 管伙伴——GLM 已做独立核读。本文是 GLM 作为审阅方给主笔的落文档建议：哪几处值得动、建议文本是什么、哪些明确不动。**总判断：不需要推翻重写任何现行设计**；讨论自己也收敛到这个结论（原文末节"批判的武器不能替代武器的批判"——下一阶段最大的投入是把 P2.1 跑起来，不是继续增厚设计）。

## 讨论内部的三处修正，按最终形态采信

讨论是来回修正过的，采纳时别按中间版：

1. **"多 agent 对话无效"的收窄版才是结论**：互看、讨论、趋同没有稳定证明优于独立求解加聚合；增加通信本身不能当质量依据；有明确分工、异构信息源、外部工具反馈、独立核验的多执行者仍然值得。讨论引用的两篇（Debate or Vote、The Cost of Consensus）就是 `docs/research/multi-agent-effectiveness-20260908.md` 里的 Choi 与 Bertalanič——收窄版与仓库研究自己的边界一致。**要写进文档的必须是收窄版**，口号版会误导后续实现者把"砍通信"做成"砍分工"。
2. **"缺长期角色是产品缺口"被撤回为"定位选择"**（讨论第五节修正第二节）。Participant 三层表（长期角色／本次任用／本次执行）不进规范；只留"低成本复用熟悉的执行能力"（收藏、常用阵容、选人偏好预填）作候选。
3. **"持续跟进 ≠ 常驻监工 Bot"**（第四节末修正第二节）：跟进由持久状态、事件与确定性规则承担，只在需要判断时唤醒模型；**让模型输出 JSON 不等于把协调机械化了**——真正移出推理循环是代码直接依据已记录事实与规则作决定。这条是过滤 Grok 学习清单的关键尺子。

## 建议一：`delivery.md` §自举阶段 加"省"的验收尺子（最优先，现在就值得落）

讨论全文最能立刻兑现的一条，也是"实现反过来裁剪设计"的机制本身。建议文本（可直接用）：

> 自举验收的"省"按交付计总账：每份经核验的合格交付，计入全部消耗——失败、备用、返工、读回、评审与协调的 token 一并计入，不按名义口径报。每新增一轮模型调用，要能说明它带来了什么新信息、证据或必要判断；只是搬运状态、重复规则、维持对话的部分应交给代码或删掉。三个直接问题随时可答：比直接操作 Harness 省事吗？同等验收要求下省 token 吗？出了问题之后更容易继续吗？

落点：`delivery.md` §自举阶段（B5 附近），与现有"门触发计数"段并列。理由：它把 `run.md` 已有的成本度量（Gate Receipt 逐票 token、关键路径与总 token 观测）接到产品验收层，给 P2 实现一把现成的尺子；讨论末节"实现也会发现哪些设计不值得兑现"靠它才有据可裁。

## 建议二：`vision.md` 反定位写成两条轴（替换此前单句否定的想法）

比"不做数字伙伴"一句更准的写法是讨论第五节的四象限——**组织中心轴**（伙伴 vs 项目与承诺）×**协调机制轴**（临场对话 vs 确定性规则）。Grok Bot 在"伙伴 × 对话"格，HCTL2 在"项目 × 规则"格，另两格（伙伴 × 规则、项目 × 对话）各点一句即可。建议文本：

> 连续性放在哪里，是一条产品轴：Grok Bot 式的数字伙伴让角色跨任务延续，HCTL2 让项目与承诺延续，再为每次工作选入执行者——伙伴可以是推荐结果，不必是事实的组织中心。协调靠什么是另一条轴：临场模型对话，还是持久状态、事件与确定性规则——HCTL2 把不需要智能的工作从模型的推理循环里移出去，模型只在需要判断时被唤醒。两条轴独立：长期伙伴不必持续消耗推理成本，按次选人也不自动更省。

落点：`vision.md` §要解决什么不解决之后新增一小段，或并入 §一句话定位后面的展开；"从推理循环里移出去"半句可同时替换 §设计原则"省"条尾巴。注意愿景层不点"数字伙伴"以外的具名产品——Grok Bot 的名字进 research 文件，不进愿景。

## 建议三：五模块"制度表"进设计地图（可选，或只进 research）

讨论第八节的这张表是全文最好的产品叙述，每行三列说清一个模块"替协作省了什么"：

| 模块 | 系统承载的协作制度 | 省掉的模型劳动 | 仍值得调用模型的部分 |
| --- | --- | --- | --- |
| Room | 目标、已决事项、来源、正式承诺与讨论的区别；上下文装配规则 | 每次重读完整聊天、复述共识、猜哪些话算决定 | 澄清目标、比较方案、发现未解决的矛盾 |
| Task/Kanban | 契约、状态投影、阻塞条件、完成证据 | 反复问进度、读聊天猜完成、重复整理机械状态 | 判断新需求的影响、提出优先级建议 |
| Run | 获准执行图、前置、派发、超时、重试、计票与停止规则 | 不断决定"轮到谁、还等不等、要不要催" | 解决执行中的新问题、理解失败、建议改计划 |
| Participant | 能力与配置记录、席位职责、权限、精确派工与输入通道 | 每次协商谁负责什么、重复介绍角色、靠对话转发输入 | 专业求解、独立核验、用不同方法取新证据 |
| Repo | Git 事实、写入租约、版本、检查状态、发布与集成回读 | 盯 PR 状态、口头报告是否合并、凭散文判断版本对应 | 理解 diff、修代码、分析复杂冲突 |

落点两选一：`README.md`（设计地图）§共同规则 附近一小节；或只进建议四的 research 文件、设计地图加一行链接。倾向前者——它同时回答"为什么有五个模块"这个 README 现在答得偏弱的问题。若落 README，表按现行词汇改写（"Task/Kanban"拆开按现行称呼，"模型"统一写"模型"或"执行体"按层规）。

## 建议四：对照调研落 `docs/research/`（纪律三）

`hctl2_grokbot_compare.md` 有 27 项一手来源、区分了产品叙述与专门文档口径（"每 Bot 一台电脑"实测是账号共享云电脑、屏幕不是隔离边界）、"未找到公共定义"没有写成"不存在"——比多数已有 research 文件扎实。建议以它为底稿出 `docs/research/grok-bot-comparison-20260916.md`：复用决定标"仅参考行为"，与 `multi-agent-effectiveness-20260908.md`、`governance-attrition-20260908.md` 互引（多样性＋机械制度两条证据链在此汇合）。TAMP 两份（`.memo/notes/TAMP-design-doc.md` 及其评审稿）属演进材料，留 memo；research 索引互引即可。research 文件里可保留 Grok Bot 具名——那是选型对比的合法场合。

## 建议五：Grok 启发的候选池——登记，不实施（`.memo` 待裁清单）

讨论第二节的建议经三处修正过滤后剩七条，按讨论自己的优先序登记，每条标"等 P2 实现检验后再裁"：

1. **有范围、有期限的协作授权**（Room 范围内自动路由，越界找人）。讨论第一优先；**性质是授权制度改革**——与现行"普通 Room 每条执行边由人提交"相反，须所有者单独拍板，不能当 UI 改进混进小批。可先做无损的一半：模型交接建议自动带上下文预填下一次 Trigger Preview。
2. **无 Run 路径的有限跟进责任**（首次授权含"评审意见与检查失败的处理到可交付"）。核实 v0.18.3 仍写"无 Run 路径没有自动返工"（`repo.md` §一次变更走一遍 第 6 步），缺口真实。落地形态按修正三：跟进靠事件与规则（订阅 CI、按冻结规则推进、失败收集证据后唤醒模型），不是常驻协调 Bot；预算、截止、无进展升级写进授权。
3. **Agent 维护看板的默认产品责任＋组合命令**（一次"合进去并完成"决策驱动集成、验收、写回多个后台事务）。保留独立验收，减的是用户在模块间来回结算。
4. **Agency 可选图形工作表面**（桌面观察/接管）。六件事照讨论写死：观察目标（哪个派工）、能力类型（状态/事件/终端/截图/图形流/回放）、输入权限（四种分开）、生命周期（断线/替代/重建的失效降级）、隐私与共享、证据地位（观测≠验收）。headless 保持完整可用；不把宿主机或桌面地址变成 Participant 身份。
5. **Project 可引用 0..N Repo**（先调查后绑定、目标跨仓库）。改动大：跨仓库依赖、部分完成、补偿都要处理；渐进路径是先用户级入口＋跨仓库只读调查。
6. **平台按需接入**（首次只修本地问题时不必先建本地平台；已有 GitHub 就用 GitHub）。
7. **合并策略按仓库预批准原生形态**（固定源版本＋方式＋保护条件，条件满足允许平台合并；严格形态留给点名要固定目标基线的工作）。现行"两种授权形态"已容纳它，改的是缺省与预览体验，不是机制。

**基线漂移提醒**：讨论用的是 v0.18.2，其中看板部分的批评（"一个 Repo 一个 Board"）已被 D 批 v0.18.3 吸收（任务源零到多＋合并板投影已落）——上表不含任何看板多源项，只剩 3 里的维护责任与组合命令仍有效。

## 建议六：TAMP 接缝一句（`participant.md` 延长线）

让后续 harness 能找到这条线：工种能力评价（声明、背书、实测、独立验证四层，按任务族校准，配置变化后旧成绩只作先验）→ 匹配四段 Recall／Gate／Rank／Award；**边界：TAMP 是 Participant 选型与 Agency 供给匹配的能力，不另建 Task／Run；常规任务先用静态规则与已有评价，避免测量税与撮合延迟**。这一句把讨论第六节的飞轮（制度→记录→校准→推荐→减少试错）接到了现行对象模型上：制度产生可比较的执行记录，记录支持能力校准，校准改善推荐，推荐减少试错与无效协调——伙伴可以越用越合适，而这种改善不靠聊天维持。

## 明确不建议做的

- **不推翻、不重写 Participant 模型**：讨论自己撤回了"长期角色缺口"的判断；两条轴的表述（建议二）就是"这是选择不是缺陷"的正面写法。
- **不现在动 Room 授权规则与 Repo 接入默认**（候选 1、5、6）：都是实质的制度改革，等 P2.1 跑通第一条链路、拿到建议一的账本后再裁——讨论末节的结论正是这个顺序。
- **文档不再增厚**：六条建议里只有建议一属于"现在就该落"；二至六可在 P2 期间顺手，别为它们单独开大批。
