# 用户路径对齐：三段旅程 vs 五模块架构（v0.18.6）

> 状态：讨论中 · 只分析不改设计<br>
> 基线：main @ `31ccffc`（草案 v0.18.6）<br>
> 去向：所有者逐条裁决——口径类直接吸收进用户路径文案；结构类要么维持现行约束、要么走设计变更（决策史记转折、约束 bump 版本、配 CT 失败用例）。与 F 批（#246，Project 与 Task 解耦）重叠的问题建议并入该批一起裁<br>

## 定位与重述

所有者给出 Workbench 的三段用户路径——新建项目（SCM 地址 → 看板 → 聊天室）、产生 topic（聊天归纳出子聊天室、聊天里操作 task 与生成 Run 施工图）、观测 Run（导航三分、Run 双视图、worker 三视图）——要求对照多模块架构找出冲突与需要的修改。本文逐条对到 v0.18.6 的五模块（Project、Task、Run、Participant、Repo）与单元模型上，每条给出：现行设计怎么说、冲突在哪（还是只是口径）、建议怎么改。**本文不修改任何设计文档。**

## 总判断

先说结论：**这条路径与现行架构的相容度非常高，多处设想已经是设计本身**——

- 「新建 project 选 SCM 地址」≈ 现行的「注册仓库 + Project 同事务建 Repo Room」（[spec/project.md:37](../../docs/design/spec/project.md)）；
- 「本地另搞一套用 Gitea」≈ §36 已裁定的**随包本地平台，选型就是 Gitea**（[decision-history §36](../../docs/design/references/decision-history.md)）；
- 「任务①推荐 SCM 自带 issues」≈ D 批缺省建议项（[spec/task.md:26](../../docs/design/spec/task.md)）；
- 「快捷模板生成 DAG」≈ v0.18.4 裁定的**缺省施工图模板**（[交付文档·运行默认值](../../docs/design/delivery.md#运行默认值)）；
- 「从 Agency 那边选 participants」≈ v0.16.0 的工种（Profession）名册选人模型（[participant.md](../../docs/design/participant.md#agency-与执行体)）。

真正的分歧集中在四处：**闭包的层级**、**看板绑定的归属口径**（恰与 F 批 #246 撞车）、**(b) 路径的正当形态**（外部来源仓库不能换绑本地平台）、**worker 三视图里 VM 一档**（与已裁定的「Docker/VM 不做桌面沙箱形态」相抵）。逐条分级：

## 逐段对照

### 《新建项目》1：建立 project（SCM 地址、attach/detach、闭包）

**现行怎么说。** Repo 是第五个模块：仓库是**人在控制面登记的逻辑身份加声明的平台绑定**，身份不写进代码树、不登记每份克隆、不从 URL 或相同提交推断合并（[spec/repo.md:39](../../docs/design/spec/repo.md)）。注册确认事务激活唯一 Repo 身份，Project 在同一控制面事务创建其唯一 Repo Room；「创建 Project」命令又在同一事务创建唯一 Project Room（[spec/project.md:37-39](../../docs/design/spec/project.md)）。一个仓库可以开多个 Project；候选池 #4（Project 引用 0..N Repo）是真规范变更，留待以后。

**对照。** 「在主界面新建 project、选一个 SCM 地址」= 一个向导复合「注册仓库（若未注册）+ 创建 Project + 两个 Room」，方向与现行完全一致。两个细节写实：

- **① remote 地址 → 完成**：现行注册不要求本地有 clone、不向代码树写身份（[spec/repo.md:43](../../docs/design/spec/repo.md)），所以「给 URL 即完成」比旧架构更成立了；要补的只是向导里的身份确认（平台与仓库标识由人声明，远端地址只作辅助证据，冲突时预览列出供人确认）。
- **② 本地地址上溯 remote**：(a) attach 即「来自外部平台的仓库绑定该平台」，本机 clone 只是参与者的工作副本——完全一致。(b) 见 C5，两个修正：**其一，不需要物理 detach**——判据是登记声明的平台在哪，工作副本是否配远端是参与者的便利操作、不是登记生效条件；**其二，顺序很重要**——「外部平台仓库绑定或换绑到本地平台时拒绝」（[spec/repo.md:41](../../docs/design/spec/repo.md)），所以想走 Gitea 必须在**登记时**就声明为只在本地的仓库（上溯出的 remote 作为冲突证据确认），而不是先按外部仓库登记再换绑。声明成立后：控制面在本地平台（Gitea）建仓、持凭据单元交付初始代码、给工作副本加远端，此后与外部平台仓库走完全相同的一条链（推分支、开评审请求、检查、按保护规则合入、回读凭证）。反过来，(a) 路径下本地平台不参与、**不建镜像**。

**闭包注记（C4）。** 「ctl+project 把 task、run、participant 等概念都兜住」要按单元模型（v0.18.0）修正成三层，否则与两条已裁事实相抵——Agency 名册上的工种跨控制面供给（「一个仓库同时被多个控制面开 Project 是常态」，Agency 给每个配对控制面开隔离租户）：

| 层 | 闭住什么 | 什么在闭包外流动 |
| --- | --- | --- |
| 控制面 | 全部治理记录与判定（多个 Repo、多个 Project 的身份、授权、凭证） | 工种从 Agency 名册收进来（冻结引用，不是定义权） |
| Project | Task/Run/Room/Request/Memo/Artifact 的事实与选入记录（Room 名册、Run 席位） | Git 与平台是共享底座，跨控制面 |
| 仓库 | 仓库身份、变更集、写入租约、集成意图与凭证 | 工作副本由参与者自己管理 |

表述改法：「**事实闭包在 Project，治理闭包在控制面，供给与底座跨闭包；Project 之内 1:N 复杂连接不受限**」。task/run/room 的事实确实不出 Project；participant 的**选入记录**也闭在 Project 里，闭包直觉成立——但身份的供给（工种、Skill、执行配置）在闭包外，这正是「稳定的是参与者身份、变化的是实现方式」能跨项目成立的原因。

### 《新建项目》2：绑定 kanban

**现行怎么说（D 批 v0.18.3）。** 任务 content 的家按**仓库**绑定的任务源来定：一个仓库绑零到多个（平台自带 issues、本地任务服务器、Linear）；缺省源由人显式选定，缺省建议是平台自带的 issues；**启用看板的 Project 恰有一个源引用**（采用仓库缺省建议即继承，Project 保存自己的引用；之后仓库缺省变化不搬既有的卡）；「两层选择可以在同一个预览里确认」。一张卡一个家、认领不搬家；看板场景是 Repo 级一张合并板——本控制面所知各任务源的投影；分组两套：源内分组（milestone、Linear project、标签）只在该 Project 的缺省源里建，跨源归组靠控制面的 Task→Project 记录；认领后卡在外源的分组与 Project 归属脱钩。

**对照。** 用户的①②③三分法与候选序**已经就是现行缺省与交付顺序**；「project 有且只能有一个 task-kanban」在 project 级也基本成立——但归属口径要按上表改：**选择动作可以在建 project 的向导里做（一次预览确认两层），绑定的家在仓库、引用在 Project、板是仓库级合并板**。仓库第二个 project 建立时这步直接跳过（源引用继承）。「把 tasks 读回来并可视化」= Snapshot + 操作投影 + 合并板，现行原生支持。

**与 F 批的关系。** 所有者 09-17 已把「Project 与 Task 解耦」立为 F 批（#246）。本段的归属口径（源绑仓库 vs project、合并板与脱钩）正落在这一批的射程里——建议把 C6 的最终措辞并入 F 批一起裁，本文先按 v0.18.6 现状对齐。

### 《新建项目》3：建立聊天室

**现行怎么说。** Room 随 Project 已存在（同事务创建）；选人是 v0.16.0 之后的工种模型：**Agency 定义工种**（名册上的一类可派的人：哪个 Harness、什么模型、带哪些 Skill、条款），**人从名册里选**工种实例进 Room 或 Run 席位，控制面准入并记录，Agency 不替人选。选人发生两次、各自独立：建 Room 或 Trigger Preview 时选**规划者**（进名册、参与讨论、建议下一次调用），启动 Run 的预览时按席位要求选**施工者**——「像选设计局与选施工单位」。Room 里的 `@` 只解析本 Room 名册里的规划者；要和正在执行的施工者说话，进绑定那次执行的 Execution Chat。

**对照。** 「从 Agency 那边选 participants」在 v0.16 之后是**正确方向**（旧版架构里这是 BYOA 病，现已不是）。三个精确化：其一，Room 不是选完人才「做好」——Room 随 Project 在，第三步的领域含义是「邀请规划者进名册」；其二，此时选的是规划者，施工者要等 Run 启动预览时按席位另选，两次选人不共享；其三，跨仓库/跨 Room 借用阵容作预填的机制现成。「topic room 选人环节一样」同理成立。

### 《产生 topic》1：聊天归纳 → topic 聊天室

**现行怎么说。** Room 里的分诊不另立阶段：采纳契约就是「可执行」、留一张无契约卡就是「不做或未定」、开一间 Scoped Room 就是「需澄清」；模型可以在 Room 里贴建议卡，采纳由人做。Scoped Room 创建时冻结 parent、讨论目标、完成条件与**回填动作**；闲置 14 天（无新消息且未回填）缺省进需要关注。出生来源链机制（父房间滚动纪要预填提升预览、显式选择、去敏、不活体渗入）现成。

**对照。** 「系统不断总结『这个 topic 可以做（Yes/No）』、点了开新房间」= 模型建议卡 + 人批准 + Scoped Room——形态兼容。三个约束：其一，回填动作按 parent 分轨（C8）：**parent 是 Project Room 才能回填 Task 提案；parent 是 Repo Room（还没有 project）只能回填「升格 Project」**——Task 创建需要 project 归属。其二，「不断更新和总结」过注意力与成本两条纪律：v0.18.4 原则 2 恰好立了尺子——「没有新信息的协调不进模型循环」；建议归纳低频聚合、可关，缺省用零模型成本的显式引用与讨论窗口，配置 small-brain 才做滚动总结。其三，不新增第四类 Room（L13）：topic room 就是带生产型回填动作的 Scoped Room。

### 《产生 topic》2：聊天操作 task、DAG 快捷模板

**聊天操作 task（C9）。** 「类比 topic room 的产生建议」正是正确形态：建议/动作卡 → Trigger Preview（改哪张卡、哪个版本、什么后果）→ 结构化提交；聊天文字、正文 `@`、模型总结都不是命令。「删除 task」映射「取消 Task」（HCTL 侧 lifecycle）或后端卡删除（content tombstone）。三清单（已决/尚未定形/出界）是现成的操作底座：只有「已决」里能写成「交出什么、凭什么算交出」的条目才是节点候选。

**DAG 快捷模板（C3）。** 这条**已经是设计**：v0.18.4 裁决「跟进到可交付走缺省施工图模板」——施工、机械检查、返工（上限 2 轮）、评审关卡一席、按仓库授权形态合入；批准施工图与开工**可一次预览提交**（各自的准入与读回前置照旧）；模板随发布包提供。用户的「快捷模板 + 交互式表单」是它的 Workbench 形态，表单可从三清单与 Task 契约预填。守住一条产品尺子即可：模板是「需要持久自动施工」的入口，**简单工作默认走无 Run 轻量路径**（有契约的 Task 人只预览两次：合入、完成），不把每张卡都引导成画图。

### 《观测 Run》1：左侧导航

兼容（C12）。Workbench 是组合式场景客户端，导航是客户端状态。两点补充：「Kanban」格的诚实口径是仓库合并板在该 Project 上的过滤视图（缺省源 + 跨源归组）；建议补第四格「需要关注 / Request 收件箱」——Request 是一级对象、目标体验要求用户随时回答六个问题（谁在等我提供什么、哪个 Run 在等什么），S2 参考用例已把四种不顺利情形写成正式场景，导航缺这一格就只能靠通知，通知会漏。

### 《观测 Run》2：Run 双视图与 worker 步骤

兼容（C12）。「内容介绍」= 施工图（Workflow Revision）与施工清单投影；「DAG 拓扑」= 引擎机械位置 + 账本语义状态（交付义务/席位/尝试）双投影，并行进度、节点/席位/尝试渐进展开是 Workflow 场景既定能力；「最右侧分栏展示每个 worker 在做哪个步骤」= 各次派工的结构化执行流——正是默认观察视图。写进 UX 约定的一句权威口径：**图与进度是投影，事实在治理记录**；引擎位置与账本可能分歧待对账，Workbench 不把引擎状态渲染成语义「完成」。

### 《观测 Run》3：worker 三视图

需要拆维度（C10）。三种展示混了三个正交的轴：

| 轴 | 取值 | 由谁定 |
| --- | --- | --- |
| 运行形态 | headless（无 TTY）/ TTY / 加固域 | Worker Profile 声明、Execution Spec 冻结；加固只按宿主 OS 原生机制施加 |
| 观察阶梯 | 结构化执行流（默认）→ PTY 转录（诊断）→ 终端接管（最后一级）；恢复等级五档（exact attach / native handoff / structured inspect / semantic resume / replay） | 客户端选择，观察总可行；等级由 Agency 声明并负责 |
| 输入策略 | 受租约单写者 / 允许原生交互（来源不完整如实标注） | Execution Spec 冻结；切换走新规格 |

- **③ headless**：就是默认形态——无 TTY 的派工也有结构化流可看。
- **② TUI**：兼容——本地 Agency 参考实现（内部运行时 Herdr）的原生界面是正常 Terminal 客户端，输入按该次 Execution Spec 冻结的输入策略处理。
- **① VM 视图（C11）**：与已裁定取值相抵——技术基线写死「Docker 不做统一打包方式，也不做 Harness 的沙箱或桌面形态」「执行加固只按宿主 OS 原生机制施加」。若所求是 Grok Bot 那种 Agent Computer 图形工作表面：本地形态维持裁定不做；「观察面能力分级（图形工作表面）」已在候选池 #3 登记（六件事：观察目标、能力类型、输入权限、生命周期、隐私与共享、证据地位），远程 Agency（云上 VM 内跑 harness）属第二期交付范围。建议归入这两处等 P2 后裁，不为此重开沙箱裁定。
- 「根据 Agency 选择时的要求」改为「按该次执行冻结的 Execution Spec 声明」——Agency 能力在 Worker Profile 绑定时声明，观察某次派工时只按它当时的 Spec 与票据。

## 修订后的用户路径 v2（兼容版重述）

**《新建项目》**

1. 主界面「新建 Project」→ 给出 SCM 地址或本地路径。一个向导、三层事实：登记仓库（声明平台归属——来自外部平台则绑定该平台，本地则缺省绑定随包本地平台 Gitea；clone 是否配远端由参与者自己安排，不需要 detach）→ 创建 Project 与 Project Room（同事务；仓库的 Repo Room 已在登记时建好）→ 首个用看板的 Project 在同一预览里确认两层：仓库缺省任务源（建议平台自带 issues）与 Project 源引用。
2. 任务读回为快照与投影；Project 的看板 = 仓库合并板在该 Project 上的过滤视图；一张卡一个家，认领不搬家。
3. Project Room 已在；从 Agency 名册邀请**规划者**（工种实例）进名册、定职责与预算。调用前的 Trigger Preview 摊开整条身份链：这次由哪个工种、哪台机器、什么模型实现。

**《产生 topic》**

1. 讨论中出现可立项的 topic 时，系统低频聚合提示（可关；缺省零模型成本）；批准后开出该 topic 的 Scoped Room——冻结 parent、目标与回填动作，父房间相关讨论经提升预览显式选入。Project 内的 topic room 可回填 Task 提案；Repo Room 里的 topic 只能回填「升格 Project」。闲置 14 天进需要关注。
2. Room 里对 task 的操作走 建议/动作卡 → Trigger Preview → 提交；删除即「取消 Task」。需要跟进到可交付时，用缺省施工图模板（施工、检查、返工上限 2、评审一席、按仓库授权形态合入），批准与开工一次预览提交；简单工作走轻量路径，人只预览合入与完成两次。

**《观测 Run》**

1. 左侧导航每 Project 四格：看板（合并板过滤视图）、Room 列表、Run 列表、需要关注（Request 收件箱）。
2. Run 条目两个视图（施工任务书 / DAG 拓扑与进度）+ 右侧 worker 步骤分栏（各派工的结构化执行流）；图与进度是投影，事实在治理记录，引擎分歧如实标注。
3. 点开 worker：默认结构化执行流；Spec 声明 TTY 时可转录或接管（恢复等级按 Agency 声明），输入按冻结策略与票据；图形工作表面（VM 式）为候选池 #3、远程 Agency 第二期，本地不做。
