## 一、三条原则（所有者原话）

1. 入口应该是意图，而不是 bot 或 task。这也是为啥 HCTL2 有 repo room。
2. 分类移到后台。所以 chat room 会动态总结：是不是要新开 topic room，是不是涉及某些 tasks 的 CRUD，是不是要跑一个 DAG/Run。
3. 可观测性非常重要。AI 越能自组织，用户越需要可观测性，例如可以看到 harness 在干什么。

一句话版（Codex 压缩、所有者认可）：让用户说事情，让系统组织事情；组织过程可检查，执行过程可观察，关键决定可控制，交付结果可核验。

## 二、主笔的判断，对到 v0.18.7

**原则一，成立，现行已经这么长。** 进入 Project 就是进它的主 Room，先说事再长出 Topic、Task、Run；Task 是塑形的产物不是前提。补两个让「意图入口」不退化成「什么都能聊的框」的条件，现行都有、只是没写成原则：入口自带一个可见的范围边界，即 Project 这个命名空间盖在一个 Repo 上，跨仓库、扩权限必须显式；房间的可见状态是三张清单（已决、尚未定形、出界），用户审业务含义不审对象类型。所有者说的「repo room」按 #257 的 C2 裁决就是 Project 的主 Room。

**原则二，方向成立，现行差一个机制。** 今天模型只能在被调用时贴建议卡，没有合法又省的「持续归纳者」。主张用 Room 级缺省施工图「归纳」来做：安静 M 分钟或新消息不少于 N 条才触发；只读；预算随建 Room 时的一次批准冻结；产出只能是对三张清单的改动建议，再由清单条目机械地映射成 Topic、Task、Run 的候选卡；人点 Yes 走 Trigger Preview。省在没有新消息不跑、没新候选不更新、每次只读增量；干净在不越过「临场执行边由人提交」。自动建议开出的 Topic 要带「为什么开」的提要和「预期回什么」的一句，否则自动生成的房间没人收；这修正了主笔前一份备忘里「普通 Topic 一律不要求回填」的说法：人开的普通 Topic 不要求，机器建议开的要带。

**原则三，最重的一条，因为它是前两条的代价。** 用户亲手选人建卡时负担重但心里有数，系统代劳之后那份「有数」要用观察补回来。分三层看：事情层现行有，是「待你处理」和四问；执行层现行有，是结构化执行流、终端阶梯、证据三档，模型自述不替代观察；缺的是组织层，「系统为什么这样安排」。HCTL2 在这一层有独特优势：每一步组织都是带来源的类型化记录，采纳带回链，Topic 带前情提要与来源，Run 带冻结清单，「为什么」是机器能回答的，缺的只是把来源链摆出来的视图。可观测要接上干预边界：改未采纳的候选很轻，改活动 Run 的契约与权限走版本与替代，停止不等于撤回已发生的副作用。

## 三、Codex 评述里采的、收窄的

全文在 log。采：三点是一套逻辑而不是三个界面要求；后台做的是关联、状态、提案、授权核对、回流五件事，不是打标签；模型出语义判断、代码持有已定状态；不同对象变化门槛不同，正好是现行分诊规则；系统承担分类就得承担复用、合并、结案、回填；成型格式是系统协助产生的成果不是入口表单；用户审业务含义不审填表；组织增益从用户表达意图开始计时；强单体基线；统一入口不等于唯一模型、不等于共享记忆，需要精确定位时结构仍可达。

收窄两处。一，「已有授权能覆盖的动作可以按规则推进」：在 HCTL2 这个「已有授权」必须是冻结对象，缺省施工图或 Run，不能是 Room 级常设委托，否则回到聊天里连续派工。二，六项指标好，但并进交付文档「省」的验收总账，不另立一套；其中「形成可执行承诺的成本」是总账里没有的一项，值得加。

## 四、与所有者研究文件的接口

`collective-intelligence-research-20260918.md` §2.2 说最强的对应点在塑形阶段，另一个参与者的最大贡献可能是发现问题表示有缺陷；§2.3 把规则分认知、协调、治理三种，动态的认知分工与稳定的授权边界不矛盾。三条原则落在这两节上：原则一与二是认知规则与协调规则的产品形态，原则三是治理规则要求的可见性；「建议接下来找谁」不能悄悄变成「已经有权调用谁」，就是归纳机制只产建议卡的理由。

## 五、若落，三处加一个机制

| 处 | 改什么 | 层 |
| --- | --- | --- |
| `vision.md` 设计原则 | 加一条：以意图为入口，不要求用户先选执行者或对象类型；系统在 Project 范围内识别关联、组织话题、形成承诺；自动组织不扩大授权；每一步重要推进可追溯到有效承诺、执行依据与实际证据，并有观察与干预入口 | 愿景，不改约束 |
| `docs/user-experience/04` | 组织层可观测：每张卡、每间房、每次 Run 的来源链视图，从「这个承诺为什么没完成」追到「哪个执行、哪个版本、哪个检查在阻塞」；干预边界按轻重分 | 体验，不改对象 |
| `delivery.md` 自举验收总账 | 加「形成可执行承诺的成本」一项：从自然请求到双方认可的契约，多少时间与有效澄清 | 交付 |
| 归纳机制 | Room 级缺省施工图「归纳」：触发、只读、预算、只产建议卡；机器建议开的 Topic 带提要与预期回填 | 约束，单独出方案、配失败用例，是这四处里唯一要拍的 |
