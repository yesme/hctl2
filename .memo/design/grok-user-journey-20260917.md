所有者口述了一条 Workbench 主路径：新建项目 → 绑看板 → 选人开聊天室 → 聊天里长出 topic 与 Task → 左侧看 Kanban / Room / Run → 点开 Run 看施工图与工人。本文把它逐步对到现行五个模块和多单元拓扑（参考用例 S1），分清三件事：已经对齐的、只是向导/信息架构、会改约束的。不改 `docs/`。

对照用的尺子是现行正文，不是 8 月底的四模块稿。现行模块是 Project、Task、Run、Participant、Repo；Agency 是派出方单元，不是模块；仓库是底座，不是可独立停机的单元。

---

## 1. 一句话

这条路径作为**一个控制面上、一个 Project 的主界面故事**，和现行架构大体同向，不必另起一套对象。真正要拍板的只有几处：topic 聊天室是不是新的长期房间、有远端的本地检出能不能改挂 Gitea、界面上的「一个项目」要不要把仓库登记藏进向导。其余（从 Agency 选人、平台 issues 作缺省看板、缺省施工图模板、Run 列表看 DAG 与工人、headless / TUI / 虚拟机三种观察）现行已经有落点。

## 2. 「ctl + Project 闭包」怎么读

口述：「ctl 和 Project 是一个闭包，后边所有概念都兜住；Task、Run、Participant 等不会越过这个边界；边界之内对应关系可以 1:N 且复杂。」

对照多单元（S1 与 `architecture.md`「单元与连接」），建议读成下面三层，不要读成「一个控制面只能有一个 Project」或「控制面按 Project 各起一份账本」。

| 层 | 现行事实 | 闭包里吗 |
| --- | --- | --- |
| 控制面 | 一本用户级账本；一个人可以跑多个控制面；一个前端可以连多个控制面 | 闭包的**外壳**：授权和判定发生在这里 |
| Project | 属于某个已登记的仓库；同一控制面、同一仓库上开多个 Project 是常态（S1.1：`mac_ctl` 在 `gh-jssdk` 上开两个 Project） | 闭包的**内壁**：Task、Run、Room 名册、选入记录、Request 不跨 Project |
| 仓库（Repo） | 底座。Git 身份与平台绑定活得比任何一个 Project 久。同一仓库被两个控制面各开 Project 也是常态 | **不在** Project 闭包里。代码、评审请求、合入在仓库/平台上，各 Project 各自认领、各自验收 |

边界之内现行已经是 1:N：一个 Project 多个 Task、多个 Run、多个 Scoped Room、多次选入。Task 与 Run 一对多、Run 与评审请求一对一，已写进 Repo 约束。口述的「对应关系可以非常直接相连且复杂」与此相容，不需要新的连接对象。

不要把闭包读成：

- 控制面按 Project 拆账本（与「一本用户级账本、一人多机连同一本」冲突）；
- Agency、聊天服务器、Gitea/GitHub 跟着 Project 各装一份（它们是可被多个控制面复用的单元或内容系统）；
- 人是 Participant（现行：人不干活，人拍板；Participant 模块只管数字参与者）。

界面上可以把「打开这个项目」画成一扇门，门后是 Kanban / Room / Run。门框仍是「这个控制面上的这个 Project」，门牌上可以写仓库名，但仓库不是这扇门里的家具。

## 3. 逐步映射

判据三种：**已对齐**（合同不用动，向导按此做）；**产品向导**（顺序和藏法，不改对象）；**会改变含义**（要拍板，过了才改约束和 CT）。

### 3.1 新建项目 · 建立 Project 并给出 SCM 地址

口述：Workbench 主界面「新建一个 project」，选一个 SCM 地址。远端地址则完成；本地 git 先沿 `.git` 上溯远端，再选 (a) 推荐：attach 到远端做后续，或 (b) 在本地 detach 掉 remote，用 Gitea 另搞一套；纯本地走 (b)。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 选 SCM 地址作为入口 | 产品仍是「打开仓库」：登记 Repo、声明平台绑定，再开 Project。`CT-WORKBENCH-IA`：打开入口按 repo 选择并映射到控制面 | 产品向导：主按钮可以叫「新建项目」，提交时拆成「登记仓库 + 创建第一个 Project」。不要删 Repo 对象 |
| 远端地址 → 完成 | 来自外部平台的仓库：平台就是它来的那个（本批缺省 GitHub），本机只是工作副本；本地平台不参与、不建镜像 | 已对齐 |
| 本地检出且能上溯到远端 → (a) attach 到远端 | 同上。身份由稳定 Git identity 证明，remote URL 只是辅助证据；冲突时展示证据由人确认 | 已对齐。推荐项就是现行缺省 |
| 纯本地 → 在随包 Gitea 上建仓 | 只在本地的仓库缺省绑定随包本地平台（Gitea，已拍板）。注册时按持久意图在本地平台建仓，持凭据单元交初始代码 | 已对齐 |
| 有远端却选 (b)：detach remote，改挂 Gitea | 明文禁止：不为外部平台的克隆建镜像；评审与合入在来源平台上走 | **会改变含义**。见 §5.2 |

向导建议：人看见一步「新建项目 + 填地址」；系统做两笔账——Repo 登记（含平台绑定）和第一个 Project。同一仓库以后再开第二个 Project，走「在已有仓库上新建」，不要每次再问 SCM。这与 S1「一个仓库两个 Project」同构。

工作副本的 `git remote` 是参与者机器上的布局，不是治理命令。HCTL 不改、不删人家的 remote。选 (a) 只是「这个仓库的平台绑定指向那个远端」；(b) 若将来允许，也只是「登记一份只在本地的新仓库身份」，不是改 GitHub 上那个仓。

### 3.2 新建项目 · 绑定 Kanban

口述：一个 Project 有且只能有一个 task-kanban。① 推荐：SCM 默认的 task 能力（GitHub Issues 等）；② 其次：已有外部系统（Linear）；③ 本地方案。读回 tasks，可视化帮助理解。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 启用看板的 Project 恰有一个源 | `task.md`：「启用看板的 Project 恰有一个源引用，之后仓库的缺省建议变了也不搬既有的卡。」S1.X1：未显式同意就绑缺省源或建卡则失败 | 已对齐 |
| 推荐平台自带 issues | 缺省建议是平台自带的 issues（GitHub Issues，或本地仓库上 Gitea issues）。必须人点头 | 已对齐 |
| Linear 第二选择 | 人显式认领进该 Project，卡留在 Linear；Linear 只过身份与快照时不能作缺省源 | 已对齐 |
| 本地方案 | 本地任务服务器（Vikunja）可加绑；本地仓库还可以用 Gitea issues 当平台自带源 | 已对齐。不要把 Vikunja 和 Gitea issues 说成两套主路径 |
| 读回并可视化 | 合并板是本控制面所知各任务源的投影，不是新的权威表；卡内容以源为准 | 已对齐 |
| 左侧「这个项目的 Kanban」 | 仓库级有一张合并板（含未认领的卡、其他 Project 的分组）。项目页上可以只显示本 Project 分组 | 产品向导。不要把合并板改成「每个 Project 一张权威板」——那会让 GitHub Issues 这种天然仓级的源对不齐，也和「一张卡一个家」打架 |

「有且只能有一个」请钉在**源引用**：一个启用了看板的 Project 只认一个缺省源。仓库仍可绑零到多个源；别的源上的卡要进这个 Project，走认领，不搬家。

### 3.3 新建项目 · 建立聊天室（从 Agency 选人）

口述：有了 Project 就可以从 Agency 选取 participants，选好之后聊天室做好，里边有这些人。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 从 Agency 选 | 工种在 Agency 名册上；控制面收冻结引用；选入记录才产生 Participant。S1.2：「经 mac_agency 拿三个参与者」 | 已对齐。界面可以从 Agency 名册挑工种，提交的是选入，不是「Agency 成员」 |
| 选好房间就在 | 创建 Project 的同一事务创建唯一 Project Room。名册可以后填 | 产品向导：向导第三步再选规划者。不要把 Room 身份推迟到选人之后才创建 |
| 房间里就是选进来的人 | Room 名册是规划者。施工者在启动 Run 时另选，两次选人独立。人不是 Participant，人在名册里是 human actor | 产品向导：选人面板分「会拍板的人」和「从 Agency 来的规划者」。不要把人塞进 Participant 七层 |
| 一个 Project 一个主聊天室 | 一个 Project 一个 Project Room，进入 Project 默认打开它 | 已对齐 |

### 3.4 产生 topic · 聊天归纳

口述：聊天中冒出好主意，输入框上方或通知处持续总结「这个 topic 倒可以做，Yes/No」；人点一下，产生以该话题为主题的全新 topic 聊天室，选人环节与 Project 聊天室一样。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 系统建议、人点头才发生 | 普通消息不是入口。模型可以贴建议卡，采纳仍由人做。Trigger Preview 之后才提交类型化命令 | 已对齐。Yes = 打开预览，不是聊天正文直接建房 |
| 建议文案来自讨论归纳 | Context 萃取、滚动纪要、small-brain 都是可选辅助；缺省全本地。通知是投影，不是新对象 | 产品向导。第一期可以先做「人点建议卡」，自动归纳后做 |
| 全新 topic 聊天室，选人同 Project Room | 第三种房间只有 Scoped Room：有冻结目标与回填/结案，父名册预填后生成自己的选入记录，不活体共享；结论回填或显式结案后归档。一个 Project 仍只有一个 Project Room | **会改变含义**（若 topic 要长期存在、当第二个主房间）。见 §5.1 |
| 点 Yes 的产品含义 | 现行分诊：采纳契约 = 可执行；留无契约卡 = 不做或未定；开 Scoped Room = 需澄清。提升为新 Project 会离开当前闭包 | 产品向导，但 Yes 必须预览「将要创建哪一种」，不能一个按钮三种结果 |

### 3.5 产生 topic · 聊天里操作 Task 和生成施工图

口述：Project 聊天室和 topic 聊天室里都能通过聊天操作 tasks；也能用快捷模板为 Task 生成 Run 的 DAG，交互式表单填写即可。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 聊天里操作 Task | 类型化命令 + 预览。建议卡可以预填「创建 / 认领 / 完成」草稿，人确认后走同一命令 | 已对齐。不要让自然语言直接改 lifecycle |
| 快捷模板生成 DAG | 交付文档已有缺省施工图模板（施工、机械检查、返工、一席评审、按仓库授权形态合入）。批准与开工可以一次预览提交，各自准入仍分开。明确不做：通用可视化编辑器、模型自由生成后直接部署 | 已对齐。表单 = 填模板参数，编译成施工图版本，再预览批准/开工 |
| 等检查时不叫模型 | 缺省模板：等待检查不调用模型；返工超限、契约分歧、预算越限回到人 | 已对齐 |

### 3.6 观测 Run · 左侧三类、右侧工人

口述：每个 Project 左侧有 Kanban、Room 列表、Run 列表。Run 条目下有内容介绍和 DAG 拓扑；点哪个，最右侧都展示每个 worker 正在做哪一步。点介绍看任务书，点拓扑看执行到哪（可并行）。选一个 worker 则按 Agency 要求展示：① 类似 grokbot 的虚拟机，② Herdr 那种 TUI，③ headless 无输出。

| 口述 | 现行落点 | 判 |
| --- | --- | --- |
| 左栏三类 | 五个场景客户端的组合桌面。进入 Project 默认打开 Project Room。Overview / 需要关注是只读投影 | 产品向导。左栏是导航，不产生第六个场景。建议默认落地仍是 Project Room，与 CT-WORKBENCH-IA 一致 |
| Room 列表 | Project Room + 若干 Scoped Room | 已对齐（若 topic 不另立长期房间） |
| Run 一条目、介绍 = 任务书、拓扑 = 进度 | Workflow 场景：只读图、节点/席位/尝试渐进展开。引擎报告进度，HCTL 持有语义 | 已对齐。介绍对应冻结的施工图版本与施工清单；拓扑对应引擎路标在图上的投影。两者都是投影，不是两份权威 |
| 右侧每个 worker 在做哪一步 | 席位上的施工者 + 当前 Attempt。并行就是多个席位同时活跃 | 已对齐 |
| 选工人：虚拟机 / TUI / 无输出 | 默认无界面。观察阶梯：结构化执行流 → PTY 转录 → 终端接管。Herdr TUI 是原生 Terminal 客户端。Execution Chat 绑定一次精确派工，不是 Room | 已对齐为能力声明。grokbot 式虚拟机是某家 Agency 的供给形态，不是新模块、不是第一期必交。见 §5.3 |

## 4. 和多单元故事叠在一起时

口述路径是单机 Workbench 的主故事。S1 的多单元不否定它，只是给闭包外面加上几条边：

- 同一个 Project 的规划者可以来自本机 Agency，也可以来自远程 Agency（S1.3）。向导「从 Agency 选人」要能列出已配对的多家名册，而不是只有本机。
- ubuntu 可以只有前端、没有控制面（S1.10）。「新建项目」发生在某个控制面上，不一定发生在眼前这台机器的本机控制面。
- 两个控制面可以在同一个 GitHub 仓库上各开 Project（S1.6）。所以「选了一个 SCM 地址」不能推断「全世界只有我在用这个仓」。登记是本控制面的仓库记录，不是给 GitHub 上锁。
- 合入在平台上仲裁。本闭包的完成凭证仍只认本控制面事先采纳的证据。

这些不要求改口述路径的步骤，只要求向导不要写成「这个地址 = 全世界唯一的项目」。

## 5. 真冲突（要拍板）

### 5.1 topic 聊天室：长期房间，还是 Scoped Room / 建议卡？

现行房间只有三种：Repo Room、Project Room（一个 Project 一个）、Scoped Room（有目标、要回填或结案、然后归档）。Scoped Room 已经有自己的选入记录，选人环节可以做成和 Project Room 一样的面板。

若 topic 的意思是「先开一间临时屋把这个主意谈清楚，谈完回填成 Task 或结案」，映射到 Scoped Room，**合同不用改**。通知 Yes 打开「创建 Scoped Room」预览，目标预填为这条建议。

若 topic 的意思是「项目里长期存在的第二间、第三间主聊天室，和 Project Room 平级，各自一拨人一直聊下去」，则与「一个 Project 一个 Project Room」冲突，也与 Scoped Room 的归档生命周期冲突。这会改变 CT-PROJECT 的房间基数和归档用例。

建议默认取前一种。后一种单独立项：要么放宽 Project 与主房间的 1:1，要么给 Scoped Room 加「长期专题、不要求回填」的形态——两者都会改约束，本轮只记账。

还有第三条，不要默默走：把 topic 做成新 Project。那会离开当前闭包，和口述「不越过边界」相反。预览里若提供这一项，必须写明「这将登记/使用同一仓库上的另一个 Project」。

### 5.2 有远端的本地检出，改挂 Gitea

现行分得清楚：平台在哪，仓库就是哪一种。来自 GitHub 的克隆，评审和合入在 GitHub；Gitea 只给「从来没有平台」的仓用。不为外部克隆建镜像。

口述 (b) 是第三种：本地本来指着 GitHub，人选择 detach，改在 Gitea 上另搞一套。这会制造两个 Git 身份抢同一份工作副本，合入钥匙、评审请求、issues 家都会分叉。

建议：

- 向导只提供 (a) 和「纯本地 → Gitea」。
- 若人坚持「我不要用那个远端」，走「登记为只在本地的新仓库」：新的 Repo 身份、Gitea 建仓、初始代码按意图交付；**不**改原工作副本的 `remote`，**不**把 GitHub 上的 issues/PR 搬过来。
- 不要做静默 `git remote remove`。那是工作副本布局，不是治理。

若所有者明确要「从 GitHub 迁到 Gitea」作为一等产品路径，那是仓库换绑 + 内容迁移，需要单独的预览、导出、导入和回读，不是新建向导里的一个单选项。

### 5.3 grokbot 式虚拟机是不是第一期工人视图

现行观察阶梯已经够用：默认无输出（headless）、结构化执行流 / Execution Chat、Herdr TUI、精确 attach。grokbot 对照已经收成愿景层的两条轴（长期主体是项目与承诺；没有新信息的协调不进模型循环），明确不要把组织中心换成 Bot 名册。

建议：右侧工人视图按 Agency 绑定声明的能力展示，枚举用现行词（无界面 / 结构化流 / TUI / 精确终端）。虚拟机桌面若某家 Agency 将来能提供，算那种供给的能力声明，不写进第一期 Workbench 必选三种，也不单列产品对象。

## 6. 建议怎么改（拍板后）

只改写法、不改含义的，可以进 Workbench 实现与 CT-WORKBENCH-IA 的产品句，不必 bump 约束语义：

1. **新建向导三步**（一笔提交仍是登记 Repo + 创建 Project + 可选绑源 + 选规划者）：填 SCM 地址 → 同意缺省任务源（或选 Linear / 本地加绑）→ 从已配对 Agency 名册选规划者。落地页仍是 Project Room。
2. **地址判别**只做三岔：远端 URL；本地检出能证明来源平台；纯本地。推荐项分别是「绑来源平台」「绑来源平台」「绑 Gitea」。
