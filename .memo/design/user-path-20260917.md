## 一、所有者的路径（原文，加编号）

**《新建项目》**

- **N1【建立 project】** 用户在 Workbench 主界面里选择「新建一个 project」，并选择了一个 SCM 的地址：① 如果是 remote 的地址，完成；② 如果是本地的 git 地址，那么首先根据 .git 上溯出 remote 的地址，然后给用户选择：(a) [recommended] attach 到 remote 上去做后续操作，(b) 在本地 detach 掉 remote 后，用 Gitea 另搞一套。如果 .git 看出来是纯本地，那就直接走 (b) 好了。【注意】ctl + project 这俩可以理解为是一个闭包，把后边所有的概念都兜住了：这些概念（例如 task、run、participant 等）都不会越过这个闭包的边界，但在边界之内，它们的对应关系可以非常直接相连且复杂（1:N）。
- **N2【绑定 kanban】** 用户有了 project，就可以为这个 project 选择 task-kanban，而这个 project 有且只能有一个 task-kanban。几个选择：① [recommended] task 来自 SCM 默认的 task 能力，如 GitHub issues；② [2nd choice] 外部已有的 task 系统，如 Linear；③ 本地的方案。无论哪一种，都把 tasks 读回来并借助可视化帮助理解。
- **N3【建立聊天室】** 看板有了，接下来用户为这个 project 选取 participants（从 Agency 那边）。选择好之后，一个 chat room 就做好了，里边有这些 participants。

**《产生 topic》**

- **T1【聊天归纳】** 聊天过程中常会冒出好主意。系统在输入框上边或别的发通知的地方不断向用户更新和总结：「之前讨论中怎样的 topic 倒是可以尝试来做（Yes / No）」。用户感兴趣就点一下，产生以这个话题为主题的全新 topic 聊天室；topic 聊天室的选人环节和 project 聊天室一样。
- **T2【建立或者删除 task】** 无论是 project 聊天室还是新产生的 topic 聊天室，都可以在里边通过聊天来操作 tasks（类比 topic room 的产生建议）。不但能操作 tasks，还能直接通过快捷模板为 task 生成 Run 的 DAG 施工图，只需通过交互式表单填写。

**《观测 Run》**

- **R1** 左侧导航栏里，每个 project 有三类内容：① Kanban，② Room 列表，③ Run 列表。
- **R2** Run 列表中每个 Run 一个独立条目，条目底下两类内容：① Run 的内容介绍，② Run 的 DAG 拓扑图。无论点哪一个，最右侧分栏都展示每个 worker 以及现在在做哪个步骤。选内容介绍看到 DAG 任务书，选拓扑图看到执行到了哪一步（可能并行）。本质上①②都是对 Run 的内容展示。
- **R3** 选中一个 worker，可以根据 Agency 选择时的要求展示：① 类似 Grok Bot 的虚拟机桌面，② Herdr 那种 TUI，③ headless 无输出。

## 二、总判断

这条路径与单元模型没有冲突：控制面、Agency、前端、内容系统、仓库底座各在其位，放置、权威、交付三种关系一处没破。冲突有三处，都在产品入口与机制层：

1. **入口叙事反了。** 现行正文是「打开仓库 → 进 Repo Room → 话题成型后提升为 Project」；路径是「新建 Project → 选一个仓库地址」，Repo Room 在路径里没有位置。
2. **「聊天归纳不断向用户更新」需要一个不由人逐次点火的模型调用。** 现行规矩是普通 Room 的每条临场执行边由人提交，模型只建议。
3. **「看 worker 的虚拟机桌面」需要 Agency 声明观察面。** 现行只有终端阶梯，桌面观察还在候选池里。

另有六处半句差异，一句话能改齐；其余步骤与现行设计一致，属于 Workbench 的产品层实现。逐步核对见 §三，三处冲突的改法见 §四。

## 四、三处冲突的改法

### 1. 入口：Project-first，Repo Room 怎么办

现行入口以仓库为起点：打开仓库进 Repo Room，研究成型后提升为 Project；Repo Room 与仓库注册同寿命，`repo_scope` 只读调用从它的名册选人。路径以 Project 为起点，仓库只是新建时填的地址。两者对象模型相同，差别是谁是第一个动作。

**改法 A（推荐）：Project-first 为主路径。**「新建项目」向导一次预览完成「注册仓库（若未登记）+ 创建 Project」，两条治理记录分开写；愿景目标体验前两步改成「新建项目、选仓库地址、绑任务源、选人」；Repo Room 从「必有」改为「可选」：仓库级的无主题研究要用时再建，不再在注册事务里自动创建；`repo_scope` 只读调用改为从任一 Project 的名册发起或随 Repo Room 一起可选。影响：`spec/project.md` §Repo 注册与 Project 归档 的「注册确认事务创建唯一 Repo Room」改为可选，相关契约测试改写；`project.md` §Room 类型 表与愿景目标体验重写；`delivery.md` 切片 A 第 1 步措辞随之。

**改法 B：保留 Repo Room，向导跳过它。** 对象与约束不动，只改愿景目标体验与 Workbench 导航。代价是产品里多一个用户很少进的房间，导航要给它找位置。

**闭包与 Repo 级对象。** 无论 A 或 B，Repo 级的三样东西（平台绑定、任务源绑定、合并板）都是 Project 的「地址」，不是闭包成员；Workbench 收进「项目设置 → 仓库」。同一仓库开第二个 Project 时复用这份地址，是人的显式选择（S1.I3）。

### 2. 归纳：不是常驻 Bot，是 Room 级的缺省施工图

路径要的效果是「系统不断向用户更新和总结」。用常驻的模型不断读聊天来做，正好是「省」那条原则要避开的形状：没有新信息的协调进了模型循环。用现行机制能做到同样的体验：

- **机制**：一张 Room 级的缺省施工图「归纳」，不绑 Task（Run 允许 0..1 Task）。触发是机械的：安静 M 分钟，或自上次归纳后新消息不少于 N 条；节点只有一个，调用带塑形 Skill 的规划者，只读，输入只有自上次归纳以来的消息与三张清单的上一版；产出只能是建议卡，三种：开话题室（Scoped Room）、建 Task（采纳契约）、开 Run（缺省模板）。建议卡不是执行边；人点 Yes 走 Trigger Preview，选人预填自父 Room。
- **授权**：建 Room 时一次预览批准这张图，预算上限随之冻结；预算耗尽停，人再批。人也可以随时点「归纳一下」发一次调用。
- **省**：新消息不够不跑；跑了没有新候选就不更新卡；每次只读增量。缺省 M、N 与预算定在 `delivery.md` §运行默认值。
- **约束与契约测试**：归纳调用的 Execution Spec 权限只有读 Room；它的产出进不了任何执行边；预算越限拒绝下一次触发。这三条各配失败用例。
- **不采的替代**：让归纳者作为常驻规划者自己决定何时说话。它要么违反「临场执行边由人提交」，要么变成每条消息都调模型。

### 3. 观察面：Agency 声明三档，席位要求可以点名

现行 Terminal 场景只有终端阶梯与五个恢复等级，桌面观察在候选池。路径把它提到了主线，所以提前立项：

- **Agency 声明观察面三档**：桌面（可看、可接管、可交还的图形工作表面）、终端（PTY 或 Herdr 那样的 TUI）、只有事件流。声明与派工绑定，不与参与者身份绑定；票据由控制面签发、Agency 校验；观察、普通输入、执行控制、安全输入四种权限分开授权，接管期间旧输入者失效。
- **席位要求可以点名**：施工图或 Trigger Preview 里可写「需要桌面观察」，进选人的可行性过滤；名册里没有能提供的工种就报缺能力，不静默降级。
- **安全策略面的取值**：连接走「端点与连接」，接管与凭据走「执行加固」与「凭据」，屏幕内容与截图走「敏感数据」（`spec/system.md` §安全策略面）；账号级共享桌面与凭据不采。
- **headless 的措辞**：三档里最低一档是「只有结构化事件流」，不是没有输出；Agency 的终局结果清单照旧。
- **落点**：`participant.md` §Terminal 场景 加观察面三档与「查看、接管、交还」的产品行为；`spec/participant.md` §派工与观测 加能力声明字段与票据规则；契约测试：声明了桌面却给不出通道时拒绝连接、接管期间旧输入失效、观察不等于验收证据。这就是候选池第 3 项的六件事。

## 五、用例先行

这条路径本身值得收成参考用例 S3（单机 Workbench 路径），与 S1（多单元）、S2（不顺利的四种情形）并列：每一步写系统要决定什么、依据是人显式声明的还是推断的，人已显式声明的不成题；S2 的四种情形在 S3 的 Run 里各走一次。以后每条相关改法先在 S3 里找到那一步，再改正文。

## 六、请所有者拍板

1. 入口改 Project-first：取改法 A 还是 B；Repo Room 删、可选、还是保留只跳过。
2. 「一个 project 有且只能有一个 task-kanban」：读作「一个 Project 一块板、来源可多、认领可跨源」，还是收紧成「一个 Project 只认一个源」（D 批刚定可跨源）。

5. 模板生成的施工图默认跳过读回，人改过节点文字才读回。
6. 观察面三档进设计正文，候选池第 3 项提前立项。
7. 1:N 的含义：Run 仍只绑 0..1 Task；若要一个 Run 覆盖多个 Task，另议。
8. 路径收为参考用例 S3。
