## 一、所有者的四点（2026-09-18）

1. 用户建立「第一个」room 时，不是 project room。用户只是指定了 repo，这个第一个无主题的聊天室就是 Repo Room；后边聊天里产生的都是 topic room。
2. 「project」这个词和 repo、topic 混用了，到底指哪个要明确区分。
3. 〈control + repo〉这对限制是所有的闭包。
4. 闭包里有三个视图：rooms、tasks、runs；它们之间没有必然的从属关系，都是关联关系，甚至一对多。所有者要我验证这一条。

## 二、先认账

09-17 那条路径里，「project」一个词担了三个意思：「新建 project 选 SCM 地址」说的是仓库；「project 聊天室」对「topic 聊天室」说的是话题；我在对照时把它们全对到了现行的 Project 对象上。我该在第一处就问一句「你说的 project 是仓库还是话题」，没问，反而顺着现行对象往下写，把「ctl + project 闭包」「一个 project 一个 kanban」都按 Project 对象解释了。以后遇到一个词在同一段话里换了指代，先停下来问，再往下对。

## 三、术语，一词一义

| 词 | 是什么 | 不是什么 |
| --- | --- | --- |
| 控制面 | 一个用户级的治理实体：授权、判定、凭证的家 | 不是一台机器，也不是一个仓库 |
| 仓库（Repo） | 人在控制面登记的仓库身份加平台绑定；Git 与平台是它的底座 | 不是某份克隆，也不是工作副本 |
| 闭包 | 〈控制面，仓库〉这一对。同一控制面登记两个仓库是两个闭包；两个控制面登记同一个仓库也是两个闭包（S1 的 gh-jssdk） | 不是「一个控制面只有一个仓库」 |
| Repo Room | 每个闭包恰有一个，无主题，与仓库登记同寿命；用户指定仓库后看到的第一个房间 | 不是「项目聊天室」 |
| 话题（Topic） | 聊天里长出来的一个主题：有名字、目标、范围、名册和生命周期；产品词，用户看得见 | 不是容器，任务和 Run 不「属于」它 |
| 话题室 | 承载一个话题的房间，0..N 个；选人环节同 Repo Room | 不是 Repo Room 的子房间，两者平级，只有来源关系 |
| Task | 仓库级的承诺：验收契约版本、来源映射、完成凭证；卡的家在仓库所绑的任务源 | 不属于任何话题，只与话题关联 |
| Run | 仓库级的一次施工授权：冻结施工图、基线、席位、预算 | 不属于任何话题，只记从哪个房间发起 |
| Participant | 被选进某个房间或某个 Run 席位的一位工种实例 | 不是人，也不是 Agency 的成员 |
| Project | 现行正文里的容器对象：具名目标、范围、角色的稳定容器，拥有 Room、Task、Run | 按所有者的四点，这个词退出用户词汇；对象怎么处置见 §六 |

## 四、闭包成立吗

成立，而且现行设计已经有一半是这样写的。

- 「用户进入产品即在某个 repo 之下操作，用户级总入口不做」是显式设计决定（交付文档「明确不做」）。这就是闭包的入口面。
- 合并板是仓库级一张，任务源绑在仓库上（D 批）。这就是 tasks 视图已经在闭包里，不在 Project 里。
- Repo Room 每仓一个，与登记同寿命；`repo_scope` 调用从它的名册选人。这就是 rooms 视图的第一个房间已经在闭包里。
- 仓库身份、变更集、写入租约、集成意图与凭证归 Repo 模块，全在闭包里。

闭包兜住的：房间、话题、任务、Run、选入记录、上下文、请求、备忘、工件、变更集、凭证，以及它们之间的所有引用。跨闭包流动的只有四样：Agency 名册上的工种（收进来时冻结引用）、平台上的评审请求与合入事实（平台仲裁）、Git 对象（共用对象库是放置，不是权威）、别的控制面对同一仓库的动作（是事实，不是命令）。这四样正好是「单元与连接」一节里放置、权威、交付三种关系的内容，闭包没有和它们冲突。

一个推论要说在前面：话题不跨仓库。一件事牵涉两个仓库，就是两个闭包里各一个话题，靠引用互看。这与现行「Project 归属于一个仓库」一致，也与候选池里「Project 引用多个仓库」那条相反；所有者若要跨仓库话题，是另一个题。

## 五、三个视图的关系：逐对验证

先把现行正文里的从属关系摆出来，再看去掉 Project 容器之后还剩什么是硬的。

**现行的从属。** Project 拥有 Project Room、Task 0..N、Run 0..N；Run 与评审请求一对一；Task 到 Run 一对多、Run 绑 0..1 个 Task Revision、同一 Task 最多一个活动 Run；Scoped Room 可由某个 Run 的 Request 派生；Room 与 Run 互相引用不包含；Request 从 Run 投影回 Project Room；Memo、Artifact 归 Project。三处从属都挂在 Project 上，Room、Task、Run 三者之间本来就只有引用。

**去掉容器后，逐对看。**

| 对 | 关系 | 硬还是软 | 依据 |
| --- | --- | --- | --- |
| 房间 → 任务 | 一个房间里可以采纳多张任务，一张任务可以在多个房间被讨论、被引用；任务也可以不来自任何房间（任务源里已有的卡被认领） | 软，多对多 | 采纳命令带来源回链，回链是引用不是归属；认领不搬家 |
| 房间 → Run | 一个房间可以发起多个 Run；一个 Run 记它从哪个房间发起（0..1），Run 也可以从看板卡或命令行发起 | 软，一对多；发起来源 0..1 | Trigger Preview 在房间里做，记录的是来源；Run 的 Request 投影回发起房间，房间归档后投影回 Repo Room |
| 任务 → Run | 一张任务先后可以有多个 Run；一个 Run 绑 0..1 个任务契约版本；同一任务同时最多一个活动 Run | **硬** | 这是完成凭证的成立条件：Run 正常完成才有资格提交这张任务的完成命令，绑两张就说不清完成了谁。研究类、归纳类 Run 不绑任务 |
| 三者 → 仓库 | 每个房间、任务、Run 都恰好在一个闭包里 | **硬** | 任务的卡有一个家在仓库所绑的任务源；Run 要一个仓库基线；房间的消息事实在该仓库的聊天服务器房间 |
| 任务 → 话题 | 一张任务可以挂零到多个话题作分组标签 | 软 | 看板分组靠控制面的记录，不搬卡 |

结论：所有者的判断成立，带一条例外和一个空位。

- 例外是任务与 Run 那一条：不是从属，但也不是随意关联，一个 Run 最多认一张任务、一张任务同时最多一个活动 Run。这条要留着，否则完成凭证没有主语。
- 空位是 Project 今天除了「容器」之外还在承担的四件事，去掉容器后要有人接：选人策略与预算上限、随 project_version 冻结进 Task 与 Run 的策略摘要、写入型调用的准入前提（`repo_scope` 调用今天只能只读，因为没有 Project 就没有策略）、归档时的静止要求。这四件是授权域的事，不是容器的事，见 §六。

## 六、Project 对象怎么处置

三条路。

**甲、Project 退场，字段分两处。** 授权域那四件事上移到仓库设置：闭包有一份版本化设置（允许的 Agency 与工种、预算上限、多样性要求、评审发布缺省），Task、Run、调用冻结的是仓库设置版本，不再是 project_version。目标、范围、名册、生命周期这四件下沉到话题：话题就是今天 Project Room 的身份加 Project 的目标范围字段，归档只把房间置为只读，不等 Run 结束，因为 Run 不属于它。Scoped Room 并入话题室：为 Request 或决定临时开的话题室多带一份回填义务，其余同。房间只剩两种：Repo Room 一个、话题室零到多个。

**乙、Project 改名为话题，仍是对象，不是容器。** 保留一个稳定 ID 和 Overview 投影，Task 与 Run 只挂标签。授权域的四件事仍要上移，否则话题室里发不了写入型调用。

**丙、保留 Project 作正式名，用户词叫话题。** 一个概念两个名字，正是今天混乱的来源，不取。

我推荐甲，理由是三条：第一，它把「不越过闭包」变成对象模型的直接后果，Task 与 Run 的家本来就在仓库；第二，授权域上移后 Repo Room 就能发写入型调用，第一个房间不再是二等房间，和所有者第 1 点一致；第三，房间从三种减到两种，Scoped Room 的回填义务变成话题室的一个可选声明，少一类对象。代价也说清：模块名 Project 与愿景里的「Project-scoped」「五个对象 Repo、Project、Room、Task、Run」都要改口，这是一次词汇批加一次约束批。

## 七、若拍板，必然要改的地方

| 现行 | 改法 | 层 |
| --- | --- | --- |
| `repo_scope` 调用只能只读 | 放开：写入型调用的策略与权限从仓库设置版本来；Repo Room 与话题室同权 | 约束，配失败用例 |
| Task 是 Project 中的承诺，Project 是板上的分组 | Task 是仓库级承诺；话题是任务的分组标签，零到多个 | 约束与正文 |
| Run 冻结 Project version 与策略摘要 | 冻结仓库设置版本、来源房间（0..1）、任务契约版本（0..1） | 约束 |
| 归档 Project 要求无非终态 Run、无活动租约 | 归档话题只把房间置为只读；Run、租约、意图不受影响，Request 改投影到 Repo Room | 约束，用例反着写 |
| 三种房间 | Repo Room 加话题室；Scoped Room 的回填义务成为话题室的可选声明 | 约束与正文 |
| 创建 Project 同事务建 Project Room | 开话题即建话题室，名册从来源房间预填，来源消息显式选择 | 约束 |
| 愿景「Project-scoped」与五个对象 | 「仓库为界」与四个对象：仓库、房间、任务、Run（话题是房间的一种） | 愿景与词汇表 |
| 设计地图的模块名 Project | 模块名另议：意图模块的名字可以照旧，也可以改「话题」，词汇批定 | 索引 |
| 用户路径 | 指定仓库 → Repo Room 出现 → 绑任务源 → 选人进 Repo Room → 聊天归纳出话题 → 话题室里采纳任务、开 Run → 左栏 rooms、tasks、runs 三视图 | 交付与参考用例 |

用例过一遍，只挑会变的几步。S1 的 mac_ctl 在 gh-jssdk 上「开两个 Project」变成一个闭包里的两个话题室，两个话题各有名册、各自采纳任务；两个控制面各开话题仍是两个闭包。所有者 09-17 路径的第一步「新建项目选地址」变成「登记仓库」，第一个房间就是 Repo Room；「topic 聊天室选人同 project 聊天室」自然成立，因为两者就是同一类房间的两个实例。S2 四种不顺利情形不受影响，它们都在任务与 Run 那条硬边上。

## 八、我不确定的地方

- 「话题」要不要有稳定 ID 和只读 Overview（乙的那一半）。用户要回答「这件事进展到哪」时，没有一个可指的话题对象就只能翻房间；我倾向要，但它只是投影加标签，不是容器。
- 归档话题后，挂在它名下的任务标签怎么显示：留着不动最省事，卡不受影响。
- 仓库设置版本冻结进 Run 之后，改策略对活动 Run 无效，这与今天 project_version 的规矩一样，只是换了主语；要确认所有者没有「改策略立刻生效」的期待。

4. Scoped Room 并入话题室，回填义务变成可选声明。
