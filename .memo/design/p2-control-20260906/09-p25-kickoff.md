## 一、定位与重述

**同层裁决：P2.5 是 P2 的最后一个功能里程碑「治理」，对应自举阶段的 B4 与 B5 的功能面；它把「下一步做什么、做完没有、凭什么算做完」从人和主笔手里，交给 control 的确定性规则加 workflow 引擎。**

- **在整体里的位置。** `01-plan.md` §十 的功能里程碑表里，P2.5 是「Workflow、Run、Seat、Gate、候选切换、多票评审（Dagu）」，当时写「待写」。`docs/design/delivery.md` §自举阶段：B4 引入 workflow engine、Run、Seat 和独立 Gate；B5 是候选切换、多票评审、regate（被评对象换了版本，重新过关卡）和完整故障恢复。
- **它是什么。** 人批准一张**施工图**（Workflow Revision：和引擎无关、不可变的步骤图，每一步写清「交出什么、凭什么算交出」），再启动一次 **Run**（对这张图、任务契约、代码基线、候选施工者、权限和预算的一次整体授权）。Dagu 只负责机械地跑图、等待和重试；每一步的**交付义务**（Obligation）、义务里的**席位**（Seat，一把椅子，票按椅子算）、某个施工者坐上椅子干的那一次**尝试**（Attempt）、**评审关卡**（Gate）怎么计票、最后签不签**凭证**（Receipt），全由 control 按冻结规则判（`docs/design/run.md` §为什么存在、§模块拥有什么）。
- **它接手的，正是主笔现在手工充当的那张图。** `07` §七「先做 Run 的用例」五条：挂着的「作者待修正」由图记着并进「待你处理」；「退回看红」写成节点的机械判据；换版本旧票自动作废；「谁在等谁」从图上读；「换了错误类别」由机器出候选、人判。
- **所有者 10-19 的原则落到 P2.5 是三句话**（`07` §二 第 41 条 ④：「推进由人或 workflow 引擎定，不由 LLM 自己定。」）：
  1. 推进只来自两处：人的命令（批准、启动、暂停、恢复、取消、替代、回答 Request），和 control 按冻结规则对已记录事实的归约。Dagu 只报机械进度（`spec/run.md` §写入约束：「Run 状态只由 control 根据获准命令和治理记录推进，workflow engine 回读只提供观测」）。
  2. LLM 只在席位上干活：施工、评审投票、读回施工图。它不排图、不选下一步、不签凭证，它的自述补不了完成谓词。
  3. 规则定不了的交人（§二 第 1 件）：进 Request 或「待你处理」，不交给一个模型去判。
- **范围之外**：Workbench 与 Run 图的界面（P3）；判断点与 sysone；运行中从节点派生子节点；多主机与 Dagu 集群；在 HCTL2 自己的仓库上跑（§二 第 4 件）。

- **依据**：`spec/run.md` §写入约束 第一行、§Workflow 与 Run 授权、§启动与 Manifest 里「HCTL Profile 的规则分四组」与「编译前先以 schema……lint」两段；`run.md` §施工图怎么凝结。
- **验收**：
  1. **不合法的图编译拒绝。** schema、Profile、图结构任一不过就拒绝；编译器拒绝子 DAG、默认 command/script、HTTP/action/agent/Harness 一类副作用；Dagu `human.task` 只作被动检查点（CT-RUN 第 1 条）。
  2. **达成判据与边。** 外部执行节点没有达成判据就拒绝；产物依赖的边无生产节点、类型不匹配或悬空就拒绝；两个外部执行节点直接相连、不带产物引用的边拒绝；静态图有环拒绝；结构件连出的控制边、loop 重入、冻结模板的 dynamic fork、引用尚未产生的上游产出的边都要编译通过（CT-RUN 第 33 条）。dynamic fork 的候选、基数、预算、选择函数与权限上限没预先固定的拒绝（CT-RUN 第 14 条的编译期一半）。loop 的编译：按施工图声明的返工轮数上限（缺省 2 轮，`delivery.md` §运行默认值）展开成有界结构，每轮一个新检查点（`spec/run.md` §启动与 Manifest 第 3、4 条：每次重入创建新 Obligation、不算环、批准后节点集不变），超过上限走失败边或请人（`run.md` 关键规则）；不编译成 Dagu repeat 或子 DAG，也不跨 dagRun（`workflow-engines.md` 2026-10-19 复核第 1 条）；Manifest 冻结的上限与编译用的是同一个数（`07` §二 第 46 条 ③）。
  3. **票数 lint 只拒能证明的。** 法定票数大于必需评审席位数时登记拒绝；两席要求与材料相同、未声明互异、法定票数二的图登记通过并附「可能合成一票」、缺哪项信息与可选处理，由人选（§二 第 1 件）；同一席位模板展开的两席不因模板相同被判同键；lint 用的键与计票同一条（CT-RUN 第 4 条的登记期一半）。
  4. **保存计划只登记、不启动。** 关联由 Run 模块随登记事务保存，Task 只投影；别的 Project 的 Task 拒绝；登记失败不留关联；响应丢失后重试不产生重复版本或关联；不带 Task 的合法登记通过；继续编辑形成新 Revision、不覆盖旧的；无显式跳过读回的模板不跳过批准前置（CT-RUN 第 7 条）。
  5. **批准核读回。** 未声明关闭读回而缺读回记录引用时拒绝；读回所引图摘要、快照摘要与本次批准不符，读回报新快照而实际交付的 Bundle 装旧快照，产出调用的 Bundle 含来源 Room 消息条目或带任何 Room 的消息读取权限，产出者在来源 Room 名册快照里，声明换 Worker Profile 而实际未换——都拒绝；声明关闭读回照常通过；只改「上下文」章节的新 Revision 编出的节点、边、席位与旧版相同（CT-RUN 第 34 条）。确无来源 Room 时只把「产出者在名册里」记不适用，其余隔离照查；「直接文本」不免检（CT-RUN 第 35 条）。快照只含三张清单的固定结构；产出来源的三种取值与回避规则（CT-RUN 第 36 条）。保存成功但未批准不得启动；批准比较登记、读回、实际交付三处原摘要，换成 Git 对象编号或最新清单时拒绝（CT-RUN 第 39 条）。
  6. **命令行。** `workflow register / compile / approve` 从真实 `hctl2` 走到处理函数，修改动作先预览、确认后提交；`workflow show` 列出节点、判据、边与 lint 提示。
  7. **退回看红。** 至少退回三处：环检测、产物依赖落地、读回摘要三处一致性，各自对应的用例要红。

### 第 5a 包 · 计票的纯算法（可在演示 3 走完前开）

- **范围**：不碰存储的一个库：输入是已记录的事实与冻结数据（席位、获准候选范围、有效裁决及其键、截止与预算状态、否决权声明），输出是「签通过 / 确定不可达 / 暂未收齐」和要撤销的席位。实现「有效裁决、仍可产出、已结束、仍可能加入、已定」五个词与五步重算。
- **依据**：`spec/run.md` §计票与结束 全节、§Request、重试与 Gate 里关于去重键、否决权与多样性的几段。
- **验收**：
  1. **重复组。** CT-RUN 第 29 条逐句写成用例：法定票数为一、同组两席，通过先到与要求修改先到两种顺序结果相同；法定票数为二、两席只能落到同一键且材料已证相同时判确定不可达；同组另一席还能改用不同键时不得提前判不可达；一席已有有效裁决、另一席未派发且冻结引用证明不了键不同时不得签通过；提案已冻结待准入时既不计票也不撤；独立组够数提前结束后，被撤席位交回的提案只留历史；已结束的席位不阻塞任何组；同组两席都结束且无有效裁决时不形成票。
  2. **切换与否决。** CT-RUN 第 30 条逐句写成用例：未声明多样性时合法切换使两席同组按一票计；一席候选含不同配置并切换后成两票，之前不提前判不可达；否决席无有效裁决而仍可产出时不得签通过、不得撤；否决席的切换条件；已交提案不切换。
  3. **上界。** 运行中上界（含未定组里已有的有效裁决）少于法定票数时返回确定不可达，上界够时不得提前失败；恢复后按已记录事实重算，不因别的组没收齐而阻塞（CT-RUN 第 31 条的运行期一半、第 17 条的判定一半）。
  4. **多样性只有两项。** 两票引用同类直报、两席同一 harness 不因此拒绝；声明了 Profile 互异而实际相同仍拒绝；删掉的两项不改去重键（CT-RUN 第 32 条的计票一半）。
  5. **性质用例。** 除了逐句的例子，再加一组随机生成事实序列的性质用例：同一组事实无论到达顺序，最终结论相同；签了通过就不再变。
  6. **退回看红。** 至少退回三处：重复组取最有利而不是最不利、否决席没裁决也签通过、上界不算未定组的有效裁决，对应用例要红。
- **依赖**：无。
- **写**：Claude（ubuntu，写入会话去留的调研之后；有实例空出来就开）；找问题 Codex（mac）；核验 GLM（ubuntu）。（Claude 的 PR 不由 Claude（ubuntu）核验。）

  4. **完成 Task。** 绑定 Task 的 Run 正常完成后，占用标记以比较并交换推进为 `completion_pending`，以稳定幂等键提交「完成 Task」；Task 独立验收并校验精确的 Integration Receipt；Task 拒绝不回滚 Run；current Revision 已前移时按契约分歧拒绝、Task 标需要关注（`spec/task.md` 第 42 行）。

每包的验收七条，缺一条不算过：

1. **先实测五个问题，再定交法。** 用本机现装的版本，在真实会话上把五个问题各试一次：正文怎么不经输入框交进去；一轮的结束与回答从哪里取（子代理的事件怎么区分）；能不能只对这一次启动生效、不动用户的全局配置；怎么续接上一次的对话；走结构化接口时窗格里能是什么——这家 harness 的界面能不能连上同一个会话；不能就按通则用 H0 的观测窗格（`07` §二 第 45 条 ①）。像 #362 那样读 harness 自己记录的输入核正文，不靠模型自述。结论补进调研文件的那一家，证据分官方文档、源码、实测三档。机制和「一轮」对不上、或要动用户的全局配置，先报所有者。
