## 一、Fable 在 P2 计划 v3 里的原理解（原文，所有者判有大问题）

3. **Repo 的稳定身份——所有者要一个具体例子，先把词说清。** 控制面指 `hctl2-control` 这个常驻进程加它的账本文件 `~/.hctl2/control.sqlite`；装在哪台机器、以哪个 OS 用户运行，就归那个用户。它记的是 HCTL 自己的事实：登记过哪些仓库、谁有哪些授权、哪个版本被谁裁决过。它不是 harness 会话，也不是 Git 仓库本身。上一版提到的「Codex 云端会话」是写岔了：那是一个 harness 会话，跑在 OpenAI 的机器上，与控制面无关，忘掉它。例子：仓库 hctl2 在 GitHub 上。第一台机器是你的 Mac，装了 HCTL，跑着控制面 A；`/Users/haibara/workspace/hctl2` 这个克隆连同它的几个 worktree 是 A 挂接的一个执行现场（Repo Instance）。你在 A 上注册 hctl2：A 生成一个稳定 ID，比如 `R-7f3a`，让工具箱把它写进克隆里的受跟踪文件 `.hctl2/repo.toml`，文件经 PR 合入 main；A 的账本记下「R-7f3a 已登记，Repo Room 是某个聊天室」。此后 A 写进仓库的一切——任务契约正文、施工图、备忘、策略——都带着 R-7f3a。第二台机器是你的 Ubuntu 工作站；远程连接 P2 还没有，所以它暂时跑自己的控制面 B。B 克隆 hctl2、运行注册命令：工具箱读到 `.hctl2/repo.toml` 里已有 R-7f3a，B 不再造新 ID，只在自己账本里记「R-7f3a 已登记」；于是 A 写进仓库的任务契约在 B 那里被认出是同一个仓库的东西，B 发的 PR 引用的仓库也是 R-7f3a。第三个人是合作者小王，用自己的电脑、自己的 HCTL（控制面 C）克隆 hctl2，同样读到 R-7f3a、同样复用。三个控制面各有各的账本、各有各的 Repo Room，但说到「hctl2 这个仓库」时用的是同一个名字。这就是一对多：一个仓库，多个控制面各自登记它；正因为一对多，身份不能记在任何一个控制面里，只能记在仓库内容里跟着克隆走。反过来看没有这个文件会怎样：B 与 C 各自造出 `R-9c1d`、`R-2e08`，A 合入 main 的任务契约在它们眼里属于一个陌生仓库，PR 里的仓库引用对不上，只能靠人手工建映射。这个文件不是锁、不是所有权，也不涉及平台：GitHub 上的仓库编号是平台绑定的事，每个控制面各绑各的，纯本地仓库没有平台照样有身份。它的内容就三样：稳定 ID、创建时间、共享配置的引用。远端地址、目录名、HEAD 都不能代替它：会换、随便起、可能碰巧相同。有一个零成本的替代是用根提交的哈希当身份，不用写文件也不用提交；短处是 fork 与原仓库同根分不开、也带不了配置，约束选了文件（CT-REPO 里 fork 与身份碰撞要求确认）。留下的题只是这个文件第一次由谁提交到哪个分支：**定**默认分支上的普通文件，注册命令让工具箱在一个 ChangeSet 工作树里写出来，人经正常路径合入（我们自己的仓库走 PR，纯本地仓库走 `integrate` 快进），合入前 Repo 保持待确认。

## 二、这段理解依赖的几条假设（供所有者逐条推翻）

1. 「一对多」指的是**多个控制面**（每个 HCTL 安装各有一本账）各自登记同一个 Git 仓库。
2. HCTL 有权往这个仓库的默认分支写一个受跟踪文件（`.hctl2/repo.toml`），并且约束层的存储拓扑（`<repo>/.hctl2/` 下的 repo.toml、projects/、workflows/、memos/、policies/、schemas/ 都是 Git 跟踪文件）对每个被 HCTL 管的仓库都成立——也就是默认「这个仓库是我们自己的」。
3. 仓库的身份必须跟着普通克隆走，因此只能写在仓库内容里，而不是记在控制面的账本、平台的仓库编号或远端地址上。
4. 注册的意义是「认出同一个仓库」；fork 是另一个仓库（CT-REPO 要求 fork 与身份碰撞时确认）。

## 三、Fable 自己看到的可疑处（不代替所有者的判断）

- 假设 2 在「给别人的上游项目做贡献」时不成立：我用 HCTL 给一个开源项目提 PR，我没有权限往它的 main 加 `.hctl2/repo.toml`，更不能把任务契约、施工图、备忘写进它的仓库；可这正是 HCTL 该管的场景。若如此，「不可变正文家在 Repo」（`spec/system.md` §Git 的双重角色）也要重新审视：正文要么进用户自己的旁路 ref 或另一个仓库，要么只在账本。
- 「一对多」也可能指别的东西：一个仓库上并行的多个 HCTL **Project**（这在设计里本来就是 Repo → Project 0..N），或者多个团队各自部署的 HCTL（云上的、CI 里的），它们与仓库的关系不是「登记」而是「挂接」。
- 身份的替代来源：根提交哈希（跟克隆走、fork 同根；这在贡献上游的场景里反而是想要的——我的 fork 与上游是同一个逻辑仓库）、平台上的仓库编号（只对有平台的仓库成立）、远端地址（会换）、纯粹由控制面本地记账（不跨控制面）。哪一种对，取决于「认出同一个仓库」到底要服务什么。

## 四、要在长聊里问清的问题

1. 所有者说的「多个 HCTL 展开工作」里，「HCTL」指什么：一个人的一本账、一个团队的一次部署、还是一个 Project？
2. 被 HCTL 管的仓库，HCTL 有没有权往里写受跟踪文件？如果不一定有，约束层 `<repo>/.hctl2/` 那套跟踪文件要搬到哪里？
3. 「认出同一个仓库」要服务哪些具体动作：把 PR 里的变更集对回账本？把两台机器上的现场对到同一个 Repo？让两个人的 HCTL 共享任务契约？还是只需要本控制面自己不认错？
4. fork 在所有者眼里是同一个仓库还是另一个仓库？

## 五、2026-09-06 新输入：绑定了平台的 Repo 都对应平台上的一个仓库

决策史 §36 之后，只在本地的仓库缺省绑定随包的本地平台（Gitea），来自外部平台的克隆绑来源平台；只有显式不挂平台的受限路径没有平台。于是除受限路径外，每个 Repo 都在某个平台上有一个仓库（平台实例 + 仓库编号或 owner/name），本机的克隆只是 Repo Instance。这给第三节「身份的替代来源」加了一个候选：平台上的仓库身份。它对「贡献上游、没有写权限」的场景也成立（上游仓库在平台上有身份，fork 也有）；对「多个控制面各自登记同一仓库」的场景，两个控制面看到的是同一个平台仓库。不在这里下结论，留给长聊；本地平台自身的仓库身份怎么跨机器、怎么迁到外部平台，也一并列入待问。
