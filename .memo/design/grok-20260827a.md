## 怎么来的

通读设计并更新仓库之后，所有者要求调研 Bazel 一类构建平台。讨论从「Tuwunel 在 Mac 上为什么用 rustc 1.95」落到「Linux / Darwin 是否必须同一把编译器」，再落到真正的选择理由：不是为了编聊天服务器，而是现有打包**确定性不够，违反工程实践**。所有者明确要上 **Buck2**。

同日后半：所有者要求抛开「Darwin 可以钉另一把 rustc」的初判，按业界实践重问；确认 **Tuwunel 作为跨平台组件应对齐编译器版本**，并要求把这条写进本文：各构建 target 使用**同一版本号**的编译 toolchain（不限于 rustc）。

## 所有者的判断

1. **选 Buck2 不是因为 Tuwunel。** 是在整段打包/工具链过程里看见输入没进产物身份、宿主机工具链靠 PATH 和事后 tsv 记账——确定性是纪律不是机制。Buck2 要兑现的是「构建是函数」这条实践。
2. **调研范围是整个产品构建**（跨平台、toolchain、多语言），不是某一个上游包。
3. **跨平台构建 target 共用同一版本号的编译 toolchain。** 平台差的是三元组、sysroot、链接器、按 OS 能力开关的 feature，不是 Linux 1.95、Darwin 1.98。一种语言一把版本号，所有我们自己编的 target 共用；升级是一次有意的全平台回归。不漂成 `stable`。

初判曾写「Linux / Darwin 是不同构建，toolchain 版本不必一致」。那条作废，由第 3 条取代。平台仍是不同的**制品**（链接、feature、签名各走各的），但编译器版本号不再按平台漂移。

## 现行构建实际在做什么

三件活已经分开，没有总图：

| 活 | 现在 |
| --- | --- |
| 第一方代码 | `src/` Cargo workspace（`agentd` / `tool` / `protocol` 等），`rust-toolchain.toml` = **1.98.0** |
| 上游运行时 | `packaging/dependencies`：按 target 钉 URL/SHA，打原生离线包 |
| 开发机工具 | rustup、Xcode/`xcrun`、Homebrew bison/pkgconf、apt；脚本约定，不是图里的目标 |

三个发布 target：`linux-x86_64`、`macos-aarch64`、`macos-x86_64`。官方有包的用官方包（Linux 上的 Tuwunel、各平台 Vikunja/Dagu 等）；没有官方 Darwin 包的 Tuwunel、以及 tmux，从锁定源码编。

第一方 Rust 已经全局 1.98，符合第 3 条。Tuwunel 目前不是：Linux 吃上游 1.95 官方 deb，Darwin 用 1.95 现场编——碰巧版本相同，但是「官方 blob + 自己编」两份来源，不是「同一配方的两个 target」。

## Tuwunel 与 rustc（事实）

锁定源码 [`v1.9.0 / 5b366914`](https://github.com/matrix-construct/tuwunel/tree/5b3669144219d5d4c0774743c84191b476f1b54f) 的 `rust-toolchain.toml` 写着 `channel = "1.95.0"`，并注明这是该项目的权威工具链。Darwin 两个 target 在文件里是注释，只表示 rustup **不会自动下载** `*-apple-darwin` 标准库，不是源码不能编 Mac。

因此：

- Linux：拿官方 deb，不现场编，碰不到 rustc。
- Darwin：解开同一份源码 tar，**不改上游 src**。`prepare_source_tree` 只有校验哈希和解压。改的是我们的 cargo 调用：`rustup target add` 补上 Darwin std；`--no-default-features` 后自选 feature（关掉 `io_uring` / `systemd` / `jemalloc`，另开 `direct_tls`）；`LIBCLANG_PATH` 指向 Xcode；编完改 Mach-O `@loader_path`、ad-hoc 签名、核对 minos。feature 写入 `tuwunel-features.txt`。

**1.95 对齐的是上游那份 toolchain 文件**，Linux 官方包碰巧也是那份文件编的。Mac 打包机上现在仍可能同时存在 1.95（Tuwunel）和 1.98（HCTL2 第一方）。日常在 `src/` 开发只要 1.98。用户装好的离线包不需要 rustc。

按第 3 条，Tuwunel 若视为你们交付的跨平台组件，不能长期停留在「Linux 官方 1.95 包 + Darwin 另一把 rustc 自己编」。收口只有两条干净的路（实现时二选一）：

1. Darwin 继续 1.95，与上游文件和官方 Linux 包同一把刀（并接受 Linux 侧仍是不透明 blob）；或
2. **两边都从锁定源码自己编**，共用一个钉死的 rustc 版本（例如都 1.98）。

业界默认是第 2 条那种「同一份源码、一把编译器、多个 target」。第 1 条是继续消费官方 Linux 制品时的权宜，不声称两份二进制是同一构建。

## 确定性缺口（选 Buck2 要对上的那件事）

已经有的是**事后记账**：下载 SHA、`MANIFEST.sha256` / `PAYLOAD.sha256`、Mac 的 `macos-build-environment.tsv`（事后抄 rustc/clang/make/macOS 版本）。缺的是**事前约束**：没声明的不准参加构建；参加了的必须进入产物身份。

Darwin 上 `TUWUNEL_BUILD_INPUT_SHA256` 等于源码 tar 的哈希，**不含 rustc / clang / SDK**。换 Xcode、换 PATH 上的 rustc，源码哈希仍对得上。官方 zip/deb 钉哈希的那一段是确定的；一进入自己编（Tuwunel、tmux、第一方二进制），确定性就变成纪律。

宿主机漏进动作的东西包括：`xcrun` 的 clang 与 libclang、`require_command clang`、Homebrew bison/pkgconf（只核 formula 版本字符串）、Linux 上「支持范围内最旧 glibc」的文字约定、Darwin feature 写在 shell 变量里——没有「编译器变了旧产物必须作废」的机械关系。

多 harness 自举时，这种漂移会看起来像代码 bug。这和产品自己反对的失败同类。

## 构建平台对照（压缩）

封闭图（Bazel / Buck2 / Pants）：构建当纯函数；工具链也是输入；适合多语言、按平台分叉。Bazel 9 + `rules_rust` 生态最大，公开口径偏大团队。Pants 偏 Python。Buck2 核心 Rust、规则全在 Starlark、入门即 `rust_binary`、Apache-2.0/MIT、Reindeer 把 Cargo 依赖生成 `BUCK`；**没有稳定 tag**，内部跟 HEAD，开源用 `latest` 预编译或 DotSlash 钉进仓库；**本机步骤默认不沙箱**，封闭性要接 Remote Execution 才硬；prelude 与内部同一份，工具链未开源。

对照：`rust-toolchain.toml` 一个 `channel`、Go 的 `toolchain` 行、Chromium 一份钉死 revision 的 clang 编七个以上 OS——都是「编译器版本全平台共用」。Buck2 的 configuration / `select` 用来分叉 **target、sysroot、feature**，不是给每个 OS 另选一个编译器版本号。

任务编排（Nx / moon / just）：不管 `rustc` 的每一个 crate。Nix 钉机器上有什么，可给 Buck 喂 toolchain，不是 Cargo 的替代。Earthly 是容器步骤，和「桌面发行不进 Docker」不是一条路。第一方代码继续用 Cargo 当语言构建器仍然成立；Buck2 要取代的是「没有总图、输入靠 PATH」。

## 若上 Buck2：要兑现什么

选择理由是工程实践，兑现形态应是：

- Buck2 自身用 DotSlash / 审过的 commit 钉死，和依赖同一纪律。
- `Cargo.toml` / `Cargo.lock` 仍是 crate 依赖的事实源；`BUCK` 由 Reindeer（或同类）生成，不两份手写图。
- **每个发布 target 是 configuration**：三元组、sysroot、链接器、按 OS 的 feature 可以分叉；**每种语言的编译器版本号全 target 共用**，做成声明的 toolchain 目标，升级一次、全平台失效重编。
- rustc / clang / SDK 钉哈希下载，或 Nix 提供再喂给 Buck。没有远程执行时，不能假装 `buck2 build` 会挡住没声明的 `xcrun` clang。
- 第一方 crate、自己编的 Tuwunel / tmux 进图；若某上游继续用官方包，那是哈希钉死的 blob，不计入「我们编的 target」的编译器对齐，也不得和自己编的另一平台冒充同一构建。
- 清单从「编完抄环境」改成动作 digest 的投影。Mach-O `@loader_path`、签名、minos、Intel 必须在 Intel 上编，仍是我们的规则，prelude 不会自带。
- Workbench 等壳定了再决定是否进图。

成功标准：`buck2 build //apps/hctl2-agentd:hctl2-agentd` 与 `buck2 build //packaging:<target>`；改 rustc 版本会使**所有**自己编的平台产物 digest 失效；开发者能问图而不是读 tsv。切默认之前，Cargo + 现有打包脚本仍是能打出发行物的路。

## 与先前相关判断的关系

OS 沙箱（执行面、Harness 入场券）是另一件事，见 [grok-20260824a](../notes/grok-20260824a.md)。本文的确定性是**构建面**：编产品和编上游依赖时，宿主机漏进动作的工具链。不要把两套沙箱写进同一个门票。

「Darwin Tuwunel 单独改钉 1.98、Linux 仍吃官方 1.95 包」与第 3 条冲突，不再作为待选配方。

## 历史实施清单（已由后续方案吸收）

1. 仓库钉 Buck2 + prelude commit / DotSlash。
2. 第一方 Rust 进图，Reindeer 生成 third-party；保留 `cargo test --locked` 作对照直到对得上。
3. 按 platform configuration 收自己编的组件（Tuwunel / tmux 等）；官方包保持哈希。
4. Tuwunel 编译器对齐：在「Darwin 钉 1.95 并标明 Linux 为上游 blob」与「两边从源码共用一个 rustc 版本」之间选定并改配方；rustc 版本写入构建输入，不是事后 tsv。
5. 无远程执行时，toolchain 目标如何强制（钉死的 rustup 发行物 vs Nix）。不上执行集群就把封闭性写在「钉死的、全平台同一版本的 toolchain」，不要写在「Buck2 会替你沙箱」。
