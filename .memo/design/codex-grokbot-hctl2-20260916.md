# Codex：Grok Bot 对照之后，给 HCTL2 设计主笔的建议

> 状态：讨论中 · 所有者授权保存建议；合入本备忘不等于采纳其中的设计改动
> 基线：main @ 42b2565（草案 v0.18.3）
> 去向：供 Claude 主笔逐条取舍；候选落点见 §五，本 PR 不改 `.memo/` 之外的文件

## 一、结论与依据

我的结论是：保留现有五模块、三面架构和 Agency 代理边界，修正部分论证，补清能力评价与推荐的演进方向，然后把主要精力放回实现。这次比较没有给出推翻整体设计的理由。

我依据的是所有者保存的[完整对话](../notes/hctl2_grokbot_compare.md)，包括首条答复附带的完整调研报告，而不只是开头的比较摘要。原文经 [PR #232](https://github.com/yesme/hctl2/pull/232) 合入；其中 HCTL2 的对照基线是 `e0cc1ee`，本文另核当前 `42b2565`，不把旧基线描述当作现状。

对话要按发展顺序读。前半提出了跨项目长期负责人、扩大 Project 的仓库范围、改变本地平台缺省值等建议；随后所有者把重心拉回“省”“项目与承诺”及 TAMP。中途建议不是最终决定，也不能因为保存在原文里就进入施工清单。

我此前读过分享页正文，却没打开首条答复附带的完整报告；完整补读后，结论的重心也应调整：先解释现有设计如何承接最终讨论，不把每个中途提议都扩成一个需要补齐的产品缺口。

本文分开三种性质：所有者在对话中明确的方向、现行设计已经规定的边界、我建议主笔考虑的改法。后两者发生冲突时，建议不能自行覆盖约束。

## 二、三个观点分别成立到哪里

### 1. 产品长期围绕什么组织

Grok Bot 围绕持续存在的数字伙伴组织体验，HCTL2 围绕持续存在的项目与承诺组织事实。这是产品重心的区别，不是“一个能长期存在、另一个只能做一次性任务”。Grok Bot 的官方设计说明把持续身份与 Bot 名册放在中心；HCTL2 的[产品原生核心](../../docs/design/vision.md#产品原生核心与架构最小内核)则明确要求换掉执行工具后项目仍可继续。[Grok Bot 官方设计说明](https://x.ai/news/designing-grok-bot)

长期伙伴与项目中心并不冲突。用户可以反复选同一工种、复用方法和偏好，也可以逐渐信任一类经过检验的供给；每次参与什么工作、获准做什么、什么算完成，仍回到本次项目与承诺。熟悉的伙伴是履约者，不是项目事实的唯一保管者或最终裁判。

因此，“伙伴是否长期存在”和“日常协调是否反复调用模型”是两件事。伙伴可以按需唤醒；项目制也可能因重复交接而浪费 token。不能从产品定位直接推导成本优劣。

### 2. 协作的价值不等于聊天的价值

我支持的工程取舍是：可重复判定的权限、版本、等待、派发和验收手续交给机械规则；把模型调用留给理解需求、求解、取得新证据和判断分歧。它减少的是无信息增量的协调，不是把所有讨论都删掉。

研究支持“不能把增加通信本身当成收益”，不支持“任何多 agent 对话都没有收益”这个全称判断：

| 一手研究 | 能支持什么 | 不能推出什么 |
| --- | --- | --- |
| [Debate or Vote，v2](https://arxiv.org/abs/2508.17536v2) | 在所测基准中，多数投票解释了通常归给辩论的大部分收益；独立求解与聚合是重要对照 | 任意任务、模型、协议下的交流都无效；论文的理论结论也有建模前提 |
| [The Cost of Consensus，v1](https://arxiv.org/abs/2605.00914) | 所测同构小模型配置中，无引导的辩论相对独立自纠后聚合，付出更多 token 却没有相应质量收益 | 直接证明当前这批前沿模型在真实 PR 评审中的收益或固定节省比例 |
| [Kenton 等，v2](https://arxiv.org/abs/2407.04622v2) | 两方辩护交给第三方判断，在信息不对称的抽取式问答中优于裁判直接回答；其他任务结果混杂 | 无边界的同伴聊天有效，或所有任务都该加一轮辩论 |
| [Zhang 等，v3](https://arxiv.org/html/2502.08788v3) | 模型异构在所测部分辩论方法里有收益，比较基线和任务很重要 | 异构独立投票在等 token 下普遍多出一个固定幅度 |

多样性、工具反馈、分工和聚合规则都是可能的收益来源，不是把它们摆齐就保证正确。同模型的独立采样也可能改善结果；不同模型也可能一起犯错。HCTL2 按“执行配置与交付材料”去重，是治理上的计票选择，不是对采样是否有用的科学定理。

这同样不否定我们正在使用的“独立首审 → 作者按证据修正 → 交叉审阅”。第二轮如果检查了新版本、补了反例或纠正了第一轮的错误，就有新信息；只是让大家再表一次态则未必值得。现行 Run 的评审关卡不设席位间商量回合，和人在 Room 中讨论设计是不同边界，不能借研究结论把后者一并禁掉。

“制度”的类比有解释力：换掉参与者，授权、承诺与判定规则仍在。但制度只能保证按规定的程序和证据判定，不能保证需求写对、测试覆盖完整、评审结论真实；它也不是 agent 自发形成社会规范。机械制度减少模型自由解释重复规则的机会，其质量收益与总成本仍要实测。

### 3. TAMP 可以承接伙伴推荐，不必改变产品中心

TAMP 是任务与参与者匹配的设计底稿。所有者在原文最后的明确方向，是让实践中的能力评价逐渐支持发现与推荐：先按能力相关性召回，再在合格供给中考虑供需与成本，而 HCTL2 的核心仍是项目与承诺。

这比“收藏常用参与者”多了一层实际价值：系统不仅记得用户找过谁，还能积累谁在什么条件下做成过什么，用来减少下一次选人的试错。它也不等于完整复刻数字伙伴产品：长期人格、自由记忆和持续在线不是推荐能力的必然组成。

现有 [TAMP §10](../notes/TAMP-design-doc.md#10-证据层级绩效通道与能力更新) 与 [§11](../notes/TAMP-design-doc.md#11-匹配与调度)已经有能力证据、配置变化、召回、可行性过滤、排序与最终任用的区分，不必重新造一份匹配理论。不过，这份底稿还有自己的一套任务、执行和组织管理模型；它与[早期架构评审](../notes/tamp-review-20260905a.md)都不是现行 HCTL2 约束，不能整篇升格。

## 三、现有架构已经承接了什么

这次讨论主要补的是论证与后续用途，而不是缺少一层新架构。

| 对话想得到的收益 | 当前已有位置 | 我的判断 |
| --- | --- | --- |
| 项目不随伙伴或工具消失 | [vision §产品原生核心与架构最小内核](../../docs/design/vision.md#产品原生核心与架构最小内核) | 保留；补清可复用伙伴关系与项目权威不冲突即可 |
| 等待 CI、核对版本不反复问模型 | [run §关键规则](../../docs/design/run.md#关键规则)、[设计地图 §共同规则](../../docs/design/README.md#共同规则) | 已有机械事实回读与确定性推进，无须增设长期监工 Bot |
| 持续委托，但不依赖常驻前端 | [run §Workflow 场景](../../docs/design/run.md#workflow-场景)、[vision §两种控制制度](../../docs/design/vision.md#两种控制制度) | 持久执行可复用 Run；简单工作保留无 Run 路径，不另起一套后台任务 |
| 方法可以复用、更换、比较 | [participant §专业化 Participant：告别 BYOA](../../docs/design/participant.md#专业化-participant告别-byoa) | 已有版本化 Skill（技能包）；待补的是履约经验如何帮助下一次选择 |
| 参与者自己的运行方式保持自由 | [participant §Agency 与执行体](../../docs/design/participant.md#agency-与执行体) | 保留代理边界；推荐也只消费 Agency 的公开供给和获准的结果证据 |
| 复用材料而不复制整段聊天 | [context §投喂三档：内联、指针、代取](../../docs/design/context.md#投喂三档内联指针代取) | 已有交付办法；伙伴连续性不要求给控制面增加一份门后会话记忆 |

部署、权威与交付的关系继续引用 [architecture §单元与连接](../../docs/design/architecture.md#单元与连接)。一个能力推荐功能没有理由改变这三种关系，也没有理由把 Agency 门后的进程、主机、会话或内部团队暴露给控制面。

## 四、TAMP 接入现有模型的建议边界

以下是我的建议，不是已经拍板的接口或数据模型。

1. **从现有工作提取需求。** Room 调用的目标与范围、Task 的验收要求、Run 席位要求已经是输入；匹配所需画像可以从它们生成，不让用户再维护第二份任务契约。
2. **评价有版本的公开供给。** 关联 Agency 工种、可核验的执行配置与方法版本、任务类型、交付条件和结果。模型版本、思考深度、Harness、Skill 变化都可能影响表现；不知道的条件标未知，不根据名字或展示人设继承旧成绩，也不探查门后的部署布局。
3. **先可行，再比较经济性。** 能力相关性负责找候选，权限、材料可达和本次隔离要求负责排除不合格候选。价格排序比较达到验收要求的预期总成本，而非单次报价；延迟、返工与失败成本都可能改变结果。组合推荐还要看能力是否互补，不能只取单项分数最高的几位。
4. **推荐与任用分开。** 当前 [Agency 与执行体](../../docs/design/participant.md#agency-与执行体)写的是人从名册选、控制面准入记录。先做候选预填与推荐解释即可承接这次方向；让排序结果自动取得派工权是另一个取舍，不能用 TAMP 底稿的自动任用描述覆盖现行授权。
5. **把评价改进与方法改进分开。** 更懂得谁适合什么，不等于某个模型因此学会了新技能。成功做法可以成为 Memo 或 Skill 的候选，但正式发布、版本确认、装载仍沿现有路径；不因聊天里出现一条经验就自动改活动执行的方法。

落到所有者[参考用例](../notes/HCTL_case_study.md)，先看人已经说了什么：

| 用例中的一步 | 系统在这里要决定什么 | 依据是显式声明还是推断 | 对推荐的含义 |
| --- | --- | --- | --- |
| mac 控制面基于 gh-jssdk 建两个 Project | 工作归哪个仓库、哪个 Project | 人已显式声明 | 不让匹配器重新猜仓库归属 |
| mac 的两个 Project 都选用了 mac 的运维工种 | 复用哪份供给、建立哪次选入记录 | 人已显式选定工种；各次选入仍分别存在 | 已知选择直接执行，推荐不成为额外关卡 |
| cloud 控制面也从 mac Agency 取得运维工种 | 谁为这次派工负责、哪份授权生效 | 连接与选择已显式声明 | 同一供给可被多处使用，不合并控制面的权威或租户数据 |
| 原文提出未来依据能力评价推荐伙伴 | 人尚未指定时，哪些候选适合本次工作 | 原参考用例外；来源是本次 Grok Bot 对话末段与 TAMP §11 | 是未来推荐场景，不反推原用例的显式选择有缺陷 |
| 希望跨控制面共享履约评价 | 哪些记录获准共享、可以相信到什么程度 | 原参考用例与本次方向都未规定共享协议 | 首步用各控制面自己获准持有的记录；共享方式留待真实需求，不推断默认打通租户 |

我建议先让既有交付记录可用于人工比较，再做简短候选推荐。复杂竞价、全套组织考核、持续探针或学习排序模型，都不是这次文档补充的前置条件；[TAMP 旧评审 §三](../notes/tamp-review-20260905a.md#三-潜在瑕疵与工程落地风险必须警惕的陷阱)指出的测量成本问题仍然成立。

## 六、两处值得修正的研究归因

这两处是证据不足或归因错误，不是“机械制度”方向被推翻。

### 1. Magentic-One 不证明确定性编排胜过模型编排

当前研究文件在 Magentic-One 的“对三问”及跨篇归纳中，把消融当成“编排由代码持有”的直接证据。原论文 [§4.1](https://arxiv.org/html/2411.04468v1#S4.SS1)写得很清楚：编排者根据材料与对话判断是否完成、是否停滞、下一位是谁。它不是把这些判断全部移出模型的系统。[§5.3](https://arxiv.org/html/2411.04468v1#S5.SS3)的消融同时移除了结构化任务与进度记录、计划、跟踪、循环检测和显式指令，不能把差异单独归给代码。

建议追加的复核结论：该实验支持完整的计划、跟踪与恢复结构相对简化群聊基线有价值；不直接验证 HCTL2“由确定性规则承担机械协调”的成本与正确性收益。后者有自身的工程理由，需要自己的运行对照。

### 2. “异构独立汇总胜出 3 到 8 个点”没有对应的统一实验

当前研究的“跨篇归纳 → 四个具体追问”把不同论文压成了这句结论，但同文件对 Zhang 的局限已承认：它没有比较“两模型各自求解后投票”这个异构独立基线。[Zhang v3](https://arxiv.org/html/2502.08788v3)研究的是异构辩论及指定对照；不同方法、任务与预算之间的数字不能合成异构独立汇总的通用收益。

建议追加的复核结论：异构可能带来互补，效果依赖任务、模型强弱、聚合方式和预算；现有引文不足以给 HCTL2 的独立评审承诺一个固定增益区间。保留各论文自己的实验结果，撤掉综合句里的确定幅度。

这两项之外，“多样性 + 分工 + 外部验证”的价值排序也应被读作设计判断，不是把不同论文拼成的一份统一消融实验。没有必要为维护方向而维护过强的证据表述。

## 七、先把实现变成证据

原文最后的“实现不足”应当影响排期。设计已经有一条足够明确的路；本次讨论不构成再开一轮全库设计重写的理由。

建议沿[交付文档的无 Run 自举](../../docs/design/delivery.md#纵向切片-a无-run-自举)做成 B2，再沿[完整治理](../../docs/design/delivery.md#纵向切片-b完整治理)走到 B4。这是引用既有顺序，不是新排期：真实代码修改、发布评审、取得检查与评论、一次返工、目标更新回读和独立完成验收，先由正式入口承接，不依赖维护者手工搬材料或改内部存储。到 B4 再验证持久等待、评审关卡和自动推进，不把本来需要人选择的 B2 返工悄悄自动化。

建议在现有验收记录里增加以下对照信息，不先建新评测平台：

| 要回答的问题 | 最少记录什么 | 为什么 |
| --- | --- | --- |
| 是否减少无效模型工作 | 准备、执行、评审、失败、备用、返工、读回的总用量与总耗时（含等待）；模型版本、思考深度、Harness 与配置；缓存计费条件和实际费用（可得时） | 跨模型 token 单价不同；遗漏准备与失败成本会制造“省”的假象 |
| 是否减少人的协调 | 人工搬运、盯状态、补上下文和处理异常的次数与时间；正常授权另列 | 少调用模型却让人承担更多协调，不是产品收益 |
| 是否仍完成同样的承诺 | 相同代码基线与验收要求下的合格交付、误报、漏报和返工；整个任务集的失败样本也保留 | 不能只挑成功样本，或通过放松验收换取漂亮成本 |
| 等待与恢复是否可靠 | CI 失败、评审后版本变化、合入请求结果未知、组件重启后继续的记录 | 正常演示不能证明故障时制度还成立；具体判据沿现有契约测试 |

简单等待 CI 的状态没有变化时，不应为了“有人在跟进”的表象让模型重新解释一遍进度。反过来，诊断新失败、发现契约冲突或提出不同解法，是值得保留的模型工作。判别看新增信息与必要判断，不看输出是散文还是 JSON。

从 Grok Bot 值得学的优先是委托后少操心、当前结果容易检查、介入后可继续的体验；不是先添一个常驻经理。执行现场的可见性与成功方法复用也值得保留，但先利用现有投影、Agency 能力声明、Memo 和版本化 Skill。完整桌面接管或自动经验发布若超出现有能力，单独论证，不夹进这轮措辞修正。

实现层脚注：当前 [src/README.md](../../src/README.md)列出的主要是 P1 Git 机械组件与基础封装，control、公共 CLI 和 Workbench 仍待落地。因此本文谈的是设计取舍与验证建议，不是 HCTL2 已在产品表现上胜过 Grok Bot，也没有完成两者端到端成本实验。

## 八、建议主笔如何取舍

我建议先接受三件事：收窄研究与设计里的过强断言；把“项目与承诺为中心，也能积累与推荐伙伴”写清；把“省”交给真实交付的质量、成本和人工介入记录检验。这些可以小范围改文，不需要更换主架构。

TAMP 的推荐方向值得保留，具体供给评价结构、自动任用权限及跨控制面评价共享仍待独立取舍。跨项目全局 Participant、Project 改为关联多个仓库、改变本地平台缺省值、任意聊天唤醒与竞价市场，也没有因本次对话获得实施授权；若以后真有用例，再逐项讨论。

Claude 可以逐行采纳、部分采纳或拒绝 §五。凡是只改理由，就保持现行约束不动；凡是会改变授权、计票、交付或当前范围，就标出具体变化交所有者裁决。本备忘的合入只保存这份意见，不替设计主笔完成修改，也不把建议自动变成新的验收义务。
