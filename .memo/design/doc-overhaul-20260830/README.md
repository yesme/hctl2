## 4. 方法论(回路规则)

- **发现问题的回路终点必须是能修对的人,不是原来写的人。**所有闸门与核验只出报告;修改一律回到 GPT。这是切断「Fable 写 → GPT 挑错 → Fable 改不对 → 往复五六轮」的唯一机制。
- **两个病各有触发条件,拆阶段即可避开**:GPT 的病(钻细节、叠床架屋)只在它拥有结构决定权时发作 → 目录冻结后它没有落点;Fable 的病(细节写不对)只在它拥有改写权时发作 → 它不持笔。
- **换手不换题**:总图、施工、闸门用同一张迁移表说话,harness 之间只传表不传散文。
- **能机械的绝不交给 LLM**:链接、版本戳、死名、禁令密度先做成 CI;LLM 核验面收窄到只有 LLM 能判的东西(结构是否仍是一个系统、删除是否丢了承重规则)。
- **不对称是有效的,包圆是无效的**:Fable 有结构权无修补权;GPT 有执行权无目录权;Grok 只许答「通过 / 回滚哪几句 / 进停车位」;K3/GLM 只扫描不判断。

## 7. 判据

### 7.1 死文四判据(命中任一)

1. **被转向取代**:所述事实/选型/机制在 decision-history 有明确取代/撤销/改判记录,正文仍以现行口吻陈述;
2. **无权威对应**:设计层出现的对象/状态/命令在合同层无定义,或合同层机制无模块认领;
3. **重复权威**:同一事实在两处以上完整定义;
4. **无入口且非历史**:无任何权威文档链接它,又不属于历史记录类。

处置三档:删 / 转历史(来时路折叠段或台账一行)/ 改写为当前事实。Git 历史即 archive。

### 7.2 负例三留与处置四态(对应「删繁为简」)

每条「不得/不能/禁止/不允许/永不/必须拒绝」先答三问:它是否保护事实权威、权限、不可变版本或故障恢复?它是否对应历史上反复发生、正向规则仍容易犯的错(有前科:评审史抓到过、所有者经验、业界高频)?它是否区分两个表面相近、混用后后果严重的概念(特别 tricky,如「ACK 未知不盲重投」「旧代次结果只留审计」「Engine 路标不补足完成谓词」)?

| 标签 | 处置 |
| --- | --- |
| 特别容易犯 | 留一句,最好作为正面道路里的对照 |
| 特别 tricky | 留 |
| 可机械覆盖(已有 CT-*/类型/fail-closed 能挡) | 删文案,指到测试族;错误原因不直观时留一句解释 |
| 其余 | 改写成正面陈述,或删 |

配套问法(仓库已裁决过一半):「正确道路写清了它还进得来吗?」——进不来就删;进得来说明正确道路没写清,改正面句而不是加禁令。禁令密度进 CI 报告,大修后全库禁令总数必须净减;每条保留的禁令能指认满足哪条判据。

### 7.3 层次边界(再陈述一遍,施工时对照)

设计正文回答为什么与怎么用(只用产品词 + 日常语言);合同层定义对象、状态、写入者与共享机制;delivery 只定义范围与验证(可引用合同词,不重定义);research 保存源码与运行证据;decision-history 只保留转折;`.memo` 保存过程材料。实现名只进 delivery/research 与明确需要冻结 provider 能力的 binding 声明。
