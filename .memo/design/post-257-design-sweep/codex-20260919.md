## 一、结论与范围

值得做一次全设计文档的一致性清理，但不需要推翻重写，也不应把 #257 已定的关系重新当成候选。

[#257](https://github.com/yesme/hctl2/pull/257) 已经从体验整理扩为“体验澄清＋场景与验收同步”，修正了直接相关的设计、约束、术语与测试要求。它不是只改导航的 PR，也没有承诺审完其余所有章节。下一步要找的是仍依赖旧关系的叙事、约束和验收，不能因为新句已写进去就认定旧前提全部消失。

本次只抽查了基础用户体验、设计地图、架构、Project / Task / Run / Participant 正文，以及相关 Spec、CT 与交付段落。下面不是全库审计结果，没有验证产品行为，也没有把纸面问题认定为运行故障。全部引文以文件头的提交为准；相对链接供继续阅读，后续核对仍应固定提交。

## 二、先分清四种关系

这四个视角回答不同的问题，不宜画成一条包含链。

| 视角 | 回答什么 | 本次核对采用的依据 |
| --- | --- | --- |
| Unit（独立部署单元） | 什么可以独立安装、启停，Control、Agency、前端、内容服务怎样连接 | [architecture.md §单元与连接](../../../docs/design/architecture.md#单元与连接)；四类单元和仓库底座 |
| Module（领域模块） | Project、Task、Run、Participant、Repo 分别决定什么事实 | [设计地图](../../../docs/design/README.md#hctl2-设计地图)与各模块约束 |
| 对象归属 | 哪个 Project 的 Room、Task、Run；哪些身份、授权和验收分别独立 | [体验 §松散耦合具体意味着什么](../../../docs/user-experience/04-project-navigation.md#松散耦合具体意味着什么)与 [spec/connections.md §场景与第三方适配器](../../../docs/design/spec/connections.md#场景与第三方适配器) |
| 用户导航 | 怎样进入主 Room、Topic Rooms、按源看板、Runs 与待处理事项 | [体验 §Project 是主入口](../../../docs/user-experience/04-project-navigation.md#project-是主入口) |

#257 主要澄清了后两项，并影响前两项的表达。它没有把每个 Project 变成一套独立部署的系统，也没有让共用资源成为共用授权的理由。

已确认的基准如下，来源是所有者原话和本轮准入的正文，不是评审人数：

- 每个 Project 当前关联一个 Repo；同一 Control 可以为同一 Repo 建多个 Project，各有唯一主 Room。只知道 Control 与 Repo，不足以确定是哪份工作。见 [C2 原话](../../../docs/user-experience/04-project-navigation.md#2026-09-19c2-确认)。
- 两个 Project 是独立 Namespace，可以把同一外部卡分别认领为自己的 Task；共享的是源卡内容，不是契约、Run、授权或完成凭证。见 [Namespace 原话](../../../docs/user-experience/04-project-navigation.md#2026-09-19project-独立-namespace)与 [spec/task.md §契约与来源](../../../docs/design/spec/task.md#契约与来源)。
- 固定归属与交叉引用并存。Rooms、Kanbans、Runs 是并列入口，Room / Task / Run 不形成必经的包含链；各 Room 与各 Run 分别选人。见 [体验 §Participant 分别选入](../../../docs/user-experience/04-project-navigation.md#participant-分别选入)。
- 导航并列没有取消 Run–Task 的绑定、并发和完成条件，也没有改变 Agency 代理边界。见 [体验 §松散耦合具体意味着什么](../../../docs/user-experience/04-project-navigation.md#松散耦合具体意味着什么)及 #257 描述中的保留边界。

## 三、抽查发现

前三项对应本轮讨论中提出的例子。它们的性质不同，不合计成“三处架构错误”。

### F1：把一种施工图来源写得像唯一来源

位置：[run.md §模块拥有什么](../../../docs/design/run.md#模块拥有什么)。原文：“施工图（‘干什么的计划’）从 Project Room 的塑形讨论中长出”。

依据：[用户流程 §T3](../../../docs/user-experience/02-user-journey.md#t3模板与表单生成-run-计划)允许从 Task 选择模板、填写表单、保存计划；[spec/run.md §Workflow 与 Run 授权](../../../docs/design/spec/run.md#workflow-与-run-授权)已定义登记时关联 Project 与可选 Task，清单来源也可以是显式直接文本。Topic 的讨论不因此被排除。

判断：这是设计层的来源叙事过窄，不足以证明 Spec 强制每个计划先经过主 Room。读者可能把“从 Project Room 长出”当成必经步骤，进而为模板路径补造聊天。

建议替代方向：写成“施工图可以由讨论塑形或从模板填写而来；其版本、批准和与 Task 的关联由 Run 模块管理”，讨论产生结晶的说明只按适用场景保留。替代的是该句对来源的笼统限定，不重开结晶与对象归属的既有区分，也不取消批准、读回与开工前置。

验收例：从已有 Task 填模板并保存计划，仍使用既有登记、读回和批准规则，不为满足叙事而伪造主 Room 消息；从 Topic 塑形也不被强制搬回主 Room。

### F2：Git 存放与公开范围仍沿用旧说法

位置：同一节。原文：“判决的权威在控制面存储，结晶副本进 Git（私有仓库默认全文，公开仓库可降为仅摘要）”。

依据：[spec/system.md §控制面自己的存储](../../../docs/design/spec/system.md#控制面自己的存储)区分治理记录与治理正文，[§Git 的双重角色](../../../docs/design/spec/system.md#git-的双重角色)区分代码仓库与控制面治理材料；[spec/repo.md §发布评审](../../../docs/design/spec/repo.md#发布评审)规定审计副本留在控制面治理材料中，不默认随代码克隆分发，公开关联按冻结范围决定，公开摘要不能代替返工正文。`git log -S '私有仓库默认全文' origin/main -- docs/design/run.md` 将该表述追到 `98dfd67`，不是 #257 新加的规则。

判断：“副本进 Git”本身不错误，材料后端也可以是 Git；问题是没有说明是哪份 Git，且继续以仓库公私属性直接概括全文与摘要的取舍。当前约束已经分别回答存放、公开与交付，该旧括号不能继续承担这三件事。

建议替代方向：设计层概括为“判决由控制面保存；审计副本属于治理材料，公开关联和返工材料按各自获准范围交付”，链接到上述唯一权威。替代旧括号，不新订存储后端、公开策略或凭证规则。

验收例：同一 Repo 的两个 Project 分别开展工作时，共享代码不自动公开双方治理材料；公开 PR 只有获准摘要，也不能导致返工者拿不到已获准交付的完整裁决正文。这是现有存取与交付规则的核对输入，不是新增安全制度。

### F3：分组相关 CT 有笼统的旧概括，不能直接判成强制分组

位置：[contract-tests.md §CT-PROJECT](../../../docs/design/contract-tests.md#ct-project--project--room)：“Project 分组与 Room anchor 可重建”；[§CT-TASK](../../../docs/design/contract-tests.md#ct-task--task--kanban)：“Project 分组映射（父任务/milestone/标签降级）有测试”。

依据：[spec/task.md §契约与来源](../../../docs/design/spec/task.md#契约与来源)明确原生分组映射是可选的；没有稳定映射时，人仍可显式认领。CT-TASK 邻近条目已经写了“启用原生分组映射才……”，并有未启用或无能力却补建分组的失败输入。

判断：我在口头初查中将其列为“可能让实现者误以为每个 Project 必有分组”。复核邻近正文后，这一项应收窄为验收表述不清与重复，不把它报成已成立的约束冲突，也不声称无分组路径完全没有测试。

建议替代方向：将 Task 原生分组的笼统条目并入现有 CT-TASK 条件用例；Room 映射的重建另按现有 Room–Server Binding 核对，不和 Task 分组混成一句。保留已启用映射的重建要求，正常的无分组路径不因这两条概括新增义务。

### F4：体验接手页仍带合入前状态

位置：[docs/user-experience/README.md §从另一台机器接手](../../../docs/user-experience/README.md#从另一台机器接手)：“仍待复审、合入以及产品实现和行为测试”。

依据：#257 已合入，合并提交见文件头。判断：前两项已过时，后两项不能因文档合入而标完成。这是附带发现的状态文字问题，不是架构矛盾。

建议删除“仍待复审、合入”，继续明确产品实现与行为测试尚须分别验证。本备忘没有修改该页。

## 四、建议怎样做全量核对

建议全量检查、按问题修改，不以重写篇幅衡量完成度。设计主笔继续由 Claude 承担；Codex 可做独立关系核对与改后复核。这是分工建议，不在本 PR 派发工作。

### 先列一份清单，再集中修改

沿已确认用例逐步核对，每项记“位置、原句、用例步骤或裁决出处、问题性质、建议改法、受影响的验收”。人已经显式选了 Project、Repo、Source 或 Participant 的步骤，直接使用该选择，不再讨论如何替人猜测。

处置分三类即可：明确被取代的旧句按裁决纠正；原意仍成立但条件不清的句子收紧表达；确实要求新增行为取舍的另列待裁，说明选法与代价。不把第三类藏在措辞清理中，也不把本备忘的建议写成所有者已拍板。

### 按关系走到底，不按文件各自润色

| 核对主线 | 走查输入 | 需要一致的地方 |
| --- | --- | --- |
| 同 Repo 的多个 Project | S1.1、S3.P1：人在同 Control 显式建立 A、B | 主 Room、查询范围、默认设置、授权和归档不因 Repo 相同而合并 |
| 同卡、不同 Project、两个 Task | S3.P5 / P7 / T7：分别认领，观测标题与 Done，再取消一方或删除共享源卡 | 身份、对账、自动写回、完成、幂等与删除预览都保留各自 Task 的含义；既不复制源卡，也不互相完成 |
| Room / Task / Run 交叉引用 | S3.T4 / T6 / T10：独立选人，关闭一间 Topic，Request 直接升级为 Topic | 引用不搬归属、不继承授权；关 Room 不结束关联工作；来源无需补造 |
| 从计划到交付 | S3.T8 / T9、R1–R7：保存模板计划、开工、观察、验收及失败处理 | 保存计划不等于启动 Run；执行、检查、评审、集成、Task 完成各自成立；待处理只汇总已有事项 |
| 共用单元与材料交付 | S1.N3 / N4 / N8：共用 Git 对象库、异机凭据、Agency 不可达 | 部署共用不改治理归属；副本可读不等于获准；失联不等于执行已丢失 |

具体步骤在 [S1](../../../docs/design/scenarios/S1-multi-unit.md#参考用例-s1多单元协作)与 [S3](../../../docs/design/scenarios/S3-user-journey.md)。这张表是待核对范围，不表示每行都已发现缺陷。用例外的检查要注明来源，不为填表发明产品要求。

### 范围和边界

主范围是设计地图、架构、模块正文、Context、Spec、术语表、Delivery、CT 与场景；首页和体验目录检查入口、状态与引用。相关 Skill、开工指引只核是否还教旧做法。历史研究、裁决记录和 Memo 正文保留，确需提示接手者时更新状态或去向，不抹掉讨论经过。

现成的[文档纪律](../../../docs/design/doc-discipline.md#文档纪律)与[写作指南 §提交前收口协议](../../../WRITING-GUIDE.md#08-提交前收口协议)已经提供分层、唯一权威与连带核对规则，继续使用，不新造一套文档治理机制。关键解释和体验叙事仍保留；去重的是重复定义，不是“为什么存在”。

约束未变的修辞修正不增设行为测试；确实改变约束的改动，按既有规则同步版本和 CT 失败输入。Run–Task 基数与占用、完成判据、Agency 代理边界等 #257 明确保留的语义，若要变化，应说明独立依据和行为取舍，不能从“并列导航”直接推出。

## 五、完成判据与本次交付

全量核对完成的判据应是：同一个用户步骤，在体验、架构、约束与验收中得到同一个答案；每项问题有修正、保留理由或明确待裁去向；没有因修辞调整新增身份、权限或执行义务。文档机械检查验证链接、版本等，不能替代这条内容判据，也不能证明产品行为已经实现。

本次交付只有这份独立备忘。正式设计、体验正文、Spec、CT、历史研究与产品代码均未改；没有执行全库审计或产品行为测试。后续修正若落实，再按实际提交核销对应发现，不因本 Memo 合入就写“设计已清理完成”。
