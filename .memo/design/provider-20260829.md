# 运行时 provider 抽象：讨论底稿与裁决

> 状态：已拍板 · 已落地<br>
> 基线：main @ fa0e9e7（草案 v0.13.1 → v0.13.2/3/4/5 → 定形 v0.14.0）<br>
> 去向：docs/design/agent.md#agency + spec/agent.md#运行时与观测 + delivery.md 限时验证第 6 项 + decision-history §27/§28

## 提案（所有者，2026-08-29）

对本机 agent 的访问经"provider"实现；将来的远程数字员工也经新 provider 接入——只要实现 provider 的 API/功能。HCTL 需要的是**定义和桥接**。三个面：

1. hctl-workbench 经 provider 的 UI/terminal 接口 attach，在 UI 里直接操作底层终端；
2. provider 自家 client 连接自家 native 接口，在自己的 UI（即设计所言"第三方 UI"）里操作对应 harness；
3. hctl-control 经 provider 的可编程 API（可能是 CLI）headless 地操作 agent。

由此可先用 herdr 做本地 provider，直到本地有更便宜更好的方案。

## 定位

这是把 Terminal 场景补齐成与其他三景同构：chat server / 任务后端 / workflow engine 的 content 系统都可插拔且原生客户端即互操作面，Terminal 是最后一个第一方特例。provider 合同罩得住全部已知实例：tmux（attach 面 + 自身 client + control mode）、herdr（TUI/--remote + socket API）、OpenCode server（无 PTY 的 provider，只有 API 面 + Web 面）、将来的远程数字员工执行端点。不新造对象——扩展既有"运行时后端"受控端口为逐项能力声明的 provider 合同，与 Harness 能力探测同一套纪律。

## 三条裁决（所有者）

1. **native client 输入记为带外并入账**：provider 原生客户端是执行面的内容原生界面，观察不设限；输入不经输入租约，agentd 按带外输入入账（source 标注），不产生可准入结果。
2. **扇出点按 provider 能力声明**：声明了多观察者与缺口披露的 provider 自己扇出，否则 agentd 网关兜底。
3. **状态检测只作观测来源**：按自述机制归入既有仲裁序（hook 级或屏幕推断级），不因转手升级置信度，不获生命周期写入权。

附带边界：provider ≠ participant——provider 只回答"在哪跑、怎么够得着"（三协议面中的执行端点），谁在工作仍由 Participant 与执行规格回答。provider 报告的恢复能力必须翻译为四级恢复词汇（exact attach / semantic resume / replay / 丢失），翻译不出按丢失。

## 分层澄清（herdr =(agentd+tmux)？）

方向对，等式两边都要修：herdr 不是搭在 tmux 上，而是自带 vendored 终端仿真，占据的是 [tmux 的物理会话槽位] + [agentd 的观测/扇出/接管切片] + [终端 UI 客户端切片] 的并集；它**没有** agentd 的治理切片（租约、代次、冻结规格、审计、恢复等级裁决——审计确认其控制方记录为进程内映射，无代次/TTL/持久游标）。所以准确写法是：herdr ≈ tmux ∪ agentd(观测半边) ∪ 终端UI，agentd(治理半边) 谁都替不了。这正是 provider 是正确切口的原因：胖 provider（herdr）与瘦 provider（tmux）都塞得进同一合同，治理半边永远在 HCTL。

## 实测依据（2026-08-29 Linux x86_64 容器探针，可丢弃）

同负载（10 终端各 idle bash → 各灌 200 KB 输出）：tmux 3.7c 单 server 1.95 MiB → 全保留 21.9 MiB（默认截断 8.6 MiB），10 隔离 server 合计 19.3 MiB；herdr v0.8.2 headless 空载 13.7 MiB → 10 pane 19.9 MiB → 输出后 112 MiB。二进制 2.2 vs 21.7 MiB，均为官方静态单文件免编译。herdr socket API 带版本协商（protocol 20）与 schema 导出。数据已录入 docs/research/{tmux-runtime,herdr}.md 复核记录。

## 追加裁决轮（同日，v0.13.3）

所有者两问与裁决：

**Q1：治理五件套对 herdr 也有价值，它为什么没实现？能实现在那里么？**
架构层答案：herdr 的位置是单信任域——用户即权威本人，"算不算数"与"我刚才干了什么"是同一个问题，治理没有对象（无任务、无验收、无承诺账本）。技术上能补（持久化控制方表 + 编号 + 过期），但架构上不该：治理事实必须绑权威账本，herdr 要做就得先长出控制面（变成一个 HCTL）；且即便它做了我们也不能用——治理须跨 provider 统一，信任各家自带治理等于把权威拆成 N 份方言。provider 自带机制的正确位置永远是执行协助。

**Q2：数字员工 provider——治理做在 provider 层，还是拉齐由 hctl-control 提供通用治理？**
裁决：拉齐。理由：统一性（账本单一事实源、裁决跨 provider 可比）、信任边界（远程 provider 在别人的信任域，其治理声称是自述）、抽象平整（合同越薄越可插拔）。细化：治理权威在 control，但部分义务需要现场执行点——本地是 agentd；远程退到合同面，即**栅栏回显**能力声明项（携带并回显代次/租约引用、按合同拒绝不匹配项——§23"代次不在 Dagu"的推广）。未声明者整通道低信任降级：输入带外入账、结果弱证据类提案。

落点：spec/agent.md 治理永不下放段 + agent.md 两条新规则 + participant.md 执行端点对齐句 + CT-AGENT 两条失败用例 + decision-history §27 追加段。版本 v0.13.2 → v0.13.3。

## 生态位与三面对位（同日，续）

所有者两个定位判断，均成立并细化：

1. **"herdr 占据 HCTL 四模块版图里 Agent 模块/Terminal 场景的生态位"**——细化为：它是该生态位的**纯居民**（工程投入 100% 在此格，直方图审计无 room/kanban/workflow 目录）。纯居民是供应商而非竞品（对照：Superset/Multica/Codeg 跨格，是对手）；四场景由此对称——每景都采用该生态位最强纯居民当 content 系统。herdr 占的是此格 content 半格；治理半格市场无主，是 HCTL 落点。
2. **"herdr client 就是 Agent 模块的第三方 UI"**——精确落格为 Terminal 场景的**内容原生界面**（Matrix 客户端之于 Chat 的对位物）：观察与 content 操作随意，输入带外入账，提交不了治理命令。与另一格**合规第三方场景客户端**（走公开命令面 + control 票据、可携带 human provenance）二分；升格须 provider 侧适配，非 HCTL 义务。三面对位闭合：herdr server = provider、client = 内容原生界面、socket API = 可编程控制面——单产品占满合同三个面。

附带问答（实现层，已答）：herdr 为 Rust 单二进制、client/server 分体同构 tmux；RSS 差距源于产品选择（子系统数量 + 解析后格子式 scrollback 表示，实测放大 ~45 倍）而非语言。

落点：agent.md provider 节补"三面可由一家占满 + 两格区分"段；herdr.md 复核记录补生态位对位条。无合同变更，不 bump 版本。

## 刀口上移（同日，v0.13.4）

所有者定位（成立并落地）："tmux 太瘦不成 provider——它们需要加上 agentd 才是一个 provider"，这实际上放弃了"把 Agent 模块/Terminal 场景这刀切在 mux 上"的旧读法，把刀切到了逻辑更高的 agent 管理层。落定的三层图：provider = 执行服务（受理执行请求、常驻持有现场、报告恢复等级；herdr、数字员工端点、**agentd 内建的运行时服务**都是）；mux（tmux/Zellij/shpool）= 原语/部件，不直接承担 provider 合同；agentd 双身份在合同上分开——治理桥（面向所有 provider，唯一份）与内置 provider 宿主（N 之一，自己跟自己签同一份合同），换任何 provider 不动桥。tmux 选型与 P0 结论不变，变的是合同层级。

同轮遗留：**provider 命名**——所有者嫌"provider"太泛（且与 LLM provider 撞），要更意象化的"agents 的落脚处"。候选：车间（Workshop，接施工隐喻链：工地/现场之上的车间，推荐）、宿主（Host，业界标准但撞"主机"）、场地（Venue）。待拍板后做一次机械替换。

落点：spec/agent.md provider 定义句改写（执行服务受控端口 + 原语降级 + agentd 双身份）；agent.md 刀口段；architecture/glossary/README/delivery 及五类受控端口枚举全线改"运行时 provider"（agentd 对原语资源的 owner lease 条款保留"运行时后端"并标注为内置 provider 原语）；decision-history §27 刀口上移段。版本 v0.13.3 → v0.13.4。

## 概念对齐：provider = 执行者派出方（同日，v0.13.5）

所有者纠正："provider 完全不是'落脚干活儿的地方'！provider 是 agents 的团队、外包的派出方——从 herdr 这里'要一个满足某个 spec 的 harness'来做 participant。"接受并落地：供给关系是一等语义，承载现场只是交付方式。三类实例在此读法下完全统一：内置 provider 从本机 Harness 目录派、herdr 从其 integrations 名册派、数字员工 vendor 从外包名册派。三点增益：① participant.md 三协议面（发现/条款/端点）与供给合同同构——本就是劳务市场的形状；② 既有裁决更自然（治理不下放=外包方无裁决权、自述不可信=派出方自我报告不是验收、栅栏回显=派出的工人随身携带工单号）；③ mux 不成 provider 的真正理由明确：派不出执行体。钉住的边界：派出物填七层身份链的下层（模型、执行者配置、一次物理执行），参与者身份层不随派出转移——工牌是我们发的（合同语言："要一个 harness 来做 participant 的执行体"）。命名：英文保留 provider（supplier 本义贴切），中文对照"派出方"；场地系候选（车间/宿主/场地）作废。

落点：spec/agent.md 定义句改供给语言（含交付物核验、派出不转移身份）；agent.md provider 节开头、刀口段、正交句；participant.md 三协议面同构句；glossary/architecture/delivery 对照；decision-history §27 概念对齐段。版本 v0.13.4 → v0.13.5。

## Agency 定名、agentd 退场与刀口终局（同日，v0.14.0）

三轮收束：

1. **命名**：所有者否决 provider（太泛）并给出概念：agents 的团队/外包派出方。候选（Agency/Contractor/Vendor/Stable/Bureau）中定 **Agency**——"Agency 里有很多 Agent"是词源原生关系（talent/employment agency）。防 intelligence-agency 误读（那种 agency 给 agent 下任务；我们的模型里下任务的是 HCTL）。所有者随后指出我把"运行时 provider"与"agents 的派出方"粘连——修正："运行时"归原语层（运行时后端/mux），派出方就叫 Agency。
2. **agentd 退场**：所有者以订阅式远程 Agency 用例挑战"必须摸到进程"，要求双方辩论。合题：正方赢下控制命题（control 唯一控制者、本地/远程同一合同面、混用成立）；反方保住的不是"控制 agent"而是①现场保管（我们 clone 里的代码看守——归工具箱）②主场证据加成（第一方观测+运维兜底——建模为观测来源+部署形态，不是架构盒子）。旧 agentd 两身份拆开：派遣归内置 Agency（hctl2-agency，crate 改名代码跟进）；治理与网关归 control。AGD 条款待按 内置 Agency/控制面网关/现场保管 三类重归。
3. **过程纪律**：所有者批评提交过频、讨论未收敛即落盘（v0.13.5 把重发消息误当确认是实例）。"讨论不落盘，拍板才提交"入 AGENTS.md 纪律 4 与 CONSTRAINTS 台账。
4. **版本**：承重墙移动，bump 中位 v0.13.5 → v0.14.0（此前 v0.13.2–v0.13.5 四个 patch 是同一堵墙的逐步挪动，本轮定形）。
