## 提案（所有者，2026-08-29）

对本机 agent 的访问经"provider"实现；将来的远程数字员工也经新 provider 接入——只要实现 provider 的 API/功能。HCTL 需要的是**定义和桥接**。三个面：

1. hctl-workbench 经 provider 的 UI/terminal 接口 attach，在 UI 里直接操作底层终端；
2. provider 自家 client 连接自家 native 接口，在自己的 UI（即设计所言"第三方 UI"）里操作对应 harness；
3. hctl-control 经 provider 的可编程 API（可能是 CLI）headless 地操作 agent。

由此可先用 herdr 做本地 provider，直到本地有更便宜更好的方案。

## 定位

这是把 Terminal 场景补齐成与其他三景同构：chat server / 任务后端 / workflow engine 的 content 系统都可插拔且原生客户端即互操作面，Terminal 是最后一个第一方特例。provider 合同罩得住全部已知实例：tmux（attach 面 + 自身 client + control mode）、herdr（TUI/--remote + socket API）、OpenCode server（无 PTY 的 provider，只有 API 面 + Web 面）、将来的远程数字员工执行端点。不新造对象——扩展既有"运行时后端"受控端口为逐项能力声明的 provider 合同，与 Harness 能力探测同一套纪律。

## 三条裁决（所有者）

1. **native client 输入记为带外并入账**：provider 原生客户端是执行面的内容原生界面，观察不设限；输入不经输入租约，agentd 按带外输入入账（source 标注），不产生可准入结果。
2. **扇出点按 provider 能力声明**：声明了多观察者与缺口披露的 provider 自己扇出，否则 agentd 网关兜底。
3. **状态检测只作观测来源**：按自述机制归入既有仲裁序（hook 级或屏幕推断级），不因转手升级置信度，不获生命周期写入权。

附带边界：provider ≠ participant——provider 只回答"在哪跑、怎么够得着"（三协议面中的执行端点），谁在工作仍由 Participant 与执行规格回答。provider 报告的恢复能力必须翻译为四级恢复词汇（exact attach / semantic resume / replay / 丢失），翻译不出按丢失。

## 分层澄清（herdr =(agentd+tmux)？）

方向对，等式两边都要修：herdr 不是搭在 tmux 上，而是自带 vendored 终端仿真，占据的是 [tmux 的物理会话槽位] + [agentd 的观测/扇出/接管切片] + [终端 UI 客户端切片] 的并集；它**没有** agentd 的治理切片（租约、代次、冻结规格、审计、恢复等级裁决——审计确认其控制方记录为进程内映射，无代次/TTL/持久游标）。所以准确写法是：herdr ≈ tmux ∪ agentd(观测半边) ∪ 终端UI，agentd(治理半边) 谁都替不了。这正是 provider 是正确切口的原因：胖 provider（herdr）与瘦 provider（tmux）都塞得进同一合同，治理半边永远在 HCTL。

## 实测依据（2026-08-29 Linux x86_64 容器探针，可丢弃）

同负载（10 终端各 idle bash → 各灌 200 KB 输出）：tmux 3.7c 单 server 1.95 MiB → 全保留 21.9 MiB（默认截断 8.6 MiB），10 隔离 server 合计 19.3 MiB；herdr v0.8.2 headless 空载 13.7 MiB → 10 pane 19.9 MiB → 输出后 112 MiB。二进制 2.2 vs 21.7 MiB，均为官方静态单文件免编译。herdr socket API 带版本协商（protocol 20）与 schema 导出。数据已录入 docs/research/{tmux-runtime,herdr}.md 复核记录。

## 追加裁决轮（同日，v0.13.3）

所有者两问与裁决：

**Q1：治理五件套对 herdr 也有价值，它为什么没实现？能实现在那里么？**
架构层答案：herdr 的位置是单信任域——用户即权威本人，"算不算数"与"我刚才干了什么"是同一个问题，治理没有对象（无任务、无验收、无承诺账本）。技术上能补（持久化控制方表 + 编号 + 过期），但架构上不该：治理事实必须绑权威账本，herdr 要做就得先长出控制面（变成一个 HCTL）；且即便它做了我们也不能用——治理须跨 provider 统一，信任各家自带治理等于把权威拆成 N 份方言。provider 自带机制的正确位置永远是执行协助。

**Q2：数字员工 provider——治理做在 provider 层，还是拉齐由 hctl-control 提供通用治理？**
裁决：拉齐。理由：统一性（账本单一事实源、裁决跨 provider 可比）、信任边界（远程 provider 在别人的信任域，其治理声称是自述）、抽象平整（合同越薄越可插拔）。细化：治理权威在 control，但部分义务需要现场执行点——本地是 agentd；远程退到合同面，即**栅栏回显**能力声明项（携带并回显代次/租约引用、按合同拒绝不匹配项——§23"代次不在 Dagu"的推广）。未声明者整通道低信任降级：输入带外入账、结果弱证据类提案。

落点：spec/agent.md 治理永不下放段 + agent.md 两条新规则 + participant.md 执行端点对齐句 + CT-AGENT 两条失败用例 + decision-history §27 追加段。版本 v0.13.2 → v0.13.3。
