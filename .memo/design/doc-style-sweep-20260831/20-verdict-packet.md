## 一、要你拍的十条

### 裁 1 · 愿景层能不能出现对象名

**冲突在指南自己身上。** §0.4 给愿景层的验收标准是「读完不需要知道任何对象名」，但同一行的允许词汇是「核心产品词 + 日常语言」——而核心产品词就是 Project、Task、Run、Obligation、Seat 这张对象名单。两条互相取消。

Grok 报告时按更严的那条读，于是 `vision.md` 出了三条下沉（最小内核对象表、两种控制制度对照表、三类数据各住哪）。按松的那条读，这三条里至少前两条不成立。

这条还和文档纪律撞车：纪律写「愿景、论证与体验叙事不因篇幅或『与约束重复』被删除」，而 Grok 建议把 `vision.md:104` 的对象表搬走。

**我推荐：放宽验收标准，保留核心产品词。** 改成「读完不需要知道约束层对象——Obligation 的铸造条件、generation 字段、锁路径」。理由是愿景要讲清「意图 → 承诺 → 治理 → 运行」四阶段，不让它说 Project 和 Task，它就只能造一套同义词，那比直接用产品词更难读。

**这条卡住：** Grok #1、#2、#3。放宽后 #1 只剩「删掉那条命令信封的状态转换」，#2、#3 撤销。

### 裁 2 · 根 `README.md` 算哪一层

**两家独立收敛到同一个结论。** Grok（疑点 4）和 GLM（异议 3）都说根 README 不是愿景层的浓缩：它同时做四件事——愿景一句（①）、三面图（②）、早期实现与打包现状（④）、三条阅读路径。路由表现在把它整份归 ①，所以图里塞进 SQLite、`hctl2-control`、Dagu 直接改写、P2/P3 阶段代号，全部报成下沉。

但若真按 ① 收，把实现状态和阅读路径删掉，仓库入口就只剩口号，找不到代码现状。Grok 的话是「门面的职责是指路，不是说服」。

**我推荐：路由表加一行「门面」**，允许根 README 按段混层，但每一段必须能指回本层权威。图仍要瘦身（三面 + 四模块，产品名和阶段代号改成链接），因为混层不等于免检。

**这条卡住：** Grok #4，以及 GLM 各文件判断里对根 README 的核对口径。

### 裁 3 · 设计地图的「文档纪律」搬不搬

Grok（疑点 2 + 异议 2）说 `design/README.md` 一页干三件事：索引、共同规则、文档纪律。前两件是架构层，第三件是写作协议——它自己都已经把文风推给了写作指南，却仍在设计地图里立十一条硬边界。新读者读地图会被写作流程挡住；实现者改约束时又不一定想到来这里看纪律。

三个选项：

- **(a) 整节搬进 `WRITING-GUIDE.md`。** Grok 的建议。代价是指南的定位要改——它现在的开头写着「本文管风格与结构，内容与权威在设计地图」，搬进来就得推翻这句。
- **(b) 原地不动。** 代价是补丁链继续，我在 #114 加的那句边界说明只是延缓。
- **(c) 搬到独立文件（例如 `docs/design/DOC-DISCIPLINE.md`），设计地图留一行链接。** ← **我推荐这个。**

理由：文档纪律对设计正文是**规范性**的（谁能定义什么、新对象的引入门槛、审计几轮），而写作指南是非规范的作业帮助。把规范性的内容并进非规范文件，等于给指南升格，那会引出「指南和 spec 冲突时听谁的」这个本来不存在的问题。独立文件保留它的规范性，同时把它移出产品文档的阅读路径。

**这条卡住：** Grok 疑点 2、异议 2，以及 S3 与纪律第一条的重复（搬家后重复自动消解，S3 管怎么写，纪律管谁能定义）。

### 裁 4 · 「契约」和「约束」两个中文词并存

GLM（B13）报的，我核实了规模：**21 个范围文件里「契约」132 处、「约束」351 处**，两个词都在译 contract 这一族，而词汇表没有声明它们的分工。读者会当成两个东西。

具体是：`vision.md:56`、`task.md:15`、`architecture.md:58` 用「验收契约（Task Revision，下称"契约版本"）」，而模块级一律用「模块约束」「约束层」「写入约束」。

通读 K3 时又查到第三种用法：`spec/agent.md:78`「每个 harness 适配器必须为其接入端口声明**终局结果契约**」——这里是协议意义上的 contract，既不是 Task 的验收内容，也不是规范文档的规则。**三种意思共用一个词。**

两个选项：

- **(a) 词汇表声明分工。** ← **我推荐。** 「契约」专指 Task Revision 承载的验收内容，那是人与人之间关于「做完算什么」的约定；「约束」指规范文档立的规则；`spec/agent.md:78` 那种协议义按 L7 黑名单改写（例如「终局结果的约定」）。前两者确实不是一回事，把 Task 的验收契约叫「验收约束」会丢掉「双方约定」这层意思。
- **(b) 统一成一个词。** 代价是上面那层意思没了，而且要改 132 处。

**这条卡住：** GLM B13，以及后续每次审计都会重新吵一遍这两个词。

### 裁 5 · L7 词汇黑名单要不要再收紧一句

GLM（异议 1）说黑名单那行缺一条消歧规则。我核对了：**规则大半已经在了**——那行现在写的是「约束（结构专名一律如此）；普通名词按句意选『约束 / 规则 / 该怎么办』」，而且这句在 GLM 的基线里就有。

所以这不是指南的洞，是 **PR #119 执行时没遵守自己刚立的规则**：改名脚本对复合名词位置也一律替换成了「约束」。

GLM 的提议比现有规则严一格：复合名词位置**不用「约束」**，而不是「按句意选，约束也在候选里」。

**我推荐：采纳这一格收紧。** 判据是证据规模——见下面第二节，复合名词位置有 20 处，无一例外都被读成 constraint，其中「公开约束」的方向正好读反（public restriction）。既然实测零例外，就不必留「约束」这个选项让下一个人再判一次。

### 裁 6 · S1 第二关要不要挂到词汇表上

GLM（异议 2）说 S1 第二关「口号只能用日常词」没有可机械核对的判据：「结晶」「铸造（义务）」「路标」这类词不在核心产品词表里，但也不是一次性黑话，审计者只能凭感觉裁。它建议改成：不在 `glossary.md` 与核心产品词清单里的词一律报，由所有者裁豁免。

**我推荐：不采纳，改成就地裁这三个词。**

理由：那条规则会把成本转嫁给你。「结晶」在 `spec/README.md:51` 是一整节的立论，「铸造义务」是 Run 模块的核心动作，「路标」出现 25 处且是引擎与 HCTL 分责的关键比喻——按 GLM 的规则这三个每轮都会被报上来，而你每轮都要重裁一次。判例本来就是累积的，直接在这里裁一次更省。

我的建议是三个都留：它们各自在第一次出现处有释义或紧跟判据，符合 S1 第一关；也都不是两字压缩词，读者能从字面猜个八九不离十，符合第二关。若你判其中某个不合格，说一声，我按判例落。

### 裁 7 · 设计正文里的状态机口径怎么收

Grok（疑点 1）说四个模块设计正文和同名约束的边界不稳：「为什么存在」「模块拥有什么」「场景角色表」停在架构层是合格的，渗进去的是「关键规则」和「场景」后半——状态枚举（Task 三态、Scoped Room 归档前置）、适配器终局约束、P2 CLI 子命令、Dagu 和 Herdr 的产品名。

后果具体且可验证：约束层一放宽（例如归档允许显式结案），设计正文的复述就过期，而没有任何检查会发现。

**我推荐：设计正文只写可观察的产品规则，状态枚举、字段、阶段代号、实现名一律改成链接。** 但不要把设计正文降成目录页——「为什么存在」和场景角色表删掉，愿景层就会对象名不够用、架构层说不清怎么组装。

**这条卡住：** Grok #9、#11、#12、#14、#15 五条，是越层清单里最大的一组。

### 裁 8 · 契约测试里「只有主题名、没有判据」的条目怎么办

GPT（#71、#74、#75）报了三处，共九条用例只写了要检查的名词，没有输入、判据和预期结果，例如 `contract-tests.md:49` 只写「编译/Profile 拒绝、0..1 Task 绑定」。GPT 给了补全后的成品句。

这里有个隐患：**补不出来的那些，说明 spec 本身没写清。** 补全动作会把这件事暴露出来。

两个选项：

- **(a) 补全，补不出的单独记一条 spec 缺口。** ← **我推荐。** 契约测试的作用就是反向验证约束写清了没有；补不出来正是它该报警的时候。
- **(b) 本轮不动，等实现阶段再补。**

选 (a) 的代价是 `contract-tests.md` 会长（九条变约十五条），而且可能带出 spec 的修订，那部分要按「会改变含义」单独走。

### 裁 9 · T1 的 SHOULD 一档要不要留

K3 的全量计数：MUST 238 处，MAY 122 处，**SHOULD 0 处**。指南 T1 立了三档，语料只用了两档。我逐条查过唯三的 SHOULD 候选，三处都是 MUST（详见第二节）。

**我推荐：明说本语料只有 MUST 和 MAY 两档，删掉 SHOULD。** 理由是 HCTL2 通篇 fail-closed——能偏离、只需说明理由的规则，在这套设计里就不是约束。留一档从不使用的强度，下一个写作者会拿它当「不太确定的 MUST」的避风港，而那种句子本来就该改写或移出规范文本。

反对这个改法的理由也成立：留着它不花成本，将来真出现建议性规则时不用改指南。你拍。

### 裁 10 · 词汇表的中文对照要不要继续要求

文档纪律写「专有名词保留英文，但每个文档第一次出现时给中文对照」。K3 的计数显示这条**基本没被执行，而且分成两种情况**：

| 类型 | 例子（英文次数／中文次数） | 中文对照实际被用吗 |
| --- | --- | --- |
| 真译名 | 仓库 41、上下文 40、施工图 32、裁决 30、凭证 28、参与者 25 | 用，且比例合理 |
| 释义式对照 | Task 361／任务承诺 1、Run 297／一次受治理施工 1、Workbench 81／工作台 1、Agent 54／执行治理模块 1、Terminal 46／终端场景 1 | 全库只出现一次，就在词汇表里 |

区别在于后一类根本不是翻译，是定义。「一次受治理施工」没法在句子里替换 Run，写「这次受治理施工的 Manifest」比写「这个 Run 的 Manifest」更难读。所以这条纪律对释义式对照是不可执行的。

**我推荐：把纪律拆成两句。** 有自然中文译名的（仓库、看板、参与者、上下文、施工图、裁决、凭证、技能包、工件、备忘）按现规则，每个文档第一次出现给对照；只有释义式说明的（Task、Run、Agent、Workbench、Terminal、Seat、Obligation、Attempt 等），**词汇表给一次定义即可，正文不再要求括注**——正文里反复插入「Run（一次受治理施工）」只会打断阅读。

## 二、四家交叉验证

### 三家独立收敛到同一处：代次家族缺一张总表

Grok（簇 A）、GPT（#28、#31、#53、#59）、GLM（B19）从三个不同角度撞上同一件事：**六个 generation，六处各自定义，没有一处把它们排齐。**

- Grok 查结构，发现 `spec/agent.md:64`、`spec/connections.md:99–103`、`spec/run.md:79`、`glossary.md:107` 各写了一遍「这几层不是一回事」，但没有一处给出六行对照。
- GPT 查语言，发现 `connections.md:151` 用「backend generation」，而全书其他地方叫「Agency binding owner generation」——**同一个东西两个名字，且没有任何一处声明它们相等**。
- GLM 查语言，发现 `glossary.md:107` 一句话里挤了五个代次概念。

这是本轮最强的归并候选，也是唯一一处三家独立命中的。Grok 已经把六行表的内容整理好了（成员、管哪块资源、权威落点、何时产生、能不能从别的推导），可以直接用。

### 两处「一张表，四个名字」——我改判的

这两条是我在核对四家结论时查出来的，两家的报法都不准。

**其一：七层身份链。** GPT #60 说「七层身份链在本文和链接中都没有列出，读者无法知道下层具体是哪几层」，并建议把这个说法整个删掉，改写成「Agency 只提供模型、Worker Profile 和 Execution Runtime 这三类」。

**这个建议不能采纳**——七层是列出来的，就在 `participant.md:13`，一张七行表（参与者身份、项目角色、人设、模型与特殊训练、Skill、执行者配置、一次物理执行）。按 GPT 的改法会删掉一条真实的跨文件引用。

真正的毛病是**同一张表有四个名字**：`participant.md:13` 叫「七件事分层」，`design/README.md:86` 叫「七层拆分」，`participant.md:45` 叫「七层链」，`spec/agent.md:66` 叫「七层身份链」——而且后三处都没有链到那张表。改法是统一叫法并补链接，属于只改写法。

**其二：恢复等级与保证等级。** GLM B12 说这两个词在 `agent.md` 并存、无区分释义，读者无法确定是一个概念还是两个，需要对照 spec 才能裁。我查了：**是同一件事，四个名字。**

`agent.md:38` 有一张表定义了 exact attach / semantic resume / replay 等档位。`agent.md:30` 管它叫「恢复等级」，`agent.md:46` 和 `:69` 叫「保证等级」，`spec/agent.md:66`、`:68` 叫「恢复等级」，`spec/agent.md:86` 叫「Terminal 各能力」。四个名字指同一张表，没有一处声明它们相等。

改法同上：统一叫法，其余位置链回定义处。也是只改写法，不改变任何判定。

### 四家之间的分歧：两处，我判 K3 对

GPT 按 T1 报了两处「需要」，K3 的逐处标注把同样两处判成「客观必要」。这是本轮唯一的正面冲突。

- **`spec/system.md:70`。** 原句是「**需要**提交 HCTL 命令却无法提供等价预览、版本或权限信息时，动作**必须**禁用、保留为待处理请求或安全拒绝」。GPT 说这里的「需要」承担 MUST、强度不明。**K3 对**：「需要」在条件从句里（「当某个动作需要提交命令时」），真正的义务由同句后半的「必须」承担，没有强度歧义。GPT 给的重写句仍然更好读，但它属于 L5 长句拆分，不是 T1 违规——**改法不变，归类要改**，否则会被当成强度错误去调档。
- **`spec/README.md:14`。** 原句是「某个步骤的产物：只追加、短期或一次性，但**需要**被精确引用」。这是票据族的判定条件，不是义务句，K3 的「客观必要」成立。GPT 的重写（改成「而且后续规则可以精确引用它」）仍然值得采纳，理由同样是可读性而非强度。

结论：这两处照 GPT 的句子改，但不计入 T1 的强度问题。**T1 的真实违规只有 3 处**，就是上一节那三条。

### 结构与用词双重命中的三处

判例二要求结构和用词分开报，四家照做了，于是同一位置出现两条记录。这三处是重叠最密的，落地时要一次改完，不能分两个 PR 各改一半：

| `participant.md:45` | #17 上浮：商业化延长线是愿景写进了架构 | GLM B18（「劳务市场的形状」「同构」）、A12（「供给约束」） |

### 只有 K3 捞到的（机械扫描的净收益）

五样东西两轮人工通读都没发现，只有全量计数能看出来。

**其一：整个语料里没有一条 SHOULD。**

| 档 | 用词 | 处数 |
| --- | --- | --- |
| MUST | 必须 125 + 不得 66 + 只能 46 + 禁止 1 | **238** |
| SHOULD | 应当 0 + 不应 1（且那 1 处在 `usage.md`，非规范文档） | **0** |
| MAY | 可以 | **122** |

T1 立了三档，实际只用了两档。K3 从 80 处「需要」里挑出 3 处实质是义务的，本来是 SHOULD 的候选——**我逐条查了，三处全都不是 SHOULD，是 MUST**（见下一条）。所以这一档不是「写漏了」，是这套设计里真的没有「默认如此、偏离说明理由」的规则：HCTL2 是 fail-closed 的，能商量的规则就不是约束。

这需要你拍一下（**裁 9**）：T1 是保留空着的 SHOULD 一档，还是明说本语料只有 MUST 和 MAY 两档、写不出 MUST 的规则一律移出规范文本。我倾向后者——留一档从不使用的强度，下一个写作者迟早会拿它当「不太确定的 MUST」的避风港。

**其二：那 3 处「需要」不是档位问题，是同一条规则被写了两遍。** 我把三处都查了：

- `architecture.md:49`「既有 content 能否迁移……**需要**单独预览和校验」——同一条规则在 `contract-tests.md:96` 写作「既有 content 迁移**必须**显式预览、导出、导入并回读校验」，权威在 `spec/system.md:34`。架构层用弱一档的词复述了约束层的 MUST。
- `spec/connections.md:145`「范围、权限、候选或验收含义变化**需要**显式替代」对 `spec/run.md:65`「范围、验收、候选、权限、Gate ……变化**必须**创建替代 Run」。**两处都在约束层**，强度词不同，列举项也不同（前者三项，后者六项）。这不只是文风问题——两份规范文件对同一条规则给出不同的清单，实现者按哪份写都能说自己合规。
- `spec/system.md:55`「不可信扩展**需要**操作系统强制隔离和能力削减的代理接口」——没有第二处，是真的漏写了强度词。

前两处的改法不是把「需要」换成「必须」，而是**删掉复述、改成引用**；第三处直接补成「必须」。

### 判例：约束／契约／清单（裁 4＋5 的判据，进指南 L7）

三个词各管一种机制，判别就问「偏离了会发生什么」：

- **约束**＝遵守／违反。单向规则，spec 对实现立的；违反是实现 bug（CT 红）。constraint 一律译约束。
- **契约**＝采纳／分歧。双方约定，偏离是领域事实（分歧待裁、重新采纳）。验收契约一族本来就对；「契约测试」是业界成词，保留。
- **清单**＝冻结／逐项核对。单侧声明的逐项要求，checklist 味正是本义（施工清单、根上下文清单同族）。「终局结果契约」3 处属此类，改「终局结果清单」。

落地口径：结构专名 112 处（约束层／模块约束／写入约束）与验收契约族不动；「约束测试」4 处是 #119 误伤，改回「契约测试」；20 处复合名词残留逐处判源概念——contract 义改契约／清单／约定，constraint 义按句意选规则／条款。

### 判例：路标、铸造、结晶（进指南 S1）

- **路标：不合格。** 所有者当场问「路标是啥」——最重要的读者从字面猜不出来，且它是三名一物（路标 25／机械位置 5／Engine 位置 2）、全库无定义。整族清掉，不再立第四个术语，用两个平常短语：概念写「**引擎报告的进度**」，失联场景写「**引擎停报进度**」；同段复指顺写「该进度」；引擎侧具体对象仍叫 Engine 检查点。「引擎」二字不是地点是**出处**——语料里有两套进度（引擎自报的机械进度、HCTL 账本的语义进度），两权分立要求词汇层面就分清是谁的一面之词。
- **铸造：不合格。**「铸造义务」中文不成话（17 处，另 3 处在来时路不动）。换平常词「**创建**」；原来靠动词暗示的「造币权只在 control」改由句子明写主语承担——这正是 L2 本来的要求，「铸」一直在替句子偷懒省主语。「铸造条件」→「创建条件」。
- **结晶：合格，留。**「智慧的结晶」是中文固有用法，不是生造比喻；`spec/README.md:51` 有整节定义；机制义（判决落 Git 的只读沉淀，回灌不能伪造未结晶判决）平替会啰嗦一圈。

我在裁前对路标、铸造的「合格」判断是错的，教训与自造词那两次打回同源：有就地定义不等于读者读得懂，裁词以读者当场能不能接上为准。
