## M · 方法论（判断单位：场景之间的一条边）

| 编号 | 问题 | 不过的样子 |
| --- | --- | --- |
| M1 | 这条边两侧是不是两个阶段：换了人、换了系统、或换了责任？ | 两侧同一个人在同一个系统里连续干，边只是名字 |
| M2 | 过这条边的东西有没有唯一的交付物？ | 递过去的是一堆散件，或者同一件事有两种交付物 |
| M3 | 什么条件下算过去、谁判、判据是机械的还是散文？ | 条件写成「准备好了就」；判的人不明；判据只有一句话 |
| M4 | 别家有没有这条边？别家递什么？ | 别家普遍没有这条边而我们有；或别家有而我们没有 |
| M5 | 快：过这条边多不多一个来回？ | 过边要求人或模型再确认一次同样的事 |
| M6 | 省：过边要不要重读一遍上下文？ | 接手方拿不到结晶，只能重读聊天或重跑 |
| M7 | 好：这条边换来了什么质量？ | 说不出一个没有这条边就会出的错 |
| M8 | 是否过早投票：市场没收敛、我们已把一种做法写进约束？ | 约束层钉死了一个别家还在两三种做法之间摇摆的选择 |

## A · 模块与架构（判断单位：一个具名概念，或一条条款所在的层）

| 编号 | 问题 | 不过的样子 |
| --- | --- | --- |
| A1 | 概念过不过门槛：独立生命周期、恢复边界、权限边界三者有其一？ | 三者皆无，却有自己的名字 |
| A2 | 概念在不在该在的层（四层路由表）？ | 愿景层出现字段名；约束层出现「为什么更好」 |
| A3 | 它是核心概念，还是实现方案？ | 名字描述的是「怎么做到」而不是「是什么」 |
| A4 | 概念成族了吗，族规则只定义一次吗？ | 同族成员各写一套规则 |
| A5 | 条款的目的能否用一句「它为什么在这」复述？ | 复述不出来，或复述出来发现目的在别处已被满足 |
| A6 | 模块能否覆盖方法论要求的全部功能？ | 方法论轴发现的某个阶段或交付物没有模块认领 |
| A7 | 同一概念是否有两个名字？ | 同一层里两个词指一件事 |

## I · 具体实现（判断单位：一条「必须」背后的强制手段，或一个部件）

| 编号 | 问题 | 不过的样子 |
| --- | --- | --- |
| I1 | 这条「必须」由什么强制：账本机制、适配器回读、还是只有文字？ | 句子里没有任何机制词，也没有引用到定义机制的条款 |
| I2 | 只有文字的，能不能改成机制？ | 能用比较并交换、摘要、租约、代次或归约表达，却写成了对模型的叮嘱 |
| I3 | 这个部件的业界最佳实践是什么？ | 没有问过就自己写 |
| I4 | 借用等级与取舍：跨平台二进制、SDK、复制代码、借鉴想法？ | 能借二进制的借了想法；超集的复杂度没算过账 |
| I5 | 我们自己写的部分是不是胶水？ | 第一方代码里出现了别家已经解决的通用功能 |
