## 一、角色与保险

- **审**：Fable，四条轴全部。
- **对抗核验**：新开上下文的 Fable 子代理，一轴一个；只拿到发现清单和文档，拿不到我的推理过程。任务只有一件：默认怀疑，逐条推翻，每条结论必须引用约束原文。「改含义」的条目一条不免；我最近写的文件（`participant.md`、`spec/participant.md`、`context.md`、`architecture.md` 的 Terminal 行、`docs/research/methodology-mattpocock-skills-20260902.md`）列为重点。
- **改**：需要知道「为什么」的改动归 Fable：愿景、架构正文、模块边界、方法论投票、来时路。能写成一条可核对指令的改动，默认也由 Fable 用子代理做，不另开一轮传话；所有者想并行时，把对应任务书（第三轮会写好）直接扔给另一家 harness 即可。
- **裁决**：所有者，只在第二轮。

## 二、三轮怎么走

```text
第一轮 · 长跑（Fable，无需所有者）
  1.1 定标与脚手架  → 状态板、检查表、清点脚本
  1.2 机械清点      → 四张表进 10-inventory.md
  1.3 业界调研      → docs/research/ 条目 + 边界对照
  1.4 通读与发现    → 11-findings-draft.md（按层逐文件写，不在脑子里攒）
  1.5 对抗核验      → 12-adversarial.md，合成 13-findings.md
  1.6 裁决包        → 20-verdict-packet.md，开 PR、自合，停
第二轮 · 拍板（所有者，一次）
  在裁决包里逐条填「同意 / 否 / 改为」，或在聊天里说，Fable 回填
第三轮 · 长跑（Fable）
  3.1 方法论与边界批 → 3.2 概念与分层批 → 3.3 机制与部件批 → 3.4 写作批 → 3.5 抽成评审 Skill
  每批一个 PR；收口 README
```

第一轮预计要跑很久，这是设计好的：所有者不用在中间出场。会话中途被压缩或换机器都没关系，状态板加已提交的中间文件就是全部状态。

## 三、第一轮，逐阶段

### 1.1 定标与脚手架

- 在本目录建 `README.md` 状态板：阶段、状态、产出文件、最后更新的 sha。
- 把四轴原则改写成四张检查表，写进 `02-checklists.md`。每张表的每一行都能对一个位置说「过」或「不过」；行首带编号（M 方法论、A 架构、I 实现、W 写作），发现清单引用编号当判据。检查表的起点：

| 轴 | 检查表要覆盖的问题 |
| --- | --- |
| M 方法论 | M1 这条边两侧是不是两个阶段（换人、换系统、换责任）；M2 过去的是什么，有没有唯一的交付物；M3 什么条件下算过去，谁判，判据是机械的还是散文；M4 别家有没有这条边，别家怎么递；M5 快：这条边多不多一个来回；M6 省：过边要不要重读上下文；M7 好：这条边换来了什么质量；M8 是否过早投票——市场未收敛而我们已写进约束 |
| A 架构 | A1 概念过不过门槛（独立生命周期、恢复边界、权限边界三者有其一）；A2 概念在不在该在的层（四层路由表）；A3 是核心概念还是实现方案；A4 概念是否成族、族规则是否只定义一次；A5 条款的目的是否被文本遮住（能否用一句「为什么在这」复述）；A6 模块能否覆盖方法论要求的全部功能；A7 同一概念是否有两个名字 |
| I 实现 | I1 这条「必须」由什么强制：账本机制、适配器回读、还是只有文字；I2 只有文字的，能不能改成机制；I3 这个部件的业界最佳是什么；I4 借用等级（二进制、SDK、复制代码、借鉴想法）与取舍；I5 我们自己写的部分是不是胶水，还是重新造了轮子 |
| W 写作 | 沿用写作指南全部条目与 S1 两关；新增 W1 驼峰拼接名；W2 同一层同一表内中英夹杂；W3 关键词汇中英互译是否准确、是否自造词或错词频 |

- 清点脚本放 `src/build/docs/`，用现有检查器同款工具（shell、perl，不引新运行时），每个脚本一个目的：

| 脚本 | 输入 | 输出 |
| --- | --- | --- |
| `inventory_concepts` | `repo//:docs_tree` 加词汇表 | 每个具名概念（代码体英文名、「」内中文名、词汇表词条）按文件、按层的出现次数；定义位置；首次出现是否给对照；驼峰拼接名清单；同一概念在同一层里中英两写的清单 |
| `inventory_edges` | `spec/connections.md` 的交接总表 | 每条交接四格：交付物、写入者、准入条件、失败处理；空格标 `—` |
| `inventory_enforcement` | `spec/*.md` | 每句含「必须／不得／只能」的句子，标出机制词（比较并交换、摘要、租约、代次、归约器、回读、outbox、幂等键）；无机制词的单列 |
| `inventory_components` | `delivery.md`、`docs/research/README.md` 条目索引 | 每个外部产品与第一方部件：目的、现选择、借用等级三列骨架 |

脚本做成 Buck 目标 `root//build/docs:inventory`（genrule，输出一个目录），第一轮只生成报告，不加进检查 profile；驼峰名与同层中英一致两项在第三轮清完之后才升为 `sh_test` 进 profile，否则现在必红。注意 Buck2 跑 `sh_test` 时 cwd 是 cell 根（`src/`）不是项目根，路径一律用 `$(location ...)`。新增脚本会触发 PR 门的调研要求：说明查过没有现成工具能对中英混排的设计文档做概念清点，脚本只做提取与计数、不做判断。

### 1.2 机械清点

跑 `root//build/docs:inventory`，把四张表原样放进 `10-inventory.md`，附生成命令与 sha。表就是表，不加评论；评论进 1.4。

### 1.3 业界调研

- **边界抽取**：对 `methodology-landscape-20260824.md` 审计基线表里的每个工具，按同一模板抽「阶段边界表」：

  | 阶段 | 阶段产物 | 跨越条件 | 谁判 | 判据是机械的还是散文 | 对应我们的哪条边 |

  写进 `docs/research/methodology-boundaries-20260902.md`（根目录，方法论类）。对照我们的六条边（连接约束总表），分三类列出：别家有、我们没有的边（遗漏候选）；只有我们有的边（过早投票候选）；别家交付物定义得更干净的边（改写候选）。
- **限时扫尾**：一个工作日内，只找 2026 年下半年新出、有真实用户的方法论工具，逐仓库 `gh api` 验证存在与活跃度，按一对象一文件进 `docs/research/`，宣传语不作数。找不到就写「无新增」，不硬凑。
- **部件矩阵**：填满 `inventory_components` 的骨架，加两列「业界最佳」与「取舍」，每行钉一个来源。已有研究条目的直接引用，缺的补条目。写进 `docs/research/build-tools/` 或对应类别目录，索引加行。

这一阶段的读源码、clone、比对交给子代理，主会话只收表。

### 1.4 通读与发现

- **顺序**：愿景层 → 架构层 → 约束层 → 交付与参考。读完一个文件就把发现写进 `11-findings-draft.md`，不在上下文里攒；跨文件的对照靠 1.2 的清点表，不靠记忆。
- **发现格式**（一行一条）：

  | 编号 | 位置（文件 §节名） | 发现 | 判据（检查表编号） | 建议 | 类别（只改写法 / 改含义） | 证据（原文或清点表行） |

  位置只写节名不写行号；建议要写到「能直接照着改」的程度，改含义的写清改前改后的含义差异。
- **每条边一张小表**（第一轴专用）：快、好、省三格，答「多不多一个来回、要不要重读上下文、换来了什么质量」，结论一句话。
- **目的高于文本**：对每条条款先写一句「它为什么在这」，写不出来的本身就是一条 A5 发现。

### 1.5 对抗核验

- 一轴一个新开上下文的 Fable 子代理。给它：`13` 之前的发现清单、文档、四轴原则、检查表；不给它我的推理。指令：默认怀疑，逐条给「维持 / 修正 / 推翻」，每条必须引用文档原文，推翻要说清哪一句话证明发现不成立。
- 结果进 `12-adversarial.md`。合成规则：推翻的删，修正的按修正后写，维持的保留；合成后的清单是 `13-findings.md`，每条带核验结论。
- 我最近写的文件里的发现，核验子代理要额外回答一句：作者是否在为自己的写法开脱。

### 1.6 裁决包

`20-verdict-packet.md` 只放「改含义」的条目，按五组排列：方法论投票、概念增删、机制改造、部件替换、写作规则。每条带位置、发现、判据、建议、核验结论，末尾留一格给所有者填「同意 / 否 / 改为」。

**分两档，减少所有者的工作量**：

- **A 档必须逐条答**：方法论投票、模块边界、任何要推进版本号的条目。
- **B 档默认按建议执行**：概念增删、机制改造、部件替换、写作规则。所有者只标反对的；没标的视为同意。

所有者可以一句话把 B 档改成「也逐条答」。「只改写法」的条目不进裁决包，第三轮直接落。

第一轮以一个 PR 收尾：本目录全部文件加 `docs/research/` 新条目加清点脚本，PR 描述按模板三节，CI 绿自合。合完更新状态板，停，等第二轮。

## 四、第二轮：拍板

## 六、会话纪律

- 每完成一个阶段就提交到本轮分支并更新状态板；阶段内不攒大提交。
- 主会话只读表、写判断、派子代理；clone、读源码、对抗核验、机械修改都交子代理。
- 位置引用一律「文件 §节名」，不写行号，不写篇幅。
- 分支名 `claude/review-r1-*`、`claude/review-r3-*`；合并前先 `git checkout` 离开题目分支；BEHIND 就合一次 main 再合。
- 遇到需要所有者拍板的事，不在第一轮中途停下问，写进裁决包的 A 档，继续跑。
