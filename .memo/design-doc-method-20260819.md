# 设计文档写作原则与修订方法（v0.8 → v0.9 大修记录）

> 日期：2026-08-19<br>
> 主题：从 v0.8 过度精简到 v0.9.0 愿景恢复、v0.9.1 概念归并与分层的完整方法论<br>
> 用途：所有者提出的原则与工作方式的忠实记录；未来可抽取为“设计文档写作”的 skill/规范。

## 背景

v0.8.0 把规范收敛为四模块时，以“移除平行权威”为由连愿景层一起删除，文档退化为纯合同。v0.9.0 恢复愿景层；随后的概念清点暴露出 75+ 个具名概念满天飞的问题，引出 v0.9.1 的分层与归并。本备忘记录这两轮修订中沉淀下来的原则。

## 写作原则（所有者提出）

1. **权威去重只针对合同，不针对解释。** 一个对象只能有一个定义；但愿景、论证、体验叙事不与合同竞争权威，不得因“重复”或篇幅被删。删掉“为什么”，合同就失去裁决新问题的方向。
2. **设计文档必须回答为什么。** 每个模块开篇要有“为什么存在”；全库要有愿景层（一句话定位、失败模式、心智模型、目标体验、命名原则）。
3. **心智模型可以保留而不构成流水线。** 表述精准优美的模型（如四阶段链“意图 → 承诺 → 治理 → 运行”）不要因为怕误读而删除——加一句消解误读的话即可（“一件事不必完整经历四个阶段”）。
4. **说人话。** 用自然中文认真写作；中文语境不常用的音译行话必须翻译（spike → 限时验证，dogfood → 自举自用）；专有名词保留英文，但每个文档首次出现时给中文对照（Participant（参与者））。
5. **概念引入有门槛。** 每个具名概念都是一次认知税。只有具备独立生命周期、独立恢复边界或独立权限边界之一的才配有名字；否则它是字段、步骤产物、状态值或引用格式。LLM“觉得需要就顺手起个 CamelCase 名”是主要污染源，必须定期全量清点。
6. **分层写作，信息不平铺。** 设计层只用约 20 个产品词 + 日常语言的规则（“每个变更集同时只有一个写入者”）；合同词汇（复合对象名、状态机、写入者表）下沉到 spec 层；实现名（字段名、锁文件路径）不进设计文档。类比：任何应用都有几百个类名，没人把它们写进设计文档。
7. **附着公开标准与事实标准，不重复造轮子。** 四个场景都有外部概念体系可以直接引用：Chat Room ↔ Matrix/Slack，Kanban ↔ Linear/GitHub/Jira 事实词汇，Workflow ↔ Conductor/BPMN，Terminal ↔ PTY/tmux/ACP。既然承诺第三方客户端可按场景接入，场景概念就必须说第三方听得懂的话；自造词只保留确有差异化语义的部分（Obligation、Verdict/Receipt、写租约）。
8. **概念按族归类。** 族的共同语义定义一次（Revision / Binding / Receipt / Lease / Intent / Snapshot 六族），成员一行导出；学会族规则 + 核心词，任何复合名都能现场解码。
9. **不是每个东西都是类。** 执行路径上的一个步骤、一份冻结字段组、一张短期票据，都不是领域对象；把它们建成类是过度建模。
10. **结构与框架的可读性优先。** 修订可以推倒重组结构，不必在现有结构上修修补补。

## 修订方法（这两轮实际使用并验证有效）

1. **全量对比评审先行**：按文档簇多路并行评审新旧版本，合并去重后逐条对抗核验（默认怀疑、设法驳倒），再由人裁定哪些属于错误删除。
2. **恢复与归并分开提交**：v0.9.0（恢复愿景）与 v0.9.1（概念归并）各自成 commit，各自可回滚；决策记录进 decision-history。
3. **合同语义冻结**：恢复/重组过程中既有合同文本只做“插入包围”或带评审的等义搬移，不顺手改语义；每轮改动后跑独立的合同漂移核验。
4. **多视角核验**：每轮至少覆盖四个独立视角——覆盖度（该恢复的都恢复了吗）、合同漂移（语义变了吗）、语言（说人话了吗、首现对照给了吗）、结构一致性（链接/锚点/版本串/图）。
5. **概念清点工具化**：用正则全量提取 CamelCase 名 + 出现次数 + 是否在对象表中定义，暴露“顺手起名”问题；按门槛逐个裁决：保留 / 并入 / 降级 / 除名。

## 未来抽取 skill 时的骨架建议

评审一份设计文档时依次问：它回答“为什么”了吗 → 它在正确的层写作吗 → 每个具名概念过门槛了吗 → 概念成族了吗 → 场景概念对齐外部标准了吗 → 它说人话吗。
