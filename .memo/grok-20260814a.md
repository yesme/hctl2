## 项目现状

这是一个**纯设计阶段**的仓库：没有可安装应用、可执行 CLI、构建脚本或测试套件。权威基线是 Draft v0.7.0（2026-08-14）。README 已明确标注这一点，没有夸大实现状态。

四层语义模型（Room → Task → Run/Gate → Attempt/runtime）和事实源边界写得比一般设计文档严：Workbench 只投影、Conductor 只做机械状态、外部 tracker 只拥有配置字段、evidence 压过自述。参考实现准入规则清楚（First Tree → L4，Codeg → L3，HCTL1/Conductor → L2，Orca → L1）。`invariants.md` 对 L3 source 字段授权、completion、Engine effect 的禁止项足够硬，能当实现合同。

真正会卡住实现的，不是“层分不清”，而是若干被当一等公民使用却未定义的对象、一条能绕过 effect authority 的 Engine 路径，以及 Phase 1 验收面和交付范围互相打架。

## 做得好的地方

- 参考实现准入规则清楚：不允许用 donor 同名概念反向定义公共对象。
- SoT 切分整体自洽：SQLite 管操作态，Git 管可共享产物，Conductor 管机械 token，Harness/PTY/worktree 都是可替换执行资源。
- `invariants.md` 与 layer contract 大体可互相印证。
- README 诚实标明“尚无安装/构建/测试”。

## 优先修订顺序（若后续改设计）

1. 定义 Artifact 与 ChangeSetRevision（Issue 1–2）——否则 Gate/Receipt 无法实现。
2. 收口 HUMAN / SUB_WORKFLOW 与 L2-ENGINE-01（Issue 3）。
3. 拆 Phase 1 验收面（Issue 4），删 lifecycle 政策逃生口（Issue 5）。
4. 冻结 Phase 1：单 TaskRevision/Run、CLI 名、单写锁、AttemptSpec。

## Issues

### Issue 1 -- Severity: bug

- File: docs/design/layers/l2-workflow-governance.md:137
- Description: Regate、quorum 和 Phase 1 的 19 步治理切片都把 `ChangeSetRevision` / `ArtifactRevision` 当成 Verdict/Receipt 绑定的不可变 subject（`subject digest mismatch` 会使旧票 stale；切片步骤 7 和 12 铸造 “ChangeSetRevision 1/2”）。`domain-model.md` 只定义了 `ChangeSet`（写/证据边界），并说 Verdict 绑定一个未命名的 “immutable subject revision”。Glossary 既没有 `ChangeSetRevision` 也没有 `ArtifactRevision`，也没有 digest 配方（Git tree/commit SHA vs 领域对象 vs Artifact 快照）。两个实现者可以各自满足正文，却做出不兼容的 subject 身份，从而破坏 X-REV-01 / L2-GATE-02，并使 Receipt 无法重放。
- Suggestion: 在 `domain-model.md` 里把 subject 定义成单一 typed object（推荐：`ChangeSetRevision = {change_set_id, revision_id, tree_or_commit_sha, parent, digest}`，并写清何时 `ArtifactRevision` 才是另一个 subject）。写明 Verdict/Receipt 的 `subject_revision` 就是该 digest；author rework 只推进这一身份；除非 scope/acceptance 变化，TaskRevision 保持不变。更新 glossary，并去掉 `lifecycle.md` 里非正式的 “ChangeSet/Artifact revision” 措辞。
- Status: open

### Issue 2 -- Severity: bug

- File: docs/design/domain-model.md:49
- Description: Artifact 是面向用户的一等公民——Project 内容、Room/Task/Run 邻近导航、“verified Artifact is implementation truth”、`artifacts` 表、`Artifact Diff` timeline items、`ArtifactRevision` 作为 gate subject——但声称“对象含义与 identity 的唯一完整定义”的 `domain-model.md` 从未定义 Artifact。Glossary 也没有这一条。实现者会在“任意 Git path”和平行 `artifact_id` 图之间分叉，然后对 Memo、PR、spec、ChangeSet 输出是否算 Artifact 各写各的。
- Suggestion: 补 Artifact 对象：稳定 `artifact_id`、Project/Repo 作用域、kind（spec/code/doc/PR-head/other）、Git path 或 blob 身份、revision/digest、与 ChangeSet 的关系、谁可以 publish。明确普通 Git 文件未 adopt 前不是 Artifact，且 Artifact ≠ Memo ≠ ChangeSet ≠ Task。
- Status: open

### Issue 3 -- Severity: bug

- File: docs/design/layers/l2-workflow-governance.md:66
- Description: Phase 1 HCTL Profile 允许 `HUMAN/WAIT`。`WAIT` 被标成不创建 Obligation 的 Engine control task（`l2-workflow-governance.md:99`，`domain-model.md:165`）。`HUMAN` 从未分类。L2-ENGINE-01（`invariants.md:62`）只说 control 可以 poll/complete/fail/signal HCTL **external** task——Conductor HUMAN task 不是 SIMPLE external worker，而是经 Conductor human-task API 完成。再叠上“Conductor UI 只读”，这仍留下第二条可写完成路径，除非明确禁止 HUMAN，或把它定义成只有 `hctl2-control` 在 HCTL Request 之后才能完成的 WAIT。按 Conductor 文档实现的人会接一条 human-task 队列，静默破坏 effect authority。
- Suggestion: 从 Phase 1 Profile 去掉 HUMAN，或定义为 control 拥有的 WAIT：无 Obligation、无 Conductor human-task worker，完成只走授权 Request 决议 → WorkflowEngineAdapter signal/complete。把 L2-ENGINE-01 扩到一切 Conductor mutation，而不仅是 external task。同一轮修订应要么从 Phase 1 去掉 `SUB_WORKFLOW`，要么定义子 execution 是否共用 `run_id`、Obligation 如何键、cancel/fence 如何下传。
- Status: open

### Issue 4 -- Severity: bug

### Issue 5 -- Severity: bug

- File: docs/design/cross-layer/lifecycle.md:166
- Description: Lifecycle 说只有显式 `CompleteTask` **或预先批准的 narrow policy** 才能写 `TaskCompletionReceipt`。L3-COMPLETE-01（`invariants.md:54`）说 Run completed、agent 自述、Git commit 和 provider Closed 不得产生语义完成。这条政策逃生口未定义（谁批准、可在什么条件触发、是否仍是 typed CompleteTask）。最自然的读法——“Run 绿了且有 Receipt 就自动完成”——正好是 L3-COMPLETE-01 禁止的第二完成写者。不变量优先于 lifecycle，但按闭环章节实现会出较弱规则。
- Suggestion: 删掉政策析取。完成只走 L3 admission 之后的 `CompleteTaskIntent`（acceptance + 所需 Receipts + 无未解决 contract divergence + actor authority）。若后续 ADR 想要 control 签发的自动完成，也必须仍是该命令，绝不能静默写 Receipt，且 Run-terminal 不得作为合法触发器。
- Status: open

### Issue 6 -- Severity: suggestion

- File: docs/design/layers/l1-execution-runtime.md:28
- Description: Attempt 作为 L2/L1 seam 的描述是对的（control 拥有 identity/candidates/admission；agentd 拥有进程观察；`attempts` 落在 L2 表组；SoT 行把 Attempt 判给 `hctl2-control`）。但 typed seam 对象 `AttemptSpec` 从未定义，Attempt 生命周期状态只散落各处（`Starting` 是 Run 状态，Attempt 用 `LOST`，RoomInvocation 用 `Interrupted`，对账用 Running/Waiting/Lost/Superseded/Orphan/Terminal Valid/Invalid）。文档还说 agentd 拥有 “Attempt lease/heartbeat/cancel”。没有字段列表和 `Attempt.status` 的单一写者，层正文禁止的第二份 Attempt truth 很容易在 `RuntimeRegistry` 里再造出来。
- Suggestion: 定义 `AttemptSpec`（attempt_id、seat_id、run_id、generation、WorkerProfile、HarnessAdapterBinding、ChangeSet、digests、leases、deadline）以及只由 control 在观察 agentd 之后写入的 Attempt 状态枚举。写明 agentd 的 cancel/heartbeat 是执行 control 命令加上进程事实，不是平行生命周期。
- Status: open

### Issue 9 -- Severity: suggestion

- File: docs/design/domain-model.md:149
- Description: Run 可以绑定 `0..N` 个 TaskRevision（亦见 `l2-workflow-governance.md:76`、L3-RUN-01）。未决问题 1（`validation.md:121`）仍承认默认 Task/ChangeSet/PR 基数和多 Task 集成分支政策未定。因此 Phase 1 允许一个多 Task Run，而其 merge/PR/worktree 政策并不存在。治理切片是单 Task；放任 `0..N` 不受约束，会产生一份日后变成“产品本身”的非正式分支政策。
- Suggestion: 在该 ADR 出现之前，Phase 1 Profile/领域冻结：每个 Run 最多绑定一个 TaskRevision（0 个允许用于非交付自动化）。把 `0..N` 留作后 Phase 1 句子，而不是当前合同。
- Status: open

### Issue 10 -- Severity: suggestion

## 结论

作为设计基线，Draft v0.7.0 在身份/SoT、donor 边界和可测试不变量上比常见设计文档更自律。需要处理的是实现阻断级缺口：未定义的 Artifact 与 gate subject、HUMAN 对 L2-ENGINE-01 的漏洞、Phase 1 验收面把已排除的 Chat bridge 当出门条件、以及 lifecycle 里可以自动完成 Task 的 undefined policy。其余是 Phase 1 冻结项和编辑性统一，适合走 ADR 或一次 v0.7.1 修订集中处理。
