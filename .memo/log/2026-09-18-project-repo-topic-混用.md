**Claude（摘要，全文是 `design/closure-control-repo-20260918.md` 的 §一到 §九）：**

先认账：09-17 那条路径里「project」担了仓库、话题、Project 对象三个意思，该在第一处就问「你说的是仓库还是话题」，没问。

四点的验证：第一个房间是 Repo Room，成立，现行正文每仓一个、与登记同寿命，要改的是它今天是二等房间，`repo_scope` 调用只能只读；术语一词一义列成表，Project 退出用户词汇；闭包〈控制面，仓库〉成立，现行已有一半这么写（用户级总入口不做、合并板仓库级、任务源绑仓库、Repo Room 每仓一个），跨闭包流动的只有 Agency 的工种、平台上的评审与合入事实、Git 对象、别的控制面的动作，正好是「单元与连接」的三种关系；一个推论是话题不跨仓库。三个视图无从属，成立，带一条例外和一个空位：例外是任务与 Run（一个 Run 最多认一张任务、一张任务同时最多一个活动 Run，这是完成凭证的主语）；空位是 Project 今天除了当容器还干的四件事（选人策略与预算、随版本冻结进 Task 和 Run 的策略摘要、写入型调用的准入前提、归档时的静止要求），去掉容器要有人接。

Project 对象三条路：甲退场（授权域四件事上移到仓库设置版本，目标、范围、名册、生命周期下沉到话题；Scoped Room 并入话题室，回填义务变可选；房间从三种减到两种）、乙改名为话题仍是对象不是容器、丙保留正式名用户词叫话题。推荐甲。代价：愿景的「Project-scoped」和「五个对象」要改口，模块名另议，是一次词汇批加一次约束批，决策史记转折，版本升 v0.19.0。六项拍板：闭包定义、Project 处置、`repo_scope` 只读放开、Scoped Room 并入话题室、关系表两条硬边、版本与批次。

**Claude（摘要，全文是 `design/closure-control-repo-20260918.md` §十）：**

就按这三份算第一手资料，别家的解读不算。用例里「project」七处，全是话题或两可，没有一处非得是容器：mac_ctl 在 gh-jssdk 上的两个 project 是一个闭包里的两个话题室，各有名册；cloud_ctl 每仓一个 project 分不出是登记仓库还是第一个话题室；ubuntu_bench 连的三个远程 project 是两个控制面、三个闭包里的三个话题室；共用对象库是放置，与话题无关。用户流程里的「project」全是仓库或「Repo Room 对话题室」：新建 project 选地址是登记仓库；ctl + project 闭包是〈控制面，仓库〉；一个 project 一个 kanban 是一仓一板，和 D 批完全一致；为 project 选人建聊天室是选人进 Repo Room；每个 project 三类内容是闭包的三个视图。

由此 `user-path-20260917.md` 的拍板项 1（入口先后）、2（一个 project 一个 kanban 怎么读）作废，是把词对错造出来的题；4、7 并入闭包备忘；3、5、6、8 仍待拍。顺带一处收敛：D 批的「启用看板的每个 Project 一个缺省源引用」按新口径简化成每个闭包一个。若拍板，S1 要过一遍词，不变量不变，只换主语。
