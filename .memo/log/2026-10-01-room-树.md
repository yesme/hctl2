## 主笔 · 一

分支 `claude/room-tree` 已从 `origin/main` 拉好。现在是讨论阶段，按纪律不提交。

repo 里的相关内容看完了：Room 的现行设计、v0.18.7 的扁平化、群体智能三原则、Context 的前情提要，加上 workbench/remote-control 两组 ADE 审计。先核实你的描述，再答三个问题。

#### 核实：基本正确，要补两处

pi 的会话确实是一棵树，主源是 [session-format.md](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session-format.md)。会话文件里每条记录带 `id`/`parentId`，从任意一条往回接新话就是"原地分支"，所有分支都留在同一个文件里。`/tree` 用来在分支之间跳。离开一条分支时，系统会用 LLM 把它总结成一条 branch summary，挂到新位置上。另外 `/fork` 会另起一个会话文件，并记下 `parentSession`，所以跨文件也是一棵树。

要补的两处：

- **这是"一个人 + 一个 agent"的会话树，不是多人聊天树。** 树长在单个 agent 的上下文上。
- **模型每次看到的永远只是一条线**：从当前叶子回溯到根的那条路径。树是给人管理上下文窗口用的工具，模型看不到整棵树。

顺带答你括号里的问题：SCM 那块现在叫 **Repo 模块**，场景叫 **Change（变更）**。

#### 1. 有没有别家这么组织 chat？

我们审计过的 ADE 里，没有一家把对话组织成 pi 这样的原地分支树。离得最近的是下面几类：

| 形态 | 产品 | 说明 |
| --- | --- | --- |
| 复制式 fork | Happy、HAPI、MindFS、Yoda | Happy 复制并截断 Claude 的 JSONL 来 fork 和回退；HAPI 直接用厂商自带的 fork；MindFS 能从历史任意一条消息 fork；Yoda 里 fork 会生成一个新任务 |
| 父子会话谱系 | MindFS、LobeHub、Grok Bot | 主 agent 和子 agent 的父子关系，比如 MindFS 把子代理会话导入成"会话树"，LobeHub 限一层。这是委派关系，不是讨论分支 |
| 频道下挂讨论串 | Claude Tag（Slack）、OpenClaw、Multica | 房间下面只有一层讨论串，Multica 是 Project → Issue → Task |
| 不是 chat 的树 | First Tree | 它的 Context Tree 是知识树（Markdown/Git），聊天本身是平铺的。名字最像，实际最不像 |

审计范围以外再补三家：LobeChat 从 v1.34 起支持[从任意消息开分支](https://lobehub.com/changelog/2024-11-27-forkable-chat)，有"带上下文"和"从零开始"两种模式；Claude Code 的 [`/branch` 和 `--fork-session`](https://code.claude.com/docs/en/sessions) 是复制出一个新会话；Matrix 的讨论串（`m.thread`）[规定只有一层](https://github.com/matrix-org/matrix-spec-proposals/pull/3440)。

**规律是：编码 harness 普遍会 fork，但做法是复制出新会话，会话之间是平铺的列表。只有 pi 把分支做成了一等结构。协作平台则一律是"房间加一层讨论串"。**

#### 2. 社区怎么评价？

**正面：被当作 pi 最有辨识度的能力。**

- Armin Ronacher 在[《Pi: The Minimal Agent Within OpenClaw》](https://lucumr.pocoo.org/2026/1/31/pi/)里称之为 side-quest：比如工具坏了，开一条支线去修，修完由系统总结回主线，主线的上下文不被污染。
- 用户在 GitHub 讨论里给的用法有三种：读书时每个问题从根上分出一支，每支都带完整原文但只聚焦一个问题；多步流程做完一步就回到起点再做下一步，省钱也防止上下文膨胀；从 agent 犯错的位置之前重来。

**质疑与摩擦：**

- 官方仓库有个帖子标题就是["What is the point of the tree functionality?"](https://github.com/earendil-works/pi/discussions/5205)。核心批评是：回到更早的分支时，**磁盘上改过的文件不会跟着回滚**，对话回去了，代码没回去，两边会对不上。
- 终端里的树不好导航。社区为此做了 pi-rewind 扩展，还有人专门写了浏览器界面。
- branch summary 和压缩一样会丢信息，被放弃的那条支线上的细节可能就此没了。
- 一位用户的定位很准："pi 更像 tab 补全，不是 vibe coding"。也就是说，树服务的是人在旁边精细掌舵的单人场景。

#### 3. 我怎么看

架构层的结论：**"Room 组织成树"成立，而且值得做；"一个 Room 里的对话做成 pi 式的树"不成立。** 这是两棵不同的树，必须分开看。

**第一棵：Room 与 Room 之间组成树。建议做。**

- 现状是两层：每个 Project 一间主 Room，下面平铺若干 Topic Room，Topic Room 不能再开子 Topic Room（`spec/project.md:62`）。放开这一条，Room 的组织就从列表变成了树，正好是你说的"在 ideas 上导航"。
- 我们现有的机制和 pi 几乎一一对应。开 Topic Room 时的**前情提要**，就是 pi 的 branch summary，而且更强：由人确认、可去敏、固定了来源。**"出生后各长各的"**就是 pi 的分支各自生长。
- 这也正好接上 9/19 定的群体智能原则二"chat room 会动态总结是不是要新开 topic room"：系统建议从当前 Room 长出一个子节点，不是往列表里多加一行。
- 不用自建。Matrix 的 Spaces 本来就是房间层级（`m.space.child`/`m.space.parent` 加 `/hierarchy` 接口），可以直接作为投影。要注意的是 Spaces 实际上是 DAG，一个房间可以挂在多个空间下。所以"谁是谁的父节点"要记在控制面存储里，以它为准，Matrix 只负责展示。
- 和"不强制 Room → Task → Run 包含链"那条规则不冲突，这棵树只在 Room 模块内部。

**第二棵：一个 Room 内部的对话分支。建议不做。**

- pi 需要这棵树，是因为单个 agent 的上下文窗口是一条线，人得亲手修剪。HCTL 的上下文问题已经由 Context 解决了：每次调用都会从 Room 里萃取一份 Context Bundle，执行体从来不读整条时间线。pi 用树手工做的事，我们已经用机制做了。
- Room 是多人共享的事实记录。同一时间线一旦分叉，不同参与者看到的"当前"会不一样。这会撞上三条现行约束：时间线由 chat server 线性给出，治理引用按事件 ID 冻结，Matrix 讨论串只有一层。
- pi 原生的单人场景在 HCTL 里也有对应：一个 harness 的 Execution Chat。如果派出的 harness 本身就是 pi，它自己就带这棵树，用不着 HCTL 再造一棵。

**美学上补一笔。**

- Change 的 Git 历史其实是 DAG，分了要合。Room 树是只分不合，结论去 Memo、Task 或施工图结晶，不回流成消息。
- 所以把两者区分开反而更好看：Room 🎄（只分支）、Kanban 🏊（泳道）、Workflow 🗺️（地图）、Change 🌿（分支加合并）。
- 如果想借 pi"支线总结回主线"的手感，可以给关闭 Topic Room 加一张**可选**的结题卡，回贴到父 Room。只能是可选的，v0.18.7 已经去掉了普通话题的强制回填。

#### 需要你拍板的三件事

1. **放开 Topic Room 嵌套，让 Room 组织成树？** 要不要设深度上限？关闭或归档一个父节点时，子树怎么处理？要注意，这和 v0.18.7 的扁平化是同一方向的反向操作：那次撤掉的是"仓库级 Room → Project → Scoped"这种跨层级的树，这次是 Project 内部按话题长出来的树，性质不同。但值得你确认一下，当时扁平化的理由是否也适用于这里。
2. **确认 Room 内部不做分支？**
3. **要不要关闭 Topic 时可选回贴结题卡？**

#### 一、编码 harness、Pi、协作平台：差别在哪

**规律是这样的。三类产品存的东西其实差不多：多数都给每条消息记了父节点，底下本来就是一棵树。把它们分开的是两件事。一是"现在停在哪条路径上"这个指针归谁；二是旁边有没有一个退不回去的第二方。**

| | 谁在看 | 指针归谁 | 想岔开时怎么做 |
|---|---|---|---|
| 单人聊天（ChatGPT、Claude.ai） | 一个人 | 这个人 | 原地分叉，用 ‹2/3› 切换 |
| Pi | 一个人 + 工作区 | 这个人 | 原地分叉（`/tree`），工作区不跟着动 |
| 其他编码 harness | 一个人 + 工作区 | 人能挪，工作区挪不动 | 复制成新会话，在列表里平铺 |
| 协作平台（Slack、Discord、Zulip、Matrix） | 很多人 | 谁也不能替别人挪 | 开新容器（讨论串、topic），链回出处，只许一层 |

- **单人聊天能原地分叉。** 指针只有一个主人，挪了不会误导别人。模型又不记事，每次请求都按选中的路径重新拼上下文，放弃的分支不留痕迹。所以 ChatGPT 和 Claude.ai 背后都是树，只是用小箭头藏起来了。
- **协作平台从不原地分叉。** 共享时间线是大家的共同参照，"我上面说过"必须指向同一处。如果谁能替别人挪指针，每个人看到的历史就不一样了，查过的平台没有一家这么做。分歧一律变成所有人都看得见的新容器，再链回出处：Slack 和 Discord 的讨论串、Zulip 的 topic（还能把跑题消息挪过去）、Discourse 的"另开话题回复"、Matrix 的 thread。
  - 而且普遍只许一层。据 Slack 设计团队的回顾，早期允许"回复的回复"，结果很快变得极其复杂，砍成一层才成功。Matrix 规范直接写了不能嵌套。
  - Reddit、HN、邮件也有深树，但整棵树大家共享，折叠只是个人的阅读偏好。
- **编码 harness 卡在中间。** 只有一个人，但多了一个不能分叉的第二方：磁盘上的工作区，还有跑着的进程、git 和外部副作用。对话退回去了，磁盘没退回去，模型就在一个已经不存在的世界里继续干活。所以它们收敛到三件事：
  1. 线性记录，加上"退回到第几轮"的标记，不给可浏览的树。Claude Code 的会话文件其实也是父指针树，退掉的分支还留在文件里，只是界面画成一条线。
  2. 回退时可以选择连文件一起回，但总是回不全（第三节细说）。
  3. fork 就是复制出一个新会话，在列表里平铺，多数不记来源。本轮复核的 Codeg、Superset 都是这样。要并行跑的分叉，连工作区一起复制：Claude Code 现在的 `/fork` 自带独立 worktree。

worktree 就是编码 harness 版本的"另开一个讨论串"：共享的可变状态不能同时处于两种状态，那就把容器拆开。三类产品背后是同一条规律。

**Pi 是编码 harness 里唯一把单人聊天那套搬进来的。** 它的会话文件就是树：`/tree` 在同一个文件里跳到任意节点接着聊，离开的分支可以生成一段摘要带过去，还能打书签。代价是工作区这个第二方它也躲不开：`/tree` 只动对话，不动文件。

**本轮复核刚好看到反向验证。** 同一个分叉操作，产品一进多人平台就换了实现：
- Hermes Agent 的 `/branch` 在桌面端是父会话下的分叉，侧栏嵌成树；到了 Discord、Slack、Matrix 上，默认另开一个同级讨论串。
- Claude Tag 的 `!fork` 把 Slack 讨论串续到一个新讨论串，两边互相链接。

**对 HCTL2 的含义（架构层）：** Room 是多方的（人加模型 Participant），所以 Room 里不该原地分叉。分歧的做法是新容器加一条回到出处的链接，这正是现在 Topic Room 的做法。"Room 是🎄"能成立的只有容器之间的树，也就是 Topic Room 下面还能不能再开 Topic Room；不会是消息树。

#### 二、Matrix 到底怎么做房间层级

**先更正我上次的说法。Matrix 确实有原生的房间层级（Spaces），但只有 Space 能有子节点，而 Space 本身不是聊天室。我们打包的 Cinny 还会把多层 Space 压成一层。所以"直接拿来做投影"要打折扣。**

1. **Space 是一种"文件夹房间"。** Matrix 里一切都是房间。Space 是创建时声明了 `type: m.space` 的房间，这个类型以后改不了。客户端不把它当聊天室：Element 打开 Space 看到的是房间目录，新建 Space 默认只有管理员能发言，规范也不鼓励在 Space 里发消息。可以这样理解：普通房间是文件，Space 是文件夹。
2. **父子关系由两边各写一条。**
   - 父 → 子：Space 里放一条 `m.space.child` 指向子房间，必须带 `via`（从哪些服务器加入），可选排序和"推荐"标记。
   - 子 → 父：子房间里放一条 `m.space.parent`，可以标 `canonical`，意思是"主父节点"。
   - 两条由各自房间里有权限的人分别写，互相不需要同意。Space 管理员可以把任何房间挂成自己的子节点，子房间不用点头。反过来，子房间自称的父节点，只有在父 Space 也列了它、或者自称者在父 Space 里有权限时，客户端才认。
   - 在普通聊天室里写 `m.space.child`"不起作用"，所以聊天室不能直接有子节点。
3. **为什么说它是 DAG 而不是树。**
   - 一个房间可以同时挂在多个 Space 下，这是设计目标：同一个房间可以属于好几个社区。
   - `canonical` 只是提示。规范原话是：只应有一个 canonical 父节点，但不强制；有多个时取房间 ID 最小的。
   - 环被"明确禁止"，但协议不拦，实现得自己防死循环。
   - 所以数据上是一般的有向图，约定当 DAG 用，客户端画成树。
4. **怎么读出整棵树。** `/hierarchy` 接口从一个 Space 往下走：分页、可以限深度、只沿父到子的方向走；同一个房间可能出现多次；可以跨服务器。实现层脚注：我们用的 Tuwunel 默认深度 3、最多 10。
5. **权限完全不继承。** 每个房间的权限只管自己。唯一的跨房间关系是"受限加入"：子房间可以写"某个房间的成员不用邀请就能进"。但这只在进门那一刻查一次，之后你退出父 Space，在子房间里照样还在。让权限沿树继承的提案 2021 年就开了，至今没进规范。想"把人踢出整个 Space"，只能一个房间一个房间地踢。
6. **消息层只有一层。** thread 不能嵌套，嵌套 thread 的提案没有被采纳。
7. **客户端差别很大。** Element 左栏是可折叠的嵌套树，也有完整的 thread 面板。Cinny（我们打包的 v4.12.6）把一个 Space 里所有子 Space 压成一层分类、不缩进，也没有 thread 面板。
8. **"有子房间的聊天室"在 Matrix 里的原生画法：** 把这个节点做成子 Space，里面放一个排第一的"主房间"承载聊天。Discord 桥就是这么映射的：服务器对应 Space，频道分类对应子 Space，频道对应房间。
   - 一个叶子 Topic Room 后来长出子话题，就新建一个子 Space，把原房间挂进去当主房间，再在上一级换掉链接。房间 ID 和历史都不变。
   - 代价是房间数大约翻倍，而 Cinny 里看到的仍然是压平的。

**上次那句"父节点以控制面存储为准，Matrix 只负责展示"，意思是：**
- Matrix 的父子链接是两个房间各写各的，可能互相不一致，可以有多个父节点，Space 里任何有权限的人（比如在 Element 里拖一下）都能改。这些都不适合当事实。
- HCTL2 本来就记着每个 Topic Room 是从哪条主 Room 消息或哪个 Request 开出来的（`spec/project.md:62`）。这就是唯一的父节点事实。
- Matrix 侧的链接由 HCTL2 按控制面去写，是投影。有人在 Matrix 侧改了，不反过来改控制面，只当作漂移，下次投影时纠正。
- 子树级的动作（归档整棵子树、调整子树成员）Matrix 不会级联，只能由控制面逐个房间执行。这正好落在"安全是策略面的事"那条约束上：控制面留一个策略点，不在 Matrix 里另外解决。

**现状和建议。** 现在的设计根本没用 Space：Project Room 和 Topic Room 在 Matrix 里是平级房间，靠 Room–Server Binding 对上号（`spec/project.md:190`）。如果要房间树，我倾向 Matrix 侧保持浅：一个 Project 一个 Space，所有 Room 都是它的直接子房间；树只在 Workbench 里按控制面的父指针画。
- 理由：Cinny 本来就会压平；子 Space 加主房间会让房间数翻倍；Matrix 在我们这里是 content 系统，层级属于控制面。
- 代价：Workbench 就位之前（`project.md:60`），用 Matrix 客户端的人看不到树。

#### 三、rewind 彻不彻底：两方辩论

**先给结论：没有一家做到"彻底"。所有工具都把"对话回到哪"和"文件回到哪"当成两件事，让用户三选一：都回、只回对话、只回文件。没有一家能撤销 shell 命令和外部副作用。Pi 站在最极端：核心只回对话，文件交给扩展。Codex 和 Amp 则在往回撤。**

**Pi 的"环境保持工具"。** 没找到叫 rcopy 的；npm 上同名的包是 2014 年一个无关的文件复制库。你记得的应该是下面这一类扩展。Pi 核心不碰文件，提议内置文件回退的 issue 和 PR 都被关了（#8152 标为 not planned），于是社区长出了三四十个恢复文件的包：
- **pi-rewind-hook**（166★，最完整）：每一轮把 git 快照绑到树节点上。在 `/tree` 跳转时问你"保留当前文件 / 恢复到那个点 / 撤销上次恢复"；在 `/fork` 时问"只要对话 / 都要 / 只要代码"。它还能顺着 fork 的来源链找快照。见第 5 张截图。
- **pi-rewind**（115★）：有 diff 预览和重做栈，但它按时间戳把树节点对到快照上，不够精确。
- **pi-workspace-history**：每轮前后各拍一次快照，README 写着"`/tree` 是真正的时间机器"，但不会悄悄覆盖它没拍到的手工修改。
- **Pi 自带的两个示例扩展正好代表两种态度：** git-checkpoint 每轮拍快照，但只在 `/fork` 时问要不要恢复代码；dirty-repo-guard 干脆在有未提交改动时禁止切换或分叉会话。
- Pi 核心另有 `/clone`，把当前分支复制成一个新会话文件。这是复制，不是保持环境。

**正方：回退必须连环境一起回。**
1. 对不上的后果很具体。Pi 讨论 #5205 的开帖原话："第 2、第 4 个任务已经写到盘上了，可 AI 不知道了。"#8152 把这叫作"无声的不一致"。Codex 的回退只回对话，相关 issue 至今开着；Gemini 文档也提醒"只回退代码的话，你可能得告诉模型"。
2. 需求一直在：Pi #1223、#5522，Codex #9618，Kimi CLI #599 都在要。Cline 的说法是：能连文件一起回，犯错的成本就降到几乎为零，所以才敢放手让 agent 自动执行。
3. Pi 的树让这个问题更尖锐。别的 harness 只能往回退，Pi 能在兄弟分支之间来回跳，每跳一次，工作区都可能和当前分支对不上。树越好用，越需要环境跟着树走，那三四十个扩展就是这么来的。

**反方：做不彻底，就别假装彻底。**
1. 副作用远不止文件。DeepSeek-Reasonix 的检查点文档写得最直白："bash 和外部副作用（rm、mv、写数据库、部署）不追踪，回退撤不掉。"Claude Code 文档自己列了一串不覆盖的：bash 改的文件、子代理的修改、外部改动。Kimi 直接写"代码改动不回退"。
2. 回退一半比不回退更危险，而且两个方向都出过事。
   - Claude Code：有人抱怨回退悄悄丢了没提交的手工修改（#64615），另有五个 issue 抱怨根本没回退；还有人把它叫作"挂着撤销菜单名字的数据丢失"。
   - OpenCode：有人"丢了 14 天的工作"（#10589），也有人反过来只想撤消息、保留文件（#7963）。
3. 厂商在后撤。Codex 删掉了实验性的 `/undo`，官方解释是"用的人不多，设计还给很多用户添了麻烦"。据 Amp 的公告，它不再在编辑或恢复时回滚文件，理由是模型自己撤改动更有分寸，回滚本来也只是尽力而为。
4. 人也是一方。#5205 里有人说："要是树能把磁盘改动也回滚，人就只能看着，没法真正参与。"人在两轮之间自己改的文件，全量回退会一起抹掉。
5. 版本控制才是对的工具。Claude Code 文档自己写着"不能替代版本控制"；Aider 每次修改都提交一次，`/undo` 就是撤销上一个提交。

**我的看法（架构层）。** "彻底"只对被纳管的状态成立：快照、提交能回去，没纳管的副作用永远回不去。而且只要工作区有不止一个写入者，"回退"本身就会毁掉别人的东西，这又回到第一节的第二方问题。所以诚实的设计不追求彻底，只做三件事：
1. 分叉或回到某个点时，把能纳管的外部状态冻结成引用，比如提交 SHA。
2. 不能纳管的，明确标出"未回退"。
3. 多方场景永不改写历史，只追加补偿。

HCTL2 已经站在这一边，而且结构上比 Pi 更干净：
- Room 时间线只追加（`spec/project.md:74`）。
- Run 不分叉会话：讨论背景写成施工图里的"上下文"一节，随版本冻结，原文说这"比把聊天会话复制给施工者更干净"（`run.md:73`）。
- 一个 ChangeSet 同时最多只有一个写入租约，工作树只是它可替换的物理资源（`spec/repo.md:51`），所以写入者只有一个。
- 开 Topic Room 时冻结阻塞对象（`spec/project.md:62`）。

所以在 HCTL2 里，"回到某个点重来"等于新开一个容器、再钉住那一刻的代码版本，而不是把谁退回去。如果以后 Topic Room 要承载"从这里重来"，前情提要里该钉住的是那一刻的 ChangeSet Revision。

#### 四、Pi 树的社区评价

**一句话：评测文章和重度用户很推崇它，但它在社区里不是"最爱的功能"。摩擦集中在三处：文件不跟着回、树大了难管、只有终端里能用。**（博客类来源被出口代理拦截，相关几条只看到检索摘要。）

**正面：大家拿它做什么**
- 管上下文窗口。Armin Ronacher 1 月的文章里的用法：开一条支线去修一个坏掉的工具，修完跳回主线，让 Pi 把支线总结成一段带回来，主线上下文不被污染。在新分支里跑 `/review` 也是同一招。
- 从走岔的路上退出来，或者回到压缩之前的某个点重新开始。
- 扇出兄弟分支：从同一个起点分别试 A、B、C、D。
- 读书或读长文档时，每个问题开一个分支，用户原话是"省钱，也防上下文膨胀"。
- 评测文章称它是 Pi"最强"或"最被低估"的功能；Composio 说"Pi 的树模型是更好的设计"。Hermes Agent 的分支功能 issue 直接写着"受 Pi 启发"。

**质疑与摩擦**
- **文件不跟着回。** 这是最大的一条，第三节已经详述；官方不收，交给扩展。
- **树只长不剪。** 删除孤立分支（#8883）和删子树的 API（#6500）都被拒，树会越长越大。
- **树大了就慢。** 长会话里 `/tree` 会卡死（#6478）；长条目被截断，有人要求能看全文（#5830、#6379）。
- **挂错分支。** 有些条目挂到了错误的分支上（#6558、#9178）；分支总结也会失败（#8845）。
- **只有终端里能用。** RPC 接口只提供 fork 和 clone，不提供原地跳转，相关请求被关了（#8645）。也就是说，任何非终端客户端都只能"复制成新会话"，退回到别的产品的做法。
- **跳转位置不保存。** 当前停在哪个节点不写盘，重启后默认回到文件里最后一条。如果跳过去之后没发消息，这次跳转就丢了。社区专门写了 pi-session-anchor 来补这个洞。
- **维护者基本不出声。** #5205 没有维护者回复；文件回退的提议被关闭时也没留评论。

**它在 Pi 里有多重要。** CHANGELOG 2,939 行里，提到树的有 57 行，提到压缩的 123 行，提到扩展的 469 行。"最爱的扩展"讨论有 35 条回复，没有一条提到树或回退工具。Pi 的重心是极简核心和扩展体系，树是一个被推崇的副产品。

**我的读法。** 大家称赞的全是"一个人管上下文"的用途；摩擦全来自第二方（文件）和规模（剪枝、性能、截断）。这再次支持第一节的结论：在 HCTL2 里，树应该长在容器这一层，而不是消息这一层。另外，Pi 的分支摘要和我们的前情提要是同一个想法：换路径时不复制全部历史，只带一段摘要加一个指针。Pi 的摘要格式是"目标 / 约束 / 进展 / 决定 / 下一步"再加文件清单，和我们"已定与未定分开写"很接近，可以对照着看。

#### 五、浏览器界面在哪；树和 DAG 怎么导航

**先更正：我上次说"有人专门写了浏览器界面"，指的是 #5205 里 shuowu 写的 pi-tree。它其实是基于 Pi SDK 的读书伴侣应用，有自己的会话，不读你的 Pi 编码会话。要在浏览器里看自己的 Pi 会话树，最完整的是 pi-session-manager。**

- **Pi 自带的。** `/export` 导出成 HTML，左边画整棵树（过滤和搜索与终端里一样），右边显示选中的那条路径，链接里能带节点 ID。`/share` 会生成一个私有 gist，可以在 pi.dev 上看。这是最省事的办法。
- **pi-session-manager**（190★，仍在活跃开发）：桌面应用，也能以本机服务器的方式在浏览器里打开；它也能读 Claude Code、Codex、OpenCode、Gemini 的会话。它的"Branch Atlas"视图三栏联动：一张分支图（节点加连线）、一列可折叠的分支段、对话正文（第 1 张截图）。
- **pi-tree**（shuowu）：左侧是"Session Tree"缩进列表，在分叉处内联展开，可以一层层点进去，带面包屑（第 3 张）。
- **pi-web**（7.0k★）：用一个下拉框切换分支，没有分叉的直线段折叠起来；它区分"从这里改"（文件内的分支）和"新会话"。
- **终端里：** Pi 自己的 `/tree` 是缩进列表（第 2 张）；pi-undo-tree 是 Emacs undo-tree 式的二维节点图加 diff 预览（第 4 张）。

同一棵树在这些工具里有三种画法：缩进列表、节点连线图、兄弟切换器（比如 ChatGPT 的小箭头）。最完整的 pi-session-manager 恰好是"图、列表、正文三者联动"，和下面工作流工具得出的结论一样。

Pi 的 `/tree` 里有几个可以直接借用的小技巧：
- 没有分叉的直线段不缩进，只在分叉处缩进。
- 按类型过滤：只看人说的话、隐藏工具调用、只看打了标签的条目。
- 标签当书签用；输入即搜索。
- 截图里它装着 2,759 条记录，依然能用。

**树和 DAG 怎么导航：业界答案相当一致。大纲为主、图为辅，两者联动；每个节点只认一个正式父节点，其他关系画成交叉链接，绝不复制节点。这一条能同时管 Room 树和 Run DAG。**

**仓库现状。**
- Run 已经定了：打开默认看 DAG，可以切到任务书，两者共用施工者侧栏（`run.md:92`，验收在 `contract-tests.md:273`）。
- 没定的有三件：图大了怎么办、循环和重试的历史怎么显示、怎么聚焦。`04-project-navigation.md:79` 那句"历史如何折叠由界面设计处理"说的是 Runs 列表，不是图本身。
- Room 树完全没有设计。

**业界反复出现的做法**
1. **大纲为主、图为辅、两者同步。** Dagster 的资产图配一棵缩进侧栏树，选中一个节点会自动展开它的祖先。我们的引擎 Dagu 是图加节点状态表。研究结论也一致：缩进树对新手更好懂；连线图在一个节点有多个父节点时不会重复，也更好控制。
2. **一个正式父节点，其他关系画成交叉链接。** 反面教材是 Airflow：老的 Tree View 把 DAG 硬画成树，一个有 N 条上游路径的任务会被画 N 次，2.3 版用网格视图换掉了它。
3. **在焦点处给出"祖先面包屑 + 兄弟切换 + 子节点列表"。** 只有兄弟箭头不够：有用户说 ChatGPT 的 ‹2/3› 让分支多的对话"整段几乎找不回来"，于是出现了第三方的分支查看器。
4. **折叠时汇总状态。** Argo 里一个节点超过 3 个子节点，就把中间的收成"N 个隐藏节点"；Reddit 超过 10 层就显示"继续这个讨论"，把子树当成新的根打开。
5. **时间是第二根轴。** DAG 只画结构，画不出"第 3 次重试"或"第 2 轮循环"。Airflow 的主调试视图是"任务 × 每次运行"的网格；Temporal、Dagu、Prefect 都有时间线。
6. **按注意力重新分组。** LobeHub 的话题可以按运行中、等人、完成、失败分组；Zulip 有 Inbox；我们有"待你处理"。
7. **基本功。** 要能用键盘导航：我们技术栈里的 React Aria 自带符合无障碍规范的 Tree 组件。视图状态写进 URL，能直接链接到某个节点。

**用到 Room 树（我的建议）**
- Rooms 改成 Project 下的缩进大纲。每个 Topic Room 的正式父节点就是它的来源（已有记录）；跨 Room 的引用画成链接，不重复成行。
- 默认显示两到三层；更深的用"以此为根"打开，带面包屑。Zulip 只有两层命名，照样撑起了大社区。
- 每行显示汇总计数：未读、待你处理、未结 Request；折叠起来的父节点把子孙的数字加总。
- Room 头部放祖先面包屑、兄弟切换和子 Room 列表。父到子那条边上挂前情提要，它本来就是这条边的摘要。
- 可以切换到"按注意力分组"。画布式的地图放到后面做、做成可选的，研究显示用不用它很看人。

**用到 Run DAG（我的建议）**
- DAG 继续做默认视图，只画义务节点；动态扇出和 Gate 的席位扇出各收成一个带计数的节点。
- 加一个同步的大纲：义务按拓扑顺序排列，能展开到席位，再展开到每次尝试。这就是设计里说的"渐进展开"，同时也是无障碍的替代视图，以及通往任务书的桥。
- 加一个"节点 × 尝试"的网格或时间线。循环会生成新的 Obligation，重试会生成新的 Attempt，静态图画不出来。
- 焦点模式：高亮上下游各一跳，显示"是怎么走到这里的"，再给一个"跳到下一个等人处理的节点"的按钮。
- 图大到一定程度才显示小地图；Run、节点、席位、尝试都能直接链接。

**一个模型能不能同时管列表、树和 DAG？部分能。** 导航框架可以共用：大纲行、一个正式父节点、额外的边、汇总状态、焦点和面包屑、注意力视角、URL 状态。但画法不能统一：把 DAG 硬塞进树是 Airflow 已经放弃的路，画布对列表和浅树又是负担。所以应该是"共用大纲，各自配第二视图"：Run 配图，Room 可选配画布。这也符合"协作拓扑与控制拓扑正交"（`vision.md:152`）。

**架构层真正要定的不是画法，而是控制面要提供哪些事实，让这些视图都画得出来：**
- 每个节点唯一的正式父节点；
- 带类型的交叉链接；
- 能从事实算出来的汇总状态；
- 能直接链接的稳定 ID；
- 尝试和循环作为一等记录。

这些 HCTL2 大部分已经有了（Topic Room 来源、Obligation、Attempt、Seat）。缺的主要是 Room 之间的父子关系本身。

## 主笔 · 三

你说得对：房间之间的关系应该放在 Matrix 原生存储里，我上次把这件事放进控制面是错的。仓库里其实已经有先例：Kanban 早就是这么定的。

#### 1. 房间之间的关系归 Matrix

`spec/task.md:89` 的原话：「卡与卡之间的阻塞与父子关系是任务源的原生语义，归源持有；HCTL 认得它但不另存」。具体做法有三点：
- 适配器从任务源读出这些关系，投影成四个只读字段：父卡、子卡、阻塞它的卡、它阻塞的卡。
- 改关系走 content 写入通道，以回读为准，不走治理命令。
- 任务源不提供依赖语义时，这些字段为空。

Room 树照这个做就一致了：
- 父子关系用 Matrix 的 `m.space.child` 和 `m.space.parent` 存。
- HCTL2 只读出来投影成「父 Room / 子 Room」字段。
- 改挂走 Matrix 写入，以回读为准。
- 多父的情况，正式父节点取 `canonical`，其余画成交叉链接。

不过我想给你的规则补一条例外，否则 Workflow 套不进去。你的规则是：模块内对象之间的关系归该模块的原生系统，控制面只记跨模块映射。但 Workflow 的 DAG 边不在引擎里，在控制面：Workflow Revision 由控制面保存精确正文（`spec/run.md:68`），引擎拿到的只是编译后的副本。原因是这些边本身就是契约，决定什么可以自动推进。

所以我建议把规则写成：**模块内对象关系归原生系统；进控制面的只有两类：跨模块映射，以及本身就是治理事实的关系（契约、授权、修订谱系）。**

这样还顺带解开了上次的「能不能改挂」问题。Topic Room 身上其实有两种关系，只是在出生那一刻重合：
- **出处**：它从哪条消息或哪个 Request 开出来。这是前情提要的冻结来源，属于治理事实，在控制面，永不改。
- **挂在谁下面**：这是协作上的组织方式，属于 content，在 Matrix 里，可以改挂。

Kanban 里有同样的二分：Task–Backend Binding 的家指针在控制面、不改写；卡在源里的父卡可以随便挪。

按这条规则把四个模块对一遍：

| 模块 | 对象间关系 | 归属 |
|---|---|---|
| Room | 房间父子 | Matrix 原生（`m.space.*`） |
| Room | 出处（从哪条消息或 Request 开出来） | 控制面，治理事实 |
| Kanban | 父子卡、阻塞 | 任务源原生（已定，`spec/task.md:89`） |
| Workflow | 图内的边 | 控制面，因为它是契约；引擎只拿编译副本 |
| Workflow | 图与图之间 | 没有关系：子 DAG 被编译器拒绝（`spec/run.md:102`） |
| Change | 堆叠 PR 的 base、`#123` 互引 | 平台原生，只读投影 |
| Change | ChangeSet 的修订谱系（`parent_revision_id`） | 控制面，治理事实 |

放进 Matrix 原生的代价也要看清（实现层脚注）：
- 在 Matrix 里只有 Space 能有子节点。所以每个 Project 要变成一个 Space；一个 Topic Room 一旦有了子话题，就要变成「子 Space + 主房间」。
- Room–Server Binding 因此要多绑一个 Space ID。
- Cinny 会把多层 Space 压成一层显示。
- 子树级的动作（比如归档整棵子树）Matrix 不会级联，仍要控制面逐个房间执行。这属于治理动作，放在控制面不违反上面的规则。

#### 2. rcopy

我没在 Pi 生态里找到这个名字。你描述的是 CoW 克隆：XFS 和 btrfs 的 reflink（`cp --reflink`）、APFS 的 clonefile 都属于这类。更往外一步，还有 VM 或沙箱快照，连进程和内存都能一起 fork。如果有链接发我，我去看具体实现。

它不推翻结论，而是让结论更精确：**能 fork 的是「被纳管的那部分客观世界」。** 文件和沙箱在纳管边界内，CoW 能让 fork 它们变得很便宜。已经推出去的 git、发出去的消息、远端数据库和调用过的 API 在边界外，fork 不了。

在 HCTL2 里，这块被纳管的世界就是 ChangeSet 的工作树。从某个点开一个新 ChangeSet 时，用 reflink 建工作树是一个很好的实现选择（实现层脚注）。

#### 3. 多观察者：同一房间里只有一个客观世界

同意，你的表述比我的好：**分支只能 fork 主观（上下文），不能 fork 客观（世界）。**

结合第 2 点，换方向完整的做法是三步：
1. fork 出一个新房间，带前情提要，这一步分叉的是主观。
2. 钉住当时客观状态的引用，比如 ChangeSet Revision。
3. 需要时再基于这个引用开新的 ChangeSet，这一步分叉的是纳管内的客观。

同一个房间里只有 thread：只有一层，所有人可见，不能切换方向。原因就是你说的多观察者，所有人眼里只有一份对客观世界的观测。

实现层脚注：现在的设计里没有 thread 这个概念，Cinny 也没有 thread 面板。所以「房间内有 thread」是一个新增项，需要拍板。

#### 问题一：「模块内的关系归原生系统」要不要留一个例外

你定的规则是：一个模块里，对象和对象之间的关系，存在那个模块自己的系统里。控制面只记跨模块的对应关系。

但 Workflow 的 DAG 套不进这条规则。DAG 里的边（比如「A 做完才能做 B」）也是模块内的关系，按规则应该存在引擎 Dagu 里。可现在的设计是：这张图由人批准、存在控制面，Dagu 只拿到一份编译出来的副本。
