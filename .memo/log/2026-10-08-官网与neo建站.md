# 2026-10-07/08 官网与 neo 建站

> 场合：DeepSeek 席（omp）与所有者，跨 10-07 晚到 10-08 凌晨的一次连续会话；本文件写完即冻结。<br>
> 范围：所有者指定记录从官网讨论那段起的每句输入（2026-10-08 说明）；三件事——① hctl2 官网，② 站内要突出的产品理念，③ neo 建站方式（AI 时代的网站构建）。<br>
> 结论与提案在 [`.memo/design/hctl2-site-20261007/`](../design/hctl2-site-20261007/README.md)；本文件只存所有者原话与每轮结论，harness 的长答复不逐字复制。

## 原话

1. 所有者：

   > 参考几个非常大的agent合作平台，例如docs/research/workbench下的几家 (codeg, first-tree, multica, superset, orca, cumora等) 他们的官网 - 我也想为hctl2做一个官网。
   > 其实hctl2的风格稍微有一点点像herdr - 感觉比较工具化/工程化，包括命名都是 (harness control)。但是我希望它的审美反而体现出一些风格，尤其是在字体的选择上 (steve jobs关于衬线字体和无衬线字体的讨论深得我心)。
   > 你做一下计划。

   结论：出第一版计划——定位为仓库正文的公开投影；参照系改用仓库现有研究（比另做一轮网调更可信）；审美走"三声部排印"；给出信息架构、构建路径（Buck2 原生与引 SSG 两条）、阶段计划与待拍板项。

2. 所有者：

   > 我觉得有几个重点要突出：
   > 1. 应该有实际的页面（这个等到我们的workbench有了就好了）
   > 2. 突出participant的概念。现在bot比较火，是不是叫bot比较容易理解？
   > 3. 我们的原则：
   > - 广泛、充分的调研 - 产业届类似产品+严谨的学术研究
   > - idea很重要，对话是合作的起点。但是，agent之间的讨论≠更优的方案(学术成果).
   > - 对话不是合作的终点-执行阶段最重要的是纪律性 - 三段论：mechanical → sysone → human
   > - 设计的最核心是解决信息过载 - agents的智力是充裕的资源，人类的关注才是稀缺的bandwidth (符合管理学理论)。这也是战争中参谋部的作用之一 (第一次世界大战的教训)。
   > - 我们痛恨重新造轮子，因此每个模块都是开源项目的组合

   结论：五条原则成为站点脊柱，逐条核过证据成色（见 02）；Participant 的处理建议是保留对象名、把 bot 当对照物（见 02 §Participant 与 bot）。

3. 所有者：「我指的是『应该有实际产品页面的snapshot』」——即站上要有产品页面的真实快照；它等 Workbench 就绪，空窗期不放假图，用 `docs/demos/demo-1.md` 的真实终端记录顶替，且快照必须带 commit 与日期、可复现。

4. 所有者：「sysone指的是最近流行的system one -> Jev」——纠正了 harness 最初把 sysone 读成 spec 里 `gate` 的猜测。sysone = System One（Jev、CLM 一类判断器），与 [`room-judgment-20261002.md`](../design/room-judgment-20261002.md) 开头的定义一致：输入小状态与有限选项，输出概率，不生成文字。

5. 所有者：

   > 出计划的话我感觉
   > 1. 不要和现有的文档/代码纠缠 - 网站是它自己的事，不要反过来影响了文档/开发。
   > 2. 内容可以由文档『编译』产生，但我觉得不能是直接的mechanical的编译，而应该是给prompt、然后由LLM基于现有代码库的一次generation。这也是new diagram。这里指的不是整个网站一次性被generate出来，而是我们主动地merticulasly地manually地design整个网站架构、导航逻辑、艺术效果等，只是『文本生成』这个动作是由prompt艺术加工出来的 - 文本生成也是一段一段生成的。比如这个页面想讲几件事，那么每件事是一个独立的prompt。
   > 3. 生成结果可以缓存 - 这个你看怎么借鉴buck2的building system - 只要作者觉得okay (prompt不改, 类似于compiler)，参考的文本不改 (类似于source code)，那么生成出来的文本结果就不要改，避免反复生成烧token
   > 4. 要区分内容/展现。内容由前边的『neo编译/llm生成』产生，产生的是段落、意群、逻辑、用户流程；而后边的展现则是风格、字体、字号、位置、交互效果、颜色等内容。这个也可以是生成式的。
   > 感觉是做了个neo网站编译系统啊哈哈哈。你看要不要开个新project

   结论：按"生成式构建系统"重做计划——手工定架构、导航与排版，LLM 只做逐单元文本生成，缓存按单元键控（借 Buck2 的概念，但不把模型调用放进构建 action 与 CI）；内容与展现分层；建议独立仓库。见 03。

6. 所有者：

   > 全部存进memo，包括我的每句输入，这样未来不丢context。（我们实际上聊了三件事：① hctl自己的网站(各种参照物、风格等)，② hctl2的设计理念(产业和学术研究、mechanical->sysone->human的三段论、对于idea的重视程度、产品的本质是注意力管理，等)，③ 一种新的(neo)网站构建方式/AI时代的网站构建方式）。而且同意 - 未来开个新project: hctl2-site.

   结论：本次会话按这三件事整理进 `.memo/design/hctl2-site-20261007/`，所有者同意未来开新 Project `hctl2-site`（尚未创建、尚未开工）。
