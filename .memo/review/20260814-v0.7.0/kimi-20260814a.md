## 需要收口的问题

### 1. `validation.md:129` 的 "ELK default distribution decision" 是孤儿条目

"ELK" 在全仓库只出现这一次，没有任何定义。如果它指 Eclipse Layout Kernel（Run graph 布局），则与已定格的技术栈冲突——README.md:130、workbench.md:49、foundation.md:150 都已固定 "React Flow + Dagre"。无论哪种解释，这条未决问题要么是过期残留，要么缺少上下文，建议澄清或删除。

### 2. `domain-model.md:215` 与 `invariants.md` L1-MAP-02 / `l1-execution-runtime.md:104-105` 存在措辞冲突

领域模型写"**显式 TTY** RoomInvocation 可以有 0..1 InvocationRuntime"，但不变量和 L1 映射表无条件地写 "RoomInvocation → 0..1 InvocationRuntime"，且 L1 表格明确说 InvocationRuntime 可以是 "one container/scope **or structured session**"。也就是说：纯结构化协议（无 TTY）的 RoomInvocation 到底有没有 InvocationRuntime？两处顶层规范文档给了不同答案。按 `docs/design/README.md:128` 的优先级规则，这两份文档同级并列第一，没有 tie-breaker，建议直接统一。

### 3. HUMAN/WAIT 节点 → Request 的映射缺一句话

L2 Profile 允许 `HUMAN/WAIT` 节点（l2-workflow-governance.md:66），而 domain-model.md:165 和 L2 文档都声明 WAIT 等系统 task 不创建 Obligation；同时 L2 文档又说"Run 需要输入时，control 创建 durable Request"（:141）。但 control 通过什么机制感知 Conductor 中 HUMAN 节点进入等待、从而创建 Request（poll snapshot？event？），整条链路没有写明。这是治理切片步骤 9 实际会用到的路径，值得补一句显式说明。

### 4. CLI 二进制名未定格，且 `hctl` 与前代重名

文档中 CLI 写作 `hctl status`、`hctl terminal attach`（l3-task-kanban.md:221、l1-execution-runtime.md:172,210），而组件族命名是 `hctl2-workbench/control/core`，项目名 HCTL2，直接前代 HCTL1 的仓库正是 `yesme/hctl`。二进制名撞前代项目名会造成 PATH/包管理冲突和认知混淆。这属于该进 ADR 的决定，目前 ADR catalog 18 条里没有覆盖。

## 编辑性小问题

- **Composer 语法缩写漏了 `/`。** 规范集是四个符号 `@ / $ #`（README.md:61-64、l4-project-room.md:108-113），但 5 处写成 `@ / $ #`（l4:206、workbench.md:74,129、phase-1:25、validation.md:15），`/compare`、`/memo` 这类 typed action 被漏掉。
- **repo 级 `.hctl2/` 内容两处不一致。** system-architecture.md:97-103 的 repo `.hctl2/` 没有 `skills/`，phase-1-and-dogfooding.md:174-181 的目标布局有；而 L1 文档明确 Skill 有 "global/repo scope"（l1:189），repo 级 skills 的存放位置应该统一。
- **"Projects Overview" vs "Project Overview"。** workbench.md:17 用复数（旧版 §10 的标题残留），其余全部用单数指 per-project 聚合视图。若真想表达跨项目列表，应起独立名字；否则统一为单数。
- **一次性未定义术语。** `DecisionReceipt`（l4:58）和 `Context Capsule`（lifecycle.md:58）各出现一次，领域模型和术语表都没有定义；建议分别归入 Receipt 体系和 ContextManifest/Bundle 体系，或补定义。
- **`Needs you` / `Needs You` / `Needs Attention` 混用。** HCTL 自己的投影叫 "Needs Attention"（l3:24），但 l3:126 用反引号写了 `Needs you`——那是 Codeg 的 lane 名。建议 Codeg 引用处保留原样，HCTL 自身一律用 "Needs Attention"。
- 未闭合问题列表与三项限时验证有冗余（#2≈V-SPK-01、#12≈V-SPK-02、#14≈V-SPK-03），可交叉引用避免两处漂移。
- Phase 1 交付底线是"同一 Room 至少两个 independent stream"（phase-1:27），L4 验收测试是"3–5 个 Participant 交错 stream"（l4:263）——底线与压测口径不同不算矛盾，但建议注明关系。

- **规格体量 vs 进度。** 3300 行规范性文档 + 18 条计划 ADR，而 B0 尚未开工。好在交付顺序是"B2 第一自举点不等待 Conductor/quorum"，thin-slice 策略正确；主要风险是规格先行漂移，建议 B0 开工后把 contract test 编号（V-L4-01 等）直接落成测试名，让文档与代码互相锚定。
