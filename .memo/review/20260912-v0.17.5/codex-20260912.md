## 结论

主方向没有被整体改回去，但不能认为这批 PR 合起来已经前后一致。发现五组需要处理的事项：一组评审结束条件缺口、四处已修正文句回退、一组设计与约束不一致、一组治理材料交付的过渡范围不明，以及后续施工入口未跟上裁决。

本报告只提出修正建议，不替所有者增加规则或提前实施后续批次。P1 表示进入相应实现前应先澄清的正确性问题，P2 表示需要定点修正的一致性问题；不是线上事故等级。

## F1 · P1：重复票取不利结论，与提前结束评审之间缺少结束条件

**位置：约束层。** [spec/run.md](../../../docs/design/spec/run.md) §Request、重试与 Gate；[contract-tests.md](../../../docs/design/contract-tests.md) §CT-RUN。

#211 新增：执行配置与交付内容相同的票合为一个重复组；组内裁决不一致时不计通过票，按不利裁决处理。相同一节仍保留：达到法定票数后撤销剩余 Attempt（尝试），立即签汇总凭证。

缺的是：重复组什么时候已经可以算一张最终通过票。下面是约束允许配置的反例，不是建议采用的默认票数：

1. A、B 是两个不同的合法选入记录，不是作者；实际 Worker Profile（执行配置）摘要和交付内容摘要相同。门槛是一票，没有单席否决权，两次尝试都已派出。
2. A 的通过票先准入。如果此时视为已达门槛，就取消 B 并签凭证；B 随后交回的要求修改只能按迟到结果保存。
3. B 的要求修改先准入，随后 A 通过。同一组出现分歧，按新增规则不能计通过票，结果与上一种顺序不同。

这不是已经复现的运行故障，而是文本允许两种实现：一种只归约结束前已收到的票，另一种等重复组的结论稳定后才计通过票。现文没有选择；“迟到结果拒绝”也不能回答应该什么时候结束。

**建议：修正。** 先明确重复组何时形成最终计票结果，再限定“达到法定票数”。按已选择的不利裁决规则，应避免拿尚可能被本组其他有效票推翻的通过票签凭证；组内超时、撤销如何影响结果，也按冻结策略写明。独立组之间达到门槛后能否提前结束，是另一件事，不必因此要求所有评审一律等齐。

同节“去重后计入票少于法定票数时按法定票数不可达处理”，也应区分“尚未收够”与“剩余有效票全部回来仍不可能够”，与后文“剩余票已不可能达到门槛”统一。

**核销判据：** 在既有 CT-RUN 中覆盖上述两种到达顺序、重复组超时或撤销、尚未收够但仍可达到门槛，以及独立组足够时的正常结束。现有重复票用例把门槛设为二，两票去重后必然不够，未覆盖这个提前签凭证的分支。

## F3 · P2：设计仍说每条边都要有产物，约束已允许纯控制依赖

**位置：设计层与约束层。** [run.md](../../../docs/design/run.md) §施工图怎么凝结，对照 [spec/run.md](../../../docs/design/spec/run.md) §Workflow 编译与 Profile、[contract-tests.md](../../../docs/design/contract-tests.md) §CT-RUN。

#210 的设计仍写：“一条边就是下游节点的准入条件引用上游节点的结晶或凭证标识”“每条边都落地”。#211 的编译规则已经正确拆成两类：控制依赖不要求产物引用；产物依赖才要求引用上游声明的产出。编译时查声明，运行时才查产物的精确版本与摘要。

因此，合法的 timer、noop、join 等结构边在约束和 CT 中应通过，按设计这句话却应拒绝。设计后面七条未来扩展条件已经用“每条产物依赖的边”，前面的现行凝结规则仍未同步。

**建议：修正设计，维持约束。** 把该条限定为“产物依赖引用上游声明的产出”，说明纯控制依赖按引擎结构表达；细则指向当前编译规则。不要求编译时已存在尚未执行产生的凭证。该节自述“六条”而现有七项，也应校准，但不是本项的语义问题。

**核销判据：** 同一张带合法控制边的施工图，设计说明、编译规则与 CT 得到同一结论；仍拒绝找不到上游产出声明或类型不匹配的产物依赖。

## F4 · P2：治理材料交付局部采用新裁决，但共用交付规则仍保留旧范围

**位置：约束层的跨批衔接。** [spec/run.md](../../../docs/design/spec/run.md) §Workflow 编译与 Profile、§从节点到结果；[spec/project.md](../../../docs/design/spec/project.md) §三种交付方式；[context.md](../../../docs/design/context.md) §同一 Run 内的接力：节点之间传什么。

09-12 所有者明确让 #211 的规则四按治理材料方案改写：Verdict、Receipt 的权威在控制面，交付可指向“已交付到执行现场的精确副本”，不再写成 Git 影子。

但同一份现文把具体交付委托给旧规则：

- `spec/project.md` 的 pointer 只允许可打开的 Git 对象或 worktree 路径，并排除“控制面存储”。
- `spec/run.md` 的返工交付仍写“其 Git 结晶副本只作 pointer”；`context.md` 仍沿用 Git 副本的叙述。
- 已拍板的 [治理正文方案](../../design/case-study-20260907/03-governance-text.md) §九、§十明确包括：治理材料仓库属于控制面存储；获准并实际交付的精确 Git 对象或只读材料路径均可作指针，原禁句要收窄到不能直读治理记录库。

问题不是要求这次把材料后端全部实现，而是新句采用了哪一部分没有写清。若按新方案交付执行环境中的普通只读材料文件，它符合“精确副本”，却不在旧 pointer 范围内；若仍只准 Git 副本，新句就没有落实所有者这次要求承接的交付范围。

**建议：修正交付范围或明确过渡限制。** 只同步已经在 #211 采用的部分：区分治理记录库与已实际交付的只读材料；保留必读裁决正文、摘要核验和预算规则。若完整的新交付能力仍留 C 批，应明说当前支持的副本种类，不让两种范围同时充当无条件规则。

**核销判据：** 能明确回答：非 Git 的获准只读材料副本当前是否可作 pointer；只有需要在线解析的控制面定位符是否应拒绝；返工者拿到的是否仍包括必须阅读的裁决正文。材料仓库的备份、镜像与垃圾回收整体落地仍按 C 批，不借此提前扩项。
