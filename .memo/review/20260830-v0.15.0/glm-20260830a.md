## 一、结论

**设计成立，该收笔了。** 六轮评审的轨迹是收敛而非振荡：v0.7–v0.8 的真矛盾（无 Run 路径的 Receipt 无写入者、Attempt 缺 `Pending→Lost` 边）→ v0.10.2 "问题不在正确性在可开工性" → v0.12.3 codex 终审 Go，且诊断方向反转——剩余风险是**文档过度设计**而非缺合同。v0.13.0 撤回 Git broker / presence proof、v0.14.0 删 agentd 全押 Herdr、v0.15.0 客户端动作合同，三次转向都在"收缩到真不变量"这一方向上，与终审裁决一致。

当前的主要风险已不是"设计错"，而是三件别的事：

1. **陈旧传播不完整**（机械性债务，见 §三 A）；
2. **合同密度无可执行对偶**（CT-* 仍是文档，见 §三 B2）；
3. **单人执行带宽**（正确但重，见 §三 B3）。

## 二、交叉核对：未发现新矛盾

本轮对历史高危点做了跨层核对（设计正文 ↔ 合同层 ↔ delivery），以下各处在三层是同一套话，未发现 v0.7–v0.12 时代的"两份同级文档无 tie-breaker"型冲突：

| 高危点 | 核对结果 |
| --- | --- |
| 无 Run 完成路径 | human 命令 + Integration Receipt，不伪造 Gate Receipt；connections「验收与回流」/ run.md / delivery 切片 A 三处一致 |
| Attempt / Invocation 丢失 | 只在 connections 失败表定义一次（"执行身份丢失处理规则的唯一定义"），模块合同引用不复述 |
| E2EE | managed Room 强制非 E2EE，事后加密走 fail-closed + 换绑；CT-PROJECT 有对应测试行 |
| Herdr 已知限制 | 无 generation 回显、512 条事件环无 sequence、API/TUI 交错写、退出回读不足——全部如实降级标注，未假称能力（system.md 单写者节、agent.md Agency 节一致） |
| 单写者 / 三类数据 / 结晶规律 | vision–architecture–spec 三层同构；账本唯一权威 + Git 双重角色（正文 vs 审计影子）边界清楚 |
| Task 完成双来源 | 只接受有权 human 命令或 task-bound Run 正常完成的 reducer 同一命令；provider Done 只能"请求"，拒绝后并列显示不回写——与 0.7 时代 bug 3/5 的修复方向连续 |

## 三、瑕疵

### A. 机械性：陈旧传播不完整

这是 v07-v012 复盘诊断过的老病（"横切转向没有完整传播"）的小规模复发：

1. **根 README 停在 v0.12.0**：声称基线 v0.12.0；目标架构图仍画 `agentd` 节点与"harness / 运行时后端"，而 agentd 已于 v0.14.0 退场、Herdr 接管 Agency，Tauri 2（v0.14.2）与 v0.15.0 均未反映。README 是仓库门面，是新读者第一眼。
2. **`notes/doc-cleanup-backlog-20260825.md` 自身过期**：13 条过强断言中至少两条（agentd-only terminal、tmux 拓扑写死）已被 v0.14 转向天然解决；清单未刷新，等于又欠一笔同款债。建议整轮清点：逐条标注"v0.13–v0.15 已处理 / 仍开放 / 已失效"。
3. **fable-20260824 生死级建议无裁决记录**：F1（关单摩擦指标化进 CT-PRODUCT）、F2（整机总账：从零安装到第一件事的时间上限、空载总 RSS 上限）、F11（十秒六问无测量方法）——提了没人接。不是文档错误，但违反"拍板才提交"的闭环纪律；接或不接都该留痕。
4. codex 终审遗留的三个"进切片再拍"局部决定（Chat 非 E2EE 三个最小行为、Run pause 用户语义、Project 归档 Matrix 禁言）未显式登记进 delivery 未决问题，存在被遗忘的风险。

### B. 结构性：设计层风险

1. **Herdr 押注加深**。v0.14.0 把终端运行时全部押在 v0.8.2 的年轻上游上：第一阶段"受租约输入、精确 attach、完整持久 trace"三件事实际都在打折，天花板由上游决定。合同诚实标注了限制，但"外部证据未联网复核"是 0.7 以来三轮评审的连续遗留。建议：把 Herdr 上游活跃度/路线图列为持续观察项；B2 前的真实验收显式走一遍降级路径（原生输入无租约、非 exact attach 的 semantic resume）。
2. **合同密度无可执行对偶**。kimi（0.10.2）提出、gemini 同轮附议："状态机只是散文与表格，矛盾拖到实现期才暴露"；gemini 建议"契约测试骨架与 B0 同步"。目前 CT-* 仍是纯文档，P2 一开 control 这个缺口立刻变现。spec 中 Run/Attempt/Request 的状态机与 CAS 规则应最先转成可执行测试。
3. **正确但重**。四模块 × 状态机 × CAS/outbox/readback × 五类受控端口，单人推进 B0→B5 是长路。这是执行风险不是设计错误，但直接决定下一步策略：优先级应让位于"长出第一块带契约测试的 control 代码"，而非继续打磨 P1（tool/protocol/packaging 已绿，边际收益低）。
