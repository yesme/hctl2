## 审议范围与方法

本报告独立检查以下材料：

- 从 `729238e`（2026-08-14，四层文档重组）至 v0.15.0 规范性提交的实际 diff 与提交顺序；仓库没有 `v0.7.0` Git tag，因此以该提交作为 v0.7.0 时期的代码基线；
- 当前 `README.md`、`docs/design/`、`docs/design/spec/`、相关实现证据，以及 `src/` 中实际存在的代码、Buck2 目标和打包实现；
- 当前 macOS arm64 第一方 Buck2 测试与 clippy 构建。

本轮没有读取或采用同一评审轮中其他 harness 的报告结论。`main @ 90d2a2d` 相比最后一笔 v0.15.0 规范性提交只增加了评审 memo；本报告对设计的判断建立在规范正文、实现和构建结果上。

## 总体裁决

v0.15.0 的**架构主干正确，已经足够停止大规模概念扩张并转入实现**。需要保留的核心是：

1. Project、Task、Run、Agent 是四个语义模块，不由聊天串、外部卡片、工作流节点、终端或 worktree 反向定义；
2. 展示、控制、执行三个部署面与四模块正交；
3. metadata 归 HCTL 用户级账本，场景 content 归 provider，正式交付物结晶进 Git；
4. Workbench、CLI 和 provider 原生客户端没有等级，动作按目标端点和可验证信封分类；
5. 四个模块各自保留薄 adapter 和版本化 binding，不建设跨模块通用 shim 服务；
6. Tuwunel、Vikunja、Dagu、Herdr 和 Tauri 2 优先复用现有产品，不在 HCTL 内重建同类系统；
7. B2 先走无 Run 的真实开发链路，Dagu 和完整 Run 到 B4 才进入必需路径。

当前问题不是方向错误，而是**精确合同显著领先于产品代码**。设计可以开工，但不能把所有字段和失败分支都当成已被证明的最终协议；接下来的实现应当允许用真实行为修订合同细节。

## 从 v0.7.0 到 v0.15.0 的演化判断

### v0.7.0—v0.9.1：从层级模型改成语义分责

这一阶段把单体设计文档改为四个模块，并分开愿景、设计正文和精确合同。它解决了早期把 Project、Task、Run、Agent 当作物理层级，以及把界面对象、领域身份和运行时混在一起的问题。这个方向应保留。

### v0.10.x：数据权威和部署结构成形

metadata/content/artifact 三分法、展示/控制/执行三面、用户级唯一账本、每个 Repo 多个执行现场，是当前设计最稳固的一组决定。它们共同回答了“数据在外部系统、治理在 HCTL 时怎样保持一致”：外部变化先作为 provider content 或 Snapshot；只有模块明示接纳且满足来源、目标、版本、幂等和回读条件的动作，才形成 HCTL 命令请求。

### v0.11.0—v0.13.1：交付顺序与正确性机制补齐

P0—P3、B0—B6、单写者、outbox/readback、Result Proposal、Receipt 和分层 generation 使设计具备故障恢复和真实自举的判据。与此同时，Context、Participant、Run/Gate 的字段开始快速增加，设计细节第一次明显快于实现。

### v0.13.2—v0.14.2：外部运行服务和桌面壳定型

agentd+tmux 退场、Herdr 直接承担 Agent/Terminal 运行服务，是符合“不要重复造轮子”的修正。Tuwunel macOS 制品改由 HCTL Release 托管，正常发行不再重编；Workbench 改选 Tauri 2。旧 tmux 验证仍可作为资源和行为基线，但不再代表产品维护并行实现。

### v0.15.0：客户端按动作分类

“Workbench 不比四个原生客户端加起来更高贵”是正确裁决。Matrix 消息、Vikunja 卡片、Herdr 输入、Dagu 管理动作和 HCTL command 不应被统一归为只读或带外；应按 content、human command request、runtime input、Result Proposal 和 unsupported provider mutation 分别处理。当前合同已经保留了必要的 actor mapping、target、version/generation、idempotency 和 fresh readback，没有把“都是用户意志”误写成“可以省略验证”。

## 正确且应冻结的架构决定

### 四模块与三面架构

四模块回答事实由谁拥有，三面回答进程和数据部署在哪里，两者没有互相替代。Agent 不是 Herdr，Run 不是 Dagu，Task 不是 Vikunja，Project 也不是 Matrix Room；外部产品只实现对应场景的 content 或机械运行能力。

### 数据权威和外部写入

当前设计不试图禁止外部客户端写 content，也不把 provider 当前状态倒签成 HCTL 治理事实。命令先在账本持久化，再由 tool/adapter 执行，ACK 未知时回读而不是盲重投；这套规则足以覆盖本地 Git、远端任务平台、Dagu 和 provider Done 等不同副作用。

### 模块专用 adapter，而非通用 shim

Matrix、任务后端、workflow engine 和 Agency 的替换单位、能力和故障含义不同。把它们压进一个通用 CRUD 或通用 provider 协议只会产生新的私有平台。稳定边界应当留在模块合同和 Resolved Port Binding，adapter 只翻译本模块实际消费的接口。

### 外部二进制优先

四个主要场景都已经选定成熟外部实现。额外功能只要体积、RSS、运维和授权可接受，就可以作为二进制的未用子集存在；不需要为了“只包含我们需要的功能”重新实现一个缩水版本。

## 需要修正或用实现验证的内容

### 1. 规范细节超过了现有知识

当前规范已经精确列出 Context Manifest/Bundle 的 tokenizer、renderer、compressor、逐项 token 计量、retention policy，Participant 的七层身份链，以及 Run/Attempt/Result Proposal 的多组 generation 和摘要字段。概念方向有价值，但其中不少字段尚未经过一次真实 prompt 组装、Harness 派工、崩溃恢复或 B2 自举。

风险不在于字段数量本身，而在于未验证的实现选择已经取得规范性地位。后续不应继续增加 v0.16 式概念；先实现最小链路，只有确实承担恢复、权限、不可变引用或机械验证职责的字段才继续保留为合同。

### 2. Herdr 的 `managed_single_writer` 暂时不能作为已兑现能力

Herdr v0.8.2 的原生 controller 与 API 写入可以交错，API 没有统一 writer gate、input provenance 事件或 fence 回显。规范写“provider 不能统一拦截所有写入时就关闭原生 controller”，但当前没有说明怎样证明这个入口已经对同一 OS 用户不可用，也无法检测用户直接连接 Herdr socket 后的写入。

因此第一阶段可以正式支持 `native_interactive_allowed`：原生输入是有效运行时输入，但明确降低逐次 actor、generation、单输入者和 replay 保证。`managed_single_writer` 应标成 Herdr v0.8.2 暂不支持，或者先提供并验证能够隔离所有原生写入路径的机制。这个限制不要求 HCTL 重建终端服务。

### 3. `hctl2-tool` 的 P1 范围过宽

交付文档计划让 `hctl2-tool` 负责 commit 署名、lint、PR 正文组装、memo 写入、有效变化侦测、worktree 保全和失权执行。这里混入了两类工作：

- HCTL 特有的正确性边界：worktree 所有权和保全、执行已持久化的精确 Git intent、target head/commit/diff 回读；
- 已有工具能够承担的普通机械工作：Git 提交、Buck2 lint、GitHub PR、文件写入。

工具箱应只实现前一类合同，并调用 Git、Buck2、`gh`/GitHub API 等现成机制完成后一类工作；不应重新实现 Git 引擎、lint runner 或 PR 客户端。当前 `hctl2-tool` 只有 help/version scaffold，仍有机会在增加代码前收窄边界。

### 4. Dagu 合理，但收益尚未由产品链路证明

HCTL 自己拥有 Run、Obligation、Seat、Attempt、deadline、重试、Gate、Result Proposal 和 Receipt；Dagu 只保存依赖、条件、timer、等待位置和机械历史。这种分工能保证语义不被 engine 私有对象绑住，但也使 adapter 和对账成本偏高。

现在不需要重开选型。应按交付文档等到 B4，用真实的等待、loop、重启、迟到 completion 和 UI 越界 mutation 验证它。如果最终实际消费只剩极薄的路标能力，再根据实现复杂度判断收益；在此之前既不要提前接入 Dagu，也不要自建工作流引擎。

### 5. 产品路径还没有被验证

设计已经能精确回答“什么事实有效”，但尚未证明一个用户完成小改动要经历多少步骤、首次得到可用结果需要多久、Preview/Receipt 的打扰程度是否合理。B2 的意义不只是证明账本正确，还要观察用户是否被迫手工搬运事件 ID、上下文、命令和证据。不能用继续补文档代替这项验证。

## 已确认的文档和实现不一致

### Tuwunel macOS 发行形态

`docs/design/delivery.md` 的 chat server 条目正确写明正常发行消费 HCTL 托管的 macOS 预编译包，但同文件“打包策略”仍写 Tuwunel 从源码原生构建。`src/packaging/dependencies/README.md` 的平台表和构建说明开头、`src/packaging/release/assets/USAGE.md` 的源码构建段也保留了旧说法。

实际 Buck 图和 lock 已经固定 HCTL Release 上的 arm64/x86_64 Tuwunel 制品；源码和 Rust 工具链只在显式更新托管制品时进入图。大修应统一为这一事实，并保留“源码伴随包”和“更新制品 workflow”的区别。

### macOS 15 基线的理由已经失效

macOS 15 最初因为官方 tmux Darwin 二进制的 deployment target 被升为产品基线；tmux 已退出当前分发，但基线仍存在。不能直接断言应降低版本，因为 Herdr、Tuwunel 托管包、Tauri 2 和其他 Mach-O 可能提出新的最低要求；应重新检查当前分发物的实际 deployment target，再给 macOS 15 写入新的证据或降低基线。

### Dagu research 的旧阻断表述没有跟随设计改判

`docs/research/workflow-engines.md` 仍把 `human.task` 缺少 attempt generation 写成阻断性 P0 风险；当前 Run 合同已经改为 generation 全在 HCTL，Dagu 只作路标，未获准推进会被回读为 binding 分歧。研究文件是追加式证据，不应改写旧段，但需要追加当前改判，避免读者把历史风险当成现行合同。

### 版本标头与引用精度

`context.md` 和 `participant.md` 仍标草案 v0.14.1，而总基线是 v0.15.0。若标头表示“最后一次语义修改版本”，应明确写出；若表示“所属规范基线”，应统一更新。`architecture.md` 对远程端点“约束与未决问题”的引用只指向整个 `spec/system.md`，没有精确标题，读者无法定位。

## 实现现状与验证结果

截至本报告基线：

- Rust workspace 只有 `hctl2-tool` 与 `hctl2-protocol`；
- `hctl2-tool` 只实现 help/version 和稳定错误 envelope；
- 尚无 `hctl2-control`、公共 `hctl2` CLI、SQLite 账本、domain command、outbox 或 provider adapter；
- 主要实现工作集中在 Buck2、三目标打包、离线安装和四项外部服务生命周期；
- 本机 macOS arm64 运行第一方 Buck2 test：5 项通过、0 失败；`root//:clippy` 构建成功；
- 本轮没有重跑完整外部依赖包和发布包，因此不对最新版完整发行生命周期作额外声明。

所以目前是“供应链和设计先行、产品内核尚未开始”，不是一个已有完整功能、只需补界面的系统。

## 建议的下一步

### 第一项：收窄并完成 P1

先完成 Herdr 最小真实路径：精确 command/cwd/env 启动、观察、断开重连、输入、resize、停止，并对 exit code、stop receipt、sequence/gap 和 writer 保证做类型化降级。当前正式路径先使用 `native_interactive_allowed`。

同时把 `hctl2-tool` 收窄为 B2 需要的 Git/worktree/readback 原语；已有工具能完成的部分只做受控调用，不重写功能。

### 第二项：实现 B0

随后建立 `hctl2-control`、公共 `hctl2` CLI 和 SQLite 底座，最小验收包括：

- 唯一 writer；
- command idempotency；
- 相同 key 异载荷拒绝；
- event/outbox 持久化；
- 崩溃和重启后得到相同结果；
- Query/Preview/Submit/Subscribe 最小公共接口。

新依赖按仓库纪律先研究成熟 Rust 组件；服务、数据库迁移、CLI 和 IPC 不手写已有轮子。

### 第三项：B1/B2 的首个真实开发切片

在 B0 之后接入最小 Project/Task、Herdr 和 Git 工具链，完成一次真实非文档代码修改、测试、readback 和 Integration Receipt。先以这条链修改合同细节，再考虑 Dagu、完整 Gate 和 Workbench。
