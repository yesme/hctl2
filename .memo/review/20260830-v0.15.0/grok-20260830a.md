## 结论先行

承重架构是对的，不该再推倒。瑕疵主要是合同过密、文档还在说死人、实现停在「能装四个依赖」而领域代码几乎为零。下一步不该再开一轮架构，而该把 **P1 做成真的，然后走 B2 无 Run 切片**。

不要做：再写 v0.16、Workbench、复活 agentd、Linear/GitHub、Dagu `human.task` 全套、Context small-brain、13 条 MUST 大扫除、Vikunja Done 适配器。

## 1. 现在的 design 正确吗？

对。四刀切分现在是同一套话，而且互相正交：

1. **语义**：Project / Task / Run / Agent，短路是设计不是例外
2. **部署**：展示 / 控制 / 执行；client-server 是架构，local-first 只是默认装法
3. **数据**：metadata / content / artifact；能承载 ≠ 能裁决
4. **完成**：只有有权人和 task-bound Run 正常完成后的同一条「完成 Task」命令；七件事实不许互冒

v0.13 之后几条纠偏也是对的：三条底线（工具不是人、合入钥匙不进工具、隔离 worktree）不可关；OS 笼子是加固；Dagu 只当路标；P0 只验自己的接缝；Herdr v0.8.2 做不到的事写进合同降级，而不是再造一个终端产品。

所以：不要再找第五个模块，也不要再为每个 crash point 发明一个聚合。0.7→0.8 的教训、0.12 审计的教训、0.13 所有者的批评，三次指向同一件事——架构主线已经够用。

### 真正的瑕疵

按会伤害下一阶段的程度排，不是按文档字数排。

**A. 合同写成了分布式恢复系统，产品主线是单用户本机自举。**

分层 generation、丢失/fence、outbox/readback、CT 负例矩阵，作为长期正确性骨架成立。作为第一份代码的施工图过重。所有者已经批过「禁令穷举不完、先看正确道路有没有内生冲突」；[doc-cleanup-backlog](../../notes/doc-cleanup-backlog-20260825.md) 里 13 条过强 MUST 仍写着「先不改」，其中 `agentd-only terminal`、`tmux 拓扑写死` 相对 v0.14.1 已经过时。实现者若按字面 MUST 开工，会先建不该建的子系统。

**B. 文档漂移，死人还在说话。**

现行合同层已经几乎清掉 `agentd`。但还活着的有：

- `hctl2-agentd-prd` 状态仍是「讨论中」（83 条 AGD 归属作废，能力清单还有用）
- `participant.md` / `context.md` 仍盖 v0.14.1
- `architecture.md` 指向 `spec/system.md` 的「端点约束与未决问题」——目标文件没有这一节
- 决策史 §19/§22/§25 仍按 `agentd+tmux` 口吻写，读者从中段进来会以为那是现行选型
- `workbench-shell.md` 正文还写第一阶段 Electron，合同已是 Tauri 2
- WezTerm 在 delivery / agent 场景表里仍像一等客端；v0.15 的一等原生终端是 Herdr TUI

这些不是架构错，是会把 harness 带进死胡同的索引错误。

**C. Agency 合同有一大块是「标明做不到」。**

Herdr v0.8.2：无统一 writer gate、无逐次输入事件、事件环无 sequence/gap、退出/停止回读不足。合同诚实，这是优点。代价是 `managed_single_writer` 基本是纸面模式；第一阶段真实路径是 `native_interactive_allowed` + 不完整 provenance。B2 必须按这条路设计，不能假装租约剧场已经成立。

**D. Context / Participant 横切正文超前于 B2 真正需要的最小集。**

专章该有——fable O1/O2 拍过，§21 也落了合同。但「快省准 + small-brain + 压缩 + 七层身份」对第一次自举过重。B2 真正要冻结的是：选中的来源、digest、权限、隔离 worktree。其余（派生索引形态、跨 Repo 传承、lesson 自动提案）合同自己都还标着未决。

**E. 单用户三选二仍是产品空洞。**

合同现在写：第一阶段只证明逻辑 Participant 分离，物理独立标 known/unknown。这比假装「三个模型 = 独立评审」诚实。但 B5 仍要求在自己仓库上走完三选二。一个人开发自己时，要么三席绑同一人（独立性作废），要么模型当评审（允许，但没写成第一阶段构成规则）。这不挡 B2（delivery 写明 B2 不等 quorum），但会在 B4 炸。

**F. 实现已经偏了一点，还没有走进领域。**

- delivery 说 content 系统在 control 出现后、按首次消费产品化；仓库已经用 `hctl2-services` 管五进程一键启停。工程上合理，权威上这份脚本在组件表里没有名字。
- P0 合同要的是实际 API；发行 smoke 基本是 health。这正是 v0.13 批过的「能启动 ≠ 接缝成立」。
- `hctl2-tool` 只有 `--help` / `--version`。P1 出门条件「工具箱就位」没达成。
- v0.15 把 Vikunja Done 做成可请求完成命令，方向对，但 command envelope 还不存在。现在去做 provider 事件适配器，是倒着建。

**G. 产品赌注仍没量。**

11 家都留模型自报侧门，可能因为人关单太烦。HCTL 赌的是「证据替人验好、人按一下」。`CT-PRODUCT` 有「十秒答六问」，没有关单动作数/等待秒。整机 RSS 还停在 tmux 基线。这些是产品风险，不是对象模型错误；量要在 B2 之后，不要再为此加一章设计。

**不算瑕疵、不要再争论的：**

- 四模块不是流水线
- 不做自建聊天桥
- 不做 agentd / 内置 Agency / 自建 PTY
- Dagu UI 不当普通 Run 入口
- 房间不开 E2EE
- Workbench 不是内核
- 第一阶段不做 Windows / 多用户 / 双远端看板完整适配

未决清单里剩下的（多 Task Run、Project 拆并、远程认证、预算耗尽、Scoped Room 归档）都是第一阶段之后的产品问题，现在立法是补丁链复发。

## 2. 下一步做什么

一句话：冻结架构，补完 P1，用 B2 来打设计。

按仓库自己的 P/B 表，加上 checking 的教训，顺序是：

### 0. 最多半天的「死人封印」（可选，但便宜）

不改合同语义。只做索引卫生，避免下一个 harness 按废纸施工：

- agentd PRD 头改成「已废弃组件归属 · 条款待按 Herdr / control / tool 三类重归」
- cleanup backlog 里明显过时的两条标过时
- 决策史 §19/§25 加一句「已被 §29 取代」
- 不要重写 13 条 MUST——所有者说过先不改，实现时按 v0.13 三条底线读，过强句当债务

### 1. 把 P1 做真（现在的主线）

两块，可并行：

**`hctl2-tool` 真正的机械能力**——隔离 worktree、Git 身份/有效变化、保全、失权、稍后才要的合入 readback。没有它，B2 的「隔离工作树 + Integration Receipt」是空话。现在这个二进制是脚手架。

**Herdr 接缝探针**——按 delivery 第 2 项：版本协商、建 workspace/pane、输入/resize、观察/重连、停止/退出、恢复等级翻译。现有 smoke（protocol 行 + snapshot）不够。旧 `src/testing/tmux` 只留对照，不要扩成产品路径。

P1 明文还要求「用 Herdr 原生 API 启动、观察、停止一个 Harness，不带治理语义」。这比再讨论 Agency 抽象更接近产品。

agentd PRD 83 条不要整表重归再动手。抽出 P1 真正用到的十来条（现场保全、失权、观测来源分级、做不到就降级）跟代码走；其余等 control 出现再归。

### 2. 只补会挡住 B1 的 P0 接缝

- Tuwunel：AppService、按事件 ID 读正文、加密状态回读（B1 要用 Room）
- Vikunja：卡片读写、条件写入是否可用（B1 影子 Task）
- Dagu `human.task` 不挡 B2，delivery 写过，别提前做

不要把发行 smoke 绿当成 P0 出门。

### 3. 然后才是真产品：P2 / B0 → B2

`hctl2-control`：一本 SQLite、单 writer、命令信封（actor 来源 / expected version / 幂等）、Query/Preview/Submit、公共 `hctl2` CLI 的 `init/start/status`。

B2 纵向切片 A 才是「设计对不对」的第一次实验：

> Project Room → 一次有边界的 Room Invocation → 隔离 worktree 改真实非文档代码 → 人看 diff/证据 → CLI 点完成

这条路故意绕开 Workflow、Gate、三选二、Workbench、Vikunja Done。它会打脸或确认：Context 最小冻结、写租约、三条底线、Receipt。设计里过密的部分，以这次打脸为准收，而不是再开评审轮。

### 4. 过程上随时可拍、不挡产品的

CI 的 A/B/D（发行整包还要不要挡第一方 PR）。C 已落地，cache 后 Darwin 不再是常态 50 分钟，但职责判断仍要所有者拍。这是合入口径，不是领域设计。

### 明确排到 B2 之后

| 事 | 为什么晚 |
| --- | --- |
| Workbench / Tauri | P3，不承担 B0–B5 |
| Dagu / Run / 三选二 | B4；先把单用户 Gate 构成写成一句正面规则再开工 |
| Vikunja Done → 完成请求 | 先有同一条完成命令，再接 provider 事件 |
| Context 压缩 / small-brain / lesson | B2 用指针+digest 就够 |
| 远程控制面 / 多机 | 架构方向已定，第一阶段只本机 |
| 关单摩擦指标、整机 RSS 上限 | 有 B2 再量；现在立法是空的 |

## 该信哪一层

- 信合同层的四模块、三条法、两条完成路径、三条底线、Herdr 降级条款。这些 checking 从 0.7 打到 0.15，没有被推翻。
- 不要按 CT 负例矩阵的密度排期。那是验收语言，不是施工顺序。正确道路是切片 A。
- 不要按 `hctl2-services` 已经能起五进程，就以为进入了 P2。那是发行面提前，治理事实还没切换。仓库对自己这点是诚实的：没有公共 CLI，没有完整应用。
- 0.12 审计加过的机制，以 0.13 收窄后的版本为准，不要把在场证明和沙箱入场券从决策史中段捡回来。

若只做一件事：把 `hctl2-tool` 从帮助文本变成能隔离 worktree 并回读 Git 的工具箱，同时给 Herdr 一条可重复的 start/observe/stop 探针。做完这两件，设计文档里剩下的对错会自己浮出来；现在再评一轮 v0.15，边际收益已经很低。
