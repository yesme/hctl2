## 一、总判断:设计文档是正确的,可以按它开工

三个最重要的架构判断都站得住,而且在逐文件核对中彼此一致:

1. **治理事实唯一权威在用户级账本,content 三分(metadata/content/artifact)。** 这条从 v0.10 走到现在没有再动摇,4×3 归属矩阵、丢失恢复合同、Git 双重角色(正文 home vs 判决审计影子)在 architecture/system/各模块合同里说法一致,没有发现互相打架的地方。
2. **供应端全部可替换、复杂度外包。** 四个默认二进制(Tuwunel/Vikunja/Dagu/Herdr)+ 各模块自己的受控端口和薄 adapter,不建通用 shim——这个刀法把"自建面"压到了 control + tool + 适配代码 + Workbench 四块,是对的。
3. **v0.15.0 的"客户端没有等级、动作合同是真正边界"是正确的收尾。** 把权限语义从"客户端产品类别"移到"动作落点 + 可验证信封",系统合同的五类动作分类(content 写入/human 命令请求/运行时输入/结果提议/不支持的 mutation)和四模块逐一裁决的实际路径,是可测试的合同而不是口号;Vikunja Done 的信封条件(doer 映射 + 明确前后变化 + remote revision + fresh readback + 规范幂等 tuple)把口子开得足够窄。

v0.7.0→v0.15.0 的轨迹本身是健康信号:几乎每个大版本都在**做减法**——自建聊天桥接退役(v0.12.2)、"用户在场证明"与"沙箱入场券"撤销(v0.13.0)、P0 从替第三方验轮子收窄到只验自用 API(v0.13.0)、agentd 与自建终端服务退场(v0.14.1)、客户端等级取消(v0.15.0)。方向一直朝着"治理内核最小、其余外包",且每次都留了撤销记录。

三处我特别背书的设计(核对过闭环):Run 正常完成谓词 + Task claim 双态(`active/completion_pending`)把"Engine 报告完成 ≠ Run 完成 ≠ Task 完成"三层缝全部封死;"重试"拆成五种身份不同的路径(传输重投/候选切换/Engine retry/语义返工/替代执行)是对这个老问题最干净的切法;代次分三层(语义 owner / runtime / 基础设施 fence)并禁止混写,配合"丢失"状态的唯一定义处,恢复语义没有含糊地带。

## 二、瑕疵

### 结构性瑕疵一:合同层钉死了 Herdr v0.8.2 的能力细节,和自己发明的能力声明机制冲突

spec/agent.md 明文写"Herdr v0.8.2 的能力边界进入合同",并列出 512 条内存事件环、无公开 sequence/gap、API 与原生 controller 交错写入等版本特定事实;spec/system.md(§受控端口、§单写者两处)与 spec/connections.md(§启动顺序)各自复述一遍。合同层至少六处点名 Herdr v0.8.2。

但设计自己已经有这些事实的正确安放处:Resolved Port Binding 冻结"实测能力与降级方式",Execution Spec 冻结输入策略。合同层只需要**能力语汇**——栅栏回显、逐次输入记录、事件游标、退出/停止回读四项能力"有则如何、无则按低信任降级"——具体某版 Herdr 缺哪几项,属于 delivery.md 的 P0 条目、研究记录和 binding 声明。现状的代价:Herdr 走双周稳定版节奏,它每补一项能力,HCTL 都要修改规范性合同并滚版本号;而"不得把 Dagu、Vikunja 或 Herdr 的私有对象提升为 HCTL 对象"的既有纪律,精神上同样适用于"私有版本的能力清单"。建议:合同层改写为能力条件句,v0.8.2 缺项清单下沉到 delivery/binding(一个 patch 版本可完成,语义不变)。

### 结构性瑕疵二:设计领先实现太多,继续打磨文字的边际收益已经转负

v0.13.0→v0.15.0 五天三个大版本,全部是文字;`src/` 里实现只有 63 行的 protocol crate 和 142 行的 hctl2-tool 骨架。合同精细度已经到了只有实现能证伪的深度——Execution Spec 十几个冻结字段、Task 双路径创建的崩溃恢复、Context Bundle 的逐项压缩记录、Result Proposal 的逐输出代次 tuple。这些不是错,但每个未实现的合同细节都是一笔**设计负债**:实现接触现实后必然有一批要改,而且文档纪律自己写了"第二轮审计若主要发现第一轮新增概念的问题,回滚而不是打补丁"——这条规则的存在本身说明作者知道边际在哪。结论不是文档有错,是**该停手了**:v0.15.0 足以作为施工基线,之后只按实现反馈改。

### 局部瑕疵(可归入一个 patch 批次)

1. **CT-PACKAGING 没跟上 Tauri 换选。** delivery.md 的 CT-PACKAGING 仍是 Electron 专用措辞("renderer Node/raw IPC/远程脚本…拒绝");v0.14.2 已把安全边界合同改成壳中立(Tauri capability/permission/scope 与 Electron 安全网并列),但"未声明的 Tauri capability/IPC 即拒绝"的失败用例缺位。合同变了、测试矩阵没变,违反"新合同要配 CT 失败用例"。
2. **"引擎只是路标,不拦判决"在派发侧不对称。** 完成与评审确实只依据账本;但 Obligation 只在"control 观察到路标进入等待态"时铸造,引擎失联期间**新派发会停**(安全暂停)。architecture.md 的降级叙述("路标停更只待对账,不拦判决")容易被读成"引擎宕机 Run 照常推进"。补半句"路标停更时新义务的铸造随之暂停"更诚实,不改变任何机制。
3. **版本戳不齐。** participant.md 与 context.md 头部仍标 v0.14.1(v0.15.0 重印未覆盖);vision.md 与 spec/README.md 标 v0.15.0 但日期写 2026-08-29(拍板实际在 08-30)。
4. **错字。** agent.md 场景表"场景客端"(缺"户")。

以上四条加上瑕疵一的下沉,建议合并为一个 v0.15.1 patch 批次;之外我没有发现事实性矛盾——特别核对过的高危缝隙(README 无等级口径与图、Herdr TUI 从"带外"改判"正常运行时输入"在 root README/architecture/agent/system 四处的传播、Vikunja Done 与 Dagu console 的不对称裁决、Request 跨模块字段唯一定义、丢失状态唯一定义)都已一致。

## 三、下一步

**主建议:冻结 v0.15.0 为施工基线(小账并入 v0.15.1),转入 P1/P2,以纵向切片 A——B2 第一次真正自举——为北极星。**理由:P0 的关键探针实质已基本齐备(Herdr 有专项验证记录与 macOS 实测,Tuwunel/Vikunja 有打包与生命周期验证,Dagu 探针合同上本就只需在 B4 前完成),设计侧不存在开工阻断项;剩下的每一分正确性,只能从"第一个真实变更走通全链"里长出来。

工程顺序建议(每步都有明确出口):

1. **B0 底座,先造通用机件。** 用户级账本 schema、command envelope(actor 来源/目标/预期版本/幂等键)、outbox/inbox 与回读。六族规则(Revision/Binding/Receipt/Lease/命令/Snapshot)的正确读法是实现指令:先写一个通用的"冻结记录 + JCS/SHA-256 digest + CAS + 租约/代次"库,四模块只是它的实例化——这一步做对,后面每个模块的合同细节都是配置而不是新代码。
2. **P0 补最后两针(与 1 并行,限时可丢弃):** Tuwunel 的账号/房间/AppService/按事件 ID 读正文与加密状态回读,Vikunja 的卡片/分组/条件写入/webhook 观测——都是 B1 首次消费前的合同要求。
3. **hctl2-tool 最小集(P1):** Git identity 无副作用读取、worktree 保全与失权、integration intent 执行与回读。三条底线里两条("合入钥匙不进工具""隔离工作树")的物理执行者就是它,现在只有 142 行骨架。
4. **B2 切片打通:** 注册 Repo → 挂接现场 → Project/Task → Project Room 发起写入型 Room Invocation(经 Herdr adapter)→ 隔离 worktree + 写租约下产出 ChangeSet Revision → integration intent/Receipt → 「完成 Task」。第一个真实的非文档变更走通,设计负债从此按事实清偿,文档修订从"审出来的"变成"跑出来的"。
5. **上游同步走一步:** 给 Herdr 提四个 issue——栅栏回显、逐次输入记录、事件 sequence/gap、退出/停止回读。它们是 `managed_single_writer` 从"HCTL 入口校验"升级到"物理执行点强制"的前提;Herdr 双周发版且第三方移动端生态(Moshi/ServerCC/Redock)正把它推成事实标准后端,这类通用能力的诉求越早提越可能被排上。

不建议做的:继续整轮文字审计(见瑕疵二);在 B2 之前碰远端任务后端、远程控制面认证或预算硬上限(未决问题列表是诚实的,它们都不在自举路径上)。
