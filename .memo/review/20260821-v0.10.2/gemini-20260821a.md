## 一、 仓库定位与当前形态

HCTL2 是为同时管理多个 Coding Harness（Codex、Claude Code、OpenCode 等）的开发者设计的项目协作与治理系统。其核心主张是把**人主导的目标塑形**（讨论提炼为承诺）与**机器驱动的可验证施工**（授权、执行、裁决与独立验收）连接成机械可校验的事实链。

当前仓库状态是一份高密度的**纯设计与合同规范基线（草案 v0.10.2）**，约 3,800 行 Markdown，暂无生产代码、构建脚本或测试套件。当前全部工作均在为后续 B0–B6 自举提供不可违背的语义与合同边界。

0.7+ 的演进历程体现了极其清晰的“反思—纠偏—立法—收口”主线，经历两次关键摆动后收敛为当前形态：

| 版本阶段 | 演进动作与动因 | 核心收益与定调 |
| --- | --- | --- |
| **v0.7–0.8** | 收敛为四模块结构。v0.8 试图通过激进删减“消除平行权威”，导致愿景层和解释性心智模型丢失，多轮评审（Kimi/Grok/Fable）暴露出补丁链膨胀与概念缺失（如 `ChangeSetRevision`、`Artifact` 缺位）。 | 暴露出“合同去重”与“解释保留”的边界混淆。 |

## 三、 核心架构优势与理论突破

### 1. “七件事实不许互相冒充”
HCTL2 将现实开发中最容易混淆的七层事实做了彻底的语义切割：
> **Harness 跑完、进程退出、代码提交、评审通过、CI 变绿、外部 Issue 关闭、Task 验收通过** 是七件彼此独立的事实。

* **不可冒充的 Actor Provenance**：沙箱中执行的 Harness 无法自报人类身份调用终结命令；
* **Task 终结权严格收口为两条路径**：仅限有权人类在看板提交，或绑定 Task 的 Run 正常 Completed 后由 Reducer 提交同一个 `CompleteTaskIntent`，且 Task 模块必须独立重验。

### 2. 三维正交切分体系
* **语义分责（4 模块）**：Project（意图）/ Task（承诺）/ Run（治理）/ Agent（运行），短路（无 Run 的调用、无 Task 的施工）是显式设计；
* **部署分面（3 面）**：展示面（仅投影与类型化命令）/ 控制面（唯一治理权威）/ 执行面（专职承载 content 与物理执行）；
* **数据分类（3 类）**：metadata（控制账本）/ content（系统记忆）/ artifact（Git 结晶），配合三条铁律（能承载 ≠ 能裁决；冻结摘要是防火墙；命令走 HCTL、记录落平台）。

### 3. 高标准的文档工程与审查留痕
* 语义变更单独提交并标注 `(semantic change)`，单次提交全量清扫关联文档并同步 `decision-history.md`；
* 规范性文档中完全隔离合同层与设计层语言，无合同词汇逆向泄漏；
* 外部参考实现（Implementation Evidence）固定 commit、License 与明确的裁决边界（采用 vs 拒绝）。

## 四、 核心风险与开工障碍（从规范到代码的代沟）

当前设计在逻辑严密性与哲学自洽性上处于极高水平，但从“规范”走向“代码实现与自举”面临以下实质性挑战：

1. **第一阶段进程拓扑与 Local-First 体验的张力**：
   第一阶段出门门槛要求拉起 Electron Workbench + Rust `control`/`core`/`agentd` + Conductor（需 Redis/PG）+ Matrix Homeserver + 本地任务服务器。开箱运行 5~6 个进程对单机开发者心智造成显著负担。纵向切片 A（无 Run 自举）才是真正的最小可用闭环，需明确标记切片 A 之后的组件为“可延后独立裁剪项”。
2. **合同深度押注于未验证的外部依赖能力**：
   - Matrix 事务 ID 幂等与单 Homeserver 线性顺序；
   - 任务后端支持 CAS 条件写入令牌（Vikunja 等候选未实测）；
   - Conductor 单机最小持久化打包与分发重量。
   *结论：交付文档中的 5 项开工前限时验证是事实上的 Phase 0 阻断门禁，必须先于 B0 开工。*
3. **关键高频规则仍滞留于 Memo 讨论稿**：
   - `ContextManifest` 的新鲜度、覆盖、预算与组装规则（`.memo/design/context-design-20260819.md`）；
   - Participant 7 层拆分与单用户三选二 Gate 构成规则（`.memo/design/participant-design-20260819.md`）。
   若不升格为合同，在自举阶段（B2/B4）将导致实现分叉。
4. **唯一不可再生资产缺少备份与迁移规范**：
   用户级元数据账本（`~/.hctl2/control.sqlite`）被定性为“唯一不可再生的权威，必须备份”，但目前备份、导出、搬迁与损坏恢复机制尚无正式合同。
5. **规范密度无可执行对偶**：
   状态机目前以散文与表格形式存在，缺少配套的可执行契约测试矩阵（Contract Test Suite Skeleton），隐式矛盾可能拖延至编码阶段才暴露。
6. **零星历史文字残留**：
   `docs/design/spec/connections.md:12` 中仍保留“同一 RepoInstance 内的目标状态……在一个事务中提交”的旧表述，需修正为用户级控制面账本事务。

## 五、 下一步行动与演进建议

1. **封笔停更纯文本理论文档**：停止 0.11 的理论扩写，避免陷入过度设计的自旋；
2. **将 5 项限时验证定性为 Phase 0 即刻启动**：验证 Matrix 时序、Vikunja CAS 令牌与 Conductor 最小单机栈；
3. **锁定切片 A（Slice A）为首要物理里程碑**：优先打通 `hctl2-core` + `hctl2-control` 最小命令管道与 Project/Task 基础功能，实现 B2 阶段真实无 Run 自举；
4. **收拢 Context 组装与单用户 Gate 规则入合同**：消除自举阶段的规范空白；
5. **契约测试骨架与 B0 命令信封同步落地**：将散文状态机约束转化为第一批可执行测试用例。
