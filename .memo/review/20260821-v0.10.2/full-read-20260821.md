## 项目一句话

给"同时管多个 Coding Harness 的开发者"的项目协作系统：把**人主导的目标塑形**（讨论 → 承诺）与**机器驱动的可验证施工**（授权 → 执行 → 验收）连起来。核心洞察是"七件不同的事实"——Harness 跑完、进程退出、代码提交、评审通过、CI 绿、外部 Issue 关闭、Task 验收，全部不许互相冒充；整套系统就是把这条边界做成机械可校验的事实链。当前只有设计文档，零代码，配套 B0–B6 自举计划与契约测试矩阵。

## 版本演进（0.7 → 0.10.2）

主线是纠正"过度简化"与"补丁蔓延"两个方向的摆动：

- **v0.7–0.8**：收敛为四模块结构；kimi/grok/fable 三轮评审（2H/24M/47L）暴露补丁链问题。
- **v0.9.0**：恢复愿景层——上一轮删过头，确立"权威去重只针对合同，不针对解释"。
- **v0.9.1**：设计层/合同层两层分家；复合概念 41→28，立命名门槛与六族规则（Revision/Binding/Receipt/Lease/Intent/Snapshot）。文档方法论成型点。
- **v0.10.0–0.10.2**：最大架构转向，全部由 .memo 讨论驱动：4 场景 × 3 类数据立法（统一律"artifact 是 content 的结晶"）；三面架构与场景/系统正名（第四模块改名 Agent）；控制面归用户级——一人多机连同一本 metadata 账本，"协作随用户走、clone 只是物理现场"，干掉"Room 账本住 clone"的灵魂存肉体错误；chat server（Matrix）拥有消息 content；每 Repo 选任务后端；判决双层保存（账本权威 + Git 结晶副本）；砍 per-clone 账本只留锁与缓存。

## 三个正交切分

1. **语义分责（4 模块）**：意图→承诺→治理→运行，Project/Task/Run/Agent 各拥有一段事实；短路是显式设计（Task 可无 Run、Project 可直达 RoomInvocation），不是流水线。
2. **部署分面（3 面）**：展示面（Workbench/CLI，只投影+类型化命令）/ 控制面（control+core，唯一治理权威）/ 执行面（chat server、task backend、Workflow Engine、agentd）。client-server 是架构实质，local-first 只是默认部署形态。
3. **数据分类（3 类）**：metadata/content/artifact，配三条法——能承载≠能裁决（平台消息不能触发派发、拖卡不能完成 Task、引擎 COMPLETED 不能签凭证）；冻结摘要是防火墙（content 可变、治理引用 digest 冻结）；命令走 HCTL、记录落平台。

## 贯穿全系统的机械纪律

- 正式变化 = 类型化命令（actor + expected version + 幂等键 + digest）；外部事件只能是 Snapshot/ResultProposal，经准入才变事实。
- 三个单写者（用户级账本、per-clone control、agentd scope）全部锁 + generation，旧代次一律失权；副作用走持久 outbox + 回读，ResultUnknown 不盲目重做。
- "重试"拆成五条身份不同的路径（传输重投/候选切换/Engine retry/语义返工/替代执行），混用即错。
- 权限只能逐级缩小：Project role → Run Manifest → ExecutionSpec → envelope。
- Task 完成只有两条路：有权 human 从 Kanban 提交，或 task-bound Run 正常 Completed 后 reducer 提交**同一个** CompleteTaskIntent 且 Task 独立重验；Harness/模型/CI/外部 Closed 都不是终结 actor。

## 评价

合同先于代码且自我约束极强：概念数量被主动压缩、每轮评审留痕、决策史与反对意见全部入库。0.7 以来每次转向都在做同一件事：把"靠 prompt 和界面维持的正确性"换成"靠身份、版本、证据机械维持的正确性"。主要风险与 kimi-20260821a 的判断一致：第一阶段体量、合同押注未验证依赖（Matrix 幂等/线性顺序、任务后端并发令牌）、合同密度尚无可执行对偶。
