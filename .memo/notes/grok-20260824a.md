# 开工评论过重：所有者批评（v0.12.3）

> 日期：2026-08-24<br>
> 对象：草案 v0.12.3（`79da0e3`）；Grok 通读设计后的开工评论及其后续解释<br>
> 状态：Informative · 讨论备忘，不改规范。合同与交付仍以 `docs/design/` 为准。<br>
> 来源：所有者对开工评论的五条批评，以及当轮把评论改写成「人话、正面路径」之后的工作笔记。文中「所有者」是批评原文的压缩；「待裁定」是 Grok 的读法，尚未升格。

## 怎么来的

仓库快进到 v0.12.3 后，Grok 给了一份「可以开工、第一刀是 P0 探针」的评论。评论把三件事写成了开工前必须认的硬门：OS 沙箱套不上就不能受治理启动、Dagu 完成接口的代次隔离、探针不能把「能启动」写成「合同成立」。后又补了两句给实现看的话：没有第三条完成路径；三选二不是 swarm。

所有者先要求把这几句讲成人话，接着逐条反问。批评针对两层：一层是**这份评论的写法**（行话、防御、用禁令代替正面道路）；一层是**设计把支撑项抬成主线硬门**是否过了。

## 所有者的批评

下面五条是批评本身。压缩了口头重复，不改立场。

### 1. OS 沙箱是不是主线，值不值得当成开工门票

合同里那句「不能强制 OS 沙箱的候选不得受治理启动」，听起来像强制。所有者问的是产品问题，不是释义：

- 到底强制不强制？还是其实不必强制？
- 能不能把后端撮进一个 image，用 Docker 起？Docker 启动要多久，对桌面 App 是不是太久？
- 现在流行的、**不做多工具协同**的 harness / agent，默认在不在沙箱里？
- 如果它们默认不在，我们费这半天劲干什么？**这是不是主线目标？**

隐含的尺子：主线是人把目标说清楚、承诺可验收、该自动干的活有授权。笼子如果只是加固，就不要写成第一期进场券。

### 2. 完不完成不在 Dagu 里判，代次也不该推给引擎

判断是否完成在 Dagu 外面，在 HCTL。系统对引擎说「做完了」之后，该交给评审关去验。所有者问：**代次关系是应该在 Dagu 层控制的么？**

隐含：把「Dagu 完成 API 带不了代次」写成 B4 阻断，是把适配器接缝抬成了产品问题。身份（第几次尝试）如果本来就在 HCTL，就不该先去验证引擎内部会不会点错下一轮。

### 3. 第三方自己的正确性，不是我们的验收清单

很多「控制验证」听起来像在替 Matrix、Vikunja、tmux、Dagu 证明它们自己的轮子转得圆。「不重复发明轮子」两边都管：不自研聊天服务器、看板、引擎、终端复用器；**也不帮它们做它们自己该确认的事。**

隐含：P0 若变成给依赖写正确性测试套件，就是用另一种方式重复发明轮子。

### 4. 不要用禁令清单代替正面道路；先看正确道路有没有自己打架

「没有第三条完成路径」这类补句，本质是用文字限制 coder：不要叠床架屋，写清楚就行。或者：正确的路只有一条，但你怎么穷举得完所有会出错的情况？**太防御了。**

所有者要的是：

> 首先验证「正确道路是不是有内生的逻辑冲突」。

不是先列「不要实现 CI 绿了就算完」「不要把引擎完成当成任务完成」。禁令穷举不完；逻辑自洽才能约束实现。

### 5. 三选二要正面描述，不要自我辩护

「三选二不是 swarm」和上一条是同一类病：先假设有人攻击，再答辩。所有者要的是正面描述——这个机制是什么、它在正确道路上干什么——不是和群聊互投对比着自辩。

## 当轮读法（待裁定，不是规范）

下面是把批评吃进去之后的工作笔记。不改合同；若要改合同，另走转向并升版本。

### 沙箱：合同写的是强制；不该当主线硬门

合同现状（`spec/agent.md` / `spec/system.md` / 来时路 §16）：HCTL 拉起来的工具必须进 OS 强制笼子；套不上就不得受治理启动。威胁模型已经声明不防「同机恶意用户」，但又把 HCTL 自己启动的工具豁免掉——笼子是为了让这两句同时成立。

流行工具的默认（2026-08 公开文档，单工具、人盯着屏幕用）：

| 工具 | 默认 |
| --- | --- |
| Codex CLI | 开（工作区可写） |
| Claude Code | **关**（`/sandbox` 才开；这层有时还能被自己关掉） |
| OpenCode | **没有正经原生沙箱** |
| 本仓库 `run` 脚本 | 全部跳过权限 |

一个人用一个工具时，业界经常不关笼子，靠人盯。HCTL 更严，是因为多了它们没有的一层：后台开多个工具，这些工具可能碰到完成命令、账本、密钥、别人的工作树。

主线要保住的是下面三件，按重要性：

1. 工具进程不是人。复制人的命令、调用 `hctl2 task complete`，也按不了完成。这是身份，不是笼子。
2. 合入 Git 的钥匙不进工具环境。合入走 HCTL 自己的动作。
3. 写代码只在隔离工作树。弄脏了丢掉。

外层 OS 笼子是这三件之上的加固。第一期把「套不上就不准开」写成 P0/B2 硬门，会把每天都在用的 OpenCode / Grok 挡在门外，也和「尽早拿自己做自己」反着来——设计过程自己就在跳过权限开它们。

**建议（待裁定）：** 受治理启动先强制上面 1–3；外层笼子套得上的套，套不上的标清楚、允许开，合入和完成仍只走 HCTL。不要当产品门票。若采纳，这是合同收窄，来时路单独立项。

Docker：聊天服务器 / 看板 / 施工引擎这三样服务器可以 compose，但编码工具、tmux、agentd、control 不行——它们要碰真实工作树、终端、系统钥匙串。挂卷进去等于在笼子上打洞。Docker 引擎没起来时，冷启动常见十秒到几十秒，Mac 上拉虚拟机可以到一分钟，桌面 App 等这个会关。三个服务器也不该进同一个容器：聊天挂了不该拖死看板和施工。现有打包策略已经把 Docker 排除出统一方式，只给 Tuwunel 在 Mac 上留例外。**不建议用「一个 image 装全部后端」当桌面形态。**

### 代次在 HCTL，Dagu 只当路标

正确顺序（施工图路径）：

1. Dagu 走到一个等待点（`human.task` 在这里只表示「引擎停下等外界」，不是人来评审）。
2. HCTL 看见在等，派出谁、带哪份上下文。
3. 工具交提案和证据。
4. 该过的评审关在 **HCTL** 过。Dagu 不评审。
5. HCTL 点头后，才对 Dagu 说这个等待点可以往前走。
6. 图的成功终点到了，HCTL 再总检材料；齐了，才有资格申请「完成任务」。

所以不是引擎把活交给评审关。是 HCTL 借引擎记住走到哪了。

**代次（第几次尝试）是 HCTL 的身份。** 换人、同一位置再干一次，HCTL 自己开新尝试。Dagu 对等待点关掉它自己的重试，HCTL 说「这个点做完了」就不会点到下一轮。把 Dagu 完成接口的代次隔离写成 B4 阻断，过重；那是适配器接缝。

**建议（待裁定）：** 重试策略在 HCTL；Dagu 只当路标。P0 对 Dagu 只看「能不能当等待点、能不能独立进程连上」，不验它内部完成 CAS。

### 只验接缝，不验人家的轮子

选型看接口够不够用、能不能独立进程连上。不够用就换家。

P0 该验的是我们的边界还在不在，例如：看板拖卡不能完成 HCTL 任务；聊天消息不是命令；引擎说走到终点不等于任务完成。不该验：Matrix 事务 ID 是否幂等、Vikunja 排序算法、tmux 键盘协议全集、Dagu 内部完成队列。那些是依赖自己的轮子。

Grok 开工评论把「能启动 ≠ 合同成立」举成 txn 幂等、If-Match、六工具键盘矩阵，混了两件事。前一类是帮依赖做 QA；后一类里只有「拖卡不能冒充完成」这种接缝属于我们。

### 正确道路：没有内生逻辑冲突；有一处重量

两条路交汇在同一个「完成任务」动作。

- **轻量：** 房间说清楚 → 记下承诺 → 叫一次工具改隔离工作树 → 人看 diff 和证据 → 人点完成。
- **施工图：** 人批准图 → 人开工（两下分开）→ 引擎停在等待点 → HCTL 派人、过评审关、合入 → 图走完且材料齐 → 程序用同一个完成动作去申请 → 任务自己再验契约和证据。

核对过，结构上不互相否定：

- 同一道门、同一把锁。施工进行中，人不能另点完成；施工失败了，程序也不能替人取消任务。
- 施工走完和任务完成是两件事实。图可以走完，验收仍可以不过。这时施工停在「做完了」，任务停在「还开着、需要人看」。人补证据后点完成，或另开一轮施工。不是死锁。
- 评审关过了，只说明这一版过了这一关，不是已合入，也不是任务完成。关卡、合入、验收三张证明叠在一条路上，职责不抢。
- 没有施工图时不做假的评审关。契约写明必须内部独立评审，就走施工图；只接受外部 PR 评审的，引用那次精确证据。分叉清楚。

**有冲突的是重量，不是逻辑。** 愿景要求轻量路径必须比「自己开个终端干完」更轻；合同上合入仍是记下意图 → 工具箱执行 → 回读 → 才给证明。简单改动会变成干活一次、合入一次、完成一次。路通，但可能偏重。要用预览把确认收短，而不是再开一条「CI 绿了就算完」。那是另一件事实，不是漏掉的路。

实现约束写正面道路即可，不要写禁令清单。正确道路写清了，第三条路径进不来——不是因为文档禁止，是因为完成动作不认那件事实。

### 三选二：它是什么

施工图里可以放一个评审关：对已经钉死的那一版产物（一份指纹，改一个字节就是另一版），按事先写好的规则收票。

- 关卡上有几个固定席位，开工时绑好人，跑的时候不换裁判。
- 写这一版的人不占必须的评审席。
- 规则写明要几张同意票。够了，写出「这一关过了」的证明，给后面的合入和验收当材料。
- 产物改了新版，旧票作废，关卡重开。

它做的事：一次施工里几个人按各自方法看**同一版**东西，看的是指纹，不是聊天里「大家好像同意了」。票过的是关，不是任务单。

（不拿 swarm 当对照。要对照时另写，不写进设计正文。）

## 对开工顺序的影响（仍待裁定）

Grok 原评论「可以开工，第一刀是 P0」这句仍成立。改变的是 P0 **验什么**：

| 原评论写成硬门的 | 批评之后 |
| --- | --- |
| OS 沙箱套不上 = 不准受治理启动 | 先保住身份 / 合入钥匙 / 隔离工作树；外层笼子是加固，不当门票（若所有者拍板，须改合同） |
| Dagu 完成 API 代次隔离 = B4 阻断 | 代次在 HCTL；Dagu 当路标；不把引擎内部 CAS 当产品门 |
| 给 Tuwunel / Vikunja / tmux 写正确性矩阵 | 只验接缝；依赖内部正确性不是我们的课题 |
| 给实现补「不要第三条路」「不是 swarm」 | 写正面道路和三选二是什么；不写禁令、不写自辩 |

P0 五条轨里，聊天 / 看板 / tmux 仍要看「能不能独立进程用上、接缝还在不在」。沙箱和 Dagu 代次从「阻断产品」降为「加固 / 适配器」。远端 Linear/GitHub 本来就已移出 P0，不动。

未改的：P0 仍是可丢弃探针，不写 `hctl2-control` crate；P1 才是 `agentd` + `tool`；B2 才是第一次真正自举。

## 尚未拍板

1. 外层 OS 沙箱从「受治理启动入场券」收窄为加固——要不要改合同。
2. Dagu 等待点是否明确关掉引擎侧重试，重试只由 HCTL 开新尝试。
3. 交付文档 P0 清单是否删掉「帮依赖做 QA」的条目，改成只列接缝。
4. 设计正文要不要补三选二的正面一段（不写 swarm）；轻量路径的合入/完成重量要不要在愿景或 Task 正文用产品语言说清。

这四条任何一条进规范，都是转向，不是评论修补。
