## 结论 - GPT

**你的判断基本对，但我会把 mu 的核心说得再准确一点：它不是“给主模型增加 35 道检查题”，而是把散落在规则、提示词和主模型自我判断里的选择，抽出来做成一层独立、类型化、可弃权、可记录的语义决策层。** Jev 是这层的主要后端，但不是不可替换的架构前提；真正值得借鉴的是“在哪些位置判断、只给什么证据、判断后允许发生什么”。

对 hctl2，我认为这是一个很合适的补齐机会，而且不必另起炉灶。你们已经有一份非常接近的任务书：`.memo/design/p2-control-20260906/06-small-brain-engine-research.md`，明确留了 **A：持续建议开 Topic；B：@ 时补齐相关上下文；C：新 Topic 前情提要起草**。mu 能提供这些位置的实现参照，但不应把它的自动审批、自动记忆和完成判定直接搬过去。

另外，三个容易被介绍文章掩盖的事实是：

- **准确数量是 35 个决策点，不是 35 道固定问题，更不是每轮固定调用 35 次。**
- **mu 当前连“目标是否达成”都默认交给生成模型结合检查事实来判断，Jev 是兜底；它并不认为所有判断都适合小判定器。**
- **它的 shadow 模式在权限审批路径上有明确例外，不能理解成全局绝对无行为影响。**

以下主要依据 mu 的 `8dfebe3` 和 hctl2 的 `d58b547` 所对应源码。没有运行真实 Jev 对照实验或桌面实机测试；涉及效果数字的地方，我会区分作者历史测量与当前代码。

### 一、沿源码看：mu 实际在干什么

#### 1. 它是在 pi 的生命周期里插入判断，而不是另写一个万能 agent

关键入口是：

```
packages/kyrn-judge/src/extension/kyrn-judge.ts
```

它把 preflight、任务帧、记忆、技能披露、权限、工具输出准入、遗忘、完成检查、看板、蜂群等功能注册进 pi 的事件系统。注册顺序也有明确含义：中途插话先处理；preflight 先决定本轮档位；任务帧在其他功能读取目标之前更新；硬约束检查在权限审批之前执行。

主干可以简化成：

```
用户消息 / 工具调用 / 工具结果 / 回合结束
                     ↓
             确定性规则先筛一遍
                     ↓
        针对这个决策点构造一小份 state
                     ↓
           一道或一批类型化问题
                     ↓
             Judge 返回判定
                     ↓
        本地 policy：采用 / 弃权 / 回退
                     ↓
       具体 feature 执行动作，并记录结果
```

这里有四种不同的工作，不应混在一起：

| 工作                                   | 谁负责             |
| -------------------------------------- | ------------------ |
| 开放式推理、规划、写代码               | 主模型             |
| 改写目标、写短说明等生成性工作         | Writer／生成模型   |
| 分类、选择、关系判断等有界问题         | Judge              |
| 权限、事件顺序、状态持久化、实际副作用 | harness 的程序代码 |

所以，“大模型负责工作，小模型负责判断”是个有用概括，但不是绝对分工。后面会看到，**证据要求高的完成判断，又被放回了生成模型和硬事实一侧**。

#### 2. 真正的核心抽象是 `DecisionSpec`

`packages/kyrn-judge/src/decision.ts` 中，每个判断不是一段散落的 prompt，而是一份声明：

| 字段                                | 含义                               |
| ----------------------------------- | ---------------------------------- |
| `id`、`version`                     | 判断的稳定身份与版本               |
| `questions` / `questionsFor(input)` | 固定问题，或按候选项动态出题       |
| `buildState(input)`                 | 专门为这个问题组装输入             |
| `policy(answers, input)`            | 把模型答案转成宿主行为             |
| `fallback(input)`                   | 不问、失败、弃权时怎样继续         |
| `capabilities`                      | 需要分类、关系判断、评分等哪类能力 |
| `cacheImpact`、`latency`            | 对缓存与执行时机的约束说明         |

引擎支持 `off / shadow / active`，记录题面版本、答案、模型、延迟、使用量、回退原因等。它还要求大多数 Choice 题有 `none / other / unclear / unknown` 这样的退出选项，避免“无论如何必须选一个真实答案”。

**我认为，这是 mu 最值得拿走的设计。** 它把“这个判断是不是正确、是不是值得做、出错了怎么办”变成可以单独讨论和测试的程序单元，而不是只能凭整段对话感觉好坏。

不过两个细节要注意：

第一，`latency`、`cacheImpact` 不是填上就自动获得正确调度。真正的等待、批处理、缓存边界和迟到结果处理，仍然写在各个 feature 里。第二，账本默认不保存完整输入 state，原因是隐私；因此，**“有账本”不自动等于“可以完整回放所有历史判断”**。

#### 3. Jev 是合适的后端，但不是这个设计的全部

Jev 的接口定位是：输入状态，输出预先定义类型的概率判断，而不是生成任意文字。这个形状很适合嵌进代码分支。官方所谓“不产生幻觉”的论证主要涉及输出 schema 保证；**不能据此推导“语义判断永远正确”**。[TypeSafe AI](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

mu 自己也没有把架构绑死在 Jev 上。配置和级联实现支持其他后端，并区分模型擅长的能力。一个非常实际的例子是：源码明确记录本地 Laya 在关系题和有序评分上不可靠，因此这些能力可以不交给它，直接升级到下一层，而不是“接口一样就都能用”。

对 hctl2 的直接启发是：

> 应该建立“轻量判断接口”，而不是建立“到处调用 Jev 的接口”。
> 引擎能不能做分类、关系判断、生成、可靠返回概率，必须分别声明和验证。

#### 4. 三条最值得深入看的调用链

###### 任务帧：先判断有没有变化，再决定是否生成

`decisions/task-frame.ts` 问的是：

> 这条消息是新任务、增加约束、纠正、切换子目标，还是没有相关变化？

它不负责把新目标写出来。识别到需要变更后，`extension/features/frame.ts` 才安排更新。更新过程还处理串行合并、超时、帧过期、会话切换后的迟到结果等问题。

这比“每来一句话，让模型重新总结整个房间”精确得多。

对 room 来说，可以借的是：

**先检测讨论状态发生了什么变化，再更新相应的派生视图；不要每轮重写所有目标、问题和结论。**

###### 人话看板：先判断有什么新东西，再花钱写说明

`decisions/board-read.ts` 先选择当前阶段、正在处理的验收项、哪些事件值得告诉人、相比上次看板是否有变化。只有识别到值得更新的信息，才让 Writer 写给人看的文字。它甚至把“相关”进一步收窄为“这次更新不说，用户会错过什么”。

这是非常适合 hctl2 的模式：

> **判断值得不值得提示，比生成一条漂亮提示更应该先做。**

否则“智能建议”很容易变成持续制造低价值通知。

###### 蜂群：不是所有发现都广播给所有人

`hive.publish` 判断发现值不值得发布；`hive.deliver` 判断某个收件者是否需要它；`hive.relate` 判断新旧发现是什么关系。发布、投递、取代是三个不同的问题。

这与 hctl2 的 B——“@ 某个参与者时，补齐它需要但还没收到的信息”——高度相关。

但要借的是**按收件者与当前工作筛选信息**，不是把蜂群里的“新发现取代旧发现”直接移植成治理事实的自动覆盖。

### 二、35 个到底是什么，什么时候问，怎么选出来

#### 1. 数量：35 个决策 ID，不是 35 道题

我核对了 `manifest.ts` 与 `manifest.test.ts`。测试会收集源码中 `defineDecision` 的 ID，再与 manifest 比较，不只是检查一份手写介绍。按唯一 ID 计数，是 **35 个决策点**。

不同数量要分开：

```
决策点数量 ≠ 原子问题数量 ≠ 模型请求次数 ≠ 实际生效动作数
```

例如，单个 `input.preflight` 就有 **10 道原子问题**：

| 类型       | 问题                                                         |
| ---------- | ------------------------------------------------------------ |
| 1 道分类题 | 本轮是什么类型                                               |
| 6 道是非题 | 是否旁支问题、需要澄清、需要改文件、需要经验、值得并行、应该先计划 |
| 3 道量表题 | 任务复杂度、推理深度、工具复杂度                             |

这些问题共享一次输入状态，批量判断。另一些决策点则是“一条候选消息一道题”“一个工具输出块一道题”，题数取决于当时的候选集合。

下面按当前 manifest 归组；“存在这个决策点”不等于默认开启，更不等于每轮都会触发。部分功能是可选或实验性的。

这里最重要的不是清单，而是它的**事件驱动性**。

比如工具准入会跳过源码读取、短输出、错误输出和某些已经整理过的子代理报告；主动遗忘只在默认的 50%、70%、85% 等上下文边界考虑新增裁剪；preflight 在父级已路由的子代理里会跳过重复判断。**它不是让一个旁路模型持续把所有问题重新问一遍。**

#### 3. 这 35 个怎么选出来的？

结论是：**人工工程分解，加上生态借鉴和局部实验迭代；不是 Jev 内置题库，也没有证据表明“35”是某种优化计算的结果。**

追溯用的材料是 2026 年 9 月 20 日的 `01-jev-integration-brainstorm.md`。里面先按 pi 的生命周期划分输入、循环内、蜂群、结束等阶段，再列出可以介入的行为，每个位置还有其他开源项目的先例。后来的实现则把这些想法变成独立决策规格，并不断改题面和策略。

我从它的实现中归纳出的选题方法是：

> **先找宿主程序能够改变的动作，再找决定这个动作所需的语义事实。不要先凑一份“模型可以回答的问题大全”。**

例如：

| 先有的动作                 | 才需要问的问题                           |
| -------------------------- | ---------------------------------------- |
| 是否让一块输出占用上下文   | 这块内容是什么性质，是否属于明确噪声     |
| 是否再调用 Writer 更新看板 | 相比上次，是否有用户需要知道的新信息     |
| 是否投递给某个调查者       | 这条发现是否会影响它当前在查的问题       |
| 是否修改任务帧             | 用户是否改变了目标、约束或子目标         |
| 是否继续工作               | 是否还有未完成事实，现有证据是否支持停止 |

这也解释了为什么题目会变化。最典型的是工具输出准入：早期构想问“它与当前目标相关吗”，现在普通路径问的是“这是什么类型的输出”。源码明确说明，本地模型把关系题几乎全判成相关，因此退到更可靠的分类题。

**因此，对 hctl2 不应问“我们还能再列出多少题”，而应问“哪个具体行为目前靠粗规则、靠参与者猜测，或者根本没人负责”。**

#### 4. 如何扩展？

mu 的扩展分三层。

**新增判断内容**：增加 `DecisionSpec`，定义输入、题面、策略、回退、版本和需要的模型能力。

**接入真实生命周期**：在对应 feature 里决定何时触发、哪些候选值得判断、如何批处理、最多等多久、迟到结果怎样处理，以及结果对应什么动作。

**补齐验证与可见性**：加入 manifest、规格测试、标注案例、账本和开关；先看判断是否正确，再看是否真的被采用，最后看采用后是否改善了结果。`mu.json` 可以配置已有决策，但不是往配置里写一道自然语言题，就自动获得一个完整的新功能。

我会额外要求每个新题都回答三个问题：

**判断错了会损失什么？不判断会怎样？这道题的答案到底会改变哪条程序分支？**

第三个回答不出来的题，通常没有必要上线。

### 三、源码里最好与最需要警惕的地方

#### 1. 最好的不是“判断多”，而是把判断边界做小

我最认可四点。

**第一，判断与执行分开。** 模型回答的是有限问题，policy 才决定行为。这比让主模型一边做事一边给自己裁决，更容易审查。

**第二，判断与生成分开。** 任务帧与看板都不是每次直接生成；先识别变化、选材料，再决定要不要生成。

**第三，状态是按问题专门构造的。** 不把整个会话一股脑交给旁路模型，而是给当前动作、目标、候选项、最近变化等有界材料。

**第四，很多错误被设计成可恢复。** 准入裁剪保存原文和指针；遗忘改变发出的上下文投影而不是删除会话历史；不确定时经常保留内容。

这几项比“用了 Jev”本身更有长期价值。

#### 2. 但高置信关系判断，仍然可能错得很严重

`hive.ts` 有一段很有价值、也很不利于过度宣传的校准记录：

作者用 11 次真实 hive 中的 **153 对人工标注笔记**做检查。对于跨调查者的“新发现取代旧发现”，在原来的 0.6 门槛上，**6 次判为取代，0 次正确**；错误中最高置信度达到 0.87。于是跨调查者的取代门槛被提高到 0.9。

这说明两件不同的事。

一方面，作者确实有在看错误，而不是只看模型返回得漂不漂亮。另一方面，**提高阈值只说明挡住了这批已观察到的错误，并不证明新阈值已经可靠**。

对 hctl2，尤其不能把下面这些东西等同：

```
“内容很相似”       ≠ “是同一个 Task”
“后来的说法更完整” ≠ “已经取代旧契约”
“模型说是决定”     ≠ “有权的人已经决定”
“看起来都完成了”   ≠ “可以写入完成状态”
```

另外，mu 的级联只能升级它识别出的不确定答案；**自信但错误的答案不会因为用了级联，就自动被第二个模型纠正**。

#### 3. “小输入”既是优势，也是信息盲区

工具输出准入的当前实现很能说明这个问题。

普通 `tool.admission` 不判断“这是不是完成目标所需的关键证据”，而是分类为错误、结果、进度、重复告警、通过日志等。只对明确的噪声类别进行省略；源码、错误、边缘摘要等有额外保留规则。

这是一种合理退让，但不能把它宣传成完整的语义上下文管理。

同样，`goal.ts` 当前明确说：判断目标是否成立，需要读证据，快速 judge 读得太薄。因此默认使用会话模型或配置的生成模型，Jev 作为后备；未完成验收项、未经验证的修改、失败检查等事实仍然具有约束力。

我的评论是：

> **Jev 适合把已有、可见的状态映射成有限选择；不应期待它替宿主补出被省略的证据。**

对 room，候选召回和 state 构造的重要性，至少不低于选哪个判断模型。一个从未进入候选集合的关键决定，后面的分类器再准也选不回来。

#### 4. 单次判断便宜，不等于系统整体更便宜

作者 9 月 21 日的历史回测很克制，结论就是：已有局部正向效果，但不能证明整体净收益为正。几个例子：

| 历史观察                                          | 应怎样解读                                                   |
| ------------------------------------------------- | ------------------------------------------------------------ |
| 工具准入判断了 194 批、2,412 个块，没有省略任何块 | 触发器可能花了大量成本确认“应该原样保留”；不是应当为了节省而强行删除 |
| 技能披露确实减少了暴露的说明                      | 能证明隐藏发生，不能直接证明隐藏正确或任务质量提高           |
| hive 明显减少了发布和投递数量                     | 筛选率不是准确率，更不是任务成功率                           |
| 浏览器步骤判定较快，但不少任务未闭环              | 模型调用快不等于整个任务可靠                                 |

这些是早期留存样本的观察性回测，不是当前版本的随机对照；部分原始聚合结果只保存在作者本机，不能当成已独立复现。

后续代码已经做了改进，例如工具输出批量判断、限定值得判断的输出、限制等待时间；preflight 默认不再随档位切换 thinking，以避免缓存代价。这里应肯定它的迭代，而不是把早期结果当成今天仍未修复的缺陷。

真正需要衡量的是：

```
净收益
= 少做的主模型工作与返工
- Judge 成本
- Writer 成本
- 缓存损失
- 误判后的补读、恢复与重做
- 对人的打扰
```

对 room，最后一项可能比模型账单更重要。

#### 5. shadow 与权限审批的例外，值得专门记下来

引擎定义中，shadow 会记录判定，但把 fallback 放在 `outcome` 返回给调用者。与此同时，它还暴露了原始的 `judged`。

权限实现中，当用户选择“Jev 审批”时，会采用：

```
decision.judged ?? decision.outcome
```

危险命令路径也明确写了注释：这个审批模式下，shadow 的判断仍然计入审批。

这不是我推测出来的漏洞，而是代码中的产品选择：**权限模式表达了另一层用户意图**。但它意味着用户和开发者不能把全局 shadow 理解成绝对不生效。

还有一个适配细节：部分 Choice 策略在 provider 没提供概率分布时，会跳过概率门槛；`tool.approval` 的 `needed` 也有这样的处理。换成 LLM 后端后，“接口相同”并不保证“置信度策略相同”。

**hctl2 应比这里更严格：shadow 的无副作用保证，放在最终动作准入处，而不是只靠模型引擎返回值的约定。**

### 五、对 hctl2 的启发：不是造一个“房间管理员模型”，而是补齐可审计的轻量判断

#### 1. 你们的 TODO 已经找对了位置

现有任务书的三件事，与 mu 的机制能直接对照：

| hctl2 已有位置            | mu 最有用的参照                                              | 不应照搬的部分                             |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| **A：持续建议开新 Topic** | `board.read` 的变化／新闻性判断，`task.frame` 的方向变化识别 | 不要把“新任务”标签直接变成创建房间命令     |
| **B：@ 时补齐缺口**       | `hive.deliver` 的收件者相关性判断                            | 不要因一次低分就永久丢弃来源或关键约束     |
| **C：前情提要起草**       | `questionsFor` 的候选选择；先选择再 Writer 的两段式设计      | 不要让模型生成来源指针，或把未定改写成已定 |

这三件事在你们现有设计里属于控制面的系统能力，不是 Room 中某个 Participant 的自由发挥；这点与引入一层专用 judge 很契合。

而且你们的约束比一般 agent 产品更严格：前情提要的来源由组装器赋予，草稿在确认前不生效，语义观测不改写权威事实。**这些不是引入小模型后要绕过的限制，而恰恰是让小模型可用的条件。**

#### 2. “提问题”要区分两种完全不同的动作

这里有两个层次：

**系统问 Judge：**

> 这段讨论是否出现值得单独处理的问题？
> 这条消息是不是本次 @ 必须补给参与者的上下文？

**塑形参与者问人：**

> 我们本次是否承诺支持这个范围？
> 这个验收条件是否足够？
> A 与 B 之间要选择哪一个？

前一种适合 small-brain。后一种是人的决定，不能因为模型置信度高就替人作答。

你们的 `hctl2-shaping/SKILL.md` 已经有很好的分工：事实自己查，决定等人说；按依赖关系找本轮可问的“前沿”；已决、尚未定形、出界分开；所有建议通过 Trigger Preview 才变成动作。

所以，我建议不是再增加一个会反复审问人的 agent，而是：

> **让 small-brain 帮忙发现“此刻值得把什么拿到人的决策面前”，让 shaping 负责把问题说清楚，让控制面负责是否接受这个决定。**

#### 3. fork room、创建 task、收敛 task 是三个轴，不是一道总选择题

这是我认为最重要的建模修正。

##### 讨论组织轴：是否值得另开 Room？

判断的是讨论焦点、参与者、上下文和持续讨论成本。

一段讨论很长，不一定应该开新房间；它可能仍然只有一个问题。反过来，一句很短的话也可能引出了值得独立研究的问题。

##### 承诺轴：是否要建立或修订 Task？

判断的是是否形成了交付义务，以及是否需要可追踪的契约。

新 Task 不必对应新 Room；新 Room 也不必产生 Task。研究任务的答案可以未知，但研究产物和验收方式可以明确。

##### 证据与决定轴：是否已经可以收敛？

至少要拆成：

- 讨论的问题是否已经答清楚；
- 是否有权的人作出了决定；
- 是否需要采纳一个新的 Task Revision；
- 是否已有足够证据完成精确版本的 Task。

这些不是同一个“完成度分数”。

你们当前规范本来就允许纯讨论没有 Task/Run；普通 Topic 也不以完成条件、结论回填或结案理由为创建与关闭前置。另一方面，Task 还允许存在未采纳契约的身份映射，不能把“是否已有完整验收项”误当成“任何 Task 都不得创建”的统一门槛。

#### 4. 我建议先做六组判断，而不是复制 35 个决策点

下面是建议的形状，**不是声称 hctl2 现在已有这些接口**。

| 建议的判断组            | 问 Judge 的具体问题                                          | 触发时机                       | 最多产生什么                          |
| ----------------------- | ------------------------------------------------------------ | ------------------------------ | ------------------------------------- |
| `room.topic.suggest`    | 是否出现可精确表述的独立问题？是否值得持续单独讨论？是否已有合适 Topic？ | 讨论出现实质变化后             | 一条可忽略的开题／转入已有 Topic 建议 |
| `context.gap.select`    | 对本次 @ 的目的，这条未交付消息是否必要或有帮助？            | 构造本次 Invocation 的上下文前 | 候选材料选择                          |
| `room.preface.classify` | 哪些原文应进入提要？属于缘起、已定、未定、约束中的哪部分？   | 创建 Topic 的预览阶段          | 带来源的摘录和分节草稿                |
| `task.proposal.ready`   | 是否表达了交付义务？产物与验收能否说清？缺的是事实还是人的决定？ | 明确承诺或候选任务出现后       | Task／契约草案，或待答问题            |
| `task.proposal.relate`  | 与候选 Task 是重复、细化、新增验收、范围冲突，还是独立工作？ | 新提案与已有 Task 可能重叠时   | 对比与修订／新建建议                  |
| `room.frontier.check`   | 前沿问题是否已回答？是否还有冲突或遗漏？是否值得请人确认共同理解？ | 一轮塑形结束、关键答案到来后   | 收敛提醒或下一轮问题候选              |

这里故意没有 `task.auto_complete`。

**小模型可以判断“值得进入完成预览”，不能凭语义印象替代完成凭证。** hctl2 的验收项已经区分 `mechanical / gate / human`，完成针对精确 Task Revision；应继续走已有的完成机制。

##### `room.topic.suggest` 应怎样出题？

不建议直接问：

> “这里应该 fork 吗？”

这道题把太多产品偏好藏进了模型。

我会拆成两步。

先识别状态：

> 当前新增内容，是继续原问题、补充约束、纠正原理解、提出独立问题，还是无法判断？

只有出现独立问题或明显方向变化，再判断组织方式：

> 这个问题是否值得持续单独讨论？
> 把它分出去是否有明确收益，而不是仅仅减少当前消息长度？
> 已有候选 Topic 是否已经承接它？

然后程序根据策略决定是否展示建议。**“语义不同”只是证据，不是开房条件；“值得隔离讨论”才接近真正的产品问题。**

#### 5. 什么时候问：以事件和新证据为中心，不按固定频率盘问

我的建议是：

**A 在有实质变化后问。** 新的人类决定、新的独立问题、明显范围变化、研究结果到来，可以进入候选；普通确认、重复表达、流式片段，不必重问。对同一语义建议要去重，忽略后没有新证据就不要马上再弹。

**B 在实际组装上下文时问。** 以本次 @ 的目的和参与者已获交付的游标为边界，而不是不断给每个参与者预生成所有上下文。

**C 在预览时问。** 开题意图已经明确，就不要再花一次模型调用判断“要不要建议开题”；直接选择来源、分类，必要时生成草稿。

**Task 关系判断在候选提案或契约发生变化时问。** 不需要每来一句聊天，就对全项目所有 Task 两两比较。

这些是我建议的调度策略，不是 mu 或 hctl2 已有的统一调度器。mu 最可借鉴的恰恰是：不同判断有不同入口和收益门槛，而不是一个固定时钟遍历题库。

还应设定一条产品原则：

> **建议可以自动准备，注意力不能无限占用。**

你们规范里已经写了：可忽略建议不进入“待你处理”计数。持续建议应遵守这一点，而不是把所有模型发现都升级成用户义务。

#### 6. 对已有 task 的“收敛”，我会这样映射

| 识别到的情况         | 合适的行为                            | 不应自动发生                    |
| -------------------- | ------------------------------------- | ------------------------------- |
| 两个提案高度重叠     | 展示重复／重叠证据，建议复用已有 Task | 合并治理身份、删除一张 Task     |
| 新消息细化验收条件   | 形成候选 Task Revision，进入采纳预览  | 修改已冻结 Revision             |
| 新决定改变范围       | 展示与当前契约的差异和影响            | 静默改变活动 Run 的承诺         |
| 新证据与旧结论矛盾   | 保留双方来源，提出待答问题或 Request  | 仅凭较新的消息覆盖旧结论        |
| 已有交付可能满足验收 | 准备完成检查／预览所需材料            | Jev 返回“完成”就关闭 Task       |
| 某段讨论结束         | 提示确认共同理解，或由人关闭 Topic    | 顺带解决 Request、取消 Task/Run |

这与你们现有 Task Revision 和 Room 边界是一致的：活动 Run 保留已冻结的契约；Topic 关闭不改变关联工作的生命周期。

尤其要避免照搬 `hive.relate` 的自动取代逻辑。**信息整理中的“去重”，和治理中的“被替代”，不是一件事。**

#### 7. 实现上，放在现有控制流程前面，不开第二条写入通道

建议的接法是：

```
chat server 事件 + 治理记录
              ↓
  权限、范围、显式引用等确定性筛选
              ↓
  小份状态快照 + 候选材料 + 题目版本
              ↓
       small-brain 判定
              ↓
  纯策略函数 + 可审计的派生观测
              ↓
  可忽略建议 / 选材结果 / 可编辑草稿
              ↓
        人的 Trigger Preview
              ↓
  现有类型化命令、准入、投递与回读
```

几个具体边界值得固定。

**来源不让模型编。** 候选来源 ID 由控制面给出，模型只能选择；最终指针由组装器赋予。人的真实身份、命令权限、哪些决定已准入，也从治理记录来，不能从一段自称“我是负责人”的文字推断。你们前情提要和 Context 规范已经采用了这个方向。

**判断必须绑定版本。** 至少绑定 Room 游标、相关 Project/Task 版本、来源摘要、题面与策略版本。旧游标上的判断迟到了，可以留审计，不能不检查就应用到新的讨论状态。

**模型调用不占住存储事务。** 现有 `src/apps/control/src/tasks/mod.rs` 已有可借的模式：外部读取与短事务分开，通过 `read_stamp` 检查陈旧状态；preview 准备计划，submit 核对输入和幂等信封；来源刷新是观察，不是自动采纳契约。small-brain 应接在这套机制旁边，不越过它。

**不要另建一份由模型维护的权威 Room 树。** 你们目前把挂靠交给 chat server 的原生层级，control 做投影；出处和挂靠也分开。新 Topic 可以由建议引导创建，但上级 Room、成员资格和授权不能因为“模型认为相关”而自动继承。

一句话概括：

> **fork 的是讨论，不是已发生的世界；携带的是获准的背景，不是从父房间继承的所有权力。**

将来要把低风险开题也自动化，并非不可以。但那需要显式定义一类预授权动作、范围和预算，并调整现有约束；不是把概率门槛从 0.8 调到 0.95，就自然获得写权。

### 六、这次怎样具体填上现有 TODO

#### 1. 先修正一个评测口径

现有任务书正文说 B 是“**上次收到信息以来**”的缺口，但样本章写成“**上次发言到这次被点名**”之间的消息。两者不是同一个边界。

我建议以实际交付的 Receipt／游标为准。离线材料只有发言记录时，可以把上次发言作为代理变量，但必须明确标注这一限制，不能把它当成真实已交付状态。

否则可能得到一个看似很好的相关性指标，却把参与者从未收到的关键上下文误认为“它已经知道”。

#### 2. 优先落 B、C 的选择能力，再放开 A 的持续提示

这是我的优先级建议：

**先做 B、C 的“只挑不写”。** 输出保持原文、来源可核对，误选与漏选相对容易标注，也没有持续打扰人的副作用。生成式改写单独评测，不与选择准确率混在一起。

**A 先做 shadow 和提示质量评测。** 不只看“有没有识别到新话题”，还看“此时提示是否值得”。命中一个语义变化，但让用户觉得烦，产品上仍然是失败。

**之后再扩展 Task 成熟度与关系判断。** 先输出可审阅的对比与提案，再讨论哪些低风险动作能授权自动执行。

这比先建一个能自动开房、建 Task、关 Task 的通用 room-router 风险小，也更容易知道究竟是哪一层提供了价值。

#### 3. 沿用已有样本计划，但补上动作级指标

你们任务书已经要求至少 A 100 个判断点、B 20 个 @ 点、C 6 次开题，并比较机械规则、Jev、本地指令模型和嵌入模型。这比“接入 Jev 试试看”更有价值，不应因为 mu 的架构有吸引力就跳过。

我建议在这个基础上重点补：

| 层次       | 必须单独观察的指标                                 |
| ---------- | -------------------------------------------------- |
| 候选召回   | 关键来源有没有在进入 Judge 前就漏掉                |
| Judge      | 误报、漏报、弃权，按问题类别分别统计               |
| 策略       | 正确判断是否变成了不合适的动作                     |
| 提示体验   | 每个 Room 的打扰次数、重复提示、忽略后重弹         |
| 上下文     | 必需约束保留率、漏选后的补读、总交付量             |
| 生成草稿   | 是否把未定写成已定，是否出现来源没有的内容         |
| 控制正确性 | 陈旧结果、重复事件、重试是否导致重复建房或重复提案 |
| 总成本     | Judge、Writer、等待、补读与人工干预一起算          |

还需要专门加入中文里的否定、转折、引用和角色差异，例如：“先别做”“以后再说”“他建议”“我不是同意，只是在举例”。这些案例不是靠调一个全局置信度门槛就能覆盖的。

**此次调研足以补入 mu 单案、题目设计方法、触发机制与边界建议；但还不能据此宣布 Jev 已经赢得你们四类引擎的真实对照。** 对模型的选择，应继续由这份样本和动作级结果决定。

当前桌面端是 **Electron + React + TypeScript**，使用 `electron-vite`，依赖中有 React 19、React DOM、Arco Design 等；来自 AionUi 路线。源码里的“原生桌面端计划”主要是在整理桌面交互和去掉浏览器痕迹，不是已经改成 GPUIx。

### 最终建议

**借 mu 的决策单元，不搬 mu 的整个自动化权限。**

对 hctl2，最值得立即吸收的是：

> 把“有没有值得处理的新情况”做成轻量判断；
> 把“该带哪些证据”做成可复核选择；
> 把“要不要形成承诺”留给现有预览与准入；
> 把“承诺是否完成”留给精确版本的证据机制。

你们已经有 Room、Context、Task Revision、Trigger Preview 和 small-brain 的位置。缺的不是再发明一套 agent 架构，而是把这些位置之间的**语义判断接口、触发条件、回退行为和评测口径**补齐。mu 最有价值的地方，就是让这件事从一个模糊的 TODO，变成了可以逐项实现、逐项验收的工程问题。

## 结论 - Grok

你的判断对了一半：核心确实是「有边界的场景判断」，但判断器不是 Jev 这一个模型。源码里的产品是一套 DecisionSpec：题面、概率、本地策略、失败回退、账本。Jev、本地 Laya、任意 LLM 都只是可插拔的答题后端。

仓库是 [qybaihe/mu](https://github.com/qybaihe/mu)，2026-09-22 建，最近推送 2026-09-30。339 star、32 fork、1 个 watcher。预发布 0.1.x，作者自称每天在用。底座是 pi（编码代理循环），桌面端是 AionUi 的 Electron 壳，不是 GPUIx。

### 它实际在干什么

一轮里，主模型仍然规划、写代码、调工具。mu 在 pi 的钩子上插了一层判断内核：`packages/kyrn-judge/`。每个决策点是一次 `defineDecision`，不是一段 prompt。

契约在 `decision.ts`：

- `questions`：boolean / choice / score，选项必须带逃生门（`none` / `other` / `unclear` / `unknown`），否则注册直接抛错。
- `buildState`：把输入压成小状态。注释写明判断器窗口 32K，只送摘要和元数据。
- `policy`：概率变成动作。默认三区，`P≥0.8` 算 yes，`P≤0.2` 算 no，中间弃权。选择题选中项低于 0.6 也弃权。
- `fallback`：等于没有判断器时 pi 的原行为。
- 模式：`off` / `shadow`（问了、记账、不改变行为）/ `active`。默认全部 shadow。
- `decide` 永不因判断器失败而 reject。超时、宕机、畸形答案、弃权，全部走 fallback。

五条铁律写在 `kyrn/docs/01-jev-integration-brainstorm.md`，代码对得上：判断器判断，代码执行，主模型思考；规则先吃确定区，判断器只吃灰区；错了必须便宜且可逆；安全侧只能加闸不能拆闸（`tool.risk` 没答案就弹确认，不能放行）；每次判断入账，题面带 `version`，改措辞必须升版本。

所以 README 说的「每一轮 35 个判定点」是目录规模，不是每轮真的问 35 次。多数点由事件触发，而且可以整批一次请求。`input.preflight` 就是 10 题打在一次调用里。

不是从某个题库抽的，是把 pi 一轮里「现在要么死规则、要么问主模型」的决定点列出来，再按铁律筛。构思文档 §4 按钩子分了 A 输入、B 循环、C 蜂群、D 收尾、E 会话、F 工具。源码里现在能对上的决策 id：

选题标准就三条，而且他们用 bench 证过措辞比选题更要紧。`kyrn/docs/03-local-judge.md`：同一模型、同一状态、31 条标注消息，「要不要改代码」长问法 42%，短问法 `Does user_message request a code change?` 74%。枚举、量词、复合条件会掉到随机。所以扩展规则写在 `input-preflight.ts` 头注释里：一题一个短谓词，状态字段用反引号点名，改措辞就升 `version`。

什么时候问：绑在 pi 钩子上，不是定时轮询。`latency` 分三档：`inline` 堵住循环但有等待上限，`parallel` 跟别的活赛跑，`background` 不堵。`cacheImpact: prefix-mutating` 的点只在缓存边界做（首轮披露、压缩），避免把省下的 token 用缓存失效赔回去。

怎么扩展：加一个 `defineDecision`，在对应 feature 里 `engine.decide`，默认 shadow。动态候选用 `questionsFor`（一条技能一题，一次请求）。每题标能力 `classify | relate | rate | meta`，判断器档案里声明自己不擅长的，级联直接跳到下一档；没有任何一档可信，答案强制中性。新后端只要说同一条线协议 `{state, questions} → {answers}`。

### 对这个设计的判断

值得拿的是不对称，不是 35 这个数字。

判断器的错被设计成单向的：上下文侧拿不准就留；安全侧拿不准就问人；经验侧拿不准就不存。这比「让小模型做路由」稳，因为动作空间是代码写死的，模型选不了选项以外的东西。shadow 默认也诚实：新点先和结果对过再打开。

弱的地方作者自己的回测写得比 README 清楚，见 `kyrn/docs/08-jev-retrospective.md`。技能披露能藏描述（13 个会话里藏了 511 个技能描述实例）。hive 发布门 662 个候选过了 89 个，约 13.4%，但没有证据证明投递改变了任务。工具输出准入占了已记录判断输入的大约 54%，这批样本没有兑现节省。浏览器 14 次真实 Jev 步骤里 2 次 done、10 次 blocked。经验捕获 6 次全 skip。没有同任务的无判断器对照，账本里的答案不等于正确答案。35 个点里，真正闭合了「判定 → 动作 → 事后结果」的不多。

另一处：任务帧仍是替身。几乎所有题都相对 `goal` 作答，而 goal 还不是 writer 维护的 200 token 帧。没有锚，题再短也是在猜。

## 结论 - Claude

mu 是 pi 的深度二开（pi 0.87.1 基础上，一个人用 8 天写了 277 个提交），在 pi 的事件钩子上接了一个「判断内核」：每一轮里 35 个决策点，每个决策点就是向小模型 Jev 问一道有限选项的题，拿到概率后由本地代码决定动作。它最有价值的不是「用了 Jev」，而是**把「判断」从「生成」里剥出来，并且给判断建了一整套工程纪律**：三区间阈值、逃生选项、fail-open、影子模式、每次判定入账。这套纪律和我们 9 月 28 日定的「只挑不写、配了小模型才改写」是同一个判断，而且他们把它做完整了。

对 hctl2 的启发是真实的，但要搬的是**机制和纪律，不是那 35 道题**：那 35 道题几乎全是编码 harness 的回合内判断（上下文准入、工具风险、漂移），没有一道是「要不要开新房间、要不要建任务、要不要合并任务」。那部分得我们自己设计，而且 Grok 在 PR #290 已经把前半截做了。

### 一、它在干什么（读源码）

**抽象只有一个：`DecisionSpec`。** 每个决策点声明：

- `questions`：一到多道题，三种题型。是非题返回 P(true)；选择题返回选项和概率分布；打分题返回在有序档位上的位置。
- `buildState`：把输入压成一个小状态（元数据和摘要，不是正文），决定性字段放最前。原因是 Jev 窗口 32K，超了截尾。
- `policy`：把概率变成动作，或者弃权（`ABSTAIN`）。
- `fallback`：没有 judge 时的确定性缺省，**必须等于宿主原生行为**。
- 另有 `version`（题面或策略一改就加一，让账本可比）、`cacheImpact`（动作会不会改写前缀、破坏 prompt cache）、`latency`（inline / parallel / background）。

**引擎的三条铁则，全部写在代码里：**

1. **fail-open**。judge 超时、报错、弃权，一律返回 fallback，`decide()` 永远不抛错。唯一例外是安全闸门（`tool.risk`），它 fail-closed 到「问用户」。
2. **三区间加逃生选项**。是非题只有 P ≥ 0.8 算「是」、P ≤ 0.2 算「否」，中间一律「不确定」走缺省。选择题必须含 `none/other/unclear/unknown` 之一，`defineDecision` 在定义时就抛错。理由写在注释里：没有逃生门的选择题会以满置信度选一个错的。
3. **三种模式**。`off` 不问；`shadow` 问了、记账、但返回缺省；`active` 才生效。新决策点一律从 shadow 起步，拿账本和事后结果对照后再放权。

**判断和写字分开。** Jev 不生成文字。要写字的地方（任务帧、经验条目、人话看板）另配一个 `writer` 生成模型，而且代码对 writer 的输出做强约束：约束条目必须是用户原话，改写了就换回原句；回复格式不对就整条拒收、保留上一版。

**级联。** 可以配 `laya,jev`：本地小模型先答，只有它拿不准的题才送给 Jev；每个 judge 有能力档案（classify / relate / rate / meta），不被信任的能力直接跳到下一级；没有任何一级可信的题给中性答案，所有 policy 读成「不确定」。本地 judge Laya（3.2 亿参数）只在「这段文字是什么」这类单文本分类上可用，两段文字的关系判断、打分、对请求本身的判断都不行，他们量过。

**账本。** 每次判定一条记录：题面版本、状态的 SHA-256、各题答案与概率、用了哪级 judge、耗时、最终动作是来自 judge 还是 fallback。设计意图是把事后信号当免费标注：被删的内容后来又被召回，说明那次删错了；注入的经验被用上了，说明召回对了。阈值靠这个按用户、按项目校准。实际做到的只有一处（hive 的「替代」关系，用 153 对人工标注把跨 bee 替代的门槛从 0.6 抬到 0.9）。

### 二、社区怎么看

一句话：**几乎还没有社区**。项目 9 月 23 日首发，到 10 月 2 日 339 星、32 fork、1 个 watcher，npm 总下载 837 次，3 个 issue 全是 Windows 安装问题，2 个 PR 来自同一个路人。GitHub Discussions 没开。Hacker News、Reddit、X 上没有任何提到 mu 的帖子。唯一的第三方英文评论是一个自动生成的开源周报，说「值得研究它的决策点架构，但要等 1.0 和英文文档」。

中文那边，作者在 linux.do 发了推广帖，随帖送 3600 个 Jev key。帖子有三页以上回复，但 linux.do 被这里的出口代理拦着，读不到；而且送 key 的帖子，回复数本身不说明评价。[以上标注为「摘要」的，只看到搜索片段]

所以**真正有分量的批评来自两处：作者自己的回测，和围绕 Jev 本身的争论。**

**作者自己的回测**（`08-jev-retrospective.md`，943 条判定记录）结论原话：「Jev 已有局部正向作用，但当前记录不足以证明整体价值很大或净收益为正。」分项：

- 工具输出准入判了 2412 块，**一块都没删**，却吃掉 54% 的 Jev 输入 token。
- 漂移监测问了 252 次，只有 6 次说有问题，「没有验证它们实际救回了多少任务」。
- 经验捕获 6 次全部 skip。
- 目标完成判断被用户反馈「Jev 判断结束不准，读不出测试其实还红着」，于是降级为兜底，改由大模型判。
- 真正有收益的两处：技能说明按需披露（省了上下文）、hive 的发布过滤（662 条候选只上板 89 条）。
- 唯一的对照实验是测试日志裁剪：Jev 在 29 个调好的目标上删 40.2%、必需行零丢失。但真实日志回放时解析器连一个候选都没产出，真实收益来自一条确定性规则：把重复的失败输出折叠，省 51%。作者自己写：「我最初的合成基准测的是一个在这位用户的真实用法里不出现的分布，这一点必须写在前面。」

**围绕 Jev 的争论**（这不是针对 mu，但 mu 全押在上面）：

- 正面：Jev 是 TypeSafe（OpenAI 前 RLHF 团队成员创办，9 月 15 日出 stealth）的托管判断模型，每百万输入 token 0.042 美元、输出免费，一道题 0.3 秒左右。pi 上游在 0.99.0（9 月 29 日）把它做成了原生的 classifier model，LangChain、Langfuse、pydantic-ai 都接了。生态里已有十几个 pi / Claude Code 扩展在做同类事。
- 反面：Theo Browne 说它「大致和一个 switch 语句一样聪明」，用来做压缩是「范畴错误」；他自己花一千美元跑的 Jev 路由基准，效果和一个中档模型持平、略贵、慢 5 倍 [摘要]。社区复测准确率约 73.8%，低于官方 86.6%，并发现选项顺序会翻转答案、状态里塞指令会左右判决 [摘要]。概率不是校准过的置信度：是非题在明显的例子上也只给到 0.83–0.86。
- 对 mu 的直接影响：**pi 上游已经原生支持 Jev**。mu 的护城河不再是「能接 Jev」，而是那 35 个预先接好的点、hive、人话看板和桌面壳。而 mu 钉在 pi 0.87.1 上，要跟上游还得合一大截。

### 三、35 个问题是怎么选出来的

这是你最关心的一问，答案比我预想的清楚，因为作者把过程写了下来。

**第一步：一张分类表，不是 35，是 36 个候选。** 2026 年 9 月 20 日的头脑风暴文档（`01-jev-integration-brainstorm.md` §4）按一轮对话的生命周期分六组：

- A 输入阶段（8 个）：这轮是不是闲聊、要不要先澄清、复杂度、要不要派蜂群、要不要带经验、披露哪些技能、要不要先出计划、中途插话怎么路由。
- B 循环内（9 个）：工具输出准入、主动遗忘、执行前风险、输出里有没有注入指令、漂移检测、工具失败分类、逐轮思考强度、通知路由、删掉的东西要不要留痕。
- C 蜂群（5 个）：选模型、回传闸门、蜂群健康、结果去重、自动侦察。
- D 收尾（4 个）：完成声明核验、经验写入、经验遗忘、用户反馈信号。
- E 会话级（6 个）：压缩方式、旁支隔离、缓存保温、代码定位、测试选择、提交检查。
- F：把 Jev 直接给主模型当工具。

**第二步：选题标准。** 文档 §5 有一张表，把「你提的八个点」逐条对到 A–F 上：是否 chat、是否调蜂群、是否融入经验、是否遗忘、子代理选模型、skill 披露、主动遗忘、context 该不该通知你。也就是说，**起点是作者自己用 harness 时反复遇到的八件烦心事**，分类表是把它们系统化之后补全的。入选标准写成了五条铁律：Jev 判断、代码执行、主模型思考；规则优先、Jev 管灰区；错了必须便宜可逆；入口准入优于事后遗忘；每个判断都入账。另有一条「Jev 不该做的事」：要写字的、要多步前瞻的、没有逃生门的开放集、超 32K 的状态、单独当安全边界的，都不给它。

**第三步：淘汰和增补。** 对照 git 历史（9 月 22 日之前是一个压缩提交，只能靠文档日期）：

| 候选                                                         | 命运                  | 原因                                                         |
| ------------------------------------------------------------ | --------------------- | ------------------------------------------------------------ |
| B7 逐轮调思考强度                                            | 明确不做              | 多数 provider 换 thinking 参数会丢 prompt cache，比省下的思考贵 |
| A2「先澄清」提示                                             | 删除                  | 真实会话里模型两次反问「Jev 是什么」而不去看工作区；新规矩「用户是最后的解法来源」 |
| goal.met 用 Jev 判目标达成                                   | 降为兜底              | 用户反馈判不准                                               |
| 工具输出准入的「相关吗」问法                                 | 换成分类问法          | 关系式问法把噪音也判成相关                                   |
| B6 瞬时失败自动重试、E2 旁支隔离、C4 子代理结果去重          | 搁置                  | 要改 pi 内核                                                 |
| F 给主模型的 judge 工具                                      | 没做                  | —                                                            |
| 第二波：task.frame、tool.constraint、tool.approval、turn.rewind、board.read、hive.relate、memory 四个新点 | 9 月 22–23 日一夜加入 | 来自产品需求文档和路线图                                     |

**第四步：作者自己给出的刹车。** PRD §12：「相比继续增加决策点，当前优先级应是：任务状态准确、原文可靠召回、完成证据可信、效果可量化。」

**什么时候问。** 全部挂在 pi 的事件钩子上，没有定时轮询：

- 用户每发一条消息：`input.preflight`（十道题一次问完，决定本轮档位）和 `task.frame`（这条消息是新任务、约束、纠正、子目标，还是什么都不改）并行问。
- 每 6 次工具调用：`turn.drift`（后台）。循环由规则判（同一调用同一结果三次），不问模型。
- 每次工具结果超过 6000 字符：`tool.admission` 分块问。
- 回合结束：`turn.completion`、`memory.applied`、`memory.outcome`。
- 蜂群里每只 bee 每轮结束：`hive.publish`、`hive.deliver`、`hive.relate`。

**怎么扩展。** 没有写成清单，但从代码能推出流程：写一个 `DecisionSpec`；在 manifest 登记（中英文标题与摘要；测试会检查每个 spec 都在 manifest 里、都属于某个 feature）；默认 shadow；用 `MockJudgeProvider` 写测试；在 `features/` 下写一份设计说明，末尾写「哪些没在真实 Jev 上跑过」。他们每份 feature 文档都老老实实写了这一节。

**我的评语。** 这套选题方法有三点值得学，也有一处明显的坑。

- 学：先从自己的痛点出发，再用生命周期分类补全，再用「代码能不能判、错了可不可逆、要不要写字」三把尺子筛。
- 学：题面措辞当成第一等工程问题。他们在 31 条标注消息上做消融，同一道题换个问法，准确率从 42% 到 74%；结论是「短、具体、单一谓词」，问「这是什么」而不是「相关吗」，问「够不够」而不是「相不相关」。
- 学：没有标注就先 shadow，shadow 期间不等待、不影响任何行为。
- 坑：**35 个点里只有 2 个有标注集**（preflight 37 例、测试日志 38 例），其余全部「阈值未校准」。0.6、0.7、0.8 这些数是拍的。回测也说明了：大多数决策点有动作、无闭环收益证据。决策点数量和价值证明之间差了一个数量级。

### 四、对 hctl2 Room 阶段的启发

先定位：mu 的 35 个点全是**一个 agent 一个回合内**的判断，对象是上下文、工具和子代理。我们 Room 阶段要判断的是**一群人和参与者的持续对话**该怎么组织：开不开新 Topic Room、建不建 Task、已有 Task 要不要收敛。对象不同，但判断的形状完全一样，而且我们已经留好了位置：

- 2026-09-19 原则二「chat room 会动态总结是不是要新开 topic room」，当时的落地建议是一个 Room 级缺省施工图「归纳」，只产建议卡（`.memo/design/intent-entry-principles-20260919.md` §二）。
- Grok 的 PR #290 已经把三件轻量活调研了一轮：A 持续建议、B @ 时的缺口、C 前情提要起草；结论是「缺省机械规则，模型只留形状」，卡在样本不够。
- 约束层已有 small-brain 三档：不配只挑不写；配了可按相关性选入并分节；能生成文字才改写。

**mu 给我们的，是这几件可以直接搬的机制：**

1. **判断与写字分开，而且用代码守住边界。** 我们的三档规则说的就是这件事，但 mu 多做了一步：writer 的输出被代码校验，约束必须是用户原话，格式不对整条拒收、保留上一版。我们前情提要的「原文片段必须与来源逐字一致、来源指针由组装器赋予」是同一思路，可以照 mu 的 `frame/writer.ts` 再加一条：改写句和它所依据的原文对不上就退回只挑不写。
2. **三区间加逃生选项，加 shadow 模式。** 这是 Grok 调研里没有的工程层。我们的「持续建议」如果上模型，应该先在 shadow 跑：判了、记了、屏幕上不出提示；拿账本对照人实际什么时候开了 Topic，再决定阈值。这正好解决 #290 卡住的「没有标注就不能开跑」：**shadow 模式让产品自己攒标注**，不用先靠人工标公开语料。
3. **task.frame 的问法。** 「这条消息对当前任务做了什么：新任务 / 加约束 / 纠正 / 推进子目标 / 什么都没改」。这就是 Room 里「要不要开新 Topic」的题面原型，而且它的 policy 有两个细节值得抄：把「约束」和「纠正」的概率合并后再过门槛，因为它们导向同一个动作；「确定变了但不确定变成什么」是一个独立结果，记成待答问题，绝不悄悄改写目标。
4. **memory.merge 和 hive.relate 的收敛问法。** 新条目对旧条目是「相同 / 更精确 / 矛盾 / 无关」；后来的发现对先前的是「替代 / 矛盾 / 支持 / 无关」。这是「已有 Task 要不要收敛」的现成题面。他们还有两条很好的不对称规则：矛盾时只有用户的话能让旧条目退役，模型或子代理的话不能；替代别人的条目要 0.9，修订自己的只要 0.6，因为替代别人的会把那条从板上拿下来并通知所有持有者。
5. **规则先行、模型管灰区、事件触发不轮询。** 他们的循环检测是规则（同一调用同一结果三次），只有漂移才问模型；Grok 的建议也是「机械预滤响了才问」。两边一致。

**具体到 Room 阶段，我建议的决策点候选（都是建议卡，不越过「临场执行边由人提交」）：**

| 候选                             | 触发                                                         | 题面形状                                                     | 动作                                                         | 缺省（不配 small-brain） |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------ |
| room.topic-shift                 | 新消息到达且机械预滤响了（转折词、长时间离开当前话题、连续多条不回应当前问题） | 选择题：接续当前话题 / 回答旁支问题 / 开始新话题 / 回到更早的话题 / 说不清 | 「开始新话题」过门槛才在输入框上方提示「可以开个 Topic」；人忽略后同一段三十分钟不再问 | 不提示，只有手动开题     |
| room.commitment                  | 同上，或 @ 到参与者                                          | 是非题：这段话是不是在约定「交出什么、凭什么算交出」         | 过门槛才贴一张 Task 候选卡，走采纳契约                       | 不贴                     |

**三处要提醒自己的边界：**

- Jev 把正文发到第三方，这在我们这里是安全策略面的一个策略点，缺省不允许（CONSTRAINTS 和 #290 都已写）。mu 全押托管 judge，我们不能。本地 judge（Laya 这一档）他们自己量过，只能做单文本分类，关系判断不行，而我们最想做的「这条消息和当前话题什么关系」恰好是关系判断。所以本地档可能要走 Grok 建议的小生成模型（千问 2.5 一类）答选择题，而不是 Laya 这类纯分类头。
- mu 的教训：决策点数量不是价值。他们 35 个点里有收益证据的只有两三个。我们应该从一两个点开始（topic-shift 和 brief-section），shadow 攒够标注再谈下一个。
- 不要重演 #290 的死局。那次卡在公开语料里没有换话题的样本。shadow 模式正是出路：产品一上线，人每次手动开 Topic 就是一个正例，判定记录和它对上就是标注。
