## 任务定义(所有者原话归纳)

1. **去除死文**:演化至今很多过时内容还留在现有文档里,该删的删、该归档的归档。
2. **收束集群**:放开细节回到大局,看内容结构与文件结构上有无可整合、可拆进目录的;有无跨域同构可以合并。
3. **删繁为简**:「正确的路只有一条,错误的 case 无穷无尽」——罗列「一定不要」要非常谨慎,只有特别容易犯和特别 tricky 的错值得落下来;能被机械覆盖、不倚赖 LLM 的,改成机械覆盖。
4. **严丝合缝**:全面大修,前后一致、整体性高。

## 可用 harness 与所有者观察到的特性

| harness | 强项 | 弱项(所有者经验) |
| --- | --- | --- |
| GPT-5.6-sol(xhigh) | 逻辑缜密、一致性强 | 容易抓细节没大局观,钻死胡同,在一两个细节上叠床架屋产生无效内容 |
| Fable-5(xhigh) | 愿景与协作、架构意识 | 细节老写不对;「Fable 写 → GPT 挑错 → Fable 改但没改对/改全」往复五六次,最后只好让 GPT 自己改 |
| Grok-4.6(xhigh)、K3(high)、GLM-5.3(max) | 可用 | — |

## 核心判断

往复五六次的根因不是能力差,是**交接方向错了**:挑错的人把问题扔回给细节弱的人改。解法是三条:

- 大局的归大局,细节的归细节——**不让同一个 harness 既定刀法又逐字执行**;
- 核验者**只报不改**,修改永远由执行者自己做;
- harness 之间**不传散文,传表**——大局判断变成可机械执行的逐文件动作清单,细节对错就不再依赖大局者。

## 分工

| 阶段 | 谁 | 做什么 | 出口 |
| --- | --- | --- | --- |
| 0 · 刀法 | Fable | 写大修方案 memo:全库清单逐文件标 删/归档/合并/拆分/保留;目标目录结构;跨域同构的合并映射;「一定不要」条款的存留判据;哪些禁令改成机械检查。**不写正文** | 所有者逐条拍板 |
| 1 · 执行 | GPT-5.6-sol | 按拍板后的方案逐批施工:删、移、合、改写。硬约束:只做方案列出的动作,**不新增概念、不新增禁止条款**;施工中发现方案未覆盖的问题,记进「待裁决」清单,不原地补 | 一批一个 PR,引用方案条目编号 |
| 2a · 机械核验 | 脚本(Buck2 test 目标) | 链接/锚点有效、版本戳一致、禁用词(如「张力」)、孤儿文件、指向已删章节的引用、术语表覆盖、每条合同变更配 CT 用例 | CI 红绿,不靠人眼 |
| 2b · 高度核验 | Fable | 只读整合后的全貌,回答三个问题:合并有没有吃掉真正的区分?删繁有没有删掉承重的规则?新读者能否只靠文档重建系统?**只出报告,不改文** | 发现回给 GPT 改 |
| 2c · 细节核验 | Grok-4.6(或 K3 二选一) | 冷读全库做对抗性挑错:矛盾、漂移、遗漏 | 同上,回给 GPT 改 |

GLM 不上:三个核验者已够,再多只增噪声。K3 可替代 Grok 做最后一次「新读者冷读」。

## 为什么这样切

- **四个关注点有顺序依赖**:先定结构(2),才知道什么是死文(1)——一段话在旧目录里是死的,在合并后可能正好是承重墙;再做删繁(3),因为每条「一定不要」的存留是语义裁决,要逐条过所有者;一致性(4)不是阶段而是横切的门,靠 2a 脚本兜底、2b/2c 人眼补漏。所以阶段 0 必须先把结构和判据定死,GPT 才有一张不会让它钻进去的地图。
- **针对 GPT 的死胡同**:病在一两个细节上叠床架屋,解药是「方案之外不动、发现问题只登记」——与 design/README.md 文档纪律「审计最多两轮,第二轮若主要发现第一轮新增概念的问题则回滚」同源,只是前置到施工阶段。
- **针对 Fable 的细节病**:阶段 0 的产物必须是表格化的逐文件动作清单而非散文,大局判断变成 GPT 能机械执行的指令;阶段 2b 只读、只报、不碰文件。
- **关注点 3 的存留判据(草案,待拍板)**:每条「不要」只有三种活法——(a) 承重不变量(如三条底线),留在合同;(b) 决策史里实际犯过或差点犯的错,留一句加指针;(c) 能机械检查的,转成 CT 用例或 lint 后删掉散文。三者皆非,删。执行者手里有过滤器,只有边界案例上升到所有者。

## 交接载体

Agent 之间只传两张表:

- **方案表**:文件 | 动作(删/归档/合并/拆分/改写/保留) | 理由 | 需拍板?
- **待裁决清单**:问题 | 发现者 | 建议

每批 PR 的「定位与重述」节直接引方案表编号;所有者审 PR 看编号对不对,不必读全 diff。

## 与既有纪律的关系

沿用 AGENTS.md 与 design/README.md 文档纪律:memo 先行、拍板才落盘、一轮一个 PR、真语义变更单独立项标注、四视角核验(覆盖度/合同漂移/语言/结构一致性)。本方法论只补一件事:**把核验与修改的方向固定为单向**——核验者报告,执行者修改,大局者不执行。

### 「一定不要」清单的处理

设计正文四张角色表的"不能做什么"列、关键规则里的否定句、delivery CT 矩阵——三层表达同一批禁令。按前文判据:CT 是机械覆盖,所以设计正文只留"能做什么",禁令归 CT;承重不变量(三条底线、Task 只有两个终结来源、普通 Room 临场边只由人创建、Room 不签发 Verdict/Receipt)留合同一处。system.md 安全边界与 connections.md 失败表是承重的,保留。delivery「明确不做」保留但可缩。每条的最终去留逐条过所有者,执行者只按判据初分。

### 机械核验脚本(阶段 2a 要建的,按 CONSTRAINTS 走 Buck2 test 目标;先在 docs/research/ 落 lint 工具选型再写)

1. Markdown 链接与锚点:相对路径存在;`#anchor` 在目标文件可解析(含中文标题的 GitHub anchor 规则)。
2. 版本戳一致:所有「草案 vX.Y.Z」头部与根 README 基线相符,或在允许滞后的白名单里。
3. 禁用词与词形:「张力」、执行身份不可证场景的「中断」、驼峰对象名残留、`*Intent` 命令名。
4. 孤儿文件:`docs/` 下未被任何索引(design/README、research/README、子目录 README)引用的文件。
5. 概念单点定义(弱检查,只报告不阻断):核心产品词与合同词的定义句只在 owner 文件出现。
6. 合同变更配 CT:decision-history 新增带「(vX.Y.Z)」的章节时,同一 PR 的 delivery CT 矩阵必须有新增行。
7. `.memo/review/` 子目录名与文件头基线一致。

### 批次顺序与版本

批 1 结构(目录移动与拆分,纯搬家不改语义,链接脚本护航)→ 批 2 死文(删/归档)→ 批 3 三组同构合并 → 批 4 删繁(禁令按判据处理,配 CT)→ 批 5 门户收束(README/vision)。每批一个 PR,机械核验绿了才进人眼核验(2b/2c)。基线冻结在 v0.15.0,大修完成一次性升 v0.16.0(结构变动算 minor)——需拍板。规模估计:阶段 0 方案约一天(Fable);五批各半天到一天(GPT);每批核验半天。
