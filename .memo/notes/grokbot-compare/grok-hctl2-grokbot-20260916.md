## 0. 这篇备忘是什么

所有者把与 ChatGPT 的 Grok Bot × HCTL2 对照全文录在 `.memo/notes/hctl2_grokbot_compare.md`，并提炼三条：

1. Grok Bot 的核心是「数字伙伴」，HCTL2 的核心是「项目与承诺」。
2. agents 之间靠聊天「协作」不产生额外价值；价值来自多样性与外部机械制度。
3. HCTL2 通过扩展 TAMP（仓库里是 Task–Actor Matching Protocol，不是机器人 Task and Motion Planning）来管理「数字伙伴」。

本文是读完**整份对话**之后给主笔的消化建议。对话后半段已经把三条收成一条链：长期主体是项目与承诺；没有新信息的协调不应进模型循环；伙伴感靠履约记录上的推荐，不靠把组织中心换成 Bot 名册。

**不要推翻五个模块、选入作用域、Gate 不设商量回合、完成与合入分开、Agency 不拥有验收权。** 那些正是对照里 HCTL2 强的部分，也是「省」的载体。

## 2. 建议主笔改的设计正文（只动愿景，且是文案）

下面三处给 `docs/design/vision.md`。意图是把对照后半段已经收口的话写进用户能读到的层。**不改五个对象、不改选入、不改 Gate 计票。**

### 2.1 「不解决什么」加一条非目标

现文（「要解决什么，不解决什么」）写了不重做 LLM / Harness、不让每项工作都必须聊天或先画施工图，但没点名组织中心。

建议在「HCTL2 不解决」那句里加：

> 不把跨项目的数字伙伴关系当作组织中心。熟悉的工种、方法和选人偏好可以预填、复用；每次任用的材料、权限、预算和评审资格仍以本次 Project / Task / Run 为准。Jack 记得什么、Jack 觉得完成了没有，不能当项目事实的最终来源。

依据：对照「伙伴作为长期主体 / 项目与承诺作为长期主体」表；后半段「这首先是定位选择，不能直接视为缺陷」。

### 2.2 原则 2「省」补一把可检查的尺子

现文已有「多个参与者本身不是目标，误差不相关的证据才是」，并指向多 agent 调研。缺的是对照里那句：

> 让模型输出 JSON，并不等于把协调机械化了。如果「下一步给谁」「是否完成」仍由模型重新推理，成本还在。真正移出推理循环，是代码依据已记录事实和规则作出这些决定。

建议在原则 2「省」段落后加：

> **没有新信息的协调不准进模型循环。** 谁已获权、下一步前置是否满足、什么算完成、旧评审还是否有效、何时找人——这些由控制面按已记录事实检查。新增一轮模型调用，要能指出它带来了什么新信息、证据或必要判断；只搬运状态、复述规则、维持对话的，交给代码或删掉。衡量仍按同等验收下每份合格交付的轮次与 token，失败、返工、读回、评审和协调全部计入。

依据：对照「省」段、CI 等待应用代码订阅而不唤醒 LLM 的例子、愿景已有的成本度量方向。

### 2.3 原则 4「协作拓扑与控制拓扑正交」加半句

现文：Room 回答在哪里交流；Workflow/Run 回答谁有权自动推进。

建议补：

> Room 是人塑形的地方，不是席位之间靠对话形成裁决的地方。席位之间不设商量回合；参与者之间的日常协调（轮到谁、是否还在等、要不要再催）优先走事件和规则，不走互读散文。

依据：对照把五个模块重述为「系统承载的协作制度」那张表；`spec/run.md` 已有「不设商量回合」，愿景层缺对应的人话。

## 3. 不要当文案落、需要所有者另拍的（主笔不要自行写进规范）

对照前半段 ChatGPT 曾主张向 Grok 学「持续推进」，后半段收成「跟进用状态机，模型按需唤醒」。下面几条会动默认责任，不是润色。

| 题 | 对照里的主张 | 和现文的冲突 | 建议 |
| --- | --- | --- | --- |
| Room 获准范围内自动路由 | 边界、资料、预算内的下一步调用，control 检查后执行，越界再找人 | 普通 Room 每条执行边须人的 Trigger Preview | **拍板题**。可先做「自动备好下一次 Preview」（不改授权），再议有范围协作授权 |
| 无 Run / 轻量路径的有限跟进 | 首次授权包含「在这个任务和这条 PR 上处理评审意见与检查失败，总预算与截止固定」；每轮仍是新调用，不复活旧执行 | 无 Run 路径明确没有自动返工，PR 评论要人再开 Invocation | **拍板题**。这是「省」能否从原则变成默认产品责任的关键，比动态 DAG 更急 |
| 看板由执行侧维护 | Agent 更新进度、关联证据、准备验收；人做交付决策。默认视图按「不用我 / 要我决定 / 可验收 / 停住了」 | 规范完整在判定侧，推动责任没有默认主体 | 产品实现可先做；不要让维护者的自述变成完成凭证 |
| 用户一次决策、后台多事务 | 「合进去并完成这件事」一次预览，合入与验收仍分事务，部分成功如实停 | 用户决策边界被模块边界切开 | 交付 / Workbench，不改对象模型 |
| 长期角色前台 | 工种名片、方法、选人偏好可复用；「继续交给 Jack」解析为一次新任用 | 现文已禁止跨 Room/Run 自动同一条选入 | 展示层聚合即可；选入记录作用域不动 |
| 可选桌面观察 | 按 Dispatch 绑定的 GUI 通道；headless 仍完整；不学账号级共享电脑和凭据 | 有观测抽象，无完整云桌面协议 | Agency 能力声明 + 交付；不改 Participant 身份 |
| Project 引用 0..N Repo | 问题可以先于仓库成立 | Project 属于一个 Repo | **真规范变更**，不要和「省」绑成一包 |
| TAMP 推荐层 | 召回 / 可行性门 / 排序 / 任用；需求从现有契约生成；常规任务用静态规则，避免测量税 | 选人仍是人从名册里选、控制面准入 | 留 `.memo/notes/TAMP-design-doc.md`；设计正文最多承认「选人将来可有推荐，任用仍走现有命令」。不要把第 11–12 章合同网 / 开放市场焊进 spec |

主笔若写演进段落，请把上表标成「对照提出、尚未拍板」，不要写进「当前规范」。

## 4. 给主笔的消化顺序（若吸收）

1. **先改愿景 §不解决什么、原则 2、原则 4**（本文 §2）。这是对照已经收口、与现文不冲突的部分。
2. **不要在同一 PR 里改 Room 执行边或无 Run 返工。** 那是另一份方案，要单独走 05 的方案形状。
3. **TAMP、桌面、跨 Repo Project 仍后手。** 规范已经够用；对照最后一段说的是实现不足，不是设计厚度不够。

对照原话（供主笔写原则时对齐语气，不必整段粘贴）：

> 持续跟进不必意味着增加一个持续监工的 Bot；它可以主要由持久状态、事件和确定性规则完成，只在需要判断时调用模型。
>
> 长期存在的应该首先是责任记录和执行状态；模型可以按需被唤醒。
>
> 推荐回答「谁更适合履行这份承诺」，HCTL core 继续决定承诺是什么、授予哪些权力、依据什么验收。

## 5. 比改设计更急的

对照结尾：「批判的武器不能替代武器的批判。」下一批最有用的材料不是更长的规范，而是一条自己的变更：从契约到返工到合入，中间没有人在终端里补操作，并能报出总 token 与人工介入。没有这条账，「比 Grok Bot 更省」仍是纸面。

建议验收（给实现，不进约束）：同样一项工作，HCTL2 用更少的无效推理完成、验收没有放松、故障后没有把协调劳动交还给人。
