本次采用截至 **2026 年 9 月 15 日**的 Grok Bot 官方资料，以及 hctl2 固定提交 `e0cc1ee`、设计基线 **v0.18.2**。一个重要前提是：**hctl2 仍处于早期实现，control、公共 CLI 和完整 Workbench 尚未交付**。因此，下文比较的是 Grok 的公开产品能力与 hctl2 的规范方法论，不能把后者的设计完整度直接当作已实现的可靠性。[hctl2 当前实现说明](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/src/README.md)

四个单元的关系可以先这样看：

| 单元 | Grok Bot | hctl2 规范 | 方法论差异 |
|---|---|---|---|
| **Room** | 私聊、群聊、项目 channel；Bots 可以交流、交接和唤醒彼此 | Room 保存目标塑形与讨论；执行通过明确的预览和命令授权 | Grok 让对话推动协作；hctl2 明确区分讨论与执行授权 |
| **Kanban** | 官方多团队实践采用 Notion Projects/Tasks，由 PM Bot 和专家维护 | Task 保存承诺，Task Revision 冻结验收契约；看板内容由任务后端承载 | Grok 展示工作组织方式；hctl2 定义状态如何成为可验证的完成事实 |
| **Run** | 对话 turn、后台工作、routine execution，以及近期运行记录 | Run 是冻结施工图、契约、基线、席位、权限、预算的一次整体授权 | Grok 有执行与历史；hctl2 进一步定义执行的治理含义 |
| **Agency / Participant** | 长期 Bot 有名字、职责、记忆；平台提供运行能力 | Participant 是某个 Room 或 Run 席位里的选入记录；Agency 是供给方 | Grok 强调角色连续性；hctl2 分开角色、方法、权限和物理运行 |

这里还有一处术语校准：hctl2 正式模型有 **Project、Task、Run、Participant、Repo 五个领域模块**；Room、Kanban、Workflow、Terminal、Change 是对应场景，Agency 则是参与者供给方。你列的四单元很适合比较，但最后的成果封存、代码合入和集成凭证，还需要补上 Repo/Change 才能闭环。[hctl2 架构](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/architecture.md)

**Room 最深的差异，是消息是否可以产生下一次执行。** Grok Bot 明确支持一个 Bot 向另一个 Bot 发送异步消息，唤醒对方并继续交接；用户也可以发新消息调整正在进行的工作。hctl2 普通 Room 中，模型消息和正文里的 `@` 只能提出建议，必须经过人的 Trigger Preview 和结构化提交，才能产生下一条执行边。自动协作可以进入已批准的 Run，在冻结边界内推进。[Grok 协作文档](https://docs.x.ai/grok-bot/chat-and-collaboration)、[hctl2 Room 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/project.md)

这意味着，给 hctl2 增加“交接建议卡、自动带上上下文、一键确认下一位协作者”，可以沿用现有规则；让模型在普通 Room 中自行唤醒任意参与者，则涉及授权制度的修改。

**Kanban 上，必须区分官方实践与内建协议。** Grok 官方的多团队文章确实展示了“每项目一个 channel、一组 Bots、一块 Notion 看板”：Projects Manager Bot 配置项目和编制，PM 维护数据库，专家认领任务，卡住时标为 Blocked 并通知人。但作者明确称其为实验性模式。因此准确结论是：**Grok 已展示基于外部工具的多 Bot 看板协作；尚不能据此认定它有与 hctl2 等价的任务治理模型。** [Grok 多团队实践](https://x.ai/bot/guides/how-i-run-multiple-teams-of-grok-bots)

hctl2 的重点在于区分：

- **阶段**：Backlog、Ready、In Progress、Review。
- **健康状态**：Blocked、需要关注。
- **Task 生命周期**：开放、完成、已取消。
- **完成凭证**：针对精确契约和逐项证据，经过独立验收后形成。

所以外部卡片 Done、CI 通过、模型说完成，都不能直接替代 Task 验收。甚至 **Run 正常完成后，Task 仍可能因契约分歧或证据不足而保持开放**。这是 hctl2 很有辨识度的设计。[hctl2 Task 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/task.md)

**Run 上，不能说 Grok“没有 run”。** 它的 Routine 支持时间或事件触发，有近期成功/失败历史，也能暂停、编辑和测试。不过，Routine 主要回答“某个 Bot 何时再做这件事”；hctl2 Run 则代表一次完整授权，并进一步区分 Obligation、Seat、Attempt、评审裁决和正式凭证。公开资料未提供 Grok 与这套模型等价的通用 Run 契约，这应表述为“未找到公共定义”，而非断言内部不存在相关机制。[Grok Skills 与 Routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)、[hctl2 Run 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/run.md)

同时，hctl2 并不要求所有工作都先画施工图：不需要内部 Gate、持久重试或候选切换等能力时，可以走有限 Room Invocation 和独立验收的轻量路径。[hctl2 无 Run 路径](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/task.md)

**Participant 上，双方对“同一个人”的定义差异很大。** Grok 的具名 Bot 可以跨任务、跨项目持续存在，记忆和职责围绕这个角色积累。hctl2 的 Participant 则只存在于被选入的 Room 或 Run 席位中；Room 的 planner 与 Run 的 worker 独立选取，同一工种、同样叫 Jack，也可能是两条不同记录。[Grok Bot 生命周期](https://docs.x.ai/grok-bot/bots)、[hctl2 Participant 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/participant.md)

Agency 再把物理执行隔开：control 面向一次 **Dispatch（派工）**，Agency 负责门后的进程、主机和会话。同一规格内更换执行体，可以不改变派工身份；供给方却不能自行扩大权限或宣布任务验收完成。因此，Grok Bot 与 hctl2 Participant 很难一对一映射，实际要拆成可复用角色配置、多个作用域内的选入记录，以及运行资源。

你举的**“看 participant 运行环境/PC 桌面”**，确实是非常有价值的比较切口，但核查后需要精确到下面这一层：

| 维度 | Grok Bot | hctl2 |
|---|---|---|
| 底层电脑 | 同账号 Bots **共享持久云电脑** | 主机与进程归 Agency 内部，control 不建立完整机器拓扑 |
| 每个执行者的屏幕 | 每 Bot 有独立工作屏幕 | 未定义等价的完整 Bot PC/GUI 工作屏幕协议 |
| 观察方式 | 可查看点击、输入、导航和工作状态 | 默认结构化执行流；PTY 转录用于进一步诊断 |
| 接管方式 | 可以接管桌面完成验证，再交还 Bot | 已定义执行连接、票据和输入控制；图形桌面通道仍需扩展 |
| 观察对象归属 | 从 Bot 对话进入其工作屏幕 | 连接绑定**某次精确执行/派工** |
| 隔离含义 | 独立屏幕不隔离共享文件和登录状态 | 是否具备具体隔离能力，须看 Agency 声明与实际兑现 |

Grok 的电脑文档明确说，同账号 Bots 共享文件、浏览器会话和命令行凭据，各自 screen 只是工作表面。因此不能将“每 Bot 有屏幕”理解成“每 Bot 独占 VM 和凭据”。此外，人查看 Bot 云桌面，与 Bot 访问人的本地 PC，是两个方向的能力。[Grok 电脑与应用文档](https://docs.x.ai/grok-bot/computer-and-apps)

对 hctl2，也应把你的原判断稍作修正：**它有运行现场观测、屏幕信号和接管的抽象；缺少的是 Grok 那样明确产品化的 GUI 桌面能力。默认姿态是 headless＋结构化执行流，PTY 和终端接管逐级升级。** Workbench 将来有图形界面，也不等于它已经定义了如何观看 participant 的操作系统桌面。[hctl2 Participant 与 Terminal](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/participant.md)

据此，我对 hctl2 的建议有三个优先方向，均属于本次调研的设计推论：

1. **先完善“谁在做、卡在哪里、下一步需要什么”的界面。** 把当前行动、Request、证据和下一步命令放到卡片上，减少为了解进度而打开终端的需要。
2. **沿 Agency 增加按 Dispatch 绑定的可选桌面观察与接管能力。** 可以从 Participant 卡进入，但连接必须落到精确派工，保留票据、输入权、失效和恢复语义；没有桌面的 Agency 仍应完整支持 headless 工作。
3. **提供长期角色的连续体验，同时保留独立选入记录。** 可复用工种名片、方法和选人偏好；本次权限、预算、上下文和评审资格仍明确确定。

需要单独做规范决定的，则是普通 Room 中的自主唤醒、运行中新增治理节点、跨阶段继承 Participant 身份和权限。这些会改变 hctl2 已经选择的控制方式。**桌面可见性可以沿现有边界扩展；模型的行动权是否扩大，应作为另一项明确设计决定。**

# Grok Bot 与 HCTL2 的协作方法论比较

**核心判断。** 两者都试图让多个数字参与者持续完成工作，但组织工作、分配执行权和认定完成的方式不同。Grok Bot 把长期存在的 Bot 放在产品中心，通过对话、共享电脑、技能和自动触发形成委派关系；HCTL2 把目标、承诺、授权执行和验收证据分别建模，使协作结果可以按精确版本核验。前者的重点是减少人每天协调工作的负担，后者的重点是让授权和完成不随聊天、运行进程或外部平台状态漂移。这是对双方资料的分析归纳，不是性能或可靠性排名。[^1][^13]

比较 room、kanban、run、agency/participant 时，不能把名称相近的东西直接视为同一对象。Grok Bot 的官方产品原语包括 Bots、Chats、Prompts、Tools、Artifacts；HCTL2 的五个领域模块是 Project、Task、Run、Participant、Repo，Room、Kanban、Workflow、Terminal、Change 是对应场景，Agency 则是供给方。下面沿用四个问题域来比较，同时保留这些层次差异。[^1][^13]

**证据范围。** 调研截止 2026 年 9 月 15 日。Grok Bot 采用 x.ai 的官方设计文章、产品指南与 docs.x.ai 专门文档；设计文章日期为 9 月 3 日，Overview 更新于 9 月 11 日。HCTL2 固定为 main 的提交 `e0cc1eedaf12fd80c9cffff7a2926e062757ef72`，设计基线为草案 v0.18.2。下文称“产品事实”时指官方文档明确记载的能力，未做登录后的端到端实测；称“HCTL2 规范”时指设计要求，不能自动算作已交付功能。[^2][^13]

HCTL2 README 明确写明仍处于早期实现，尚无可用的公共 CLI 或完整应用。源码工作区已有 hctl2-tool、事实读取与基础库、依赖打包；control、公共 CLI、Workbench 尚待进入后续实现。把它与 Grok Bot 比较时，能够比较的是架构承诺与产品方法，不能把规范完整度当作运行可靠性的证据。[^13][^24]

**1. 四个问题域的对应关系**

| 问题域 | Grok Bot 的对应物 | HCTL2 的规范对象 | 最关键的差异 |
| --- | --- | --- | --- |
| room：在哪里形成共同目标？ | Bot 私聊、group chat、项目 channel | Project 模块下的 Repo Room、Project Room、Scoped Room | Grok 对话能直接协调并唤醒 Bot；普通 HCTL Room 的模型发言只形成建议，执行须走人的结构化授权 |
| kanban：如何追踪承诺与进度？ | 官方实践中的 Notion Projects/Tasks 数据库，由 PM Bot 与专家协同维护 | Task、Task Revision、完成凭证；Kanban 是场景，卡片内容由任务后端承载 | Grok 展示一种工作组织方式；HCTL 规范化了卡片状态与验收完成之间的边界 |
| run：一次执行到底是什么？ | 对话 turn、后台工作、routine execution 与近期 run records | Run/Manifest、Workflow Revision、Obligation、Seat、Attempt、Verdict/Receipt | Grok 有执行记录；HCTL Run 额外代表一整份冻结授权及其完成判据 |
| participant：谁持续承担工作？ | 有名字、职责、记忆的长期 Bot | 被选入某个 Room 或某个 Run 席位的工种实例 | Grok 强调跨任务的角色连续性；HCTL 选入记录受作用域约束，规划者与施工者独立选取 |
| agency：谁供给运行能力？ | 产品托管层，功能上提供电脑、工具与运行能力 | 维护 Profession 名册、接受 Dispatch、转接执行和观测的 Agency | Grok 未公开等价的可替换 Agency 协议；HCTL 明确区分供给责任与治理权威 |

**2. 方法论：把什么作为长期稳定的中心？**

Grok Bot 的设计文章把侧栏从聊天历史转向 Bot 名册：人回到产品，是继续找同一位有名字、有职责的 Bot。群聊处理共同项目，协调 Bot 帮忙分派工作。这个设计降低了“我该打开哪个任务、重新解释哪些背景、下一步找谁”的日常成本。它采用的是长期角色持续承担工作的方式。[^1]

HCTL2 的长期稳定中心更接近 Project 的目标、Task 的承诺、已授权的 Run 和精确成果。规划与执行可以更换工具和物理现场，上层事实仍保留；运行端提交结果提案，由拥有该事实的模块校验后才生效。这使系统可以回答“谁按哪份授权，对哪个版本做了什么，凭什么验收”。[^14][^18][^23]

二者也有很强的共同点：都不把 agent 等同于一次随用随丢的模型调用，都重视专业分工、可复用方法、长期材料和人类介入。Grok Bot 101 的编码案例已经明确分出外层 Bot 与内层 Cloud Agent：外层收集上下文、准备任务，内层编码执行。它与 HCTL2 的规划/施工分离有相似动机；差异在于 HCTL 把这条交接写成冻结对象、权限和证据规则，Grok 案例主要呈现为组织实践。[^10][^20][^27]

因此，最值得研究的轴不是“自主/不自主”，而是：**什么可以在运行中自由改变，什么必须先变成已授权事实。** Grok 允许用户发新消息调整当前工作，Bots 也能互相唤醒；HCTL 普通 Room 保留人的临场决定，进入 Run 后才按冻结边界自动推进。两者都允许自主工作，但放置授权边界的位置不同。[^3][^15][^19]

**3. Room：共享讨论，还是执行的入口？**

**Grok Bot。** 用户可以和一个 Bot 私聊，也可以把多个 Bots 放入群聊。普通群消息允许参与 Bots 判断谁回应，明确点名可指定承担者。Bot-to-Bot 消息是异步交接，接收方可以被唤醒后处理任务。群聊因此同时承担共同上下文、工作分配和交接可见性的作用。[^3]

在官方多团队案例中，一个项目对应一个 channel，PM 和专家 Bots 都在其中讨论、认领、汇报。一个既有 Bot 可以被复用到新项目，角色不会因为换了 channel 就自然重建。需要注意，这个“每项目一群”的组织方式是作者配置的实践，不是已公开的统一 Project/Room 领域契约。[^4]

**HCTL2。** Room 归 Project 模块，负责保留目标如何形成、依据是什么、哪些事项已决定、哪些还未定形。Repo Room 是仓库级探索入口；Project Room 伴随具体项目；Scoped Room 冻结临时讨论的目标与回填动作，回填成功后归档，也可由有权人记录放弃、无决定或被取代而结案。聊天消息由 Matrix chat server 承载，治理记录由控制面保存。[^14][^15]

它的授权差异尤其重要：聊天中的 `@` 本身不会派工。普通 Room 里，人的动作先经过 Trigger Preview，明确参与者、上下文、权限与预算，再通过类型化命令提交。模型提出下一位协作者，只生成建议；即使消息正文含有 `@`，也不能由此自行扩展协作链。固定、重复的自动协作进入 Workflow/Run。[^15]

Room 还区分规划与施工。Room 的 `@` 只解析本 Room 的规划者；与正在执行的施工者互动，应进入绑定该次执行的 Execution Chat。后者没有独立 Room 身份，其输入和事件也不自动进入 Room，要通过显式 Share to Room 才回流。这避免同名规划者与当前执行者被界面混为一人。[^20][^21]

| 场景 | Grok Bot | HCTL2 规范下的处理 |
| --- | --- | --- |
| “请 Researcher 找资料，再交 Writer” | 可以通过 Bot 消息交接继续工作 | Room 模型提出下一次调用建议；人确认新预览，或使用已批准的 Workflow |
| 用户中途说“先处理另一件事” | 直接消息能优先于后台工作并调整当前 turn | 补充输入按既定范围处理；若改变冻结范围、验收或权限，须进入相应变更/替代路径 |
| 想问正在运行的 worker 卡在哪里 | 在 Bot 对话或电脑视图中追踪 | 从对应执行进入 Execution Chat，不能仅按同名 Room 规划者路由 |
| 临时拉人解决阻塞 | 群聊或异步 Bot 交接 | 可通过 Request 升级为 Scoped Room；解决结论回填原阻塞范围，或由有权人显式结案 |

这些差异不是“哪个聊天界面更丰富”，而是消息能否直接产生新的执行权。若 HCTL2 希望获得 Grok 式无缝交接，可先自动准备下一次 Trigger Preview，减少重复输入；若希望模型在普通 Room 中直接唤醒下一位参与者，则需要修改现有授权规则，不能当作一个 UI 快捷操作。[^15][^22]

**4. Kanban：任务协作实践与验收契约**

**Grok Bot 的官方案例是什么。** Eric Zakariasson 建立 Notion Projects 和 Tasks 两个数据库，再用 Projects Manager Bot 与 Project Ops skill 创建项目、群聊和成员编制。项目 PM 维护数据库，专家认领工作；遇到阻塞时把卡片标为 Blocked 并在群里请求帮助。作者明确标记这是仍在尝试的实验性模式。[^4]

它说明 Grok Bot 可以参与既有人类项目管理工具，遵循职责和流程，形成可见的任务看板。但这份案例没有公开 Task Revision、验收凭证、外部状态冲突处理或领取任务的并发协议。可以说“已展示基于 Notion 的多 Bot 看板协作”，不能据此说“Grok Bot 内建了与 HCTL2 等价的 Kanban 治理内核”。

**HCTL2 的 Task 比卡片多了一层。** Task 表达长期承诺，Task Revision 冻结验收契约；卡片、评论、排序和日常流转保留在所选任务后端。当前规范是一个 Repo 一个 Board，Project 是板上的分组，Task 是卡片。卡片可以先没有契约，但首次启动 Run 或请求治理意义上的完成之前，必须显式采纳契约。[^16][^17]

HCTL2 严格区分三类状态：Task 生命周期只有开放、完成、已取消；Backlog、Ready、In Progress、Review 是阶段；Blocked 和需要关注是额外健康标注。外部后端显示 Done 是来源事实，不会直接写成 HCTL 完成。可确认是有权人实施的 Done 动作，才可能经适配器生成完成请求，仍须走独立验收。[^17]

| 容易混淆的信号 | 在 HCTL2 中能证明什么 | 还不能证明什么 |
| --- | --- | --- |
| 卡片移到 Done | 任务后端发生了状态变化 | 验收契约已经满足 |
| Bot/模型说“完成了” | 存在完成自述；只有经规定提案通道提交并冻结后，才构成 Result Proposal | 已产生正式完成凭证 |
| CI 通过 | 某个精确代码版本通过相应检查 | 人工验收项、评审项或整个 Task 自动通过 |
| Run 正常完成 | 本次冻结施工的完成条件成立 | 当前 Task 契约一定仍匹配、Task 独立验收一定通过 |
| Task Completion Receipt | 指定生命周期、契约和逐项证据完成了准入 | 外部卡片写回一定已经确认 |

表中依据为 Task 与 Run 的规范。它的产品含义是，系统有时应同时展示“外部已关闭、HCTL 未验证”，或“已完成、外部同步中”，而不是把来源状态合并为一个看似确定的标签。[^17][^19]

这里两者可以相互借鉴。Grok 的 PM Bot 让更新卡片变得自然；HCTL 的 Task 契约让“卡片已更新”与“交付已被证明”分开。对 HCTL 最合理的借鉴，是让模型帮助形成任务、组织评论、解释阻塞和准备完成材料，同时保留独立完成校验。对 Grok 的使用者，则应把外部看板视为协作事实库，对关键交付另行定义验收者和证据。

**5. Run：不要把 Routine、一次尝试和治理执行混为一谈**

**Grok Bot 确实有 runs。** 官方文档定义 Skill 为可复用的方法，Routine 为某个 Bot 按时间或事件执行工作的安排；Routines 界面可查看近期成功/失败记录，也能暂停、编辑、测试和删除。当前文档记载每 Bot 最多 50 个 routines，每 routine 保留最近 20 次 run records。测试运行会做真实动作。这些是产品已有的运行管理能力。[^5]

但 Routine 不是 HCTL Workflow Revision 的严格对应物。前者回答“这位 Bot 何时再做这件事”，后者需要固定控制图、节点输出、席位要求与治理规则。Grok 的一次 turn、一次 routine run、一次 Cloud Agent 工作都可能在宽泛意义上叫“执行”，而 HCTL 对这些层级分别建模。[^5][^10][^19]

**HCTL2 的 Run 是一份整体授权。** 启动时 Manifest 冻结施工图、至多一个 Task Revision、代码基线、上下文引用、席位、候选配置、权限与预算等。Workflow 引擎负责机械推进，control 负责语义准入；Dagu 报告节点状态，并不直接决定 HCTL 的完成状态。[^18][^19]

| HCTL2 名词 | 需要它的原因 | 与 Grok 公开概念的关系 |
| --- | --- | --- |
| Workflow Revision | 固定要做的图和判据 | 可与 Skill/流程说明比较，但不是同一规范对象 |
| Run + Manifest | 固定本次整体授权 | 比一次 routine run 的公开描述包含更多治理含义 |
| Obligation | 固定某一步必须交付的逻辑结果 | 未找到公开的一一对应对象 |
| Seat | 固定执行或投票位置，避免换候选增加票数 | 不能直接等同群聊中的一个 Bot |
| Attempt | 表达某候选对一个席位的一次执行 | 可类比一次工作尝试；具体身份规则不同 |
| Gate / Verdict / Receipt | 区分评审规则、意见与校验后的证明 | Grok 可安排 reviewer Bot，但未公开同等计票/凭证协议 |

HCTL Run 有启动中、运行中、暂停中、已暂停、取消中以及完成、失败、已取消、被替代等状态；完成前必须证明必需义务与输出成立、尝试已终态或撤权、无影响输出的未决副作用、引用仍匹配。终态不复活。它还区分传输重投、候选切换、引擎重试、语义返工和替代 Run，避免“重试”成为绕过身份与权限变化的通用按钮。[^19]

相比之下，Grok 公开说明了 steering、停止、routine 暂停与成功/失败历史，但本次未找到通用 Run 的公开事务规范、冻结授权结构、租约或证据归约协议。这是**公开证据范围的差异**，不等于断言其内部没有调度、重试、权限或持久化。[^3][^5]

另一个容易被忽略的共同点是：简单任务都可以直接做。HCTL 明确设计无 Run 的轻量路径，有限 Room Invocation 或人工工作产生精确成果，再由有权人预览并完成独立验收；只有需要持久重试、候选切换或内部 Gate 等能力时才进入 Run。不能把 HCTL 描述成“任何事情都要先画 DAG”。[^16]

**6. Participant 与 Agency：名字、身份、供应方、机器是四件事**

Grok Bot 的 Bot 是长期角色：名字、title、description、avatar 和长期学习上下文共同构成可反复返回的对象。复制 Bot 会复制配置、技能和 routines 等，但不复制对话历史和学习记忆；隐藏不会暂停 routines，删除 Bot 也不代表清除共享电脑文件。这些生命周期行为表明 Bot 身份与底层持久资源并非一一对应。[^6]

HCTL2 的 Participant 则是被选入特定 Room 或 Run 席位的工种实例。Room 的规划者与 Run 的施工者独立选人；同一工种、同样名字，在两个作用域中仍是两条记录。项目保存选人策略，不保存一份自动贯穿所有阶段的成员身份。人属于 human actor，不进入数字 Participant 的分层。[^20][^21]

HCTL2 把参与者相关信息分成七层：Profession、Participant、persona、模型及训练、Skill、执行者配置、一次派工。拆分的价值在于，不让“叫 Jack”“采用某模型”“安装某技能”“使用某个终端”互相替代。角色标签不能自动授予权限，Skill 版本也不能自动取得评审票权。[^20]

Agency 在此是派出方，维护工种名册和条款，接受冻结执行规格，转接输入、停止、观测与结果。控制面持有 Dispatch，不需要建立门后的主机、进程与会话拓扑；Agency 在规格内重启、换机或接替执行体，仍可维持同一派工。Agency 负责履约与资源，但不拥有验收、票权和执行范围的裁决权。[^21][^22]

| 身份问题 | Grok Bot | HCTL2 |
| --- | --- | --- |
| “这位同事是谁？” | 长期 Bot profile 与记忆 | 特定作用域内选入的 Participant |
| “他为什么会这样工作？” | 描述、学习上下文、Skill 与产品运行机制 | persona、模型、版本化 Skill、Worker Profile 分开记录 |
| “实际谁提供运行能力？” | 平台托管能力 | Agency；可有本地与外部供给方的架构空间 |
| “谁有权访问业务系统？” | 通常代表已登录成员；团队 connector 可例外采用服务凭据 | 本次授权的窄能力与受控端口；模型不持通用治理凭据 |
| “换进程是否换人？” | Bot 可在持久电脑上跨会话继续 | 不应由进程变化改变 Participant/Dispatch 的逻辑归属 |
| “同名是否同一主体？” | 名称不是访问主体本身 | 尤其不能跨 Room/Run 用名称代替选入记录 |

访问主体与人格必须再分开看。Grok 安全文档说明，Bot 没有独立的认证身份或凭证，通常以其所属成员的访问身份行动；多建一个 Bot 并不形成新的安全边界。HCTL 的逻辑 Participant、Agency 租户、本次执行权限，也不能仅靠名字或专业标签证明隔离，仍依赖实际的能力执行与证据。[^9][^21]

HCTL 也不应被概括为“每个 Participant 天生拥有强隔离沙箱”。Agency 的跨控制面租户边界，与某次派工的文件、网络、工具或凭据隔离是不同层次；后者必须有明确能力声明和兑现方式。可认证的独立性才能标为 known，无法认证时要保留 unknown 或不支持状态。冻结的 Context Bundle 记录交付材料，也不自动证明模型不存在其他会话影响。[^21][^22]

“Grok 平台在功能上承担了 Agency 类职责”是合理的分析类比，但不是官方对象映射。公开文档没有把 Grok Bot 描述成可由任意第三方实现、能返回名册与履约条款的 Agency 端口。反过来，HCTL2 的外部 Agency 架构空间也不代表当前已经有可直接接入 Grok Bot 的适配器。[^9][^20][^24]

**7. 桌面与运行环境：最值得精确拆开的差异**

“Grok Bot 支持看 participant 的运行环境/PC 桌面”这一观察成立，但更准确的模型是：**同一账号的 Bots 共享一台持久云电脑，每个 Bot 有自己的工作屏幕。** 文件、浏览器会话和命令行凭据共享；独立屏幕不是独立安全边界。每个 Bot 在自己的屏幕上一次执行一个 computer-use task，多个 Bots 可以在各自屏幕上并行工作。[^2][^7]

设计文章用“每个 Bot 有自己的电脑”来描述角色体验；专门文档则明确底层共享范围。因此不应把设计措辞扩展为“每 Bot 独占 VM、浏览器身份和文件系统”。较可靠的解读是，产品把每个 Bot 的工作表面做成可单独访问的体验，而账号级电脑是共享资源。[^1][^7]

Grok 的观察阶梯为状态、预览、接管：用户先看是否活动，必要时展开侧栏查看工作，再在敏感步骤进入完整控制。专门文档确认预览可看到点击、输入和导航；登录验证等需要人处理时可以接管后交还。另一个方向——Bot 在人的本地电脑运行命令——是独立能力与权限设置，不能和人观察 Bot 云桌面混为一谈。[^1][^7][^8]

HCTL2 当前规范并非没有运行观察，也非默认把所有内容都放进 TUI。它默认 headless，以结构化执行流作为首层，PTY 转录用于第二级诊断，终端接管放在最后一级，并明确不要求每次执行都有 shell。文本确实提到进程、屏幕、心跳、钩子等观测，但只把这些当作触发关注的信号。[^20][^21]

| 能力 | Grok Bot 官方文档 | HCTL2 当前规范 |
| --- | --- | --- |
| 查看 agent 工作状态 | 活动、等待、需注意等对人状态 | Task/Run/Dispatch 投影、Request、结构化执行流 |
| 观察可交互 PC 桌面 | 明确定义 Agent Computer 预览 | 有通用屏幕观测提及，未定义等价的完整云桌面能力 |
| 真实终端/PTY | 云电脑包含终端 | 明确定义二级诊断和终端接管，不要求每次都有 PTY |
| 人接管并交还 | 官方产品流程 | 有票据与输入授权、接管规则；图形桌面协议仍需补充 |
| 观察对象归属 | 从 Bot 对话进入其工作屏幕 | 终端属于某次精确执行/派工，不属于 Participant 本身 |
| 看不到当前现场 | 文档提供电脑恢复/重建路径 | 必须按 exact attach、native handoff、structured inspect、semantic resume、replay 等能力如实标注 |
| 观察是否等于验收 | 可提供截图或动作记录供检查 | 明确不等于；必须进入证据和结果准入链 |

最实质的差异不是 GUI 对 TUI，而是 **“环境以谁为入口、以什么为身份、允许证明什么”**。Grok 的入口是熟悉的 Bot；HCTL 的权威连接对象是某次执行。前者适合持续委派和现场协助，后者有利于避免用户误接入旧执行、错误续用权限，或把旧屏幕当作当前成果。

对 HCTL 的建议是，沿现有 Agency 端口增加可选的图形工作表面能力：前端仍可以从 Participant 卡进入，但必须解析到精确 Dispatch 和当前可观察目标。没有活动执行时，应明确显示无活动现场，或者只提供标记清楚的历史回放；不按名称猜测一台电脑。这个方案是建议，当前规范并未实现或定义完整图形协议。[^21][^22]

**8. 上下文、记忆与成果：四单元背后的第五条主线**

Grok Bot 的上下文连续性主要体现在长期 Bot 的角色记忆、历史对话和共享环境。工具与 Skills 可以共享，记忆与 routines 则随 Bot；跨角色协作通过群聊、直接消息或共享文件发生。这样可以降低反复初始化工作的成本，但角色记忆仍应回到业务来源核对不断变化的事实。[^2][^6]

HCTL2 管的是“开工时到底交付了哪份 prompt 包”，而非取代 Harness 的整个会话上下文管理。Context Manifest 记录来源与选择，Context Bundle 记录按具体消费者权限物化的内容；长期 Memo 需要显式提炼并发布。任务评论、聊天和平台评审意见可以成为来源，但不会因被检索进上下文就改变验收契约。[^27]

这一差异解释了双方对交接的取舍。共享电脑让 Grok 的另一个 Bot 可延续已有文件和登录状态；HCTL 的跨执行交接要求精确成果、发布的 Memo、证据或裁决引用，终端 trace 不自动进入下一位执行者的上下文，未封存半成品也不默认继承。前者强调工作延续方便，后者强调继任者拿到的材料可定位、可解释。[^7][^22][^27]

成果对象也不能漏掉。Grok 将 Artifacts 列为产品原语，支持可预览、可编辑的文件结果；HCTL 除 Artifact/Memo 外，还通过 Repo/Change 模块管理 ChangeSet、精确快照、发布评审和集成凭证。只比较 room、kanban、run、participant，会遗漏“结果在哪里被封存、谁有权把它合入、完成证据从哪里来”的闭环。[^11][^13][^23]

**9. 用同一任务比较：修复登录故障并交付**

以下是根据官方能力与规范构造的比较场景，不是双方性能实测，也不是 Grok 强制执行的标准流程。

| 步骤 | Grok Bot 的合理使用方式 | HCTL2 的规范路径 |
| --- | --- | --- |
| 形成目标 | 在项目群说明问题、期望结果与不可做的动作 | 在 Project Room 塑形，记录来源与未决问题 |
| 确立承诺 | PM Bot 在 Notion 创建/更新任务并说明验收目标 | 显式采纳 Task Revision，区分机械、Gate、人判验收项 |
| 选人 | 复用工程 Bot，必要时请 reviewer Bot 协助 | 独立选择 Run 席位上的 worker，不自动沿用 Room 规划者身份 |
| 开始工作 | 对话或 Bot 交接触发，可再委派 Cloud Agent | 批准 Workflow 并显式启动 Run，冻结 Manifest，通过 Agency 派工 |
| 遇到需要登录的页面 | 打开 Bot 云桌面，人完成验证后交还 | Request 指明阻塞和获准输入方式；若 Agency 没有图形能力，应说明不支持该现场接管 |
| 审查 | Reviewer 检查结果、截图、PR 或来源 | 对精确 ChangeSet/Artifact 版本独立审查，按冻结 Gate 规则计票 |
| 中途改验收目标 | 用户消息可以调整工作 | 契约产生新 Revision；活动 Run 不被静默改写，须按规则处理分歧或替代 |
| 任务收尾 | Bot 返回结果，PM 更新外部看板 | Run 满足自己的完成条件，再请求 Task 独立验收并写入凭证 |

这个例子显示，Grok 更容易把人与多个 Bots 的日常合作连成连续体验；HCTL 需要更多显式对象，但能精确保留改约、换执行、评审和交付的关系。若修复不要求 HCTL 内部 Gate、持久重试或候选切换等能力，可以采用无 Run 路径，避免增加不必要的施工图；仅凭任务“小”不能绕过契约要求的评审。[^16]

再看三个异常情形：

- **作者换了一个名字参与自审。** Grok 可以安排角色分工，但本次未找到公开的机械独立计票协议。HCTL 中仅改显示名不会改变原选入记录，因此不能取得本应回避的必需评审席位。不同选入记录之间，回避作者配置是可声明的 Gate 策略，重复票去重要求实际执行配置与交付材料均相同，不能简化为“同模型一律只算一票”。这些规则证明逻辑分离，不证明物理或组织独立；若要求后者而端口无法认证，须返回不支持。它们仍是规范要求，尚不能视为已实现可靠性。[^19][^21]
- **用户停止工作，但此前已经写了文件或发出操作。** Grok 明说 Stop now 不回滚已完成动作；HCTL 同样需要区分逻辑撤权、物理停止和已发生的副作用。它的规范要求撤销旧权限，必要时隔离现场，不能只把状态标为取消就让第二个写入者开工。[^3][^19][^22]
- **任务板显示 Done，但交付证据不完整。** Grok 的看板实践没有公开统一处理协议；HCTL 应保留外部状态，同时拒绝无证据的完成，不用“看起来结束了”填补验收项。[^17]

**10. 对 HCTL2 的演进建议**

以下是设计建议，不是当前功能声明。优先级按“能否提高日常使用价值、是否保留现有治理边界”排列，未估算人日或开发成本。

| 建议 | 可以带来的价值 | 是否需要改动规范边界 |
| --- | --- | --- |
| 在卡片上先显示当前行动、阻塞、证据与下一步 | 借鉴 Grok 的注意力管理，减少进入终端查看进度的需要 | 主要是既有投影与 Request 的产品实现 |
| 模型提出交接时自动准备下一次 Trigger Preview | 保留上下文与来源，减少人复制粘贴 | 可沿用当前 human submit 规则 |
| 把 Participant 卡做成执行入口 | 让人从“谁在做”进入当前派工/历史，而不用先理解底层端点 | 展示可以聚合；必须保留 scoped identity 和精确派工归属 |
| 为 Agency 增加可选 GUI 观察与接管能力 | 支持浏览器验证、视觉调试与桌面现场协作 | 需要新增能力与协议约束，但不必改变 Participant 身份定义 |
| 把成功工作整理成版本化 Skill 候选 | 降低重复任务的准备成本 | 可生成候选材料；安装与能力申报归 Agency，后续执行冻结精确版本和摘要；经验转 Skill 的流程仍需设计 |
| 让普通 Room 的模型自动唤醒任意下一位参与者 | 获得更流畅的自主协作 | 直接触及现有执行边规则，需要新的授权制度 |
| 让同一个 Participant 自动贯穿 Room 和 Run | 增强“始终是同一个同事”的体验 | 触及选入记录作用域；不能只合并 ID |
| 让拖卡 Done 直接变成完成 | 操作更短 | 会削弱独立验收，当前不建议 |

桌面扩展应至少说明六件事：

1. **观察目标。** 哪个 Dispatch、哪次有效授权、哪个工作表面；是否共享底层环境。
2. **能力类型。** 状态、结构化事件、PTY、截图、图形流、只读回放分别支持哪些。
3. **输入权限。** 观察、普通输入、执行控制、安全输入分别授权；接管期间谁持有输入权。
4. **生命周期。** 断线、旧派工替代、机器重建、输入过期后如何失效或降级。
5. **隐私与共享。** 什么会显示在屏幕上，谁能看到，截图如何发布，不能把视觉工作表面当成隔离凭据的证据。
6. **证据地位。** 屏幕与动作日志是观测；用于验收时仍需绑定精确对象、来源和规则。

上述要求可以沿用 HCTL 已有票据、代次、输入权限与 Agency 能力声明的思路扩展。应增加的是“可选观察通道”，而不是把宿主机 ID 或某个远程桌面地址变成 Participant 的永久身份。即使某个 Agency 不提供桌面，headless 执行也应保持完整可用。[^21][^22]

对于长期角色连续性，一个可评估的方向是提供“可复用的角色档案或选人模板”，让用户在界面上保持熟悉感，同时在每个 Room 与 Run 建立独立选入记录。可复用的是人设、方法和候选偏好；权限、预算、上下文与评审资格仍在本次作用域中重新确定。这属于建议中的额外抽象，当前 Participant 不能直接当作跨阶段员工档案使用。

如果未来确实要实现 Grok 式更自由的交接，建议先明确它是新的授权类型：允许哪些接收者、什么工作范围、多少扇出、预算多少、何时必须回到人。HCTL 的 Run 规范允许在冻结图与有界模板内自动推进，可以优先实现这条路径。Agency 门后的执行体也可以使用内部 agent 团队，但这些队友不因此变成新的 HCTL 席位或获得额外票权。普通 Room 中开放临场自主协作，应有单独的规范决定，而不是依靠提示词“别乱派活”。[^15][^19][^20]

**11. 当前成熟度与需要继续验证的地方**

| 结论 | 证据状态 | 应保留的限制 |
| --- | --- | --- |
| Grok 有长期 Bot、群聊与异步交接 | 官方产品文档明确 | 未实测复杂并发、长期稳定性与实际限制 |
| Grok 支持看桌面与人接管 | 官方电脑文档明确 | 账号共享电脑；每 Bot screen 不等于独立 VM |
| Grok 有 Kanban 多团队模式 | 官方作者公开实践 | 使用 Notion；并非已公开统一治理协议 |
| Grok 有 routine runs | 官方文档明确 | 公开运行历史不等于完整通用执行契约 |
| HCTL 定义 Room/Task/Run/Participant 治理 | 固定提交中的规范明确 | 核心控制面与完整产品尚未交付 |
| HCTL 已有运行相关软件 | 已有工具、基础库与依赖打包 | 第三方组件能启动，不代表五模块闭环已实现 |
| HCTL 对屏幕完全没有定义 | 不成立 | 有观测提及；尚未形成等价图形桌面产品协议 |
| HCTL 默认必须使用 TUI | 不成立 | 规范是默认 headless/结构化流，PTY 与接管逐级升级 |
| 两者已有互通方案 | 未证实 | 目前只能给出语义映射，不能承诺即插即用 |

实现方面，HCTL2 的 `src/README.md` 明确列出 hctl2-tool 已有 Git/SCM、工作树、封存与事实回读等机械能力；独立运行不产生治理账本或 Receipt。Agency 目录当前主要已有技能目录，可用性申报与 control 适配器待建。Room/看板/工作流/终端依赖的打包与生命周期验证，是后续完整系统的基础，不是领域治理已完成的证据。[^24][^25][^26]

Grok 资料存在产品叙述和专门文档口径不完全相同的情况。例如设计文强调 Bot 自己的电脑，专门电脑页明确账号共享；本报告采用专门文档的资源与权限边界。未公开的底层事务机制统一表述为“未找到公共定义”，不据此反推不存在。

后续最有价值的验证不在于继续收集宣传功能，而在于四个可复现案例：多 Bot 同时修改同一任务的归属与冲突；停止之后残留动作的可见性；电脑恢复后进行中的工作与旧登录状态如何处理；验收标准改动后，旧结果是否还会被计入完成。对 HCTL，这些应对应未来控制面契约测试；对 Grok，需要在获准测试环境里做真实操作，公开文档不能代替结果。

**12. 适用方向与设计取舍**

如果目标是让使用者今天就能把研究、运营、资料整理和跨网站工作交给持续工作的数字同事，Grok Bot 的长期角色、事件唤醒和桌面接管形成了连贯的产品方法。它的多团队看板案例尤其展示了：在已有工具里建立责任和协作，不一定需要先造一个新的项目管理系统。[^4][^10][^12]

如果目标是构建跨 Harness 的工程协作系统，并清楚区分目标讨论、验收承诺、冻结施工、独立评审与精确集成，HCTL2 的规范提供了更明确的责任模型。它的价值要通过后续实现兑现，尤其要证明复杂的治理边界能在简单任务上保持足够轻。[^13][^16][^23]

对 HCTL2 最有价值的借鉴，是把 Grok 的可理解性和连续体验应用到已有模型上：让人一眼知道谁在做、卡在哪里、需要什么决定，必要时能看到并帮助执行现场。与此同时，应保留它已经明确的身份作用域、授权冻结和独立完成校验。桌面能力可以增加，模型的行动权是否扩大则应作为另一项明确设计决定。

站在hctl2的立场，从grokbot里能学到什么不？5个模块 - room/kanban/run/participant/repo，分开来看，比。更详细讲为什么grokbot的tradeoff更好。

--------------------------------------

**有，而且有几处值得直接调整 hctl2 的核心规范。我的主要判断是：对日常开发协作，Grok Bot 更合理地把“持续推进工作的责任”交给了系统，减少了用户亲自调度、跟进和救场的次数。**

hctl2 对“这次调用是谁授权的、结果对应哪个版本、凭什么算完成”定义得很认真。但用户委托“把这个问题解决掉”以后，通常也期待系统接住中间的找人、调查、返工、等待检查和整理结果。Grok Bot 在这些地方采取了更积极的默认值。

下面的“更好”，主要指**个人或小团队使用多个 Agent 完成日常开发工作时，更少打断、更少重复解释、更容易放手委托**，不是声称 Grok Bot 已经证明拥有更强的审计或验收保证。hctl2 以固定提交 `e0cc1ee` 的 v0.18.2 规范为基线；Grok Bot 的一些看板和工程流程来自官方作者搭建的实践，我会和产品内置能力区分。

先给出五块的判断：

| 模块 | hctl2 当前取舍的重心 | Grok Bot 值得学习的取舍 | 我建议 hctl2 改什么 |
|---|---|---|---|
| **Room** | 每次协作调用都有明确的人类授权；讨论与执行输入分开 | 已委托范围内，Bot 自己找人、交接、继续推进 | 批准一段协作的边界，允许边界内自动路由；统一用户的沟通入口 |
| **Kanban** | 承诺、契约、执行、完成各有精确事实 | Bot 维护日常进展，人关注阻塞和可交付结果 | 让 Agent 承担看板维护与跟进；把多项后台治理动作组合成少量用户决策 |
| **Run** | 冻结施工图、候选、权限和验收规则后执行 | 长期负责人持续观察、修正、重试，再把成熟做法自动化 | 默认支持“负责到可交付”的轻量执行，而不把自动跟进局限在正式 Workflow |
| **Participant** | 某个 Room／Seat 中的一次选入身份 | 长期角色、领域经验、持续职责，以及可查看和接管的工作环境 | 增加稳定的角色主体；把长期身份、本次任用、本次执行分开 |
| **Repo** | 仓库既是写入边界，也是项目组织入口 | 从工作目标出发，调用已有代码工具与平台 | 让 Project 可以跨 Repo；平台按需接入；采用更贴近原生平台的合并策略 |

**1．Room：Grok Bot 的取舍更好，是因为它接走了“下一步该找谁”的调度劳动。**

hctl2 的普通 Room 中，模型可以建议下一位协作者，但不能自行发起调用或唤醒执行体；每条临场执行边必须来自人的动作，并经过 Trigger Preview。系统会代填上下文等信息，所以它已经减少了复制粘贴；剩下的成本是**每次交接仍然要等人判断和操作**。另外，Room 中的 `@` 面向规划者，给正在施工的人补充指令，要进入绑定具体执行的 Execution Chat。[hctl2 Room 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/project.md)

Grok Bot 的群聊允许 Bots 判断谁回应、异步联系和交接，用户也可以用直接消息调整正在进行的工作。它的设计文章明确讨论过这个取舍：更多分派和交接控件，会增加用户的协调工作，因此让 Bot 承担更多路由责任。[协作文档](https://docs.x.ai/grok-bot/chat-and-collaboration)、[官方设计文章](https://x.ai/news/designing-grok-bot)

例如，用户说：

> 查一下登录偶尔失败的问题，前端和后端一起看，先给我原因和修复建议。

接下来可能需要前端读浏览器日志、后端查接口行为，再找熟悉鉴权的人解释某个历史设计。

**这些交接多数是在实现用户已经委托的目标。** 如果涉及的成员、资料和预算都在获准范围内，再让用户逐条确认“是否请后端回答这个问题”，所增加的信息量很少，却会让调查停在用户的可用时间上。

这就是 Grok 的取舍更好的原因：

- **协作能在用户离开时继续。** 后台进程还活着，只解决了执行持续性；下一次找人仍要等用户，协作就没有持续性。
- **用户不用扮演人工调度器。** 他关心问题是否查清，通常不想决定每次咨询的执行顺序。
- **审批更容易集中在真正的变化上。** 例如需要读取另一套资料、扩大修改范围、增加预算，而不是重复批准目标内部的普通步骤。

我会给 hctl2 增加一种**有范围、有期限的协作授权**：允许哪些成员参与、可以使用哪些资料、可以做哪些动作、总预算和停止条件是什么。模型提出下一次调用后，control 检查它是否落在这份授权内；符合就执行，越界再找人。每次调用仍生成自己的结构化记录。

这是对当前“普通 Room 的每条执行边只能由人提交”的实质修改。它让系统承担更多策略检查，也承担错误路由、循环讨论和浪费预算的风险。但对一个成员明确、资料范围明确的小组，这些风险可以通过限额、可见记录和随时停止来约束，换取的异步工作能力很值得。

Grok 自己也保留了动作级审批和自动审查规则，因此值得学的是**减少常规路由审批，把审批放到具体影响上**。[Grok Bot 审批机制](https://docs.x.ai/grok-bot/approvals-security-and-privacy)

Room 与 Execution Chat 的用户体验也应该合并得更自然。用户可以在原来的讨论现场说“负责这个修复的人再检查一下 Safari”；界面展示这条指令将送往哪个执行、哪条分支，后台仍绑定精确 Dispatch。只有同时存在多个合理目标时才让用户选择。**精确的输入归属应由系统保证，不必要求用户先理解规划者和施工者的记录区别。**

**2．Kanban：值得学的是让 Bot 负责维护和推动工作，让看板成为用户检查结果的地方。**

hctl2 在这块已经有不少正确取舍：卡片可以先没有契约；小事可以走无 Run 路径；卡片内容也由外部任务后端承载。它并没有要求每张卡都先变成一份复杂合同。与此同时，当前规范仍是一个 Repo 一个 Board，并在首次 Run 或完成前要求显式采纳契约；轻量路径的合入与完成分别有预览。[hctl2 Task／Kanban 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/task.md)

Grok Bot 没有公开一套与 hctl2 对等的内置 Kanban 治理模型。官方介绍的一种实验用法，是每个项目一个频道和名册，用 Notion 存项目与任务，让 PM Bot 维护数据库，成员推进任务，受阻时再找人。[官方多团队实践](https://x.ai/bot/guides/how-i-run-multiple-teams-of-grok-bots)

**这个取舍的优点，是先把“项目管理这份劳动”自动化，而不要求用户先接受一整套新的项目管理制度。**

这里有两个特别值得 hctl2 学的地方。

**第一，维护看板本身应该是 Agent 的职责。**

用户委托了一项工作以后，谁来补充进度、追问停滞原因、关联 PR、检查证据、把任务标成“需要你决定”？如果这些都要人做，看板只是把原本藏在聊天里的管理负担显示出来。

Grok 的 PM Bot 模式至少把这个责任交给了一个明确的主体。它可能更新错，因此不能让它的自述直接变成完成凭证；但这不妨碍它负责日常维护。

hctl2 可以让 Agent：

- 更新普通进度、整理评论、关联结果和检查记录；
- 发现停滞后，在授权范围内继续跟进；
- 准備验收材料，并解释还缺哪一项；
- 把契约变更作为建议交给人，正式完成继续由控制面验证。

**“Agent 负责推动”与“控制面负责判定”可以同时成立。** 现在 hctl2 对后者定义得更完整，前者值得成为默认产品责任。

**第二，用户做的是交付决策，不必按后台模块逐个结算。**

假设一项小修已经给出了明确 diff、测试结果、截图和验收项。用户的决定很可能就是：

> 这份结果符合要求，合进去，完成这件事。

hctl2 可以用一次完整预览承载这个决定，后台依次执行集成、回读、Task 验收与外部状态同步。它们仍然是独立事务：合入成功但某项验收不满足，就如实停在那个状态，不能假装全部成功。

这样既保留了不同事实的区别，又减少了用户在 Change 和 Kanban 之间来回结算的动作。对于新卡片，也可以在“按这些标准处理”的一次确认中，明确展示并组合契约采纳与启动，而不是让用户感受到多个独立行政步骤。

这比单纯减少一个按钮更重要：**后台对象边界不必一一对应用户决策边界。**

代价是组合命令、部分成功和恢复体验会更复杂。但这些复杂性由产品实现一次，通常比每位用户在每项任务上反复处理更划算。

我还会把看板的默认视图优先组织成：

- 系统正在处理，无需我介入；
- 需要我补充信息或做决定；
- 已经准备好让我验收；
- 长时间没有可靠进展。

hctl2 现有的版本、来源、Run、证据和同步状态仍然有价值，可以在详情中展开。默认界面首先应该帮助用户判断**自己的注意力该放在哪里**。

**3．Run：Grok Bot 更好的取舍，是把一次委托延伸到“结果已经值得交给人”，包括中间的返工。**

这里有一条很具体的规范差异：hctl2 的无 Run 路径明确没有自动返工。PR 收到评论后，需要人发起新的 Room Invocation，再把选中的评论交给它。正式 Run 可以定义返工，但轻量路径的继续推进责任会回到人手里。[hctl2 Repo 的完整变更流程](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/repo.md)

Grok 的官方工程实践中，长期工程 Bot 会管理编码 Agent，读取结果和证据，跟进评论、CI 失败及冲突，继续发指令，直到工作进入可评审状态。作者还配置了按风险决定自动合并或交人审核的流程；这是作者搭建的工作方式，不是所有账号开箱即得的保证。[Grok Bot for Engineering](https://x.ai/bot/guides/grok-bot-for-engineering)

**我认为 hctl2 应该直接学习这种“持续负责”的默认值。**

因为用户委托“修好登录问题”，通常已经包含：

- 第一轮测试失败后继续修；
- 评审指出遗漏后再改；
- 等 CI；
- 处理授权范围内的普通冲突；
- 把结果整理到可验收程度。

这些是交付的正常组成部分。如果每轮都要重新派单，用户委托出去的是第一轮操作，后续项目管理仍留在自己手里。

hctl2 可以在首次授权中明确一段有限的跟进责任，例如：

> 在这个任务、这些路径和这条 PR 范围内，继续处理评审意见和检查失败；总预算与截止时间固定；涉及需求变化、权限扩大或预算越限时找我。

每轮仍然创建新的调用和 ChangeSet 版本；旧执行不复活，旧评审不冒充新版本评审。**可追溯性来自记录每轮发生了什么，不必依赖每轮都由人重新按启动键。**

还有一个更深的 Run 取舍：**目标、权限和验收需要稳定；实现策略需要有发现空间。**

hctl2 的 Run 会冻结 Workflow、候选、权限等内容，改变某些要素需要替代 Run。它也已经允许 Harness 在节点内部自行拆解任务，所以不能说 hctl2 要把每个操作都预先画进 DAG。[hctl2 Run 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/run.md)

我会利用它现有的内部自主空间，把默认执行做得更轻：

- 用户主要确认目标、边界、预算和交付标准；
- 一个负责人可以在边界内观察 Worker、调整提示、组织调查和返工；
- 需要独立裁决的交付点，再使用明确的 Gate；
- 真正改变承诺或权限时，才进入新的授权。

**不必第一步就开放任意动态 DAG。** 甚至可以先用简单的 Workflow 模板实现“施工—检查—返工—评审”，把持续跟进做好。当前更迫切的问题是轻量工作缺少完整的推进责任，而不只是图是否可以动态增加节点。

Grok 的自动化路径也更贴近用户形成经验的过程：先完成一次任务，把成功的方法保存为 Skill，再用 Routine 指定何时运行。[Skills 与 Routines 文档](https://docs.x.ai/grok-bot/skills-routines-and-automations)

这值得 hctl2 学，因为很多工作在第一次执行前并不知道最佳方法。**从实际成功过程沉淀 Workflow，往往比在没有执行经验时先设计完整施工图更可靠。**

这笔取舍的代价是运行路径更难预测，可能反复尝试、消耗更多 token。因此要有累计预算、截止时间、无进展检测和升级条件。对探索性开发，我更愿意让系统承担这些约束下的尝试成本，换取用户不必持续守候。

**4．Participant：这是最值得大改的一块，要让“长期负责人”和“可以介入的工作现场”真正成立。**

hctl2 当前的 Participant 是某个 Room 或 Run 席位里的选入记录。同名角色出现在规划和施工阶段，也不因此共享一份跨阶段身份。它已有长期 Project／Room 上下文、Memo、可复用配置等机制，因此不能说它每次从零开始；欠缺的是一个明确的、跨任务持续存在的角色主体。[hctl2 Participant 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/participant.md)

Grok Bot 则把角色本身放在产品中心：名字、职责、对话、工作上下文和后续任务，都围绕一个持续存在的 Bot 展开。[Bot 管理文档](https://docs.x.ai/grok-bot/bots)

**为什么这对日常工作更好？因为委托关系需要连续性。**

“你继续负责 CI 稳定性”和“本次从某 Agency 选择一个符合条件的执行配置”，解决的是不同层次的问题。前者让用户知道以后找谁、把反馈给谁、谁应该留意新问题；后者保证这一次执行如何落实。

长期角色还有实际的信息组织价值。它可以逐渐积累某个领域的工作材料：哪些测试容易假失败、哪份文档已经过时、怎样提供用户需要的证据。调用时自动找到这些材料，比用户反复选择和补充更省事。这个收益不意味着记忆永远正确，重要事实仍应回到权威来源核实。

我会把它整理成三个层次：

| 层次 | 应该持续保存什么 | 不应自动继承什么 |
|---|---|---|
| **长期角色** | 稳定身份、职责、工作偏好、默认 Skill、带来源的经验、持续待办 | 跨项目通用写权限、评审票权 |
| **本次任用** | 在这个 Room／Seat 中的职责、预算、授权范围 | 其他任用的权限与独立性资格 |
| **本次执行** | Dispatch、实际配置、输入版本、工作树、观察与接管通道 | 已结束执行的输入权和写租约 |

这样，“同一个 Jack 持续负责前端”在用户眼里成立；每次具体执行仍然有精确授权。独立评审也不会因为换了一张任用记录就自动成立，仍然需要核对实际配置、材料与作者关系。

长期记忆的代价是陈旧信息、误记和经验污染。我会给经验保留来源、时间和适用范围，让本次执行记录采用了哪些材料；正式评审按需要使用隔离的上下文。没必要把每条工作经验都变成人工批准的 Memo，也没必要把经验当作验收事实。

你提到的**“能看 participant 的运行环境／PC 桌面”**，同样值得提升为明确产品能力。

先澄清实际边界：Grok Bot 文档说，同一账号的 Bots 共享一台持久云电脑，各自有屏幕；文件、浏览器登录态和命令行凭据共享，屏幕不是安全隔离边界。用户可以查看现场，接管处理登录等步骤，再交回 Bot。[电脑与应用文档](https://docs.x.ai/grok-bot/computer-and-apps)

它的价值至少有三层：

- **状态：** 知道它还在工作，不必盯日志。
- **查看：** 看到它卡在登录框、错误页面还是测试界面，减少靠文字猜现场。
- **接管后继续：** 人解决一个必须亲自处理的步骤，然后让原任务接着走。

Grok 的设计采用了状态、侧栏预览、完整接管的分层，避免默认鼓励用户一直监视电脑。[官方设计文章](https://x.ai/news/designing-grok-bot)

**这比“给每个 Agent 开个终端窗口”更好的地方，是把人工救援接入了正常工作过程。** 一个原本会让任务失败或重新开始的障碍，可以变成一次短暂介入。持久环境还减少重复登录、安装依赖和寻找上次文件的成本。

hctl2 适合让 Agency 声明自己能提供哪些观察面：结构化事件、终端、浏览器、桌面。Workbench 在角色卡或任务卡上提供统一的“查看—接管—交回”入口，底层仍然连接精确 Dispatch。Headless 继续是一种有效实现；具备 GUI 的环境则有明确的产品契约。

我会学 Grok 的持久环境和介入方式，但不会默认复制账号级共享凭据。对 hctl2，按项目或信任范围共享环境、保留 ChangeSet 写入隔离，会更符合它的定位。桌面基础设施和环境漂移也有成本，应该按能力提供，而非要求所有 Participant 都运行完整桌面。

**5．Repo：值得学的是让工作目标先成立，再把 Repo 作为具体交付边界。**

hctl2 明确规定 Project 属于一个 Repo，并在交付范围中明确排除了用户级总入口。这是一个有意识的产品选择。[Project 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/project.md)、[交付范围](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/delivery.md)

Grok 的工程方法把外层 Bot 用于收集 Slack、Notion、GitHub 等上下文，再把明确的编码工作交给内层 Agent。工作可以先以问题和职责出现，再逐渐定位到代码。[Grok Bot 101](https://x.ai/bot/guides/grok-bot-101)

**这个取舍更好，是因为用户经常还不知道问题属于哪个 Repo。**

例如“登录成功率下降了，查一下原因”，可能涉及前端、API、配置、基础设施或第三方服务。如果必须先选 Repo 才能开始协作，就把一部分问题定位工作提前交给了用户。

即使已经知道要改哪里，一个目标也可能天然跨仓库：

> 统一 Web、API 和文档中的登录体验。

用户心中是一项交付，代码上可能是三个仓库。分别建立 Project 后，再由人拼接上下文、依赖和整体进展，会削弱外层协调工具的价值。

我会让产品层的 **Project 可以引用 `0..N Repo`**：允许先调查、后绑定，也允许一个目标涉及多个仓库。每个 ChangeSet、写租约和集成意图仍然指向一个精确 Repo。

这项修改的代价是真实的：要处理跨仓库依赖、部分完成和补偿，不能再靠单一 Repo 层级天然限定所有上下文。但不必追求跨 Git 仓库的原子合并；可以清楚地记录“前端已合入、API 待检查、整体尚未完成”。

如果要渐进实施，我会先做用户级入口和跨仓库只读调查，再放开多 Repo Project，最后处理跨仓库写入编排。它们都服务于同一个实际收益：**用户可以把完整问题交给系统，不必先替系统切成它能接受的形状。**

Repo 还有两处默认值值得更务实。

**一处是平台接入成本。** hctl2 对纯本地仓库默认建立本地代码协作平台；无平台是显式选择的受限路径。本地仓库也沿用完整的发布、评论、合入链路。[hctl2 Repo 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/repo.md)

统一流程有实现和一致性收益，但用户第一次只想修一个本地问题时，要承担建仓、初始交付、服务生命周期等成本。既然 hctl2 已经设计了无平台路径，就可以把能力按需启用：已有 GitHub 就用 GitHub；纯本地先用本地检查和明确验收；需要 PR 线程或多人协作时再启用本地平台。

这是从 Grok“在既有工具上完成工作”的方式推导出的 hctl2 建议。对首次使用，先得到一项可检查的结果，通常比第一天就统一全部基础设施更有价值。

**另一处是合并策略。** hctl2 的规范承认，目前核验的平台都无法保证它严格形态要求的“预期目标头不变”，因此需要显式选择接受目标前移的授权形态。[hctl2 集成约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/repo.md)

我更倾向让用户按仓库预先批准一种贴近平台原生能力的政策：

> 固定待合入的源版本、合并方式和保护条件；条件满足时允许平台合并；记录实际结果。只有明确要求固定目标基线的工作，才使用更严格的限制。

这样用户在设置仓库策略时理解一次语义，日常预览主要看具体变更、证据与异常。精确版本、持久集成意图、执行后回读和唯一凭证都可以继续保留。

**Repo 的可信内核是 hctl2 的优势，值得改变的是它给普通工作设置的默认组织方式与接入成本。** Grok 的公开材料不足以证明它拥有同等强度的版本与集成保证，这部分没有理由为了模仿产品体验而放弃。

如果我是 hctl2 的负责人，我会按下面的顺序做：

1. **先做有限授权下的持续跟进。** 同一个负责人能接住调查、协作交接、PR 评论和 CI 返工，直到结果可审。它同时改善 Room、Run 和 Participant，最直接减少用户被叫回来的次数。
2. **再做统一的交付与介入界面。** Kanban 显示谁在推进、哪里需要人、哪些结果可验收；从同一现场查看运行环境、补充指令、接管和交回；一次完整决策可以驱动多个后台模块。
3. **再调整 Repo 与 Project 的关系和接入默认值。** 让用户能先提出问题，再由系统帮助定位仓库；允许完整目标跨仓库持续存在。

第一版可以用一个具体场景验收：**修一个 UI bug，过程中经历一次 CI 失败、一次评审返工和一次需要人工处理的网页登录，最后提交带截图与测试证据的 PR。** 记录用户被打断几次、多少障碍由系统自行恢复、最终证据是否可信，以及总耗时和 token 成本。这个场景最能检验 hctl2 是否真正学到了 Grok Bot 更好的取舍：用户委托之后，系统能持续承担多少推进工作。

--------------------------------------

**有。hctl2 最值得坚持的优势，是它把“承诺了什么、授权了什么、实际执行了什么、凭什么算完成”分开，并为这些事实建立了独立于 Agent 的记录。** 这在长周期开发、多 Agent 评审、频繁返工和故障恢复中，比单纯让 Bot 持续推进更有价值。

如果给优势排个顺序，我认为 **Kanban／Task 的完成语义、Run 的评审与恢复规则、Repo 的精确交付链**最突出；Room 的上下文来源和 Participant 的执行身份为它们提供基础。

先说明比较边界：按这次研究的固定版本，hctl2 仍有大量能力处于规范阶段，已实现的主要是 Git／worktree 等机械组件，control、公共 CLI、Workbench 等尚待落地。所以这里主要说的是**设计和方法论更强**，不能据此认定当前成品已经更可靠。Grok Bot 也有审批、自动审查、动作记录等控制，不能把它当成完全依赖提示词的系统来比较。[hctl2 实现状态](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/src/README.md)、[Grok Bot 安全机制](https://docs.x.ai/grok-bot/security)

| 模块 | hctl2 更强的设计 | 用户得到的实际好处 | 更值得采用这一取舍的情况 |
|---|---|---|---|
| **Room** | 区分讨论、正式决定、执行授权；冻结交付上下文与来源 | 能查清错误来自需求、交接材料还是执行；换 Agent 后仍保留项目依据 | 长期项目、多人交接、需求反复变化 |
| **Kanban** | 完成绑定精确任务契约和逐项证据 | 避免“卡片 Done 了，但承诺没交齐”；新需求不会被旧结果冒充完成 | 有明确验收标准、需要可靠进度的开发 |
| **Run** | 评审资格、票数、版本、重试、撤权有明确规则 | 避免重复票、旧评审误用、失联执行继续写入等问题 | 多 Agent 评审、并发、长任务、自动恢复 |
| **Participant** | 角色、方法、配置、权限和具体执行分开 | 能选择与替换执行工具，核对实际配置，精确观察和接管 | 多 Harness、多供应方、专业化评审 |
| **Repo** | 写入、封存、评审、合入、回读分别验证 | 确认审的是哪个版本、合入的是否就是它，失败后保住成果 | 真实代码交付、多人改同一仓库、关键分支 |

**1．Room：hctl2 更好地保留了“为什么这么做”，也更容易定位协作中的错误。**

Grok Bot 的长期角色、记忆和自然交接，让工作延续得很顺。hctl2 更有价值的另一面，是把讨论产生的知识和决定放到项目本身，而不是主要依靠某个 Bot 记住。

它区分了聊天记录、正式 Memo、任务契约、Workflow，以及实际交给某次执行的 Context Bundle。普通讨论不会自动修改已经采纳的承诺；临时 Scoped Room 需要回填结论或显式结案；执行时的上下文有来源、版本和交付记录。[hctl2 Project／Room](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/project.md)、[Context 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/context.md)

**这比“聊天历史都还在”更有用，因为保留记录和解释错误是两件事。**

例如，讨论中明确说过“必须兼容旧客户端”，后来实现者却删掉了旧字段。真正需要判断的是：

- 这句话只是一个建议，还是已经形成正式决定？
- 它有没有进入本次执行的输入？
- 它是否在裁剪或摘要中被遗漏？
- 执行者已经收到要求，但没有遵守？

hctl2 的输入清单与交付记录，能为区分这些情况提供依据。不同原因对应不同修复：修改需求、修上下文组装、完善方法，或更换执行者。否则人很容易只得出“这个 Agent 不靠谱”，然后换一个 Agent 重试，原来的系统性问题继续存在。

这里也要把保证说准确：hctl2 管理的是**系统交给执行者的输入包**，并不声称能完整控制 Harness 后续自己收集的上下文，更不能证明模型真的理解了每条要求。但它至少明确了系统应该负责的输入边界。

**另一个优势是可以放心讨论尚未决定的方案。**

“也许可以删掉这个兼容层”“要不要让另一个模型试试”，在 hctl2 中首先是讨论内容。正式授权需要有可识别的转换，冻结参与者、资料范围、权限与预算。这对探索架构、讨论高成本方案很有用：用户不必担心每句推演都被理解成立即执行的委托。

我仍然赞成上一条提出的“范围内自动协作”。应该减少的是反复点击；应该保留的是**模型建议必须落到一份有效授权上，讨论文字不能自行扩张权限或改写承诺**。Grok 的自然交接更方便，但其公开协作文档没有给出与 hctl2 相同精度的上下文冻结和决定升格契约。[Grok Bot 协作文档](https://docs.x.ai/grok-bot/chat-and-collaboration)

这个取舍的代价是显式沉淀和来源管理更重。对短小的一次性任务，收益有限；对持续数周、多人交接的项目，避免反复丢失“当初为什么这么定”，会节省大量后续解释成本。

**2．Kanban：hctl2 最明显的优势，是“完成”有独立于执行者的定义。**

Grok 的官方团队实践会让 PM Bot 维护 Notion 看板，工程 Bot 根据 PR、CI 和评审结果更新进度。这很适合推动工作，但看板状态与交付标准之间的关系，主要由具体团队的方法和自动化流程建立。[Grok 多团队实践](https://x.ai/bot/guides/how-i-run-multiple-teams-of-grok-bots)、[Grok 工程实践](https://x.ai/bot/guides/grok-bot-for-engineering)

hctl2 则把这件事提升为系统契约：

- Task Revision 固定这一版承诺的范围和验收项；
- 每项要求明确由机械检查、评审席位还是人来判；
- 完成时逐项核对相应证据；
- Completion Receipt 记录究竟完成了哪一版承诺，以及依据是什么。

外部卡片关闭、Agent 退出、Run 正常结束，都不能直接代替这套验收。[hctl2 Task 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/task.md)

**它解决的是开发里非常常见的“局部成功被当成整体完成”。**

例如，任务要求：

> 修复登录问题，兼容 Safari，增加回归测试，并合入主干。

Agent 提交了代码、单元测试通过，也开了 PR。这些都是有效进展，但 Safari 尚未验证，PR 也没有合入。hctl2 的设计能让这些事实同时成立：

> 实现已提交；部分检查通过；任务尚未完成。

这对用户的实际好处是：**可以依据看板安排后续工作，而不用每次重新翻聊天、PR 和测试记录，确认 Done 到底是什么意思。**

第二个优势是**需求变化不会悄悄改写历史**。

假设一个 Run 按 Task Revision 3 开始施工，期间用户采纳了 Revision 4，增加一项兼容要求。hctl2 允许新契约存在，但旧 Run 仍然对应旧契约；它完成后，不能自动宣称 Revision 4 已完成。

这个规则看起来严格，却能避免一种很难察觉的错误：新需求显示在同一张卡上，旧执行交了结果，卡片变绿，于是所有人都以为新需求也做了。

第三个优势是**不同系统的状态可以如实不一致**。外部已关闭而 hctl2 尚未验证，可以明确显示两种状态；hctl2 已验收、外部写回还未确认，也不必伪装成完全同步。[hctl2 Kanban 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/task.md)

代价是契约、证据和同步状态增加了复杂性，也可能让某项看起来已经完成的工作暂时停留在待验收。**当错误地宣布完成会误导后续开发时，这个成本很值得。**

这里最应保留的是独立验收，不一定是独立按钮。上一条建议把合入与完成组合成一次用户决策，后台依然应该分别验证。契约本身写错、测试覆盖不足，系统也仍可能验收一个不理想的结果；hctl2 提高的是验收过程的明确性，不是自动保证验收标准正确。

**3．Run：hctl2 更擅长处理多 Agent 工作中“不顺利的那一半”。**

Grok 的优势是负责人能持续观察、调整和催促。hctl2 的优势，是提前定义出现重试、返工、失联和分歧时，哪些身份、权限与结果仍然有效。

**首先，多 Agent 评审有明确的有效性规则。**

hctl2 把评审绑定到精确版本，规定作者选入记录不能占本 Run 的必需评审席位；各席位的交付上下文不能包含本 Gate 其他席位的裁决；候选重试不能增加票数；代码版本变化后，旧票失效。它还按实际 Worker Profile 与交付材料摘要去重，显示名和人设不参与计票。[hctl2 Gate 与计票规则](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/run.md)

这对用户有什么用？

假设三位 Reviewer 都说“通过”。用户真正需要知道的是：

- 它们是否审了同一个版本？
- 是否有人只是在重复另一个人的结论？
- 同一个评审者重试了三次，是否被当成三票？
- 评审通过以后代码又变了，旧结论是否还在发挥作用？

hctl2 把其中一部分问题变成控制面的确定性规则。这比每次在提示词里强调“请独立、认真评审”更容易持续执行。

不过，这些规则**不证明模型之间统计独立，也不证明评审正确**。hctl2 自己也区分逻辑身份分离与物理、组织独立；供应端无法认证的要求，不能冒充已经满足。它提供的是更明确的评审制度。

**其次，重试不会被当成一种含糊的“再来一次”。**

hctl2 区分消息重投、候选切换、引擎重试、语义返工与替代执行。它们改变的对象不同：

- 消息回执丢失，应该取回或重投同一个动作，不能再造一份交付；
- 执行工具故障，可以在获准候选里更换尝试，不能增加评审票；
- 代码修改后重新评审，要对应新版本；
- 需求或权限变了，需要新的授权边界。

这些区分的价值在于：**自动恢复可以继续工作，同时不悄悄复制副作用、沿用旧验收或扩张权限。**

**再者，取消和替代包含撤权责任。**

例如 Worker A 失联，系统准备让 Worker B 接手。A 可能只是网络断了，进程仍在修改文件。hctl2 要求处理旧派发、输入权、写租约与运行现场的隔离；不能证明必要隔离时，不能把它当作已经安全释放。[hctl2 Run 状态与撤权约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/run.md)

这类问题在顺畅演示中不明显，长任务和多 Agent 并发时却很实际。hctl2 的取舍是为恢复规则付出实现成本，换取故障发生后仍能解释“谁还可以写、哪个结果还算数”。

Grok 已有停止、恢复、持续跟进等能力，但公开材料没有展开与这些规则对等的完整协议，因此不能断言它内部处理不好。可以明确说，**hctl2 把故障下的正确性定义得更完整，也更适合作为多个执行工具共同遵守的契约**。

这部分的代价是设计复杂、恢复有时宁可等待，也不猜测安全。但执行数量越多、任务越长、重复副作用越昂贵，这个取舍越有价值。

**4．Participant：hctl2 更适合“有意识地选择执行能力”，也更容易在更换工具后保留项目制度。**

Grok Bot 把 Bot 包装成长期同事，用户体验更自然。hctl2 的分层则让用户有机会回答更具体的问题：

> 这次究竟用了哪个 Harness、什么模型、哪版方法、哪些权限？其中哪些信息经过核验，哪些只是供应方声明？

它区分工种、选入身份、人设、模型、Skill、Worker Profile 和 Dispatch；Skill 还区分声称具备、实际可用、本次已装载，并标注能否核验。方法或配置更新，不应悄悄改变已经冻结的执行。[hctl2 Participant 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/participant.md)

**这个取舍的实际收益，是质量变化可以被调查，专业能力可以被替换。**

例如，同样叫“安全 Reviewer”的角色，上次找到了问题，这次没有。仅靠名字和对话连续性，很难知道原因。hctl2 的设计允许比较：

- 本次实际使用的模型或 Harness 是否变了；
- 方法论 Skill 是否升级或根本未确认装载；
- 收到的材料是否不同；
- 执行权限或工具可用性是否发生变化。

它不能保证不同运行输出一致，但能让用户比较输入条件，避免把所有差异都归因于模型“今天状态不好”。

Grok 当前的官方说明中，模型选择由 Cursor 管理，没有面向用户的模型选择器。hctl2 的多 Agency、多 Harness 设计，则把执行来源的选择作为正式能力：可以让不同工具承担施工、评审和其他职责，项目的身份、契约与完成规则仍由自己的控制面保存。[Grok 模型与部署说明](https://docs.x.ai/grok-bot/security)、[hctl2 架构](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/architecture.md)

**第二个优势，是看现场、输入和接管分别有准确的目标与权限。**

hctl2 的连接和输入权绑定具体 Dispatch。旧执行被替代后，旧连接、旧输入与旧结果不能继续代表当前工作；观察某个执行也不自动意味着能控制它。[hctl2 Participant 约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/participant.md)

例如任务已经重试，用户还开着旧终端，系统需要清楚地告诉他：这是旧执行，不能把这里的操作或迟到结果算到新执行上。Grok 的桌面体验更直观，hctl2 在“你正在看谁、控制哪一次运行”上定义得更精细。这两种优点可以结合。

**第三个优势，是能力、写权与判定权明确分离。**

施工者可以编辑获准的 ChangeSet，但不能因为能写代码，就自行签发任务完成或集成凭证；Skill 可以指导工作，但不能给自己增加权限。

这比把所有角色放进一个共享工作环境，更适合多项目、多供应方的受控协作。Grok 文档明确，同账号 Bots 共享电脑上的文件、浏览器会话和命令行凭据，独立屏幕不是隔离边界。[Grok 电脑共享边界](https://docs.x.ai/grok-bot/computer-and-apps)

但不能反过来说 hctl2 已经默认提供完整强沙箱。实际隔离仍要由 Agency 实现并提供证据。它更好的地方，是把“应该具有的能力”和“已经证明具有的能力”分开，不把未知当作满足。

代价是适配、配置和认证更复杂。适合把这些复杂性封装成少量可靠工种；没必要要求用户每次亲自操作全部七层概念。

**5．Repo：hctl2 对“代码究竟交付了没有”的定义更扎实，这是最贴近真实工程的一项优势。**

Grok 的工程实践会检查 PR、CI、截图与评审结果，这些已经很有用。hctl2 则进一步要求把以下关系明确连起来：

> 获准修改的范围 → 封存版本 → 被评审版本 → 获准合入的版本 → 实际目标分支结果。

它通过 ChangeSet、写租约、精确快照、Integration Intent 和回读后的 Receipt 表达这条链。[hctl2 Repo 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/repo.md)

**第一，它减少“审的是 A，合进去的是 B”的机会。**

真实开发中，PR 会反复更新，主干会前进，检查可能针对旧提交，评审通过后也可能又有修改。

hctl2 要求评审与证据对应精确版本；基线或结果树变化，会影响版本身份与旧评审的效力。合入时再次核对待合入对象和条件。

这比简单判断“这个 PR 上存在批准、存在绿色检查”更有意义，因为它关心的是**这些批准和检查是否仍然适用于这次实际交付**。

**第二，它把源分支写入与目标分支合入分开授权。**

Agent 可以在独立工作树里修改、提交，并在获准范围内发布去评审；这不自动赋予它合入目标分支的权力。

这个取舍让用户更容易大胆开放施工：允许 Agent 尝试多种实现、运行测试、提交版本，同时把最终目标更新留在独立的判定链上。**有明确的交付边界，反而可以支持边界内部更大的自主空间。**

**第三，它认真处理“操作可能已经成功，但我没收到回复”。**

假设系统请求平台合并，随后网络超时。此时不能简单认定失败，再随意换一条路径操作；也不能因为发出了请求就宣布成功。

hctl2 规定先持久化集成意图，再执行并回读；结果不明确时保留未知，确认后再签发相应凭证。平台不支持某种并发保证时，也必须按实际能力选择授权形态，不能执行时悄悄降低原先承诺。[hctl2 Repo 集成约束](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/spec/repo.md)

这和上一条批评它的默认值并不冲突：**可以把平台原生策略设得更好用，但已经批准的保证不能在执行时偷偷改变。**

还有一个很实际的优点是成果保全。取消、失败和清理资源，不等于用户愿意丢弃代码；清理前要确认残留修改已有可恢复副本，或者取得明确的丢弃决定。hctl2 当前机械工具已经实现了一部分 worktree、封存保全和本地集成能力，完整治理凭证链则仍待控制面落地。[已实现的机械能力](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/src/README.md)

代价是中间状态更多、版本检查更严格，有时会要求重新评审或等待对账。对于最终要进入共享代码库的工作，这些成本直接换取了交付的可核验性和失败后的可恢复性。

我会给 hctl2 增加一组与上一条“顺畅交付场景”互补的验收场景：**需求在执行中升级；评审后代码再次变化；旧 Worker 失联后又恢复；合并请求超时但平台实际已成功。** 系统需要在这些情况下仍然正确回答：当前承诺是哪一版、谁还有写权、哪些证据有效、结果是否已交付，以及人下一步该做什么。能把这些场景处理清楚，才算把 hctl2 的设计优势兑现成了产品优势。

我还读到一段话，蛮有意思：

机器人缺的是社会性

一群人一起干活，真正让事情办成的从来不是谁最聪明，而是大家都知道什么时候该听谁的、什么时候该让一步。

周末你和几个朋友约好一起做饭。没有人被指定为总指挥，但有人自然地开始洗菜，有人去切肉，有人负责看火。中间盐放多了，站在旁边的人不用谁发指令就顺手加了点水。整个过程中最关键的协调不是来自某个“大脑”，而是每个人对“我们正在一起做一顿饭”这件事的共同理解和随时调整。如果换成一个厨房里有十个互不相识的人，每个人都很会做饭，但没有这种默契，结果很可能是一团糟。

人机协作的实验反复验证了这一点。研究者发现，人类和AI在提供信息上的影响力几乎相同，但人类同伴拥有一层AI不具备的东西，叫做规范性影响，也就是“我在意你怎么看我”这种社会压力。当AI充当队友时，这种规范性影响消失了，人们系统性地低估AI的建议权重。更值得关注的是，即使实验中明确告知参与者谁是专家，AI团队依然倾向于取平均意见而非采纳专家判断，团队越大这种倾向越严重，在知识测试中因此损失了高达四成的准确率。这说明问题不在个体能力，而在协调机制本身。

多机器人系统面临的核心矛盾可以概括为：集中控制高效但不可扩展，分散控制可扩展但效率低下。纯集中式方案在机器人数量增加时急剧退化，且无法在执行中自我纠错；纯分散式方案虽然规避了单点故障，却承受极高的通信开销，一个完全分散的系统在测试中成功率只有百分之二十五，而混合方案达到了百分之八十二点五。新松发布的羿枢系统试图用“集中协同、分布执行”的三级架构来绕过这个问题，但它依然依赖一个大脑层来做全局决策，本质上还是在用中心化方案解决分散式问题。

人类之所以能在大规模群体中实现有效协作，不是因为每个人都足够聪明，而是因为人类发展出了一套共享意向性——能够在“我们”这个层面上构建共同目标，并围绕这个目标自发形成规范和分工。这种能力让人类可以在没有中央指挥的情况下协调数百人甚至数千人的行动。机器人群体的研究也发现，AI agent群体能够自发形成社会规范，但这种涌现是被动的、脆弱的。当前的多机器人系统缺少的不是智能，而是一种主动的、可传承的社会性协调层，它独立于任何单个机器人的能力，也独立于任何中心化的控制指令。

就像一支足球队。每个球员的传球、跑位、射门能力当然重要，但如果没有人教他们“越位了要往回跑”“队友被包夹了要主动接应”这些不写在个人技能表里的规则，十一个能力再强的球员上场也只是一盘散沙。这些规则不控制任何一个球员的具体动作，但它们让所有人在同一套预期下行动，整体的配合才成为可能。机器人群体缺的正是这套“不在说明书上的规则”。

这类似于经济学中的“制度”概念。诺斯认为，制度是社会中博弈的规则，它不直接决定谁赢谁输，但决定了博弈以什么方式进行。一个有效的市场不需要一个中央计划者告诉每个人该生产什么、该买什么，它需要的是一套产权规则、合同法、诚信体系。多机器人系统目前的设计思路过度聚焦于“谁来分配任务”和“任务怎么分配”，而忽略了更底层的问题：机器人之间是否存在一套共享的行为规范，让它们在任务分配之外也能自主协调？制度经济学的启示在于，当博弈者数量增加时，制度的边际成本远低于中央协调的边际成本。机器人群体的扩展性瓶颈，本质上是一个制度供给问题，不是算力问题。

如果你未来要设计或部署多机器人系统，核心工作不是让每个机器人更聪明，而是为机器人群体建立一套内生的协作规范。具体来说：第一，在设计阶段就要为机器人之间的“社会互动”预留接口，而不是只关注任务执行能力；第二，让机器人能够从协作经验中学习和固化有效的互动模式，而不是每次协作都从零开始协商；第三，把人类的协作规范——比如轮流、让步、主动补位——作为设计机器人群体行为时的参照系，而不是把它们当作人类独有的东西排除在外。你不需要教会每个机器人如何完成所有任务，你需要教会它们如何在一起工作。

**明白，你指的是：hctl2 把协作所需的“制度”做成了系统能力，从而减少 Agent 每次靠对话重新协调的成本。这确实应该放在前面比较的第一层。** 我之前主要把它概括成可追溯、可验收、可恢复，漏掉了这些设计共同带来的一个核心收益：**把不需要智能的工作，从模型的推理循环里移出去。**

读完 hctl2 的 research 和愿景后，我会修改之前的判断：**持续跟进不必意味着增加一个持续监工的 Bot；它可以主要由持久状态、事件和确定性规则完成，只在需要判断时调用模型。**

hctl2 的愿景其实已经把这条主线写得很清楚：冻结契约、按来源装配上下文、类型化交接、由代码读取外部事实，都在缩小模型需要搜索和解释的范围；衡量“省”，看的是每份经过核验的交付消耗多少轮次和 token。[hctl2 设计原则](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/vision.md)

**你贴的“制度”类比，恰好解释了为什么这能省。**

一项协作中，有大量问题并不值得每次重新讨论：

- 谁已经获得这项工作的权限？
- 这个结果应该交给谁？
- 下一步的前置条件是否满足？
- 什么算完成？
- 失败后可以重试几次？
- 哪个版本的评审还有效？
- 出现什么情况才需要人介入？

如果这些规则没有稳定载体，就容易变成 PM Bot、工程 Bot、Reviewer Bot 之间反复发送的自然语言。每一次都需要模型读取状态、解释规则、组织语言，再让另一个模型重新理解。

**hctl2 的价值，是把这些重复出现的协作问题预先定义好，让执行时直接检查和执行。** Agent 可以保留理解需求、调查问题、编写代码和专业评审的自主空间。

按这个角度，五个模块的意义可以重新表述：

| 模块 | 由系统承载的协作制度 | 可以省掉的 LLM 劳动 | 仍值得调用 LLM 的部分 |
|---|---|---|---|
| **Room** | 目标、已决事项、来源、正式承诺与讨论的区别；上下文装配规则 | 每次重新读完整聊天、复述共识、猜哪些话已经算决定 | 澄清目标、比较方案、发现尚未解决的矛盾 |
| **Kanban** | Task 契约、状态投影、阻塞条件、完成证据 | PM Bot 反复询问进度、阅读聊天后猜任务是否完成、重复整理机械状态 | 判断新需求的影响、提出优先级或范围调整建议 |
| **Run** | 获准的执行图、前置条件、派发、超时、重试、计票和停止规则 | 协调 Bot 不断决定“现在轮到谁”“是否继续等”“要不要再催一次” | 解决执行中的新问题、理解失败原因、提出需要改变计划的建议 |
| **Participant** | 能力与配置记录、席位职责、权限、精确派工与输入通道 | 每次协商谁负责什么、重复介绍角色、靠对话转发输入和结果 | 专业求解、独立核验、运用不同方法取得新证据 |
| **Repo** | Git 事实、写入租约、版本、检查状态、发布与集成回读 | 让模型盯 PR 状态、口头报告是否合并、凭散文判断检查对应哪个版本 | 理解 diff、修复代码、分析复杂冲突和设计问题 |

这张表描述的是 hctl2 的设计方向及其可省掉的工作，并不意味着 Grok Bot 内部所有这些环节都在使用 LLM。

**一个例子就能说明，为什么我前面推荐“长期负责人”的方式需要调整。**

设想一条 PR 正在等 CI。用模型承担日常协调，可能是：

> 定时唤醒负责人 → 读任务与历史 → 查询 CI → 解释还没结束 → 更新进度 → 下次重新来一遍。

同样的用户体验，可以主要由代码实现：

1. 订阅 CI 事件，或由普通程序轮询。
2. 状态没变化，就继续等待，不调用 LLM。
3. 全部检查通过，按已批准规则进入下一步。
4. 检查失败，收集对应版本的失败证据。
5. 只有需要诊断和修改时，才调用执行者。
6. 结果返回后，由代码更新状态、核对预算和决定是否允许继续。

用户仍然得到“我离开以后，事情有人跟进”的体验，但后台不必一直有一个模型在读日志、写进度散文。

而且消耗不只是生成那几句交接话：还有接收者读取它们的输入、后续上下文中的重复携带，以及额外调用带来的等待。具体计费受缓存等机制影响，但减少无信息增量的轮次，仍然是明确的优化方向。

**所以，长期存在的应该首先是责任记录和执行状态；模型可以按需被唤醒。** 一个长期角色可以有稳定职责、方法和工作材料，不必持续以 LLM 调用的形式运行。

这里还有一个容易混淆的地方：**让模型输出 JSON，并不等于把协调机械化了。** 如果每次“下一步给谁”“是否完成”仍由模型重新推理，只是把回答格式变成 JSON，主要成本仍然存在。真正移出推理循环，是代码直接依据已记录事实和规则作出这些决定。

**hctl2 的 research 支持这个方向，但“多 Agent 对话不能提升完成度”需要稍微收窄。**

更准确的结论是：

> **多 Agent 相互阅读、讨论和趋同，并没有稳定证明比独立求解与聚合更划算；增加通信本身，不能被当作质量提升的依据。**

例如，*Debate or Vote* 发现，在其测试的基准中，多数投票已经解释了通常归功于辩论的大部分收益；*The Cost of Consensus* 的主实验中，辩论比独立自我修正后的聚合消耗更多 token，却没有取得相应的准确率收益。后者也包含辩论有收益的配置，因此不能推广成所有模型、任务和协作形式都无效。[Debate or Vote](https://arxiv.org/abs/2508.17536)、[The Cost of Consensus](https://arxiv.org/abs/2605.00914)

**有明确分工、不同信息来源、外部工具反馈或独立核验的多个执行者，仍然可能值得使用。** 要审查的是新增通信到底带来了什么，而不是仅凭 Agent 数量决定好坏。hctl2 的研究本身也明确区分了这些情况，并承认部分建议来自其他任务基准的外推，尚不是代码评审的直接实证。[hctl2 多 Agent 有效性研究](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/research/multi-agent-effectiveness-20260908.md)

**你贴的文章还有一个很有用的启发：共同规则可以独立于单个参与者存在。**

这和 hctl2 很接近。换一个 Harness、换一个模型、重启一个进程，承诺、权限、交付义务和验收规则仍然存在。参与者加入工作时，接受这套制度即可，不必重新和其他参与者商量一遍整个协作方式。

不过，hctl2 与文中“内生社会性”的主张也有区别：

- hctl2 主要依靠人定义、控制面执行的制度，尚不能称为 Agent 自发学习和形成规范的系统。
- hctl2 仍有中心化的语义控制面。**中心化的确定性状态机，与中心化的 LLM 调度员，成本结构很不一样。** 不能把文章中对某些集中式机器人方案的结论，直接套到它身上。
- 文章混合了人机团队、LLM 团队和物理机器人研究。制度的类比可以借鉴，其中的实验数字不能直接证明 hctl2 一定优于 Grok Bot。

对 hctl2 而言，完全可以先通过明确接口、稳定状态和可执行规则，获得一部分“默契”的效果，而不用让模型模拟“在意同伴评价”“互相让步”这些社会过程。

这也改变了从 Grok Bot 学什么的优先级：

**值得学的是持续委托的体验、运行现场的可见性、接管后继续、结果容易检查；协调层则应优先采用事件和规则。** 只有遇到新信息、语义歧义或现有规则无法处理的问题时，才升级为模型协商。

最后，“省”也应该反过来约束 hctl2 自己。额外的计划读回、多个评审席位、反复全文重评，都需要证明它们带来了足够的收益。不能因为它们被写进正式规范，就免于成本审查。hctl2 已经要求统计失败、备用、返工、读回等全部消耗，这个方向是对的。[hctl2 Run 的成本度量](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/run.md)

我会把产品验收标准写成：**在保持验收质量的前提下，降低每份合格交付的总 token，并同时记录耗时和人工介入。每新增一轮模型调用，都要说明它带来了什么新信息、证据或必要判断；只是搬运状态、重复规则、维持对话的部分，应交给代码或直接删掉。**

--------------------------------------

还有个有趣的地方 - grokbot的产品立足点貌似是“数字伙伴”（因此可以跨越项目）而非“任务本身”（所以每次重新挑人） - 这个和hctl也是本质的不同。

--------------------------------------

**是，这个区别比“有没有群聊、看板或桌面”更根本：两者选择了不同的长期主体。Grok Bot 让“伙伴”持续存在，工作围绕伙伴展开；hctl2 让“项目与承诺”持续存在，再为它们选入合适的执行者。**

我会把你说的“任务本身”稍微扩展成“项目与承诺”，因为 hctl2 并非每次完成任务就结束一切。它的 Room、项目知识、决策和来源也长期存在。区别在于：**连续性主要放在人身上，还是放在事情及其制度上。**

Grok 的官方设计文章对此非常明确：产品从聊天历史转向 Bot 名册，希望用户明天回来面对的仍是同一个 Bot；它的定义包含稳定的身份、职责和不断积累的工作上下文。[Grok Bot 设计文章](https://x.ai/news/designing-grok-bot)、[Bot 定义](https://docs.x.ai/grok-bot/bots)

hctl2 则明确要求：即使所有 Harness、会话和工作树都被替换，Project 的目标、论证、来源和未决问题仍然存在。Participant 是选入某个 Room 或 Run 席位的记录，规划与施工分别选人。[hctl2 Project 设计](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/project.md)、[Participant 定义](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/docs/design/participant.md)

| 比较点 | Grok Bot：伙伴作为长期主体 | hctl2：项目与承诺作为长期主体 |
|---|---|---|
| 用户首先想到什么 | “这件事找谁帮我？” | “这件事要交付什么，需要什么能力？” |
| 什么跨任务延续 | 角色身份、工作偏好、经验与持续职责 | 项目目标、契约、知识、证据和执行历史 |
| 新工作怎样开始 | 把新事情交给熟悉的伙伴 | 根据本次工作要求选入参与者并授权 |
| 复用的主要对象 | 同一个 Bot 及其工作关系 | 工种、Skill、执行配置、项目材料与流程 |
| 更换执行者意味着什么 | 用户可能需要重新建立配合、补充角色经验 | 项目制度保持，替换负责履约的执行资源 |
| 跨项目工作的自然程度 | 同一个伙伴可以参与多件事 | 复用能力，但在新的项目范围内重新任用 |
| 用户主要积累什么 | “谁了解我、谁擅长什么、我愿意把什么交给他” | “这件事为什么做、怎样做、依据什么判断已经做完” |

这里“重新挑人”也不等于每个 Task、每个步骤都从头配置，更不等于重新冷启动全部上下文。hctl2 可以复用工种、配置和 Skill，同一 Room 中的参与者也能被多次调用；它坚持的是**本次任用有自己的范围和资格，不能仅凭同名角色就继承另一处的权力**。

**这会产生两种不同的委托关系。**

在 Grok 的产品逻辑里，用户可以说：

> 你一直负责我的前端工作。这个项目结束了，下一个项目还找你，你应该越来越了解我的习惯。

角色关系先存在，项目是一项项交给它的工作。跨项目不是额外扩展，而是这种定位自然带来的结果。

在 hctl2 的逻辑里，用户更接近于说：

> 这个项目需要前端施工和独立评审。根据要求选人，给他们必要材料，按契约交付；下个项目可以重新选择更合适的组合。

项目先存在，参与者因任用而进入。更换工具或模型，是系统应该容易承受的正常变化。

因此，**同一个名字在 Grok 中表达关系连续性，在 hctl2 中主要是本次任用的显示标签。** 这确实不是简单调整侧栏就能完全抹平的差异。

**但它和前面讨论的“省”，是两条可以分开的轴。**

一条轴是：产品围绕伙伴，还是围绕项目。

另一条轴是：协作主要靠模型临场对话，还是靠确定性规则推进。

长期伙伴完全可以只在有工作时唤醒，平时由事件和状态机维持职责；项目制系统也可能因为每次重复组装材料、解释背景而浪费 token。所以：

- **伙伴长期存在，不必持续消耗推理成本。**
- **每次重新任用，也不自动意味着更省。**
- **人设、记忆、权限和运行实例，不必绑定成同一个生命周期。**

这也是我需要修正前面建议的地方。我之前把“缺少跨项目长期负责人”较多地当作 hctl2 值得补齐的产品缺口。现在看，**它首先是定位选择，不能直接视为缺陷。**

如果 hctl2 的目标是让开发者持续使用最合适的 Harness，以更少的无效推理完成可核验的工作，那么把项目事实保存在执行者之外、允许按要求重新选人，是合理的。强行把它改成“经营一支越来越懂你的数字员工团队”，反而可能引入另一套产品负担：角色记忆维护、跨项目经验筛选、职责重叠，以及对某个伙伴的路径依赖。

反过来，如果用户购买的主要价值就是“有一个长期了解我、跨越各种事情帮我工作的伙伴”，那么项目制的重新任用与显式材料交付，确实会显得生硬。Grok 在这类需求上的优势不能仅用 token 成本来评价；减少重复解释和重新建立配合，本身就有价值。

**“制度”与“伙伴”也可以同时存在，只是要决定哪一个拥有最终权威。**

hctl2 可以提供收藏的参与者、常用阵容、可复用的工作偏好，甚至一个跨项目的伙伴入口。用户仍然可以说“这件事继续交给 Jack”。后台把这个意图解析为一次新的任用，明确本次材料、权限和预算；项目契约与完成证据继续属于项目。

这样，用户可以保留熟悉感，系统也不必让“Jack 记得什么、Jack 觉得完成了没有”成为项目事实的最终来源。

对 hctl2，我会优先做**低成本复用熟悉的执行能力**，而不急着把数字伙伴升级为整个产品的组织中心：选人可以预填，方法可以复用，偏好可以按范围带入；每次具体任用和交付仍然清楚。是否再提供完整的伙伴式体验，应由“跨项目关系本身是不是用户要购买的主要价值”来决定。

--------------------------------------

“制度”与“伙伴”是可以同时存在的。事实上，在HCTL2的研究/讨论中，专门有一章“TAMP模型”，就是为了在未来、通过在实践中不断获得检验的“能力模型”，Agency的“工种模板”逐渐获得了相对比较稳定的能力评价 - 因此，主动“选伙伴”的过程就可以进一步被优化为被动“被推荐伙伴”的discovery/recommendation过程：能力相似度相当于relevance召回，按需求/供给的$做最后的精排（fine-ranking）。
这样，我们既有机械化mechanical的“制度”，又有高度匹配需求的“伙伴” - 有一点还是保持了 - HCTL的core依然是“项目与承诺”。

--------------------------------------

**这个补充纠正了我上一条的局限：HCTL2 不需要把产品中心移到“伙伴”，也能持续积累对伙伴的了解，并逐步自动完成选人。** 我之前把它能做的事情收窄成“收藏常用参与者、复用配置”，没有充分考虑 TAMP 已经提出的能力测量和供需匹配机制。

我找到了 [TAMP 设计稿](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/.memo/notes/TAMP-design-doc.md)和[配套架构评审](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/.memo/notes/tamp-review-20260905a.md)。它们仍是讨论与演进材料，与你说的“未来通过实践逐渐形成”一致；其中的原则“先分析工作，再谈人”，正好说明了为什么有推荐伙伴的能力，也不改变 HCTL 的核心。

**这里实际有三种不同的长期积累，可以同时存在：**

| 长期积累 | 回答什么 | 在你描述的 HCTL2 中 |
|---|---|---|
| 项目与承诺 | 要做什么，为什么，怎样算完成 | 仍是产品与治理的核心 |
| 能力与履约记录 | 谁在什么条件下擅长什么，表现多稳定，实际成本如何 | 随实践积累，为工种模板及其具体配置提供评价依据 |
| 匹配经验 | 什么样的需求，交给什么供给，结果更好 | 改进 discovery／recommendation，减少人工选型 |

所以，**“按任务重新任用”完全可以是后台语义；“推荐已经验证过的合适伙伴”则是前台体验。** 用户不必每次从一张陌生名册里重新选人，系统也不必默认把所有新工作都交给同一个熟悉的 Bot。

这使 Grok Bot 与 HCTL2 的区别更准确地落在了**匹配从哪里出发**：

- Grok Bot 的产品重心是已有的伙伴关系：把新工作交给持续存在的角色。
- HCTL2／TAMP 从本次项目需求出发：发现合适的供给，其中当然可以包括用户已经熟悉、表现稳定的伙伴。

长期伙伴可以成为推荐结果，但不必成为所有项目事实的组织中心。

**你用“relevance 召回＋供需的 `$` 精排”来描述这个过程，抓住了它的推荐与撮合性质。** TAMP 把它进一步展开成四段：

| 阶段 | 要回答的问题 | 主要依据 |
|---|---|---|
| **Recall：召回** | 哪些候选可能适合？ | 能力相似度、技能索引、相似任务的历史表现、当前环境与负载 |
| **Gate：可行性过滤** | 它是否真的具备接这项工作的条件？ | 能力门槛、工具、权限、必要上下文、时间窗口、做审分离 |
| **Rank：排序** | 合格候选中，哪个组合更符合本次需求？ | 能力缺口覆盖、供给方约束、预期成本、时延、负载等 |
| **Award：任用** | 本次最终交给谁，以什么条件执行？ | 人或获准策略作出的选择，并进入正式授权 |

[TAMP 第 11 章](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/.memo/notes/TAMP-design-doc.md#11-匹配与调度)明确区分了召回相似度与最终匹配，并要求排序能够解释具体覆盖了哪些需求、受到哪些条件限制。

这里的 `$`，我会理解成**达到本次交付要求的经济性**。报价很重要，但需要结合实际成功率、返工成本、开始时间和交接成本来看。一个报价低、却经常需要额外三轮修正的供给，未必更省；一个能力更强但明显超出任务需要的供给，也未必值得选。价格排序应在可行候选中进行，不能买掉权限限制或必要的评审隔离。

**更关键的是，能力评价的积累，让“信任伙伴”有了可复用的依据。**

这不只是给工种模板贴一个“高级前端工程师”的标签，而是逐渐形成这样的认识：

> 这个模板对应的某个模型、Harness、工具和权限配置，在这类任务上经过多少次验证；通常能达到什么结果，花多少成本；哪些条件下容易失败。

TAMP 为此区分声明、背书、实测、独立验证，并按任务族维护校准信息。它也要求配置变化后重新看待历史成绩：更换模型、工具、提示或权限，旧成绩可以作为先验，但不能把旧版本的确定性原样继承过来。[TAMP 能力证据与更新机制](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/.memo/notes/TAMP-design-doc.md#10-证据层级绩效通道与能力更新)

落到 HCTL2，评价需要关联**工种模板、实际执行配置版本、任务类型和执行条件**。一次 Participant 的成功可以贡献证据，但不能直接证明整个工种在所有任务上都同样可靠。

这也接上了前面关于“制度”和“省”的讨论：

**制度产生可比较的执行记录；记录支持能力校准；能力校准改善推荐；推荐减少试错、重复选人和无效协调。**

这样，hctl2 那些精确的任务版本、执行记录、验收与成本信息，就不仅用于事后追溯，也成为下一次分配工作的输入。伙伴可以越用越合适，而这种改善不必主要依赖反复聊天来维持。

不过，这套推荐本身也要遵守“省”的原则。配套评审专门指出了“测量税”和撮合延迟：如果每次小任务都让多个模型介绍自己、竞标、互评，再请模型选赢家，就会把刚省掉的协调成本重新加回来。它建议常规任务先用静态规则和已有评价匹配，复杂任务或异常重配时才引入更重的机制。[TAMP 架构评审](https://github.com/yesme/hctl2/blob/e0cc1eedaf12fd80c9cffff7a2926e062757ef72/.memo/notes/tamp-review-20260905a.md)

这里“机械化”也允许使用检索模型或经过训练的排序模型。关键在于：**依据已经形成的画像和规则计算推荐，避免每次通过多轮生成式对话重新协商同一类问题。**

对架构而言，我会保留 TAMP 评审稿中的这个边界：**它作为 Participant 选型与 Agency 供给匹配的能力存在，需求画像从现有项目、任务契约和上下文中生成；它不再建立另一套 Task／Run。** 推荐回答“谁更适合履行这份承诺”，HCTL core 继续决定承诺是什么、授予哪些权力、依据什么验收。这样，伙伴的发现和匹配可以越来越自动化，项目与承诺仍然是整个系统的出发点。

--------------------------------------

有时候觉得，hctl2是一个价值观、方法论皆非常明确的方案的，唯一最大的问题是 - 想了很多、也非常贴近现实没有胡想瞎想，但依然是代码/实现不足、仍未开发完成。“批判的武器不能替代武器的批判”。

--------------------------------------

我同意。**hctl2 现在最缺的，是一组由真实运行产生、能够反复复现的交付结果。** 价值观、方法论和设计已经足够明确，可以用来指导实现；接下来需要实现反过来检验这些判断。

而且，“实现不足”不只是交付进度的问题。它意味着我们前面讨论的几项优势，还没有完全从设计判断变成产品事实：

- 确定性编排在结构上减少了 LLM 协调，但完整流程的上下文准备、读回、评审和返工，最终是否真的更省？
- 契约与证据让完成定义更清楚，但用户能否轻松完成一次真实工作，而不绕开系统？
- 模块边界与恢复规则写得明确，但进程失联、平台超时、版本变化同时发生时，实现能否守住这些规则？

**这些问题继续读论文、完善规范，只能提供更好的假设；答案要从运行中产生。** 所以前面说“hctl2 在某些方面优于 Grok Bot”，严格说是架构与方法论上的判断，还不能直接兑换成产品层面的胜出。

我觉得 hctl2 的明确性，到了这个阶段应该产生一个实际效果：**让下一步的选择变少。** 已经知道哪些事实必须由代码掌握，哪些判断值得调用模型，哪些权力不能交给执行者，就可以据此把一条路径做通。无需等所有未来能力——尤其是 TAMP、开放 Agency 供给、复杂组队——都具备，才开始证明核心价值。

最有说服力的对象，就是 hctl2 自己的一次真实开发变更：从明确交付要求开始，调用执行者，取得测试和评审证据，处理一次返工，最终合入并完成验收。入口可以先朴素，但中间不能靠维护者在终端、聊天和数据库之间偷偷补操作。

这里的“做通”也不只是成功演示一次。它要能重复承受普通开发中那些不漂亮的情况：检查失败、评审要求修改、主干前移、执行中断。否则跑通的可能只是演示脚本，还没有证明那套制度能够承担日常工作。

我会用三个非常直接的问题评价这个阶段：

1. **是否比直接操作 Harness 更省事？** 人有没有少搬运上下文、少盯状态、少做重复派单。
2. **是否在同等验收要求下更省 token？** 把失败、返工、读回、评审和协调全部算进去。
3. **出了问题以后，是否更容易继续？** 能否保住成果、明确当前状态，并给出准确的下一步。

这三个问题也会反过来裁剪设计。某条规则确实拦住了错误，就有了保留它的实证；某个步骤反复消耗成本，却没有改变任何结果，就应该重新检查；某种抽象在实际接入中总需要例外，说明边界可能还要调整。**实现过程不仅兑现设计，也会发现哪些设计不值得兑现。**

所以，“想得很多”本身不必被否定。这些研究已经让 hctl2 少走了一些明显的弯路，也提供了评价实现的尺子。但研究的收益需要通过交付才能兑现；继续增加设计深度，未必还是当前收益最高的投入。

你引用的那句话放在这里很贴切。对 Grok Bot 等产品最有力的回应，会是一条这样的记录：**同样一项工作，hctl2 用更少的无效推理完成了，验收没有放松，发生故障后也没有把协调劳动重新交还给人。** 下一阶段最值得积累的材料，就是这样的真实任务、成本账、失败记录和完成凭证。
