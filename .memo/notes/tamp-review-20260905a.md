---

## 一、 同层裁决与定位

> **定位**：TAMP 落在 HCTL2 架构中 **Participant（参与者）模块的能力决策层** 与 **Agency（派出方）供给侧的撮合编排层**。它回答的核心问题是：在 Run 铸造 Seat、或 Project 邀请协作者时，面对多个候选 Participant（人类、不同模型/Harness 组合、技能包），依据什么标准、函数与协议完成选人与组队。
>
> **裁决**：**设计成立，且理论厚度与工程洞察极深。** 说明书将传统工业与组织心理学（SFIA / e-CF / 岗位分析 / 冰山模型）与 AI Harness 运行时（KSAO-X、执行包络、四级证据、校准卡、做/审分离、合同网）进行了工业级焊接。它精准击中了多智能体协作中“把匹配简化为向量余弦”、“把声明当能力”、“LLM 自评严重失真”等核心死穴。

---

## 二、 核心亮点与理论突破

### 1. 三层词典设计（L0 情境 / L1 对外受控词表 / L2 调度叶子）
消解了“通用标准词表（如 SFIA）太粗无法驱动底层代码调度，私有自造叶子太细无法对人与外部解释”的两难：
- **L0（Cynefin / Bloom）** 决定认知与情境策略（简单问题规则走完，复杂问题预留探索预算，混沌问题先跑止血 runbook）；
- **L1（SFIA / e-CF）** 决定人机共用坐标系与对外沟通；
- **L2（带行为锚点的调度叶子）** 决定精确撮合。每条 L2 必须映射至 L1，结构整密。

### 2. 四段式匹配流水线（Recall → Gate → Rank → Award）
坚决否定了“用向量余弦相似度直接完成成交”的流行做法：
- **Recall（召回）**：允许使用向量余弦、协同过滤、倒排索引做宽口径召回；
- **Gate（门控）**：权限、工具、上下文、数据驻留、做/审隔离的硬性 0/1 过滤；
- **Rank（排序）**：按缺口覆盖度 $S_{cap}$ 与参与者供给满足度 $S_{need}$ 进行双向拟合；
- **Award（授标）**：多目标帕累托前沿展示，人工或策略最终授标。

### 3. 直击数字员工死穴：“四级证据”与“校准卡”
- **声明不等于证据**（Declared → Attested → Measured → Verified）：公共 Benchmark（如 SWE-bench）被冷酷归为 Attested 先验，高风险任务（R2/R3）严禁依赖未测量的自报能力成交；
- **校准卡机制**：指出了 LLM 在 Contract Net 招标中往往“严重过度自信且成本预估不准”，强制在投标出价前经过校准卡折减（$\hat{p}_{\text{eff}} = \mathrm{recalibrate}(\hat{p}_{\text{self}})$），这是解决市场机制在 Agent 领域失效的关键补丁。

### 4. KSAO-X 执行包络与版本化身份
不仅将冰山模型中不可测的“动机/价值观”务实地替换为可观测行为（如约束遵守、抢权倾向、过度自信），还补充了数字伙伴特有的 **X（执行包络：工具集、权限、上下文预算、验证器）**。同时确立 **“改工具/Prompt/权限即升版本”**，旧战绩只作收缩先验，防止换皮继承虚高声誉。

## 三、 潜在瑕疵与工程落地风险（必须警惕的陷阱）

这份设计格局宏大、推演周全，但在向 HCTL2 落地工程化时，存在以下 4 个必须克制的过载点：

### 1. 警惕“评测税 / 测量税”吞噬系统吞吐
- **问题**：设计中包含了极度精细的动态测量（探针、四层轨迹评估、多通道回写、ECE/Brier 校准、EMA 更新协方差 $\sigma$）。
- **风险**：在日常软件开发中，如果要为一个几百行的代码补丁跑完一整套完整的十维 Task Card 标注、多目标帕累托求解、探针评估与 ECE 计算，**运行这套撮合与评估系统自身的 Token 消耗与串行时延，很可能会超过完成任务本身的成本**。
- **建议**：坚持文档 §22 阶段 A 原则（极简冷启动）。前中期只使用静态规则门控 + 启发式缺口计算，严禁过早引入动态连续学习模型与复杂的非线性拟合。

### 2. 与 HCTL2 既有领域模型的对齐与边界收束
- **问题**：TAMP 作为一个独立设计，包含了自身的 `TaskCard`、`TaskGraph`、`HandoffEnvelope`、`Run`、`MatchDecision` 等全套对象。
- **风险**：容易与 HCTL2 现有的四模块骨架产生概念竞争（HCTL2 的 Task 是承诺层的不可变 Task Revision，Run 是施工图治理，Participant 是执行主体）。
- **建议**：
  - **TAMP 不能成为平行的第二套任务与工作流引擎**，它必须定界为 **HCTL2 Participant 模块内部的“组队选型策略插件”**；
  - Task Card 应当从 HCTL2 的 `Task Revision + Context Bundle` 中投影生成，而不是让用户填两套表单；
  - HandoffEnvelope 则直接对应 HCTL2 的 Seat 接力与 ChangeSet 提交凭证。

### 3. 谨防 HR 式考核机制在代码协作网络中产生异味
- **问题**：文档全盘吸纳了 360 同行互评、KPI（按时率/返工率）、OKR 目标贡献等传统企业 HR 工具。
- **风险**：虽然声称“信度加权、防止单 KPI 暴政”，但在 Agent 与人混合的代码网络中，复杂的互评极易引发博弈（例如：同厂商模型家族互相刷好评、Agent 为保按时率拒接棘手的复杂 Refactor 任务）。
- **建议**：在初期阶段，**坚决裁剪 360/KPI/OKR 这类主观与宏观通道**，只保留最硬的三个事实通道：**确定性测试与 Lint 结果、实际 Diff 采纳率（Handoff 成功）、以及人类 Reviewer 的 Explicit Verdict**。

### 4. 合同网拍卖与联盟生成的实时延迟
- **问题**：Contract Net 的 Announce → Bid → Award 涉及多轮往返与竞价。
- **风险**：大部分 SDLC 任务在工程上具备很高的确定性（例如编写契约测试、更新依赖）。如果每次任务派发都拉起多模型异步竞标，会导致严重的交互等待。
- **建议**：确立“两档派发”——常规任务走**确定性静态规则匹配（毫秒级）**；只有处于 Cynefin Complex 域、多重技能缺口或发生异常重配时，才激活轻量 Contract Net 协作。

## 四、 对 HCTL2 的演进建议（分阶段落地）

1. **短期（P1/P2 阶段 · 保持克制）**：
   - 将 TAMP 作为 `.memo/notes/` 的长期指导底稿；
   - 在 HCTL2 的 Participant 模块中，先实现最硬核的子集：**执行包络 X（工具/权限/模型版本）的静态定义** 与 **做/审分离门控（R0-R3 规则）**；
   - 绝不在 P1/P2 期间扩充复杂的技能云数据库。
2. **中期（B2 自举后 · 引入 L2 叶子与校准卡）**：
   - 提取 10~15 个 SDLC 核心调度叶子（ADR、最小补丁、契约测试、威胁建模）；
   - 为常用模型（Codex, Claude, Grok, GLM, DeepSeek 等）建立初步的校准卡（记录自报 vs 实际通过率），避免盲目使用单一“最强模型”。
3. **长期（多 Agent 自治编排）**：
   - 逐步开放联盟形成与双向拟合成交，完整释放 TAMP 的动态组队潜力。
