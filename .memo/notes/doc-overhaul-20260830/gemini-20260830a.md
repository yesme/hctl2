## 二、 为什么选 Fable 起草方案，而不是 GPT？

结合全库各 harness 提交的讨论备忘（`claude-20260830a.md`、`codex-20260830a.md`、`glm-20260830a.md`、`grok-20260830a.md`、`kimi-20260830a/b.md`）的交叉分析，核心理由如下：

### 1. 任务性质匹配度：开工方案是“大局观”任务
大修目标的前两项是**“去除死文”**与**“收束集群（回到 big picture、看内容结构与文件结构找可整合/跨域同构合并）”**。
- **Fable 的强项**：擅长愿景理解、架构意识与顶层叙事结构，能站在全系统视角拉平 4 模块 × 3 面架构的全局表达。
- **GPT 的已知短板**：抓细节失大局、容易钻牛角尖。若让 GPT 从空白页主导目标结构，容易将现有复杂度重新组织成另一套复杂度（如 Codex 本次起草的开工手册已达 352 行，体现了其在流程规则上的“过度完备与叠床架屋”偏好）。

### 2. 切断历史失败回路：“大局与细节解耦，审修单向流动”
各家共同指出的核心病因：历史上的 5~6 轮空转是因为让 **Fable 写正文 → GPT 挑错 → Fable 改不全**。
- **正解**：
  - **Fable 管“目标长什么样”（只出骨架表与判据，拍板后冻结，不碰正文）**；
  - **GPT 管“逐字写对”（在冻结的骨架与白名单笼子里执行改写，唯一主笔）**；
  - 评审发现的细节问题由 **GPT 自己改**，绝不把 nit 扔回给 Fable。

## 三、 给 Fable 起草开工方案的“硬笼子”

为防止 Fable 发作“细节写不对”的毛病，对其起草方案的任务作如下硬约束：

1. **只传表，不传散文**：
   - 产出必须是清晰的**目标文件树**与**逐文件动作清单**（保留 / 归档 / 合并 / 拆分 / 删）；
   - 明确列出**跨域同构合并映射**（如三条底线、E2EE 不启用等在多处复述的收拢点）；
   - 明确**「一定不要」负面清单的三留判据**（特别容易犯 / 特别 tricky / 不可机械覆盖，三者居一才留）。
2. **零正文修改**：
   - 方案阶段不修改 `docs/design/` 下的任何文字。
3. **消费现有证据，不重新调研**：
   - 直接消费已有的债务台账（`doc-cleanup-backlog-20260825.md`、各 harness 的 v0.15.0 评述与死人清单）。

## 四、 全局开工协作链条建议

| 阶段 | 负责人 | 核心动作 | 产出 / 闸门 |
| :--- | :--- | :--- | :--- |
| **阶段 0 · 方案起草** | **Fable-5 (xhigh)** | 起草开工方案表：目标文件树、跨域合并映射、死文与负例判据、行数预算（**零散文修改**） | 方案讨论稿（`.memo/design/`） |
| **阶段 1 · 事实普查** | **K3 / Grok / GLM** | 机械盘点带行号的死人清单（agentd/tmux 等）、断链、版本戳、禁令清单 | 事实核对表 |
| **阶段 2 · 方向锁死** | **所有者 (Human)** | 审阅并增删 amend 目标结构与判据 | **冻结的大修宪章与文件树** |
