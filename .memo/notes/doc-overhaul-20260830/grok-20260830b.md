# 开工方案由谁起草：Fable，不是 GPT

> 状态：讨论中<br>
> 基线：main @ 240cdfb（草案 v0.15.0）<br>
> 去向：无（过程记录，不进合同）；拍板后化为 Fable 的阶段 0 任务卡<br>
> 日期：2026-08-30<br>
> 说明：Informative。所有者问：读完本目录各家开工方法论与安排表之后，整个开工方案由 gpt-5.6-sol (xhigh) 还是 fable-5 (xhigh) 起草。本文是 Grok 的独立判断。读过：`claude` / `codex` / `glm` / `grok-a` / `kimi-a` / `kimi-b`。

## 裁决

**由 Fable 起草整个开工方案，不要让 GPT 来写。**

「开工方案」就是结构权：目标树、逐文件动作、判据、顺序、闸口。六份备忘里，GPT 的已知病正好是**一拥有结构决定权就叠床架屋**。把方案交给它，等于在过程层重演 v0.12。

本目录当时**没有 Fable 自己的稿**。缺的不是第七份方法论，是一张可拍板的目标树 + 方案表。这正是 Fable 该交的作业。

Codex 那句「如果只能选一个主笔，选 GPT」说的是**改库**，不是写开工方案。它自己这份手册已经露出 GPT 起草方案的形状：九个阶段、十二条机械检查，还把 Herdr writer gate、`hctl2-tool` 范围、macOS 15 三条**语义待裁决**塞进文档大修。完整、自洽，也过重。方案若由 GPT 写，大概率再长一截。

Fable 的病是细节写不对、按 nit 单改不全。所以它写方案时必须被关进「只出表」：文件 | 动作 | 理由 | 要不要拍板。不许写最终段落。Claude 把这点说死了，其余几家也同意。

## 怎么开（仍是 Fable 执笔，不是 GPT 代写）

1. **输入已经够，不许从零发现。** 种子是：Kimi b 的判据/范围/行数预算、Claude 的三组同构与死文候选、Grok-a / GLM 的死人现在时、`doc-cleanup-backlog` 13 条、v0.15 各评审。Fable 消费它们，不另开调研。
2. **Fable 交一份方案，不是又一份方法论。** 必须有：目标文件树、旧→新迁移/动作表、删除·归档·禁令三条判据（可直接收 Kimi b / Claude 已写的）、施工顺序与闸口、DoD。一件事要在方案里拍死：一个大 PR（Codex / Kimi）还是按簇多 PR（GLM / Claude / Grok-a）——这是结构选择，归 Fable + 所有者，不归 GPT。
3. **GPT 只审方案，不重写方案。** 只答：漏了哪些现行文件、把历史当成现在、把未决写成必做。发现列成表，所有者一次接受/拒绝。不要「GPT 挑错 → Fable 改方案」循环；Fable 不当 nit 修补工，这条对方案稿同样生效。
4. **拍板后 GPT 才碰 `docs/design/`。** 方案之外的动作登记，不原地补。

一句话：**刀法归 Fable，刀工归 GPT。** 开工方案是刀法，所以是 Fable。
