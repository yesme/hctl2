## 这件事是什么、不是什么

所有者给出的四项目标：

1. **去除死文** — 演化留下的过时内容，该删删、该进 archive 进 archive。
2. **收束集群** — 回到 big picture，看内容结构与文件结构：能整合的整合，能拆进目录的拆，跨域同构能合并的合并。
3. **删繁为简** — 正确的路只有一条，错误的 case 无穷无尽。罗列「一定不要」必须非常谨慎：只留下「特别容易犯的错」和「特别 tricky 的错」；能被测试/类型/fail-closed 机械挡住的，不要靠 LLM 记禁令。
4. **严丝合缝** — 全面大修，前后一致，文档整体性高。

这不是再开一轮架构、不是 v0.16、不是把 [v0.15.0 评述](../review/20260830-v0.15.0/grok-20260830a.md) 里「冻结架构、去做 P1/B2」作废。产品施工主线仍是 P1 工具箱 → B2 无 Run 切片。本次只修**文档作为文档**：死人、目录、禁令密度、交叉一致性。不新增具名对象，不重开 v0.13–v0.15 已拍裁决。

## 两个模型的已知失败模式

所有者经验（本仓库已发生过对应事实）：

| 模型 | 强 | 败 |
| --- | --- | --- |
| gpt-5.6-sol (xhigh) | 逻辑缜密、交叉引用、唯一写入者、前后一致 | 抓细节没大局；在一两个死角叠床架屋；v0.12 缺口审计一次塞进五项机制、后来撤回两项即此类 |
| fable-5 (xhigh) | 愿景、协作、架构意识、正确道路的正面叙述 | 细节写不对；GPT 挑错后它改不全/改不对，往复 5、6 次，最后只好挑错的人自己改。v0.8 精简方向对、writer/恢复被删过猛，也是这类 |

因此：**不要再走「Fable 写全文 → GPT 挑错 → Fable 按 nit 单改」**。那正是会再空转 5、6 轮的形状。Fable 不当 nit 的修补工；GPT 不当目录的作者。

Grok-4.6 (xhigh)、K3 (high)、GLM-5.3 (max) 不当第三套主笔。各有一块窄活，见下。Grok 自己也被批过用禁令清单代替正面道路，故只当闸，不再写愿景。

## 施工宪法（拍板后谁都不能破）

半页，开工前由所有者锁死：

- 不新增具名对象、不新增 CT 族、不把未决项立法。
- 决策史只归档、不重写论证；现在时与过去时分开。
- 「不得」默认删。留下的必须能标成「特别好犯」或「特别 tricky」；否则改成正面道路，或指到已有 CT / 类型系统 / fail-closed。
- 审计最多两轮。第二轮如果主要在打第一轮新造的句子，回滚那批句子，不继续补。
- 发现若需要改目录或加概念，进停车位，本轮不做。
- 未拍板之前，任何模型不得直接改 `docs/design/`。

## 分工：两段锁死，换手不换题

不对称是有效的，包圆是无效的：

1. **Fable 有结构权，没有修补权。** 设计层初稿的事实错误由 GPT 直接改，不交回 Fable。
2. **GPT 有合同权，没有目录权。** 想拆文件、想加对象，只能进停车位。
3. **Grok 当闸，不当作者。** 只许答：通过 / 回滚哪几句 / 进停车位。
4. **K3 / GLM 当扫描仪，不当设计师。** 死人、断链、版本戳、实现名泄漏。

| 层 | 主笔 | 原因 |
| --- | --- | --- |
| 死人清单、断链、版本戳 | **K3** 出表，GLM 可复扫 | 机械、高召回；不要模型「判断该不该留」 |
| 目标文件树、合并/拆分/归档 | **Fable** 出提案，**Grok** 审三问，**所有者锁** | 第 2 项目标就是 Fable 的强项 |
| 设计层正文（vision / architecture / 模块人话 / 横切章） | **Fable** 初稿 | 正确道路用正面叙述，克制「不得」清单 |
| 设计层初稿上的事实错误（过时实现名、坏链接、错误字段） | **GPT 直接改 Fable 的稿** | 切断 5、6 轮空转 |
| 合同层（`spec/*`）与「不得 → 正面道路 / CT」分类执行 | **GPT** | 一致性与唯一写入者是它的强项；目录已锁，不能靠加对象修一致 |
| 合同层有没有叠床架屋、有没有新造概念 | **Grok 只做闸** | 不许开新设计 |
| 删繁为简的分类表 | **GPT 打标签**，Grok 抽检 | 见第 3 步；GPT 不许发明新条 |
| 全文一致性一遍 | **GPT**，带预算 | 见第 4 步 |

四个目标对应谁：

| 目标 | 主责任 | 明确不要 |
| --- | --- | --- |
| 1 去死人 | K3 清单 + 各簇主笔执行 | GPT 单独开「过时内容审计」长文 |
| 2 收束集群 | Fable 出树，所有者锁 | GPT 在写作中改目录 |
| 3 删繁为简 | GPT 分类+执行，Grok 抽检 | Fable 凭直觉砍合同禁令；GPT 另写一套不得 |
| 4 严丝合缝 | GPT 在冻结树上做 | Fable 按 nit 单改 spec；多模型循环直到「看起来齐了」 |

## 详细开工步骤

第 0–1 步是讨论，不改 `docs/design/`。第 2 步起按冻结目录的簇改，一簇一闸，不合完上一簇不开下一簇。

### 第 0 步 · 死人清单（K3，high）

纯机械。输出一张表，每条标：删 / 搬进 `docs/design/references/` 或 `.memo` 归档 / 改成「已被 §N 取代」一句。

现行文档里仍以**现在时**出现、至少要扫到的死人：

- `agentd` / `hctl2-agentd` / `hctl2-agency` 当作仍要建设的组件
- Zellij 或 tmux 当作第一阶段现行 runtime（决策史 §19 口吻未标明已被 §29 取代）
- Conductor 当作现行引擎
- 用户在场证明、OS 沙箱入场券当作仍生效的硬门
- WezTerm 当作一等 Terminal 客端（现行一等原生客户端是 Herdr TUI）
- Electron 当作现行 Workbench 壳（现行是 Tauri 2，Electron 只是安全网）
- `participant.md` / `context.md` 仍盖 v0.14.1 这类版本戳漂移
- `architecture.md` 指向 `spec/system.md` 不存在的「端点约束与未决问题」
- [doc-cleanup-backlog](./doc-cleanup-backlog-20260825.md) 里已过时的 `agentd-only terminal`、`打包与 tmux 拓扑写死`

GLM 复扫：断链、版本戳、设计层泄漏的实现名。**这一步不改正文。** 先把尸体抬出结构讨论，否则 Fable 会把过时段落也「整合」进新目录。

`hctl2-agentd-prd` 头应改成「已废弃组件归属 · 条款待按 Herdr / control / tool 三类重归」——这是索引卫生，可随第 0 步或第 2 步第一簇做，不整表重归 83 条 AGD。

### 第 1 步 · 目录与收束（Fable xhigh 出树，Grok 当门，所有者锁）

只准出**一份结构提案**，不准改 `docs/design/`。

Fable 必须回答：

- 目标文件树（哪些合、哪些拆进子目录、哪些进 archive）
- 跨域同构的合并候选：四场景 × 三类数据、受控端口、完成路径、失败/丢失——这些只该有一份权威
- 设计层 / 合同层 / delivery / research / memo 的边界再陈述一遍
- 每份现行文件的命运：保留 / 并入 / 拆 / 归档

Grok 只审三个问题，不审文笔：

1. 还是不是四模块 × 三面 × 三条法，有没有偷渡第五模块或新聚合
2. 合并有没有把唯一 writer 并丢
3. 有没有把「未决」写成合同

**所有者拍板后，这份目录冻结。** 之后任何 agent 发现「还是拆开更好」，进停车位，本轮不做。这是防 GPT 钻死胡同、也防 Fable 写着写着改架构的闸。

### 第 2 步 · 按簇重写（换主笔，按层切）

建议簇顺序：

1. 地图 + 愿景 + 架构（大局先钉）
2. 四个模块的**设计层**（人话、正确道路）
3. `spec/` 合同层（唯一 writer、交接、降级条款）
4. delivery + CT（验收，不是第二份合同）
5. glossary / decision-history 的现在时 vs 历史时

每一簇：**写 → 闸 → 合入该簇 → 下一簇。** 不要攒到全文再审。不要 15 个文件一起改。

主笔按层切，不按「谁开的头谁改到完」——见上表。设计层 Fable 初稿、GPT 改事实；合同层 GPT 主笔、Grok 闸叠床架屋。

### 第 3 步 · 删繁为简（分类表，不许自由发挥）

不要下「把不得列表改短」这种题。GPT 会一边删一边补新的不得。

给 GPT 一张表，只许对**已有条文**打标签，不许发明新条：

| 标签 | 处置 |
| --- | --- |
| 特别好犯（人/模型会下意识走错） | 留一句，最好是正面道路里的对照 |
| 特别 tricky（不写就会做成另一套状态机） | 留 |
| 已有 CT / 类型系统 / fail-closed 能挡住 | 删文案，指到测试族 |
| 其余 | 删 |

Grok 抽检分类，不重写。然后 GPT 按表改文。Fable 可以读改完的设计层，看「正确道路是否还读得见」，但**不要让它把删掉的不得再写回来。**

[doc-cleanup-backlog](./doc-cleanup-backlog-20260825.md) 的 13 条过强 MUST 并进这张分类表处理，不另开一轮「逐条改合同」。已过时的两条先按第 0 步标过时。

### 第 4 步 · 严丝合缝（GPT，一遍，带预算）

全文只做一次一致性通过，清单写死：

- 同一概念只在一个权威位置定义
- 现在时 vs 决策史过去时
- 版本戳、专名、实现名不进设计层
- 交叉链接可点、不指向已删节

发现若需要**改目录或加概念**，进停车位，本轮不修。第二轮若主要在打第一轮新句子，按仓库纪律：**回滚，不继续补丁。**

## 明确不要做的（过程，不是产品禁令）

- 不要 GPT 独挑整库。「全面大修 + 严丝合缝」会触发完备癖。
- 不要 Fable 独挑整库，更不要让它根据 GPT 的问题单改合同。
- 不要让任何一个模型在写作中改目录。
- 不要把这次大修做成 v0.16 架构转向。
- 不要并行开工 Workbench、复活 agentd、Linear/GitHub、Dagu `human.task`、Context small-brain、Vikunja Done 适配器——那些是产品线，见 [v0.15.0 评述](../review/20260830-v0.15.0/grok-20260830a.md)。

## 工作量与产出形状

- 第 0–1 步：一两轮对话，产出死人表 + 冻结目录。零 `docs/design/` diff。
- 第 2 步：约 4–5 个 PR，按簇。每个簇一次闸就停。
- 第 3 步可并进第 2 步的合同簇与 delivery 簇，不必单独成轮；但分类表必须先于改文存在。
- 第 4 步：一个收口 PR。

比「全文写完再对打」短，也符合已立的「审计最多两轮、第二轮在打新概念就回滚」。
