# 全库文档大修：多 Agent 分工与开工手册

> 说明：可复用的方法与本次 HCTL2 大修的具体开工建议
> 基线：main @ 4ae0f64（草案 v0.15.0）
> 来源：2026-08-30 所有者提出的死文清理、结构重组、删繁为简与全文一致性要求，以及 Codex v0.15.0 独立架构审议

## 一句话结论

**GPT-5.6-sol xhigh 负责事实盘点、实际改写和最终一致性；Fable-5 xhigh 负责目标文档结构与一次整体复审；human 在目标结构和语义裁决处拍板；Grok-4.6 xhigh 可做一次删除安全审计。**

如果只能选一个主笔，选 GPT-5.6-sol xhigh。不要采用“Fable 写全文 → GPT 持续挑错 → Fable 反复补丁”的方式；按照既往经验，最后仍会变成 GPT 重写，只是多出数轮返工。

OpenAI 当前把 `gpt-5.6-sol` 定位为旗舰能力模型，支持 `xhigh` 与 `max` reasoning effort，并建议在代表性任务上比较不同 effort。本文建议用 xhigh：本任务复杂且要求一致，但目标是删除和归并，不需要鼓励无限探索。来源：[OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model)。

## 任务定位

这不是一次普通的文案润色，也不是逐文件修错。它位于文档体系和架构表达层，目标是重新建立一套完整、短、可导航、相互一致的权威文档。

本轮要同时完成四件事：

1. **去除死文**：删除已经失效、被替代或重复的内容；只有仍有独立阅读价值的历史才进入 archive；Git 能恢复但当前读者不需要的内容直接删除。
2. **重组全文**：从整体叙事和文件职责出发决定合并、拆分、建目录和交叉引用，避免按演化顺序留下补丁链。
3. **删繁为简**：正文优先写唯一正确路径；负面规则只保留常犯、后果严重或非常容易混淆的情况，其余转成机械检查或删除。
4. **保证整体一致**：术语、事实权威、模块边界、版本、链接、实现选型、交付顺序和当前代码必须互相吻合。

硬约束：

- 四模块、三面架构、metadata/content/artifact 三类数据、无等级客户端、模块专用 adapter、外部二进制优先是当前架构主干；不能借整理文档在没有新裁决时推倒重来。
- 设计正文回答为什么、整体怎样使用；合同层定义对象、状态和写入规则；research 保存源码与运行证据；decision-history 只保留重要转折；`.memo` 保存过程材料。
- 不因为某段文字难以安置就发明新对象、新层或新文件。
- 不以 archive 代替删除。
- 不用多名 agent 同时编辑同一批正文；实际写入始终只有一个主笔。
- 讨论和蓝图阶段不提交规范修改；目标结构经 human 确认后，整轮大修进入一个 PR。

## 为什么这样分工

### Fable 不做最终主笔

已知优势是愿景协作、整体结构和架构意识；已知风险是精确事实、合同细节和全库同步修改不够可靠。让它直接写全文，会使 GPT 的详细复审逐渐变成重写，并形成多轮来回。

因此 Fable 的输出限制为：目标文件树、阅读路径、章节提纲、合并拆分关系和整体复审意见。它不负责字段、状态机、版本、依赖、链接和代码事实。

### GPT 不从空白页设计整体结构

已知优势是事实核对、逻辑一致、跨文件修改完整；已知风险是过早钻入局部，在一个细节上增加过多规则。让 GPT 一开始就自由决定文档结构，容易把现有复杂度重新组织成另一套复杂度。

因此 GPT 先做受格式约束的事实盘点；目标结构由 Fable 提案并经 human 拍板；GPT 在固定结构内实际改写。这样把它的精确性用于执行，而不是让局部问题主导全局。

### 其他模型只承担独立且有终点的任务

更多全文 reviewer 不会自然产生更好结果，反而会形成相互矛盾的问题清单。附加模型只做一种检查：

| Agent | 任务 | 不做什么 |
| --- | --- | --- |
| Grok-4.6 xhigh | 删除安全审计：检查被删内容是否仍含有效决定，检查合并后是否丢失权威、权限、恢复和数据归属 | 不重写全文，不提出新架构 |
| GLM-5.3 max（可选） | 中文可读性：重复、病句、指代不清、英文夹杂失控 | 不修改合同含义，不增补规则 |
| K3 high（通常不用） | 如必须使用，只做初始文件分类和重复候选标记 | 不做最终裁决；可机械完成的工作不交给它 |

## 完整工作流程

### 阶段 0：冻结基线和权限边界

负责人：GPT-5.6-sol xhigh，只读。

动作：

1. 更新到最新 `origin/main`，记录精确 SHA 和设计基线版本。
2. 完整读取 `AGENTS.md`、`CONSTRAINTS.md`、根 README、`docs/design/`、`docs/research/README.md`、`.memo/README.md` 和实际代码树说明。
3. 明确本轮是“整理现有决定”还是包含语义修改。未经 human 裁决的语义冲突进入待裁决表，不能由主笔静默选择。
4. 建立本次大修工作目录：`.memo/design/document-overhaul-<date>/`。阶段产物都放这里，正文尚不修改。

阶段产物：`00-scope-and-baseline.md`。

停止条件：权威层级、目标范围或是否允许语义修改不清楚时，先报告，不继续改正文。

### 阶段 1：机械盘点

负责人：GPT 调用现有 shell/Git/Buck2 能力；能确定的工作不用模型猜。

至少收集：

- 全部 Markdown 文件、行数、一级/二级标题和相互链接；
- 每个文件的状态标头、基线版本、所属类别；
- 规范正文中出现的实现名和历史组件名；
- `agentd`、tmux、Zellij、Conductor、Electron 等已被替代名称的出现位置，并区分规范、research、decision-history；
- 相同或高度相似的标题、规则和段落；
- 所有“不得、不能、不允许、禁止、永不、只接受、必须拒绝”等强约束；
- 文档中的版本、平台、二进制来源和依赖事实，与 lock、Buck target、代码树是否一致；
- 相对链接和 heading anchor 是否存在；
- 正文引用 `.memo` 的位置，以及该引用是否仍有必要。

优先使用现有命令和一次性只读检查。若需要新增长期保留的 checker，必须先按仓库纪律调研原生机制和现有工具，再另行决定是否进入产品或 CI；大修本身不顺手建立一套文档构建系统。

阶段产物：`01-mechanical-inventory.md`，只记录事实，不给结构方案。

### 阶段 2：GPT 建立当前事实表

负责人：GPT-5.6-sol xhigh，只读。

逐文件、逐主题形成以下表格：

| 字段 | 含义 |
| --- | --- |
| source | 当前文件与章节 |
| layer | vision / architecture / design / contract / delivery / research / history / memo |
| current responsibility | 这段当前承担的唯一职责 |
| authority | 它是否有权定义该事实 |
| status | current / duplicated / superseded / contradictory / historical-only / implementation-note |
| evidence | 后续决定、当前代码、lock 或测试位置 |
| decision needed | 是否需要 human 裁决 |

这一阶段只回答“现在有什么、哪个是真的、哪里冲突”，不回答“新文件树长什么样”。

阶段产物：

- `02-authority-map.md`
- `03-known-contradictions.md`
- `04-current-architecture-one-page.md`

`04` 必须控制在一页左右，只写当前架构主线；它是 Fable 设计新结构的事实输入，不是新的规范正文。

### 阶段 3：Fable 设计目标文档体系

负责人：Fable-5 xhigh，只读。

输入：阶段 0—2 产物、当前文件树和全文；事实冲突以 GPT 的证据表为准，Fable 不自行猜测实现细节。

必须输出：

1. 目标文件树；
2. 每个文件的一句话职责，以及明确不负责什么；
3. 面向新读者、实现者、provider adapter 开发者的三条阅读路径；
4. 旧章节到新章节的迁移表；
5. 应合并的跨模块共同规则；
6. 必须继续留在各模块内的差异；
7. 删除、archive 和保留 decision-history 的原则；
8. 目标篇幅与章节比例，只给方向，不为了数字硬删必要合同。

Fable 不得：

- 写最终段落；
- 改字段、状态机、依赖版本或实现事实；
- 为了结构对称制造四份相同文件；
- 把 research 或历史内容升格为规范；
- 看到个别例外就新增一层抽象。

阶段产物：`05-target-document-map-fable.md`。

### 阶段 4：human 拍板目标结构和语义问题

这是第一次必须由 human 决定的节点。

human 需要看到：

- 当前架构一页摘要；
- 目标文件树；
- 旧→新迁移表；
- 待裁决问题及各自影响；
- 预计删除、合并、archive 的范围。

没有拍板前，不改规范正文。拍板后，将接受的目标结构冻结为 `06-approved-rewrite-plan.md`，后续 reviewer 不能随意推翻。

### 阶段 5：GPT 完成实际大修

负责人：GPT-5.6-sol xhigh，唯一正文 writer。

建议修改顺序：

1. 建立新目录和文件骨架；
2. 搬迁仍然有效的段落，不在搬迁时顺手扩写；
3. 合并共同规则，删除原位置副本；
4. 按目标主线重写设计正文；
5. 收窄合同中的重复说明和负面清单；
6. 清理 delivery、research 索引和 decision-history；
7. 删除死文件，处理必须保留的 archive；
8. 最后更新根 README、设计地图和全部链接。

每个源章节必须在迁移表中得到一种明确处置：keep / merge / split / rewrite / delete / archive。禁止出现“新文档看起来完整，因此旧段落大概可以删”的无记录删除。

主笔必须遵守：

- 不新增未经批准的架构决定；
- 不因一处边界难写而在多份文件重复补规则；
- 一个事实只有一个权威定义，其余位置链接或用一句话概括；
- 历史候选不进入现行正文；实现名只进入 delivery/research 和明确需要冻结 provider 能力的合同；
- 每新增一个段落，检查它替代了什么、是否真的必须存在；
- 发现目标结构无法容纳现行事实时，暂停并报告结构问题，不自行增加目录或新概念。

### 阶段 6：机械验证

负责人：GPT 执行；检查结果进入 PR 证据。

最低检查集：

1. `git diff --check`；
2. 全部本地 Markdown 相对链接和 heading anchor；
3. 文件状态标头与设计基线版本；
4. 术语和禁用措辞扫描；
5. 已退场实现名在规范层的残留；
6. 依赖版本、发行来源、目标平台与 lock/Buck 当前事实对照；
7. 重复标题和近似重复段落；
8. 所有强负面规则的保留理由；
9. 目标文件树与实际文件树一致；
10. 迁移表中的每个源章节均有处置结果；
11. 删除文件不存在仍被引用的链接；
12. design/spec/delivery/research 对同一事实没有互相冲突。

机械检查发现的问题直接修复；若修复需要新语义决定，回到 human，不让 checker 的便利性决定架构。

### 阶段 7：两次有边界的模型复审

#### Fable 整体复审

只回答：

- 主线是否清楚；
- 文件职责是否自然；
- 章节比例是否失衡；
- 读者是否能从愿景走到合同和交付；
- 是否仍能看见明显的演化补丁痕迹；
- GPT 是否又在某个局部堆了过多内容。

输出最多给一份按严重度排序的问题清单，不直接编辑文件，不评论字段级正确性。

#### Grok 删除安全审计

只回答：

- 删除或 archive 的内容中是否仍有生效决定；
- 归并共同规则后是否丢失模块差异；
- 是否删除了故障恢复、权限、权威归属或数据丢失时的关键规则；
- 正文是否与当前代码、lock 和 provider 能力矛盾；
- 是否有“看似重复、实际限定条件不同”的内容被错误合并。

输出必须引用旧来源、当前目标和具体丢失内容；没有证据的风格意见不进入修订。

### 阶段 8：human 裁决 review，GPT 一次性修正

不让 Fable、Grok 和 GPT互相对话五六轮。human 对两份清单逐项接受、拒绝或改写要求；GPT 只应用已接受项目，再重跑机械检查。

如果修正导致目标文件树或架构主线发生实质变化，重新请 human 检查；否则不再启动一轮全文自由 review。

### 阶段 9：一个 PR 提交整轮大修

PR 描述必须完整写：

- 定位与重述；
- 当前生效约束集；
- 业界方案调研，以及为什么没有新建文档生成器/检查器；
- 目标文件树；
- 删除、archive、合并数量；
- 待裁决问题的最终结果；
- 机械检查和模型复审结果；
- 哪些内容明确没有在本轮改变语义。

不按单个文件拆成一串临时 PR，因为中间状态会使链接和权威分布不完整。整个大修在一个分支和一个 PR 中完成；必要时可以保留少量按迁移阶段组织的 commit 供 review，合并时遵循仓库当时的提交策略。

## 本轮 HCTL2 大修的已知待裁决问题

以下三项不能只靠整理措辞解决，应在阶段 4 明确决定：

1. **Herdr `managed_single_writer`**：v0.8.2 没有统一 writer gate，也无法可靠检测同一用户直接使用原生 controller。是标为暂不支持，还是提供并验证隔离机制？
2. **`hctl2-tool` 范围**：是否正式收窄为 HCTL 特有的 Git/worktree/intent/readback 边界，把 lint、commit、PR、memo 等普通工作交给 Git、Buck2、`gh` 等现有工具？
3. **macOS 15 基线**：原理由 tmux 官方二进制提出，但 tmux 已退场。需要检查当前 Tuwunel、Herdr、Tauri 2 和全部随包 Mach-O 后重新证明或调整。

下面属于事实修正，不需要重新讨论架构方向：

- Tuwunel 正常 macOS 发行消费 HCTL 托管预编译包；源码构建只用于更新托管制品；
- Dagu research 需要追加“generation 留在 HCTL、Dagu 只作路标”的后续改判；
- `context.md`、`participant.md` 的版本标头含义需要统一；
- 远程端点、未决问题等引用应指向精确标题；
- 历史 tmux/agentd 描述只留在有阅读价值的 research/decision-history，不留在现行规范。

## 删除、archive 与 decision-history 标准

### 直接删除

满足任一条件，且不具有独立历史阅读价值：

- 已被新决定完整替代；
- 与权威位置重复；
- 只是过去为了修补另一段文字而增加的解释；
- 描述已退场实现，却没有提供仍可复用的证据；
- Git 历史足以恢复，当前读者不需要看到。

### 进入 archive

只有满足以下条件之一：

- 曾经是一份完整、可独立阅读的正式基线，仍需要被外部链接或迁移说明引用；
- 记录无法从 decision-history 的短摘要理解、但以后很可能用于兼容或迁移的旧合同；
- 因审计、授权或发布要求必须保留可浏览副本。

archive 文件必须在文件头明确“已失效、由什么替代”，不得被设计索引当成现行规范。

### 留在 decision-history

只保留真正改变方向的转折：为什么从 A 改成 B、被什么事实触发、现在由哪份规范承接。普通措辞修正、重复核对和实现细节不进入历史。

## 强负面规则的筛选标准

每一条“不得、不能、禁止、永不、只允许、必须拒绝”在保留前回答：

1. 它是否保护事实权威、权限、不可变版本或故障恢复？
2. 它是否对应历史上反复发生、而且普通正向规则仍容易犯的错误？
3. 它是否区分两个表面相近、混用后会产生严重后果的概念？

三项都否：删除。

如果规则能由 schema、类型系统、Buck2、lint、链接检查或合同测试完整保证：正文改写成正向合同，把具体反例移入测试；只有错误原因不直观时保留一句解释。

不要把所有可想象的错误列入规范。错误 case 无穷，正文应让正确路径清楚且可执行。

## 给各 Agent 的开工任务摘要

### 给 GPT-5.6-sol xhigh：事实盘点

> 只读全库，不修改正文。建立文件职责、权威来源、重复、失效、矛盾和实现事实表。先完成全库盘点，再报告任何局部问题。不要提出新对象或新架构。每个结论引用具体文件、章节、提交或当前代码。输出机械盘点、authority map、contradiction list 和一页当前架构摘要。

### 给 Fable-5 xhigh：目标结构

> 使用已经核实的事实表设计目标文档体系。重点是全局叙事、文件职责、合并拆分、阅读路径和历史材料去向。只输出文件树、提纲和迁移表，不写最终正文，不修改合同细节，不自行解决事实冲突。优先减少文件和重复规则；不要为了形式对称制造文件。

### 给 GPT-5.6-sol xhigh：实际改写

> 按 human 批准的目标文件树和迁移表，作为唯一 writer 完成全库大修。一个事实只保留一个权威位置；不新增未经批准的语义；每个旧章节必须有明确处置。优先删除、归并和正向表达；能机械保证的错误移入检查或测试。完成后运行全部机械一致性检查并提交证据。

### 给 Fable-5 xhigh：整体复审

> 只检查主线、结构、阅读体验、章节比例和是否仍有局部堆叠。不要审字段和实现事实，不直接改文件，不提出新架构。输出有限、按严重度排序的问题。

### 给 Grok-4.6 xhigh：删除安全审计

> 对照迁移表和 Git diff，检查删除、archive、合并是否丢失仍生效的权威、权限、恢复、数据归属和模块差异。每个问题必须同时引用旧来源与新目标；不做自由文风 review，不直接改文件。

## 完成定义

大修只有同时满足以下条件才算完成：

- 新读者能从根 README 在少量跳转内理解产品目标、四模块、三面和交付顺序；
- 每个文件有唯一职责，设计、合同、交付、research、历史和 memo 不互相越权；
- 每个现行事实只有一个权威定义；
- 已退场组件不出现在现行规范，除非用于明确说明能力边界；
- 所有删除和 archive 都能从迁移表解释；
- 强负面规则均通过筛选，机械可验证部分已有对应检查或测试去向；
- 文档与当前代码、lock、平台和 provider 能力一致；
- 本地链接、heading anchor、版本标头、术语和禁用措辞检查通过；
- Fable 整体复审和 Grok 删除安全审计已逐项裁决；
- required CI 通过并合并到 `remote/main`。

完成后的文档应当明显更短、更容易进入，也更难在一个局部修订后破坏全文；如果只是把旧内容重新搬家并增加更多索引，就不算完成。
