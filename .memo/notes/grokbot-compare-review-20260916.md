## 一、三条核心观点的分层定位

所有者提炼的三条：

1. Grok Bot 的核心是「数字伙伴」，HCTL2 的核心是「项目与承诺」。
2. Agent 间通过聊天「协作」不产生额外价值；价值来自多样性与外部机械制度带来的判定和输入。
3. HCTL2 通过扩展 TAMP 实现数字伙伴的管理。

**逐条定位：**

| 观点 | 落在哪层 | 与现状的关系 | 结论 |
| --- | --- | --- | --- |
| 1 伙伴 vs 项目与承诺 | 愿景层 | vision 的一句话定位、四阶段、Project 连续性、最小内核都在表达它，但从未作为显式定位声明写下 | **完善**：vision 补一段定位声明 |
| 2 聊天不增值，多样性+制度增值 | 已在约束层与研究里落地 | 就是 `docs/research/multi-agent-effectiveness-20260908.md` 的结论，已变成 vision 原则 2 的尺子、spec/run.md 的席位隔离与去重 | **不动**约束；措辞收窄见下 |
| 3 TAMP 承接伙伴管理 | 延长线 | TAMP 仍是 `.memo/notes/` 讨论稿；vision 延长线只有数字员工市场三协议面 | **完善**：延长线一节升级 |

## 二、第 2 条的 fact-check（措辞收窄）

方向成立，「不产生额外价值」要收窄为三层：

- **同构互看、趋同式聊天：不增值且更贵。** 六篇等预算复核（Huang、Smit、Zhang、Choi、Zhu、Bertalanič）结论一致；[Debate or Vote](https://arxiv.org/abs/2508.17536)（NeurIPS 2025）证明收益主要来自多数投票；[The Cost of Consensus](https://arxiv.org/abs/2605.00914)（2026-04）测得辩论 token 是独立自纠的 2.1–3.4 倍、从众率最高 85.5%——注意其标题自带限定词 Unguided **Homogeneous**。两篇外部核实均存在，与 repo research 记载一致。
- **异构模型、独立投票、分工接不同证据、外部工具验证：有稳定正收益**（3–8 个点级；Zhang、Yang、Verga、Wu、MetaGPT、AutoGen、Cemri）。所有者的「多样性」与「机械制度」恰好覆盖这部分。
- **「互看」唯一被证明有用的形态是对抗式辩护 + 第三方裁决**（Khan、Kenton）——hctl2 的 Gate（独立席位、互不见面、归约器汇总）已经是这个形状，不用改。

边界（research「未查到」节已有，引用时保持）：证据多在推理/问答基准，代码评审直测文献里没有；前沿模型上证据比小模型薄。两条反而支持编码域应用的旁证：SWE-bench Verified 上多 agent 编排略负（Kim），Anthropic 自述编码任务不适合多 agent。

所有者原话（原文 779 行）「避免**无谓的** agent 对话消费 token」里的「无谓的」是关键限定，建议以后引用时保留；要修的只是括号注「多agent对话并不能提升任务的完成度」——按 research 的准确结论是「同构互看趋同不提升；异构+独立+外部证据提升」。

## 三、对设计正文的两处改动建议（主笔执行）

### 建议 A：vision.md 加一段定位声明

**位置**：`docs/design/vision.md`，建议放「一句话定位」之后或「不解决什么」附近。

**为什么**：Codex 这轮讨论演示了缺这段的代价——它先把「没有跨项目长期角色」当缺陷提了一整节（三层身份表），被所有者用 TAMP 纠正后才收回成「定位选择，不能直接视为缺陷」。这个「先当缺陷、再被修正」的成本，以后每家外部评审都会再付一次。写进 vision 就钉死了。

**建议写什么**（意思，不代拟成文）：

- 长期主体是项目与承诺，不是执行者：连续的是目标、契约、知识、证据与执行历史；参与者因任用而进入，同名角色不继承另一处的权力（现有句都有，这里做的是把它们提升为「定位选择」并点名对立面）。
- 「数字伙伴」是定位差异不是能力缺口：围绕伙伴组织工作的产品（如 Grok Bot）服务的是「长期了解我」的购买价值；HCTL2 服务「这件事要交付什么、凭什么算完成」。两者可共存于一个产品，但项目事实的最终权威不归任何伙伴。
- 配套在「不解决什么」加一条：不把数字伙伴作为产品的组织中心（伙伴式体验可以作为推荐层存在，见延长线）。

### 建议 B：vision.md「延长线」一节升级

**位置**：`docs/design/vision.md` 末节「一条留到将来的延长线」。

**为什么**：现在延长线只写了数字员工市场的三个协议面（发现档案、约定条款、执行端点），没有回答「伙伴式体验怎么在 HCTL2 里成立」。TAMP 讨论稿（`.memo/notes/TAMP-design-doc.md` + 评审）已经回答了，本轮讨论把它收敛清楚了，值得把结论写进延长线。

**建议写什么**（意思）：

- 任用是后台语义、推荐是前台体验：「按任务重新任用」与「推荐已验证过的合适伙伴」不冲突；长期伙伴可以是推荐结果，不是项目事实的组织中心。
- 匹配四段：Recall（能力相似度召回）→ Gate（可行性过滤）→ Rank（排序，含经济性——报价要结合成功率、返工与交接成本看，不能买掉权限限制与评审隔离）→ Award（人或获准策略任用并进入正式授权）。
- 能力评价关联工种模板 + 实际执行配置版本 + 任务族 + 执行条件；配置变化后旧成绩作先验不原样继承；区分声明、背书、实测、独立验证。
- 边界：它作为 Participant 选型与 Agency 供给匹配的能力存在，不另建一套 Task/Run（Codex 原话可引：「推荐回答谁更适合履行这份承诺，HCTL core 继续决定承诺是什么」）；警惕测量税——常规任务用静态规则与已有评价，复杂或异常才上重机制。
- 不动 `.memo/notes/TAMP-design-doc.md` 本身，不进当前交付范围。

**不建议动的**：约束层、architecture.md、五模块正文。第 2 条观点已是承重墙（vision 原则 2/6/7、spec/run.md 隔离与去重、「分歧不靠评审员再商量」）。在架构层再加一句「协作问题的默认载体是状态与规则，不是模型间对话」可做可不做，我倾向不做——现有原则已覆盖，再加有重复风险（参见文档大修「删繁为简」原则）。

## 四、Codex 建议的分拣（超出三条观点的部分）

Codex 在五模块对比（原文 349–576 行）里提了一批具体建议。按其自身修正与现行基线（含刚合的 D 批 #231）重新分拣：

**已被现行设计覆盖，不用动：**

- 观察与接管的**身份与通道边界**（B 批已落：Agency 一道门、票据由控制面签发经 Agency 校验、连接绑定精确 Dispatch、exact attach）。
- 看板多源与卡片映射（D 批 #231 已落）。
- 「组合命令 / 一次用户决策驱动多个后台动作」与「注意力视图」：交付层事项，不动设计正文，可在 P2/P3 的产品化阶段再议。

**值得单独立项（触及授权或默认形态，按 9-13 铁律用例先行）：**

1. **Room 的「有范围、有期限的协作授权」**：把「普通 Room 每条临场执行边必须人提交 Trigger Preview」上移为「一段授权内 control 自检、越界找人」（原文 389 行）。看板维护责任（PM 角色：补进度、追停滞、备验收材料，原文 407–420 行）本质是它的一个特例，建议并入同一立项。这是对授权密度默认值的实质修改，Codex 自己也标明「需要新的授权制度」；与 Run 的「冻结边界内自动推进」同源，是延伸不是推翻。
2. **轻量路径（无 Run）的有限跟进责任**：首次授权中明确「在此任务/路径/PR 范围内继续处理评审意见与检查失败；预算与截止固定；越限找人」（原文 463–467 行）。每轮仍建新调用与 ChangeSet 版本、旧评审不冒充新——与现行规则兼容。
3. **合并策略默认值**：按仓库预先批准贴近平台原生能力的政策，严格的「预期目标头不变」形态降为可选（原文 562–566 行）。C 部落了两阶段发布与确认记录的**机制**，但没动默认授权形态；这是小立项。
4. **观察面能力分级**：Codex 的「桌面扩展六件事」（观察目标、能力类型、输入权限、生命周期、隐私共享、证据地位，原文 272–281 行）。B 批落了身份与通道边界，没做观察面分级——B5 的证据三档管「结果怎么算数」，不管「观察面分几级、桌面怎么声明」。这份清单可直接当方案输入。

**不建议现在动：**

- **Project 0..N Repo**（原文 546–550 行）：C 批刚拍完 Repo 身份与交付链，一期连单 Repo 闭环都没跑通；Codex 自己标的代价（跨仓依赖、部分完成、补偿）是真实的。记为已知延长线即可。

- Codex 的时间判断（原文 share 链接末尾轮次）与本文结论一致：继续加深设计不是当前收益最高的投入，最缺的是真实运行的交付结果。本建议书也按这个原则收口——两段 vision 小改 + 立项备忘，不新开设计批次。
