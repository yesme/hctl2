# HCTL2 战略拐点评估：与 T3 Code / Orca 的范式对比及 Room 核心假设研判

Antigravity (Gemini) · 2026-11-23 · 整理自与项目所有者的两轮架构与产品策略讨论，供下一阶段路线取舍参考。

---

## 一、 核心裁决（TL;DR）

1. **生态层位裁决：HCTL2 与 T3 Code、Orca 不在同一抽象层，不存在正面同质化替代关系。**
   * **[T3 Code](https://github.com/pingdotgg/t3code) 与 [Orca](https://github.com/stablyai/orca)** 本质上是 **“多会话复用器与单兵并行工作台（Multiplexer & ADE）”**，解决的是 **“单人开发者如何低摩擦地同时操控 10 个编码代理窗口并审阅代码差异”**（执行优先，Execution-first）。
   * **HCTL2** 本质上是 **“连接持久意图塑形与机械可验证交付的项目协作系统”**（[愿景](../../docs/design/vision.md) · [三面架构](../../docs/design/architecture.md)），解决的是 **“模糊需求如何在多参与者之间澄清并冻结为契约、执行体如何在受控写边界内施工、完成结果如何凭外部回读证据验真”**（契约与验真优先，Contract & Verification-first）。

2. **去留与转向裁决：放弃“通用多终端编排面板”叙事，通过“砍枝留核”聚焦上游 Room 塑形与下游机械验真。**
   * **如果继续沿用“拼装重型外部组件 + 追赶通用桌面工作台（Workbench）”的全栈路线**：**不建议继续投入。** 单兵多终端与多端遥控的交互体验已被 Orca 与 T3 Code 拉至极高水位；同时，跨接多套异构内容系统的状态对齐负担，会在产品真正触达核心体验前消耗绝大部分工程精力。
   * **如果围绕两大独有壁垒做减法转向（Pivot）**：**非常有继续推进的价值。** HCTL2 押注的 **（1）以持久 `Room` 承载跨会话、跨角色的需求澄清连续性**，以及 **（2）不依赖模型自述的零信任机械治理（独占 `Write Lease`、开工 `Context` 隔离组装、基于精确提交围栏与回读事实的 `Receipt`）**，恰好踩在 T3 Code 与 Orca 走向高并发与多人协作时的结构性盲区上。

## 二、 全景对标：T3 Code、Orca 与 HCTL2 的异同

### 1. 三者的底层共识
* **Harness 中立与自带订阅（BYOS）**：均不自建底层编码大模型，而是封装开发者本机已登录的 Claude Code、Codex、OpenCode、Cursor CLI 等工具。
* **本地优先（Local-First）与 Git Worktree 物理隔离**：代码与运行环境留在受控主机，利用 `git worktree` 或独立分支消除多代理并发改写同一工作区的冲突。
* **人在回路（Human-in-the-Loop）**：均承认现阶段代理输出不可盲信，在关键推进与合入节点保留人的观察、纠偏与放行权。

### 2. 核心架构与方法论差异

| 维度 | T3 Code (`pingdotgg/t3code`) | Orca (`stablyai/orca`) | HCTL2 (`yesme/hctl2`) |
| :--- | :--- | :--- | :--- |
| **核心定位** | **Chat-first 轻量多端控制面** | **Terminal-first 并行代理开发环境 (ADE)** | **全链路目标塑形与受治理施工系统** |
| **最小调度原语** | `Thread`（单次任务对话线程 ↔ 分支/工作树） | `Worktree + PTY Pane`（并行终端分屏） | `Room → Task → Run → Attempt → Receipt` 因果链 |
| **需求澄清位置** | 无独立阶段（默认输入提示词时意图已就绪） | 外部前置（从 Linear / GitHub Issue 拉入现成工单） | **核心阶段（[Project / Room](../../docs/design/project.md)）**：持久房间承载澄清、`Request` 索取与 `Memo` 沉淀 |
| **协作拓扑** | 主体为 `1 人 ↔ N 线程`（Orchestrator V2 支持父子 `delegate_task` 委派） | 主体为 `1 人 ↔ N 独立终端`（散射并行，人工比对合并） | **`M 人 + N 数字参与者`**：Room 内共识塑形，经 `Agency` 按工种/技能派发席位 |
| **上下文（Context）纪律** | 会话级历史消息流，跨工具切换有损 | 各工作树终端彼此独立，依赖仓库静态文件共享 | **一等公民（[Context 设计](../../docs/design/context.md)）**：按契约最小化组装开工包，**严禁向执行体泄露控制面治理与评审底牌** |
| **写边界与完成判定** | 人工审阅内联 Diff + 一键发起 PR | 工作树隔离 + 编辑器内联批注与人工合入 | **零信任机械证明**：独占写租约（`Write Lease`）+ 精确 `{base, head}` 围栏 + 外部事实回读签发 `Receipt` |
| **冷启动心智负担** | 极低（`npx t3@latest` 秒级拉起） | 低（桌面安装包开箱即用，预置数十种 CLI） | **高**（概念链路完整但组件栈厚重，冷启动门槛陡峭） |

### 3. 代差本质：从“单兵多路复用”到“工程级可信交付”
* **T3 Code 解决的是“交互降噪与异地接续”**：把易闪烁的终端界面抽象成流式对话与移动端审批（`T3 Connect`），本质是更顺手的遥控器。
* **Orca 解决的是“单兵并发吞吐”**：把工作树生命周期、守护进程级 PTY 保活、代码差异审阅与浏览器视觉检查整合进统一桌面，本质是更高密度的驾驶舱。
* **HCTL2 解决的是“规模与协作复杂度上升后的失控”**：当并行任务上升到十余个、周期跨天或转交他人时，单兵工作台会集中暴露四类失效：**（1）私人终端内的澄清过程随会话关闭而蒸发；（2）执行身份丢失后的残留或重派进程存在越权污染分支风险；（3）代理自称“验证通过”缺乏可重放的外部证据；（4）评审代理易受执行代理上下文诱导。** HCTL2 的契约冻结、租约围栏与回读凭证体系在架构深度上明显领先于前两者。

## 三、 核心假设深潜：以 Room（聊天室）为核心承载需求澄清与多人协作

HCTL2 的关键假设在于：**功能（Function / Feature）的边界澄清应在持久化的聊天室（Room）中完成，并以聊天室作为解锁未来多人、多代理团队协作的核心现场。**

### 1. 与 Orca / T3 Code 的愿景契合吗？
**底层基因完全不契合——双方是从软件生命周期的两端相向而行，而行业近期的演化正在验证 HCTL2 这一预判的前瞻性：**
* **Orca 与原生 T3 Code 均以“单次执行会话”为中心**：Orca 默认工单进门前已完成澄清；T3 Code 的对话虽呈聊天形态，但生命周期绑定在单条编码线程上，分支合入后该线程即告终结。
* **HCTL2 的 `Room` 锚定“塑形连续性（Shaping Continuity）”**：如 [Project 与 Room](../../docs/design/project.md) 所定义，当短期 Harness 会话、终端与工作树销毁或更换后，Room 依然存续，用来回答“当初为何这样定、否掉了什么备选方案、哪部分已稳定为 [Task](../../docs/design/task.md) 承诺”。
* **外部演进信号**：单兵并行工具正普遍撞上 **“私人终端黑盒（Private Terminal Silo）”**——开发者甲与代理在本地拉扯数十轮后交出大段代码，评审者乙却完全看不到取舍依据。近期 T3 Code 社区围绕 *Agent Rooms*（`#31121`）、多人共享线程署名（`#31979`）及多人分支 *Campfire* 的探索，以及企业侧 Salesforce 推出 *Slack Code*（在频道内拉入多方角色与编码代理共同塑形需求并签字放行），均印证了**“把需求澄清从私人终端迁回共享持久空间”是真实的下半场命题**。

### 2. HCTL2 在 Room 模型上做对的两处关键设计
1. **在“无序聊天流”与“受控施工”之间设置了治理离合器**：
   把代理直接塞进普通群聊极易引发刷屏失焦，或让代理把随口试探误判为正式需求变更。HCTL2 明确分离了聊天底层 `Content` 与控制面存储中的治理记录：只有经提炼发布的 **`Memo`（长期记忆）** 与显式采纳的 **`Task` 契约版本** 才具备治理效力，且普通 Room 的临场执行边由人提交、模型 Participant 仅提议下一条边。
2. **将 `Request`（请求卡）建模为一等公民对象**：
   多人与多工种代理协作的最高频阻塞点在于跨角色索取信息、裁决与授权。将这种索取结构化为 `Request` 对象而非淹没在滚屏 `@提及` 中，抓住了团队异步协同的核心抓手。

### 3. 当前路线下必须直面的三重结构冲突

1. **线性消息流（Stream）与全局规格画布（Canvas）的冲突**
   聊天流擅长承载**增量讨论与分歧拍板（Delta）**，却不擅长呈现复杂功能的**当前完整契约状态（State）**；消息超过数十条后，参与者极易陷入爬楼回溯负担。以 Room 为核心，界面形态不能止步于纯消息流，必须形成 **“左对话流（讨论与 `Request` 拍板）↔ 右实时契约画布（`Memo`、`Task` 验收条款与 [Run](../../docs/design/run.md) 回执）”** 的联动结构。
2. **外挂通用 IM 客户端（`Tuwunel` + `Cinny`）与“Room 核心体验”的冲突**
   * **领域交互缺失**：若 Room 是核心体验，最高频动作就是划选讨论提炼 `Memo`、在流内直接点按交互式 `Request` 决策卡、比对并冻结 `Task` 契约、内联核验 `Receipt` 摘要。通用 Matrix 客户端 Cinny 不具备这些领域原语，只能退化为文本命令或外部跳转，削弱了“以聊天室为核心”的成立前提。
   * **团队迁移阻力**：进入多人协作场景后，研发团队日常已驻留在 Slack、飞书或 Discord 中。要求外部团队为了采用编排系统而全员额外迁入一套独立的通用 Matrix 客户端，推广摩擦极高；团队只会接受**专为研发塑形深度定制的协作工作空间**，或与现有聊天工具的轻量桥接。
3. **重型组件栈与“单人冷启动”的冲突**
   绝大多数协作工具依赖“单人先高频用爽 → 自然扩展至小团队”的冷启动路径。若单人处理常规小需求也须跨越完整的房间、看板、工作流多系统编排，冷启动阶段就会因仪式感过重而受阻。系统需要支持**渐进式仪式感（Progressive Ceremony）**：单人明确小改可一键坍缩为最小契约派工；遇到模糊边界或多人分歧时，再自然展开完整的 Room 澄清链路。

## 四、 战略拐点（Pivot Point）：具体转向与取舍建议

1. **扭转对外定位：告别 *"Multi-Harness Orchestration Panel"*，聚焦 *"Agent-Native Shaping & Verifiable Delivery"***
   不再与 Orca、T3 Code 比拼终端分屏密度或通用桌面外壳；将底层 Harness 彻底退居幕后（平时作为受控无头执行体，仅在排查异常或人工接管时按需打开终端视图），把稀缺精力全部集中在**“上游多人多角色需求塑形 + 下游零信任机械验真”**这一头一尾的闭环上。

2. **架构做减法：审慎评估剥离通用重型外挂内容后端，收拢核心交互闭环**
   * **若坚定走“Room 驱动的多人塑形产品”路线（推荐主航道）**：与其让控制面跨接 Matrix（Tuwunel/Cinny）、Vikunja、Dagu 等多套异构外部服务并承受长期的状态对齐与打包体积负担，不如由 `hctl2-control` 直接维护轻量的统一事件流与存储，配一个极薄但**原生支持 `Request` 卡片、`Memo` 提炼、`Task` 契约画布与 `Receipt` 回执**的专属 Room 界面；团队既有的 Slack / 飞书 / GitHub 则通过外围通知与审批适配器按需接入。
   * **若选择退守纯工程治理底座（备选轻航道）**：放弃自建前端面板，将核心能力浓缩为单二进制治理边车（CLI / MCP 服务），专职提供 **开工 `Context` 隔离编译、`Write Lease` 与 OID 围栏保护、外部事实回读与 `Receipt` 签发**，直接寄生在开发者现有的终端、T3 Code、Orca 或代码平台之上。

3. **设立唯一硬性拐点判据：本仓日常开发的真实自举（Dogfooding）**
   判断下一阶段该扩写功能还是做减法，最客观的标尺只有一条：**项目所有者与多席位编码代理在开发 HCTL2 自身的下一个真实需求时，是否真心愿意在 HCTL2 的 Room 与契约链路内完成澄清、派工与验收，且比绕开它直接手写备忘派活更省心？** 只要率先打通高频、低摩擦的本仓自举，产品拐点即告确立。

## 五、 实现层脚注

以下记录基于当前仓库基线（`ba8354f`）核对的代码与文档现状，仅作工程进度与成本参照，不改变上文架构层判断：

- **控制面与三条真实交付链已具备可运行实证，但公开入口认知存在滞后**：根 [`README.md`](../../README.md) 仍写着“还没有可用的公共 CLI 或完整应用”，而 [`docs/usage.md`](../../docs/usage.md) 与 [`docs/demos/demo-3.md`](../../docs/demos/demo-3.md) 显示 `hctl2`（P2.1 公共 CLI）、`hctl2-control`、`agency`、`hctl2-services` 与 `hctl2-tool` 均已在 `src/` 下落地，并在 Ubuntu 上跑通本地 Gitea + Claude Code 写入交付（A 链）、受保护 GitHub `main` + Codex 交付（B 链）及三次人工预览（C 链），仅图形端 `hctl2-workbench` 尚未实现。
- **随包异构服务的物理体积与 Cinny 边界印证了“重栈摩擦”**：据 [`docs/demos/demo-3.md`](../../docs/demos/demo-3.md) 第一.2 节记录，同时打包 Tuwunel、Cinny、Gitea、Vikunja、Dagu、Herdr、Process Compose 等固定二进制后，完整离线运行载荷约 **635 MB**；同时 [`docs/usage.md`](../../docs/usage.md) 明确指出随包 Cinny“主要用于 Matrix 互操作和人工查看，不是 HCTL2 Workbench，也没有 HCTL2 治理权限”——这直观体现了“打包了通用聊天端”与“拥有原生 Room 治理交互”之间的落差。
- **仓内既有竞品审计与本文的边界判断一致**：[`docs/research/workbench/stably-orca.md`](../../docs/research/workbench/stably-orca.md) 对 Stably Orca 的四层审计已明确指出其 L4 很弱（Native Chat 仅对应单条代理会话投影，无独立 Project Room 或长期协作记忆）、L3 卡片身份仍绑定 worktree 而无独立 Task 契约版本，印证了 HCTL2 在 L3/L4 层面的差异化空间。
- **本仓自身协作尚未迁入 HCTL2 闭环**：按 [`AGENTS.md`](../../AGENTS.md)「唤醒与派活」与「评审与合入」记录，目前本仓调度 Claude、Codex、Antigravity、DeepSeek 等十余个席位的日常研发，依靠的仍是 `.memo/` 下的 Markdown 派活表与 GitHub Actions 关卡（`pr-contract.yml`、`review-gate.yml`），尚未跑在 HCTL2 自己的 Room 与 Run 上——将这套已被日常验证有效的本仓协作流低摩擦地迁入系统自身，正是检验去留取舍最直接的试金石。
