# Gate 计票（第 5a 包）

P2.5 第 5a 包：评审关卡的计票，只做纯算法。依据是 [`spec/run.md` §计票与结束](../../../docs/design/spec/run.md#计票与结束)，以及 §Request、重试与 Gate 里关于去重键、否决权与多样性的几段。它不读写存储，不依赖别的 crate，也没有三方依赖。席位、候选与事实从哪条记录取，由第 5b 包在接入时决定；本包只规定输入长什么样、怎么算。

## 接口

`tally(&Gate) -> Result<Tally, Invalid>`：输入是法定票数和这一轮关卡的全部席位，每个席位带着冻结数据与已记录的事实；输出是结论、按键分好的组，和第三步要处理的事实（`Findings`）。同一组事实无论按什么顺序排进 `Gate::seats`，结果都一样。

席位上的字段：

| 字段 | 含义 |
| --- | --- |
| `veto` | 关卡策略给这一席声明了否决权 |
| `candidates` | 这一席还能用来产出裁决的 Worker Profile 摘要：正在跑的尝试用的那个，加上获准候选里还没试过、没失败的 |
| `material` | 这一席交付内容摘要所依据的冻结引用（ReviewSubjectRef、席位必需 Skill 的引用、根 Manifest）的摘要；两席不同即证明交付内容不同 |
| `delivered` | Bundle 交付后的实际交付内容摘要 |
| `attempt` | 最近一次尝试：未派发、在跑、已交提案、失败（`allowed` 表示故障类型在冻结策略允许切换之列） |
| `pending` | 已冻结、尚未准入的提案，带它产出时的键；不计票，也不当作没有 |
| `vote` | 有效裁决：已过结果准入的裁决与键；`evidence_channel` 只为凭证记录，不进键 |
| `end` | 由既有准入与撤权规则判定的结束：取消、替代、到截止 |
| `budget_left`、`time_left` | 预算、剩余截止还允许再开一次尝试 |

五个词对应的方法：

| 约束里的词 | 方法 |
| --- | --- |
| 有效裁决 | `Seat::vote` |
| 仍可产出 | `Seat::producing`；其中「还能再开尝试」是 `Seat::can_open_attempt`，候选切换也用它判 |
| 已结束 | `Seat::ended` |
| 仍可能加入 | `Seat::may_join` |
| 已定 | `Group::decided` |

组（`Group`）留着组内每一席的有效裁决（`votes`），不只留一个代表。`passing` 是「组内全是 `accepted`」，也就是最不利的那票仍是 `accepted`；`split` 是组内裁决不一致，要标需要关注。

结论 `Outcome` 有三种，与开工书第 5a 包的「签通过 / 确定不可达 / 暂未收齐」对应：

- `Pass`：签汇总 Verdict/Receipt，撤销 `revoke` 里的席位。已交提案待准入的席位不撤；被撤席位之后交回的提案只留历史，不形成组、不改已签汇总。
- `NoPass`：这一轮已经过不了。原因有两种，可能都有：上界少于法定票数（约束里的「确定不可达」，`upper_bound < quorum`）；或者 `Findings` 里有不是 `accepted` 的否决票、或没取得有效裁决就结束的否决席。两种原因谁先记下来随到达顺序变，「过不了」本身不变，所以合成一种结论。
- `Pending`：暂未收齐，继续等；等待由各席位的结束保证有界。

**本包不定出口。** 过不了之后走哪条路由归约器定，属第 5b 包：
- 返工；
- 交人（契约分歧）；
- 建 Request 或标类型化技术失败（否决席候选耗尽）；
- 返回 `quorum-unreachable` 沿失败边。

本包把第三步要的事实原样交出：
- `Findings::vetoes`：否决票，带裁决与分歧落点；
- `Findings::veto_unresolved`：没取得有效裁决就结束的否决席；
- `Findings::contract`：投了契约内分歧的席位，不论是不是否决席；
- 各组的 `votes`：普通席的非通过裁决。

`NoPass` 只说明这一轮签不了通过，不说明要沿失败边。调用方先按冻结规则做完第三步，再据此推进。

五步重算的落法：
1. 「结果准入」在调用之前完成，准入过的裁决才记成 `vote`。
2. 按键分组，`Group::decided` 用「没有席位仍可能加入」判。
3. 第三步要的事实写进 `Findings`，归约由调用方做（见上）。
4. 签通过要满足三条：已定的通过组够数；没有仍可产出的否决席；`Findings` 里没有不是 `accepted` 的否决票，也没有无裁决就结束的否决席。契约分歧不挡通过，通过了也照样在 `Findings::contract` 里，Task 照样要标需要关注。
5. 算上界：当前全部有效裁决（含未定组里的）是固定输入，每个仍可产出的席位取对通过最有利的落点。

`Diversity::check` 是席位多样性的检查，只有两项可声明：Worker Profile 互异、回避作者所用的 Worker Profile。启动时用选定记录的 Profile 查，候选切换后用实际 Profile 查，有违反就拒绝启动或拒绝切换。证据通道与 harness 不在其中。声明了回避作者 Profile 却没给作者 Profile 时，报 `AuthorUnknown`，不当作检查通过。

## 约束没写死、本包自己定的读法

这几处请评审与第 5b 包留意：

1. **不给非通过裁决排先后。** 约束说组的裁决「取最不利」，但没给 `rejected` 与两种 `changes_requested` 之间的先后。计票只需要知道最不利的那票是不是 `accepted`，就是 `Group::passing`。非通过裁决之间谁压过谁、归约成哪条出口，由第 5b 包的归约器定，本包把每一票原样留在 `Group::votes`。
2. **「冻结引用能否证明不同」用 `material` 判。** 两席的冻结引用摘要不同，就证明交付内容不同；相同则证明不了，算可能相同。前提要第 5b 包在接入时核对：`material` 是对 ReviewSubjectRef、席位全部必需 Skill 的引用摘要、根 Manifest 按规范形式算的内容摘要，不能拿两个不同的定位符当作交付内容不同的证明。
3. **上界里，未交付的席位总能落到一个自己独有的键上**：它的交付内容还没定，没有什么能证明它与别人相同。这和「仍可能加入」里「证明不了不同即算可能相同」方向相反，两者各取对自己那一步保守的一边：上界不提前判失败，已定不提前签通过。
4. **已冻结待准入的提案**，键按它产出时记下的算（既用于「仍可能加入」，也用于上界）；它的裁决内容在准入前不用，上界里按 `accepted` 计。
5. **CT-RUN 第 29 条第一句的两种顺序。** `accepted` 先到时，组要等另一席准入或结束才定；`changes_requested` 先到时，按第 31 条的上界规则，这一轮当场就判过不了，因为那个组已经过不了。两种顺序的结论相同；但「标需要关注」（`Group::split`）只在两票都准入后才出现。

**还没定、留到第 5b 包之前的一处：第三步什么时候动手。** 判出过不了的那一刻，`Findings` 与各组的 `votes` 里已有什么，随到达顺序变。例如否决席的否决票可能已到，也可能还没到。归约器如果当场就定出口，同一组事实会因为谁先到而走不同的路（返工、交人还是失败边）。另一种做法是等仍可产出的席位都结束、事实收齐再定。性质用例数过这种情形：3000 个世界里没通过的，约三成在第一次判出过不了时，`Findings` 随顺序不同。这是归约器的规则，设计正文没写，已报所有者；本包只保证「过不过」与顺序无关。

## 用例

`tests/ct_run.rs` 把 CT-RUN 第 29、30 条逐句写成用例，另有第 31 条运行期的一半、第 17 条判定的一半、第 32 条计票的一半，以及第三步的事实怎么交出：普通席的实现内分歧、契约分歧、否决席的契约分歧、驳回与契约分歧同组。`tests/properties.rs` 是性质用例：随机生成各席位的事实序列，按八种到达顺序逐条记录、逐条重算，签了通过就照撤销名单撤席。检查五件事：

- 第一次不是暂未收齐的结论（通过或过不了）不随顺序变；
- 签了通过就不再变；
- 判了过不了，之后再来的事实也翻不回暂未收齐或通过。判了过不了之后仍把剩下的事实记进去，只为核这一条；之后控制面怎么处理这一轮，是归约器的事；
- 不通过时，各顺序把全部事实记完后的结果完全相同；
- 每个席位都结束后不会还停在暂未收齐。

另外输出一个数：没通过的世界里，第一次判出过不了时 `Findings` 随顺序不同的有多少（见上「还没定」一节），只输出，不断言。

随机数用固定种子的 splitmix64，失败时报出种子就能复现。
