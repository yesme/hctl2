## 问题

我们在 [yoda 条目](./workbench/yoda.md)里看到一件事：Feature Delivery（六阶段、仅人批准、产物默认草稿、上游变更使批准过期）2026-07-13 一个下午加进来，33 天里没有一次功能迭代，2026-08-15 在一个标题叫「fix(privacy)」的提交里被顺手整体删掉，文档与迁移至今未清。[生态审计](./methodology-landscape-20260824.md)已经记了另两处线索：MetaGPT 默认路径把 SOP 瀑布换成单点 LLM 路由，BMAD 砍到只剩四阶段文档链加确定性脚本。

要回答的问题只有一个：**在我们调研过的方法论、编排、纪律类工具里，治理性或结构性功能——阶段门与人工批准、规格与契约冻结、多 agent 角色与编排、评审门与多票、验收清单与证据、返工上限、机械关单——被加进来之后又被删掉、弃用、藏进开关、简化成提示词、或长期无人迭代，是个案还是规律？** 顺带问：社区反馈里有没有「太重、太绕、跑一次要批五道」一类导致简化的声音，以及有没有把门做到主路径并留住了的反例。

答案先说：**是规律，不是个案。19 家里 17 家出现了至少一处治理件的流失**（另两家是 unlazy 与 SSSF：前者整体在收紧、后者根本没有过迭代）。但流失的形状不是「用户嫌重把门拆了」这一种，而是四种并存：维护者自己嫌贵砍掉（成本）、门在提示词里从来没触发过所以宁删勿修（不生效）、harness 原生能力把流水线吞掉（被替代）、加了就没人再碰（停滞）。留住的门几乎全在流程两端（出货边界、文件系统写入），用代码判；流程中段的判断门（要不要人批、做完了没有）留住的全靠提示词。

## 逐家发现

一张表，一行一个治理件。「结局」用六个词：**删除**（代码或文件不在了）、**弃用**（还在但官方不推荐或进了 shim）、**变可选**（从默认路径退到开关、旗标或可选安装）、**变提示词**（原来有脚本或状态机判，现在只剩一句 prompt）、**停滞**（加入后无人迭代，或已知失效未修）、**留住**（还在主路径，放进表里是为了对照）。另有两个特殊词：**拒绝加入**（用户或贡献者提议加门、维护者不收）和**承诺未兑现**（文档说有、代码没做到）。

### 逐家补充

**yoda。** 时间线与删除现场已在 [yoda 条目复核记录](./workbench/yoda.md)复原。要补的一句是它在这张表里的位置：它是唯一一个「治理模块整块从产品里消失」的样本，其他家都是逐门流失。原因也最干净——一个人加一个 agent 在一个下午生成了一万六千行治理代码，从未进入主路径，删的时候连单独的提交都不值得。

**spec-kit。** GitHub 官方项目，核心步骤从没被删，但「必做」的门只剩工作流 gate 一道，`clarify / analyze / checklist` 全归可选；宪法变更从机械清单退成一条 LLM 命令；用户要求「太重」时维护者一律指向扩展与预设（TinySpec、preset），加门的 PR 一律推回社区仓库。值得记的一个反向细节：`verdict_input` 非交互回答不是旁路旗标，而是让 gate 从 stdin 或 workflow input 读同一个 verdict，且 fail-open 漏洞被修——这是「门留住并被修补」的形状。扩展 hook 被 agent 静默跳过（[#2688](https://github.com/github/spec-kit/issues/2688) "sits near the end of a 300+ line SKILL.md"）至今未修。

**OpenSpec。** 三处流失都由维护者明说：archive 的人类确认从 v0.4.0 起被模板教给 agent 用 `--yes` 绕过（理由是非交互）；proposal 阶段的 `validate --strict` 因为「我们其实不再跑校验」被删；固定阶段序列在 1.0.0 被「随时编辑任意工件」替代。留住并强化的是 CLI 的 `archive.ts`：具名阻塞态、`--no-validate` 必须配 `--yes`、scenario 漂移拒绝——全在代码里。但 agent 面对的 `/opsx:archive` 技能已改成手工 `mv` 加一句「用 AskUserQuestion 确认」，两条路并存是有意的。

**Kiro。** 三阶段人批没有被删，是被包围：Quick Plan 一步生成不设门、1.0 起默认自由聊天、Run all Tasks 并行执行、Plan 模式批准即开跑。维护者在博客里把这叫「质疑结构与质量意味着慢的假设」。任务完成由 agent 自勾一年未变，相关 issue 在 2026-08 的 backlog 清扫里以「不确定在当前版本还成立」批量关闭。issue 里两种声音并存：要少批的约 9 条，要 spec 与 steering 被遵守的约 13 条，后者更多。

**BMAD。** v4 的治理件（PO 清单、DoD 清单、架构清单、QA 角色与 gate、故事草稿校验、团队包）在 v6 无一原样保留，但去向分三类：变成一段提示词门（PO 清单）、被证明是死门后删除（Ask First "never fired"、DoD 勾选框 "carried no state"、架构清单出厂即全勾）、职能迁到独立的并行评审层（QA）。最有代表性的是「要不要人批」这件事本身在 2026-08-28 交给了模型的路由门，维护者的理由是「零爆炸半径」的硬标准在耦合代码库里不可满足、所以什么都走全套仪式。BMAD 是本表里「加了又删」次数最多的一家，也是维护者书面解释最多的一家。

**GSD。** 没有整体砍治理，走的是固定三步：先加门（几乎全在提示词层），用户抱怨烧 token 与打断多之后把默认值调松、加 `--auto`，旁路造成事故（[#2107](https://github.com/open-gsd/gsd-core/issues/2107) 无人看到确认提示就装了东西）之后再补硬门。真正死掉的是八个从未接线的 `gates.confirm_*`、从不比较阈值的安全门、四十 KB 从未加载的 verify-phase 工作流——三处都是「门在提示词里存在但没人读」。对抗式验证者是全程留住并加严的反例。

**Gas Town 与 beads。** 阶段边界审计已核出：Go 的合并管道完整存在但在 HEAD 无调用方，合并由 Refinery agent 按清单手做；Witness 从「无证据即重置」变成 restart-first。beads 的 gate 节点可表达四型门却不强制任何 actor 的 `bd close`。本轮的提交考古与社区反馈见下文补充段。

**MetaGPT。** 生态审计已核出默认路径把 Engineer 评审与 QA 的 hire 注释掉、改为 TeamLeader 单点路由。本轮的提交考古见下文补充段。

**ruflo。** 它的流失形状与别家相反：不是「门太重被拆」，而是「门先以提示词和占位 JSON 的形式宣传，被社区审计揭穿后，在 v3 用真实现补上或改成诚实报错」。v2 的 Truth verification 在源码里就是 `// Simulate`，v3 直接不迁；SPARC 17 模式退成可选插件里的提示词自检；hive-mind 共识在库里有实现、在 MCP 主路径里是本地等票。留住并在代码里强化的只有发布链路（Ed25519 witness manifest、OIDC 发布门）。

**superpowers。** 维护者用自己的 eval 砍门：子代理评审循环「五个版本各五次试验质量分相同、时间翻倍」于是内联；双评审「贵且易被 gaming」于是合一；对抗性评审「用户很讨厌」于是删；每三任务停一次「浪费人时间」于是删；控制器遇冲突停下「有人一停九小时」于是自主裁决。同一位维护者对「跳过评审」的请求全部拒绝，并写下本表最有分量的一句话（[#1120](https://github.com/obra/superpowers/issues/1120)）："I spent a bunch of time in the run up to 5.0 attempting to tune superpowers to do effort level setting and make decisions about when it wasn't useful to run the review loops and what I ended up seeing was that the model used that as permission to skip steps when they really needed to be mandatory." brainstorming 的设计批准门被砍后又以 `<HARD-GATE>` 加回，是本表唯一一处「因模型跳过而把门加重」的记录。

**agent-os。** 三次重写三次删治理：1.4.1 删决策记录（没人用），2.1.0 删两周前刚加的 Roles 与 verifier（太复杂、bloat），v3 删整条实施与校验流水线（harness plan mode 做得更好）。社区加门的三个 PR 全部未合。砍完之后用户反而在讨论区要求补回校验步骤（[#344](https://github.com/buildermethods/agent-os/discussions/344) "What is missing is any validation step between shaping and implementation."）并考虑降级回 v2；v3 唯一留下的门「必须在 plan mode 里跑」是一句提示词，[#325](https://github.com/buildermethods/agent-os/discussions/325) 证明会被跳过。v3 之后至钉定只有四个提交。

**ccpm。** 一次重构把 38 个命令、4 个 agent、11 条规则和 hooks 全部折成一个 SKILL.md 加五份参考文件，官方理由是跨 harness 兼容。顺带消失的是写侧唯一的硬门 `epic-close`（"Cannot close epic. Open tasks remain"）——v2 只剩「警告」；`issue-close` 变成固定文案 "all acceptance criteria met" 无核查。留住的全是只读脚本。重构后再度停滞：最后提交 2026-03-18，之后的 issue 零回复。

**Taskmaster。** 治理件留在代码里但被放到默认工具集之外：依赖校验不在 `core` 七个工具里，`set_task_status` 在；autopilot 状态机是代码强制的（GREEN 必须零失败、finalize 拒脏工作树），但测试结果由 agent 自报、且整套不在默认路径。0.42 起无人值守 loop 推荐 `--dangerously-skip-permissions`、Docker 沙箱 opt-in。项目 2026-02 后停更导流 SaaS，autopilot 随之停滞。

**mattpocock/skills。** 治理件流失形态最丰富：删仪式（Handoff、事后交接）、硬边界改成可被 agent 自己写的 Notes 覆盖（wayfinder）、清单降为参考（tdd）、设置藏进默认关闭的开关（PR 分诊面）、以及两次没有任何书面理由的静默删门（triage 预览确认、spec 进 triage 流）。所有「加强制」的请求（机器可校验契约、强制校验阶段、hook 强制）维护者一条不接，唯一硬强制件 git-guardrails 被归入 `misc/` 边缘化。他愿意机械强制的只有 import 方向（[#877](https://github.com/mattpocock/skills/issues/877) dependency-cruiser），不是流程。

**tdd-guard。** 钩子拦截这条主路径没删，但从首发一周后就开始加逃生口，之后每一次放宽都由用户的「太严」「误拦」触发并由维护者明说。作者最后承认孤立校验器分不清 refactor，把新项目导向带会话历史、可口头 override 的继任者 Probity。MCP 文件系统工具绕过钩子（[#48](https://github.com/nizos/tdd-guard/issues/48)）一年未关。

**unlazy。** 反例：审批绑定、证据绑定、fail-closed、ABANDON 不算完成，全程收紧；29 个 issue 里没有一条抱怨太多提示，18 位参与者几乎全在要求更严。它的两处「放行」（Stop 钩子可选、六次无进展后放行、歧义时不拦）是设计前提不是后退。但它唯一删掉的东西也很说明问题：v1 用散文规定的 `2^(N-1)` 努力倍增，次日测出「模型忽略它」即删。钉定后一个月只有一个提交，单人维护。

**Foreman 与 SSSF。** 两家都是「一次性发布、随后冻结」。Foreman 在发布前就拆了两道「换不来安全」的门（关 issue、进度评论），删了自定义 HITL 渲染器交给框架默认；留住的返工上限是提示词里的一句话加一个由模型自己数评论的常量。SSSF 唯一「核对声明 vs 现实」的门名实不符（只查文件存在、不查 diff），非作者 issue 给出了一次 5,222 个文件混进绿灯的实测，PR 补上对照真 diff，维护者零回应、零提交。两家的社区反馈里都没有「太重」，只有「门太松」和「没预算」。

## 初步归纳

只归纳事实层面的规律，每条给样本数。样本总数 19（18 家方法论工具加 yoda）。

1. **治理件流失是规律：19 家里 17 家出现至少一处「删除 / 弃用 / 变可选 / 变提示词 / 停滞」。** 未出现的两家是 unlazy（整体收紧）与 SSSF（发布后零迭代，无从流失）。出现次数最多的是 BMAD、superpowers、mattpocock/skills、GSD、spec-kit、OpenSpec，各有五处以上。
2. **「加了又删」的间隔普遍很短。** 同日（BMAD 硬停止→软化、GSD auto 直通承诺→绕过）、次日（unlazy `2^(N-1)`）、一周（Kiro `--trust-all-tools`、spec-kit `/analyze` 子代理）、八天（superpowers SDD 强制→推荐）、两周（agent-os Roles）、33 天（yoda）。超过三个月才被砍的治理件几乎都是「一直没人用」的（agent-os decisions.md、BMAD PO 清单、ccpm 命令集）。样本 11 处。
3. **维护者明说的砍门理由分五类，成本占最大头。** token 与时间成本（superpowers 五处、GSD human-verify 默认关、mattpocock Handoff、BMAD #2760、ccpm "Reduced token usage"、ruflo 300K tokens）；门在提示词里不触发所以宁删勿修（BMAD Ask First、DoD 勾选框、unlazy `2^(N-1)`、mattpocock 事后交接 "rarely fired"、GSD verify-phase "never loaded"）；被 harness 原生能力替代（agent-os v3、superpowers Codex 钩子、OpenSpec `allowed-tools`）；无人值守需要非交互（OpenSpec `--yes`、GSD `--auto`、Taskmaster 0.42、superpowers 九小时卡死、Foreman denied-not-parked）；自述太复杂或 bloat（agent-os 2.1.0、GSD 维护者回复、BMAD #169）。明说理由的样本 13 家；无任何书面理由的静默删门 4 处（yoda、mattpocock 两处、ccpm epic-close）。
4. **「太重」的抱怨主要来自试用一次的外部评测与 HN；仓库 issue 里的用户更多在抱怨门不生效。** 外部：Böckeler、Scott Logic、HN GSD 帖、HN Gas Town 帖、Kiro HN 评论。仓库内两种声音的比例：Kiro 约 9 比 13，mattpocock/skills 要更强制的多于要少摩擦的，unlazy 29 条里零条嫌重、几乎全要求更严，SSSF 只有「门太松」，agent-os 的 bloat 全是维护者自述、用户反而在砍完后要补回校验。两种声音都响的是 GSD 与 superpowers。样本 8 家。
5. **门被砍之后又被加回、或砍松后又收紧的摆动出现在 6 家。** superpowers brainstorming（删六阶段→加 `<HARD-GATE>`，理由是模型跳过设计）；GSD checkpoint（auto 直通→出事后加 `blocking-human`）；BMAD 审查最少发现数（删→加，A/B 证明数量要求有效而人格设定无效）；Kiro 阶段门（0.8.x 丢门→修回）；Taskmaster `generate`（弃用→"after popular demand" 补回）；spec-kit gate fail-open（修补）。摆动的方向一致：**因成本砍、因模型不遵守加回**。
6. **提示词层的门有独特的死法：存在但没人读、或被约束方自己持有豁免。** GSD 八个 `gates.confirm_*` 从未接线、安全门从不比较阈值、四十 KB 工作流从未加载；BMAD 架构清单出厂即全勾、故事校验引用已删文件、Ask First 从未触发；mattpocock wayfinder 的约束与豁免在同一份 agent 拥有的文件里；ruflo 410 处引用不存在工具的提示词；spec-kit 扩展 hook 在 300 行 SKILL.md 末尾被跳过。样本 5 家 10 处。这类门被删时维护者的用词是 "never fired"、"the gate does not gate"、"carried no state"、"models ignore it"。
7. **用代码留住的门全在流程两端，中段判断门无一家用代码留住。** 见上节反例表：代码门 10 家，全部是 merge / publish / mark-ready / 文件系统写入 / 越界回滚 / 状态机终态；「要不要人批」「做完了没有」「评审可不可以跳」三类判断门在 19 家里没有一处由代码判定且输入不由施工模型写（与[阶段边界审计](./methodology-boundaries-20260902.md)「谁判完成」的结论一致）。
8. **「逃生口长成主路径」出现在 5 家。** Kiro Quick Plan 与 1.0 默认自由聊、BMAD Quick Flow 吞并 Phase 4、GSD YOLO 成推荐默认、OpenSpec `--yes` 写进 agent 模板、Taskmaster `--dangerously-skip-permissions` 成无人值守推荐。加逃生口时的措辞都是「快路径，不是跳过结构」（Kiro）或「给有经验的用户」（GSD）。
9. **加门的社区 PR 几乎全部未合。** spec-kit approval-gates 扩展（推回社区仓库）、`--gate-script`、权限门；agent-os 三个 PR；mattpocock #583 静默关闭；SSSF PR #15 零回应；BMAD #2740 被「删掉死机制」的 PR 取代。收下的只有 OpenSpec 的 `skip_specs`（一个显式的逃生口）与 unlazy 的收紧 PR。样本 6 家 9 处。
10. **停滞是比删除更常见的结局。** 加入后无人迭代的治理件：GSD gates 配置、Taskmaster autopilot、ccpm 全部、agent-os v3 后、Foreman 全部、SSSF 全部（含已知假阳性未修）、mattpocock retro / handoff / git-guardrails、yoda 33 天、Kiro `[x]` 自勾与 Correctness 只在 IDE、BMAD 架构清单预勾选 bug 跨三个小版本、tdd-guard 导向继任者。样本 12 家。其中五家（Taskmaster、ccpm、agent-os、Foreman、SSSF）是整个项目一起停。
11. **单人维护是流失的共同背景。** 19 家里由一个人主导提交的有 yoda、agent-os、ccpm、mattpocock/skills、unlazy、Foreman、SSSF、tdd-guard、OpenSpec（实质双人）、BMAD（创始人过半）、Gas Town（1.5 个人加 agent）；治理件删得最干净、最无理由的三处（yoda、ccpm、mattpocock 两次静默删门）全出自单人仓库。样本 11 家。这是相关不是因果，记下备查。
