## 问题

所有者点名读这一节，问两件事：它对 HCTL2 的 Task → Run 转化有什么启发；施工图在施工过程中能不能改。

## 这一节说了什么（只记报告原文里有的）

**协作机制**。DeepSeek Harness 的 Agent Team 模式：一个 lead agent 通过 `spawn_teammate` 异步创建具名、持久的队友，每个队友领一个委派任务；队友起步有两种方式——fresh 模式不带 lead 的历史，fork 模式拿一份 lead 已完成回合的一次性快照。**所有 agent 共用同一个仓库 checkout**，改动彼此立刻可见。通信走持久的点对点信箱（`send_message`）：消息在正在运行的队友的下一个步骤边界送达，让空闲的队友开新回合，让不活跃的队友恢复。lead 用 `list_agents` 看运行状态，用 `wait_agent` 等状态、信箱或共享任务的变化。**任务归属、依赖和建议性的写范围维护在一块共享任务板上**，用四个 `team_task_*` 工具操作，更新带版本检查。只有 lead 能打断队友的当前回合（`interrupt_agent`）。工作完成后 lead 审查并测试合并后的改动，给出最终答复。

**训练**。Agent Team 模式用强化学习训练，奖励由三部分组成：任务表现；鼓励委派与 agent 间通信的协作奖励；以及一个「派生时延」惩罚。派生时延的算法：把执行事件及其协作依赖表示成一张有向无环图，按固定的 prefill 与 decode 速率把 token 数折成成本，加上实测的工具执行时间，取关键路径长度。目的是鼓励有用的并行、惩罚不必要的串行与同步，并降低对服务端批处理与排队延迟的敏感度。

**结果**。报告自称是初步实验，比的是「观察到的最强多 agent 配置」对「可得的最强单 agent 基线」，横轴是**每次 rollout 的墙钟截止时间**。ProgramBench 取参考解在隐藏测试上通过率不低于 95% 的 172 道「金题」，指标 Almost@1（得分不低于 0.95 的 rollout 比例）：多 agent 从 1 小时的 13.59% 升到 8 小时峰值 30.04%，单 agent 对应 12.79% 与 20.39%。FrontierSWE v2 的无 GPU 子集，指标 Mean@5：多 agent 从 1 小时的 13.50% 升到 20 小时的 32.90%，单 agent 从 10.50% 升到 28.20%。每个截止时间都是多 agent 领先。

## 怎么读这些结果

三点边界，都是报告自己给的或从设定直接推出的：

1. **比的是墙钟，不是 token。** 同一截止时间下多 agent 并行跑，消耗的总算力更多；这是「并行换时延」的结果，不是「多 agent 更省」的结果。它与[多 agent 协作有效性](./multi-agent-effectiveness-20260908.md)里「同等 token 下辩论不敌自一致性」的结论不冲突：一个说时延，一个说 token。
2. **模型是专门为这套协作训练过的。** 协作奖励直接鼓励委派与通信，派生时延惩罚直接塑造并行结构。没有这样训练的模型未必有同样的收益；把这个结果推广到任意 harness 的「开团队模式」是过度推断。
3. **最强对最强，初步结果，无消融。** 报告没有拆开说哪一部分贡献了增益——共享任务板、信箱、fork 快照、还是单纯多份算力。

## 对 HCTL2 的启发

下面区分「报告事实支持的」（F）与「我们的推断」（I）。

### 一、Task → Run 的转化：施工图停在承诺尺度，分解在节点里面发生

- F：DeepSeek 的分解是 lead 在运行中做的，任务板上的任务由 lead 动态创建、领取、依赖、更新；没有一张事先画好的图。训练时用的那张有向无环图是**事后**从执行事件重建出来的，用于算奖励，不是执行前声明的。
- I：这正是 HCTL2 已经裁决的分工——施工图的节点是承诺尺度的义务，一个节点的一次尝试（Attempt）内部可以是一整个团队；分解发生在尝试里面，不进施工图。DeepSeek 的 Agent Team 就是「Participant 内部自带图」的一个现成实例。所以 Task → Run 的转化不该追求把义务切细到可以直接派单的粒度：切到「值得独立验收、说得清判据」为止，再细的分解交给执行体。Trigger Preview 里应当能看出一个席位的执行者配置是否是团队模式，因为团队模式的一次尝试烧的 token 与墙钟都不同，预算按节点冻结时要按这个估。

### 二、施工图能不能改：两张图，各管一层

- F：DeepSeek 的执行图在跑的过程中一直在变——新队友、新任务、新依赖——但它从头到尾都在 lead 的进程里，不是任何治理对象；被记录下来的只有事件。
- I：HCTL2 要分清两张图。**治理图**是施工图：批准前冻结，节点是义务，判据二选一，边由结晶或凭证承载，运行中不归约子节点——所有者 2026-09-09 的裁决。**执行图**是一次尝试内部的动态结构：谁派了谁、谁等谁，归执行体自己，随时可变，HCTL 不管也不该管。这一节没有给「治理图应该可变」提供任何证据，反而给「把可变的那层放进执行体」提供了一个训练出来的样本。
- I：可以借的是**事后重建**这一手。执行体的适配器把派生、等待、消息这类事件作为结构化观测上报后，控制面可以从事件重建一次尝试的依赖图，算关键路径——这是「快」的可计算定义：一次 Run 的快慢看关键路径长度，而不是看总 token；总 token 是「省」的账。两个数从同一张事件图上算，都作观测入控制面存储，不进施工图。

### 三、即使在团队内部，依赖也是机械存的

- F：任务归属、依赖、写范围放在共享任务板上，用工具读写，更新带版本检查；信箱是持久的，送达有明确的时机语义。
- I：这补强了[依赖图与协作](./prove2me-dag-collaboration-20260908.md)的第二个命题——「依赖用机械方式存，不写散文」——在另一个尺度上也成立：不只是跨模型的大项目，一个模型自己的团队也把依赖放在带版本检查的板上，而不是靠信里说。对 HCTL2 的落点：本地 Agency 参考实现若接 DeepSeek Harness 这类团队模式，任务板的更新事件应作为结构化观测进 Execution Chat 投影，让人能看见尝试内部的图，同时它不进治理。

### 四、写范围是建议性的，隔离边界在尝试不在队友

- F：所有 agent 共用一个 checkout，改动立刻互见；写范围只是「建议性的」，靠任务板协调而不是靠锁。报告没有报告冲突率。
- I：这与 HCTL2 的 ChangeSet 与写租约不矛盾，只要把边界画对：**隔离边界在一次尝试**——一次尝试独占一个 ChangeSet 与工作树，团队里的队友共享它，那是尝试内部的事；**跨尝试、跨席位之间才是租约与独立工作树**。评审席位也不该看到队友之间未封存的中间状态，它拿的是封存后的 ChangeSet Revision。这条应写进 Participant 正文的一句话，防止把队友当成席位。

### 五、fresh 与 fork：上下文按快照给，不共享活体

- F：队友起步要么不带 lead 历史，要么拿一份 lead 已完成回合的一次性快照；没有持续同步的共享对话。
- I：与 HCTL2「每个席位拿自己的包、不看彼此发言、包是冻结快照」同向。fork 模式相当于我们的 Context Bundle 里内联前序结果；fresh 模式相当于只给指针。

## 采用结论

**仅参考行为**。协作机制的具体工具（`spawn_teammate`、`team_task_*`、`wait_agent`）属于 DeepSeek Harness 的接入面，若本地 Agency 参考实现接它，走 harness 适配器的结构化事件归一（生命周期、工具调用、权限请求之外，加一类「团队事件」），不成为 HCTL2 对象。派生时延的算法（事件图关键路径）值得作为「快」的度量借鉴，属于计量方式，不是依赖。

## 未查到与边界

- 报告没有公开 Agent Team 的任务板与信箱的接口规格、冲突率、每次 rollout 的 token 总量；「派生时延」的 prefill 与 decode 速率取值未给。
- 结果是初步的、无消融的、最强对最强的；以上推断没有把它当作「团队模式普遍更好」的证据。
- 本文只读了 §5.3.5 与 §5.3.4 末段、§6 开头，未读其余章节。
