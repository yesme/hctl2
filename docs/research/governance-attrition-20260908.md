# 治理功能为什么活不长：33 家的跨族归纳与对 HCTL2 的含义

> 类别：跨候选归纳 · 证据编号：E-GOVERNANCE-ATTRITION<br>
> 状态：调研归纳 · 日期：2026-09-08；发布后正文不改，只在文末追加复核记录<br>
> 逐家证据在两篇分册：[工作台类 15 家](./governance-attrition-workbench-20260907.md)、[方法论类 19 家](./governance-attrition-methodology-20260907.md)；总览与复用决策用语见 [docs/research/README.md](./README.md)。

## 问题与样本

起因是 [Yoda](./workbench/yoda.md) 的 Feature Delivery：六阶段、只有人能批准的治理流程，一个晚上加了一万八千行，活了 33 天没有一次迭代，在一个标题叫 fix(privacy) 的提交里被顺手删掉。所有者问：别家有没有同样的事？于是把我们调研过的产品翻了一遍——工作台与 Agent 协作平台 15 家，方法论、编排与纪律工具 19 家（Yoda 两边都算），去重 33 家。查的是同一件事：**治理性或结构性的功能**（看板与任务状态机、阶段门与审批、规格或契约冻结、多 agent 编排与角色、评审门、返工上限、验收与证据）加进来之后，有没有被删、弃用、藏进开关、简化成提示词、或长期无人迭代；社区里有没有「太重」的声音；谁把门留住了、靠什么。两篇分册只记事实与维护者原话，推断单列；本篇归纳，并写对 HCTL2 的含义。

## 一句话结论

**治理件流失是行业规律，不是 Yoda 的个案**：工作台 15 家里 9 家、方法论 19 家里 17 家出现过至少一处删除、退役、藏开关、变提示词或停滞。真正的反例只有几家，而且它们留住的门有共同形状。

## 五条跨族规律

### 一、活得短，死得静

有明确加入与退出时间的自造治理功能，两边合计二十多例，**没有一例活过半年**：Yoda 的 review-loop 状态机 33 小时，Feature Delivery 33 天；BMAD 的硬停止当天软化，unlazy 的指数退避次日撤回，Kiro 的全信任开关一周，superpowers 的强制规格驱动八天变推荐，agent-os 的角色两周；emdash 的看板与 Best-of-N 四个月，Orca 的自动调度器三个月，Multica 的验收字段不到两个月。活过三个月才被砍的，几乎都是一直没人用的。

删除普遍不写进变更记录：工作台 5 家（emdash 博文只说「不在这版里」，Yoda 三件大砍不进 CHANGELOG，Orca 只在 PR 正文一句），方法论 4 处静默删门无任何书面理由，全出自单人仓库。写清楚的反例是 first-tree，每次退役都进 release notes。

### 二、死因不是「用户嫌重」，是「门不生效」加成本

这是最出乎意料的一条。抱怨「太重、我只想开个终端」的声音确实有，但**集中在 HN 上试用一次的人**：Superset、Conductor、emdash 的发布帖，加 Multica 一篇长文；方法论那边是外部评测与 HN。**仓库 issue 区里，要「更多机械约束」的用户多于要「更少」的**：工作台 7 家有用户要后端状态机、等待审批列、规格驱动、任务生命周期，无一被实现；unlazy 的 29 条 issue 零条嫌重、几乎全要求更严；agent-os 砍完「臃肿」之后用户反而要补回校验。

维护者自己说的砍门理由分五类，按出现次数：token 与时间成本；**门在提示词里不触发，所以宁删勿修**——原话是 "never fired"、"the gate does not gate"、"carried no state"、"models ignore it"；被 harness 原生能力替代（plan mode、审批、钩子）；无人值守需要非交互；自述太重或不可达（「neither reachable nor editable」「shrunk to a residue」「unused in practice」）。

### 三、用代码守住的门全在流程两端，中段判断门无一家守住

方法论 19 家里用代码留住的门有 10 家，**全部落在两端**：出货边界（合并、发布、标就绪、关单后的合并证明）和文件系统写入（必问路径、越界回滚、TDD 写入拦截）。流程中段的三类判断门——**要不要人批、这一步做完了没有、评审可不可以跳**——19 家里没有一处由代码判定且输入不由施工模型写。这与我们的[阶段边界审计](./methodology-boundaries-20260902.md)「谁判完成」一节的结论完全一致。

工作台那边同一形状：治理从产品状态机退到提示词或 skill 层 7 家（Orca 调度器变 agent 自己的循环，Multica 的写入纪律挪进 skill，Yoda 的 review-loop 状态机换成通用提示词引擎，emdash 自建的计划层拆掉改透传 CLI）。反向的只有三处：Cumora 把列语义从散文改成机器可读的 kind 列，Multica 把领队角色从提示词改成结构字段，Codeg 的阶段提示词、排队与失败即停。

提示词层的门还有独特的死法：存在但没人读（GSD 八个确认门从未接线、四十 KB 工作流从未加载），或**约束方自己持有豁免**（mattpocock 的约束与豁免在同一份 agent 拥有的文件里；BMAD 的清单出厂即全勾）。

### 四、留住的治理面都绑在外部既有事实上

工作台 15 家里留住并持续迭代的治理面，无一例外绑着一个外部系统已经在维护的事实：工单镜像 5 家、PR 与 diff 评审门 7 家、透传 CLI 原生的计划与审批 4 家、定时自动化 6 家。**自造的跨任务阶段门或角色编排**，留住并迭代的只有 5 例，而且都很薄；退出或停滞的 7 例。

看板是最好的对照：15 家里 9 家加过，删 2、降格 2，另有 3 家用户开 issue 要而没被接。**留住的看板，列都绑到机器可判定的状态**——Superset 泳道来自 workspace 与 PR 状态，Cumora 的 kind 列，Codeg 的排队、准备中、已评审；被拿掉的是人工自由拖动的列（emdash、vibe-kanban）。Yoda 8 月新做的看板窗干脆写明「只观察不接管」。

### 五、摆动、逃生口与集中删除

- **摆动方向一致：因成本砍，因模型不遵守加回**。方法论 6 家有这种来回：superpowers 删了六阶段又加 HARD-GATE，GSD 直通出事后加 blocking-human，BMAD 删了评审最少发现数又加回（A/B 证明数量要求有效而人格设定无效），Kiro 丢了阶段门又修回。
- **逃生口长成主路径**，5 家：Kiro Quick Plan、BMAD Quick Flow、GSD 的 YOLO 成推荐默认、OpenSpec 的 `--yes` 写进 agent 模板、Taskmaster 的跳过权限成无人值守推荐。加逃生口时的措辞都是「快路径，不是跳过结构」。
- **社区提交的加门 PR 几乎全部未合**，6 家 9 处；收下的只有显式逃生口和 unlazy 的收紧。
- **重写与迁移是集中删除的时机**，5 / 15：emdash 的 v1 一次改 1,499 个文件并同日关 43 个 issue，vibe-kanban 云化，Crystal 换代成 Nimbalyst。
- **单人维护是流失的共同背景但不是决定因素**：方法论篇里删得最干净最无理由的三处都出自单人仓库；工作台篇里三家单人产品结局相反（Yoda 大砍、Codeg 周周加、Cumora 静止）。与整体退出相关的是商业压力：vibe-kanban 停业时说「couldn't find a business model」。

## 对 HCTL2 的含义

下面是我的判断，分「已有立场得到印证」和「新的建议」两类。

**印证了的立场**

1. **我们的差异化恰好落在全行业的空白处，风险也恰好在这里。** 33 家没有一家用代码守住中段判断门——完成、验收、评审可不可以跳。HCTL2 把这三样放进账本：完成只由有权的人或绑定契约的 Run 正常完成后的归约器提交，凭证逐项绑证据，评审席位与票是账本记录。这是别人没做的事，也是别人做了都没留住的事；「没人做成」既是机会，也说明它难在生存而不在设计。
2. **「能用代码管的不用提示词管」得到 33 家的反证支持。** 所有靠模型自觉的门在样本里全部软化或死亡，死法是「never fired」；我们「Skill 给方法、账本给门」的立场（见 [Participant 正文](../design/participant.md)）是对的，不能松。
3. **门要绑在既有事实上才活得久。** 我们已经这样做：合入凭证绑 Git 回读，外部机械事实前置只由工具箱读回，证据分三级且工具箱回读最高，契约正文冻结在 Git。验收项的校验等级里 `mechanical` 应当是默认与多数，`human` 是少数。
4. **看板列必须是派生的。** 我们的泳道由生命周期、本地阶段与外部投影共同派生，人不能把卡拖成「完成」。留住的看板都是这个形状。
5. **删除要留痕。** 静默删除 5 / 15；我们「约束变更推进版本、小修订进台账、新约束配失败用例」的纪律正是 first-tree 那种反例的做法，坚持。

**新的建议**（B 档，所有者不反对就按此落）

6. **逃生口不绕账本。** 我们也有逃生口：无契约的卡、无 Run 的轻量路径、法定票数可为 1。样本说逃生口会长成主路径，所以设计上要保证逃生口降的是**治理强度**而不是**记账**——无契约卡仍有身份映射、完成仍需凭证、一票评审仍是账本里的票。建议在交付文档的产品验收里加一条：任一逃生口走完，账本里仍有可回溯的对象与凭证。
7. **把「never fired」变成一个指标。** 别家的门死于没人发现它没在工作。建议自举阶段（B2 起）统计每条门的触发次数与绕过次数；一条门在连续若干个真实变更里从未触发或全部绕过，就要重新审视它是该修还是该删，并且删要进台账。这是把样本里的死因转成早期信号。
8. **主路径必须真的走过。** Yoda 的 Feature Delivery 死于「从未进入主路径」。我们的对应物是无 Run 轻量路径的「人的预览不超过两次」与自举门 B2 到 B5：HCTL2 必须用自己的门治理自己的开发，而不是只在测试样例里通过。这一条已经在交付文档里，这里只是把它的分量提到「生存条件」。
9. **让 PR 评审门作为一种证据来源接入，而不是与之竞争。** 行业留住的评审门是 PR 与 diff 评审（7 家）。我们的 Task 正文已经允许「接受外部 SCM 评审时引用可回读的精确外部证据」；建议在 Gate 策略里把「外部 PR 评审通过」明确列为一种可声明的席位证据等级，让用户从熟悉的门迁移过来，而不是先放弃它。
10. **警惕重写。** 集中删除都发生在重写与迁移时。我们将来若重写 control 或 Workbench，要求重写 PR 对每条被拿掉的门单独写台账行，不允许「不在这版里」。

## 未查到与边界

- 两篇分册各自的「未查到」已列；本篇不重复。
- 样本全部是开源或有公开变更记录的产品，闭源产品（Grok Bot、Conductor、Helio 的一部分）只能看官网与公开讨论，删除可能被低估。
- 「治理性功能」的判定由我们下，边界在分册的问题一节；把看板、自动化这类结构性功能一并计入，是为了不漏掉「治理退到工具」的路径。
- 相关不是因果：单人维护、商业压力与流失的关系只记为观察。
