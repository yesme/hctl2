## E-YODA · Yoda

### L1 核心价值与产品闭环

Yoda（LovStudio 出品，全称 "Your Orchestra of Delegated Agents"）是一个 Electron 桌面应用，把本机装好的编码 agent CLI（它叫「客户端」，旧称 Runtime；注册表里 31 家）收进一个工作区。官方文档给的公式是「任务 = Runtime（在哪跑）× Agent（以什么角色跑）」：Runtime 是 Claude Code、Codex 这类可执行程序，Agent 是用户自己定义的「System Prompt + Skills + 首选模型」，不绑定任何 Runtime。

它的完整闭环是：把仓库注册为 Project（可归入命名 Workspace 分组），从提示词或外部工单（Linear、Jira、GitHub/GitLab/Forgejo Issues、飞书任务等十三家）创建 Task；Task 二选一——「主分支直跑」不建分支不开 worktree，或「worktree 隔离」每任务一个分支加 git worktree；Task 里跑一条 agent 会话（钉定版本明确「一个任务就是一条会话」，再上一个 agent 走共享 worktree 的兄弟任务，fork 直接生成新任务）；会话是真 PTY + xterm.js，可用 tmux 包住以跨应用重启存活；人在 Changes 视图看 diff，合并、cherry-pick 或丢弃；最后归档——归档前可自动向会话注入一条预设的 Skill 或命令（比如让 agent 把改过的文件提交好），等它跑完再归档，归档意图先落库、崩溃后可续。多 agent 场景由「开发范式」承载：单 Agent（vibe coding）、Team（一个 Coordinator 领着按需拉起的 Worker，在同一 worktree 里经 `team-at` 脚本互相派活）、Compare（同一需求多份并行任务）。

产品自我定位不是任务治理而是「Harness 观测」：README 说「提示词只是表层，agent 的实际行为由它加载的 Skills、Hooks、Memory 和上下文决定」，Yoda 把这条链路逐项摊开、可覆写。这决定了它的工程重心在会话与终端层（源码里 `conversations` 178 个文件、`agent-hooks` 54 个、`pty` 41 个，对比 `tasks` 78 个、`team-rooms` 17 个），与 HCTL2 关心的「承诺与完成」只在边缘相交。

### 审计基线与许可

固定实现基线为 [`main@960fd322`](https://github.com/lovstudio/yoda/tree/960fd3224508edc52fb7e99d9e8f8cf1723ad683)（2026-09-04，提交信息 "chore: release v0.20.3"），与最新发布版 [`v0.20.3`](https://github.com/lovstudio/yoda/releases/tag/v0.20.3)（同日）是同一个 commit。发布节奏很密：v0.19.1（08-13）、v0.20.0（08-16）、v0.20.1（08-17）、v0.20.2（08-19）、v0.20.3（09-04）。

**血缘：它是 Emdash 的硬分叉。** [`LICENSE.md`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/LICENSE.md) 原文是 Apache License 2.0 全文，版权行为「Copyright 2026 LovStudio / Portions Copyright 2026 General Action, Inc.」；General Action 是 [generalaction/emdash](https://github.com/generalaction/emdash)（YC W26，Apache-2.0，5.6k stars）的公司。仓库 API 标 `fork: false`，是脱离 GitHub 分叉关系的拷贝，但 git 历史完整保留：最早提交是 Emdash 作者 2025-09-12 的 "first commit"，Yoda 自己的历史从 2026-05-11 的 v0.1.0 开始，分叉点对应 Emdash 2026-05-10 的主干。截至钉定版本全仓 8,376 个提交，其中 2026-05-10 之后 3,167 个，3,160 个出自同一位维护者 MarkShawn2020——实质是单人项目；GitHub 列出的 100 位贡献者绝大多数是继承来的 Emdash 作者。README 关于分叉来源没有说明，CHANGELOG 0.3.8 只留了一句「移除旧的 Emdash 数据目录自动迁移路径」。许可上 Apache-2.0 允许移植源码，但移植 L1 代码时应回到上游 Emdash 审计，而不是从 Yoda 抄。

社区体量：71 stars、22 forks，创建于 2026-05-10，最近推送 2026-09-04。issue 与 PR 合计只有 17 个编号（3 个 open issue），Yoda 时期的外部提交者 4 人、约 7 个提交（Windows 崩溃、迁移、更新器修复）。这是活跃的单人产品，不是社区项目。

技术栈：TypeScript（约 14.6 MB）+ Electron/electron-vite/electron-builder；渲染端 React + MobX + TanStack Query + xterm.js；主进程 Drizzle ORM + SQLite（better-sqlite3）+ node-pty + ssh2，tmux 作为可选会话外壳；另有 `packages/protocol`（与手机端共享的 wire 协议）、`services/relay`（公网中继）、`native/`；手机端在独立仓库。仓库结构是 `src/main/core/<领域>/` 每域一个 `controller.ts` 自动注册成类型化 RPC，`src/shared/` 放两端共享类型与客户端注册表，`agents/` 是面向 agent 的仓库地图，`docs/adr/` 有九份 ADR。

**官方文档与钉定源码的四处出入**，引用时要区分：

- 文档站「运行模式」列五种（normal / brainstorm / compare / review / team）；源码里范式只有三种 kind（`single`、`team`、`compare`），`brainstorm`、`review`、`build` 被列为「已退役的运行模式」并强制折回 normal，`compare` 不再单独出现在选择器里。
- 文档站「会话与对话」说「一个任务可以开多个会话」；0.20.1 起改为「任务即会话」，0.20.3 的 `createConversation` 会拒绝往已有未归档会话的任务里再插一条（Team Room 成员席位是唯一例外）。
- 文档站有整页「Feature 开发闭环」、仓库内 `agents/architecture/features.md` 也在，但 Feature Delivery 的全部代码（主进程 `features/`、`shared/features.ts`、`feature-workflow.ts` 与界面，31 个文件）已于 2026-08-15 在一个标题为 "fix(privacy)" 的提交里整体删除；`features` 五张表只剩在 0038/0039 号迁移里，`schema.ts` 中已无。
- 客户端数量：README 说 32、`providers.md` 说 30、文档站说 27，注册表实际 31。

### 家族归属

按[方法论家族地图](../methodology-landscape-20260824.md#一家族地图已知五族的校准--新七族)，Yoda **以「会话多路复用 / 并行 worktree」族为主，「编排器」族为辅；角色模拟只是提示词皮肤**。

- 主族证据：内核继承自 Emdash——人保留全部分派与裁决权，工具只管 N 个并行会话的生命周期与 worktree。Task 的两种隔离级别（[`CreateTaskStrategy`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/shared/tasks.ts) 里的 `new-branch` / `checkout-existing` / `from-pull-request` / `no-worktree`）、tmux 包裹、每家客户端的 resume 标志与终端输出分类器，都是这一族的标准装备。
- 辅族证据：Team Room 走的是编排器路线——[ADR 0007](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/docs/adr/0007-coordinator-led-agent-room-orchestration.md) 说「Yoda 是持久的编排内核，不是又一个推理 Agent」，负责身份规范化、持久化每次分派、只在目标会话接受后才回 ack、观察会话终态并把完成事件送回 Coordinator、重启后恢复待处理分派与路由预算。这些是编排器的机械骨架。但拓扑不在代码里：ADR 明确拒绝「只用固定 DAG」，下一步由 Coordinator 模型临场决定——这一点向群体自治族漂。
- 角色模拟：Team 范式默认 roster 是 `spec`（leader，Claude）/ `implementer`（Claude）/ `reviewer`（Codex），三个角色都是 builtin Agent 的系统提示词（[`kinds.ts`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/shared/paradigms/kinds.ts)）；[`presets.ts`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/main/core/team-rooms/presets.ts) 自己写明「团队的实际工作流（评审环、扇出…）住在 leader Agent 的系统提示词里，引擎只转发 @ 消息」。这正是地图里「角色是提示词层的东西」的判断。
- 可选的「系统记录寄生」：Team Room 的工作记录可选 GitHub 模式，把 Issue / PR 当持久协调记录、本地轮询 `updated_at` 唤醒 leader。
- 一段未存活的 spec 驱动 / 阶段门尝试：Feature Delivery（六阶段、仅人批准、产物默认草稿、上游变更使批准过期）2026-07-13 加入、2026-08-15 删除，详见「完成判定权」。

### 四层设计亮点与边界

| 层 | 真正深入且独特的证据 | HCTL 的采用方式与边界 |
| --- | --- | --- |
| L4 | 弱，但有三块可点名的机制。**项目切面（facet）**：项目内长期存在的子范围（手机端、插件面、文档站），Task 记录自己属于哪个切面（membership），与 `parentTaskId`（lineage）分开；切面带 `paths` 与 `contextFile`，后者是仓库相对路径而不是内联内容——源码注释说「agent CLI 已经会按目录层级解析 AGENTS.md / CLAUDE.md，指向真文件让它按需读深，而不是我们重造继承」；开会话时注入成一段系统提示。**提示词库**：可嵌套分组、语义化版本历史，统一承载全局 / 项目 / 系统提示词；另有 `runtime_instruction_file_versions` 表给经界面改过的 memory 文件留版本。**Harness 观测**：[`harness.ts`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/shared/harness.ts) 为 claude / codex 各声明一份表面规格——memory 文件按加载优先级、Skill 目录、slash 命令目录、subagent 目录、settings 文件、MCP 声明来源；hooks 检查器可查看注册来源、执行日志并持久化覆写。没有项目级持久 Room：Team Room 是挂在单个 Task 上的多 agent 群聊，人是叫 `you` 的一个成员；Workspace 文档自己说「只是组织层，不影响隔离边界」。 | 采用三点行为：切面的「成员关系与血缘分开、上下文给路径指针不给内联文本」可进 Context Manifest 的来源分块；memory 文件版本化对应愿景里「上下文无来源、无版本」的失败模式；按 harness 声明表面规格的做法可作 Participant 档案里「这家 harness 从哪些文件取指令」的字段形状参考。不采用：Workspace 充当 Project、Team Room 充当 Room、提示词库充当知识准入。 |
| L3 | Task 是独立行，身份不依赖 worktree（`no-worktree` 策略合法），有 `todo → in_progress → review → done / cancelled` 生命周期、`statusChangedAt`、`needsReview` 人工标记、归档意图 `archiveRequestedAt` 与归档备注、父子树、切面归属、以及启动时的范式快照（`paradigmId / paradigmKind / paradigmParams` 按当时值冻结，源码注释说「不能到时候再经 id 读，否则范式一改历史就失真」）。**两条状态链路彻底分开**：ADR 0008 与 `AGENTS.md` 都写明 Task 生命周期走 `taskStatusUpdatedChannel`、Agent 运行态走 `agentSessionStatusChangedChannel`，「两条链路语义独立，不能用其中一条替代另一条」。看板列只有四列，`cancelled` 与归档不上板；独立的 Agent 看板窗口「只观察不接管」，卡片摘要「从不按需生成」。归档是可恢复的分阶段流程：先写意图，再对每条活会话注入归档前命令并等它 settle，再归档会话，再核实运行时回收（tmux 分离会话全部清掉才算 `confirmed`），回收未确认就保留 worktree，最后才标归档；没做完的归档在启动时续。但 `updateTaskStatus` 没有预期版本、没有操作者、没有事件账本（只有遥测），看板拖卡后触发的「栏目钩子」会向该任务所有活会话注入提示词或跑 shell 命令，且「永远不能阻断或回滚移动本身」；`createTask` 默认初始状态直接是 `in_progress`。 | 采用为 L3 行为证据：Task 身份与 worktree 解绑、范式参数在启动时冻结、生命周期与运行态双通道、看板只投影不接管、「先写意图—逐步回收—回收确认后才动 worktree—启动续跑」的归档流程。边界证据：没有 Task Revision、验收条款或证据绑定，`review` 只是一列，`done` 可以被任何调用方直接写；栏目钩子是「拖卡即施工授权」的反例（Codeg 条目已列同类边界）。不采用 Task 与会话合一的身份模型。 |
| L2 | **Team Room 的持久分派协议**是它在 L2 唯一深入的东西。[`conductor.ts`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/main/core/team-rooms/conductor.ts) 说「路由不是从 agent 输出里刮出来的」：agent 只能经 `team-at <handle> "<msg>"` 脚本走本机 HTTP hook 端点投递，每位成员的脚本单独生成、把自己的 ptyId 烘进脚本（因为 Claude 的 Bash 工具和 Codex 沙箱都不可靠继承 PTY 环境变量）；脚本保留 HTTP 响应体，「让一次成功的 HTTP 交换不能伪装成一次成功的分派」——这是 ADR 0007 记录的真实事故的修法：Planner 写 `@implementer`、路由器比对存的 `implementer`、没匹配上却返 200，Planner 以为派出去了而 Implementer 一直空闲。分派消息带 `deliveryStatus`（pending / delivered / failed）落库，投递失败记诊断文本；路由跳数预算（默认 100）由人的新提示刷满、agent 消息消耗，主进程重启后恢复待投递消息并重置预算「而不是让预算看起来已经耗尽」；成员回合结束由运行态（stop hook / transcript / 输出分类器）判定，未显式 hand-off 的结束自动把控制权交回 leader；Coordinator 结束且未 hand-off 即视为工作流完成，控制权回到人，「没有后台 Agent 去猜下一步」。工作记录（会话转录 / 房间消息 / 共享文件 / GitHub Issue-PR）是适配器不是传输，`syncToRoom` 只管展示。Automation 是 cron 触发的 agent 任务，`automation_runs` 记 running / success / failed / skipped。 | 采用为 L2 专项行为证据：「投递已接受 ≠ 分派成功」的显式否定 ack、分派记录持久化且带诊断、重启恢复预算而非清零、有界级联、用运行态而非刮屏判回合结束、Coordinator 无 hand-off 即终止而不猜下一步。边界证据（都是反例）：分派的物理形态是把提示词敲进目标 TUI 再按回车，ack 的含义只是「PTY 还活着且接受了写入」；没有冻结的 Workflow，拓扑由 leader 模型临场决定；reviewer 的结论是散文 PASS；Automation 把会话第一次 `completed` 记作运行成功。HCTL2 的 Obligation / Seat / Attempt / Verdict / Receipt 在这里没有对应物。 |
| L1 | **深且是它的重心，但多数继承自 Emdash。** 运行态是一个纯函数 reducer（ADR 0008：主进程 `AgentSessionRuntimeStore` 是唯一权威，渲染端只是读模型），输入来自三类独立来源：写进 `.claude/settings.local.json` 的带标记 hooks（Notification / Stop / UserPromptSubmit，另用 `PreToolUse` 匹配 `AskUserQuestion\|ExitPlanMode` 补「等人」态）、Claude transcript JSONL 的确定性判读（最后一条用户消息与最后一条 `stop_hook_summary` 谁在后；用户按 Esc 时 Claude 写下的哨兵行特判）与 Codex rollout、以及每家客户端一个正则刮 4 KB 终端尾巴的分类器。另有每 15 秒一轮的对账器，理由是「运行态不能依赖被人看着」；会话的最后运行态落库，重启后读回时「存着 running」一律解读为 `interrupted`。PTY 侧：钉定版本把本地 PTY 移进独立 utility 进程（实测主线程被 Chromium 原生工作卡住 107–689 ms，「PTY 读取在同一个事件循环上无法被保护，只能搬走」）；tmux 重接必须确认「同一 pane pid、同一创建时间、已连接客户端数增加」才算接上，「PTY 打开成功本身不是证据」；风险清单写明「死掉的 PTY 只证明传输死了」，tmux 后端的客户端 CLI 活在 pane 里、比每个 attach 包装都长寿，任何意外的包装死亡都要先对 tmux 核实再报 Agent 退出；空闲休眠只回收无消费者的 `idle` / `completed` 会话。输出链路有代次隔离重生、序号拼接快照与实时数据、xterm 写入 ACK 释放背压、消费者租约 90 秒、只续租不推进水位 10 秒即失去背压投票（防渲染端卡住把 PTY 永久暂停）。ADR 0009 承认「首帧静默栅栏是已知缺陷」，把历史面从终端搬到 transcript——但只覆盖 claude 与 codex 两家，其余 29 家「终端就是唯一会话记录」，且「TUI 拥有交互：权限提示、slash 菜单、计划批准都只在终端里」。 | 采用为 L1 行为证据：三源独立推导运行态加不依赖观察的对账；「存着 running 即 interrupted」对应 HCTL2 的「丢失」；传输死亡 ≠ 参与者退出 ≠ Run 失败的分层判定；tmux 重接的三重确认；hook 端点文件 `~/.yoda/hook-endpoint.json` 取代 spawn 时捕获的端口环境变量（主进程重启不失联）；消费者租约与 ACK 停滞豁免。这些与 Superset、Stably Orca 条目互补，不改变 HCTL2 以 Herdr 承载 PTY 的选型；若要移植代码，源头应是上游 Emdash 而非 Yoda。 |

### 完成判定权

HCTL2 立场：Task 完成只接受有权人类命令，或绑定 Task 的 Run 正常完成后的确定性归约。Yoda 钉定版本里能把 Task 状态改成 `review` 或 `done` 的路径逐条核对如下。

| 路径 | 谁说「做完了」 | 源码实况 | 与 HCTL2 立场 |
| --- | --- | --- | --- |
| 看板拖卡 | 人 | [`moveTaskStatus`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/main/core/tasks/operations/moveTaskStatus.ts) 直接写状态并广播，随后触发该栏目配置的钩子（注入提示 / 跑命令 / 通知），钩子「永远不能阻断或回滚移动」；[`updateTaskStatus`](https://github.com/lovstudio/yoda/blob/960fd3224508edc52fb7e99d9e8f8cf1723ad683/src/main/core/tasks/operations/updateTaskStatus.ts) 无预期版本、无操作者、无验收条款、无事件账本 | 「人点」同向，但没有契约与证据可校；`done` 只是一列 |
| 任意客户端调 RPC | 任何调用方 | `tasks.updateTaskStatus` 直接暴露在 RPC 路由上，主进程不区分人、界面还是自动化 | 违反：没有准入信封 |

读法：Yoda 有两处同向碎片——Issue Worker 把运行结束只归到「待审」，Feature Delivery 曾把批准权只留给人——但前者只覆盖无人值守领工单这一条路径，后者已被删掉；主路径（看板列、Team Room）都留着模型或任意调用方直接写 `done` 的门。它的产品选择是把 Task 收窄成「一条会话加一个 worktree」，完成判定交给人在 Changes 视图里看 diff；治理层越重越先被砍，这与地图里「同向碎片散落、没有一家做成不可绕过的系统边界」一致。

### 与 HCTL2 的关系与启发

**同赛道，重心错位。** Yoda 与 HCTL2 都是多 Harness 桌面工作台，都用「Runtime × 角色」的分解，都做 worktree 隔离、工单进会话、tmux 存活。但 Yoda 的价值主张在 L1（观测 harness、让终端不掉线）和「快」（主分支直跑、任务即会话、归档即收尾），HCTL2 的价值主张在 L3/L2（承诺冻结、证据绑定、合入钥匙不进工具）。Yoda 把 HCTL2 愿景里的两种失败模式当成产品选择：「Harness 完成被误当项目完成」（Team Room 结束即 done）和「Room / Task 等同于会话 / worktree」（任务即会话）。所以它主要是 L1 行为证据与 L2/L3 边界证据的来源，不是模型来源。

**它做对了、我们没有的**：（1）运行态三源独立推导加周期对账，明确「运行态不能依赖被人看着」，并把落库的 running 读回成 interrupted；（2）把「HTTP 200 不等于派出去了」这类假成功当成一等事故写进 ADR 并修在协议层（保留响应体、负向 ack 带诊断）；（3）范式参数在 Task 启动时快照，不经 id 回读；（4）归档是「先写意图、逐步回收、回收确认才动 worktree、重启续跑」的分阶段流程；（5）per-harness 的表面规格声明（memory / skill / command / subagent / settings / MCP 各从哪个文件取）做成数据而不是散在代码里；（6）ADR 0009 把「首帧静默栅栏」诚实标为缺陷并给出每一步可独立回滚的分阶段方案。

**我们明确不采用的**：Task 与会话合一；Workspace 当 Project、Team Room 当 Room；看板拖卡即施工授权（栏目钩子向活会话注入提示词）；leader 结束回合即 `done`；Automation 的 `completed` 即成功；把提示词敲进 TUI 当分派协议、PTY 接受写入当 ack；reviewer 散文 PASS 当裁决；拓扑由模型临场决定；用系统提示词禁止「客户端原生 subagent」当强制层（Yoda 的 teammate 提示词写了这条禁令，但没有任何机械拦截）。

**对四个模块的具体启发：**

- **Project / Room**：Context Manifest 的来源分块可以借「切面」的两条纪律——成员关系（属于哪个范围）与血缘（从哪个 Task 分出来）是两个字段，不合并；上下文条目优先给仓库内路径指针并声明「读它再改」，不内联正文。memo 或指令文件经界面改动时留版本，对应 `runtime_instruction_file_versions` 的做法。
- **Task / Kanban**：Task 状态与 Participant 运行态双通道分离已是 HCTL2 立场，Yoda 提供了一个生产系统里两条链路各自恢复、互不替代的实证，以及一个反例（拖卡触发施工）。Issue Worker「运行结束只到待审、并立刻释放并发槽位」可以作为 Task 外部来源自动领取时的默认归约形状。归档 / 关闭应先落意图记录、可续跑，这与 HCTL2「先记账再执行」一致。
- **Run / Workflow**：ADR 0007 的机械骨架（身份规范化、每次分派持久化、目标接受后才 ack、负向 ack 带诊断、有界级联且重启恢复预算、完成事件回流给协调者、协调者无 hand-off 即终止不猜下一步）可以作为 Seat / Attempt 投递层的对照清单；`@implementer` 对 `implementer` 返 200 的事故是「投递成功 ≠ 分派成功」最好的教学反例，HCTL2 的 Attempt 领取必须以受派者确认为准。Feature Delivery 被删这件事本身是给 HCTL2 的产品告诫：仅人批准、产物默认草稿、上游变更使批准过期这套形状是对的，但如果单人用户感到它在「快」上不划算，它会第一个被砍；HCTL2 的无 Run 轻量路径（「人的预览不超过两次」）正是为此存在。
- **Participant / Terminal**：Herdr 适配器应采纳「传输死亡 ≠ 参与者退出」的分层：先向运行服务核实执行体是否还在，再决定是重接、丢失还是失败；tmux 类重接要求同一实例（pid、创建时间）与客户端数增加的三重确认；hook 回调端点用固定文件而不是 spawn 时的环境变量，让 control 重启后 harness 仍能回调；对无结构化事件的 harness，正则刮屏分类器只能给「等人 / 空闲」的提示，不能给终态。ADR 0009 的边界（transcript 只覆盖两家、TUI 拥有交互）也提醒 HCTL2 的结构化执行投影不能假设每家 harness 都有 JSONL 可读——这与 `harness-adapters.md` 的「JSONL 观察与双向审批分开声明」一致。

### 采用结论

**仅参考行为（Behavior reference）。** 理由：（1）它没有可独立采用的二进制、服务或库——一切都在 Electron 应用内部；（2）没有值得适配的协议——`team-at` 的 HTTP hook 是应用私有形状，harness hooks 的写法已由 `harness-hooks-20260903.md` 覆盖；（3）Apache-2.0 允许移植代码，但其 L1 内核出自 Emdash，L2 的差异化部分（Team Room、范式）是提示词层加 PTY 敲键，不是可搬运的组件；HCTL2 的运行时选型已定为 Herdr，PTY 代码移植没有需求。若将来要在 L1 移植代码，应另立 Emdash 条目审计上游，而不是从 Yoda 抄。

明确不采用：Task 即会话的身份、Workspace / Team Room 充当 Project / Room、看板拖卡与栏目钩子充当施工授权、Coordinator 结束回合充当完成、Automation `completed` 充当运行成功、提示词注入充当分派协议、reviewer 散文充当 Verdict、模型临场决定拓扑、以提示词禁令充当权限边界，以及把它的 `tasks` / `conversations` / `team_rooms` / `paradigms` 表结构带入 HCTL2 公开模型。
