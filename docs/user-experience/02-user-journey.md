# 用户体验流程

> 状态：所有者的目标体验；组织结构已确认，未声称完整应用已交付。<br>
> 日期：2026-09-19<br>
> 来源：2026-09-17 用户流程，结合 09-18/19 的 [Project 导航与组织结构](./04-project-navigation.md#project-入口与-rooms--kanbans--runs)更新；09-19 按所有者要求补入 Topic Room 前情提要与 Run 交付、观察体验，供看稿；同轮确认后，验收输入与失败反例见 [S3](../design/scenarios/S3-user-journey.md)。

这是一条从“有一份代码”到“展开讨论、安排工作、观察执行”的用户路径，不是代码施工顺序，也不是强制每个 Room 都先有 Task、每个 Task 都先有 Run。内容的归属与引用按 [04](./04-project-navigation.md#松散耦合具体意味着什么)，本页只写人怎样使用它。

## 新建 Project

### P1：选择代码来源

用户在 Workbench 选择新建 Project，并给出 SCM 地址或本地 Git 路径。Project 可以有自己的显示名称，例如 Apollo；它关联的 Repo 则显示实际代码地址。

- **远端地址：** 以所选 Repo 建立当前 Project 的工作入口。
- **本地路径、有 remote：** 读出对应 remote 供用户选择。推荐接原 remote，继续使用它；也提供断开原 remote、用 Gitea 另起一份独立工作的选项。
- **纯本地：** 直接走 Gitea 本地方案。

本地另起默认建立独立副本并接到 Gitea，保留输入目录及其 remote；原地切换作为显式选择，操作前说明修改范围与后果。见[Q2 裁决](./open-questions.md#q2本地-detach-会改哪份目录)。

“另起独立工作”不包括自动迁移原平台的 Issues、PR 和评审历史，也不建立与原平台的持续同步。界面说明本次带入的代码范围与后续目标，不把复制代码显示成整个平台迁移完成。

多 Control 场景里，用户知道正在为哪个 Control 建 Project。本地路径指用户提供的那台机器上的路径，不是远端 Control 上碰巧同名的目录。读取失败、远端不可达、未支持的平台都如实显示，不当成纯本地悄悄换路径；缺少平台访问授权时，引导用户到对应连接的授权设置。

当前每个 Project 关联一个 Repo；同一 Control 已有 Project 使用该 Repo 时，用户仍可为它另建 Project。新入口进入新 Project 自己的主 Room，不自动跳回已有 Project，也不把新 Project 改成已有 Project 的 Topic Room。展开当前 Project 的 Topic 则走 T1，是另一个动作。本轮没有追加多 Repo 或非代码 Project 的实现需求。

### P2：接入 Kanbans

用户选择要接入的 Source，读回 Tasks 并可视化。推荐顺序保留：SCM 自带 Issues 优先；已有外部系统（如 Linear）其次；也可使用本地方案。

**一个 Project 可以同时接多个 Source。** 例如 GitHub Issues 与 Linear 分别占 Kanbans 的一个条目，用户不必二选一。点击 Kanbans 展开或收起列表，点击具体 Source 的入口显示其看板。

每个入口显示所选 Source 范围中的 Tasks；卡片保留来源。跨 Source 关联不复制卡片、搬家或自动同步同名 Task；同一 Source 内的状态和排序变化仍是正常操作。尚不支持的 Source 操作要可见，不能因能读列表就声称能完成所有写操作。

读回已有卡片不表示用户已承诺由 HCTL 完成所有卡片。界面区分读回内容与已接下的工作，并显示读取失败或尚未读全的情况，不把缺少结果显示成看板为空；Source 缺少访问授权时同样提供对应设置入口。

### P3：选人并进入 Project Room

用户从 Agency 选择 Participant，完成 Project Room 的初始阵容。点击左侧 Project 名称就进入这个主 Room；它与原流程所说的 Repo Room 是同一间。

选人不是打开主 Room 或查看已有内容的前置；需要 Participant 做事时，才从该 Room 的名册选用。此时 Rooms 列表仍为空，因为它只列后来展开的 Topic Rooms。选人是协作准备，不自动启动 Run。当前步骤顺序服务首次使用，不把先建 Kanban 变成所有聊天的前置条件。

## 产生 Topic 与 Task

### T1：聊天归纳，接受或忽略 Topic 建议

聊天中，系统持续归纳值得展开的 Topic，在输入框上方或通知位置提示“这个 Topic 值得尝试（Yes / No）”。

用户接受后，可以确认主题并按同样的方式选择 Participant，建立新的 Topic Room；它出现在当前 Project 的 Rooms 中。忽略则不创建。新 Room 的名单独立选定，可以参考主 Room 的阵容，不自动继承整份会话和授权；未来 TAMP 推荐见[分别选入](./04-project-navigation.md#participant-分别选入)。

**从聊天展开的新 Topic Room 创立时，从本 Project 主 Repo Room（本目录称 Project Room）的相关讨论构造一份前情提要，作为新 Room 的开场材料。Participant 阅读这份提要，就能接上此前讨论、开始后续协作，不必先翻完原 Room 的长篇历史。** 提要在新 Room 中保留，人与 Participant 都能随时重读。

提要说清话题为什么产生、要解决什么、已确定的事实与决定及其理由、仍存在的分歧和待答问题，以及开展讨论所需的约束与材料。已定与未定分开呈现；用户可以查看并纠正。原消息与材料的出处供需要时追溯，不能用一串链接代替本应写清的前情。

提要承接的是创建时的相关背景，不是整个主 Room 的会话副本。此后的讨论在 Topic Room 内继续；主 Room 的后续发言不自动混进新 Room，确需补充时再明确带入。前情提要不替代实际做事时要查阅的代码或专业材料，也不因带入背景就带入原 Room 的授权。

主 Room 与 Topic Room 都可以继续讨论。新 Topic 不产生新 Project，引用原讨论也不把原消息从旧 Room 搬走。

已有 Request 需要多人、多轮讨论时，也可升级成 Topic Room：提要来自该请求及它要处理的工作，主 Room 没有相关消息也能创建，不必为凑出处先发一条消息。选人、确认提要与独立讨论的体验相同；关闭 Topic 不等于已回答请求。

这个体验要求包括持续建议，不只是一颗手动新建 Room 按钮。归纳尚未配置或暂时失败时如实显示；手动创建可以作为替代入口，但不能算持续建议已经实现。模型、触发与费用控制留给后续设计，不在这里预定常驻 Agent 或新的工作流。

### T2：在两种 Room 里操作 Task

Project Room 和 Topic Room 都能通过聊天建立、修改或删除 Task。用户看到准备操作哪个 Source 的哪项 Task、内容和后果，再作决定；不能只收到模型一句“做完了”。

接了多个 Source 时，新 Task 的目标 Source 需要明确。由哪种默认值减少重复选择交给产品实现；没有明确目标时，不因当前 Room 的名字猜 Source。已有 Task 可以在多间 Room 中被讨论，来源和所属 Project 不随讨论地点改变。

未提交草稿可以删除；已有工作的默认动作叫“取消并归档”，保留历史与 Source 卡片。删除 Source 卡片另行确认，先看到本 Control 中绑定这张共享卡的所有 Task、所属 Project 及活动 Run；不把删卡说成只影响眼前的 Project。有活动 Run 时明确处理其去向，停止或取消仍按各自授权另作决定，见[Q3 裁决](./open-questions.md#q3删除-task-的后果)。关闭 Topic Room 不删除它提到的 Task，也不停止关联 Run。

### T3：模板与表单生成 Run 计划

用户可以为 Task 选择快捷模板，填写交互式表单，得到 Run 的 DAG 和任务书。它们是同一份计划的两种表达，不让人维护两份相互漂移的内容。

为 Task 保存的计划可以从该 Task 的计划入口找回，继续查看、修改或准备开工。关闭预览或切到别的页面不删除已保存的计划；尚未开工的计划也不冒充活动 Run 出现在执行列表中。

生成计划不等于立即开工。进入执行前，用户能确认做什么、谁做、交付什么、如何验收及所需资源。每个 Run 独立选施工与评审 Participant，不因为它从某间 Room 发起就自动采用那间 Room 的全员与授权。

批准前按[现行默认值](../design/delivery.md#运行默认值)先做独立读回，让另一位 Participant 复述将做什么，供用户核对。施工图显式声明跳过时按既有规则处理，使用模板本身不是跳过的理由。

并非每个 Task 都要 Run。Run 可以被多间 Room 引用，引用不会改写本次任务书，也不自动增加它承担完整交付的 Task。

例如，只改一处文档的小 Task，可以先明确交付与验收要求，由人直接处理，或从 Room 发起一次有边界的 Participant 调用。产出变更与证据后，在 Task 上查看；涉及合入时按原有合入流程确认，再提交完成请求并接受验收，不为这条简单路径补造 Run 或 DAG。需要让系统按计划持续施工、检查或返工时，再选择相应 Run。详见[无 Run 的轻量路径](../design/task.md#无-run-的轻量路径)。

## 观测 Run

### R1：从 Project 的 Runs 进入

左侧 Project 下有 Rooms、Kanbans、Runs 三类列表。点击列表标题展开或收起，点击 Project 名称进入主 Room；点击旁边的“待你处理”标记则打开待处理面板，见[两个入口与处理行为](./04-project-navigation.md#待你处理从-project-标记进入)。

活动 Run 独立列在 Runs，不藏在发起它的 Room 或某张 Task 卡下面；从关联对象也可以跳转过去。切换 Room 或 Source 不改变 Run 的工作归属。

### R2：任务书与 DAG 共享 Worker 侧栏

点击 Run 默认展示 DAG，标明哪些步骤正在执行、哪些已经执行；并行时可同时看到多个进行中的步骤。用户也可以切到内容介绍，查看任务书。

无论看哪一个，最右侧都展示这个 Run 的各个 Worker 及其当前步骤。切换视图不切换执行，不把两个入口变成两次 Run。

步骤除了正在执行与已执行，还说明尚未开始、等待外部结果、等待人处理、失败等情况，并给出原因与下一步。正常等检查结果和确实等人作决定分开显示；按已有授权能够自动继续的工作，不额外要求用户逐步批准。需要人处理的事项可从相关 Run 或 Task 直接进入，也汇总到 Project 的“待你处理”面板；两处指向同一事项。

### R3：按供给能力观察 Worker

点击 Worker，按选人时约定的能力进入图形桌面、终端界面，或无交互界面（Headless）方式。Headless 没有交互屏幕，不等于没有进度、结果或需要人处理的请求。

同一执行可以提供多种观察方式，不把这三种呈现做成互斥的 Participant 类别。界面分别标明能看什么、能否输入、能否接管；打开画面只是观察，不自动取得输入权。日常了解进度和结果不以打开终端或桌面为前提。

有多次派工时，当前执行与历史记录分开展示，用户知道正在看哪一次。历史结果可以回看，不把旧画面当成当前现场；观察连接中断时显示最后更新时间与当前无法确认的情况。切换页面、关闭观察面板或断开观看不取消 Run，暂停或取消是另一个明确动作。

这些观察和输入经 Agency 指向具体执行，不转投给另一 Room 或 Run 中同名的 Participant。能力要求不强迫每个 Worker 都有一台 VM，也不承诺某个第三方已有可嵌入接口；缺能力在选择时讲清，不能等点击时才伪装成另一种已支持体验。

### R4：从执行结果到交付完成

Run 页面不在 Worker 停止输出时就把整件事涂成绿色。任务书与 DAG 旁都能看到产出、检查和评审结果，以及需要时的 PR、合入记录与 Task 验收结论。各项显示对应的代码或材料版本，点击可以查看依据。

| 用户看到的进展 | 它说明什么 |
| --- | --- |
| Worker 交回结果 | 结果可查看；检查或评审可能仍未通过 |
| 检查通过 | 对这一版结果的相应检查通过；后续是否还需评审或合入，看本次计划 |
| 评审通过 | 这一版结果得到相应评审认可；不是代码已经合入 |
| 已合入 | 目标已确认接受本次变更；Task 的验收结论仍单独显示 |
| Run 完成 | 本次获准计划正常完成；绑定 Task 时，完成请求进入 Task 的独立验收 |
| Task 完成 | 相应 Task 的验收要求已满足，并可查看接受的结果与依据 |

这些是要区分的事实，不是强制所有 Run 都按六格排队。只展示本次计划要求的环节；研究或讨论型 Run 可以不绑定 Task，也不必有代码合入。Run 完成而 Task 验收未通过时，两者如实并列显示，并指出缺哪项证据或与哪版要求不一致，不把 Run 改回运行中掩盖差异。

例如，修复构建问题的 Run 已交回代码、检查与评审通过，但还在等获准的合入操作，就显示这些已完成项与剩余事项。合入确认后再显示 Task 的验收结果；若 Task 的要求已经更新，说明本次交付满足的是旧要求，新要求仍待处理。结果保留，用户能从 Task、Run 或相关 Room 找回同一份内容。

### R5：不顺利时也说清当前情况

下列前四项是[既有 S2 用例](../design/scenarios/S2-rough-road.md#二四种情形)在界面里的读法；最后一项来自 [S1.N8](./01-multi-unit.md#必然发生的情形)，把施工者失联与 Agency 本身失联分开，不另造一套恢复流程。

| 情形 | 用户应看到什么 |
| --- | --- |
| 施工中 Task 的要求变了 | 当前 Run 正在按哪版要求做；新要求还有哪些未满足。旧成果保留，不把它显示为新要求已完成 |
| 评审通过后代码又变了 | 旧评审针对旧版；当前版本还在等待哪些重新检查或评审 |
| 施工者失联，Agency 仍可联系 | 最后观察时间、授权是否仍有效，以及正在恢复还是准备改派。失联本身不撤权，也不延长截止；改派前显示旧写者失权或隔离是否已得到确认。旧执行回来后经核对仍有资格的可以继续，核不过的不能再以旧派工写入或封存，已保管的结果仍可交回 |
| 合入请求超时，平台可能已成功 | 合入结果待确认；系统继续核对原操作的结果，不把超时显示成合入失败，也不引导用户再合一次 |
| Agency 本身联系不上 | 最后观察时间与当前无法确认的状态，不把失联直接显示为执行失败或丢失；需换另一家 Agency 时，由人确认成本与授权，不因连接超时自动改派 |

每种情况都区分系统正在做什么、是否需要人处理、影响哪些工作。界面保留结果与原入口，让人能继续核对或处理，不要求重建 Room、Task 或 Run 才找回上下文。

## 从另一台机器继续

用户可以在另一台机器的 Workbench/CLI 连接原 Control，继续查看同一 Project 的 Rooms、Kanbans、Runs，并处理需要人的动作。关闭原前端不停止远端工作；新前端不自动接管 Harness Session，也不把内容搬到另一个 Project。

这是[多单元用例 S1.5、S1.9–S1.11](./01-multi-unit.md#操作步骤)在日常流程中的体现。通过 Git 接手本目录的文档工作则需更新到已合入的修订，两种接手不混为执行迁移。
