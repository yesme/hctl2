# 愿景与设计原则

> 状态：规范性（愿景与原则层）· 草案 v0.9.0<br>
> 日期：2026-08-19<br>
> 定位：本文回答“HCTL2 为什么存在、想给用户什么体验、按什么原则做取舍”。对象、状态、命令和不变量的权威定义在[四个模块文档](./README.md)；两者冲突时以模块合同为准，本文用于裁决模块合同尚未覆盖的新问题。

## 一句话定位

> HCTL2 是把**人主导的目标塑形**与**机器驱动的可验证施工**连接起来的、以 Git 仓库为边界的本地多 Harness（编码代理工具）项目协作系统。

这句话的两端缺一不可：只有塑形没有施工，是又一个聊天工具；只有施工没有塑形，是又一个终端管理器或工作流引擎。HCTL2 的价值在于中间那座桥——人的意图如何变成机器可以领取的承诺，机器的产出如何变成人可以信任的结果。

产品姿态浓缩为四个短语：**Project-scoped、Room-mediated shaping、Task-tracked、Run-executed**——目标以 Project 为界，塑形在 Room（协作聊天室）中发生，承诺由 Task 追踪，施工交给 Run 治理。正常执行默认无界面（headless）在后台推进；终端是观察、诊断和接管的通道，不是用户理解项目的主入口。

## 为什么需要 HCTL2

软件开发正在从“一个人操作一个 IDE 或终端”转向“一个人同时管理多个能力、上下文和权限各不相同的 Coding Harness（编码代理工具，如 Codex、Claude Code、OpenCode）”。现有工具通常把其中一个局部做得很好：聊天与上下文、异步任务、worktree（Git 工作树）与终端，或通用工作流引擎；但它们没有共同回答项目生命周期中的四个问题：

1. 我们真正要解决什么，讨论依据是什么？
2. 哪些内容已经成为可排期、可验收的承诺？
3. 哪些自动施工已获授权，凭什么可以继续或通过评审？
4. 哪个具体执行实例正在哪里运行，如何观察、恢复或接管？

缺少这组回答，就会反复出现五种失败模式。

### 多 Harness 被压缩成多个终端

终端复用器能保存进程，却无法稳定表达 Participant（参与者）的角色、任务契约、审批证据、授权范围和下一步动作。标签页、面板和 worktree 的名字也扛不起长期的项目身份。

### 人成为机械消息总线

人在作者、评审者、测试者、安全审查者之间复制上下文，等待一个完成再把反馈转发给下一个。这是高出错的机械劳动，不是人的意图与判断优势。

### “Agent 完成”被误当成“项目完成”

Harness 跑完一轮、进程退出、代码提交、评审通过、CI 通过、外部 Issue 关闭和 HCTL Task 验收，是七件不同的事实。把其中任何一个当作完成，都会在版本变化、重试、迟到结果和外部同步失败时丢掉正确性。

### 上下文无来源、无版本、不可复现

把整段聊天或某个牵头 Agent 的自由总结发给下一个执行者，事后无法回答它当时看到了什么、遗漏了什么，也无法在故障切换后重现同一份交付义务。

### 界面、领域与运行时互相污染

如果 Room、Project 或 Task 直接等同于会话、进程、worktree 或终端，那么纯讨论、多次施工、权限隔离、重试和崩溃恢复都会破坏这层映射。

## 四个阶段的心智模型

HCTL2 把项目生命周期理解为一条从意图到运行的链，四个领域模块各自拥有其中一段的事实：

```text
意图 Intent      ──提炼──▶  承诺 Commitment  ──授权──▶  治理 Governance  ──分派──▶  运行 Runtime
Project · Chat Room        Task · Kanban              Run · Workflow             Harness · Terminal
```

- **意图**：我们要解决什么、为什么、依据是什么；哪些讨论已经足够稳定，可以成为承诺。
- **承诺**：哪些内容已被采纳为可排期、可验收的契约，当前进行到哪里。
- **治理**：哪些自动施工获得了有边界的授权，凭什么可以继续、通过评审或算作有效结果。
- **运行**：哪个执行实例带着哪份上下文和权限在哪里跑，如何观察、恢复或接管。

结果沿相反方向回流：运行层交出提案与证据；治理层校验后形成 Verdict（裁决）与 Receipt（凭证）；承诺层据此独立验收；意图层沉淀里程碑与长期经验。

两点必须同时成立：

1. **这是心智模型，不是流水线。** 一件事不必完整经历四个阶段：简单 Task 可以不创建 Run；Project 可以直接发起一次边界明确的 Harness 调用；纯研究或文档的 Project 可以从未施工。短路是显式设计，不改变事实所有权。
2. **这是语义责任的梯度，不是部署层级。** 从 Project 到 Harness，越靠前越接近人的意图，越靠后越是可替换的执行资源。上端的事实必须在工具更换后继续存在；下端的资源可以丢失、重建和接管。

## 目标体验

理想的完整旅程是：

1. 用户进入 Repo Room，引用代码、Artifact（登记过的交付物）、Commit 或 Memo（沉淀的备忘），邀请多个 Participant 做有边界的研究。
2. 话题成型后，把相关来源和上下文提升为一个具名 Project。
3. 用户在 Project Room 中塑形目标、范围和验收标准，把承诺提炼成 TaskRevision（任务契约版本）。
4. 简单工作由人完成，或通过一次有边界的 RoomInvocation（从聊天室发起的单次调用）完成；它不需要 Run。
5. 需要持久自动施工时，用户先批准 Workflow（施工图），再显式启动 Run，授予有边界的自主权。批准施工图与开工是两个动作。
6. Run 默认在后台推进；需要澄清、决定或授权时，系统创建 Request（请求卡）并投影回 Project。
7. 只有需要观察或接管某次精确执行（Attempt）时，用户才打开结构化执行投影或终端。
8. 执行结果与证据逐层回流；只有通过版本、规则、验收和 Receipt 校验，Task 才算语义完成。

无论走到哪一步，用户都应该随时能回答六个问题：

- Project 要交付什么；
- 哪些 Task 正在进行、待评审或被阻塞；
- 哪个 Run 在等待，为什么；
- 当前需要谁提供什么；
- 哪个 Harness 带着哪份上下文和权限在执行；
- 结论绑定哪个版本与哪些证据。

由此形成注意力分配原则：多个 Harness 默认在后台执行，前台只保留需要人商议、授权或接管的事项；正常成功保持安静。观察手段是一道阶梯——结构化执行流是默认视图，PTY 转录是二级诊断，终端接管是最后一级。如果日常了解进度要靠开终端，说明上层投影失职。

## 两种控制制度

塑形与施工不是两个房间，而是两种推进权制度：

| 制度 | 推进权在谁手里 | 主要产物 |
| --- | --- | --- |
| 塑形（Planning / Shaping） | 人是意图和授权中心；系统可以研究、建议、汇总，但不能替用户决定目标 | 规格、ADR（架构决策记录）、Task、Artifact、Workflow 提案，或普通 Git 文件 |
| 施工（Run / Automated Build） | control 在冻结的 Workflow 与规则内自动推进；人只处理例外 | 代码/文档、Verdict、Receipt、PR、Run 历史 |

批准 Workflow 与启动 Run 是两个动作：前者确认施工图，后者才允许系统消耗资源、产生副作用。Run r1 按冻结的版本施工时，Project Room 可以继续讨论 r2——讨论不必等施工结束，施工也不会随讨论漂移；范围、验收、候选或权限要变，就结束或替代旧 Run，而不是原地改。

## 产品原生核心与架构最小内核

HCTL2 不是聊天室、看板、流程引擎和终端的并列拼装。它的产品原生核心是一个**以仓库为边界的项目语义控制面**（repo-scoped project semantic control plane），由三项能力构成：

1. **Repo–Project 生命周期**：仓库注册、Project 的创建/更新/归档/恢复，以及不随外部平台漂移的稳定身份；
2. **Project 连续性**：Room、Task、Run、Artifact、Request 和证据始终回到同一个 Project——替换 Harness、会话、终端甚至外部 SaaS 之后，项目仍可继续；
3. **Project 驱动的控制**：系统根据 Project 上下文、角色、版本、能力和证据判断下一步允许发生什么。

即使把全部界面、聊天平台、Task 来源、工作流引擎和终端客户端都换掉，下列最小内核也必须保留：

| 最小内核能力 | 必须保持的性质 |
| --- | --- |
| 稳定身份与绑定 | Repo、Project、Task、Room、Run 及外部对象的身份不随客户端或平台漂移 |
| 命令准入与权限 | 每个动作校验 actor、范围、能力、预期版本、规则与幂等性 |
| 版本、证据与语义校验 | 契约冻结、Verdict、Receipt、验收与过期结果拦截可核验 |
| 执行治理 | Run 授权、Obligation（交付义务）/Seat（执行席位）/Attempt（执行尝试）、候选切换、法定票数与重新评审由语义控制面协调 |
| 持久账本与对账 | outbox/回读、崩溃恢复和投影重建跨组件保持一致 |

最小状态转换固定为：

```text
actor + 类型化命令 + 目标版本 + 证据
  → control/core 校验
  → 已提交的领域事件 + 持久 outbox 意图
```

外部平台的事件先成为观测或提案；只有通过同一道准入边界，才可能改变 HCTL 语义。

这组对仗构成产品的双重检验：**产品原生核心**回答用户为什么使用 HCTL2；**架构最小内核**回答换掉一切之后什么必须仍然成立。

## 设计原则

1. **四阶段分责。** 意图、承诺、治理、运行由四个模块分别拥有，只通过类型化交接相连，不藏跨模块副作用。
2. **领域对象少而稳定。** Repo、Project、Task、Room、Run 是用户核心对象；Obligation、Seat、Attempt 只在需要时渐进展开。
3. **协作拓扑与控制拓扑正交。** Room 回答在哪里交流；Workflow/Run 回答谁有权自动推进。
4. **人的角色是意图与授权中心。** 系统可以并行研究和建议，但不能替用户决定目标；Run 只能在批准的边界内自动推进。
5. **机械动作必须确定性。** 提及、派发、重试、候选切换、评审关卡和合并不依赖模型是否记得调用工具。
6. **Chat 不是数据库。** 消息可以形成提案；正式变化必须走类型化命令、版本检查和权限检查。
7. **Context 必须可解释。** 每次调用冻结上下文清单、来源、摘要、Skill 和权限快照。
8. **证据高于进度（evidence over progress）。** Harness 的进度、自述结论、屏幕状态和外部 Closed 都不能越过验收与 Receipt。
9. **默认无界面（headless by default）。** 状态、diff、追踪和 Request 优先；终端是诊断与接管通道。
10. **至少一次投递下的正确性。** 外部副作用使用幂等键、持久收发箱、代次拦截和对账。
11. **运行时身份可替换。** 外部会话、进程、worktree、终端连接都不是 Project/Task/Room 的身份。
12. **外部事实按字段授权。** Linear/GitHub 可以拥有明确配置的操作字段，但不能接管 HCTL 的身份、契约、验收或语义完成。
13. **复用实现，不继承边界。** 外部项目只贡献被验证的局部机制；它们的对象名称和数据库结构不进入 HCTL 公共模型。
14. **Workbench 无隐藏特权。** Workbench、CLI 和未来客户端走同一命令与查询服务；任何界面都不能直接写数据库、外部镜像或引擎任务。
15. **尽早自举自用。** 稳定版本 N 通过正式产品入口治理隔离环境中的 N+1；引导和恢复脚本不成为第二事实源。

## 要解决什么，不解决什么

HCTL2 要解决：仓库级 Harness 目录与能力探测；Repo/Project Room 中的多参与者结构化协作；可追踪、可排序、可验收的 Task；冻结施工图的持久 Run；候选切换、法定票数与重新评审；Git/worktree/PR/Receipt 的确定性验证；低噪声的注意力管理与按需商议；Harness 结构化事件与终端逃生通道；各组件重启后的对账恢复。

HCTL2 不解决：不重新实现 LLM、Coding Harness、通用工作流引擎、终端模拟器或复用器；不用自然语言提示替代分支保护、Receipt、权限或规则；不把不同 Harness 的能力伪装成完全相同；**不让每项工作都必须聊天，也不让每项工作都必须先画一张施工图**；第一阶段不做多人组织、云队列、浏览器/移动客户端和引擎高可用。
