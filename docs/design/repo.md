# Repo（仓库）与 Change（变更）

> 状态：规范性（架构层）· 草案 v0.17.0<br>
> 日期：2026-09-06<br>
> 定位：本文回答“哪些改动已经可信地进入了目标分支、凭什么，以及合入的钥匙握在谁手里”。

> 本文是 Repo 模块的设计正文：它为什么存在、拥有什么、按什么规则运转。精确对象、状态机与写入约束见[约束附录](./spec/repo.md)；模块交接见[连接约束](./spec/connections.md)，共享机制见[系统边界](./spec/system.md)。

## 为什么存在

一次改动从执行体的工作树里长出来，到成为目标分支上的一个提交，中间要经过封存、评审、检查和合入。这一段的事实——这个版本是什么、评审看的是不是它、目标分支当时在哪里、合入是否真的发生——不归聊天室、看板、施工图或终端中的任何一个。执行结束不等于合入，模型说“我已经合并了”也不算：合入是一件要被证明的事。

我们自己的开发流程把这件事暴露了出来。开一条评审请求、评审者留评论、作者修改、再审、合入——整条协作放在代码协作平台上，而之前的设计没有写下这个依赖，也没有回答“没有平台的仓库怎么办”。Repo 模块把它们收成一个模块：仓库身份、执行现场、变更集与写入权、集成意图与凭证由它拥有；代码协作平台是这个模块的 content 系统，可以有，也可以没有。

它是一个模块而不是别人的一节，理由和其他四个模块相同：仓库身份比任何一个 Project 活得久；变更集在执行体死掉之后仍然存在，是恢复的边界；合入钥匙只在控制面的适配器手里，是权限的边界。三条里任何一条都足以立一个模块，这里三条都成立。

## 模块拥有什么

Repo 模块保存“代码在哪里、哪次改动是哪个版本、它进了目标没有”的事实。它拥有：

- **仓库身份与注册**：逻辑仓库的稳定身份，写进 Git 也记在账本；一个仓库可以显式挂接多个仓库实例——某台机器上的一个克隆及其执行现场；
- **变更集及其不可变快照**：一次获准的写入边界，以及在有效写入租约下封存出来的精确 Git 快照；写入租约是一个变更集同一时刻唯一的写权；
- **集成意图与集成凭证**：把某个精确快照合入某个目标的持久授权，以及回读确认后签发的唯一凭证；目标可以是本地仓库实例上的分支，也可以是平台上的远端分支；
- **变更与平台的映射**：某个冻结版本对应平台上的哪个提交、哪条评审请求；平台账号与人的映射也放在平台绑定里；
- **外部机械事实的读侧**：检查状态、评审请求是否合并、引用是否推进、路径与摘要，由工具箱读回，供 Run 的节点前置与验收证据使用。

它不拥有：评审关卡、席位与 Verdict（裁决）归 [Run](./run.md)；任务契约版本与完成凭证归 [Task](./task.md)；Artifact（工件）与 Memo（备忘）归 [Project](./project.md)；执行体、终端与运行时观测归 [Participant（参与者）](./participant.md)。评审对象既可以是变更集快照，也可以是工件的发布版本，后者不经本模块。

## 工具箱总在，平台按仓库绑定

这个模块的样子，和 Participant 模块的 Agency（派出方）是同一种关系：本地参考实现随包发布、总是可用，远端供应端可以外接。

**工具箱是每个仓库都有的本地执行者。** 无论仓库有没有平台，物化工作树、封存版本、读取 Git 事实、本地现场锁都由工具箱做；有平台的仓库照样要它。平台适配器只管平台上才有的事：推送分支、开或更新评审请求、请求合并、把结论写回，以及把评审评论取回来给作者看。检查结果、合并状态、目标头这类机械事实仍由工具箱读回，证据等级不因为走了平台而降低。两者是分工，不是二选一。

**平台按仓库绑定，能力写在绑定上。** 注册仓库时可以给它绑一个代码协作平台——托管服务或自建服务器，对我们是同一种东西，差别用绑定上的能力声明表达：有没有评审线程、有没有正式评审状态、有没有检查、能不能远端合入、有没有身份映射、能不能保证预期目标头。默认选了哪家、以后打算支持哪些，见[交付文档](./delivery.md#选型判据)与[市场调研](../research/scm-platforms.md)。

**能力声明决定契约能不能被满足，不能替人改契约。** 契约要求平台上的三个检查通过，平台失联时本地测试通过不能顶替；契约要求合入远端主干，本机主干前移不能顶替。缺了声明过的能力，命令等待、拒绝或标为需要关注；改契约只能由有权的人显式做。

**纯本地仓库是完整的正常路径，不是降级。** 一个从头到尾没有平台的仓库，契约在采纳时不会要求平台上才有的机械证据，但三种校验等级它都可以有：机械项的证据是工具箱读回的本地事实，例如测试的退出码与本地目标头；要人判的项由人判；要内部评审的项先授权 Run。讨论在为这次变更开的 Scoped Room 里，集成走工具箱的本地路径，凭证照常写。将来给它绑上平台，是加一份绑定、多一类目标与能力；仓库身份、既有版本与凭证不变，进行中的意图沿用原绑定版本。

**集成路径按目标选。** 每一次集成意图必须固定自己的目标：是某个仓库实例上的本地分支，还是平台上的远端分支。同名的本地分支和远端分支是两个目标，对本地主干做的集成不能算作远端主干已合入。

## 一次变更走一遍

不用 Run 的最短一条链，从聊天室发起一次真实改动到合入。前置是一个活跃的 Project 和一张已采纳验收契约的 Task。

1. **发起。** 有权的人从 Project Room 发起写入型 Room Invocation（单次调用）。Trigger Preview 展示执行者、上下文、权限、预算，并写明本次授权的是“发布去评审”，不是合入。Execution Spec（执行规格）冻结变更集规则与**评审发布策略**：哪个仓库、哪个平台绑定版本、发布到哪个分支或评审请求、允许创建还是也允许更新、评审请求的描述从哪来。策略是范围，不是一句“允许发布”；执行体只能提供被允许的内容，不能换发布地点，也不能扩大权限。
2. **施工。** 工具箱物化独立工作树，执行体在有效写入租约下改代码、在自己的分支上提交。执行体不持有平台凭据，不能自己推远端。
3. **封存与准入。** 执行体提交 Result Proposal（结果提案），提案里说清是哪个变更集、哪个租约、什么基线、结果在哪个提交或工作树。保存与算数是两件事：工具箱据此把内容封存成 Git 快照并回读，这是保存；账本接受这次结果和这个版本，这是准入。封存期间被取消的调用不会因为 Git 对象已经存在而继续走到发布，平台上出现一个提交也不是准入。人在预览残留后也可以显式封存，那是人的命令，不用假装成一次调用。
4. **发布评审。** 版本获准后，控制面按第 1 步冻结的策略自动发出发布命令，不用人再点一次（开了「发布评审须人显式确认」开关的仓库除外）；适配器推送变更集分支、创建或更新评审请求，描述来自提案里的文本产出。这一步产生变更与平台映射的第一条证据：这个版本对应平台上的哪个提交。
5. **检查与评论。** 平台跑检查，评审者留评论。工具箱读回检查与线程状态；评论正文经代取进入下一次调用的开工包，见[横切正文](./context.md#投喂三档内联指针代取)。评论进入上下文只是给作者看，它本身不变成授权、契约或裁决。
6. **返工，以及主干前移。** 无 Run 路径没有自动返工。有权的人发起新的 Room Invocation，开工包里带上选中的评论；旧调用不复活。评审期间主干前移是常态：执行体在自己的工作树里把新主干合并进来或变基上去，封存为新版本——基线变了就是新版本，旧评审失效，再按策略更新评审请求、重跑检查。
7. **合入前的预览。** 有权的人预览“合入”：必需检查是否齐全且对应当前版本的提交、线程是否解决、正式评审是否满足契约；选了预期目标头形态时看目标头是否仍是预期的那个，选了接受目标前移形态时看目标保护的条件是否仍与预览时一致。这不是 HCTL 的评审关卡；契约要求内部独立评审时才先授权 Run。
8. **合入与凭证。** 人提交集成意图，控制面先持久化，适配器请求平台合并或工具箱推进本地分支，工具箱读回合并提交与目标头，确认后写唯一集成凭证，凭证记实际的目标头。结果未知就保持未知，不改道、不签成功。
9. **完成。** 人在 Kanban（看板）预览并提交完成命令，Task 校验精确凭证与其余验收项，写完成凭证。

有契约的 Task 走完这条链，人的预览只有两次：合入、完成。发布评审的授权在第 1 步，发生在封存之前，不计入这两次；它合法的原因是范围写清了，不只是发生在计数窗口之外。仓库可以打开可选开关“发布评审须人显式确认”，那是它自愿多的一次，产品默认路径仍是两次。纯本地仓库走同一条链：没有第 4 步，检查是本地测试事实，评论来自 Scoped Room，合入走工具箱。

## 关键规则

- **三条底线在这个模块的样子。** 工具不是人：席位的一票是那次执行提交的提案，由 Run 计票，控制面把结论写回平台只是记录。合入钥匙不进工具：平台写凭据只在控制面的适配器手里，执行体在自己的工作树里可以正常用 Git，但不推远端。隔离工作树：每个变更集一个独立工作树、一个写入租约。
- **合入只走四步：持久意图、执行、回读、唯一凭证。** 一个意图一个结果、一张凭证；同一目标同时只有一个待决的意图，不论哪种形态，前一个了结后下一次合入是新的授权。绕过这四步直接改目标分支只算带外改动，下次预览前被当作漂移拦下；已开启自动合并、已进合并队列都只是请求被接受，不是已合入。
- **两个头要分清。** 源分支头是待合入的提交，目标分支头是预览时主干所在的提交。本地路径能做到“目标头不是预期的就拒绝”；平台一般给不了这个保证——据我们所知，常见平台校验的都是源头。所以绑定要声明“能不能保证预期目标头”，不能保证时默认拒绝；放行不是执行时的降级，而是人事前显式选择的另一种授权形态：把这个精确源版本按指定合并方式与保护要求合入这个目标分支，接受期间目标前移。意图冻结这个选择与目标保护的快照，凭证记实际目标头。
- **目标保护不止“是否必须评审请求”。** 必需检查的清单、是否要求与目标同步、是否要求线程解决、要求的批准数，预览时读到的快照冻结进意图，执行与回读时对照；上游悄悄改规则不能让账本失序。
- **评审身份看内容与基线，不看提交包装。** 同一个获准版本只是换了提交包装，身份不变；基线变了或结果树变了就是新版本，旧裁决作废。
- **平台动作逐项分类。** 普通评论只进上下文；批准与请求修改是外部评审证据，能证明什么由契约定；平台上的“已经合并”不是事前授权，有匹配的持久意图时供回读，没有时只作外部事实与分歧。账号映射只证明来源；共享账号发出的多次批准映射不出多张票。控制面自己写回产生的事件排除在外。
- **恢复按目标分，状态按是否可能已写分。** 面向本地目标的意图只回读本地事实，不等任何评审请求；面向远端目标的意图，确定尚未投递的可以照原意图重投，可能已经写到远端而无法确认的保持未知、继续占用冲突范围。凭证的权威在账本，平台丢失后不能凭 Git 提交重建凭证。
- **本地目标正被检出时的正常入口。** 人的主工作树通常停在主干，改动在另一个工作树，集成回主干就是这个情形。正式走法是人先把目标工作树切离目标分支，再重试同一意图；工具箱拒绝时给出精确的工作树路径与这个恢复动作。
- **清理不删孤本。** 拆除现场之前先封存并证明有可恢复副本；有权的人预览残留后显式确认丢弃时才可以不留副本。

## Change 场景

Change 是 Repo 模块的操作场景，回答：这一次变更改了什么、谁怎么看它、检查过了没有、它进目标了没有、怎么让它进去。

- **看**：某个版本的精确 diff；评审讨论——平台上的评审请求线程，或本地仓库的 Scoped Room；检查结果；集成状态与凭证。
- **做**：发布评审、发起集成、把 Run 评审关卡的结论写回平台。写回是记录，走已有的副作用命令，不绕过授权；写回产生的平台事件不再触发一次人的请求。

评审关卡与 Change 场景要划清：Gate（评审关卡）是 Run 模块里冻结的治理节点，裁决在 Run 产生；Change 场景是内容与状态的呈现处，裁决在这里只是投影，就像 Task 的状态出现在看板上一样。

| 角色 | 可以做什么 |
| --- | --- |
| 场景客户端：平台原生页面与命令行 | 直接读写评审线程、检查与合并状态这些 content；平台上的批准、评论与合并按钮按绑定声明的能力映射，不因客户端身份取得治理权 |
| 场景客户端：CLI | 承载变更集查看、集成预览与提交、发布评审的预览与提交；Workbench 就位后同一命令服务供它投影 |
| content 系统：SCM platform（代码协作平台） | 承载评审线程、检查结果与合并状态的 ground truth（事实源头）；纯本地仓库没有它，讨论在 Scoped Room，检查是本地事实 |

## 模块交接

以下只列所有权方向；字段、事务与故障语义由[连接约束](./spec/connections.md)统一定义。

- [Project](./project.md) 注册仓库时，本模块激活仓库身份，Project 在同一账本事务里建 Repo Room；Project 归属于一个仓库。
- Project 或 [Run](./run.md) 准入结果提案时，本模块在同一事务里准入变更集快照；提案的接收者仍是 Project 或 Run，本模块不接收提案。
- 派工时 Execution Spec 冻结变更集与写入租约规则，工具箱按它物化独立工作树；旧写入者失权时本模块记撤权、不重授，[Participant](./participant.md) 模块停止或隔离旧执行并提供证据。
- Run 的评审对象引用指向本模块的变更集快照；评审关卡的证据可以引用平台检查与评审状态，证据通道等级仍按“工具箱读回高于适配器结构化上报高于模型转述”记。
- 无 Run 时有权的人预览后直接提交集成意图；有 Run 时评审关卡通过后由有权的人或冻结的归约器提交。本模块准入、持久化、执行、回读、写凭证；集成凭证作为 [Task](./task.md) 机械验收项的证据。
- 平台事件按[系统边界](./spec/system.md#客户端动作与-provider-事件)的四类处理，逐项映射见[约束附录](./spec/repo.md#平台动作与命令)。
