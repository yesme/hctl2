# Run 与 Workflow（施工图）

> 状态：规范性（架构层） · 草案 v0.17.3<br>
> 日期：2026-09-02

> 本文是 Run 模块的设计正文：它为什么存在、拥有什么、按什么规则运转。精确对象、状态机与写入约束见[约束附录](./spec/run.md)；模块交接见[连接约束](./spec/connections.md)，共享机制见[系统边界](./spec/system.md)。

## 为什么存在

行业并不缺工作流引擎：DAG、代理委派、重试、定时器和历史恢复都已被反复实现。真正缺失的，是一套面向项目语义、绑定精确版本与证据的治理层——它回答“这个节点对应哪份交付义务、谁有资格尝试、结果是否有效、凭什么可以算完成”。这件事不能委托给聊天室、看板、Harness、终端或任何通用引擎；它是 Run 模块的原生价值。

两种权威一句话可以分清：

> 引擎说：“这个外部节点 READY / IN_PROGRESS / COMPLETED 了。”<br>
> HCTL2 说：“它对应哪份交付义务（Obligation），谁可以尝试（Seat 与候选），对结果的裁决（Verdict）是什么，是否可以完成（准入校验）。”

引擎只报告执行进度，HCTL 只裁决语义结果；进度报告不能替代语义判决，语义判决也不改写引擎事实。

## 模块拥有什么

Run 模块保存“哪份自动施工已获授权、引擎报告的进度如何映射为语义结果”。Workflow 是它的操作场景，不是独立的领域模块。它拥有：

- **施工图及其批准**：与引擎无关的不可变控制图，即施工图版本（Workflow Revision），先批准、后开工；
- **一次授权执行**：Run 是对冻结施工图、任务契约版本、代码基线、候选、权限和预算的整体授权；
- **交付义务**：Obligation（交付义务）是一个外部节点必须产出的逻辑结果。引擎重试时，control 根据再次进入等待态的进度报告创建新义务；旧义务及其票失效，因此重试不会增加票数；
- **席位与尝试**：Seat（席位）是义务里稳定的逻辑裁判位，候选切换不改变席位——换执行配置不换裁判、不多一票，席位上的施工者启动后不换；Attempt（尝试）是某个候选的一次具体执行，物理现场崩溃或重连不改变尝试身份——掉线不丢身份；
- **评审关卡**：Gate（评审关卡）按冻结规则决定结果凭什么通过；
- **裁决与凭证**：Verdict（裁决）是对精确版本的语义结论，Receipt（凭证）是校验后的正式证明。

在三类数据里，Workflow 场景的结晶是凭证链——“干成了的证明”。施工图（“干什么的计划”）从 Project Room 的塑形讨论中长出，作为结晶归 Room 场景；它的批准与版本对象仍由 Run 模块定义——结晶归属以事实为准绳，不随对象所有权走。判决的权威在控制面存储，结晶副本进 Git（私有仓库默认全文，公开仓库可降为仅摘要）。

跑图的是现成的工作流引擎，HCTL 只拥有语义。为什么用现成引擎而不自建持久状态机，见[工作流引擎选型](../research/workflow-engines.md)里「SCXML / XState 自建」一行与[来时路 §18](./references/decision-history.md#18-workflow-engine-从-conductor-改为-daguv0121)。

## 一次评审合入走一遍

八个治理词分三类：四个对象、一个节点类型、三个票据。用一张两步的施工图——第一步修登录页，第二步评审后合入——按出场顺序过一遍：

- **Obligation（交付义务）**是施工图上一步「要交出什么」：交出修复代码；交出评审意见。不管谁来做，这一步的义务固定。它是对象：有自己的活跃、达成、失败、被替代，引擎等的就是它。
- **Seat（席位）**是义务里的一把椅子：作者席；评审席位，可多个。椅子上坐的是启动时选定的施工者；候选切换只在冻结的候选范围内换执行配置与执行体，椅子和裁判身份不变，要改选施工者只能替代 Run。它是对象：票和权限都按席位算。
- **Attempt（尝试）**是某个具体的 Participant（参与者）坐上椅子干的那一次。执行体崩了，同一把椅子开新一次尝试。它是对象：崩了从这里重来，是恢复边界。
- **ChangeSet（变更集）**是一次获准的写入范围加它的 Git 快照：允许改哪里，改完是哪个提交。它是对象：写入权限的边界；对象归 [Repo（仓库）模块](./repo.md)，Run 只引用它的精确快照作评审对象。
- **Gate（评审关卡）**是一种特殊的步：席位不干活，投票；法定票数够了才过。它是节点类型，不是对象，没有自己的生命周期。
- 三个票据是步骤产物，只被引用不被改写。**Verdict（裁决）**是席位判的，**Receipt（凭证）**是控制面判的，两个都是判定结果。**Evidence（证据）**是被判定的事实记录——一份测试输出、一个 CI 状态、工具箱回读到的提交号、一个 diff 的指针——它本身不下结论。凭证的结构是「结论、依据的规则、指向哪几条证据」：完成凭证说验收项一绑证据甲、验收项二绑证据乙；裁决也指向证据，评审员说「要改」时得引测试输出。证据有来路：工具箱直接读到的、适配器结构化上报的、模型转述的，三级可信度不同，验收可以要求某项证据不低于某级。

## 关键规则

Run 采用愿景中的[两种控制制度](./vision.md#两种控制制度)：批准与开工分开，开工后 control 才在冻结边界内自动推进。用户命令和执行体的结果先经校验并持久化，涉及运行时的动作再按撤权与 outbox（发件箱）顺序送往引擎；谁点按钮不是关键，保持这个顺序才是关键。

- 开工时冻结一份施工清单（Manifest）：项目与任务契约版本、施工图、代码基线、席位与候选、能力权限、评审与预算规则一次冻结。
- 施工图上的席位写要求，不写名字：要哪个工种、带哪些 Skill（技能包）、证据不低于哪一级。启动 Run 时才按要求从 Agency 名册选施工者，冻结进施工清单；这次选人独立于 Room 里选规划者，两拨人各选各的，像设计局与施工单位。启动后席位不换人；候选切换只在冻结的候选范围内换执行配置与执行体，工种、职责、权限不动；要换施工者，替代 Run。
- 运行中只有清单声明的放置参数可变；范围、验收、候选或权限变化通过结束或替代旧 Run 生效。
- “重试”有五种身份不同的路径——传输重投、候选切换、引擎重试、语义返工、替代执行。把候选切换当成引擎重试会多建义务并复制票数；把语义返工当成普通重试会沿用旧验收；把替代执行当成重投会让已撤权执行复活。完整分类见[约束附录](./spec/run.md#request重试与-gate)。
- 评审必须独立，独立性有三个来源：被评对象的作者不占必需评审席位；席位是经认证的 Participant 身份，不是随便一个进程；票是附证据、可核的治理记录。别家买独立性的办法有三种：锁定一个评审者；换一家厂商的模型再看一遍；多人发言、最后统一成一个意见。我们直接提供多票评审——席位互相隔离、各投各的票、不看彼此的裁决、不被先发言者带走，法定票数由施工图声明，一票也行。席位之间的分歧不设商量回合：出口只有作者返工再审，或分歧落在契约时升到人。
- 席位的多样性才是票数的意义所在，它有三层：harness 与模型不同、读到的信息与证据通道不同、能干的事不同；换个人设不算，同一个模型换个名字就是同一个错误分布采了两次样（三层的文献依据见[多模型协作有效性调研](../research/multi-agent-effectiveness-20260908.md)）。所以计票有一条机械规则：两个席位若执行配置相同、拿到的材料也相同，只算一票；这条键是我们自己定的，不是文献结论。去重后计入的票少于施工图声明的法定票数，就按票数不可达走既有的失败边，不另发明一种拒绝；两席执行配置相同时预览就警告，材料相同在派发后即可预判，不用等到计票。「席位配置互异」「回避作者所用的配置」是施工图里可声明的策略。备用尝试不增加票数；被评对象换版本后旧票作废，重新过关卡。
- 评审说「要改」分两种：活儿没干好，返工；契约本身有问题，归约器不自动返工也不换人，只把 Task 标需要关注、建议人采纳新契约版本。返工有轮数上限，到了按票数不可达处理，不原地转圈；席位可按策略只看与上一版的差异。
- 一步开始前可以等一个外部机械事实——CI 绿、PR 合并、某个文件出现。它是这一步的准入条件，由工具箱读回，不是一个有人执行的步骤，也不占席位。
- 工作流引擎自带管理界面的直接改写会先改变机械执行，因此只回读为分歧并安全暂停；精确顺序与准入见[Run 约束](./spec/run.md#写入约束)。
- 尝试的逻辑身份由 Run 拥有，物理进程由 Participant 模块观测；两边不维护两套状态。
- Run 正常完成且绑定契约时，由归约器提交同一个 Task 完成命令并交由 Task 独立验收；权威来源定义见[Task 约束](./spec/task.md#写入约束)。
- 裁决与凭证绑定精确的评审对象版本。
- 同一 Run 里节点之间靠结晶接力：评审席位拿被评版本，返工席位拿裁决正文，备用尝试拿同一份上下文并附旧变更集快照的指针。引擎报告的进度、步骤日志和终端记录都不是来源；没提交的对继任者不存在。完整规则见[横切正文](./context.md)。

## 施工图怎么凝结

施工图从 Room 的塑形讨论里长出来。塑形产出三张清单——已决、尚未定形、出界（见[塑形 Skill（技能包）](../../src/agency/skills/hctl2-shaping/SKILL.md)）——它们就是施工图的来料：只有「已决」里能写成「交出什么、凭什么算交出」的条目才能成为节点候选；「尚未定形」只能成为 Request 或 Scoped Room；「出界」不进图。问题之间的依赖在清单里就写下来，结晶时作为候选边逐条判断它是不是产物依赖——问题依赖与产物依赖不是一回事。凝结守六条：

- **节点进图前先说清判据，二选一。** 要么是机械判据——某次 CI 绿、某个 PR 合并、某个文件出现且摘要匹配，由工具箱读回；要么是评审席位裁决加证据不低于某一级。两者都说不清的义务不许进图，退回 Room 继续塑形。这条纪律借自形式化证明平台「说不出形式陈述就不是节点」的做法（见[依赖图与协作](../research/prove2me-dag-collaboration-20260908.md)）。
- **边由机械物承载。** 一条边就是下游节点的准入条件引用上游节点的结晶或凭证标识，不是一句「先做 A 再做 B」；批准时校验图无环、每条边都落地。
- **现在能开工的节点由控制面算出来。** 引擎报告的 READY 是机械进度，语义准入仍归 HCTL2；收尾看的是「没有未达成的义务」，不是谁记得做完了。
- **节点粒度用承诺尺度卡住。** 一个节点是一份值得独立验收的义务，不是一步操作；能被多个节点引用的结晶在结晶时显式标出，图不替你做复用。
- **散文不进图。** 估时、优先级、谁先谁后的口头共识留在 Room；进图的只有义务、判据、边。
- **批准前先读回。** 写图的人就是听过讨论的人，图和讨论对不上，对着图很难看出来。所以批准前找一个不在这个 Room 名册里的参与者——另一个 Room 的规划者，或专门为读回发起的一次调用——只给它冻结的图版本和三张清单的快照，不给讨论原文，让它按节点标识逐条写回人话：交出什么、凭什么算交出、依赖谁、对应「已决」里哪一条。机器先做两件对照：有节点却对不上任何「已决」条目的，是图里长出了讨论没定的事；「已决」里被定为交付义务、却没有节点的，是漏了——「已决」里的范围限制、取舍与验收条件不必成为节点，机器只对交付义务条目要求覆盖。对得上的地方人也要看，因为标识对得上不等于意思没走样，把「只读」写成「读写」机器看不出来。读回是一步加一份 Skill 的产物，批准命令引用这份产物；默认要做，施工图可以声明跳过。它抓的是义务定义错了，抓不出实现会不会做错。

施工图批准后节点集不变：**运行中暂不允许一个节点归约出子节点**。这是保守设定，不是做不到——Participant 内部可以自带依赖图，harness 也普遍有派生子任务的原生机制，节点内的分解属于尝试内部，不进图、不产生新席位与票。暂不允许的原因是还没有一套抑制膨胀的规则：图一可改，模型「顺手把 X 也做了」就有了合法入口，节点也会越切越碎。要防的膨胀有两种——需求膨胀（子节点带进父节点没承诺的东西）和图膨胀（节点与边多到协调压过做事，票跟着翻倍）。将来放开的前提是下面七条规则先立住。七条是我们按所有者对归约扩展的要求立的准入条件，其中只有关键路径预算一条的算法借自一家模型厂商训练团队模式时的时延惩罚（见[调研](../research/deepseek-v41-agent-team-20260910.md)），把训练期的惩罚搬成运行期的预算。每条都写清机器核什么、人审什么：

1. **契约守恒**：归约提交时必须附父子验收项的映射表。机器核两件事——每条子项都映射到某条父项、所有父项都被至少一条子项覆盖、没有映射不到父项的子项；子项在语义上是否真是父项的分解，机器核不了，由审核规则处理。这一条堵需求膨胀：映射不上的东西不是归约，是契约变更。
2. **预算守恒**：子节点不带新预算，从父节点的份额里切。token 按累计算；墙钟指父节点声明的共同截止时刻，不是各子节点耗时相加；节点数按本次授权内累计创建量算，创建再撤销也计数。被多个父节点引用的复用节点只从一处领预算。
3. **两个上限**：每个父节点直接归约出的子节点数有上限，每个根义务下累计创建的节点总数有上限。有这两条加预算守恒，不需要「层数」的概念，图仍是平的：一个节点要么是叶子、有判据和席位，要么已被归约、完成状态由子节点算出来。
4. **归一化**：机械类判据先规范化再取摘要，摘要相同且被验收的对象、输入与适用范围也相同的节点不许再建，只能连边引用；评审类的自然语言判据机器比不了，由审核规则处理。图解决协调不解决复用，复用靠去重强制。
5. **关键路径预算**：归约提交时按声明的份额估算带权重的路径时长——token 按速率折成时间，加上工具与等待的估时——超过父节点声明的时延预算就拒绝；缺权重的不按零算，按父节点份额算。每条产物依赖的边都要引用上游节点声明的产出，不能为了「先做完 A 再做 B」随手连。
6. **审核规则**：预算、上限、归一化与映射表的引用检查全过的归约，只剩语义覆盖一项待审；本次授权的有权人把它和契约变更、追加预算一起裁，都是需要人出场的事。一条不过就按性质走：验收项映射不上是契约变更，预算超了是追加授权，都不是归约。不承诺全自动放行。
7. **落账**：每次归约是新的施工图版本，带父子验收项的映射，可审可撤；已冻结的 Run 不自动切换到新版本，换图沿用替代 Run 的规则，撤销也不撤回已经发生的副作用。

放开之前先把度量跑起来：每次 Run 从执行事件重建尝试内部的依赖图，算带等待的关键路径时长、总 token、节点数、归约次数，作观测进控制面存储。这些数先只看不用；跑过几十个真实变更后，由它们定上限的默认值，也由它们决定开不开。

- **快慢看带等待的关键路径时长，省不省看 token。** 执行体上报的派生、等待、消息等结构化事件，控制面事后重建成这次尝试内部的依赖图：关键路径按事件的时间权重算——token 折成时间，加上工具与等待——不是数跳数，否则一个串行干等两小时 CI 的节点看起来很短。并行不该被罚，不必要的串行与同步才该。总 token 计入失败、取消、备用、返工、读回和尝试内部队友的消耗，不只算最后留下的票。三条边界：这两个数都来自执行体或 Agency 自报，本地参考实现的数据由工具箱可见进程树校准，远程自报只作参考；事件上报不全时标未知，不能当作更短的路径；一次尝试内部的图不等于整个 Run 的时长，跨尝试的等待与返工另计。两个数各说一件事，不能互相替代；它们都是观测，不进施工图。

## Workflow 场景

Workflow 场景提供施工清单预览、只读图、节点/席位/尝试的渐进展开、Request、证据、暂停/取消和恢复状态。

| 角色 | 可以做什么 |
| --- | --- |
| 场景客户端：Workbench Run 图 | 查询、预览并通过公共命令服务提交 Run 命令 |

Workbench 关闭不停止 Run。Workbench 就位前由 `hctl2` CLI 调用公共命令服务，就位后仍调用同一服务。工作流引擎控制台保留为供应端管理与诊断界面；其直接动作按[Run 约束](./spec/run.md#写入约束)回读为机械事实与分歧。

## 模块交接

以下只列所有权方向；字段、事务与故障语义由[连接约束](./spec/connections.md)统一定义。

- Project 通过启动命令交付冻结的 Project 与施工图引用；可选的任务契约版本由 Task 提供，Run 独占施工清单与执行生命周期。
- Run 向 [Participant](./participant.md) 模块交付派发时冻结的执行规格（Execution Spec）；Participant 模块只返回结果提案、证据和物理观测，变更集快照由 [Repo](./repo.md) 模块在 Run 准入提案的同一事务里准入。
- Run 的评审席位引用 Repo 模块的变更集快照；评审关卡通过后的合入意图由有权的人或冻结的归约器提交给 Repo 模块执行、回读并写凭证。
- Run 向 Task 返回精确的 Run、裁决与凭证引用；正常完成且绑定契约的 Run 可由归约器提交同一个 Task 完成命令。Run 向 Project 提交 Request 并投影低噪声里程碑。
