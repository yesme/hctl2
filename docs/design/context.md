## 为什么存在

Context 不是“把最近若干条聊天塞进 prompt”。那只能恢复文字，回答不了真正要紧的问题：这次执行继承了哪些目标、决定、约束和未决问题？每条信息来自哪里、是否还新鲜？检索覆盖了什么、漏了什么？故障切换之后，能不能重现同一份交付义务？

先划清管辖：**我们管理的是 prompt——调用开工时交给执行体的那个包；不代管执行体在会话内自行组装的工作上下文。** 仓库代码、Memo、Skill 这些材料，执行体自己会挖、自己管理——读文件、载技能本来就是它的本职，它比我们更清楚自己需要什么。它拿不到也不该自己去翻的来源只有两处：聊天史，和绑定 Task 在任务后端上的评论线——两者的读写凭据都是 HCTL 不交付给执行体的外部凭据，翻全史也烧 token。所以本文的主题就是那个开工包怎么来：从这两处讨论里萃取的相关部分 + 契约与范围 + 同一 Run 里前序节点的结果 + 指向其余材料的精确指针。

遍览同类工具后的共同结论是：上下文是必需品，而且直接决定四件事——冷启动成本、重复核验次数、模型的有效工作时间、结果的可复核性。目标不是“给得越多越好”，而是：

> 在获准范围内，用尽可能少且足够的信息恢复工作的因果链，并让每个结论都能回到来源。

检验标准就三个字：**快、省、准**。快——识别相关上下文毫秒级；省——缺省全本地、组装不花模型 token，模型辅助（相关性门、压缩、纪要）全部可选可配置；准——因果链完整、结论可回源，由冻结与可解释兜底。三个字同时成立才算合格，牺牲任何一个都要在清单里显式可见。

## 与相邻概念的分工

| 东西 | 是什么 | 不是什么 |
| --- | --- | --- |
| 聊天历史 | 完整、按序的协作记录（content，住在 chat server） | 默认 prompt，也不是长期知识库 |
| 工作投影 | 由引用、置顶/排除与当前对象重建的讨论现场 | 独立对象；可随时重建 |
| Context Manifest（根上下文清单） | 一次授权用什么来源、怎么选的、基于哪个时间点的不可变说明 | 内容本身 |
| Context Bundle（消费上下文包） | 按某个执行者的权限和预算实际物化、交付的内容 | 可以事后改写的东西 |
| Memo | 显式提炼、预览、去敏后发布的长期知识 | 聊天或执行日志的自动沉淀 |
| 任务评论线 | 绑定 Task 在任务后端上的讨论（content，住在任务后端） | 契约——改验收契约的内容仍只经「采纳契约」进入 Task Revision |
| 前序节点结果 | 同一 Run 里产出者、评审者已结晶的产出与裁决（账本与 Git） | 工作流引擎里的东西——引擎报告的进度与步骤日志不是来源 |
| 会话内工作上下文 | 执行体在会话中用自己的工具挖出来、自己管理的动态上下文（读文件、载 Skill、查 Memo） | 我们的管理对象——只观测，不代管 |

搜索索引、检索服务都是可重建的内部投影，不是权威；任何索引都必须能从来源和不可变引用重建。

## 投喂三档：内联、指针、代取

执行体不是裸模型，是模型加工具循环——读文件、跑 git 是它的普通工具调用。所以开工包里的每样东西只有三种给法，按“执行体自己够不够得着、是不是每次必用”定：

| 档 | 给什么 | 怎么给 | 例子 |
| --- | --- | --- | --- |
| 内联 | 每次必用、放得下的 | 原文直接写进 prompt | 契约与范围、指针清单本身、萃取出的讨论、评审席位的被评 diff、返工席位的裁决正文 |
| 指针 | 可能用、执行体用自己的工具够得着的 | 精确地址（ref + digest）加一句话说明；执行体按需 `git show`、读文件 | 代码、变更集提交、Memo、Skill、登记在 Git 里的 Artifact |
| 代取 | 执行体够不着的 | 开工时由组装器萃取后内联；运行中要补，走受限召回——模型提出取什么、control 按冻结的召回策略校验、HCTL 自己的检索器去取、结果作为子包塞回会话 | 聊天史、任务后端评论线、账本里的裁决与凭证 |

指针只能指向执行体在获准范围内用自身工具能打开的位置——Git 对象和 worktree 路径。指向账本或任务后端的引用不是指针，执行体解不开；这类东西要么开工时物化，要么走代取。

分档的依据是成本。解一次指针不是“几百 token”：多一轮往返，就多一次全上下文重读、多一段从此驻留在上下文里的工具输出、多一次串行延迟。同类工具消耗 token 的四个原因是固定前缀过大、每轮重读且工具输出长期驻留、让模型处理本可由代码完成的工作，以及多个执行体把前三项相乘。指针只涉及其中的工具输出，而“全内联”会直接放大固定前缀。

所以规则是**少一轮，而不是少一个指针**：确定会用的内容由组装器注入，不让模型猜；可能用的内容给少而准的指针并附摘要，让执行体有跳过的依据。探索式阅读是执行体自己的事，子上下文隔离正用于这种探索。

## 萃取与压缩：中心设计

进展由讨论驱动，讨论住在两处：聊天室，和绑定 Task 的任务后端评论线。每次调用的第一件事，是从这两处**萃取**出与这位执行者相关的部分。这一步必须快，缺省全本地、不花模型 token：先按显式引用与讨论窗口命中，再由本地检索兜住隐式关联，只有用户配了专用小模型时才引入模型判定。分级的精确定义、判定输入与审计要求见[约束附录](./spec/project.md#contextmemo-与-artifact)。

开工包里物化原文的，就是三档里的内联与代取：萃取出的相关讨论、用户显式引用的内容、契约与范围，以及同一 Run 里前序节点结果中必用的部分（见下文接力一节）。其余材料——仓库文件、Artifact、Memo、Skill——只进指针（精确引用 + 指纹 + 一句摘要），由执行体在获准范围内自己取用：可能用的东西，懒加载比预先塞进 prompt 省。顺序也随之定下：prompt 的稳定部分（契约、范围、指针清单）在前，高频变动的萃取讨论在后。语义上该这么排，推理服务的计费与缓存也偏爱这么排，两个理由不打架。

萃取出的上下文**缺省不压缩**，原文直给、预算内按选择优先级裁剪。只有当用户配置了专用小模型（small-brain）时才启用**压缩**——摘要式或逐词裁剪式都可以，但压缩永远是清单里显式记录的一步：用了哪个模型、压了多少、原文指纹是什么，全部冻结；可解释性不因压缩打折。证据类内容——指纹、凭证、验收标准原文——永不压缩。small-brain 只是执行者配置里的一个模型引用，不是新对象。

长期记忆不在这里发明：结晶进 Git、场景内容留在各自的系统，是三类数据已经回答的问题。别家在自建第五套记忆库，HCTL2 的 Context 只做一件事——把工作记忆组装对。

## 前情提要：房间的滚动上下文

从父概念转入子概念（Repo Room 提升出 Project Room、Project 派生 Scoped Room 或启动施工）以及在长房间里反复调用时，都有一份“前情提要”要交代。它其实是三种生命周期不同的东西，“每次传不传”分别回答：

| 成分 | 是什么 | 每次传吗 |
| --- | --- | --- |
| 权威骨架 | Project 的目标、范围、验收要点、当前契约、指针清单——带版本号的权威文本，不是摘要 | 每次传：小、稳定、免费，坐 prompt 的稳定头 |
| 出生来源链 | 提升时冻结的显式来源 | 不每次传：指针化，萃取命中才物化 |
| 滚动讨论纪要 | 讨论过、口头定了、但尚未结晶成 Memo 或契约的共识 | 分级，见下 |

滚动纪要按三条规则管住：

1. **没配 small-brain 时它不存在**，用零模型成本的“近详远略”代替——近期消息全文、更早的降为标题加事件指针。这个缺省的缺陷是故意保留的：重要的口头共识就该结晶成 Memo，缺省态的不完美恰好推动显式沉淀，而不是纵容“反正纪要会记住”。
2. **配了 small-brain 时它存在且每次传**：一份挂在（房间，游标）上的增量折叠缓存——新消息折叠进旧纪要，不从头重推；天生紧凑，折叠比原始聊天变化慢，不常击穿缓存前缀。
3. **它永远是派生缓存，不是权威**：每条带消息事件回源指针；治理引用不得指向纪要，只能指向精确事件；丢了就重建，不进账本，清单只记引用与指纹。它也不由房间里的模型 Participant 书写——“agent 自己决定记什么”是自述，纪要是组装器机械触发、small-brain 计算的系统派生产品。

父转子不需要新机制：父房间的纪要（若有）作为提升/创建预览的预填材料，人删减、补充、去敏并确认后冻结为子房间的出生来源链；出生之后各长各的，父房间后续讨论不会活体渗入既有子概念。

## 同一 Run 内的接力：节点之间传什么

一条施工图跑起来后，产出者、评审者和返工节点之间也要传上下文。它既不是聊天史，也不是父子传承，而是横向接力；它的存储是账本和 Git，不是工作流引擎。引擎只报告执行进度，步骤日志也不是上下文来源。规则按三档套用：

- **评审席位拿被评对象**：精确的变更集快照或 Artifact 版本。这是必用的，差异在预算内就内联；放不下就给精确到代码片段的指针和分片建议，执行体用 Git 自己查看。
- **返工席位拿裁决**：Verdict 正文小、必用，直接内联。它的权威在账本，Git 里只有结晶副本（公开仓库可能只剩摘要），所以物化以账本记录为准，副本只作指针。
- **备用尝试拿同一份包**，外加旧变更集快照的指针。**没提交的对继任者不存在**：旧工作树里没形成变更集快照的半成品不传承——和“替代执行换新工作树”是同一条规则。

Terminal 场景的分工由此定下：harness 之间只有结晶过的东西能过去——变更集分支上的提交、发布的 Memo、提案里引用的证据；终端 trace 是观测，不自动进任何人的上下文。

## 关键规则

- **可解释**：清单记录来源、筛选依据、新鲜度、覆盖面和已知缺口，权威字段见[Project 约束](./spec/project.md#context-memo-artifact)。
- **冻结**：执行规格冻结清单与消费包，并按[连接约束](./spec/connections.md)核对交付字节。
- **传承有链**：Repo Room → Project → Task/Run → 消费包只通过显式来源引用传承。
- **投喂三档**：必用内容内联，可达材料给精确指针，不可达材料由组装器代取；范围见[Project 约束](./spec/project.md#context-memo-artifact)。
- **接力只经结晶**：Run 内以变更集/Artifact 版本、裁决与证据的精确引用接力，见[Run 约束](./spec/run.md#request重试与-gate)。
- **运行中召回受原授权约束**：追加检索按冻结的范围、权限与审计规则形成子包。
- **晋升有门槛**：Memo 经显式提炼、预览、去敏和发布，保留来源、适用范围与有效期。
- **成本纪律**：采集、规范化、检索、融合和排序机械化；可选压缩记录模型、预算、结果和原文指纹。
- **降级显式**：来源不可用时标出新鲜度与缺口，按[Project 约束](./spec/project.md#context-memo-artifact)保留可回源性。

## 场景

Trigger Preview 在提交前展示本次调用的上下文构成与 token 估算；升格 Project 时的提升预览允许删减、补充和去敏，只带显式选中的来源链。这两处是用户直接触摸 Context 的地方——其余时间它安静地保持正确。
