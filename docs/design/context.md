# Context 与可解释上下文

> 状态：规范性（横切设计正文）· 草案 v0.12.2<br>
> 日期：2026-08-24<br>
> 定位：本文回答"每次执行看到了什么、为什么是这些、漏了什么"。它是横切设计正文，不是第五个模块：上下文清单与内容包的合同在 [Project 模块合同](./spec/project.md)，随执行规格冻结与交付核验在[连接合同](./spec/connections.md)与 [Agent 模块合同](./spec/agent.md)。合同级细节的完整底稿与逐条裁决来源见 `.memo/context-design-20260819.md`；生态四族地图与快省准横评见 `.memo/context-landscape-20260824.md`。

## 为什么存在

Context 不是"把最近若干条聊天塞进 prompt"。那只能恢复文字，回答不了真正要紧的问题：这次执行继承了哪些目标、决定、约束和未决问题？每条信息来自哪里、是否还新鲜？检索覆盖了什么、漏了什么？故障切换之后，能不能重现同一份交付义务？

遍览同类工具后的共同结论是：上下文是必需品，而且直接决定四件事——冷启动成本、重复核验次数、模型的有效工作时间、结果的可复核性。目标不是"给得越多越好"，而是：

> 在获准范围内，用尽可能少且足够的信息恢复工作的因果链，并让每个结论都能回到来源。

检验标准就三个字：**快、省、准**。快——识别相关上下文毫秒级、全本地；省——组装本身不花模型 token，压缩可选不强制；准——因果链完整、结论可回源，由冻结与可解释兜底。三个字同时成立才算合格，牺牲任何一个都要在清单里显式可见。

## 与相邻概念的分工

| 东西 | 是什么 | 不是什么 |
| --- | --- | --- |
| 聊天历史 | 完整、按序的协作记录（content，住在 chat server） | 默认 prompt，也不是长期知识库 |
| 工作投影 | 由引用、置顶/排除与当前对象重建的讨论现场 | 独立对象；可随时重建 |
| 上下文清单 | 一次授权用什么来源、怎么选的、基于哪个时间点的不可变说明 | 内容本身 |
| 内容包 | 按某个执行者的权限和预算实际物化、交付的内容 | 可以事后改写的东西 |
| Memo | 显式提炼、预览、去敏后发布的长期知识 | 聊天或执行日志的自动沉淀 |

搜索索引、检索服务都是可重建的内部投影，不是权威；任何索引都必须能从来源和不可变引用重建。

## 萃取与压缩：中心设计

进展由聊天室驱动，所以每次调用的第一件事，是从聊天史里**萃取**出与这位执行者相关的部分。这一步必须快、必须全本地、不花模型 token，走三级阶梯：

1. **结构化引用**：显式引用、讨论窗口、对象引用链——组装顺序的既有第一级，零成本且全对；
2. **本地全文检索**：从消息流增量维护、可随时重建的本地索引，配机械融合排序——毫秒级、零费用，兜住显式引用漏掉的隐式关联；
3. **可选的小模型相关性门**：只判"该不该拿"，判定输入用账本里的事实（谁被提及、谁认领了什么），不用消息措辞；每次判定入账可审计。

萃取出的上下文**缺省不压缩**，原文直给、预算内按组装顺序裁剪。只有当用户配置了专用小模型（small-brain）时才启用**压缩**——摘要式或逐词裁剪式都可以，但压缩永远是清单里显式记录的一步：用了哪个模型、压了多少、原文指纹是什么，全部冻结；可解释性不因压缩打折。证据类内容——指纹、凭证、验收标准原文——永不压缩。small-brain 只是执行者配置里的一个模型引用，不是新对象。

长期记忆不在这里发明：结晶进 Git、场景内容留在各自的系统，是三类数据已经回答的问题。别家在自建第五套记忆库，HCTL2 的 Context 只做一件事——把工作记忆组装对。

## 关键规则

- **可解释**：每次调用冻结一份上下文清单——来源、筛选依据、新鲜度、覆盖面和已知缺口都写在里面；事后永远能回答"它当时看到了什么、漏了什么"。模型的自由总结不能替代来源和版本。
- **冻结**：执行规格同时冻结清单与该执行者的内容包，交付前核对实际字节；此后的聊天、索引变化或另一个执行者的包都改不了已冻结记录。
- **传承有链**：Repo Room 的研究 → Project → Task/Run → 每个执行者的内容包，只能通过显式的来源引用传承；"最近消息"、当前指针或搜索排名都不构成传承。
- **运行中追加召回不越权**：执行中可以在获准范围内补充检索，但不能绕过冻结的范围、权限与审计。
- **晋升有门槛**：原始消息和执行日志不会自动变成长期知识；进 Memo 必须显式提炼、预览、去敏、发布，带来源、适用范围和有效期。
- **成本纪律：能用规则就不用模型。** 采集、规范化、检索、融合、排序全部机械化；摘要压缩是唯一显式的模型步骤——有预算、结果持久化、增量折叠而不是每次从原文重推。每次调用的上下文构成应可审计（哪些来源、各占多少），固定前缀保持稳定以利缓存。
- **降级显式**：来源不可用时按级降——先本地检索并标注来源，再提示缺口；不用陈旧缓存冒充新鲜读数。

## 场景

Trigger Preview 在提交前展示本次调用的上下文构成与 token 估算；升格 Project 时的提升预览允许删减、补充和去敏，只带显式选中的来源链。这两处是用户直接触摸 Context 的地方——其余时间它应该安静地正确。
