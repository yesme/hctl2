# Participant（参与者）与 Terminal

> 状态：规范性（架构层）· 草案 v0.18.6<br>
> 日期：2026-09-10<br>
> 定位：本文回答“谁在干活、按什么方法、结果归于谁，以及这一次派工怎样经 Agency 交互、观察和接管”。

> 本文是 Participant 模块的设计正文：它为什么存在、拥有什么、按什么规则运转。精确对象、状态机与写入约束见[约束附录](./spec/participant.md)；模块交接见[连接约束](./spec/connections.md)，共享机制见[系统边界](./spec/system.md)。

## 为什么存在

“机器上装了哪个 CLI”回答不了“这项工作该由谁、按什么方法做”。自动探索本地 Harness 只是解析链的最后一步——它知道这里有什么工具，不知道谁在工作、以什么人设出现、带着哪份方法论、是否有资格参与评审。把这些混成一团，就会出现三种熟悉的病：换个进程就像换了个人（结果无法归属）、评审席位形同虚设（同一个模型换个名字给自己投票）、以及 BYOA（bring your own agent）——手边正好有哪个工具就让哪个裸模型上，工作质量随手气波动。

另一头，进程、PTY（伪终端）、worktree（Git 工作树）和终端连接都是可替换的物理资源：它们可以丢失、重建和接管，但不能反过来定义 Project、Task 或 Run 的事实。执行结束了，不等于上层成功了。

Participant 模块把这两头接成一件事：稳定的是参与者身份，变化的是它被实现的方式。新进程、新会话、备用尝试都不产生新的参与者；换成另一个参与者也不能靠复用同一套执行配置伪装成同一个人。模块的职责，是把上层的一次授权变成可归属、可观察、可隔离、可恢复的物理执行，并诚实上报发生了什么。

**人不是 Participant。** 人不干活，人拍板：目标由人定，契约由人采纳，完成由有权的人或确定性归约判定。人在约束层写作 human actor，出现在命令、名册和裁决里，不进入本模块的七件事分层。本模块只管数字参与者。

## 模块拥有什么

Participant 模块保存“谁在干活、怎么实现、这一次由哪家 Agency 承接”的事实。它拥有：从 Agency 名册收进来的工种（Profession）冻结引用；被选进某个 Room 或某个 Run 席位的参与者记录及其人设标签；Skill（技能包）的申报值与可核验性；可复用的执行者配置（哪个 Harness、什么模型、什么权限）；工种申报的 harness、模型与承诺能力；对 Agency 的每次派工及其终端通道；以及经 Agency 提交给上层校验的结果提案与证据。它不决定 Project 目标、Task 完成、Run 的评审结果，也不创建下一条协作边。规划者的名册归 Room，施工者的席位归 Run，变更集（ChangeSet）与它的写入租约归 [Repo（仓库）模块](./repo.md)——执行体只在有效租约下写自己的独立工作树，本模块只是被它们引用。

## 七件事分层

一个数字参与者由七件生命周期不同的事组成，不能压成一份大配置：

| 层 | 回答的问题 | 明确不回答 |
| --- | --- | --- |
| 工种（Profession） | 派出方能派什么样的人：哪个 Harness、什么模型、带哪些 Skill、默认做规划还是施工、条款如何 | 具体进了哪个项目、哪次执行 |
| 参与者（Participant） | 这个工种的一个实例被选进了哪个 Room 或哪个 Run 的席位，叫什么、承担什么职责、权限与预算上限 | 跨阶段的身份、物理能力 |
| 人设（persona） | 以什么风格表达与协作 | 能否完成、能访问什么 |
| 模型与特殊训练 | 行为能力来自哪个模型谱系 | 参与者身份和权限 |
| Skill（技能包） | 本次装载哪份可版本化的方法 | 自动授权工具、自动获得票权 |
| 执行者配置 | 模型、模式、环境、候选端口怎样组合 | 此刻哪台机器可运行 |
| 一次派工 | 这一次由哪家 Agency 承接、按哪份执行规格 | 上层角色、验收或完成；门后的进程、会话与主机 |

上三层由人与控制面掌握：工种的内容由 Agency 定义，控制面拥有的是收进来时的冻结引用与摘要，不是定义权；参与者与人设标签在选人时定。下四层的实物由 Agency 供给（见[Agency 与执行体](#agency-与执行体)），控制面存储只冻结对它们的精确引用。调用前的 Trigger Preview 把这条链完整摊开：实际的参与者、人设、模型、技能包、执行配置、权限、预算和降级，一次看清再提交；冻结之后整条身份链不随后续变化漂移，结果沿链回溯到精确版本。

## 关键规则

规则分四组：身份与方法、变更集与 Git、执行体与观测、终端与恢复。变更集本身归 Repo 模块，第二组只写执行体一侧。

**身份与方法**

- Participant 是被选进某个 Room 或某个 Run 席位的一位工种实例，只存在于被选进的地方；命令权限、评审票和委派边界由 Room 名册与 Run 席位授予，见[Project 约束](./spec/project.md)与[Run 约束](./spec/run.md)。
- 人设、Skill 与能力声明分别表达风格、方法和候选能力；实际权限与本次装载以[约束附录](./spec/participant.md)和[连接约束](./spec/connections.md)冻结的执行规格为准。
- 选人发生两次、各自独立：建 Room 或 Trigger Preview 时选规划者，启动 Run 时按席位要求选施工者，像选设计局与选施工单位。项目本身不持有成员名单，只持有选人策略——允许哪些 Agency 与工种、预算上限、多样性要求。Room 名册换人不改写活动调用；Run 席位启动后不换人，候选切换是控制面在候选范围内另发一次派工。
- Skill 依次区分声明、实际可用与本次已装载。可用与已装载由 Agency 申报，control 记录申报值并标注能否核验：有经 Agency 取得的直报核验报告标 known，只有申报标 unknown；远程不天然 unknown，本机不天然 known。只有冻结进执行规格的版本对本次执行生效。
- Skill 提供指导和上下文，不获得命令、评审或写入权。
- 评审独立性按[Run 约束](./spec/run.md#request重试与-gate)记录可认证性：能机械认证的标 known，不能的标 unknown；不用逻辑身份代替物理证明。

**变更集与 Git**

- worktree 是参与者管理的可替换载体，精确成果另有可恢复副本后可以清理重建，不永久属于任何 Project、Task、Room 或参与者。
- 一个变更集同一时刻只有一个写入者；换人、接管或取消，都要先让旧写入者失权。失权是两个模块各做一半：Repo 模块撤销租约、不重授；本模块经 Agency 停止或隔离旧执行、由 Agency 交出证据，证明不了就不算隔离。
- 恢复时证明不了旧写入者已经安静退场，就把旧现场原样隔离、换一个新工作树重来；来历不明的修改绝不悄悄混进新的产出。封存、保全与清理不删孤本的规则由 [Repo 模块](./repo.md#关键规则)拥有，`hctl2-tool` 执行。
- Harness 在自己的工作树里可以正常用 Git：看分支、看日志、fetch、和目标分支比对、在自己的变更集分支上提交，获准源版本可由持凭据单元交付到平台。模型说“我已经合并了”不可信：本控制面的集成凭证只经持久意图、执行与回读产生，归 [Repo 模块](./repo.md#关键规则)，由 `hctl2-tool` 与平台适配器校验事实；其他写者更新目标是事实，是否使本次授权失效按冻结条件核对，不一概判为违规。
- Harness 只经提案交回结果，模型不拿通用的人或控制面凭据与集成权，源版本交付与目标合入分别授权，每个 ChangeSet 使用独立工作树与写租约；Harness 治理的三条底线和可选加固由[约束附录](./spec/participant.md#写入约束)定义。

**执行体与观测**

- 执行体之间只有结晶过的东西能过去：变更集分支上的提交、发布的 Memo（备忘）、提案里引用的证据。终端 trace 是观测，不自动进任何人的上下文；没提交的对继任者不存在（见[横切正文](./context.md)）。
- 观测（进程、屏幕、心跳、钩子）用于触发关注；领域结果只经提案与上层准入形成。
- 证据按“经没经过模型的嘴”分三档：直报（获准的采集方经模型写不进去的通道交来、来源与所证版本可核）、旁路（适配器旁路看到的结构化事件）、转述（模型自己说的）。转述最不可信；验收可以要求某项证据不低于某档。直报有三路来源；参与者内部的工具经 Agency 转交这一路，要 Agency 具备并声明「代为执行工具并直报」的能力才算直报。
- 参与者进程干净退出不等于交付了结果。Agency 为它接入的每个端口声明终局结果清单，正常退出但缺少清单要求的事件按协议错误处理、不默认成功；我方主动取消导致的退出按取消归因，不冒充执行失败。清单的精确要求见[约束附录](./spec/participant.md#派工与观测)。
- 观测流要么完整、要么显式截断收尾。上报通道失败后，宁可把这次派工标记为观测截断，也不交付有缺口的事件流冒充完整历史；参与者内部再派出的队友是它的内部，Agency 只报这次派工的用量，报不全标未知。
- 参与者只拿到本次派工需要的窄能力。它可以建议完成、建议下一位协作者；建议走提案通道由上层校验，不是命令。

**终端与恢复**

- Project、Task、Room、Run、Participant、Seat 都没有“自己的终端”；终端只属于一次具体执行。
- 一次派工被替代后，旧派工的连接、输入和结果一律失效，只留审计；Agency 在冻结规格内的门后接替不换派工，控制面无感。
- 客户端退出不停止执行；断流恢复按 Agency 声明并负责的恢复等级标注。

## 专业化 Participant：告别 BYOA

评审是第一个必须专业化的岗位。今天的评审靠模型的自发判断，没有方法论——这正是 BYOA 的局限。解法是在确定参与者的阶段引入**专业化 Participant：模型 + 专用方法论 Skill**。

- **方法论是 Skill，不是临时提示习惯。** 评审方法论（审查骨架、对抗核验、约束漂移检查这类审计方法）沉淀为带版本的技能包；评审席位选的是一个带该技能包（已装载态）与合适模型、执行配置的工种实例。Skill 改变的是参与者去拿什么信息、关注什么方面，也就是它的上下文；工程类 Skill 之所以有用，正因为它们改变了这一点。
- **人设不是方法。** 人设是交流与界面属性：给用户挑人时作参考，在 Room 里影响规划者的说话风格。它不作为独立性与票权的依据——同一个模型换个人设、读同一份材料，就是一票。
- **由此换来三件工程性质**：输入可追溯（凭证链记录评审所用的方法论版本与交付的材料）、可升级（方法论出新版，新调用可以采用，已冻结的执行不随之漂移）、可比较（两次评审结论不同时，能对照方法版本与模型是否变了）。这三件是版本化 Skill 的工程性质，不是文献证明的准确率结论；方法论版本有经 Agency 取得的直报核验报告时标 known，只有对方一句申报时标 unknown。BYOA 这里要排除的是裸模型临时上场，不是外部自带的参与者——外部参与者同样可以带可核验的方法。
- **与评审独立性正交叠加**：Gate 的评审席位选这类工种，得到“有方法论且独立”的评审；专业化不改变票权规则，结论仍只是裁决输入。两个席位算不算两票，只看 Run 正文那条计票规则——执行配置与拿到的材料是否相同；席位的必需 Skill 是材料的一部分，所以两份不同的 Skill 会让两席的材料不同。控制面能核对的是每个席位被交付了什么、召回了什么，不是它实际读了什么、跑了什么检查，那要凭证据核对。
- **Skill 给方法，控制面管权限与判定。** 方法论 Skill 决定怎么问、怎么切、怎么查，但它拿不到命令、票权和写入权：必须由人回答的问题不能被模型代答，完成不能自述，规划空间不能给自己签发执行权。这些门放在 prompt 里必然失守——33 家工具的复核里，提示词层的门普遍软化或死亡，常见的死法是「从未触发」——所以这些限制由控制面执行，不靠 prompt 保证。
- **自食其力**：HCTL2 自己的设计评审应最早切换到这个模式，替代各 harness 裸模型的自发评审。
- **从选人到被推荐（延长线）**：今天选人是人从名册里按选人策略挑；将来控制面帮着挑，分四步。召回：按能力相近与过去的履约记录找一批候选。可行性过滤：选人策略允不允许、权限够不够、材料能不能送到、要不要回避作者所用的配置、多样性声明满不满足。排序：能力缺口盖住多少、预期总成本（含返工）、时延、当前负载。任用：先预填候选并说明推荐理由，人点一下；本次选入与授权沿现有路径，自动任用另议。比较的是有版本、有履约条件的公开供给与结果：一次成功只算一条证据，配置一换旧成绩只作先验，Agency 的申报与我们自己的凭证分开记，具体记录结构留专题稿。常规任务只用静态规则和已有记录，复杂或异常才上重机制，避免测量税。边界：这是选人与供给匹配的能力，不另建一套 Task 与 Run；需求画像从本次 Room 调用的目标与范围、Task 契约、席位要求和上下文按适用路径生成。原料是既有凭证与执行、返工记录。制度产生记录，记录支持校准，校准改善推荐；更会选人不等于自动学会新方法，成功做法成为备忘或技能候选，发布与装载仍沿现有路径。底稿与评审在专题过程稿，尚未进入约束。
- **商业化延长线**：将来受雇的外部数字员工同样落在这套结构里——对方的派出机构就是一个 Agency，它派来的就是执行体；派出不转移参与者身份，“谁在工作”仍由控制面的 Participant 层回答，派出方只供给下四层。为什么最先值得雇的是评审者、以及市场机制为何暂不设计，见[愿景](./vision.md#要解决什么不解决什么)。

## Agency 与执行体

先把几个容易混的词分清。**Profession（工种）**是 Agency 名册上的一类可派的人：哪个 Harness、什么模型、带哪些 Skill、默认做规划还是施工、条款如何——由 Agency 定义，收进来时冻结引用与摘要。**Participant（参与者）**是一个工种的实例，被选进某个 Room 或某个 Run 的席位才存在：选进 Room 的是**规划者（planner）**，被调用参与讨论、提出下一次调用的建议，临场执行边仍由人提交；选进 Run 席位的是**施工者（worker）**，占席位干活或投票。两次选人各自独立，同一个工种在 Room 里选出的「Jack」和在 Run 里选出的「Jack」是两条记录，名字只是标签，不跨阶段共享身份。由此有一条产品行为：Room 里的 `@` 只解析本 Room 名册里的规划者；要和正在执行的施工者交互，进绑定那次执行的 Execution Chat，不在 Room 里喊——没有活动执行时界面照实说，不把输入转投同名的规划者；提及施工者、分享它的结果都不受限。**执行体（execution runtime）**是 Agency 门后按一次冻结的执行规格实际干活的运行：一个 harness 进程、装载的 Skill、一条会话。控制面看不到它，只持有对 Agency 的**派工**——提交执行规格并被接受后得到的引用，Agency 对它负责；派工把参与者记录、Skill、权限和上下文包冻结进执行规格，Agency 据此在门后拉起进程。Agency 在规格内重启会话、改派备份、换主机，是它门后换执行体，派工不变、参与者不变，控制面无感；控制面在候选范围内另发一次派工（候选切换）才是换派工，仍不换参与者。同一个施工者同一时刻跑一个还是几个执行体，是参与者自己实现的事：默认一个接一个，也可以并行。**agent** 只是行业里对编码代理的泛称，本文件只在引用行业用语（如 BYOA）时用它，不指任何 HCTL2 对象。执行体内部可以自己再派出队友——有的 harness 提供团队模式，一个执行体里跑一队 agent（见[调研](../research/deepseek-v41-agent-team-20260910.md)）——那些队友都在同一次派工、同一个 ChangeSet 与工作树里，不是席位，不投票，评审席位拿的是它们封存后的版本，看不到它们之间的中间状态。执行者配置若是团队模式，一次尝试烧的 token 与墙钟都不同，Trigger Preview 要能看出来，预算按此估；Agency 只报这次派工的用量，报不全标未知，控制面不重建门后的团队图与进程树。

Terminal 场景的专职系统是 Agency。它像 HAProxy 那样是参与者的唯一出口：control 的对手方只有 Agency，向它要人、向自己的租户派工，输入、停止、观测、终端连接与结果回传都经它转接；客户端也不直接与参与者沟通。

- **Agency（派出方）** 是参与者的供给方：维护可派出的名册与条款，接受冻结的执行规格并对这次派工负责。选人发生在建 Room 或 Trigger Preview 时（选规划者）和启动 Run 的预览时（选施工者），批准施工图本身不选人；每次都是一回“要人 → 报人”的对话：control 说需要一个带某方法论、某权限的评审者，Agency 回答名册里哪些满足、条款如何；人从名册里选，控制面准入并记录，Agency 不替人选。Agency 不制造参与者，参与者是人从名册里选进 Room 或 Run 的；Agency 定义的是工种；一般也不制造端点，远程数字员工是既存的一方，你是去约它，不是去造它。本地实现启动一个新进程，那是本地的机制，不是架构。
- **派工** 是控制面持有的唯一执行引用；门后有几个进程、在哪台机器、换过几次，控制面不知道也不需要知道。Agency 有全部通路，没有任何治理权威：转接不是准入，租约、代次、冻结规格、票据与结果准入的裁决只归控制面；恢复等级由 Agency 声明并负责，控制面只记录。
- Agency 像一台裸金属，给每个配对的控制面开一个隔离租户：一次派工只属于一个租户、只听它的控制面；另一控制面的动作在结构上不可达（精确清单见[安全策略面](./spec/system.md#安全策略面)）。两个控制面共用一个 Agency 而互不可见，是用例里的常态（mac 上的 Agency 同时给 mac 与 cloud 的控制面供人）。
- 参与者卡住由 Agency 兜住：在冻结的执行规格内重启会话、改派备份、换主机，控制面无感；规格内干不了才报「无法履约」，控制面按冻结规则处理；Agency 联系不上只是联系不上，按截止与取消条件处理；Agency 挂了由人指定别的 Agency。回来的旧执行体在门后被机械核对——图还是那张图、席位还归自己——核不过就不能再以这次派工的名义写入或封存，已保管的结果仍可交回。
- Agency 定义工种并供给七件事分层的下四层：模型、Skill、执行者配置、一次派工。选谁进 Room、谁占席位、叫什么、带什么人设标签，人从名册里选，由控制面准入并记录。
- Skill 由 Agency 申报（名册里写着这个工种带哪些 Skill、什么指纹），由参与者装载，核验报告经 Agency 取得，由控制面记录核验结果 known 或 unknown。

**发布包自带一份本地 Agency 参考实现。** 装了 HCTL 就有参与者可派，不出现“架构上很美、本机却没人可用”的情况。它对控制面承担三项职责：统一接入与租户隔离（配对认证、票据校验、转发）；执行资源（进程、PTY、终端会话、多观察者、会话恢复和原生界面，由它内部选用的现成终端运行时提供，HCTL 不自己实现 PTY 持有、终端模拟、观察者转发或重放）；待交成果保管。能不能代为执行工具并直报，按它的能力声明。运行时选型、形态候选、待命的产品要求与验证边界见[交付文档](./delivery.md#本地-agency-参考实现)。控制面内的 Agency 端口适配代码把执行规格、权限和精确引用翻译成对自己租户的派工请求并记录实际交付结果；现场执行者仍按授权操作参与者管理的 worktree，负责成果保全、Git 事实和清理，以及回读 CI 状态、合并状态、引用这类外部机械事实（组件划分见[系统边界](./spec/system.md#组件)）。

Agency 对控制面只有一个公开面：Agency 端口——要人、派工、输入、停止、观测、票据校验。它内部的运行时 API、原生界面与终端连接怎么实现是门后的事；前端观察或接管终端经同一个 Agency，凭控制面签发的票据。Agency 能力按绑定声明。

可选执行加固里的「允许调用的工具能力」由 Agency 声明并负责兑现，怎样兑现是它的内部；本地参考实现的候选手段与逐 harness 的钩子调研见[交付文档](./delivery.md#本地-agency-参考实现)，本批不选定。

## Terminal 场景

Terminal 是 Participant 模块的操作场景。它用于观察、诊断和接管一次具体的派工，可以渲染结构化执行流或真实 PTY，不要求每次执行都有 shell。Workbench 经 Agency 连接派工，凭控制面签发的票据。

正常路径上用户不需要进入终端：状态、差异、证据和 Request（请求卡）先把事情说清楚（默认无界面，headless by default）。观察手段是一道阶梯——结构化执行流是默认视图，PTY 转录是二级诊断，终端接管是最后一级。如果日常了解进度要靠开终端，说明上层投影失职。

下表定义五个恢复等级；Agency 可以声明其中多项，每项按自己的证据要求由 Agency 负责成立或降级，控制面不核进程同一性。

| 恢复等级 | 含义 |
| --- | --- |
| exact attach | 连接仍存活的精确 PTY/进程 |
| native handoff | 交接同一个外部 Harness 会话 |
| structured inspect | 查看实时结构化事件与原始记录 |
| semantic resume | 以外部会话 ID 恢复上下文，可能创建新进程 |
| replay | 只读历史 |

semantic resume 不必依赖厂商保留的会话文件：自有观测留痕（转录与结构化事件）足够时可以重建等价的最小续跑输入；重建物只是投影，不改变任何权威记录。

Workbench 就位之前，观察与接管可以经公共命令入口取得为精确目标签发的短期票据，也可以在执行规格允许原生交互时使用 Agency 的原生界面；先后路径见[交付文档的实现阶段](./delivery.md#实现阶段)。两者都是 Terminal 客户端，恢复等级按 Agency 声明的能力和输入策略标注（见[Agency 与执行体](#agency-与执行体)）。

Execution Chat 是绑定一次精确执行的结构化观察与控制视图：它不是 Room，没有独立的会话身份；里面的输入和事件也不会自动进入 Room，只有显式的 Share to Room 动作经 Project 准入后才能发布。观察、输入、执行控制和安全输入是分开授权的四种权限，接管会原子撤销旧输入者。

| 角色 | 可以做什么 |
| --- | --- |
| 场景客户端：Workbench Terminal | xterm、Execution Chat/结构化检查、经 Agency 连接派工、能力说明；按绑定选择受租约或原生交互输入 |
| 场景客户端：CLI / 其他终端客户端 | 凭短期连接票据经 Agency 观察或接管某次派工 |
| 受控端口：Agency（默认为本地参考实现） | 报名册与条款，按冻结规格接受派工并对它负责；门后持有进程、PTY 与终端会话，harness 的接入方式（ACP、原生服务端、SDK、PTY 或钩子）是它的内部 |

## 模块交接

以下只列所有权方向；派发、结果准入与恢复由[连接约束](./spec/connections.md)统一定义。

- Project 与 Run 各传入一份冻结的执行规格（Execution Spec）；Participant 模块不重新解释上层范围。
- Participant 模块只返回结果提案、测试证据和运行时观测；变更集快照由 [Repo 模块](./repo.md)的 `hctl2-tool` 封存并回读，在上层准入提案的同一事务里成为获准版本；结果与证据在接收方确认保全前由 Agency 保管，不要求原进程或工作树一直存在。
- control 与 `hctl2-tool` 校验后才可形成 Run 的 Verdict（裁决）/Receipt（凭证）或 Task 的验收证据。
- 身份、人设、Skill 申报与执行：[约束附录](./spec/participant.md)；规划者名册与升格边界：[Project 模块约束](./spec/project.md)；施工者席位与选人：[Run 模块约束](./spec/run.md)；评审席位绑定选定的施工者记录、作者回避、独立性 known/unknown：[Run 模块约束](./spec/run.md)；每次执行规格冻结完整身份链并可回溯：[连接约束](./spec/connections.md)。

尚未进入约束的部分（人设编译、AIEOS 字段级导入、远程协议面、选人推荐的记录与排序等）留在专题过程稿，按“逐条裁决、不整篇升格”进入规范。
