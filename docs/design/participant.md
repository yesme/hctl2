# Participant 与 Terminal

> 状态：规范性（架构层）· 草案 v0.16.1<br>
> 日期：2026-09-02<br>
> 定位：本文回答“谁在干活、按什么方法、结果归于谁，以及这一次干活的进程跑在哪里、怎么观察和接管”。

> 本文是 Participant 模块的设计正文：它为什么存在、拥有什么、按什么规则运转。精确对象、状态机与写入约束见[约束附录](./spec/participant.md)；模块交接见[连接约束](./spec/connections.md)，共享机制见[系统边界](./spec/system.md)。

## 为什么存在

“机器上装了哪个 CLI”回答不了“这项工作该由谁、按什么方法做”。自动探索本地 Harness 只是解析链的最后一步——它知道这里有什么工具，不知道谁在工作、以什么人设出现、带着哪份方法论、是否有资格参与评审。把这些混成一团，就会出现三种熟悉的病：换个进程就像换了个人（结果无法归属）、评审席位形同虚设（同一个模型换个名字给自己投票）、以及 BYOA（bring your own agent）——手边正好有哪个工具就让哪个裸模型上，工作质量随手气波动。

另一头，进程、PTY（伪终端）、worktree（Git 工作树）和终端连接都是可替换的物理资源：它们可以丢失、重建和接管，但不能反过来定义 Project、Task 或 Run 的事实。执行结束了，不等于上层成功了。

Participant 模块把这两头接成一件事：稳定的是参与者身份，变化的是它被实现的方式。新进程、新会话、备用尝试都不产生新的参与者；换成另一个参与者也不能靠复用同一套执行配置伪装成同一个人。模块的职责，是把上层的一次授权变成可归属、可观察、可隔离、可恢复的物理执行，并诚实上报发生了什么。

**人不是 Participant。** 人不干活，人拍板：目标由人定，契约由人采纳，完成由有权的人或确定性归约判定。人在约束层写作 human actor，出现在命令、名册和裁决里，不进入本模块的七件事分层。本模块只管数字参与者。

## 模块拥有什么

Participant 模块保存“谁在干活、怎么实现、这一次跑在哪”的事实。它拥有：参与者的稳定身份与配置版本；人设；Skill（技能包）的申报值与可核验性；可复用的执行者配置（哪个 Harness、什么模型、什么权限）；每台主机上的 Harness 目录（装了什么、实际能干什么）；获准的写入边界 ChangeSet（变更集）及其不可变快照；物理运行时与终端通道；以及提交给上层校验的结果提案与证据。它不决定 Project 目标、Task 完成、Run 的评审结果，也不创建下一条协作边。角色绑定归 Project，评审席位归 Run，本模块只是被它们引用。

## 七件事分层

一个数字参与者由七件生命周期不同的事组成，不能压成一份大配置：

| 层 | 回答的问题 | 明确不回答 |
| --- | --- | --- |
| 参与者身份 | 谁参与、结果归于谁 | 怎样运行、拥有什么权限 |
| 项目角色 | 在这个 Project 承担什么职责 | 全局身份、物理能力 |
| 人设（persona） | 以什么风格表达与协作 | 能否完成、能访问什么 |
| 模型与特殊训练 | 行为能力来自哪个模型谱系 | 参与者身份和权限 |
| Skill（技能包） | 本次装载哪份可版本化的方法 | 自动授权工具、自动获得票权 |
| 执行者配置 | 模型、模式、环境、候选端口怎样组合 | 此刻哪台机器可运行 |
| 一次物理执行 | 这一次实际落在哪个端口、哪个现场 | 上层角色、验收或完成 |

上三层归控制面账本，由用户建立和绑定；下四层的实物由 Agency 供给（见[Agency 与执行体](#agency-与执行体)），账本只冻结对它们的精确引用。调用前的 Trigger Preview 把这条链完整摊开：实际的参与者、人设、模型、技能包、执行配置、权限、预算和降级，一次看清再提交；冻结之后整条身份链不随后续变化漂移，结果沿链回溯到精确版本。

## 关键规则

- Participant 是稳定身份，命令权限、评审票和委派边界由对应模块另行授权，见[Project 约束](./spec/project.md)与[Run 约束](./spec/run.md)。
- 人设、Skill 与能力声明分别表达风格、方法和候选能力；实际权限与本次装载以[约束附录](./spec/participant.md)和[连接约束](./spec/connections.md)冻结的执行规格为准。
- Project 角色绑定职责，权限与预算另行冻结；换人通过新绑定生效，活动执行保持原版本。
- Skill 依次区分声明、实际可用与本次已装载。可用与已装载由 Agency 申报，control 记录申报值并标注能否核验：本地参考实现的申报值工具箱能回读，标 known；远程参与者只能给声明，标 unknown。只有冻结进执行规格的版本对本次执行生效。
- 评审独立性按[Run 约束](./spec/run.md#request重试与-gate)记录可认证性：能机械认证的标 known，不能的标 unknown；不用逻辑身份代替物理证明。
- worktree 是变更集的可替换载体，可以丢弃重建，不永久属于任何 Project、Task、Room 或参与者。
- 一个变更集同一时刻只有一个写入者；换人、接管或取消，都要先让旧写入者失权。
- 恢复时证明不了旧写入者已经安静退场，就把旧现场原样隔离、换一个新工作树重来；来历不明的修改绝不悄悄混进新的产出。
- 清理任何资源之前，必须确认没有唯一副本会随之消失；宁可留下现场和恢复指引，也不删孤本。
- Harness 在自己的工作树里可以正常用 Git：看分支、看日志、fetch、和目标分支比对、在自己的变更集分支上提交。但模型说“我已经合并了”不可信：合入目标分支只走持久意图、执行、回读、唯一凭证四步，由工具箱校验 Git 事实；绕过这四步直接改目标分支只算带外改动，下次合入前会被当作漂移拦下。
- 执行体之间只有结晶过的东西能过去：变更集分支上的提交、发布的 Memo、提案里引用的证据。终端 trace 是观测，不自动进任何人的上下文；没提交的对继任者不存在（见[横切正文](./context.md)）。
- 观测（进程、屏幕、心跳、钩子）用于触发关注；领域结果只经提案与上层准入形成。
- 执行体进程干净退出不等于交付了结果。每个 harness 适配器都为自己的端口声明终局结果清单，正常退出但缺少清单要求的事件按协议错误处理、不默认成功；我方主动取消导致的退出按取消归因，不冒充执行失败。清单的精确要求见[约束附录](./spec/participant.md#运行时与观测)。
- 观测流要么完整、要么显式截断收尾。上报通道失败后，宁可把这次执行标记为观测截断，也不交付有缺口的事件流冒充完整历史；harness 内部再派生的子执行体保留派生谱系，不摊平进主执行流。
- 执行体只拿到本次执行需要的窄能力。它可以建议完成、建议下一位协作者；建议走提案通道由上层校验，不是命令。
- Harness 只经提案交回结果，集成凭据由工具箱或 adapter 代用，每个 ChangeSet 使用独立工作树与写租约；Harness 治理的三条底线和可选加固由[约束附录](./spec/participant.md#写入约束)定义。
- Project、Task、Room、Run、Participant、Seat 都没有“自己的终端”；终端只属于一次具体执行。
- 一次执行被恢复或接管后进入新代次；旧代次的连接、输入和结果一律失效，只留审计。
- 客户端退出不停止执行；断流恢复按可证明的运行时身份标注恢复等级。
- Skill 提供指导和上下文，不获得命令、评审或写入权。

## 专业化 Participant：告别 BYOA

评审是第一个必须专业化的岗位。今天的评审靠模型的自发判断，没有方法论——这正是 BYOA 的局限。解法是在确定参与者的阶段引入**专业化 Participant：模型 + 专用方法论 Skill**。

- **方法论是 Skill，不是临时提示习惯。** 评审方法论（审查骨架、对抗核验、约束漂移检查这类审计方法）沉淀为带版本的技能包；评审参与者 = 稳定身份 + 该技能包（已装载态）+ 合适的模型与执行配置。
- **由此换来 BYOA 给不了的三件事**：可复现（凭证链会记录评审所用的方法论版本）、可升级（方法论出新版，所有项目同步受益）、可审计（两次评审结论不同时，能回答是方法变了还是模型变了）。这三件事对本地参考实现完全成立；对远程参与者，方法论版本只是对方的一句申报，账本标 unknown，第三件只能问到申报为止。
- **与评审独立性正交叠加**：Gate 的评审席位绑定这类参与者，得到“有方法论且独立”的评审；专业化不改变票权规则，结论仍只是裁决输入。
- **Skill 给方法，账本给门。** 方法论 Skill 决定怎么问、怎么切、怎么查，但它拿不到命令、票权和写入权：必须由人回答的问题不能被模型代答，完成不能自述，规划空间不能给自己签发执行权。这些门放在 prompt 里必然失守，所以只在账本里。
- **自食其力**：HCTL2 自己的设计评审应最早切换到这个模式，替代各 harness 裸模型的自发评审。
- **商业化延长线**：将来受雇的外部数字员工同样落在这套结构里——对方的派出机构就是一个 Agency，它派来的就是执行体；派出不转移参与者身份，“谁在工作”仍由账本的 Participant 层回答，派出方只供给下四层。为什么最先值得雇的是评审者、以及市场机制为何暂不设计，见[愿景](./vision.md#要解决什么不解决什么)。

## Agency 与执行体

Terminal 场景有两个对话方，这是其他三个场景没有的：另外三个模块各有一个专职系统，它既是名册也是宿主；Participant 模块的专职系统分成供给方与产物两半。

- **Agency（派出方）** 是参与者的供给方：维护可派出的名册与条款，按冻结的执行规格交付一个执行体端点。挑人发生在 Trigger Preview 和每次开 Room、批施工图的时候，是一回“要人 → 报人”的对话：control 说需要一个带某方法论、某权限的评审者，Agency 回答名册里哪些满足、条款如何。选择由 control 按策略做，Agency 不替它选。Agency 不制造参与者身份，身份由用户在账本里建；一般也不制造端点，远程数字员工是既存的一方，你是去约它，不是去造它。本地实现启动一个新进程，那是本地的机制，不是架构。
- **执行体（worker）** 是 Agency 供给的一次具体运行：Harness 进程、装载的 Skill、PTY 与 TUI。派工与观测直接发给执行体端点，Agency 不在派工路径上——这与“Agency 永不包含治理权威”是同一件事。
- Agency 供给七件事分层的下四层：模型、Skill、执行者配置、一次物理执行。身份、角色、人设仍由 control 账本拥有。
- Skill 由 Agency 申报（名册里写着这个参与者带哪些 Skill、什么指纹），由执行体装载，由工具箱核验，由账本记 known 或 unknown。

**发布包自带一份本地 Agency 参考实现。** 装了 HCTL 就有参与者可派，不出现“架构上很美、本机却没人可用”的情况。它在 Herdr 外面只多一层薄壳：技能目录、可用性申报，以及与 control 对话的适配器。它的进程、PTY、终端会话、多观察者、会话恢复和原生 TUI 全部采用 **Herdr**；HCTL 不自己实现 PTY 持有、终端模拟、观察者转发或重放。控制面内的 Herdr 适配代码把执行规格、权限和精确身份翻译成 Herdr API 请求并记录实际交付结果；现场执行者仍负责 worktree 保全、Git 事实和现场清理（组件划分见[系统边界](./spec/system.md#组件)）。

Herdr 提供三类接口：

| 接口 | 谁使用 | 规则 |
| --- | --- | --- |
| Herdr API | 控制面的 Herdr 适配代码 | 启动、获准输入、打断和停止都经 HCTL 验证后调用 Herdr；HCTL 不重新实现终端服务 |
| 终端连接 | Workbench / CLI 凭票据连接精确终端目标（票据字段见[约束附录](./spec/participant.md#终端通道连接与租约)） | HCTL 验证票据与当前代次；Herdr 负责观察流、终端状态和输入执行 |
| Herdr TUI | 用户直接观察或操作 Herdr | 它是正常的 Terminal 客户端；输入会推动精确运行时，但不是 HCTL 治理命令或 Result Proposal，恢复等级按下述限制处理 |

Agency 能力按绑定声明；当前 Herdr 缺项与验证边界见[交付文档 P0 第 2 项](./delivery.md#开工前限时验证)。Workbench 直连 Herdr 的传输适配器使用同一份能力声明。

## Terminal 场景

Terminal 是 Participant 模块的操作场景，也是执行体暴露给 Workbench 的 TUI 接口，记作 `participant.tui`。它用于观察、诊断和接管一次具体的执行体，可以渲染结构化执行流或真实 PTY，不要求每次执行都有 shell。Workbench 连接的是执行体，不是 Agency。

正常路径上用户不需要进入终端：状态、差异、证据和 Request（请求卡）先把事情说清楚（默认无界面，headless by default）。观察手段是一道阶梯——结构化执行流是默认视图，PTY 转录是二级诊断，终端接管是最后一级。如果日常了解进度要靠开终端，说明上层投影失职。

下表定义五个恢复等级；一次绑定可以声明其中多项，但每项都按自己的证据要求成立或降级。

| 恢复等级 | 含义 |
| --- | --- |
| exact attach | 连接仍存活的精确 PTY/进程 |
| native handoff | 交接同一个外部 Harness 会话 |
| structured inspect | 查看实时结构化事件与原始记录 |
| semantic resume | 以外部会话 ID 恢复上下文，可能创建新进程 |
| replay | 只读历史 |

semantic resume 不必依赖厂商保留的会话文件：自有观测留痕（转录与结构化事件）足够时可以重建等价的最小续跑输入；重建物只是投影，不改变任何权威记录。

Workbench 就位之前，观察与接管可以经公共命令入口取得为精确目标签发的短期票据，也可以在执行规格允许原生交互时使用 Agency 的原生界面；先后路径见[交付文档的实现阶段](./delivery.md#实现阶段)。两者都是 Terminal 客户端，恢复等级按绑定声明的能力和输入策略标注（见[Agency 与执行体](#agency-与执行体)）。

Execution Chat 是绑定一次精确执行的结构化观察与控制视图：它不是 Room，没有独立的会话身份；里面的输入和事件也不会自动进入 Room，只有显式的 Share to Room 动作经 Project 准入后才能发布。观察、输入、执行控制和安全输入是分开授权的四种权限，接管会原子撤销旧输入者。

| 角色 | 可以做什么 |
| --- | --- |
| 场景客户端：Workbench Terminal | xterm、Execution Chat/结构化检查、精确连接、能力说明；按绑定选择受租约或原生交互输入 |
| 场景客户端：CLI / 其他终端客户端 | 凭短期连接票据观察或接管精确目标 |
| 受控端口：harness 适配器 | ACP、原生服务端、SDK、PTY 或钩子能力 |
| 受控端口：Agency（默认为本地参考实现，运行时 Herdr） | 报名册与条款，按冻结规格交付执行体端点；执行体持有进程、PTY 和终端会话 |

## 原生会话导入

原生会话导入（native session import）是可选能力：由用户显式发起导入，保留外部会话 ID 与路径来源，只把用户挑选的摘要或引用带入 Context，解析器使用固定版本的样本测试。它不把外部历史复制成 Room 事实，也不是当前范围的交付前提。

## 模块交接

以下只列所有权方向；派发、结果准入与恢复由[连接约束](./spec/connections.md)统一定义。

- Project 与 Run 各传入一份冻结的执行规格（Execution Spec）；Participant 模块不重新解释上层范围。
- Participant 模块只返回结果提案、变更集快照、测试/SCM 证据和运行时观测。
- control 与工具箱校验后才可形成 Run 的 Verdict/Receipt 或 Task 的验收证据。
- 身份、人设、Skill 申报与执行：[约束附录](./spec/participant.md)；角色绑定与升格边界：[Project 模块约束](./spec/project.md)；评审席位绑定精确参与者版本、作者回避、独立性 known/unknown：[Run 模块约束](./spec/run.md)；每次执行规格冻结完整身份链并可回溯：[连接约束](./spec/connections.md)。

尚未进入约束的部分（人设编译、AIEOS 字段级导入、远程协议面等）留在专题过程稿，按“逐条裁决、不整篇升格”进入规范。
