# 三面架构

> 状态：规范性（架构层）· 草案 v0.18.7<br>
> 日期：2026-09-10<br>
> 定位：本文回答职责与单元两个正交视角，以及数据视角：三个面是职责（治理元数据 / 内容 / 呈现），「单元与连接」是什么能独立装、怎么连；每个场景的数据分哪三类、住在哪里、不可用或丢失时怎么办。模块的语义分责见[设计地图](./README.md)；对象、状态机与三类数据的权威定义在[约束层](./spec/README.md)；具体实现选型与验证在[交付文档](./delivery.md)。

## 三个面

Project、Task、Run、Participant（参与者）与 Repo（仓库）五个领域模块是**语义分责**；职责视角上，系统由三个面组成。两者正交：每个模块的 metadata（治理元数据）都在控制面，content（场景内容）都在执行面的对应系统，场景都由展示面呈现。

| 面 | 组成 | 拥有什么 |
| --- | --- | --- |
| 展示面 | 前端（Workbench 与 CLI 的统称）与第三方场景客户端 | 不因客户端身份拥有事实或特权；按动作目标查询/提交 HCTL 命令，读写 provider content，或经 Agency 观察与输入某次派工 |
| 控制面 | HCTL 自己的命令服务、控制面存储与现场执行者（组件划分见[系统边界](./spec/system.md#组件)；组成按职责归类，也是缺省的同机打包，不是安装边界——现场执行者按职责归在这一行，它的进程在哪台机器、由谁拉起见[单元与连接](#单元与连接)） | 全部 metadata：身份、绑定、授权、判决 |
| 执行面 | 五个场景的 content 系统与物理执行；Participant / Terminal 默认由发布包自带的本地 Agency 参考实现承载，Repo / Change（变更）的代码协作平台按仓库绑定：来自外部平台的仓库用外部平台，只在本地的仓库用发布包自带的本地平台，运行时选型见交付文档 | 全部 content 与机械状态；接收 provider 自有内容/运行时动作，也执行控制面按顺序发出的副作用 |

控制面归**用户级**：一个人可以多机连接同一个控制面，也可以运行多个控制面，两种都是部署形态；不同控制面里的用户身份与授权分别确认，不自动归并。仓库克隆只是参与者机器上的物理现场。单机部署时三个面同装一台机器——这是本地优先（local-first）的默认部署形态，不改变客户端—服务端结构。

Workbench 把五类 provider 客户端、跨模块导航、联合投影和 HCTL 公共命令入口组合成一个产品桌面，但没有额外权限。消息、卡片和终端输入按各模块对供应端动作的规则处理，治理命令与 CLI 共用命令服务；动作分类与接纳规则见[系统边界](./spec/system.md#客户端动作与-provider-事件)。Workbench 关闭后，领域服务和执行照常继续。

产品从选择仓库、创建或打开 Project 开始；同一控制面已有多个使用该 Repo 的 Project 时，由人选定，不按仓库地址把它们合成一个。打开仓库会连接本次选定或缺省的控制面——本机连接可在必要时拉起本机控制面，从远程控制面打开时选择它登记的仓库；仓库在哪不决定选哪个控制面。终端票据也可以把观察者带到另一个执行现场，因此一套控制面可以服务多个客户端和执行现场；一个前端也可以连多个控制面，联合视图里每项事实与每个动作都保留它来自哪个控制面。当前只交付本机连接；远程连接的认证与传输是[安全策略面](./spec/system.md#安全策略面)「端点与连接」策略点的后续取值。

执行面的各系统是独立进程或服务器，不内嵌进控制面。“轻量”指轻量的实现选择与低资源占用，不是把服务塞进控制面进程；单机部署时随包的内容系统由本机控制面托管、一键启停，那是缺省的安装位置与部署形态，不是信任范围——随包的系统同样可以被别的控制面绑定，也不是只能由本机控制面拉起。哪些东西能独立装、互相怎么连，见[单元与连接](#单元与连接)。

## 单元与连接

三个面按职责分：谁拥有治理元数据、谁拥有内容、谁呈现。这一节回答另一个正交的问题：什么东西能独立安装、启动、停止，互相怎么连。

> HCTL2 让多个独立的控制面复用 Agency 与各类内容服务开展协作；每个控制面负责自己的授权和判定，供应端负责它承载的资源与事实，前端组合这些视图和入口。仓库是共同工作的对象：代码版本由 Git 识别，平台拥有它所承载目标的更新与评审记录。

**四类单元和一个底座。** 单元的判据是两条：能独立安装、启动、停止，与别的单元只靠连接来往；连接的另一单元不可用，不自动使本单元停机。满足判据的单元承担两条义务：持久保管自己承诺保存的事实；需要凭据的动作由持有相应凭据和权限的一方完成。按部署约定接受显式的一键托管启停，是其中一种部署方式，不改变判据。

- **控制面**：拥有什么按上文三个面与下文归属矩阵，这里不重复；生命周期归用户，不随任何 Agency 或内容系统起落；向任何 Agency 要人，向任何平台绑仓库；一个仓库可被多个控制面使用，同一控制面也可为它开多个独立 Project。
- **Agency（派出方）**：一台机器上装了哪些 harness、能派出什么工种，由这台机器的主人决定；是控制面与参与者之间唯一的通路，为每个配对的控制面提供一个隔离租户，门后的进程、会话、主机与换人不泄露到控制面；生命周期与任何控制面无关，一台只跑 Agency 的机器是正常形态；同时给多个控制面供人；模型凭据是工种打包的一部分；持有还没被控制面收走的结果与证据，所以有自己的持久存储。
- **前端**：Workbench 与 CLI，不拥有事实，可以连一个或多个控制面，本机或远程；联合视图里每项事实和每个动作都保留它来自哪个控制面，前端的投影不构成新的权威；前端不绕过 HCTL 准入产生授权或获准结果，已获准的终端连接经 Agency、按既有票据与输入规则进行。
- **内容系统**：聊天服务器、任务后端、代码协作平台、工作流引擎，各自独立，多个控制面可以绑同一个；随包只是缺省的安装位置，不是信任范围，也不是只能由本机控制面拉起。
- **仓库不是单元，是底座**：Git 与平台。平台同时是一种内容系统，不因此多算一个单元；显式不挂平台的受限路径下，底座只有 Git。

`hctl2-tool` 不是独立单元，不以与控制面同机或由控制面起进程为前提；参与者可在现场调用它，控制面本机也可以运行它，那时它就是持凭据的那一方。部署位置与报告通道归约束层。

**部署对等不是权威对等。** 每个控制面负责自己的 HCTL 授权与判定，独立决定哪些结果在本控制面获准；Agency 对资源供给和执行事实负责，不替控制面作这些决定；平台按自己的规则决定它承载的目标能否更新。机器是几种单元的宿主，不是单元；一个 Agency 不必永远只占一台机器；Project 的聊天室在治理上归控制面，不等于聊天服务器部署在那台机器上——归属是权威关系，放置另说，见下文三种关系。

**三种关系。** 放置说明字节在哪里，权威说明谁能决定它是否生效，交付说明获准材料怎样到达需要它的一方。

- **放置**：会话、检出、对象库、还没推出去的提交，都在参与者所在的机器上，平台不因此拥有全部代码字节；控制面负责自己的治理记录与治理正文，参与者负责工作环境与工作副本。
- **权威**：每个控制面对自己的授权与判定负责；平台拥有它承载的目标的更新与评审记录；聊天、卡、评审线程各归自己的内容系统。一个控制面的批准不是另一个控制面的批准；一个平台上的合并结果谁都能读；另一个控制面能读到一份正文，不等于它采纳了那份契约、批准或当前指针——字节可见不转移治理权威。
- **交付**：开工所需的材料和返回的结果、证据，都要有可达且可核验的交付路径；共同平台是一种路径，持凭据单元的中转是另一种；已承诺保管的内容不能以"已有指针"冒充交付完成；显式不挂平台时只有 Git 的受限路径，共同平台不是所有交付的前置条件。

**单元之间的总规则。** 各类事实按职责确定权威；跨单元的操作不依赖一次原子提交，靠请求、确认与恢复对账衔接。平台仲裁合入、联系不上与丢失分开、结果由执行侧保管到接收方确认保全、任务源按自己的能力处理并发写，都是它的特例；精确规则按模块落在约束层。别人的写入是事实，不是本控制面的命令，也不因出自别人就违规；它可触发重核、验收或请求，能否作验收证据由本控制面的契约事先声明，批准与完成仍自己判，控制面之间不加锁。

## 场景与系统

场景是用户视角的名字，系统是 content 承载者的角色名；每个场景由一个专职系统承载它的 content。角色名是产品词，具体采用哪个实现由[交付文档](./delivery.md)的选型判据与限时验证决定。

| 场景 | 系统角色 | 系统拥有的 content | 备注 |
| --- | --- | --- | --- |
| Room（聊天室） | chat server（聊天服务器） | 聊天记录、调用过程与结果卡 | 采用 Matrix 协议；Matrix 生态客户端可直接访问；HCTL 房间不开端到端加密，准入与降级见[Project 约束](./spec/project.md#room-与消息) |
| Kanban（看板） | task backend（任务后端） | 任务卡、流转、排序、评论 | 注册仓库（Repo）或首次启用看板时由人显式绑零到多个任务源——平台自带的 issues（缺省建议）、本地任务服务器，或 Linear 这类远端平台；Project 可选其中多个源，Kanbans 按源分别提供入口；合并视图可选，不形成新权威 |
| Workflow（施工图） | workflow engine（工作流引擎） | 令牌位置、重试、定时器、机械执行历史 | 引擎只拥有机械状态，不拥有语义 |
| Terminal | Agency（派出方） | 会话转录、PTY 流 | control 的对手方只有 Agency：向它要人、向自己的租户派工，输入、观测与结果都经它转接，门后的参与者进程、会话与主机是它的内部。没有接入外部 Agency 时，默认使用发布包自带的本地参考实现；HCTL 不提供另一套第一方终端运行服务 |
| Change（变更） | SCM platform（代码协作平台） | 评审线程、检查结果、合并状态 | 注册仓库时按 Repo 绑定：来自外部平台的仓库绑它来的托管服务或自建服务器，只在本地的仓库绑发布包自带的本地平台，几种平台同等对待，差别写在绑定的能力声明里；显式不挂平台的受限路径没有它，讨论在 Topic Room、检查是本地事实。`hctl2-tool` 是每个仓库都有的本地执行者，平台适配器只管平台上才有的事；缺省选型见[交付文档](./delivery.md#选型判据) |

## 避免供应商锁定

五个场景的外部系统各有一个经调研选定的实现（是什么、为什么选它见[交付文档的选型判据](./delivery.md#选型判据)）：我们不重新发明轮子，但选型不是 HCTL 的产品承诺，可以替换。HCTL 不再增加一个通吃五个模块的独立 shim（垫片服务）；五个模块的语义不同，把它们压进同一套通用接口只会形成新的私有协议。稳定边界放在每个模块自己的受控端口，具体产品由薄适配代码接入：

| 场景 | 稳定边界 | 后续替换方式 |
| --- | --- | --- |
| Room | Matrix 协议 + HCTL 的聊天端口绑定与 Room 到服务器房间的绑定 | 可换任何 Matrix homeserver；飞书、Slack、Discord 等非 Matrix 平台由 homeserver/bridge 生态接入，HCTL 不逐个平台写聊天适配器 |
| Kanban | HCTL task backend 端口 | GitHub、Linear 等各写一个 task backend 适配器，共用 Task 身份、字段权威、Snapshot 与同一套命令准入 |
| Workflow | HCTL 的施工图版本（Workflow Revision）中间表示 + workflow engine 编译/回读端口 | 为新引擎增加编译器和回读适配器；Run、Gate、Obligation 与完成判定不随引擎改变 |
| Terminal | HCTL Agency 端口 | 远程 Agency 与本地参考实现走同一个端口；执行授权、身份、租约、证据与恢复等级不随 Agency 改变 |
| Change | HCTL 平台端口 + `hctl2-tool` 读回的本地 Git 事实 | 为新平台写一个平台适配器，能力差别写在绑定的能力声明里；仓库身份、变更集、集成凭证与授权形态不随平台改变。可替换的接口不等于可迁移的历史：评审线程随平台，普通克隆不带它 |

Workbench 是五个场景的稳定组合界面，但只使用公开的命令与查询入口：HCTL 命令与 CLI 同路，场景内容和运行时动作与对应原生客户端同路。第三方私有对象模型不进入模块约束。Terminal 的字节流和绘制性能敏感，Workbench 经 Agency 的公开通道连接某次派工的终端，票据由控制面签发、Agency 校验；输入租约、记录与恢复等级按 Agency 声明的能力如实标注。

“可替换”分三档承诺，不能混为一谈：新工作可以在通过契约测试后选择另一供应端；活动执行继续使用冻结的绑定，不热切换；迁移既有场景内容必须另行预览和校验，能否完成取决于两端的导入导出能力。HCTL 自己的治理元数据、不可变引用和 Git 结晶不依赖任何一家选型，但这不等于所有第三方场景内容都能无损搬家。

## 5×3 归属矩阵

行是场景，列是[三类数据](./spec/README.md#三类数据)；每格回答“什么数据、存在哪”。

| 场景 | metadata（控制面存储） | content（执行面系统） | artifact（结晶） |
| --- | --- | --- | --- |
| Room | Room 身份、归属 Project、规划者名册、身份映射配置、消息升格记录 | 聊天记录、调用过程与结果卡（chat server） | 决议、Memo（备忘）、施工图 |
| Kanban | Task 身份映射、字段权威绑定、冻结契约及其摘要、完成凭证 | 任务卡、流转、排序、评论（每张卡所在的任务源） | 冻结的任务契约版本 |
| Workflow | Run 授权、引擎绑定、代次、Gate 规则、裁决 | 令牌位置、重试、定时器、机械执行历史（workflow engine） | 凭证链 |
| Terminal | 执行授权与执行规格、派工引用、输入租约、代次、观测记录 | 会话转录、PTY 流（Agency 门后的参与者） | 会话中产生的代码变更（变更集快照） |
| Change | 仓库登记与平台绑定、变更集身份与写租约、集成意图与凭证、变更与平台的映射、平台账号映射 | 评审线程、检查结果、合并状态（外部平台或自带的本地平台；显式不挂平台时没有） | 合入目标的提交，以及集成凭证的审计副本 |

矩阵里的 artifact 是一种**解释性结晶规律**：重要结果通常会形成可审阅、可分发的不可变产物；它不是把 metadata 或 content 逐字节变换成 Git 文件的存储定律。结晶从哪个场景产生，就归哪个场景。例如施工图从 Room 的塑形讨论中产生，因此归 Room，而它的批准与版本对象归 Run；同理，代码变更从 Terminal 的会话中产生，归 Terminal，而变更集这个对象及其写入者归 Repo 模块。结晶归属与对象归属是两回事。没有产物的场景不必为了形式对称而补造一种结晶。

代码与变更快照保存在被治理仓库；契约、施工图、Memo 等治理正文及审计副本由控制面保管，工件按登记用途引用相应来源。身份、准入、当前指针与裁决仍由治理记录决定，字节存在不等于被接纳；审计副本不默认随代码克隆分发，见[系统边界](./spec/system.md#git-的双重角色)。

统一律与三条法（能承载不等于能裁决；冻结摘要是防火墙；命令走 HCTL、记录落平台）见[约束层总则](./spec/README.md#三类数据)，此处不重复。

Project 关联一个 Repo，同一 Repo 可以对应多个 Project；各 Project 有自己的主 Room、Topic Rooms、任务源入口与 Runs。Rooms、Tasks、Runs 在 Project 内相互引用，不因引用改变归属，也不互相包含。Room 的消息留在原 Room，Task 的卡留在原任务源；源内子任务与清单归后端原生能力。每个 Room 与每次 Run 各自选人；容器不归属某个 clone 或客户端。

## 模块交接

模块之间的每次交接都交付一个**冻结的、带摘要的不可变对象**；下表是[连接约束](./spec/connections.md)总表的产品语言投影，精确字段以约束为准。

| 交接 | 交付物 | 一句话 |
| --- | --- | --- |
| Project → Task | 冻结的任务契约版本（Task Revision）+ 来源回链 | 讨论经采纳命令升格为承诺 |
| Task / Project → Run | 冻结契约 + 施工图，由施工清单（Run Manifest）冻结引用 | 承诺进入治理；批准施工图与开工是两条治理记录，可在一次预览里提交 |
| Run / Project → Participant | 执行规格（Execution Spec）→ 对 Agency 的派工 | 治理经 Agency 派工；参与者照单干活，不做语义判断 |
| 执行回程 | 结果提案 → 裁决与凭证 | 执行只能提议；归属模块校验身份、代次、权限与证据后才算数 |
| Project / Run → Repo | 获准的结果 + `hctl2-tool` 封存回读的变更集快照 → 版本准入 | 这里保存的是代码快照，治理正文由控制面自己保存；算数仍由控制面决定：先封存回读，再在同一控制面事务里准入提案与版本；封存本身在事务之外，封存期间被取消的调用不产生获准版本 |
| 人 / Run → Repo | 集成意图 → 集成凭证 | 合入只走持久意图、执行、回读、唯一凭证四步；目标头给不了保证时，放行是人事前显式选择的另一种授权形态 |
| Repo → Task | 集成凭证，或契约事先接受的精确平台集成证据 | Repo 回读核验，Task 按自己的契约判完成；平台已合入不自动完成任务 |

## 数据丢了怎么办

两种情形分开立约：**不可用**（进程或服务暂时失联）保住已接纳事实并标明新鲜度，**永久丢失**（数据没了）按三类数据重建。精确降级与恢复见[系统边界](./spec/system.md)和[连接约束](./spec/connections.md#失败与恢复)。

**总则：任何后端不响应时，**不依赖它当前事实的操作照常，依赖的类型化拒绝；尚未确认结果的已发出动作记结果未知，已确认的成功不因断线改成未知，不冒充成功。恢复分三层：后端在自己范围内自愈，对控制面无感；控制面按冻结的截止、取消与前置机械处理；换供应端要人来定，涉及成本与授权。

**不可用——保住已接纳事实，不伪造新鲜度：**

- 聊天服务宕机不抹掉已经接纳的治理事实。不依赖新消息、来源链或新鲜上下文的施工可以继续；要用到它们的预览与命令安全暂停。
- 任务后端失联时，看板显示待同步，排队中的操作不显示假成功。必须先核对后端当前状态才能生效的命令（采纳、移动、完成）拒绝执行，而不是按缓存猜。
- 工作流引擎失联时，已冻结的本地事实照旧存在。完成与评审都由控制面判，引擎只报告执行走到了哪一步；引擎停报进度，后果只是绑定等待对账——不因此创建新义务，也不拦已有义务的判决。
- Agency 按阶梯处理：它在冻结的执行规格内自愈——重启会话、改派备份、换主机——控制面无感；规格内干不了就报无法履约，控制面按所报故障与冻结规则处理；Agency 联系不上时，派工只记联系不上，依赖新鲜事实的派工、输入或结果准入按冻结的截止与取消条件处理，不冒充成功，仍在运行的参与者按已接受的范围、截止与取消条件行事，结果由 Agency 保管到接收方确认保全；Agency 挂了由人指定别的 Agency。失联本身不证明执行已经丢失。
- 代码协作平台失联时，本地物化和封存照常，面向本地目标的集成只对显式不挂平台的仓库照常；发布评审、读评审状态和远端合入拒绝，已经发出去、不知道成没成的远端意图保持结果未知，不改道、不签凭证。

后端离线时哪些治理命令还能用？逐条命令看它要不要读后端的新鲜事实：不需要的照常执行，需要的类型化拒绝并说明原因。受影响的入口显示待处理、需要关注或安全暂停，不绕过命令服务。每类事实的精确降级与重建规则见[连接约束的失败与恢复](./spec/connections.md#失败与恢复)。

**永久丢失——按三类数据分别回答：**

- **metadata**：控制面存储是唯一不可再生的权威，必须有备份；备份包括治理记录和它承诺可取的治理正文，材料副本能恢复字节，不能倒推出丢失的授权与判决。
- **content**：丢失不会抹掉已经接纳的治理事实——已保全的决议、契约与审计副本留在治理材料中，代码留在对应 Git 副本中，有桥接来源的部分可以重放，丢掉的是尚未结晶的记忆；评审线程随平台丢失，普通克隆不带它，凭证不能凭 Git 提交重建；需要核对 provider 当前事实或重建来源链的命令仍然拒绝执行，旧结晶不冒充新鲜读数。
- **artifact**：只有保管了对应精确内容的副本才是它的备份。代码克隆不保证带治理材料或尚未交付的成果，材料镜像也不代替完整控制面备份。
- 物理观测（进程、心跳、屏幕）本就可丢弃重建，不入此列。
