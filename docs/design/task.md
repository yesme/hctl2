# Task 与 Kanban

> 本文是 Task 模块的设计正文：它为什么存在、拥有什么、按什么规则运转。精确的对象、状态机与写入合同见[合同附录](./spec/task.md)；模块交接见[连接合同](./spec/connections.md)，共享机制见[系统边界](./spec/system.md)。

## 为什么存在

“Harness（编码代理工具）跑完一轮”“进程退出”“代码提交”“评审通过”“CI 绿了”“外部 Issue 关了”和“Task 验收完成”是七件不同的事。Task 模块的意义，是把“已承诺交付什么、验收标准是什么、现在到哪一步”从聊天、执行和外部系统中独立出来，让完成成为一个可核验的事实，而不是一种感觉。

Kanban（看板）是它的操作场景。卡片的职责是把复杂的运行时细节压缩成可以直接行动的信息：一眼看到承诺内容、谁在做、卡在哪里、证据齐不齐、下一步该点什么。

## 模块拥有什么

Task 是 Project 中一项可排序、可指派、可阻塞、可验收的长期承诺。它不等于自由讨论、外部 Issue、工作流节点、worktree（Git 工作树）或一次 Harness 作业。

Task 模块拥有的是治理事实：承诺身份与它冻结的验收契约（Task Revision，下称“契约版本”）；到任务后端与关联来源的身份映射、逐字段写入权与只追加的观测快照；以及每一次完成的可核验证明。任务卡、流转、排序、评论这些场景内容（content）住在为仓库选定的任务后端——本地任务服务器，或 GitHub/Linear 这类远端平台；冻结契约与施工图作为结晶进 Git。

Task 是承诺尺度，不是工作项尺度。看板上的卡可以随后端自由增删拆合（子任务、清单都是 content），每张卡都有稳定的 Task 身份映射，但只有值得冻结验收契约的卡才升格为治理意义上的承诺——契约在首次绑定 Run、首次提交完成命令或显式升格时才创建。比承诺小的事直接是卡片或走无 Run 轻量路径；比承诺大的事是 Project 或多个 Task。

## 关键规则

- 生命周期只有开放、完成、取消三个状态。看板上的 Backlog、Ready、In Progress、Review 只是本地阶段；泳道由本地阶段、生命周期与外部来源投影共同派生；阻塞与需要关注是正交的健康标注，不决定泳道，也不是生命周期。
- 契约变化产生新的契约版本，不原地改写；活动 Run 引用的契约版本永不漂移，改约必须先结束或替代该 Run。历史版本、Run 和凭证永不改写或物理删除。
- 外部 Done/已关闭/Reopen/Deleted 只是来源事实：先成为快照，会改契约的内容等用户明确采纳后才生效；它们不自动完成、重开或取消 Task，也不停止 Run。外部删除只留墓碑。
- 一个外部实体只映射一个 Task；实体的稳定身份与它挂在哪个看板、哪个位置分离，移动位置不会产生第二个 Task。
- 完成只有两个获准来源：有权的人从看板提交完成命令，或绑定契约的 Run 正常完成后由归约器机械提交同一个命令。两条路都要过 Task 自己的独立验收——Run 完成不等于 Task 完成，失败或被取消的 Run 更不能终结 Task。
- 任何适配器、Harness 或执行体都不能绕过完成命令写完成凭证，也不能冒充人或归约器提交。
- 重开是新的一轮：不复活旧凭证，也不让旧证明或外部重开静默决定新一轮施工。

## 无 Run 的轻量路径

```text
冻结的契约版本
  → 人工编辑，或一次有边界的 Room Invocation（从聊天室发起的单次调用）
  → 变更集 / 工件的新版本 + 测试证据
  → 有权的人在看板预览精确的评审对象与验收证据
  → 提交完成命令，通过独立验收
  → 写入完成凭证
```

这条路径的产品标尺是：走完它，必须比直接开一个终端、用单个 Harness 干完这件事更轻。如果在 HCTL 里完成一件简单事反而更重，用户就会绕开系统，承诺追踪随之失效；若简单工作必须先画一张施工图，那是产品设计的失败，不是用户的失败。

简单工作不需要先画 Workflow，也不伪造只能由 Run 产生的 Gate（评审关卡）凭证；契约要求 HCTL 内部独立评审时必须使用带 Gate 的 [Run](./run.md)，接受外部 SCM 评审时则引用可回读的精确外部证据。需要持久重试、候选切换或 Gate 时，Task 才显式授权 Run；第一阶段一个 Run 绑定至多一个契约版本，同一 Task 最多一个活动 Run。开工前必须把影响契约的外部变更摆到桌面上，明确采纳、拒绝或延期，不能静默越过——细则见[合同附录](./spec/task.md)。

## Kanban 场景

Kanban 是 Task 的主要操作场景，活在 Repo 级：一个 Repo 一个 Board，由注册仓库时选定的任务后端承载。板上三级结构直接可见：Project 是分组，Task 是卡片，子任务与清单归后端原生能力——在支持父子任务的本地任务服务器里，Project–Task 正好落为任务–子任务。卡片显示契约版本、来源、排序、负责人、阻塞、需要关注、活跃 Run、Request（请求卡）、Artifact/PR/CI、外部生命周期和 HCTL 验证状态。泳道是投影，不是生命周期。

卡片不只展示状态，还把后续动作显式化为可点的入口：返工、继续推进、追问、复核等，各自映射到拥有该动作的模块既有的类型化命令——追问对应 Request 创建，返工对应 Run 的返工路径，其余同理。它们不是往聊天里丢一句话，也不在合同之外新增命令。准备动作（环境、依赖探测）与真正的施工在卡片时间线上分开展示；模型的进度自述始终标注为参考信息。这些交互源自对成熟外部工具的验证观察，但在 HCTL 中一律置于契约版本、权限和凭证之下。

Board 不说谎：外部写回在确认前显示待同步，排队中的操作不显示假成功，乐观更新必须可回滚并始终标注不确定状态。两边分歧时如实展示双重状态——外部已关闭而 HCTL 未验证时，卡片保留最后有效的非终态泳道并标注“外部已关闭 · HCTL 未验证”；HCTL 已验证而外部写回未确认时显示“已完成 · 已验证 · 外部同步中”。

| 角色 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 场景客户端：Workbench Board | 查询、预览、拖放和类型化 Task 命令 | 用拖卡启动 Run，或把 Done 泳道当作完成事实 |
| 场景客户端：Local/CLI | 通过同一 command service 完整管理 Task | 绕过命令服务直接改治理账本或任务后端数据库 |
| content 系统：任务后端（本地任务服务器或 Linear/GitHub） | 承载任务卡、流转、排序、评论的 ground truth；原生界面可直接操作卡片 | 接管 Task 身份、契约版本、Run 绑定或语义完成——拖卡永远完成不了 Task |

移动卡片只改排序：排序归任务后端，用后端的并发令牌做前置校验，本地服务器与远端平台的令牌不混用；精确规则见[合同附录](./spec/task.md)。没有 Workbench 时，任务后端的原生界面可以继续修改 content 字段；复杂采纳、冲突解决和完成预览若无等价适配能力则安全暂停。

## 模块交接

以下只列所有权方向；字段、事务与故障语义由[四模块连接合同](./spec/connections.md)统一定义。

- [Project](./project.md) 的提案经采纳产生新的契约版本。
- Task 只通过显式的启动命令授权 [Run](./run.md)，移动卡片不会启动执行。
- Run 回传凭证、裁决和证据；绑定契约的 Run 只有正常完成时才由归约器提交同一个完成命令，Task 仍独立准入。
- Harness 产生的代码或终端状态只有经 [Agent](./agent.md) 模块封存为精确版本与证据后才可参与验收。
