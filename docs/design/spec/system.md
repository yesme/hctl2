# 系统边界与适配器约束

> 状态：规范性约束 · 草案 v0.18.4<br>
> 本文只定义五个模块共享的运行机制，不拥有 Project、Task、Run、Participant 或 Repo 的领域状态。

## 组件

| 组件 | 职责 |
| --- | --- |
| `hctl2-workbench` | 无特权的组合客户端；承载五个场景的 provider 交互、HCTL 公共命令入口、联合投影与导航 |
| `hctl2-control` | 唯一领域命令服务，负责路由、权限、控制面存储、outbox 和对账；内含 Agency 端口的适配代码，不实现 Agency 或终端会话服务 |
| `hctl2-tool` | [Repo 模块](./repo.md#对象)的现场执行者：物化和隔离 Git 工作树/ChangeSet，执行已持久化的面向本地目标的集成意图，回读结果，回读外部机械事实（CI 状态、合并状态、引用推进、路径与摘要）供节点准入与证据使用，并执行适用的写入互斥、封存和 Git 事实校验。它不负责 lint 或代码检查，不代其他模块保存治理正文；获准 Git 交付由持凭据单元执行，评审请求与平台合入由平台适配器执行。独立运行时，它只提供普通本地操作，不签发 HCTL 治理结果 |
| 本地 Agency 参考实现 | 发布包自带的 Agency，实现 Agency 端口：对控制面承担统一接入与租户隔离、执行资源供给、待交成果保管，以及「代为执行工具并直报」的能力声明；它内部选用的运行时只在[交付文档](../delivery.md#本地-agency-参考实现)具名 |
| workflow engine | 通过适配器保存 Run 的引擎执行令牌、引擎步骤、定时器、重试次数和执行历史 |
| chat server | 经 Chat 端口访问的聊天服务器（Matrix 协议）；承载 Room 消息 content 的 ground truth |
| task backend | 经任务源端口访问的任务后端（平台自带的 issues、本地任务服务器或远端平台，按仓库绑零到多个，缺省源由人显式选定）；承载任务卡 content 的 ground truth |
| SCM platform | 经平台端口访问的代码协作平台（外部的托管服务或自建服务器，或 control 托管的随包本地平台，按 Repo 绑定；显式不挂平台的 Repo 走受限路径）；承载评审线程、检查结果与合并状态 content 的 ground truth；平台适配器是 control 内的适配代码 |
| 第三方场景平台 | 可以同时提供场景客户端和受控端口；这两种接入分别绑定，任何一种都不会因此取得 HCTL 治理权威 |

## 固定内核与受控端口

固定内核是一个用户级命令服务；它对每个 Repo 保持独立的语义范围，而不是在每个仓库副本各起一套控制面；多个控制面对同一仓库各有一份语义范围，互不归并。固定内核实现五模块定义的稳定身份、Revision 准入、权限、字段权威、领域归约与 Receipt；本文件只拥有共享命令信封、扩展绑定、outbox/inbox、单写者和恢复机制。

换掉全部界面与供应端之后内核必须保留什么，[愿景文档](../vision.md#产品原生核心与架构最小内核)已经回答；本文只立它在系统层的精确约束。

可以替换的端口包括：

| 场景 | 端口 |
| --- | --- |
| Room | chat server 连接：消息/附件读写、账号与房间管理、身份映射（非 Matrix 平台经 homeserver 侧 Matrix 桥接接入，不是 HCTL 端口） |
| Kanban | 任务源端口读取、字段写回与快照 |
| Workflow | workflow engine 编译、注册、执行和回读 |
| Terminal | Agency 端口：要人、派工、输入、停止、观测、终端连接与票据校验；harness 与运行时在 Agency 门后 |
| Change | 平台端口：持凭据单元交付 Git 版本，平台适配器创建或更新评审请求、请求合并、写回记录，并为代取读取评审评论正文；检查、合并状态、评审请求头、线程与正式评审状态、保护条件由 `hctl2-tool` 回读为机械事实；能力声明与两层绑定见 [Repo 模块约束](./repo.md#平台绑定与能力声明) |

受控端口是替换供应端的唯一边界，不再增加跨模块通用适配层。每个 Port–Provider Binding 固定供应端制品、模块适配器、配置摘要、实测能力和降级方式。适配器只翻译本模块实际使用的命令、查询和事件，不把供应端私有对象提升为 HCTL 对象。新供应端通过本模块的契约测试后，只能用于新绑定；已有执行继续使用原绑定。迁移既有 content 必须另走显式的预览、导出、导入和回读校验。

### 客户端使用的公开面

Workbench 的 HCTL 功能只调用 Query、Preview、Submit、Subscribe 和各模块投影。供应端客户端功能使用供应端的公开协议或客户端传输适配器。Workbench 观察或接管某次派工的终端经 Agency 的公开通道，票据由控制面签发、Agency 校验。远程 Agency 与本地参考实现走同一个 Agency 端口；非 Matrix 聊天平台仍通过 Matrix homeserver 的桥接生态接入。

### 端点与输入的信任边界

1. 各服务缺省绑定本机回环地址或仅归属者可访问的本地套接字；接受非本地连接的必须认证客户端并按权限处理。参与者相关的交互由 Agency 统一接入：Agency 的公开端点是这一类交互的唯一入口，配对认证并按租户隔离；内部运行时不作为控制面或前端的直连入口，Agency 内部怎样跨主机连接由实现决定。前端到控制面、控制面到内容系统的认证各按其绑定，不由本条覆盖。
2. 若某个供应端修改必须先由 HCTL 记账、撤权或校验，只有 control 可以通过对应受控端口发起它。chat server 与任务后端的 content 读写不受这条限制；Agency 提供的普通交互输入也不是治理命令。
3. Agency 对本租户校验每次受管输入的 Attach Descriptor、Terminal Input Lease 与 Execution Spec 冻结的输入策略。绑定未声明逐次输入记录时，原生交互只能按来源不完整的运行时输入记录。
4. 若允许经 Agency 的原生客户端输入，绑定必须明确记录它不提供 HCTL 单输入租约保证，并如实声明来源。无论采用哪种输入模式，HCTL 结果都只能从 Result Proposal 准入。

本机代管是一种部署方式：由本机控制面按部署约定托管随包服务的启停、健康检查、备份与升级。托管不改变单元判据，也不是唯一形态；托管不授予 content 之外的任何权威，服务器进程的死活只影响对应场景的可用性，不改变治理事实；不因某个控制面退出或恢复停掉共享的 Agency。

每个扩展绑定都冻结代码版本、接口/schema、配置摘要、依赖、能力和信任级别；活动执行固定使用准入时的绑定。绑定的供应端不可用时，control 必须按该绑定冻结的降级策略暂停或终结活动执行。只有归属者提交显式替代命令后，control 才能创建替代执行。

control policy 只信任来自允许来源且摘要匹配的扩展制品。扩展或注册表的自我声明不授予信任。发现操作默认只读取已配置定义、本地安装和无副作用探测；联网探测只能由用户显式启用。安装与升级必须由用户显式提交，并产生新的 Extension Revision；后续解析再产生新的 Port–Provider Binding，活动执行继续使用原绑定。

跨模块可引用的扩展信息只有两个最小概念：

- `Extension Revision`：扩展稳定身份的一份不可变版本，固定代码/制品摘要、接口与 schema、依赖、声明能力和信任级别；
- Port–Provider Binding：一次已解析端口选择，固定 binding_revision_id、Extension Revision、供应端与安装实例、配置摘要、凭据引用、实测能力、权限作用域和降级策略。

同一端口种类和作用域在一次准入中只能解析出一个绑定版本，结果不得受加载顺序或界面选择顺序影响。Room、Task、Run 和 Execution Spec 都必须引用精确绑定版本。历史执行继续使用原绑定。凭据引用只指向 secret store 条目，不得包含密钥。

健康状态、重同步游标和当前成员列表属于运行时投影。每份投影必须记录来源、版本或序号以及观测时间，但不参与不可变绑定的摘要计算。它们可以阻止新准入或驱动对账，但不会改写历史绑定。只有端点、配置、能力、信任、权限或降级规则变化时，control 才创建新的绑定版本。

Skill 的定义、三态与申报规则见 [Participant 模块约束](./participant.md#skill-与申报)：Skill 的内容由 Agency 安装并申报，Execution Spec 与 Run Manifest 冻结的是申报的精确 ref+digest 及其可核验性。

进程内扩展等同受信任代码。普通独立进程只隔离崩溃；不可信扩展必须使用操作系统强制隔离和能力削减的代理接口。

## 场景端口

所有 HCTL 命令客户端共享四类操作：

```text
Query(filters, cursor) -> Projection
Preview(command draft) -> Effect summary + preconditions
Submit(typed command) -> accepted result or typed rejection
Subscribe(cursor) -> ordered events or resync snapshot
```

客户端只能声明自己的交互能力和降级方式，受控端口只能报告供应端能力。字段写入权由对应模块的绑定授予。外部平台可以拥有场景 content 和明确授权的字段，但其 thread、Issue、workflow task、Session 或 pane 不自行授予 HCTL 身份、授权或判决；平台仓库稳定标识是人声明的 Repo 绑定字段，见 [Repo 注册](./repo.md#repo-注册)。

界面控件本身没有固定语义：同一个拖放可以只是 Task content 移动，也可以在进入 Done 时产生一个 human 完成请求；终端输入推动某次派工，不是领域命令。具体分类见下一节。若某个动作必须提交 HCTL 命令，而客户端无法提供等价的预览、版本或权限信息，客户端必须禁用该动作、保留待处理请求或返回安全拒绝。

## 客户端动作与 provider 事件

control 不根据“来自哪个产品”判定动作——客户端没有等级是愿景层的产品承诺（见[设计原则](../vision.md#设计原则)）——而根据动作落点和可验证信封分成以下几类：

| 类别 | 例子 | control 怎样处理 |
| --- | --- | --- |
| content 写入与观测 | Matrix 消息；Vikunja 创建、编辑、排序、非终态移动；代码协作平台上的评审评论与目标更新 | provider 先拥有该 content；control 按 cursor/Snapshot 对账，按模块约束更新投影或建立无契约身份，不把 content 直接当治理事实 |
| human 命令请求 | Workbench/CLI 的类型化提交；已配置的 Matrix 结构化动作；绑定卡片进入 Vikunja Done | 归一到同一个 HCTL command draft，按同一准入规则处理；危险动作（不可逆、产生外部权威副作用或扩大权限）默认先经 Preview 确认，普通命令可直接 Submit；须临场选择、危险动作未经确认或绑定未允许该来源自动提交时，保留为待处理或返回类型化拒绝 |
| 运行时输入 | Workbench Terminal、Agency 的原生客户端或其他终端客户端经 Agency 向自己的派工输入 | 立即推动该派工；按连接票据、租约和 Agency 声明的能力记录恢复等级，但不因此产生 Task/Run/Project 结果 |
| 执行结果提案 | harness/Agency 的结构化终局事件与证据 | 只进入 Result Proposal；归属模块按版本、代次和证据准入 |
| 不支持的供应端修改 | 直接在 Dagu UI 启动、停止、重试、批准，或改写已绑定执行 | 记录当前机械事实并标记绑定分歧；不倒推一条 HCTL 命令，也不补签 Receipt |

供应端事件先按 content 事实入账。只有事件能证明 actor、目标、前后版本和幂等依据时，Task 适配器才可以另行生成“完成 Task”请求。请求被拒绝时，界面同时保留供应端 Done 与 HCTL 开放状态。由 HCTL 回写产生、actor 无法映射或字段不全的事件只能形成 Snapshot。

授权模型是单用户的：只要求把直接客户端连接或供应端账号稳定映射到归属 human，并保留直接客户端（`direct_client`）、供应端事件（`provider_event`）、内部归约器（`internal_reducer`）、执行主体（`execution_principal`）或未知（`unknown`）来源；不引入组织、角色层级或复杂 RBAC。来源简化不等于可以丢掉目标、预期版本或代次、幂等键和事件顺序。

webhook 和通知只负责唤醒。接纳前仍以供应端当前回读、游标及其缺口和模块 Snapshot 为准；重复、迟到或乱序投递必须得到相同结果。各模块可接受的供应端动作见[场景与第三方适配器](./connections.md#场景与第三方适配器)；代码协作平台的批准、请求修改、评论与合并按钮的逐项去向见 [Repo 模块约束](./repo.md#平台动作与命令)，平台上的批准不是 Gate 的一票，「已合并」通知不是事前授权。

## 命令与跨服务正确性

改变事实的命令至少携带：

```text
command_id / idempotency_key
actor principal + actor source/provenance + permission scope
target stable ID
expected revision or state version
frozen adapter binding
canonical input digest
```

actor 来源只能由直接客户端连接、绑定中的账号映射或 control 内部归约器赋予。治理命令只接受两类来源：可映射到归属 human 的动作；以及 control 归约器发出的内部命令——它只能执行已冻结规则的边或已有 human 授权的后续动作：绑定 Task 的 Run 正常完成后的「完成 Task」命令、Workflow Revision 冻结的 Gate 通过后的「合入 ChangeSet」命令、注册确认后创建 Repo Room、按 Execution Spec 冻结的评审发布策略在版本获准后发出的「发布评审」命令（见 [Repo 模块约束](./repo.md#发布评审)）。内部命令的 actor 信封沿用授权它的那次 human 提交或冻结规则的引用，不构成第三类来源；执行体的 Result Proposal 只提供策略允许的内容，不能触发发布。普通 Room 的临场扇出只接受有权的 human actor；workflow 归约器只能实例化 Workflow Revision 已冻结的边。Harness、模型和执行主体只能提交 Result Proposal，不能自报为 human。

control 必须在同一个 SQLite 事务中写入领域事件、幂等结果和 outbox；跨模块命令也只能使用这一个事务边界。外部适配器使用同一幂等键投递并回读；结果未知时不得盲目重做。重复命令返回原结果，异载荷复用同一幂等键时必须拒绝。

**多写通则。** 别人的写入是事实，不是本控制面的命令，也不因出自别人就违规。它可以触发本控制面重核冻结前提、进行验收或形成请求；能否作验收证据由本控制面的契约事先声明，批准和完成仍由本控制面自己判，控制面之间不加锁。Repo 对共同平台事实的处理见[平台动作与命令](./repo.md#平台动作与命令)，任务后端实例见 [Task 约束](./task.md#契约与来源)，Agency 实例见 [Participant 约束](./participant.md#派工与观测)；控制面存储的多个前端仍经同一个逻辑写入者，不是多份治理写权。

组件不可用不会改变命令前置条件：不依赖该组件当前事实的命令可以继续，依赖当前回读的命令必须拒绝。只有冻结策略明确允许陈旧证据时，命令才能携带证据版本、观测时间和已知缺口继续。

Receipt 证明的是已经校验的结果，不是另一个 writer。投影从事件重建；缓存和界面状态保持为派生数据。

跨模块引用的规范摘要统一使用 RFC 8785 JCS 规范对象的 SHA-256，摘要字段自身不参与计算。每个领域归属者只定义自己规范对象包含哪些字段。完整 Revision 的 revision_digest 与为评审选取字段生成的 review_subject_digest 是不同语义，分别按各自语义使用，与某次字节是否相同无关。

## 外部权威副作用

包括远端 SCM 在内，会改变第三方权威事实的动作统一写成持久外部副作用命令和 outbox 记录。记录固定归属者引用、Port–Provider Binding、操作、目标、适配器声明的冲突范围、权限、规范输入摘要和幂等键。同一远端资源的关闭、重开、更新等操作共用一个冲突范围。

被治理仓库的 Git 封存与目标更新属于 Repo 的外部副作用：control 先持久化意图和 outbox，`hctl2-tool` 或持相应权限的执行方再执行和回读；治理正文保存属于控制面自己的存储，按下节保存与准入顺序处理，不经 Repo 副作用路径。Harness 和模型不直接取得集成权。适配器只投递并回读。代码集成与发布评审的意图、目标、授权形态与 Receipt 由 [Repo 模块约束](./repo.md#集成目标两个头与两种授权形态)定义；发布评审的授权来源是归属者 Execution Spec 冻结的评审发布策略，不是执行体的请求。只有适配器确认目标、版本和结果后，control 与 `hctl2-tool` 的校验事务才能写成功 Receipt。投递超时或确认回执丢失时，结果保持未知，并继续占用本控制面内的冲突范围以阻止自己的重叠写。Harness 的窄执行主体、凭据与独立 Git 工作树边界见[Participant 写入约束](./participant.md#写入约束)。

系统不承诺自动补偿任意外部写。供应端事件只有在对应模块明确列为 content、human 命令请求或运行时输入时，才按相应路径处理；其余修改由对应端口或 `hctl2-tool` 回读为 Snapshot，是否产生分歧或阻止命令按该模块的冻结前置判定；平台上的合法合入不因没有本控制面意图就被禁止。

模型不取得通用 human/control 凭据或集成权；获准源分支的 Git 交付与平台操作按 [Repo 发布评审](./repo.md#发布评审)分工。目标被别人更新后，预期目标头形态核预期值，接受目标前移形态核精确源版本、保护快照和其他前置，不把前移一概判为分歧。外部观测提供事实，Artifact、Verdict 与 Receipt 仍由对应归属者按约束产生。

## 事实与存储

### Repo 与执行现场

Repo 的登记与平台绑定由 [Repo 模块](./repo.md#repo-注册)拥有。参与者负责工作环境与工作副本，控制面负责它发出的任务与授权、接受的版本和获准目标更新。跨单元只交付履约所需的信息，不要求公开内部目录布局，不登记通用现场对象。资源管理方落实相互冲突写入的互斥、旧写者停止或隔离及独立引用不相交；共享对象库不要求整体串行，条件见 [ChangeSet 与 Git 事实](./repo.md#changeset-与-git-事实)。

| 操作 | 必要引用与核对 |
| --- | --- |
| 派工 | 任务、基线、权限、预算与执行归属；保留派工引用与语义归属者，不要求生产目录 |
| 封存与交付 | 精确成果、基线、生产者（执行或人的显式命令）、适用租约与证据；现场工具可用本地路径，跨单元不以路径代替成果身份 |
| 更新平台目标 | 冻结平台绑定与目标 ref，按两种授权形态核源头、目标头与保护条件 |
| 更新无平台本地目标 | 冻结供应端提供的目标引用与 ref，供应端须证明它仍是获准目标；只属于本次操作，不成为通用资源对象 |
| 恢复待决更新 | 写入前目标无法解析或不匹配则拒绝；可能已写但确认不足则保留原意图、目标与冲突范围，回读前保持结果未知 |

生产目录或对象库改变不自动改变授权；供应端重新核验适用的写入隔离和引用冲突。涉及待决目标时，另须证明原目标连续性；能证明连续则可换存放位置，同一路径重建 clone 则不能凭路径证明连续。

### 控制面自己的存储

控制面存储分两半，由同一个逻辑 control writer 管理：

- **治理记录**：稳定身份、绑定、授权、准入、版本与当前指针、租约与代次、幂等结果、inbox/outbox，以及 Verdict/Receipt。当前指向和批准随事务推进，不从正文后端的分支或索引反推。
- **治理正文**：已保存的不可变契约、施工图、Memo、共享 policy/schema 等材料。它们是控制面的持久资产；材料的存储不是新的 Repo、Project、Room 或 content 服务。代码与 ChangeSet 的 Git 字节仍在被治理仓库，Artifact 按登记用途指向代码或材料。

物理布局与后端在[交付文档](../delivery.md#技术基线)确定，不是对外 API。系统不默认在代码树跟踪 .hctl2/ 治理目录；人有意发布的项目文档、AGENTS.md 与工具配置照常保留。未公开治理材料不随代码 ref 推送；人直接编辑材料 Git 也只产生候选，须经对应模块的预览与准入才能生效。

材料存取有四个动作，复用既有引用与命令，不新增领域对象：

| 动作 | 保证与边界 |
| --- | --- |
| 存入 | 返回可恢复的精确正文定位及摘要前，字节须已持久保存；相同字节可去重，保存不代表准入 |
| 取回 | 按精确引用返回字节并核摘要；不存在、不可达、无权和摘要不符分别报告，不用当前版本顶替 |
| 列版本 | 从治理记录列出该对象的版本、准入及取代关系；后端日志、候选和索引不能冒充获准历史 |
| 交付 | 按材料集合、接收者与用途检查权限，交付后核验实际字节；本地可读或只有摘要不等于异机已收到 |

既有材料引用及 Manifest 条目须能稳定解析到所属控制面、材料范围与不可变内容；范围可由绑定隐含，但不能缺失。引用记录所承诺字节的摘要，领域对象另保留精确 Revision、版本关系与规范摘要。摘要不是地址或读权；后端迁址不改变冻结引用与摘要。正文摘要、完整 revision_digest 与 review_subject_digest 按各自规则使用，不能以 Git 对象编号、原始字节摘要或后端地址互换；同样字节可以对应不同领域版本。

保存、准入、交付按三个阶段进行：

1. **事务外保存**：在相应权限下保存精确字节与可恢复定位，保护候选直到准入决定完成。
2. **事务内准入**：重新核验权限、预期版本与适用代次，在同一控制面事务提交准入、定位与摘要、领域版本及当前指针、幂等结果和必要 outbox。旧版本、失权写者或失败事务留下的候选不算获准。
3. **事务后交付**：镜像、跨单元投递与外部写回按持久记录重试并回读。镜像失败不阻止已完成的本地保存与准入；必需交付尚未确认时，不冒充交付成功。

同一命令重试返回同一领域结果；正文按字节去重不能代替命令幂等，Git ref 事务也不是记录与正文之间的跨库事务。失权写者不得推进治理记录或删除仍受保护的正文；同一逻辑写者不要求所有字节写入都在同一个进程内。

候选待准入、待交付、在读快照与按保留策略仍可引用的历史都受保护，不能仅按当前指针回收。四个故障窗口分别处理：保存后未准入便崩溃，按原命令恢复候选；准入已提交而响应或镜像丢失，返回原结果并继续交付；记录在而字节或定位丢失，依赖命令暂停并显式恢复，不能编造正文；保存到准入之间回收，受保护内容不得删除。

锁、索引与可重建缓存可丢弃；尚未被接收方保全的唯一结果不是缓存。结果发送方保管精确产物与证据，直到接收方确认同一版本的字节已保全；摘要相同或指针已送到都不够。临时工作树可在精确成果另有可恢复副本后清理，不要求原进程仍活着。Context Bundle 的原文保留到归属者终态且 Result Proposal 准入窗口关闭，之后保留引用、摘要、来源、策略与丢弃事实，不假称可重放，详见 [Project 约束](./project.md#根-context-manifest)。

控制面只保存自己的领域关系与跨系统锚定，不复制供应端内部完整拓扑。密钥仍进系统 secret store，不进 Git、Room 或 Context。用户级 Profile/Skill 定义仍以精确 revision/digest 引用，当前指针经唯一写者的预期版本校验推进；活动执行不随当前指针变化。

### Git 的双重角色

Git 承载两种职责，放置、权威与交付分别按[架构原则](../architecture.md#单元与连接)理解：

- **被治理仓库的代码**：工作副本、提交与 ChangeSet Revision 由参与者一侧保管、由 Repo 模块校验并准入获准版本。平台只拥有它承载的目标与评审记录，不因此拥有未交付的本地字节。
- **控制面治理材料的后端**：保存不可变治理正文与判决审计副本；记录、批准与当前指针的权威仍由 control 在治理记录中维护，Git 中出现候选、提交或副本都不代表准入。Git 的版本记录不能代替治理版本史。

Verdict/Receipt、Run Manifest、Execution Spec、绑定、租约、代次和 Result Proposal 准入的权威在治理记录中；保存它们的审计副本不会产生第二权威。副本不默认随代码 clone 分发；向平台发布精确版本的审计关联及可见范围见 [Repo 发布评审](./repo.md#发布评审)。从材料副本可恢复所保存的字节，不能恢复未被保存或已丢失的授权；审计候选仍须经显式恢复确认。

## 单写者

用户级控制面存储「只允许唯一写者」的约束只有三条底线：同时只有一个逻辑 control writer、已确认副作用不重复执行、旧结果不覆盖新结果。当前实现先取得 `~/.hctl2/control.lock` 排他锁，再以 CAS 推进其 `control_writer_generation`——锁路径与推进机制是实现细节，不构成对外约束。writer 可以搬迁（换机器、上服务器），存储身份不变。不存在 Repo 级或 Project 级的第二个 control writer。

工作副本的互斥与旧写者隔离由管理资源的一方落实；控制面只核适用租约与证据，不取得全部 clone 的排他权，见 [Repo 与执行现场](#repo-与执行现场)。

Agency 为每个配对的控制面提供一个隔离租户：独立的派工命名空间、会话、工作副本、凭据作用域、观测流与待交结果。控制面的配对连接只到自己的租户；一次派工只属于一个租户，租户只接受它的控制面的动作；另一控制面的读取、订阅、输入、取消、结果收取在结构上不可达，不设门口逐次核对动作是谁发的。租户之间没有共享端点可“归属”，不设 Agency 端口的归属者租约。控制面恢复时推进自己的 `control_writer_generation` 并通知自己的各租户此前发出的动作作废，租户拒绝旧写者的延迟动作。租户之间可以共享显式声明的公共资源（如同一台机器上的 Git 对象库），共享的规矩是引用不相交与写租约；共享存储不等于共享会话、凭据或结果。

control 在派工、输入和停止前校验适用的语义归属与自己的写者代次，Agency 对本租户校验票据与租约；Git 写入另须有 Agency 给出的旧写者已停止或已限制在旧边界内的证据，不能以入口拒收代替物理隔离。

SQLite 事务只保证治理记录内部一致，不能连同正文后端或外部投递一起原子提交。治理正文按[保存与准入顺序](#控制面自己的存储)处理；外部副作用仍由幂等键、代次、租约、outbox 和回读共同隔离。

单写者、CAS 与 current pointer 是三件事，不互相替代：单写者回答此刻谁有权写控制面存储（本节）；expected-version CAS 回答一条命令对哪个版本生效（见[命令与跨服务正确性](#命令与跨服务正确性)）；current pointer 回答界面此刻读哪个不可变版本（推进规则由各模块写入约束定义）。ChangeSet 的单 writer 是 Repo 模块的 Write Lease（见 [Repo 模块约束](./repo.md#changeset-与-git-事实)），不属于 control 单写者。

### 代次家族

全系统共有三个代次（generation）：同族——都单调递增、旧值失权——但不同槽，各管一块资源，不得共用一个字段，也不得从彼此推导。

| 成员 | 管哪块资源 | 权威定义 | 何时产生或推进 |
| --- | --- | --- | --- |
| `attempt_generation` ／ `invocation_version` | 这一次逻辑执行归谁（语义归属者） | [Run 约束](./run.md#对象)、[Project 约束](./project.md#room-invocation) | 派发时已有；不得预填派工引用 |
| `control_writer_generation` | 用户级控制面存储此刻的逻辑写入者 | 本节 | 取得控制面存储写权时 CAS 推进；恢复时通知自己的各租户，旧写者的延迟动作被拒绝 |
| `engine_binding_generation` | 某次 Run 与引擎 execution 的绑定 | [Run 约束](./run.md#从节点到结果) | 启动、关闭或标记分歧时推进；走 Run↔引擎连接，不进派工元组 |

两条推导规则彼此独立：

- `control_writer_generation` 不能从任何归属者代次推导，它只随控制面写权推进；
- `engine_binding_generation` 不能从 `attempt_generation` 推导，因为引擎重试与候选切换是两条独立的换代路径。

派工引用不是代次：它标识控制面对 Agency 的一次委托，新的尝试是新的派工。Agency 门后换进程、会话或主机不是代次，控制面不记录。Result Proposal 必带的语义代次与派工引用见[连接约束](./connections.md#project--run--participant从授权到派工)。选入记录版本、binding revision、producer sequence 与 content cursor 都不是代次。

## 启动与恢复

恢复顺序固定为：

1. 取得自己的用户级 control 写权，不取得工作副本或 Agency 内部资源的排他权；
2. 打开控制面存储、验证 schema，恢复 inbox/outbox/租约，CAS 推进自己的 `control_writer_generation`，并通知自己的各租户此前发出的动作作废；
3. 回读已绑定 content 系统的游标（chat server、任务后端、代码协作平台的评审请求状态与 webhook 游标、workflow engine）与未确认副作用，并向自己的各租户取本控制面派工的观测与待交结果，不读别的租户或 Agency 的内部资源目录；
4. 查询 workflow engine、`hctl2-tool` 回读的 Git 事实与平台机械事实（评审请求当前头、合并状态、检查、保护条件）；结果未知的集成与发布意图按 [Repo 模块约束](./repo.md#恢复)分目标处理；
5. 将自身派工与待决动作分类为运行、等待、联系不上、丢失、被替代或结果未知；Agency 内部的孤儿资源归 Agency，不在此列；
6. 阻止本控制面已失效授权继续执行，只按原意图回读或重放可证明幂等且仍获准的动作；
7. 相关授权与冲突范围对账完成后才授予自己的新写入或输入租约，不等别的控制面或与该动作无关的结果。

UI 重载只重建投影。Agency 暂时不可达不等于执行身份已丢失，也不触发控制面重建其目录；能证明原执行身份时沿原授权对账，语义归属者或租约确实不能证明才按[连接约束](./connections.md#失败与恢复)处理。

恢复分别核五种情形：控制面重启而 Agency 正常，核原授权、派工与待决动作，不停止别的控制面的执行；Agency 重启或不可达，向自己的租户取适用派工的观测与结果，门后的工作区由它自己恢复；执行已结束、结果待交而控制面恢复旧备份，核原授权及既有处理结果，缺依据则显式恢复，不要求原进程或临时树仍在；集成可能已写时按原目标与意图保持未知，人的封存待准入时按原命令与候选恢复；换机器或重建 clone 时区分生产位置变化与待决目标连续性，不接收全套目录状态作为恢复条件。成果保管见[控制面自己的存储](#控制面自己的存储)。

### 备份与恢复

控制面备份必须由唯一写入者协调为一致备份集：同一治理记录快照，加上它承诺可取的全部精确治理正文、定位关系，以及所引用的精确用户级 Profile/Skill 定义与公开冻结配置的字节与摘要。多出未准入候选不影响完整性，少了已承诺的字节不算成功。密钥值、可丢弃缓存、PTY 原始流、各场景 content 与 Agency 内部的运行与安装定义不因此成为该备份集的一部分。

完成前验证快照边界、全部材料与定义的可达性和摘要及 schema 可读性；镜像不是一致备份的替代品。材料 Git 冗余仍能恢复精确字节，但不能推导丢失的准入或授权。Repo Git、平台数据库及其 Git、其他 content 系统和 secret store 分别备份，恢复缺项不得以伪造 Receipt 补齐。

恢复要求旧写入者已停止并取得用户级排他写权，不合并分叉控制面存储，不改变存储身份。恢复同时保护记录与正文，推进自己的 `control_writer_generation` 并通知自己的各租户，使旧票据、输入租约、outbox 执行权失权；未确认的意图与结果及其关联记录保留，已完成而待交的结果先核原授权与既有处理、再判能否准入，不因写者接替一律封死旧结果；再按原意图回读未知副作用。不推进一个通用现场代次，也不接管 Agency 的内部目录。

密钥引用仍在但值缺失时，对应绑定标为不可用并阻止依赖命令；系统不得把空值当凭据或静默降权。

## 安全边界

- 桌面壳 WebView/renderer、Web 内容、终端转义序列和外部消息都视为不可信输入。
- 打包后的桌面壳固定最小权限面，WebView 只暴露具名 typed command：Tauri 2 按 window/webview 以 capability/permission/scope 显式声明，不开放未声明的 IPC 与插件能力；以 Electron 安全网形态发行时固定 `nodeIntegration=false`、`contextIsolation=true`、sandbox=true，narrow preload 不暴露 raw ipcRenderer。禁止远程运行时脚本/CDN，CSP 拒绝远程或未声明的可执行来源。
- 文件、Git、网络、凭据和进程能力由 control 与 `hctl2-tool` 授权，不交给渲染器。
- 敏感输入不进入 Room、日志、Context 或终端回放。
- 日志与 trace 使用稳定关联 ID，但不得包含密钥和完整敏感 payload。
- 人对 HCTL 的授权模型是单用户的；Agency 必须隔离每个配对控制面的租户，未启用某项可选加固不放开另一租户的输入、结果、文件或凭据。Harness 的三条底线与可选执行加固见[Participant 写入约束](./participant.md#写入约束)。未启用某项可选加固时，如实说明该租户内模型与工具的隔离强度未验证，不宣称未验证的隔离；跨租户隔离不因此放开。
