# 文档纪律

> 状态：规范性（写作协议）· 草案 v0.15.6<br>
> 日期：2026-09-02

本文管 `docs/design/` 的**内容与权威**——谁定义什么、去重、引入门槛、修订与审计规则。**文风与结构**（分层词汇、句式、术语混排、翻译腔、压缩下限）见根目录[写作指南](../../WRITING-GUIDE.md)。它原是[设计地图](./README.md)内的一节，2026-09-02 独立成篇：写作协议的读者是写文档的人，不该挡在读产品文档的人的路径上。

为避免再次形成补丁链，后续修改遵守以下硬边界：

- 分层写作：每层的允许词汇、文风与验收标准见写作指南的四层路由表；实现名（字段名、锁路径）不进设计文档。`delivery.md` 是验证文档，可引用约束层词汇以指认被测的约束条款，但不得重定义。
- 只有约束层的四个模块约束可以定义模块特有的领域名词、状态、写入者和不变量；设计正文与场景不得重定义它们。
- 具名概念的引入门槛与族规则见[约束层总则](./spec/README.md)：没有独立生命周期、恢复边界或权限边界的不得命名；场景概念优先对齐外部标准，不重复造轮子。
- 说人话：自然中文；中文语境不常用的音译行话必须翻译。专有名词保留英文，中文对照分两种：有自然译名的（仓库、看板、参与者、上下文、施工图、裁决、凭证、技能包、工件、备忘），每个文档第一次出现时给对照；只有释义式说明的（Task、Run、Agent、Workbench、Seat、Obligation 这类），在[术语对照表](./references/glossary.md)定义一次即可，正文不要求括注。（所有者裁定，2026-09-02）
- `vision.md` 只回答“为什么、什么体验、按什么原则取舍”，不定义对象、状态或命令；与约束冲突时以约束为准。愿景、论证与体验叙事不因篇幅或“与约束重复”被删除——权威去重针对约束，不针对解释。
- spec/connections.md 只定义模块交接，spec/system.md 只定义共享机制，delivery.md 只定义范围与验证，证据文档只记录来源。
- 一个概念只在拥有它的模块完整定义一次；其他文件用链接和可观察结果引用。
- 新持久对象必须对应第一阶段中的稳定引用、命令目标或恢复边界；否则先作为实现细节。
- 精简只针对重复权威、无第一阶段用途的对象和补丁衍生对象；能够回答独立实现选择、交接、故障或权限边界的设计不得因篇幅被删除。
- 新持久对象必须说明现有命令、引用或事件为什么无法承载该边界；若同一规则需要在多个权威位置同步修改，先选定唯一权威出处，再把其他位置改为引用。
- 审计只针对稳定快照，最多两轮；第二轮若主要发现第一轮新增概念造成的问题，则回滚而不是继续打补丁。
- 来时路只记录转向：核心边界移动、实现选型更换、权威归属变化各自成章；词汇、词形与概念清扫类修订进[小修订台账](./references/decision-history.md#34-小修订台账)一行，细节在来时路核销表或专题过程稿。每记录一条改变约束的转向，基线版本至少推进一个补丁号。

发生冲突时的裁决顺序：四个模块约束解释连接端点，[连接约束](./spec/connections.md)解释交接，[系统边界](./spec/system.md)解释共享执行机制；`delivery.md` 不得改变领域含义，实现证据不得反向定义产品。
